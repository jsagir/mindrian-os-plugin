# Open UI/UX Decisions -- 10 Forks for the Design Team

The meta-decision underneath all of these: **MindrianOS has been running on a CLI-born visual system that is now spreading onto a browser wiki, a live dashboard, HTML presentations, and a SnapshotHub export.** Do we stretch the terminal system onto screens, or design a proper screen system of which the terminal is a strict subset? Settle that first; the rest follows. (Note: this is *aesthetics/design-language* territory -- per `07`, the user evidence is on *legibility*, not aesthetics, so several of these are "don't over-invest until a tester hits it.")

| # | Decision | The fork | Tension | Recommendation |
|---|---|---|---|---|
| **1** | One visual system or two? | Phase 121.5's canonical `palette.json` unifies "dark De Stijl" + "light PWS" into one system with a light/dark axis -- OR we keep two deliberately different brands (tool vs presented artifact). | Unification = consistency, less maintenance, stronger brand. Two themes = the deck can be warmer/more client-facing. | **One system, light/dark axis.** Two themes always drift. |
| **2** | How literally does De Stijl translate to a content surface? | De Stijl is the *chrome* (headers, nav, infobox, footer, dividers) around a clean readable body -- OR it invades the body too (colored block paragraphs, grid-locked columns). | Brand distinctiveness vs. readability of a 2000-word section page. | **De Stijl owns the chrome and structural furniture; the reading column is quiet.** Document it or every page is a fight. |
| **3** | Typography pairing -- confirm or extend? | Bebas Neue (display) + system-ui (body) as-is -- OR add a third face for long-form wiki body (and maybe a mono for graph labels). | A 2-font system is cleaner; a dense wiki may need a real reading face. | **Decide explicitly; produce a primitive->semantic->component type scale** covering CLI / dashboard / wiki / deck. |
| **4** | Color budget vs the graph's semantic load | The graph encodes ~9 edge types + multiple node types by *line style / weight* inside the 5 colors -- OR the graph gets a sanctioned palette extension the rest of the system doesn't use. | Palette purity vs. graph legibility -- and the graph is the moat surface. | **Line-style + weight inside the 5; break glass only if user testing says unreadable.** (= C7.) |
| **5** | Red-link / interaction-state colors | Red-link = Mondrian red from the palette; produce a full states matrix (default / hover / active / visited / disabled / focus) x (link, button, selector option, graph node) x (light, dark). | Wikipedia red-link convention collides with browser-default link-red. | **Produce the states matrix.** No defaults; everything from the 5. |
| **6** | The Decision Gate (Shape F) as the universal interactive primitive | Design all three renderings of the same primitive: keyboard-driven in the terminal, HTML in the wiki/dashboard, *conversational* on Desktop. Specifically: the tri-context (LOCAL / BRAIN / SIGNAL) strip as HTML; the RECOMMENDED marker visual; the `?`-inspect panel; how "pick verb 3 of 5" degrades to a Desktop chat turn. | This is the highest-leverage component in the product -- every interaction routes through it -- and it currently has a roadmap hole (C6). | **Spend the most design time here.** It is also the #1 priority in `07`'s tester-grounded ranking. |
| **7** | Three-surface adaptation matrix | Design the Desktop prose-state-echo (currently exists but under-designed) and the Cowork widget. What's the minimum-viable state surface when you can't draw a statusline? | Features keep getting "designed for CLI only." | **Produce a one-page matrix** -- feature x surface x rendering treatment. |
| **8** | 12-glyph vocabulary -- frozen or revisable? | (a) revise glyph choices, (b) commission SVG variants for the browser, (c) decide whether the set is *complete* (glyph for "in progress" vs "draft"? "deferred"? "rejected-with-reason"?). | The set leaks (C5, the stray-`✗` incident); the no-emoji rule is the founder's with one carve-out. | **Confirm completeness, ship SVGs, add a CI linter.** (Linter is in `08`'s Phase 121.5 scope.) |
| **9** | Motion / interaction language | Functional motion only (state changes -- expand/collapse, loading) -- OR a geometric "block reveal" decorative language. | De Stijl is static, geometric, anti-decorative; a wiki page that animates feels off-brand fast. | **Functional only.** Rule on it explicitly. (No tester evidence either way -- don't gold-plate.) |
| **10** | Dashboard + SnapshotHub -- keep, refine, or redesign? | (a) dashboard redesign or just a polish pass; (b) SnapshotHub = the *same* renderer as the live dashboard or a presentation-grade variant; (c) is the 6-view set (dashboard / wiki / deck / insights / diagrams / graph) right, and do they share one language or does "deck" differ (see #1)? | The dashboard is locked "until a new UI/UX is designed" -- a standing invitation. SnapshotHub is the artifact users hand to outsiders. | **Park most of it** (no tester evidence) **except SnapshotHub** -- design it for the "credible to outsiders" job (Gary's evidence in `07`). |

## Priority order (the order matters)

**1 and 2 are load-bearing** -- settle those and most of 3-10 fall out. **6 (the Decision Gate)** gets the most design hours regardless -- it's the one component every interaction routes through, and the only one with strong tester evidence behind it. See `07` for the full tester-grounded priority list.
