## Conflicts with the plugin plan

C1. Plan 387-03 sync is `uv sync --locked --extra mcp-server`, with `--extra modern-encoder` on request. But `uv run` for decision routes adds `--extra hmm`, and `pomegranate==1.1.2` has only an sdist in uv.lock (build needs a compiler and numba/llvmlite, 60 MB). A hmm route offline would try to install it and fail. The plan has no sync step for hmm.
C2. The sync grant lists 3 hosts. A uv that finds no Python 3.11 or newer would fetch a managed Python from github.com. Plans say "check-and-explain" for Python, but `uv sync` itself may download one unless `--no-python-downloads` is passed. The grant card then misstates the hosts.
C3. `uv sync --extra modern-encoder` gives libraries but no model weights. Every MCP route loads with local_files_only. So after the one granted setup, the scout, hsi and analogy routes still fail with "No local model found." The plan says "offline after one granted setup" and treats encoder routes as ready. That holds only for graph routes.
C4. Plan 387-06 forces UV_OFFLINE=1 on every route. A child `uv run` with an extra that was not synced (for example modern-encoder after an mcp-server-only sync) must install it, so it fails offline with only `engine_unavailable`.
C5. The plan treats the engine as a read-only checkout ("adopt"). But `uv run` writes `.venv` (and possibly uv.lock) into the engine folder, and the engine keeps `jobs.sqlite3` and `embeddings.sqlite3` under HOME even for graph-only calls. The plans mention only the two HOME folders for the engine's output in some places and "one small file" for the plugin.
C6. Plan 387-07 doctor point treats `.venv/pyvenv.cfg` as "environment prepared". It does not show which extras are installed, so a green check can still end in C4.
