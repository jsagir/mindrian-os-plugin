# Slice A -- A -- local graph schema (SQLite room.db): edge temporality, node temporality, and the legacy facts table

Verdict: **REFUTED**

## Current State

The local per-room graph lives in room/.mindrian/room.db (node:sqlite DatabaseSync, WAL, FK on). Two schema authors compose it: lazygraph-ops.cjs initSchema() creates the base nodes + edges tables, and memory-ops.cjs initMemorySchema() creates the memory tables (identity, facts, sessions, fragments, assumptions, plus log tables). room-db.cjs runs lazygraph.initSchema then memory.initMemorySchema then the Phase 109 migrations.

EDGES: The edges table is purely structural with NO temporal columns of any kind. It is defined once in initSchema as (source, target, type, properties JSON) with composite PK (source, target, type) and FKs to nodes(id). No migration ever ALTERs it -- grep for "ALTER TABLE edges" / "edges ADD COLUMN" returns zero hits across the whole repo. Every edge-creator (createAnalogyEdge, createCascadesToEdge, upsertEdge, etc.) writes only the JSON properties bag; any time-stamping that exists (e.g. linkDiscoveryCycleSource stuffing cycle_timestamp into properties JSON) is ad-hoc inside the opaque properties blob, not a queryable temporal column. There is no valid_from/valid_to, no transaction-time, no soft-delete column on edges. Edges are immutable-or-overwritten via ON CONFLICT(source,target,type) DO UPDATE -- a re-assertion clobbers the prior properties in place with no history.

NODES: Node temporality is carried by Phase 109 as a review_status ENUM plus uni-directional timestamps, NOT a closeable bi-temporal range. The phase-109-nodes-provenance migration adds 9 columns and then re-creates the table with NOT NULL + CHECK constraints. The temporal/state surface is: review_status TEXT NOT NULL DEFAULT 'proposed' CHECK IN ('proposed','confirmed','rejected','stale','superseded','needs_evidence','validated','invalidated'); created_at INTEGER NOT NULL (epoch ms); last_seen_at INTEGER NOT NULL (epoch ms); confirmed_at INTEGER (nullable). There is NO invalidated_at / valid_to / valid_until / deleted_at / superseded_at column on nodes -- grep confirms none. So a node's lifecycle is expressed as a state-machine label (review_status) advanced through promoteNodeStatus, not as a closed [valid_from, valid_to) interval. The 8 legal transitions are a closed Set in transitions.cjs (proposed->confirmed, proposed->needs_evidence, needs_evidence->validated, confirmed->validated, validated->invalidated, proposed->rejected, confirmed->superseded, confirmed->stale). 'invalidated' and 'superseded' exist as terminal STATES, but they are enum values bumped in place (UPDATE nodes SET review_status=...) with no separate timestamp marking when the interval closed -- only last_seen_at is touched. Each transition logs a memory_event node (the audit trail / pseudo-history), so temporal history is reconstructable from the event log, not from the node row itself.

FACTS TABLE (legacy, memory-ops.cjs): The facts table IS uni-temporal, and more precisely it is a valid-time soft-delete model, not transaction-time. Columns: valid_from TEXT NOT NULL (ISO string set at insert), invalidated_at TEXT (nullable), invalidated_by TEXT (nullable). 'Valid' = invalidated_at IS NULL (getValidFacts filters exactly this). There is no separate system/transaction-time axis and no valid_to other than the invalidation marker, so it is one temporal axis = uni-temporal. CRITICAL FINDING: the facts table has ZERO live non-test callers. grep across the whole repo (excluding node_modules) for addFact / getValidFacts / invalidateFact / 'FROM facts' / 'INTO facts' returns hits ONLY in (a) lib/core/memory-ops.cjs itself (the definitions + the exports doc-comment) and (b) tests/test-memory-ops.cjs. No command, hook, script, agent, or other lib/core module ever calls these. The table is created by initMemorySchema (so it exists in every room.db) but is functionally orphaned dead code -- a uni-temporal skeleton that was built and never wired into the navigation spine. The live truth-state machinery moved entirely onto the nodes table (review_status) in Phase 109; assumptions (the other validity-bearing memory table) WERE migrated into graph nodes by phase-109 backfillAssumptionsAsGraphNodes, but facts were not.

## Gaps

- Edges have no temporal dimension at all -- a bi-temporal Zep-style model needs at least valid-time on edges (e.g. valid_from / valid_to or created_at / expired_at). Mindrian's edges are point-in-time-less and overwrite-in-place; there is no edge invalidation, no edge history, no as-of-edge query possible.
- Nodes carry only forward timestamps (created_at, last_seen_at, confirmed_at) plus a status enum. There is no node-level interval close (no invalidated_at timestamp paired with the 'invalidated'/'superseded' enum state), so you cannot answer 'what was the graph state as-of time T' from row data -- only by replaying the memory_event log.
- No transaction-time axis anywhere (neither edges nor nodes nor facts). Everything is single-axis valid-time-ish at best. A true bi-temporal model needs both valid-time and transaction/system-time; Mindrian has neither cleanly separated.
- The one uni-temporal artifact that does exist (facts table) is orphaned -- it is unwired dead code, so even the partial temporal skeleton it represents is not exercised in production.
- The de-facto temporal history is the memory_event append log (transitions.cjs logs every status change), but that is an event-sourcing audit trail, not a queryable bi-temporal table; reconstructing as-of state requires log replay rather than an interval predicate.

## Raw Notes

Surprises / dead code / orphans worth preserving: (1) The facts table is a fully-built, fully-tested, ZERO-production-caller orphan. It is the cleanest uni-temporal soft-delete model in the codebase (valid_from + invalidated_at + invalidated_by) yet nothing outside its own test file touches it. Strong candidate for either removal or for becoming the seed of a real bi-temporal layer. Phase 109 migrated assumptions into nodes but pointedly did NOT migrate facts -- facts got stranded when truth-state moved to the nodes.review_status machine. (2) There are TWO Phase 109 node migrations: phase-109-nodes-provenance.cjs (the full 9-column + CHECK rebuild) AND phase-109-session-focus.cjs which independently ALTERs nodes to add review_status/created_at/last_seen_at as a fallback 'when 109-01 has not yet run' (transitions.cjs depends on those columns). So node-temporal columns can be added by either migration -- a defensive double-path. (3) The rs_discoveries object is a VIEW over nodes (json_extract of the properties bag), not a table -- and phase-109 has a dependentSchemaObjects() routine that drops-and-recreates any view/trigger referencing 'nodes' around the table rebuild, which is why the view survives the 12-step recipe. (4) Edge 'timestamps' that DO appear (cycle_timestamp in linkDiscoveryCycleSource, created/timestamps inside CausalClaim properties) are all buried inside the opaque properties JSON blob, never promoted to a column, so they are not indexable/queryable as temporal predicates. (5) Node lifecycle terminal states 'invalidated' and 'superseded' exist in the enum but there is no column recording WHEN the supersession happened beyond last_seen_at being bumped -- the close-time is only inferable from the memory_event row. Net: Mindrian owns a node STATE-MACHINE (enum + closed transition set + event log) and an orphaned uni-temporal facts table, but NOT a bi-temporal graph skeleton. Edges in particular are temporally inert. To reach the Zep pattern you would need to add a valid-time interval to edges and a paired close-timestamp to nodes, and either resurrect or replace the facts table.
