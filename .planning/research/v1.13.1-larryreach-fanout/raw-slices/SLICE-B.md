# Slice B -- Context Retrieval Today -- SessionStart dump vs graph-BFS seeding vs conversation loop vs local index

Verdict: **PARTIAL**

## Current State

Context is assembled TODAY by two unrelated mechanisms, neither of which retrieves against conversation text.

(1) SessionStart is a FULL-ROOM DUMP, not a query. scripts/session-start fires once per session (matcher startup|clear|compact). It walks EVERY subdirectory of the room that contains a ROOM.md and reads each section's memory triple via lib/core/folder-memory.cjs::readTriple, then hands the whole map to lib/memory/triple-context-formatter.cjs::formatTripleContext. There is no query, no relevance ranking against anything the user said -- it emits every section, sorted weakest-first by reasoning_health_score, packed until a 5000-token budget (DEFAULT_BUDGET_TOKENS) is exhausted, then elides the strongest sections with a footer. The only "filter" is the token budget plus a tiering heuristic (minimal/balanced/rich) driven by archetype + context-window pressure, not by content relevance. The session-snapshot.json (88-06) is a cache of the same per-section triples; on miss it falls back to the live readdir+readTriple walk (session-start lines 1001-1015). So SessionStart = "here is the entire room, trimmed to fit," never "here is what is relevant to your question."

(2) The ONLY graph-BFS retrieval is lib/core/navigation/neighborhood.cjs::getNeighborhood -- a recursive-CTE traversal of room.db (nodes/edges) from a single focus node, ranked by a frozen weighted score. It is seeded by VENTURE STATE, never by conversation text. Seeding goes through lib/core/navigation/focus.cjs (getActiveFocus reads the session_focus row; computeAutoFocus picks: active JTBD node -> DECISION_GATE most-recent-unconfirmed-decision -> room root node -> null cold start) and through lib/core/navigation-engine-offer.cjs::resolveFocusNodeId (active focus -> 'section:'+sectionPath -> most-recent memory_event target). The section itself is resolved from .mindrian/active-section.json or most-recently-modified MINTO.md (intent-classifier.cjs:639-679). At no point is the user's prompt embedded, matched, or used to choose the focus node.

(3) The conversation-to-retrieval loop is OPEN. UserPromptSubmit hooks (hooks.json) run intent-classifier, mva-detect, brain-derivation-drain, operator-update, jtbd-update, auto-explore-drain, plus file/cwd/agent/task hooks. The intent-classifier DOES call the navigation engine per turn (navigation-engine.cjs::decide, emitting a "NAVIGATION DECISION (engine v1)" additionalContext block), but it explicitly passes userText: null -- scripts/intent-classifier.cjs:1081 comment: "hot path does not forward prompt content." decide() is seeded by the pre-read quadruple for the active section (readQuadruple) and USER.md, NOT by what the user typed. userText, when present elsewhere, is only regex-scanned for a literal /mos:command slug (navigation-engine.cjs:581-590) to attribute the prior offer's outcome -- it never drives node selection or re-seeds getNeighborhood. So each prompt does NOT re-seed retrieval against its own content; retrieval re-runs against venture state (focus/section/JTBD) regardless of what was asked.

(4) There is NO local FTS or semantic index over room.db. grep for USING fts / VIRTUAL TABLE / fts5 / fts4 across lib/ and scripts/ returns zero. room-db.cjs only sets PRAGMA journal_mode=WAL + foreign_keys=ON; the nodes table (migrations/phase-109-nodes-provenance.cjs) is a plain table with a TEXT properties JSON blob and scalar provenance columns -- no full-text virtual table, no vector column. All embedding/semantic/Pinecone/cosine machinery is in the rs-* reverse-salient layer and the remote Brain, operating on public corpus metadata, NOT on a local index over the user's room.db. getNeighborhood's "relevance" is purely graph-structural (edge-type weight + recency decay + confidence + same-section bonus), with zero lexical or vector matching.

## Gaps

- No query-time retrieval: nothing embeds or lexically matches the user's prompt against room.db to fetch the most relevant nodes. The Zep pattern (per-message relevant-fact retrieval) has no analogue here.
- The conversation-to-retrieval loop is open: intent-classifier forwards userText:null, so each turn re-derives context from venture state (focus/section/JTBD), not from the turn's content. A user asking about topic X does not pull X-relevant nodes.
- No local FTS5 or vector index over room.db. getNeighborhood ranking is structural-only (edge weight + recency + confidence + same-section), so it cannot answer 'what nodes are about THIS question.'
- SessionStart cannot scale as a query: it is a full-room dump capped only by a 5000-token budget; large rooms silently elide their strongest sections rather than retrieving the relevant ones.
- getNeighborhood is the only graph-BFS but is invoked from offer/insights/packet/dashboard helpers and the engine -- none of those entry points is seeded by conversation text, so the BFS never narrows to what the user is currently discussing.

## Raw Notes

Skeleton exists for graph-native retrieval (getNeighborhood recursive CTE with a real weighted score, focus/session_focus persistence, memory_event audit trail, navigation.cjs as single chokepoint), so the LOCAL graph and the BFS primitive are owned. What is missing is the retrieval-against-conversation half: (a) no index (FTS or vector) over node text, (b) no path that turns a user prompt into a focus seed or a candidate-node set. The system deliberately decouples conversation from retrieval (intent-classifier.cjs:1081 'hot path does not forward prompt content') -- this looks like an intentional Canon-Part-8/latency decision (1200ms hard timeout, NAV_HARD_TIMEOUT_MS), not an oversight, but it means the loop is open by design.
