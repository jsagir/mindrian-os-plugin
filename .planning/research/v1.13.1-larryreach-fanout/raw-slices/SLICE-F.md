# Slice F -- Cross-room / user-graph-spans-threads (Phase 103 across-session + cross-room memory)

Verdict: **PARTIAL**

## Current State

There are two distinct cross-room mechanisms, and they are independent.

RECALL (across-session JTBD history): lib/hmi/across-session-memory.cjs is the Layer-2 read/write module. It aggregates per-room JTBDs into a single global per-USER JSON file at ~/MindrianRooms/.memory/jtbd-history.json (schema {version, rooms:{slug:{in_flight[],parked[],completed[]}}, last_updated}). Writes happen via promoteIfEligible / parkJtbd / completeJtbd through an O_EXCL lockfile pipeline (2s TTL stale-lock recovery, 200ms retry budget, then an unsafe read-merge-write fallback). Reads expose getRoomMemory, listInFlight, getJtbdAcrossRooms. lib/hmi/cross-room-memory.cjs (Layer 3) sits on top: aggregateAcrossRooms walks the registry, applies Canon Part 8 scope/sealed/opt-out filters per room, and synthesizes a by_jtbd landscape from the SAME jtbd-history.json (via the across-session module, with a direct-read fallback readAcrossSessionState). This module makes ZERO direct cross-room BRAIN.md reads -- it only optionally enriches the synthesis with generic methodology pattern hints from a single Brain semantic search call (Mode A); absent Brain it is Mode B local-only. This is what /mos:memory surfaces.

CONSISTENCY (peer BRAIN.md scalar diffing): lib/core/cross-room-aggregator.cjs (Phase 90-06) is a completely separate mechanism. aggregateContradictions reads the per-section memory quadruple (ROOM+STATE+MINTO+BRAIN) of EVERY registered peer room via folderMemory.readQuadruple, extracts only structural scalars (governing_thought_hash, problem_type enum, framework_chain_sig fnv1a hash, reasoning-exists bool), and diffs the current room against peers to emit hash_divergence / problem_type_mismatch / framework_contradiction edges. It makes ZERO Brain calls -- it is pure local filesystem scalar diffing with a four-layer Canon Part 8 redaction defense. Its output renders into the BRAIN.md 'Flagged Contradictions (cross-room)' section.

So: RECALL answers 'what JTBDs was I working on across rooms last week' (read from one global JSON), routed optionally through Brain for generic pattern hints. CONSISTENCY answers 'do my rooms structurally contradict each other' (peer BRAIN.md scalar diffing, no Brain). cross-room-memory.cjs imports cross-room-aggregator.cjs (line 50) but only to REUSE its boundary helpers (isRoomOptedOut, ALLOWED_ROOT scope logic, safeSlug) -- not its contradiction engine. The two never share a data path.

## Gaps

- The Canon Part 4 graph edge is NOT wired. graph-edge-pending.log is the Phase 103-05 drain STUB: across-session-memory.cjs is the only file that touches it, and only to WRITE (appendFileSync). grep for any reader/HAS_JTBD/room-db consumer returns nothing. - Across-session / cross-room RECALL memory does NOT live in the SQLite spine (room.db). It is JSON-file-only. grep for navigation.cjs / room-db / sqlite / room.db inside both lib/hmi modules returns only two COMMENT lines promising future room-db.cjs wiring. This contradicts Canon Part 9 ('SQL remembers and navigates'): the across-session/cross-room JTBD layer is the one memory surface still living in flat JSON outside the Part 9 spine. (The /mos:memory command itself emits a spine_read memory_event via navigation.cjs for telemetry -- memory-command.cjs:79-89 -- but the JTBD data it reads is still from JSON, so the spine sees the access event, not the data.)
- Cowork shared-$HOME multi-user scoping risk is REAL but documented-not-enforced. ROOMS_HOME resolves to os.homedir()/MindrianRooms (across-session-memory.cjs:48-49). The privacy contract (ROOM.md body lines 117, command memory.md:88) ASSERTS 'each user has their own ~/MindrianRooms/.memory/ scoped to their home directory' -- but nothing in code enforces per-user scoping. If a Cowork deployment shares one $HOME across users (or sets a shared MINDRIAN_ROOMS_HOME), all users' JTBD history merges into one jtbd-history.json with no user attribution field on any row, and the O_EXCL lock + unsafe fallback would interleave multi-user writes. The only mitigation is a Zone-3 WARNING surfaced when 00_Context/ is detected (memory-command.cjs:249-256), which warns the human but does not isolate data.
- jtbd-history.json carries NO schema migration / no user-id field. A future move into the Part 9 spine would need a migration path; none exists.
- The unsafe-fallback write path (atomicUpdateMemoryUnsafe, lines 208-227) can silently lose one racing write under lock contention -- acceptable for single-user, but a correctness hazard precisely in the shared-$HOME multi-user case above.

## Raw Notes

Both mechanisms ARE boundary-safe today (Canon Part 8): CONSISTENCY makes zero Brain calls and has 4-5 redaction layers (sanitizeDetailScalar truncates >40 char strings, FORBIDDEN_PATTERNS for email/currency/quoted-person/SSN/phone, JSON.stringify last-line audit, render-time fifth scan). RECALL's only egress is the single tryBrainSearch call gated by buildBrainQueryContext's 15-key allow-list + payloadIsClean FORBIDDEN_PATTERNS scan; the query string is built only from JTBD slugs regex-validated to [a-z0-9-]. FORBIDDEN_KEY_NAMES in cross-room-memory are deliberately char-by-char constructed (lines 118-122) so the schema-leak audit (Tripwire #1) does not flag the defensive code itself -- a nice detail.

The two FORBIDDEN_PATTERNS sets DIFFER: aggregator (lib/core, line 87-94) adds quoted-person (Lawrence|Jonathan|Nimrod|Oren|Dror), 'meeting with', SSN, phone; cross-room-memory (lib/hmi, line 108-112) has only email/currency/ISO-timestamp. Both adequate for their payloads but worth noting they are hand-maintained mirrors that could drift.

Skeleton ownership re: the Zep-pattern 'user graph spans threads': Mindrian HAS the cross-room aggregation skeleton (one global per-user store + registry-walk + by_jtbd span query getJtbdAcrossRooms). What it does NOT have is (a) the typed graph edge persisted (HAS_JTBD into room.db is stubbed), and (b) residence in the SQLite spine that Canon Part 9 mandates. So the 'graph spans threads' is currently a JSON aggregation, not a graph. Hence PARTIAL.

Registry schema dual-shape handling is pervasive and a smell: getActiveRoomDir (memory-command.cjs:142-170), resolveRoomSlug (completion-detector:154-175), isRoomOptOut (across-session:237-252), listEligibleRoomsFallback (cross-room:300-359) each independently tolerate BOTH {active,rooms:{slug:{path}}} (object) and {active_room,rooms:[{slug,abs_path}]} (array) forms. Phase 127.3 already routed jtbd-update through a chokepoint (resolveActiveRoom) per the comment at jtbd-update.cjs:189-202, but the other three readers still hand-roll the dual-shape walk -- drift surface.

memory-resume-nudge.cjs (SessionStart hook) does a defensive backfill (backfillFromWithinSession) re-running promoteIfEligible across all rooms to catch promotions missed by crashed Stop hooks -- so the in_flight set is self-healing on session start. Good resilience, but it ALSO writes graph-edge-pending.log lines on every backfill, further inflating the never-drained log.

Live state shows rooms:{} empty in jtbd-history.json despite 10 edge-log lines -- meaning a /mos:memory --opt-out or a reset wiped history.json but the append-only edge log was never truncated/drained. Confirms the log and the history file are not kept in sync and nothing reaps the log.
