## room-bind-gate-fires-on-notification-only-turns - the F.8 room-binding Decision Gate force-fires on turns whose only content is a background-task-completion notification
- **Date:** 2026-07-23
- **Error patterns:** Stop hook error, rendering your choices as a selectable card, REACHED a Decision Gate but did NOT fire, AskUserQuestion, F.8, room_bind, emitBindingGate, intent-classifier.cjs, preceding_user_text, extractAssistantText, tool_result, task-notification, gateTopicallyRelevant, MIN_USER_SUBJECT_TOKENS, gate-relevance.cjs, readTranscriptTurn, check-card-fire.cjs, preceding_user_text_source, classifyPrecedingUserContentSource, background subagent, Task tool completion
- **Root cause:** `precedingUserText` (`scripts/check-card-fire.cjs`) resolves to `''` for two very different reasons the pre-fix code could not distinguish: (1) a genuinely terse HUMAN turn ("ok", "go on"), and (2) a preceding transcript record that is a SYNTHETIC `tool_result` envelope (a background tool call's result) or an automated task-notification block, with NO human-authored text field at all. `lib/core/gate-relevance.cjs::gateTopicallyRelevant`'s conservative low-signal branch force-fired (assumed relevant) on BOTH, which is correct only for the first -- there is no human turn for a Decision Gate to be relevant or irrelevant to in the second case. The mechanism was first diagnosed as a FACT (not yet a filed defect) in `.planning/debug/live-session-running-stale-plugin-cache-fixes-inert.md`'s 2026-07-06 evidence entry, confirmed recurring 2026-07-11 and 2026-07-22 in that same file (whose own headline finding was a different topic, a deployment gap), and finally live-reproduced 3 consecutive times in one session on 2026-07-23, which motivated fixing it as its own defect rather than leaving it as a footnote. Refines (not duplicates) `.planning/debug/resolved/card-fire-over-enforcement.md`, whose fix (2026-07-20) distinguished a FRESH gate from a STALE one but did not address WHY the preceding user text is empty in the first place.
- **Fix:** Added `preceding_user_text_source` (`'typed' | 'tool_result' | 'none'`), classified by a new `classifyPrecedingUserContentSource` helper wired into `readTranscriptTurn` (walks the preceding `role:user` transcript record's content blocks: any real `.text` -> `'typed'`; every block a `tool_result` / non-text synthetic envelope -> `'tool_result'`; nothing at all -> `'none'`) and threaded through `deriveTurnSignals` with the SAME direct-field-precedence rule as `preceding_user_text` itself (backward compatible: existing unit-test envelopes default to `'none'` and are unaffected). `classifyCardFire`'s PRIMARY-path relevance branch now returns `{ intercept: false, reason: 'preceding-turn-synthetic-no-user-engagement', degrade: false }` immediately when the source is confirmed `'tool_result'`, BEFORE ever calling `gateTopicallyRelevant` -- bypassing the conservative low-signal branch entirely for this one confirmed cause, rather than weakening it generally. The BACKSTOP path and the existing WR-06/CR-06 conservative force-floor for genuinely terse HUMAN turns are byte-unchanged (scoped deliberately: this fix is PRIMARY-path only, matching the confirmed live F.8 mechanism). Verified: all 8 pre-existing card-fire test files re-run individually post-fix, all green (108 assertions); 3 new regression Behaviors added to `tests/test-209-primary-sidechannel.cjs` (12: a real F.8 gate + synthetic tool_result preceding turn -> no intercept; 13: the SAME gate + a genuinely typed "ok" preceding turn -> still force-fires, floor preserved; 14: unit-level `classifyPrecedingUserContentSource` coverage including a MIXED tool_result+real-text record, which correctly resolves to `'typed'`). RED/GREEN proof performed via `git stash` on the source file alone (new tests fail pre-fix with the exact expected assertion, pass post-fix).
- **Files changed:** scripts/check-card-fire.cjs, tests/test-209-primary-sidechannel.cjs, CHANGELOG.md. Resolution doc at `.planning/debug/resolved/room-bind-gate-fires-on-notification-only-turns.md`. Distinct from `.planning/debug/resolved/card-fire-over-enforcement.md` (that RCA is about gate FRESHNESS; this one is about WHY the preceding text is empty).
- **Pattern lesson:** A relevance/enforcement predicate that treats "insufficient signal" as a single category will conflate a genuinely low-signal HUMAN turn with a turn where there was NO human turn at all (a synthetic tool-result or automated-notification transcript record). These require opposite defaults: uncertainty from a human should stay conservative (force); the confirmed absence of any human turn should never force a Decision Gate, because there is nothing for the gate to be relevant or irrelevant to. When a "conservative default" branch keeps mis-firing, check whether it is actually conflating two structurally different input shapes rather than genuinely being under-confident about one shape.

## stop-hook-invalid-hookspecificoutput-schema - hookSpecificOutput on a Stop-hook envelope rejects the WHOLE envelope, showing a raw validation error instead of the calm systemMessage
- **Date:** 2026-07-23
- **Error patterns:** Stop hook error, Hook JSON output validation failed, Invalid input, hookSpecificOutput, hookEventName, additionalProperties: false, check-card-fire.cjs, buildEnforcementEnvelope, ALLOWED_ENVELOPE_KEYS, feynman-minto-guardian.cjs, runOnStop, MINDRIAN_MCP_FIRST thin-adapter, on-stop, v1.10.9, v1.10.10, v1.10.19, systemMessage, decision:block, additionalContext, check-hook-schema-compatibility.cjs, verify-release
- **Root cause:** Claude Code's Stop-hook output schema defines `hookSpecificOutput` for exactly three events -- PreToolUse, UserPromptSubmit, PostToolUse -- never Stop. A Stop envelope that includes `hookSpecificOutput` at all (any shape) fails schema validation as a WHOLE (`additionalProperties: false`-class rejection), discarding every other field including a correctly-set calm `decision`/`reason`/`systemMessage`, and showing the user a raw "Hook JSON output validation failed" dump instead. This is the 4th live occurrence of the exact defect class: fixed once (`scripts/on-stop`, 2026-04-15, v1.10.9->v1.10.10), reintroduced under a backwards-premise comment ("v1.10.19": claimed hookSpecificOutput was REQUIRED because top-level systemMessage would be rejected -- the opposite of true) in `scripts/feynman-minto-guardian.cjs`, reintroduced AGAIN as a straight regression inside the very file (`scripts/on-stop`) that had already fixed it once (the Phase 198-09 MCP-first thin-adapter branch), and hit live by a real user via `scripts/check-card-fire.cjs`'s `buildEnforcementEnvelope` intercept branch (whose own `ALLOWED_ENVELOPE_KEYS` allowlist legitimized the key). A related discovery: `scripts/check-hook-schema-compatibility.cjs` existed unwired into any release gate and ALSO encoded the same backwards premise -- had it ever been wired in as its own docstring intended, it would have actively blocked this correct fix and encouraged reintroducing the bug.
- **Fix:** Removed `hookSpecificOutput` outright from all 3 sites, keeping each branch's existing calm `decision`/`reason`/`systemMessage`/`continue` unchanged (the `additionalContext`/rendered-zones text those blocks carried has no valid Stop-hook delivery channel in the schema and is dropped, not smuggled into human-facing fields). Removed `'hookSpecificOutput'` from `check-card-fire.cjs`'s `ALLOWED_ENVELOPE_KEYS`. Corrected `scripts/feynman-minto-guardian.cjs`'s stale, backwards "v1.10.19" comment. Structural regression gate: corrected `scripts/check-hook-schema-compatibility.cjs` to enumerate every script `hooks/hooks.json`'s `Stop` array registers (resolving `run-hook.cmd` targets), transitively follow one level of subprocess invocation (catches `feynman-minto-guardian.cjs` via `on-stop` even though not directly registered), and fail on the literal `hookEventName: 'Stop'` pattern; wired into `scripts/verify-release` as new section 16 (same style as the existing `os.rename` gate). Corrected 2 pre-existing tests (`test-ga4-card-fire-e2e-179.cjs`, `test-ga4-card-fire-interceptor.cjs`) that had hard-asserted the BUGGY shape as expected behavior. Verified: scanner PASS (14 files, 0 findings) + a synthetic positive-control proving it actually detects the pattern; `buildEnforcementEnvelope`'s 3 verdict shapes checked directly (schema-allowed keys only); `on-stop`'s corrected inline snippet and `feynman-minto-guardian.cjs`'s `runOnStop` each exercised directly against fixtures (no hookSpecificOutput in either output). Full card-fire test suite green (10 files, 181 assertions total).
- **Files changed:** scripts/check-card-fire.cjs, scripts/on-stop, scripts/feynman-minto-guardian.cjs, scripts/check-hook-schema-compatibility.cjs, scripts/verify-release, tests/test-ga4-card-fire-e2e-179.cjs, tests/test-ga4-card-fire-interceptor.cjs, CHANGELOG.md. Resolution doc at `.planning/debug/resolved/stop-hook-invalid-hookspecificoutput-schema.md`. Distinct from `.planning/debug/resolved/card-fire-over-enforcement.md` (that RCA is about WHETHER the Stop hook should intercept; this one is about the JSON SHAPE being invalid whenever it does).
- **Pattern lesson:** A wrong belief about a hook-output schema, once written down as a code comment citing a specific version ("v1.10.19"), reads as authoritative to a future editor and gets COPIED, not just repeated independently -- 3 of this defect's 4 occurrences trace to that one backwards comment or its own file's regression, not 4 independent misunderstandings. When a schema-conformance bug is fixed once, grep the WHOLE repo for the same literal shape before considering it closed (an unwired, misnamed "release gate" script sitting nearby, encoding the same wrong rule, is exactly the kind of landmine a single-site fix leaves behind). A gate that has never been wired into anything is not a safety net -- verify it actually runs, not just that it exists.

## windows-os-rename-registry-wedge - Python os.rename() (not POSIX on Windows) wedges the room registry after the first write
- **Date:** 2026-07-23
- **Error patterns:** os.rename, os.replace, FileExistsError, WinError 183, MoveFileW, MoveFileExW, MOVEFILE_REPLACE_EXISTING, atomic write, tmp swap, room-registry, resolve-room, update-icm-index, on-cwd-changed, registry.json, registry.json.tmp, orphaned tmp, set-active, archive, git-config, Windows-only, second write, destination exists, "nothing sticks", Python heredoc in bash, fs.renameSync unaffected, track-analytics
- **Root cause:** Python's `os.rename(src, dst)` is NOT POSIX `rename(2)` on Windows -- Python docs: "On Windows, if dst exists a FileExistsError is always raised" (bare `MoveFileW`, no replace flag). The four room-registry-family scripts do the textbook atomic-write pattern (write `<file>.tmp`, then swap over the real path) inside Python heredocs in bash and used `os.rename(tmp, dst)` for the swap. On Linux/macOS `os.rename` overwrites an existing dst silently (POSIX), so the FIRST write (dst absent -- cold room creation, first list) succeeds everywhere, masking the bug. Every SUBSEQUENT write to the now-existing dst on Windows raised uncaught FileExistsError [WinError 183], exited non-zero, left an orphaned `.tmp`, and froze the real file at its last good state. Presentation: "the tool works, but nothing I do sticks." Every Windows user who created a second room or switched the active room once had a silently wedged registry. Test suites never caught it because they run under WSL/Linux and only exercised the cold-start (dst-absent) path. Corroborating: scripts/track-analytics:155 already used the correct `os.replace` -- the primitive was the house standard; the registry family was the outlier that missed it.
- **Fix:** One-word primitive swap `os.rename` -> `os.replace` at all 9 callsites (resolve-room:169, update-icm-index:146, on-cwd-changed:100, room-registry:198/252/411/454/524/587). `os.replace` maps to `MoveFileExW` + `MOVEFILE_REPLACE_EXISTING` and overwrites an existing dst on ALL platforms -- byte-identical to what os.rename ALREADY did on Linux/macOS, so Linux is provably unchanged and the Windows crash is gone. Adjacent same-defect fix (flagged, not silent): the identical anti-pattern in a test cleanup trap at tests/test-jtbd-auto-anchor-empirical.sh:91,110 was also swapped so the defect survives nowhere in tracked source. New regression test tests/test-room-registry-windows-atomic-replace.cjs (21/21) exercises the previously-untested SECOND write to an existing registry.json and asserts the on-disk bytes actually CHANGED (a frozen-file false-success would pass an exit-code-only check but fail this) plus no orphaned `.tmp` remains, runs a pure-Python os.replace overwrite-semantics probe, and structurally asserts zero os.rename survive. Deliberately NOT touched: Node's ~30 `fs.renameSync` (libuv already does MOVEFILE_REPLACE_EXISTING on Windows) and the ~/.claude/plugins install cache (ghost patch per WORKSPACE GUARD).
- **Files changed:** scripts/resolve-room, scripts/update-icm-index, scripts/on-cwd-changed, scripts/room-registry, tests/test-jtbd-auto-anchor-empirical.sh, tests/test-room-registry-windows-atomic-replace.cjs. Resolution doc at `.planning/debug/resolved/windows-os-rename-registry-wedge.md`.
- **Pattern lesson:** `os.rename` and `os.replace` are the SAME on POSIX and DIFFERENT on Windows -- for any atomic-write tmp-swap, `os.replace` is the only correct primitive (os.rename raises WinError 183 once the destination exists). A cross-platform defect where the first write always succeeds and later writes fail is the signature of a create-vs-overwrite semantic split; a Linux-only test suite will pass it forever because the dst-absent path is the one path that works on Windows too. Test the SECOND write to an existing destination and assert the bytes CHANGED, not just exit 0. When one script in the tree already uses the correct primitive (here track-analytics's os.replace), grep for the outliers.

## card-fire-over-enforcement - Stop hook force-fires a STALE Decision-Gate card on unrelated terse turns
- **Date:** 2026-07-20
- **Error patterns:** check-card-fire.cjs, reached-registry-gate-no-card, card-fire-sidechannel.cjs, gate-relevance.cjs, gateTopicallyRelevant, MIN_USER_SUBJECT_TOKENS, ran_entries, gate_subject_text, NO_SESSION_KEY, TTL bleed, side-channel, mostRecentReachedTs, TURN_FRESH_MS, gate_is_fresh, staleness, low-signal floor, over-enforcement, Phase 209/210, WR-06, /mos:doctor, Stop hook block, decision:block, rethinking-mindrianos REACH
- **Root cause:** Two stacked defects made the Stop hook force a card for a gate the model had already, correctly, judged stale. (H1) `lib/core/card-fire-sidechannel.cjs` reads unioned the `NO_SESSION_KEY` bucket into every session and TTL-bounded the session bucket at 10 minutes, so ONE gate mint bled into every later turn (same session) and every other session for 10 minutes -- populating `ran_entries` + a non-empty `gate_subject_text` on turns that reached no gate. (H2, dominant) `gate-relevance.cjs::gateTopicallyRelevant` returned `true` (force-fire) whenever the preceding user text had fewer than `MIN_USER_SUBJECT_TOKENS` (2) subject tokens -- true for every terse slash-command (`/mos:doctor`, `status`, `building`). Verified empirically against the real stored stale subject: those triggers all hit the `< 2`-token floor and force-fired. (H3 RULED OUT: not a genuine token overlap; only a minority of 2-token turns spuriously match the gate's UI boilerplate "Choose next reach", not its topic.) The 2026-07-17 `card-fire-relevance-check-gap` gate-existence guard did NOT catch it: it required a non-empty `gate_subject_text` as "proof a gate existed this turn," but the side-channel stores `subject` in the same record as `entry`, so a stale bled record carries a non-empty subject and passes the guard on subject-presence rather than gate-recency (the guard checked the wrong signal).
- **Fix:** (A) `card-fire-sidechannel.cjs`: added `TURN_FRESH_MS` (2 min), a turn-scoped freshness window; `scopedRecords` scopes the `NO_SESSION_KEY` union to that window (no cross-session leak); added `mostRecentReachedTs()` exposing gate recency; the 10-min file TTL still bounds the file. (B) `gate-relevance.cjs`: `gateTopicallyRelevant(user, gate, opts)` gained an optional third arg; its low-signal branch returns `false` when the caller marks the gate stale (`opts.gateStale`) instead of blindly forcing -- the distinction encoded is STALENESS, not token count; absent opts it is byte-identical (WR-06 floor preserved). (B-wire) `check-card-fire.cjs`: `deriveTurnSignals` computes `gate_is_fresh` (fresh = side-channel mint within `TURN_FRESH_MS`; direct-field / BACKSTOP gates always fresh) and `classifyCardFire` threads `{ gateStale: !gate_is_fresh }` into the PRIMARY-path relevance call (BACKSTOP passes `gateStale:false` since its gate is this turn's own output). Verified end-to-end: STALE bled reach + terse `/mos:doctor` -> `{continue:true}` (not blocked); FRESH this-turn reach + same terse turn -> `{decision:block}` (floor preserved). Suites green: test-209-primary-sidechannel 14/14 (new Behaviors 10/11), test-card-fire-relevance-gate 11/11, test-ga4-card-fire-e2e-179 47/47, interceptor 27/27, doctor-health 6/6, trailer-relevance 4/4, run-all-179 12/12. Canon Part 8 clean (LOCAL fs + string only).
- **Files changed:** lib/core/card-fire-sidechannel.cjs, lib/core/gate-relevance.cjs, scripts/check-card-fire.cjs, tests/test-209-primary-sidechannel.cjs. Resolution doc at `.planning/debug/resolved/card-fire-over-enforcement.md`. Closes todo `2026-07-05-fix-stop-hook-forcing-irrelevant-decision-gate-cards.md`.
- **Pattern lesson:** An existence guard that checks "is the subject present" is not the same as "was this gate reached THIS turn." When a side-channel record carries both the identity AND the subject, a stale record passes a subject-presence guard -- guard on RECENCY (a turn-scoped freshness window), not presence. And a "conservative default = always force" floor is only conservative when the artifact is FRESH; against a stale artifact it is the exact over-enforcement it was meant to prevent. Encode the freshness/staleness signal, do not proxy it with token counts.

## brain-ask-empty-envelope - brain_ask returns a structurally valid but empty DirectiveEnvelope
- **Date:** 2026-05-22
- **Error patterns:** brain_ask, DirectiveEnvelope, empty envelope, directive.guided, next_gate, mode_rationale, default_guided_pedagogical_canon, wrapDirective, buildDirective, capability map, stale contract, Phase 127, mcp-server-brain, brain-ask.cjs, directive-envelope.cjs, framework chaining, contract mismatch
- **Root cause:** Stale contract. The Phase 127 DirectiveEnvelope contract (docs/CAPABILITY-MAP.md) requires `brain_ask` to return a payload carrying a populated `directive` + `next_gate` + `mode_signals`. Phase 127 (directory `127-brain-mcp-local-stdio-shim`) implemented only the CONSUMER side -- the client-side envelope wrapper `lib/core/directive-envelope.cjs` and the stdio shim `bin/mindrian-brain-mcp-client.cjs`. The PRODUCER side -- the deployed Brain server's `brain_ask` handler `mcp-server-brain/lib/brain-ask.cjs` -- was never updated; it still returned the ORIGINAL raw search-hits payload `{question, keyword, source, count, results}` from commit dc363c54 (pre-Phase-127). With no `directive` key in the server response, the wrapper's `buildDirective` pass-through branch never fired and it fell through to its documented empty GUIDED scaffold (`directive.guided={questions:[],framework:null,stage:null}`, `next_gate.options=[]`, `mode_rationale:"default_guided_pedagogical_canon"`) on every call. The empty envelope was correct-by-design wrapper behavior fed a contract-incomplete server payload. The capability map itself had drifted -- it marked the row "shipped (Phase 127)" when only the consumer half shipped.
- **Fix:** Augmented `mcp-server-brain/lib/brain-ask.cjs` with server-side directive synthesis. `buildDirectiveFromGraph(session, keyword, limit)` runs two READ-only bound-parameter Cypher queries: (1) best-matching Framework node for the question keyword; (2) that framework's outbound chaining edges (FEEDS_INTO/CHAINS_TO/CO_OCCURS/PRECEDES/NEXT). It builds `directive.guided.{questions, framework, stage}` -- each chain target becomes a reframing question, the framework's beautiful_question seeds an opening question, chained frameworks become `next_gate.options` as F.1 "Run Methodology" verbs. `deriveModeSignals(question)` derives mode_signals from generic phrasing only (GUIDED default preserved). Returns directive + next_gate + mode_signals alongside the legacy `results` array (backward compatible). Graceful degradation: graph failure or no-framework-match omits the directive and the wrapper's empty scaffold becomes the honest "nothing to teach" signal. All Cypher uses bound parameters ($keyword/$frameworkName/$limit via neo4j.int()) -- the original string-interpolation pattern was removed, including the latent weakness on the Step 2 fallback path. Canon Part 8: READ-only sessions, zero write-Cypher, generic methodology only. IMPORTANT: the handler is served from mindrian-brain.onrender.com (render.yaml autoDeploy:true, connected to jsagir/mindrian-os-plugin) -- the fix takes effect at runtime only after the commit is pushed to origin/main and Render auto-deploys.
- **Files changed:** mcp-server-brain/lib/brain-ask.cjs
- **Pattern lesson:** A two-track Brain<->Plugin contract can be declared "shipped" when only one track lands. When a typed packet shape comes back structurally valid but content-empty, suspect a producer/consumer contract gap before suspecting the consumer wrapper -- check git history on BOTH the wrapper and the server handler, and check docs/CAPABILITY-MAP.md for a row that overclaims.

## brain-topk-uncapped-advisory - Brain forwards caller topK to Pinecone with no Brain-side cap
- **Date:** 2026-05-23
- **Error patterns:** brain_ask, brain_search, topK, Pinecone forward, uncapped, BRAIN_MAX_TOPK, Math.min, D-MOAT-2, moat inheritance, result-set cap, Phase 127.2
- **Root cause:** `mcp-server-brain/lib/brain-ask.cjs:545` and `mcp-server-brain/lib/pinecone-tools.cjs:42` forwarded caller-supplied `topK` directly to Pinecone with no Brain-side guard. ## windows-room-registry-path-normalization-gap -- bash $REGISTRY_FILE POSIX paths leak into Python open() on Windows + Git Bash
- **Date:** 2026-05-23
- **Error patterns:** /mos:rooms list, scripts/room-registry, FileNotFoundError, /c/Users/, Git Bash, POSIX path, python3 -c, open(), $REGISTRY_FILE, Windows, normwin, sys.platform, normpath, $HOME, cygpath, Instance #4, post-beta30-regression, windows-tester
- **Root cause:** `scripts/room-registry` embeds `python3 -c "..."` invocations at 8 subcommand stanzas (`create`, `read`, `list`, `update`, `set-active`, `archive`, `get-active`, `git-config`). Each interpolates bash-resolved `$REGISTRY_FILE` (computed from `$HOME + relative components`) into the Python source as a string literal. On Git Bash for Windows, `$HOME` carries POSIX form (`/c/Users/PC`), so the resolved path is `/c/Users/PC/MindrianRooms/.rooms/registry.json`. Bash and Linux Python resolve this. Windows Python's `open()` does not -- it treats the leading `/` as drive-root and the `/c/` prefix as a directory name. Result: `FileNotFoundError: [Errno 2] No such file or directory: '/c/Users/PC/MindrianRooms/.rooms/registry.json'` on every Windows + Git Bash user, on every registry subcommand. Silent for non-Windows users. Caught only on Jonathan's dogfood machine.
- **Fix:** Inlined `normwin()` Python helper at the top of every `python3 -c` block in `scripts/room-registry`. The shim is platform-detection-driven (`sys.platform == 'win32'`) so it's a no-op on Linux/macOS + WSL + native bash, and converts `/c/Users/...` -> `C:\Users\...` only on Git Bash for Windows. Every `open(...)` call inside each block was rewritten to `open(normwin(REGISTRY_FILE))`. Sibling sweep patched `scripts/reapply-modifications` (4 sites, single `$NORMWIN_SHIM` bash-var-string reused across all four `python3 -c` invocations). Deferred sweep flagged `scripts/verify-release` (4 sites), `scripts/learn-from-usage`, `scripts/track-analytics` (out of plan scope, logged to phase deferred-items).
- **Files changed:** scripts/room-registry, scripts/reapply-modifications, tests/test-room-registry-windows-path.cjs, tests/test-127.2-04-windows-path-and-update-activation.sh, .planning/debug/resolved/windows-room-registry-path-normalization-gap.md, .planning/debug/knowledge-base.md, docs/install-cache-family-premortem.md, CHANGELOG.md
- **Pattern lesson:** Any bash script that embeds `python3 -c` / `python3 << EOF` and interpolates a `$BASH_VAR` carrying a filesystem path into `open(...)` is broken on Windows + Git Bash. The `$HOME` (and every path derived from it) carries POSIX form (`/c/...`) which Windows Python's `open()` cannot resolve. The fix is a 4-line `normwin()` shim, platform-gated to be a no-op everywhere except Windows. When auditing or writing new bash scripts that embed Python, ALWAYS check for `open('$BASH_VAR')` / `open(normwin('$BASH_VAR'))` -- the latter is the new convention. Cross-platform CI matrix should include Windows + Git Bash; without it, this class of bug ships silently for the entire Windows user base for an unknown number of releases.

- **Pattern lesson:** when a mechanism grows a SECOND consumer, the question is not only "what state has no lifecycle?" (the ninth defect's lesson) but "does the second path actually FEED the shared predicate real values, or placeholders?". Here the handler correctly WRAPPED the predicate -- no fork, Part 7 honored, the header comment truthfully promising the constitutional floor is read from one place -- and was still completely unenforced, because wrapping a predicate is worthless if you hand it hardcoded inputs. A "single source of truth" claim covers the DECLARATION of a constant; it says nothing about whether every call site supplies live values to compare against it. Second lesson, and the sharpest one here: a source-presence grep is NOT a reachability proof. The sibling RCA's anti-drift assertion checked that `consumeReachedGatesForVerdict` appeared in this file's text; it did, in a branch that could never execute, and the assertion passed while the behavior was absent. When wiring a shared primitive into a second path, assert the OBSERVABLE EFFECT (the record is actually spent, the counter actually climbs) rather than the presence of the call -- and note that the dead branch was created by an ordering assumption ("dedup is a cheap pre-filter that runs first") that the implementation had already violated, since the expensive predicate ran first to compute `material`. Third: DORMANCY IS THE STRONGEST ARGUMENT FOR BEHAVIORAL PROOF, not against it. With `MINDRIAN_MCP_FIRST` unset there is zero production telemetry, so source inspection has nothing to corroborate against and "it looks right now" is the whole of the evidence; driving the real entry point and COUNTING the cards it forces converted a plausible reading into a measured 36-vs-3. Fourth: when a test must defeat a masking layer to reach the defect, make the masking layer's weakness an explicit fixture property rather than disabling it -- flapping the `gate_signature` (which is what a real LLM does under a re-prompt) both defeats dedup honestly and documents WHY the session ceiling exists, whereas stubbing dedup out would have proved a ceiling in a scenario that cannot occur. Fifth, a small process trap worth naming: an anti-drift regex that greps whole-file source will match the defect quoted verbatim inside the FIX's own explanatory comment -- strip comments before such assertions rather than deleting the explanation, or the test punishes documenting the bug you just fixed.
