## brain-ask-empty-envelope - brain_ask returns a structurally valid but empty DirectiveEnvelope
- **Date:** 2026-05-22
- **Error patterns:** brain_ask, DirectiveEnvelope, empty envelope, directive.guided, next_gate, mode_rationale, default_guided_pedagogical_canon, wrapDirective, buildDirective, capability map, stale contract, Phase 127, mcp-server-brain, brain-ask.cjs, directive-envelope.cjs, framework chaining, contract mismatch
- **Root cause:** Stale contract. The Phase 127 DirectiveEnvelope contract (docs/CAPABILITY-MAP.md) requires `brain_ask` to return a payload carrying a populated `directive` + `next_gate` + `mode_signals`. Phase 127 (directory `127-brain-mcp-local-stdio-shim`) implemented only the CONSUMER side -- the client-side envelope wrapper `lib/core/directive-envelope.cjs` and the stdio shim `bin/mindrian-brain-mcp-client.cjs`. The PRODUCER side -- the deployed Brain server's `brain_ask` handler `mcp-server-brain/lib/brain-ask.cjs` -- was never updated; it still returned the ORIGINAL raw search-hits payload `{question, keyword, source, count, results}` from commit dc363c54 (pre-Phase-127). With no `directive` key in the server response, the wrapper's `buildDirective` pass-through branch never fired and it fell through to its documented empty GUIDED scaffold (`directive.guided={questions:[],framework:null,stage:null}`, `next_gate.options=[]`, `mode_rationale:"default_guided_pedagogical_canon"`) on every call. The empty envelope was correct-by-design wrapper behavior fed a contract-incomplete server payload. The capability map itself had drifted -- it marked the row "shipped (Phase 127)" when only the consumer half shipped.
- **Fix:** Augmented `mcp-server-brain/lib/brain-ask.cjs` with server-side directive synthesis. `buildDirectiveFromGraph(session, keyword, limit)` runs two READ-only bound-parameter Cypher queries: (1) best-matching Framework node for the question keyword; (2) that framework's outbound chaining edges (FEEDS_INTO/CHAINS_TO/CO_OCCURS/PRECEDES/NEXT). It builds `directive.guided.{questions, framework, stage}` -- each chain target becomes a reframing question, the framework's beautiful_question seeds an opening question, chained frameworks become `next_gate.options` as F.1 "Run Methodology" verbs. `deriveModeSignals(question)` derives mode_signals from generic phrasing only (GUIDED default preserved). Returns directive + next_gate + mode_signals alongside the legacy `results` array (backward compatible). Graceful degradation: graph failure or no-framework-match omits the directive and the wrapper's empty scaffold becomes the honest "nothing to teach" signal. All Cypher uses bound parameters ($keyword/$frameworkName/$limit via neo4j.int()) -- the original string-interpolation pattern was removed, including the latent weakness on the Step 2 fallback path. Canon Part 8: READ-only sessions, zero write-Cypher, generic methodology only. IMPORTANT: the handler is served from mindrian-brain.onrender.com (render.yaml autoDeploy:true, connected to jsagir/mindrian-os-plugin) -- the fix takes effect at runtime only after the commit is pushed to origin/main and Render auto-deploys.
- **Files changed:** mcp-server-brain/lib/brain-ask.cjs
- **Pattern lesson:** A two-track Brain<->Plugin contract can be declared "shipped" when only one track lands. When a typed packet shape comes back structurally valid but content-empty, suspect a producer/consumer contract gap before suspecting the consumer wrapper -- check git history on BOTH the wrapper and the server handler, and check docs/CAPABILITY-MAP.md for a row that overclaims.

## mcp-servers-cache-missing-node-modules - MCP servers crash MODULE_NOT_FOUND on the first session after a plugin update
- **Date:** 2026-05-22
- **Error patterns:** MODULE_NOT_FOUND, Cannot find module, @modelcontextprotocol/sdk, node_modules, plugin cache, claude plugin update, MCP servers, Failed to connect, brain unreachable, startup-order race, npm install, lockfile, TOCTOU, stale threshold, dependency probe, vendored deps
- **Root cause:** `claude plugin update` lands a fresh plugin cache with no node_modules (neither marketplace git-clone nor npm tarball ship dependencies). A reconcile hook installs them, but it ran ASYNC so Claude Code spawned the alwaysLoad MCP servers before the ~3s npm install finished -- both servers crashed at module load. The repair mechanism also had a cross-platform defect (bare spawnSync('npm') is dead on Windows where npm is npm.cmd, fragile on Mac under GUI-launch PATH gaps). A later code review of the self-heal backstop found three more correctness bugs: bug_004 non-atomic lock creation (openSync('wx') + separate writeSync left a zero-byte window a peer misread as corrupt and unlinked the live lock); bug_001 stale threshold (90s) shorter than the 120s install timeout with an OR-gated reclaim check (false-stale reclaim of a healthy long install); bug_011 dependency probe limited to sdk+zod (a partially-populated node_modules passed the probe, no heal ran, a deeper require crashed).
- **Fix:** Hybrid B+D. PART 1 vendored production node_modules shipped with the tagged marketplace artifact (release.sh Step 6.7 `npm ci --omit=dev` into Commit A only; main HEAD stays clean) -- deps present the instant the cache lands. PART 2 portable self-heal backstop: lib/core/npm-cli-resolve.cjs runs npm via its absolute npm-cli.js off process.execPath (no PATH, no .cmd, no shell:true). Reconcile hook flipped to async:false + ordered first. PART 3 backstop correctness: bug_004 atomic lock via fs.linkSync of a fully-written temp file + readLock three-way EMPTY/corrupt distinction; bug_001 STALE_THRESHOLD_MS 90s->180s, WAIT_TIMEOUT_MS 100s->200s, isReclaimable() AND-gate (reclaim only when BOTH old AND owner-dead); bug_011 productionDepNames() probes the full package.json dependencies set. semver promoted devDependency->dependency (it crashed /mos:doctor on production-only installs).
- **Files changed:** lib/core/npm-cli-resolve.cjs, lib/core/npm-cli-resolve.test.cjs, lib/core/npm-install-lock.cjs, lib/core/npm-install-lock.test.cjs, lib/core/mcp-dep-heal.cjs, lib/core/mcp-dep-heal.test.cjs, scripts/sessionstart-npm-reconcile.cjs, scripts/release.sh, scripts/verify-release, scripts/doctor.cjs, package.json, package-lock.json, CHANGELOG.md, .claude/includes/release-process.md, hooks/hooks.json, bin/mindrian-brain-mcp-client.cjs, bin/mindrian-mcp-server.cjs

## brain-topk-uncapped-advisory - Brain forwards caller topK to Pinecone with no Brain-side cap
- **Date:** 2026-05-23
- **Error patterns:** brain_ask, brain_search, topK, Pinecone forward, uncapped, BRAIN_MAX_TOPK, Math.min, D-MOAT-2, moat inheritance, result-set cap, Phase 127.2
- **Root cause:** `mcp-server-brain/lib/brain-ask.cjs:545` and `mcp-server-brain/lib/pinecone-tools.cjs:42` forwarded caller-supplied `topK` directly to Pinecone with no Brain-side guard. Pinecone enforces its own server-side cap, so the moat against runaway result sets was INHERITED, not OWNED. D-MOAT-2 (timeout + row cap + byte cap) was enforced on the Neo4j curated-op path / brain_query / brain_schema, but the Pinecone path was uncapped at the Brain layer. Windows beta-tester deep audit (2026-05-23) confirmed by running `brain_ask({topK: 999999})` and observing no Brain-side truncation.
- **Fix:** Added `BRAIN_MAX_TOPK` env var with default cap = 100. `const MAX_TOPK = parseInt(process.env.BRAIN_MAX_TOPK || '100', 10); const limit = Math.min(topK || 5, MAX_TOPK);` in both brain-ask.cjs (around line 545) and pinecone-tools.cjs (around line 42). Naming matches the existing BRAIN_CYPHER_MAX_ROWS family from D-MOAT-2. Server-side change deploys to mindrian-brain.onrender.com on next Render auto-deploy from origin/main.
- **Files changed:** mcp-server-brain/lib/brain-ask.cjs, mcp-server-brain/lib/pinecone-tools.cjs, .planning/debug/resolved/brain-topk-uncapped-advisory.md
- **Pattern lesson:** The Brain must OWN its moats, not INHERIT them from upstream services. Upstream caps can change without notice. Every Brain query surface that forwards a caller-controllable limit needs a `BRAIN_MAX_*` env var guard at the forward site.

## stale-install-cache-audit-anti-pattern - audits reading source from stale install cache produce false-positive findings
- **Date:** 2026-05-23
- **Error patterns:** install cache, ~/.claude/plugins/mindrian-os, stale source, deployed wire, source-of-truth mismatch, false positive, NF-2026-05-23-01, RCA-TEMPLATE, Source-of-Truth Preamble, Windows beta-tester, audit harness, Phase 127.2
- **Root cause:** QA audits that read source code from the marketplace install cache (`~/.claude/plugins/mindrian-os/`) instead of the live deployed surface produce false-positive findings when the install cache is older than the fix that closed the gap. The 2026-05-23 deep-audit pass surfaced TWO false positives (NF-2026-05-23-01 and the curated-op-surface-missing claim) because the auditor's source read landed in a pre-fix install cache (plugin beta.24) while their wire probe hit the post-fix deployed Brain server (beta.25). Both invalidated findings traced to the same install-cache-vs-deployed-server delta. Pattern WILL recur every time a fix chain lands after a marketplace cache is cut.
- **Fix:** Process fix, not code fix. Shipped `## 2.5. Source-of-Truth Preamble (MANDATORY)` section in `docs/RCA-TEMPLATE.md` requiring every QA / audit prompt to declare (a) which source-of-truth its CODE claims read against, (b) which source-of-truth its WIRE claims probe against, (c) the date of audit, (d) re-verification rule against origin/main HEAD before filing. Added checklist row `- [ ] Source-of-Truth Preamble filled before any finding filed`. The Preamble does not prevent the delta from existing -- it makes the delta VISIBLE so reconciliation happens BEFORE findings are filed.
- **Files changed:** docs/RCA-TEMPLATE.md, .planning/debug/resolved/stale-install-cache-audit-anti-pattern.md
- **Pattern lesson:** Every QA audit must declare its source-of-truth before its findings can be trusted. Install cache and deployed wire diverge by an unbounded amount after a marketplace cut. ## windows-room-registry-path-normalization-gap -- bash $REGISTRY_FILE POSIX paths leak into Python open() on Windows + Git Bash
- **Date:** 2026-05-23
- **Error patterns:** /mos:rooms list, scripts/room-registry, FileNotFoundError, /c/Users/, Git Bash, POSIX path, python3 -c, open(), $REGISTRY_FILE, Windows, normwin, sys.platform, normpath, $HOME, cygpath, Instance #4, post-beta30-regression, windows-tester
- **Root cause:** `scripts/room-registry` embeds `python3 -c "..."` invocations at 8 subcommand stanzas (`create`, `read`, `list`, `update`, `set-active`, `archive`, `get-active`, `git-config`). Each interpolates bash-resolved `$REGISTRY_FILE` (computed from `$HOME + relative components`) into the Python source as a string literal. On Git Bash for Windows, `$HOME` carries POSIX form (`/c/Users/PC`), so the resolved path is `/c/Users/PC/MindrianRooms/.rooms/registry.json`. Bash and Linux Python resolve this. Windows Python's `open()` does not -- it treats the leading `/` as drive-root and the `/c/` prefix as a directory name. Result: `FileNotFoundError: [Errno 2] No such file or directory: '/c/Users/PC/MindrianRooms/.rooms/registry.json'` on every Windows + Git Bash user, on every registry subcommand. Silent for non-Windows users. Caught only on Jonathan's dogfood machine.
- **Fix:** Inlined `normwin()` Python helper at the top of every `python3 -c` block in `scripts/room-registry`. The shim is platform-detection-driven (`sys.platform == 'win32'`) so it's a no-op on Linux/macOS + WSL + native bash, and converts `/c/Users/...` -> `C:\Users\...` only on Git Bash for Windows. Every `open(...)` call inside each block was rewritten to `open(normwin(REGISTRY_FILE))`. Sibling sweep patched `scripts/reapply-modifications` (4 sites, single `$NORMWIN_SHIM` bash-var-string reused across all four `python3 -c` invocations). Deferred sweep flagged `scripts/verify-release` (4 sites), `scripts/learn-from-usage`, `scripts/track-analytics` (out of plan scope, logged to phase deferred-items).
- **Files changed:** scripts/room-registry, scripts/reapply-modifications, tests/test-room-registry-windows-path.cjs, tests/test-127.2-04-windows-path-and-update-activation.sh, .planning/debug/resolved/windows-room-registry-path-normalization-gap.md, .planning/debug/knowledge-base.md, docs/install-cache-family-premortem.md, CHANGELOG.md
- **Pattern lesson:** Any bash script that embeds `python3 -c` / `python3 << EOF` and interpolates a `$BASH_VAR` carrying a filesystem path into `open(...)` is broken on Windows + Git Bash. The `$HOME` (and every path derived from it) carries POSIX form (`/c/...`) which Windows Python's `open()` cannot resolve. The fix is a 4-line `normwin()` shim, platform-gated to be a no-op everywhere except Windows. When auditing or writing new bash scripts that embed Python, ALWAYS check for `open('$BASH_VAR')` / `open(normwin('$BASH_VAR'))` -- the latter is the new convention. Cross-platform CI matrix should include Windows + Git Bash; without it, this class of bug ships silently for the entire Windows user base for an unknown number of releases.

- **Fix:** `scripts/resolve-room` gained an opt-in `--strict` flag -- a bare Strategy-2 fallback now prints `FALLBACK:<path>` and exits 2 under `--strict`, distinguishable from a real registry hit, with zero behavior change for existing callers that omit the flag. `skills/rooms/SKILL.md` Step 2's legacy-room adoption prompt was tightened to the same "FIRE THE CARD -- mandatory" doctrine `/mos:ignite`'s B1/B2 gates use, with an explicit warning against narrating room creation before `birthRoom()` returns `{ok:true}`, and the routing note's Step 2 mislabeling ("name/slug capture") was corrected. Extending `check-card-fire.cjs` to detect "claimed a gated state-mutation's success with no corresponding filesystem/registry evidence" was scoped out as a larger structural follow-up, not attempted here.

## eureka-domain-swap-invariant -- Eureka candidate-pair generation admitted `Section` folder nodes as pairing endpoints, so a content node ranked against its OWN containing section produced self-referential "problem-definition x problem-definition" pairs the critic rejects as domain_swap_invariant
- **Date:** 2026-07-17
- **Error patterns:** domain_swap_invariant, eureka portfolio report, problem-definition x problem-definition, self-referential opportunity pair, Section container node, folder node paired against filed content, SCAFFOLD_NODE_TYPES both-scaffold only, step-4b candidate-pair exclusion, 260715-0nj precedent, container_pairs_excluded, room-native substrate, ranked list dominated by folder-label pairs, iia-deeptech-centers, older-schema top-level folders materialized as Section nodes, Seam 3.
- **Root cause:** The candidate-pair GENERATION layer in `scripts/eureka-portfolio-report.cjs` admitted `Section` container nodes (the room's own top-level folder nodes, present in older-schema rooms that materialized each top-level folder as a graph node) as legitimate pairing endpoints. A `Section` node's text is its folder slug (`props.name`), so the encoder embeds it and it enters the pairing pool exactly like a content node. The ONLY generation-layer node-type filter was the 260715-0nj both-scaffold exclusion, which drops a pair only when BOTH endpoints are in `SCAFFOLD_NODE_TYPES = {memory_artifact, Artifact}`; `Section` is absent from that set, so every Section-involving pair survived. A real content node (an Artifact filed inside `problem-definition/`) then got paired against the `problem-definition` FOLDER node itself; both sides derive the same slug and the Phase-212 critic correctly fires `domain_swap_invariant`, but only AFTER the degenerate pair has consumed a ranked-list slot. On the real navigator room iia-deeptech-centers this made all 25/25 top-ranked pairs Section-involving noise (rank-1 = Artifact `problem-definition/software-barrier-collapse` x Section `problem-definition`, 1575 of 16005 candidate pairs = ~9.8 percent). The prior 216-04 fix had cleaned the LABEL (stopped `row.type` leaking literal "Section x Section" prose) but never stopped the PAIRING, which is why the statement read `problem-definition x problem-definition` (slug) rather than `Section x Section` (type). The critic was never wrong; nothing upstream used the same signal to drop these at generation.
- **Fix:** Extended the EXISTING 260715-0nj exclusion at the SAME step-4b insertion point (Reuse-Before-Build, Canon Part 7) rather than inventing a second mechanism or touching the critic. Added a frozen `CONTAINER_NODE_TYPES = {Section}` set next to `SCAFFOLD_NODE_TYPES`; added an ADDITIVE EITHER-endpoint branch in the step-4b filter loop (checked before the both-scaffold check): if either endpoint is a Section node, skip the pair and increment an honest `containerPairsExcluded` counter; surfaced `container_pairs_excluded` in the provenance object and the report table, mirroring `scaffold_pairs_excluded`. EITHER-endpoint (vs the scaffold precedent's BOTH-endpoint) is deliberate and comment-documented: a single Artifact carries real filed content so a one-Artifact pair is legitimate, but a Section is only a folder label, never a valid endpoint on either side. Live-verified with the real encoder (MongoDB/mdbr-leaf-ir, sqlite-vec): iia-deeptech-centers `container_pairs_excluded=1575`, `pairs_scored` 16005 -> 14430 (exact), ranked Section-involving 25/25 -> 0/25, `scaffold_pairs_excluded` unchanged at 105. aion-eureka-synergy (0 Section nodes) is a TRUE no-op, proven by byte-identical json+md vs a determinism-controlled pre-fix baseline except the single new `container_pairs_excluded:0` line. Regression delta zero (git-stash A/B; the step-4b precedent test test-218-scaffold-pair-filter.cjs passes 2/2). Explicitly OUT of scope and flagged, not fixed: the percentile-population concern (Section nodes also sit in the scaffoldCohort percentile population, mildly skewing ranks) and a newly-surfaced distinct pattern (with container noise removed, iia's top is now dominated by one strong Artifact ranked at an identical AHP score against many interchangeable WhitespaceZone hypothesis nodes -- 156 of 180 nodes = 87 percent of the room -- a separate, milder scoring-differentiation issue, not the same bug).
- **Files changed:** scripts/eureka-portfolio-report.cjs, .planning/debug/resolved/eureka-domain-swap-invariant.md (moved), .planning/debug/knowledge-base.md.
- **Pattern lesson:** A node-type exclusion written as "both endpoints must be type X" (the scaffold rule) silently leaves a whole degenerate class open when a DIFFERENT type needs an EITHER-endpoint rule -- here a `Section` folder node is never a valid endpoint on either side, so the both-endpoint shape of the nearest precedent was the wrong shape to copy blindly. When extending an existing type-filter to a new node type, first ask whether the new type is content-bearing on its own (then both-endpoint, like Artifact) or a pure structural label (then either-endpoint, like Section); the scope difference is the whole fix. Also: when a fix removes the dominant noise class, RE-READ what surfaces underneath before declaring victory -- removing the Section pairs here immediately exposed a second WhitespaceZone-dominance pattern that was previously buried, which is a real (separate, tracked) finding, not proof the fix failed. And a downstream critic that "correctly rejects" a degenerate class is a symptom the class is being GENERATED upstream: the durable fix drops it at generation so it never consumes a ranked slot, rather than relying on the critic to catch it after the fact.
