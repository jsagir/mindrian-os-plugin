## Findings

### Finding A: Mindrian website shows v1.13.0-beta.26 AND v1.13.0-beta.27 simultaneously

**Verdict:** NEW FAILURE (low severity, UX-affecting, design-tension class)

**Symptom:** https://mindrianos-jsagirs-projects.vercel.app/ renders both version strings somewhere on the page.

**Root cause:** the website's `getLatestVersion()` async resolver in `website/src/lib/version.ts:39-52` fetches GitHub raw `plugin.json` first (priority 2 of 4). Plugin main HEAD currently shows `1.13.0-beta.27` (the Commit B placeholder bumped by `release.sh` Step 7.5 after every release cut, per the 7-place lockstep contract). The sync `getVersion()` callers fall through to `FALLBACK_VERSION = "v1.13.0-beta.26"`. Result: two version strings rendered in different places on the same page.

The resolver comment at lines 7-9 says this is intentional ("This is the DEV truth -- the version on this commit of the plugin, regardless of whether it has shipped to npm yet"). But the side effect is users see `beta.27` on the marketing site while npm `@next`, marketplace install, and install minisite all serve `beta.26`. The "phantom beta.27" is an artifact of the Commit B convention.

**Required code changes (THREE candidate paths):**

1. **Resolver-priority swap (recommended for a marketing site):** in `website/src/lib/version.ts`, change `getLatestVersion()` to call `fetchFromNpm()` BEFORE `fetchFromGitHub()`. Site shows what users can actually install; GitHub raw becomes the third-line fallback. ~3 line change.
2. **Vercel env-var pin (quick fix):** set `NEXT_PUBLIC_MINDRIAN_VERSION=v1.13.0-beta.26` on Vercel; resolver short-circuits at priority 1. Manual bump every release.
3. **Drop the Commit B next-pre-release bump:** keep main HEAD at the released version, no placeholder. Larger release-pipeline change; affects every consumer of plugin.json's "current" version on main.

**Tests:** after fix, `curl -s https://mindrianos-jsagirs-projects.vercel.app/ | grep -oE 'v1\.13\.0-beta\.[0-9]+' | sort -u` must return exactly one line.

**Non-code follow-ups:** decide whether the website should reflect "what's installable" (path 1) or "what the team is currently developing" (current behavior).

### Finding B: doctor --acceptance reports `version-of-record-published` FAIL

**Verdict:** PROCEDURAL FAIL (not a real regression; correct-by-design tension)

**Symptom:** `node scripts/doctor.cjs --acceptance` reports `FAIL version-of-record-published -- git tag v1.13.0-beta.27 not found`.

**Root cause:** doctor checks that the CURRENT (main HEAD) version has a corresponding git tag. After every successful release, Commit B bumps main HEAD to the next pre-release placeholder (`beta.27` in this case), which by definition has NO tag because it has not been released. The doctor's assertion conflicts with the release-pipeline contract.

**Required code changes:** `scripts/doctor.cjs` `acceptance.version-of-record-published` should distinguish "main HEAD" from "last shipped tag" and check the latter. The shipped tag IS at `v1.13.0-beta.26`, which IS present. ~10 line fix in doctor's acceptance harness.

**Tests:** post-fix, doctor --acceptance should PASS this gate after a `Commit B` placeholder is in place.

### Finding C: doctor --acceptance reports `npx-roundtrip` FAIL (exit 127)

**Verdict:** PROCEDURAL FAIL (harness invocation pattern, not a real npm regression)

**Symptom:** `node scripts/doctor.cjs --acceptance` reports `FAIL npx-roundtrip -- npx round-trip failed (127)`.

**Root cause:** the doctor's npx round-trip invokes `npx @mindrian_os/install` with arguments that the installer's own bootstrap path then forwards to `claude`, which rejects them (`error: unknown option '--version'`). The npm package IS published and resolvable (verified independently via `npm view @mindrian_os/install@1.13.0-beta.26 version`). The roundtrip test surfaces a Claude CLI flag incompatibility, not a missing npm artifact.

**Required code changes:** `scripts/doctor.cjs` `acceptance.npx-roundtrip` should test for `package downloads + exits 0 from a no-op invocation`, not `claude --version round-trip`. ~5 line fix.

**Tests:** post-fix, doctor --acceptance should PASS this gate against the published v1.13.0-beta.26 package.

### Finding D: `~/mindrianos-install-site` has no `origin` remote (release.sh Step 9.6 hard-aborts)

**Verdict:** KNOWN ENV GAP (already in memory: `feedback_install_minisite_lockstep.md` flagged "wire up a git remote" as a future cleanup)

**Symptom:** `release.sh --prerelease` hard-aborts at Step 9.6 with `/home/jsagi/mindrianos-install-site has no 'origin' remote configured`.

**Root cause:** the minisite repo was set up locally without a GitHub remote. Vercel deploy still works (CLI-driven via `vercel --prod --yes`), but the script's tag-push verification step has no remote to push to.

**Workaround applied during v1.13.0-beta.26 cut:** ran `vercel --prod --yes` manually after script abort. Live minisite at https://mindrianos-install-site.vercel.app now serves `v1.13.0-beta.26`.

**Required code changes:** none in repo. **Non-code follow-up:** create a GitHub repo for `mindrianos-install-site`, push initial history, add as `origin`, then `release.sh --prerelease` Step 9.6 will complete autonomously.

### Finding E: BRAIN_MAX_TOPK cap not yet smoke-tested against live Brain wire

**Verdict:** INFERRED-EXPECTED (source state correct; wire state needs out-of-band raw-HTTP probe)

**Symptom:** the BRAIN_MAX_TOPK guard is verifiably present in `mcp-server-brain/lib/brain-ask.cjs:551` + `pinecone-tools.cjs:43` on origin/main. Render auto-deploys mcp-server-brain from origin/main; the commit landed ~12 minutes before audit. MCP brain_search schema caps client-side `topK` at 50, below the new server-side `MAX_TOPK=100` default, so the cap activation cannot be observed through the MCP interface.

**Root cause:** none; this is testing-tool coverage gap, not a defect.

**Required code changes:** none. **Non-code follow-up:** out-of-band raw-HTTP probe to mindrian-brain.onrender.com with `topK: 200` to confirm response is bounded to `<=100`. Worth running ~30 min after Render auto-deploy completes.
