## Problem Statement

The Stop-hook `scripts/check-card-fire.cjs` force-blocked a turn that contained no unanswered Decision Gate: the F.8 room-binding card had already been fired via a real `AskUserQuestion` tool call and answered by the navigator in the immediately preceding turn, but the very next (unrelated, status-update) turn was still force-intercepted as if that same gate were pending and unanswered.

## Symptoms

expected: once a Decision Gate is fired via `AskUserQuestion` and the navigator answers it, no subsequent turn should be force-blocked for that same already-resolved gate.
actual: the turn immediately after firing and answering the F.8 room-binding gate (two questions: "Which room(s) should this session write to?" and "Remember this binding?", both answered) was blocked by the Stop hook with reason `rendering your choices as a selectable card` and `additionalContext` demanding a re-fired `AskUserQuestion` card, even though the assistant's actual output that turn was plain status prose with zero option-shaped content and zero ASCII-box glyphs.
errors: `Stop hook error: rendering your choices as a selectable card` / `Stop hook feedback: This turn REACHED a Decision Gate but did NOT fire the interactive card.`
reproduction:
  1. Trigger an F.8 binding gate (session unbound, room-selection prompt fires via `scripts/intent-classifier.cjs`'s `emitBindingGate`).
  2. Fire `AskUserQuestion` for it in that same turn and answer it (real navigator response, e.g. "Dev-repo only, no room" + "Yes, keep it bound").
  3. In the VERY NEXT turn, produce ordinary prose with no card, no gate, no ASCII box (e.g. a plain status update on unrelated background work).
  4. Observe: Stop hook still fires `decision:'block'` on step 3's turn.
started: observed 2026-07-22, plugin version 1.15.3-beta.37. Not yet bisected to a specific commit; the TURN_FRESH_MS mechanism it exposes a gap in was introduced 2026-07-20 (`card-fire-over-enforcement` fix), so this gap has existed at least since that commit landed and was not caught by that fix's own test suite (which tested stale-vs-fresh timing, not answered-vs-unanswered state).

## Technical Root Cause

CONFIRMED against CURRENT HEAD (a49d7928, v1.15.3-beta.51) by source trace, by the live `card-fire-intercepts.log` telemetry, and by deterministic reproduction.

**The record had no lifecycle.** `lib/core/card-fire-sidechannel.cjs` recorded a gate mint (`{ entry, shape, ts, subject }`) and provided exactly ONE way for that record to ever leave the store: the 10-minute `TTL_MS` expiry in `pruneStore`. There was no `consume`, no `resolve`, no `answered` marker, and no writer for one. So the record did not mean "a gate is pending" -- it only meant "a gate was rendered at time T". `scripts/check-card-fire.cjs` then treated that as a standing obligation on every Stop evaluation inside the 2-minute `TURN_FRESH_MS` window.

**Why every existing escape hatch structurally cannot cover it** (each checked in source against this exact shape):

- `askuserquestion_fired` is CURRENT-TURN scoped. `readTranscriptTurn` resets `currentTurnAssistantContents` at every `role:user` record, so a card fired and answered in turn N is invisible to turn N+1's Stop hook by construction.
- `gate-already-answered` derives `gateLabels` from THIS turn's `outputText`. On a no-card prose turn that is `[]`, and `gateAlreadyAnswered` returns false at its `labels.length === 0` guard before any comparison happens.
- `gate_is_fresh` encodes elapsed time since mint, never pending-state. A gate answered 30 seconds ago and a gate still sitting unanswered 30 seconds ago are byte-identical to it. Worse, the producers RE-MINT (three F.1 records with the same subject at 421s/421s/313s in one live session), so each re-mint re-arms the window.
- `preceding-turn-synthetic-no-user-engagement` (18cc8b8b) only fires on a CONFIRMED `'tool_result'` classification. A background task-notification that carries a real text block classifies as `'typed'` and falls straight through -- which is why the 2026-07-28 instance survived that fix.
- `gate-irrelevant-to-turn` is weakened independently by the two chrome/blob findings above, so it rarely reaches its `false` verdict.

**Why the four interim fixes all missed it.** beta.38 through beta.51 each tuned a DIFFERENT axis: which regex arm counts (5431b7e9), whether the preceding record is synthetic (18cc8b8b, 0d47ed6d), and the envelope schema (f63d1ddc). None of them touched the record's lifecycle, because the lifecycle was never the axis under examination. That is the pattern the knowledge base already warned about: five consecutive one-off patches to `classifyCardFire`'s pass-reason chain, each closing one narrow gap while the structurally adjacent one stayed open.

## Resolution

root_cause: the side-channel reached-gate record had NO lifecycle. Its only exit from the store was the 10-minute TTL, so a record meant "a gate was rendered at time T", never "a gate is still pending". `scripts/check-card-fire.cjs`'s PRIMARY arm treated that as a standing obligation on every Stop evaluation inside the 2-minute `TURN_FRESH_MS` window -- including turns after the card had already been fired and answered. No existing escape hatch could cover it: `askuserquestion_fired` is current-turn scoped, `gateAlreadyAnswered` reads labels from a prose turn's empty output, and `gate_is_fresh` measures elapsed time rather than pending-state (and is re-armed by re-mints).

fix: gave the record a lifecycle. `consumeReachedGates` (new, in `lib/core/card-fire-sidechannel.cjs`) spends a session's records; `consumeReachedGatesForVerdict` (new, in `scripts/check-card-fire.cjs`) calls it on TERMINAL verdicts only (card-fired, no-gate-signal, any relevance pass, bounded-escape degrade) and deliberately NOT on `intercept:true`, so an active force-loop still converges to `MAX_FORCE_RETRIES`. The MCP `stop-gate-handler.cjs` wraps the same primitive so the two enforcement paths cannot drift. The `classifyCardFire` predicate itself is unchanged and remains pure.

verification: 25/25 in `tests/test-209-primary-sidechannel.cjs` (9 new fixtures covering both directions across a 3-turn bleed span). Behavioral before/after over the real live sequence: 3 spurious blocks pre-fix, 0 post-fix, with the never-answered gate still forcing through the full retry loop. 11 related card-fire suites PASS; MCP suite 12/12 PASS. The 3 failures in the 209/210 roll-ups are all reproduced with every change stashed and are pre-existing and unrelated. Connector, render-coverage and projection gates PASS. Zero em-dashes added; Canon Part 8 holds.

files_changed: [lib/core/card-fire-sidechannel.cjs, scripts/check-card-fire.cjs, lib/mcp/stop-gate-handler.cjs, tests/test-209-primary-sidechannel.cjs]

residual_risk: the fix is dev-repo only and is not live for any install until a release ships.
