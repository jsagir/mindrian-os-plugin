# SEED-077 - Feynman-MINTO wired into the graph: per-artifact queryable explanation sentence

> Framing (navigator, 2026-07-28, live conversation during the v1.16.0 infrastructure
> remediation session): Feynman-MINTO today lives as one MINTO.md per section, generated by
> /mos:reason. The navigator's proposal: wire it into room.db itself, so EVERY artifact node
> carries its own Feynman-MINTO-style plain-English explanation sentence, grounded in the
> artifact's actual relevant entities/edges in the graph, queryable by both the local room.db
> graph and (in generic, non-content form) by the remote Brain graph.

**Registered:** 2026-07-28 (navigator-directed, live conversation during v1.16.0 planning)
**Class:** ARCH + PRODUCT | **Status:** seed
**Grounding:** `lib/core/navigation.cjs` + `room.db` (the typed-edge graph), `lib/memory/feynman-prompts.cjs`
(the four Feynman prompt stages), `lib/core/feynman-minto-invariants.cjs` (structure enforcement),
the Phase 150 memory cortex (`memory-artifacts.cjs`, `memory-events.cjs`), and this session's own
Feynman-MINTO scrutiny (found MINTO.md is section-granular, not artifact-granular, and its debounce/
guardian pipeline currently has no per-artifact hook at all).

## The gap this closes

Feynman-MINTO's current unit of explanation is a SECTION (`MINTO.md`), not an artifact. A room with
20 artifacts in `problem-definition/` gets one governing-thought narrative for the whole section, not
20 individually-queryable "here is what this specific artifact is and why it matters" sentences. That
means:
- The graph (`room.db` nodes/edges) knows an artifact's TYPE, provenance, and cross-refs, but has no
  first-class plain-English EXPLANATION field a query can retrieve directly.
- A retrieval-style query ("what is this artifact and why is it here") today has to reconstruct the
  answer from raw node/edge data plus the section-level MINTO.md narrative, rather than reading one
  stored, queryable sentence.

## The proposed shape (navigator's framing, needs research before planning)

For each artifact node in room.db, generate and store a short Feynman-style explanation sentence,
derived from the artifact's own relevant entities and edges (its neighborhood in the graph, not the
whole section). Store it as queryable data (a node property, or a new lightweight table) so:
- The LOCAL graph can retrieve it directly per-artifact (no MINTO.md re-parse needed).
- The REMOTE (Brain) graph can query it too, but ONLY in whatever generic/typed form Canon Part 8
  already permits (Brain never gets raw artifact prose; if this crosses to Brain at all it must go
  through the same typed-packet/generic-methodology boundary every other Brain-bound data already
  respects, e.g. via memory-cortex-packet.cjs's ids/hashes/enums-only discipline, NOT free text).

## Open questions for research / plan (do not skip these before scoping a phase)

1. Where does the sentence live: a new column on the existing node row, or a new `artifact_explanation`
   table keyed by node id? Migration cost either way, in-scope for whichever the Part 9 chokepoint
   (`navigation.cjs`) should own.
2. Who generates it, and when: /mos:reason today runs per-section on demand. Per-artifact generation
   at THIS granularity is a much higher volume of LLM calls (one per artifact vs one per section) -
   needs a debounce/batch design, and this session's own audit already found the EXISTING section-level
   debounce/guardian pipeline has real, still-partially-open defects (F-1, F-2 in the infra audit,
   phase 241 of the v1.16.0 roadmap). Do not build a second debounce mechanism before phase 241 lands;
   reuse whatever comes out of it.
3. What crosses to Brain, if anything: this needs an explicit Part 8 design pass BEFORE any
   implementation, per the same discipline SEED-076 already flagged for its own Gemini-driver piece.
   Default assumption: the raw sentence text stays LOCAL only; only a generic, typed signal (e.g. "this
   node has an explanation, length N, generated on date D") could ever be Brain-queryable, mirroring
   memory-cortex-packet.cjs's existing ids/hashes/enums-only pattern.
4. Relationship to SEED-076 (room-as-GraphRAG conversational component): SEED-076 is the bigger,
   external-LLM-driven "talk to your room" vision built on Phase 211 tri-modal retrieval. This seed
   is narrower and more local: it is about the DATA MODEL, giving every artifact a first-class,
   graph-native explanation rather than only a section-level narrative. If SEED-076 ever gets built,
   per-artifact explanations from this seed would be exactly the kind of provenance-rich retrieval
   unit its "answers cite provenance" differentiator wants. Sequence-wise, this seed could ship
   independently and would make SEED-076 stronger if it ships first, but neither blocks the other.
5. Does this actually need new generation at all, or can it be DERIVED from data the graph already
   has? Verify against `lib/core/navigation/memory-artifacts.cjs` and the existing `governing_thought`
   node type before assuming net-new LLM calls are required (Canon Part 7: reuse before build).
