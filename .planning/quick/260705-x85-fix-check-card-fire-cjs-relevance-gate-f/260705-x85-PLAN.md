# Quick Task 260705-x85: Fix check-card-fire.cjs relevance-gate false positive

## Problem (root cause, already confirmed live)

`scripts/check-card-fire.cjs::classifyCardFire()` runs the Phase 210-05 relevance
gate right before its final intercept:

```js
const gateLabels = gateRelevance.extractOptionLabels(outputText);
if (gateRelevance.gateAlreadyAnswered(precedingUserText, gateLabels)) { ... }
if (!gateRelevance.gateTopicallyRelevant(precedingUserText, outputText)) { ... }
```

`outputText` is the CURRENT TURN's assistant reply (from `readTranscriptTurn`'s
`lastAssistantText`). For a PRIMARY-signal detection (a registry gate-reaching
surface recorded via `lib/core/card-fire-sidechannel.cjs`, `ran_entries`
non-empty), the model is instructed elsewhere (SEED-021) to NEVER reproduce a
stale gate's own subject text/labels in its reply once it judges the gate
irrelevant. So `outputText` is just the model's ordinary reply to the CURRENT
user turn -- which naturally shares tokens with `precedingUserText` (an
assistant answering a question echoes the question's topic back). The result:
`gateTopicallyRelevant(precedingUserText, outputText)` returns `true` (looks
relevant) almost every time on the PRIMARY path, REGARDLESS of what the stale
reach is actually about, because it is comparing the user's turn against the
assistant's own reply to that turn, not against the reach's real subject.

Confirmed live: the same stale reach (`rethinking-mindrianos` /
`governing_thought:solution-design`) re-fired and force-blocked 3 consecutive
turns in one session on 2026-07-05 regardless of what the user was actually
discussing (interns' homework, then a Gmail draft, then this exact bug).

Investigated `lib/core/card-fire-sidechannel.cjs::recordReachedGate` (the
PRIMARY producer): it currently persists only `{ entry, shape, ts }` -- no
human-readable subject text. Its own header doctrine explicitly says "zero
user text, zero room content" (Phase 209-06 design decision). That absence IS
part of the root cause: there is no real subject text available today to
compare against.

Checked the three call sites (`grep recordReachedGate\(`):

1. `lib/hmi/selector-dispatcher.cjs` pickShape trailer door (~line 1082): has
   `result.rendered.zones.header` / `.body` in scope at the exact call site --
   the real rendered gate content (independent of what the model later says).
2. `scripts/intent-classifier.cjs` engine arm (~line 1103): has `rendered.text`
   (the dial's own rendered content from `presenter.renderDial`) in scope.
3. `scripts/intent-classifier.cjs` emitBindingGate F.8 (~line 2156): has
   `zones.header` / `zones.body` in scope (the F.8 renderer's own zones).

All three already compute genuinely real, human-readable gate subject text
before calling `recordReachedGate` -- it is simply not being captured. This is
a materially BETTER signal than `outputText` because it is the gate's own
content, not the model's downstream reply.

## Fix strategy (surgical, additive only)

1. `card-fire-sidechannel.cjs`: add an OPTIONAL, bounded `subjectText` field to
   `recordReachedGate`'s accepted opts, persisted (truncated) alongside the
   existing `{ entry, shape, ts }` scalars. Add a NEW export
   `readReachedGateSubjects(sessionId, opts)` that returns the recorded subject
   strings, completely separate from `readReachedGates` (whose bare
   entry-path-array return contract must NOT change -- `deriveTurnSignals`'s
   `ran_entries` assignment depends on it byte-for-byte).
2. Wire `subjectText` at the three producer call sites using the real rendered
   content already in scope there (header+body / rendered.text). No other
   param changes.
3. `check-card-fire.cjs::deriveTurnSignals` threads a new `gate_subject_text`
   field: direct-field envelope precedence (`e.gate_subject_text`, the
   unit-test seam) > side-channel-derived subject text (only when
   `ran_entries` itself came from the side-channel, i.e. the true PRIMARY
   path) > `''`.
4. `check-card-fire.cjs::classifyCardFire` calls
   `gateRelevance.gateTopicallyRelevant(precedingUserText, t.gate_subject_text || outputText)`
   -- i.e. prefer the real subject text when available (PRIMARY path), fall
   back to the existing `outputText` behavior when it is not (BACKSTOP path).
   `gateAlreadyAnswered`'s `gateLabels` (derived from `outputText`) and the
   `gateLabels.length === 2` binary-exemption check are LEFT UNTOUCHED -- only
   `gateTopicallyRelevant`'s second argument changes, exactly as the diagnosed
   fix specifies.

This keeps `turnContextHash`, `gateSignature`, the retry-key derivation, and
every BACKSTOP-path test byte-identical, while fixing the PRIMARY-path false
positive at its real source.
