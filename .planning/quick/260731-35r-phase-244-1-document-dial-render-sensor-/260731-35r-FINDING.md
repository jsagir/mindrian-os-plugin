# The reach dial's ranking is not wired to the sensor bank, and that is a deliberate scope boundary as of 2026-07-31

**Verdict in one line:** the sensor bank decides WHETHER the Shape F.7 reach dial renders at all;
it has zero influence on WHICH reach_id ranks top once it does. Those are two different things,
they run on two disjoint code paths, and until this artifact nothing in the repo said so out loud.

Nothing is broken. This is a scope call, taken deliberately and named here on 2026-07-31, not a
defect and not an oversight. What was missing was the sentence, not the code.

## 2. What is actually true in the tree today

Every claim below was read directly off the live checkout on 2026-07-31. Each carries the exact
line it came from so a skeptical reader can re-verify it without trusting a word of this artifact.

1. **`buildReachList` has exactly one definition in the whole tree:**
   `lib/hmi/dial-reach-orchestrator.cjs:290`. There is no second copy, no shadowing variant, no
   surface-specific fork. One function builds the dial.

2. **Its only score input is `roomState.reachScores`,** read by exactly one helper,
   `_resolveReachScore` (`lib/hmi/dial-reach-orchestrator.cjs:199-201`). Nothing else in the
   function reads a score from anywhere. If a signal is not in that map, it does not affect
   ranking, full stop.

3. **On the render path, `reachScores` is built exclusively by the cortex adapter.**
   `scripts/intent-classifier.cjs:1273-1274` assigns `cortexNodes` from context and then
   `reachScores = adapter.buildReachScoresFromCortex(cortexNodes)`. The only later mutation of that
   map is Phase 158-03's reject-penalty merge
   (`Object.assign(reachScores, reachPenalties.discountedScores)`), which DISCOUNTS scores the
   cortex already produced. It introduces no sensor-derived score. So every number that orders the
   dial comes from scoring the room's own graph nodes.

4. **The only `buildReachList` call site on that path is `scripts/intent-classifier.cjs:1341`,**
   and it is handed exactly the map from item 3. There is no second entry point where a sensor
   result could be merged in.

5. **The one REAL channel from the sensor bank to the dial is a visibility gate, not a ranking
   input.** Three facts, in sequence:
   - `decide()` does not assign `routing_source`. Verbatim from
     `lib/core/navigation-engine.cjs:1253`: "routing_source is NOT assigned here; flipped at the
     router layer when fire_skill is non-null (Phase 144)."
   - A fired sensor reach is what flips that value from `legacy` to `engine` downstream, at the
     router layer.
   - `renderEngineDecisionWithDial` early-returns the plain base block unless
     `routing.source === 'engine'` (`scripts/intent-classifier.cjs:1255-1260`).

   Read together: a sensor firing is the switch that turns the dial on. It is not a vote about
   what appears on the dial.

6. **Phase 244-04's tier-fusion work landed on a different function on a disjoint path.** It wired
   an optional `o.tierCandidates` seam plus `_applyTierFusion` into
   `lib/workflow/f-selector-ranker.cjs::rankForSelector`, supplied by
   `lib/core/orchestration-candidate-lift.cjs::buildTierCandidates`. Neither
   `f-selector-ranker.cjs` nor `orchestration-candidate-lift.cjs` touches `buildReachList` at all.

## 3. What Phase 244 did and did not fix

Phase 244 was real, correct work, and it is easy to over-read what it reached.

**What it did:** 244-04 wired sensor-derived tier candidates into the selector ranker, through the
`o.tierCandidates` seam on `lib/workflow/f-selector-ranker.cjs::rankForSelector`, supplied by
`lib/core/orchestration-candidate-lift.cjs::buildTierCandidates`. That is a genuine join between
the sensor bank and a ranker.

**What it did not do:** that ranker is not the dial. `rankForSelector` and `buildReachList` are two
different functions on two disjoint paths. Nothing in Phase 244 changed a single byte of what
`buildReachList` reads.

**Why this is a separate fact from what the phase already recorded.**
`244-RESIDUALS.md` Section 6 item 3 already notes that `rankForSelector` has exactly one live
tier-candidate supplier. That is a statement about the ranker's supply side. The fact recorded
here is different and additional: the DIAL has zero sensor supply at all, and that register does
not carry that anywhere. A reader who saw 244-04 wire tier candidates into a ranker could
reasonably conclude the sensor bank now influences the reach dial. It provably does not.

## 4. The named scope boundary

Stated without hedging, because a hedged boundary is not a boundary:

> **The sensor bank is a dial VISIBILITY gate. It is not a dial RANKING input.**

This is a deliberate scope call as of 2026-07-31. It is not a defect, not an oversight, and not a
regression. Nothing behaves wrongly today because of it. The dial ranks correctly by cortex-node
scoring, and the sensors gate it correctly through the `routing_source` engine arm. The only thing
that was wrong was the silence: a future reader tracing the code would have had to derive this
boundary themselves, and a future reader skimming Phase 244's changes would likely have assumed
the opposite.

Naming it converts a silent gap into a stated scope call with a flip condition. That is the whole
purpose of this artifact.

## 5. Flip conditions (what would reopen this for real work)

Both are written to be falsifiable and countable, not atmospheric. Either one firing is the signal
to stop patching and design the join properly.

**Flip 1, the seam patch count.** A THIRD reconciliation phase becoming necessary at the
fired-candidate-composition seam. Four patches have already landed at that same seam across four
different phases without ever unifying it:

| Phase | Patch at the same seam |
|-------|------------------------|
| 172-07 | the dead `trigger_tier` field (computed, consumed by zero rankers) |
| 222-02 | the Hedge/MWU reranker |
| 209-01 and 237-04 | the relevance gates |
| 244-04 | the `rankForSelector` tier fusion |

A fifth patch at that same seam is the signal. Four patches at one seam without a unification is
already a pattern worth reading; a fifth means the seam, not the patches, is the problem.

**Flip 2, the sensor census.** The sensor count crossing roughly 25 to 30 files. Baseline today:
**17 sensor implementations** in `lib/core/sensors/`. That directory holds 19 `.cjs` files, minus
`sensor-types.cjs` and `hat-scoping-table.cjs`, which are support modules rather than sensors. At
17, hand-coded per-sensor vocabularies are still tractable. Somewhere around 25 to 30 they are not,
and the composition problem stops being deferrable.

**Absent either condition, the narrow already-scoped work is the right call.** No fusion seam
should be built into `buildReachList`. Building one now would add a second selection brain to a
system whose architecture spine explicitly holds one governed reach path, which is a Canon Part 7
reuse-before-build problem as well as an architectural one.
