<objective>
Give a material_step gate exactly ONE resume owner, so the flow both tool descriptions
document actually works instead of dying at step two.

Today chain_run's own description says "To resume, call gate_answer with that gate_id",
and chain_run's schema also accepts a gate_answer payload threaded back in. Both paths
consume the SAME single-use ledger entry (lib/mcp/gate-ledger.cjs deletes on lookup, line
100). So the documented two-step flow -- ratify via gate_answer, then thread {gate_id,
chosen, verdict} into chain_run -- always fails: gate_answer burned the entry, and
chain_run answers unknown_or_expired_gate. gate_answer, for its part, writes a
gate_answer memory_event and returns; it never touches the entry's onStepFn, haltedStep
or restSteps, so the halted material step is stranded forever. The two test suites pin
the two halves separately and neither notices, because each drives only its own path.

Purpose: the WS-C4 line of docs/2026-08-19-PLAN-dual-graph-release.md. The Brain
recommends a chain, chain_run halts at the first material step, and a human has to be
able to approve it and have it actually run. Right now approving through the documented
verb runs nothing.

Output: gate_answer becomes the single resume verb for a material_step gate (it invokes
the chain's own execution path, it does not re-implement it); chain.cjs keeps sole
ownership of the execution logic; the single-use ledger stays untouched and becomes the
double-execution guard; both descriptions and both suites converge on the one flow.
</objective>
