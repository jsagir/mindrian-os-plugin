## Decisions made in planning (measured, binding for the executor)

### D1: the walk delegates to discoverSections, not to icm-forest.cjs
- PROVEN by reading lib/core/icm-forest.cjs: it has no function that lists files. listRoomRoots, enumerateChildBasenames and buildChildNode enumerate directories only, and buildChildNode recurses only across registered sub-rooms (.room-root), which the wiki must skip. Its own child source is discoverSections plus 3 other single-level readers.
- PROVEN by measurement: require('lib/core/icm-forest.cjs') costs 72 ms and loads node:sqlite (prints an ExperimentalWarning). section-registry.cjs costs 0.6 ms.
- Choice: the "discoverSections plus recursion" pattern that test-270's header names as the sanctioned reuse (lib/core/memory/reconcile-memory-runner.cjs walkFractalMemory, lines 174-194). At each level, a non-recursive helper lists the .md files of one folder, and discoverSections lists the child folders. The recursive function calls neither readdirSync nor any other directory reader itself. No depth constant (test-270 walker.3 keeps DEPTH_CAP in coverage-rollup.cjs only); recursion ends because no symlinked folder is ever entered.
- Section detection: the depth-1 loop stays as it is today (every non-skipped root folder is a section, including team and references). A nested page's section = the first path segment under the room root.

### D3: page id shape and every consumer
- id = room-relative path without .md, forward slashes (path.sep normalized for Windows). This is also the room.db artifact node id convention (lib/core/lazygraph-ops.cjs getArtifactId, line 382), so graph-links.cjs backlinks and graph-node clicks now point at real nested pages.
- Collision proof: section/name.md -> section/name; section/name/name.md -> section/name/name; section/other/name.md -> section/other/name. File paths are unique, so ids are unique.
- wiki-server.cjs: the 4 page routes use 2 named segments today (/wiki/:section/:page, /api/raw/:section/:page, /api/save/:section/:page, /api/backlinks/:section/:page). A nested id has 3 or more segments and gets a 404. PROVEN on Express 5.2.1 (scratch route test): '/:section/*rest' matches research/foo/foo as rest ['foo','foo'] and the editor's encoded form research/foo%2Ffoo as rest ['foo/foo']; '..%2F..%2Fetc' arrives as rest ['../../etc'], a Map miss, so a 404. The editor bundle needs no rebuild.
- wiki-export.cjs: rewriteStaticPaths already maps /wiki/<a>/<b>/<c> to a/b/c.html. The article loop writes <section>/<basename>.html, so research/x/ROOM and research/y/ROOM overwrite one file. Fix: write <outDir>/<id>.html with prefix '../' repeated (segments - 1). A 2-segment id keeps today's path and prefix.
- views.cjs compileWikiView: no change. pages.has(pageId) accepts any id string.
- wiki-search.cjs: no change (forbidden here). It reads id, title, section and content only. Its result links use /wiki/<id>, served by the new route.
- Renderer wikilinks: the @ig3/markdown-it-wikilinks pattern is /\[\[([-\w\s/]+)(\|([-\w\s/]+))?\]\]/ (node_modules/@ig3/markdown-it-wikilinks/index.js:9). A target with a dot never becomes a link. PROVEN: a nested href renders as /wiki/research/foo/foo.

### D4: what [[name]] resolves to when 2 pages share a basename
buildPageIndex becomes deterministic. Sort pages by number of id segments (fewer first), then by id in codepoint order. Pass 1 sets every full id key (lowercased); the first page in sort order wins a case-insensitive tie. Pass 2, in the same order, sets each key below only when the key is not set yet:
- the lowercased title,
- the lowercased basename (last id segment),
- for a decision-16 artifact (an id of 3 or more segments whose last 2 segments are equal), the lowercased folder path (the id without its last segment).
Result: [[name]] resolves to the page whose full id equals name. If none, it resolves to the first page, in the order above, whose title, basename or folder path equals name. Examples: [[name]] goes to research/name (2 segments) and not to research/name/name or research/other/name (3 segments). [[research/solo]] goes to research/solo/solo. [[research/other/name]] goes to that exact page. In the measured room, [[ROOM]] goes to funding/ROOM. An unresolved name keeps today's fallback (href /wiki/<lowercased name>).

### D5: malformed frontmatter must not crash the wiki
PROVEN: 3 nested files in the measured room have YAML that makes gray-matter throw. Today they are not reached. After this change they are, so an unguarded scan crashes the server, view_compile and the export. Paths: research/2026-07-07-fable-max-pack/opportunity-harvest-formula/opportunity-harvest-formula.md, research/2026-08-05-tnufa-graphrag-grant-grader/2026-08-05-tnufa-graphrag-grant-grader.md, research/2026-08-26-trial-install-testimonial/2026-08-26-trial-install-testimonial.md. Rule: on a parse error the page keeps frontmatter {} and the body with the leading --- block removed. The rel path goes to scanWarnings with reason frontmatter_parse_failed. A file that cannot be read gets no page and reason unreadable.

### D6: the search index rebuild must not run on every page view
PROVEN: wiki-server rebuild() runs on every /wiki, /wiki/:section and article request. With 61 pages it costs 56 ms. With 418 pages the scan costs 29 to 61 ms and the FlexSearch build costs 414 to 551 ms. Rule: rebuild() always rescans and rebuilds pageIndex. It calls rebuildIndex only when pagesSignature (sha1 over id, title and content of every page) differs from the last indexed signature. Startup calls buildSearchIndex once and stores the signature. Freshness stays the same as today; the cost moves to changed rooms only.
