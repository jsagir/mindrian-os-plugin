# Phase quick-260706-5b7 Plan 01: Fix vec0 Offline Load (Vector-Store Infer) Summary

**Offline eureka runs no longer die with "no such module: vec0": vector-store.cjs now selects its backend from a live vec0 capability probe (once per process, handle-registry-gated) instead of inferring 'sqlite-vec' from a stale persisted eureka_vec table.**

## Accomplishments
- Replaced the line-160 `if (tableExists(db, 'eureka_vec')) return 'sqlite-vec'` inference with `ensureVecLoaded()` -- a cached capability probe that registers the extension on THIS process's handle before ever returning the sqlite-vec leg. This fixes the bug in BOTH directions: a stale table no longer poisons an incapable process, and a capable process now actually registers the module so it can adopt an existing eureka_vec table instead of throwing.
- Added a `_vecLoadedHandles` WeakSet gating every eureka_vec touch (`currentBackend`, `knnQuery`), so the cjs-fallback path can never prepare SQL naming eureka_vec. A caller that skipped ensureStore on a poisoned db now gets a defensive no-op, not an escaped throw.
- Built a deterministic offline poisoning contract test (5 cases) using a `writable_schema` tripwire fixture, and wired it as run-all-211 leg (10).

## How It Works (Feynman)

The old code decided which vector engine to use by asking "does the eureka_vec table exist on disk?" That is the wrong question. A table left behind by yesterday's capable run still exists today, but the native vec0 module that gives it meaning is not loaded into today's process. So the code confidently picked "sqlite-vec", then the first real query against that table hit a module that was not there and crashed the whole indexing run.

The fix asks the right question: "can I actually load and run vec0 on THIS database handle, right now?" It tries the real load (require the vetted package, enable extension loading, load from the package's own path, and run SELECT vec_version()). Only if that succeeds does it register the handle and use the fast engine. If it fails, it quietly falls back to the pure-JavaScript cosine scan. A leftover table can never lie its way into the fast path again, because the fast path is now gated on a live registration, not on a filename in the schema.

## Planner Empirical Corrections (confirmed, for Phase 212 planning)

1. **vec0 DOES load on Node v22.22.2 via allowExtension handles.** The canonical load (`enableLoadExtension(true)` + `loadExtension(getLoadablePath())` + `SELECT vec_version()`) succeeds here; the docs' Node >=23.5.0 floor is conservative. So real un-forced runs through `openRoomDb(roomDir, {allowExtension:true})` probe PASS and use the sqlite-vec leg, now correctly registered per process. The tests therefore assert nothing about un-forced real-probe outcomes (environment-dependent); every backend assertion goes through the forced seam.
2. **The `writable_schema` fixture is the deterministic poison.** `PRAGMA writable_schema=ON` + INSERT the real vec0 DDL row into `sqlite_master` + `PRAGMA writable_schema=RESET` plants a table that `tableExists` sees but that throws `no such module: vec0` on any query -- confirmed on this runtime. That makes the fixture a tripwire: a green test IS the proof the fallback path never issues vec0 SQL.
