<objective>
Fix Blocker 2 of Phase 212: offline eureka runs die with "no such module: vec0"
because lib/core/eureka/vector-store.cjs line 160 infers the vector backend from
TABLE EXISTENCE instead of from a live capability probe.

Root cause (212-RESEARCH.md "Blocker 2", commit 872a93b4, re-verified by code
read for this plan): createVecTable() short-circuits with
"if (tableExists(db, 'eureka_vec')) return 'sqlite-vec';" BEFORE ever calling
db.loadExtension() in the current process. A prior vec0-capable run leaves a
persisted eureka_vec virtual table in room.db; the next process sees the table,
returns backend 'sqlite-vec', and the first prepared statement that names
eureka_vec throws "no such module: vec0" (insertVector has no try/catch, so the
throw escapes indexNodes and kills the run). Same persisted-derived-table
disease as the 211-05 stale-vector bleed, in a new form.

PLANNER EMPIRICAL CORRECTIONS (verified on this exact runtime, Node v22.22.2,
2026-07-06 - the executor must build to these facts, not to the research's
absolutes):
1. The canonical load DOES succeed here on an allowExtension handle:
   enableLoadExtension(true) + loadExtension(getLoadablePath()) +
   SELECT vec_version() returns v0.1.9. The docs' Node >=23.5.0 floor is
   conservative. So after this fix, real runs through
   openRoomDb(roomDir, {allowExtension:true}) (eureka-room-report.cjs:298) will
   probe PASS and use the sqlite-vec leg, now correctly registered per process.
   Do NOT write assertions that expect real un-forced runs to pick cjs-fallback.
2. On a PLAIN handle (no allowExtension), enableLoadExtension(true) throws
   "Cannot enable extension loading because it was disabled at database
   creation." - the probe fails per-handle, preserving the documented silent
   plain-handle degrade.
3. A poisoned vec0 schema row CAN be planted without the extension via
   PRAGMA writable_schema (verified: any query against it then throws
   "no such module: vec0", tableExists() sees it, and even DROP TABLE throws,
   which confirms dropVecTables() silently leaves stale vec tables behind).
   This is the deterministic test fixture.

NAVIGATOR-LOCKED (do not reopen): NO Node floor change; the CJS-cosine fallback
is the correct degrade at room scale. The fix makes selection HONEST: probe
whether vec0 actually works on THIS process's handle; select vec0 only on a
passing probe; a stale vec table must never poison the fallback path.
