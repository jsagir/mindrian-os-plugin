Each arm accepts exactly one of two exact key sets: the legacy set (unchanged) **or** the nest set. Nothing in between.

How each nest value is checked. A shared helper, `_proveNestBlock(payload)`, sits beside `_isKnownFrameworkHandle` after the function's closing brace:

- **section_kind**: an own key of `data/section-job-canon.json` `sections`, read at call time (the `_releaseIntentVocabulary` idiom at `:646-655`), and it must match `RELEASE_SECTION_RE` (`:642`). An unreadable canon proves nothing (fail closed).

### 1.3 Refusal cases (each returns null, which means ambiguous; theo-ask never sends an ambiguous nest payload)

### 1.4 Where the nonce map lives

**Choice: an in-process `Map` inside `theo-ask.cjs` for the request in flight, plus the nest's own `BRAIN.md` frontmatter as the record that survives a restart. No room.db table and no sidecar file.**

- **In flight.** The map is keyed by `request_id`, with one id minted per read call, so 3 ids per scoped nest ask. Each entry is `{room_id, question_basis, read, minted_at}`. The entry is deleted when the read returns (or on timeout). It does not need to survive a restart: the HTTP read it pairs with dies with the process too.
- **Durable record.** These fields are written by the face writer that already exists, atomically (tmp file, fsync, rename; `lib/core/brain-derivation.cjs:262-268`):
  - `theo_request_ids` (comma list)
  - `question_basis` (sha256)
  - `scope_state` (`scoped` | `not_scoped` | `mismatch` | `stale`)
  - `room_id`, which the face already carries (`lib/core/feyminto/theo-face.cjs:414`)

  Later readers use these to judge "is this answer about this nest as it is now". They also tell the face which room a recommendation belongs to (item 2c).
- **Why not the literal BRIEF fingerprint.** `lib/core/feyminto/brief.cjs:54` lists `BRAIN.md` among the brief's `INPUT_FILES`, and `recordBasis` (`:240-254`) hashes it. The moment the Theo answer is written into BRAIN.md, the brief fingerprint moves, so an answer keyed to it would read stale forever. `question_basis` is the same `recordBasis` hash computed over `MINTO.md, FEYNMAN.md, CONTEXT.md, ROOM.md` (INPUT_FILES minus BRAIN.md). This needs the navigator to confirm "brief_fingerprint" means this basis.
- **Why the smallest is the face.**
  - The answer already lives in BRAIN.md. Putting its key anywhere else splits one fact into two homes.
  - A room.db table needs a migration and a write path through `lib/core/navigation.cjs` (the single SQL chokepoint) for transport state that qualifies one file.
  - A sidecar JSON needs its own atomic writer and cleanup, and nothing else would read it.
- **Part 9 status.** Compliant. BRAIN.md is a generated face (`edit_surface: 'none: every field on this face is generated'`, `theo-face.cjs:432`). The request ids are correlation handles, not memory and not a truth-claim node. Nothing new enters room.db, and the map itself never leaves the machine: only `request_id` crosses, and Theo returns it unchanged.

### 1.6 What it must NOT do

- It must not send `room_id`, `brief_fingerprint`, `question_basis`, or any hash of them. The request_id is fresh random bytes per read and never derived from the room. A stable derived id would act as a room pseudonym that Theo could link across calls.
- It must not send a problem_type derived from the section or the job. It should also not send today's computed lens as if it were the navigator's input (ruling 1). `nestHandles` takes problem_type from `classifyProblemType` on the MINTO triple (`theo-ask.cjs:116-123`; `brain-derivation.cjs:204-219`, which can only return UDP, IDP or WDP). Failing that it uses the room's `goal.rung` (`theo-ask.cjs:124-127`, read at `brain-derivation.cjs:412-419`). The rung is persisted from `brain-client` `_inferRungFromQuestion` according to `lib/core/strategy/rung-vocabulary.cjs:20-24`.
- It must not rely on the callTool belt. Before every call, theo-ask runs `guard.classify(args, {toolName})` itself and sends the nest form only when the verdict is `allow` with class `known_tool_shape`. Otherwise it sends the legacy form and records `not_scoped`.
- It must not send the nest form to a Theo that has not declared the pinned contract version, because strictObject would refuse it.
- It must not put `request_id` into `handles` or `handles_fingerprint`. That fingerprint is the planned cache key (CLOSE.md section 2), and a random value in it would defeat the cache.
- It must not add a nest form or a request_id to `framework_neighborhood`.
- It must not cache answers across runs. That is unchanged from CLOSE.md section 2.
