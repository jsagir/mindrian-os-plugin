## Decisions made in planning (measured in a scratch copy, binding for the executor)

All claims below are PROVEN in a scratch copy of HEAD 3677f2a9e (git archive of lib, data, references and the named tests, node_modules symlinked), except where marked.

D1. Engine location and the walker rule. The engine moves verbatim to lib/core/room-search.cjs; its recursive walk (walkSearchFiles, inner walk with readdirSync) moves with it. tests/test-270-no-second-walker.cjs reads a fixed OPERATOR_FILES list of 6 files (icm-forest, tree-watcher, context, graph-reason, identity, dual-path). lib/core/room-search.cjs is not in it, so the move does not put the walk under that rule. The walk is not delegated to discoverSections: discoverSections skips STRUCTURAL_DIRS (meetings, team, references) and folders with no direct .md (ri7 known limits), so a delegated walk would stop reading files that room_search reads today and undo sweep item 2 (1,121 of 1,121 files). The walker count stays 1: after the move exactly one file under lib/ defines function walkSearchFiles. Scratch result after the move: natural-language 50 checks, walk-bound 50, rank-before-cap 7, html-blindness 22 (all PASS, same counts as before), test-270 PASS (4 rules, 6 files), mcp-input-validation 35 passed. The four tests need no edit, not even a require line.

D2. No MCP in core. lib/core/room-search.cjs requires only node:fs, node:path and ./room-path-containment.cjs. It never requires lib/mcp/tool-router.cjs, zod or a session resolver. It carries its own SECTION_RE literal; the new test pins String equality with tool-router's _test.SECTION_RE. resolveSearchScope enforces SECTION_RE (one segment) for every caller; room_search callers already pass zod's SECTION_RE, so the MCP behavior does not change.

D3. Page filter at the walk, not after it. Without a filter the engine reads USER.md, STATE.md, MINTO.md, ROOM.md, section STATE.md, sub-rooms, node_modules, export folders and .html files, none of which is a wiki page. A post-filter alone is wrong: a phrase hit in an excluded file stops the word tier (the D1 short-circuit of quick 261012-kfn) and an excluded file can take one of the 5 word-tier slots. So the wiki passes includeFile = (rel) => pages.has(toPageId(rel)). Real room (rethinking-mindrianos, read only): engine walkable 424 room files without the filter, 418 with it, equal to the 418 scanRoom pages.

D4. One row per page. The wiki result unit is a page. The phrase tier gives 5 rows per file, so a common word fills the 50 rows with 10 pages. The wiki passes maxPerFile: 1: 50 rows from 50 pages, and the first 10 files are in the same order as the default call (PROVEN on the real room for the query room). The word tier keeps its engine budget of 5 pages (same answer set as room_search, by design).

D5. Response shape. A JSON array cannot carry tier, the walk fields or the reason, so the body becomes an object. The UI is an inline template script in lib/wiki/wiki-layout.cjs, not a built bundle, so it changes in the same commit. Each result keeps id, title, section, excerpt and adds line. The body never echoes the query or the words: tests/test-visible-room-leak.cjs [server] 12 sends a sentinel as the query and asserts that no sentinel is in the body.

D6. Excerpt. The engine snippet is the first 200 characters of the line; on the real room 114 of 488 sampled rows had the match past character 200, so the excerpt did not show it. The wiki builds the excerpt from the full line (re-read from page.path, the scanned path, only when the snippet is 200 characters long), takes a 160-character window that starts 60 characters before the first match, marks every term inside the window, escapes all text with escHtml, and adds ... at a cut edge. Marking uses the control characters U+0000 and U+0001 as match markers before the escape (stripped from the input first), so a query can never inject markup. Phrase tier terms = [the trimmed query]; word tier terms = found.words with Unicode word boundaries. Scratch result: 0 of 488 sampled excerpts without a mark; a page that contains a script tag returns it as &lt;script&gt;.

D7. .html files. They are not wiki pages (scanRoom reads .md only), so includeFile filters them out. The ri7 follow-up ".html pages in the wiki" stays open; when html pages get page ids, the filter includes them with no search change.

D8. Cost that replaces the rebuild. The server no longer builds an index at start or after a page-set change (FlexSearch build 414 to 551 ms at 418 pages, quick ri7). Each query walks the room. Measured on a copy of rethinking-mindrianos through HTTP, load average 1.0: phrase hit 96.0 ms, sentence 136.8 ms, below floor 134.0 ms (median of 5); server start 78.2 ms. Engine direct under load average 24: 62.9, 159.1, 143.2 ms. The old lookup cost about 0.1 ms; the client debounces 200 ms. Each page view still pays scanRoom (about 70 to 90 ms), as before.

D9. flexsearch retirement scope (smaller honest scope). npm consumers of flexsearch: lib/wiki/wiki-search.cjs only (PROVEN by git grep). scripts/generate-snapshot.cjs line 71 and templates/showcase/library.html line 10 load FlexSearch from a CDN in the browser for the static snapshot Library page; they do not use the npm package and a static page cannot call a Node engine, so they are out of scope. tests/test-visible-room-nested-scan.cjs requires wiki-search.cjs for a spy; this plan removes that spy. After this plan no code requires flexsearch, and wiki-search.cjs is deleted. package.json, package-lock.json, npm-shrinkwrap.json and references/security/cve-db.json are NOT edited here: the sweep file rules that the dependency removal belongs to a release cut, and npm-shrinkwrap.json is regenerated at release.sh Step 6.7. Follow-up for the cut: run npm uninstall flexsearch on the operator machine, drop the cve-db.json VETTED row, never hand-edit the shrinkwrap.
