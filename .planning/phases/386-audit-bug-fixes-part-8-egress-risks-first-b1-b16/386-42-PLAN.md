<objective>
Design and prove the context-based split route that replaces a bare block (owner direction of 2026-11-06). A body or a short private claim must not be refused and dropped. The route breaks the text into typed claims the way /mos:file-meeting does, keeps the room-specific claims local as proposed claims, sends only the generic sprouts MindrianOS needs, and assembles the answer locally when it returns. The guard stays the backstop and answers a raw body with the typed outcome sprouts_required.

Owner principle for Part 8 (2026-11-06, PRD section Owner principle for Part 8): a specific keyword query for research or for the remote graph may leave the room; a full body of text may not; small pieces (sprouts) go out and MindrianOS assembles the answer; the guard must never cripple contextualised work, query or search. The guard separates sprouts from bodies by shape (size, sentences, quoted room text) and always blocks credentials. A word list that blocks an ordinary keyword is the wrong tool.

Owner direction (2026-11-06, PRD section Owner direction on ambiguous calls and over-blocking), verbatim for plan 26: "block ? i dont think a block will wor it need to be context based, like the file-a meeting style where it braeks it up to claims, facts hypthtesesys ect ..." and for plan 32: "follow last asnwer for this one as well". Reading: a bare block does not work. A long text (an edge or a body) or a short private claim is not refused and forgotten. It goes through a split route like the meeting filing: break the text into typed claims, keep the room-specific claims local as proposed claims, derive the generic sprouts MindrianOS needs (framework names, problem type, keywords), send only those, and assemble the answer locally when it returns. The guard is the backstop: it never sends a raw body and answers with the typed outcome sprouts_required (a plain split guide, never silent, never echoing the text). Credentials, emails, phone-like and ID-like strings and room-lexicon terms never leave. brain_write of room text stays blocked.

Who does what. The plugin has no model. The host model (Larry) breaks the text into claims, as it does for the meeting filing. The guard cannot do that; it can only refuse with a plain guide that tells the host model how. The code in this plan does the mechanical parts: validate the sprouts against the guard, file the local claims through the existing claim writer, send the sprout calls through the existing Brain client, and assemble the answer. Pipelines without a model (the whitespace baseline, the framework chains, the framework-name refresh) already send only framework-name sprouts.

If the RCA shows the design cannot work (no route can carry the sprouts without room text), stop with NEEDS_HUMAN and do not build the module.
Output: RCA with the design lines, a failing test, the module, the typed message text.
</objective>
