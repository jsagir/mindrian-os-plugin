Reading (the main session's reading, to be checked by the owner): the purpose of Part 8 is that no external graph memory can learn the user's IP. A specific query made of keywords, for research or for the remote graph, may leave the room. A full body of text may not. Consequences for this phase:
- The guard separates sprouts from bodies by shape (size, sentences, quoted room text), and always blocks credentials. A word list that blocks an ordinary keyword (an author, a company, a month, a place, "runway") is the wrong tool and counts as over-blocking.

- Room text sent to the user's own Anthropic account (wiki briefing, chat, classifier and similar) is not an external graph memory of the user's IP. No new gate or guard for those in this phase. The disclosure question stays open and is not planned.
- `brain_write` of room-derived text stays blocked (decision A of plan 02): it sends data to be stored, not a query sprout.

## Owner direction on ambiguous calls and over-blocking (2026-11-06, owner's own words, typed on a card)

Verbatim, for plan 26 (ambiguous calls): "block ? i dont think a block will wor it need to be context based, like the file-a meeting style where it braeks it up to claims, facts hypthtesesys ect ..." Verbatim, for plan 32 (over-blocking): "follow last asnwer for this one as well".

Reading (the main session's reading, to be checked by the owner): a bare block does not work for contextualised work. When a call carries a long text (an edge or a body) or an ambiguous shape, the system should not just refuse. It should work the way the meeting filing works: break the text up into typed claims (fact, causal, heuristic, anomaly cue, mental model, assumption, hypothesis), keep the room-specific claims local (as proposed claims in the room), derive the generic query sprouts that MindrianOS needs (keywords, framework names, problem type) and send only those, as a typed packet, then assemble the answer locally when it returns. The guard stays the backstop: raw bodies and credentials never leave. When the guard sees a raw body it answers with a typed "sprouts required" outcome that names the packet route and the split guide, never with a silent block and never by sending. Consequences:
- Plans 26, 27, 32 and 33 do not choose "block" (26 option A) or "narrow rules only" (32 option A). They implement this context-based decomposition (recorded as decision option-e in each RCA).
- The existing typed packet (data/brain-packet-schema.json, Part 9: the Brain reasons over typed packets, never raw memory) is the sprout packet; reuse it (Part 7) and the claim types of the meeting filing (writeClaimNode, claim_write knowledge types).
- A short private claim is handled by the same route: its claim stays local, only the generic sprout leaves.
- Still true: credentials, emails, phone-like and ID-like strings and room-lexicon terms never leave; `brain_write` of room text stays blocked.
