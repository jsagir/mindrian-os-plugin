## 2. Check A: drain worker on Windows

Warning: close other heavy programs first. The check reads core use.

Steps:

1. Open PowerShell window 1 in the plugin folder.
2. Open PowerShell window 2 (the monitor). Paste this loop and press Enter. It prints every 2 seconds each `node.exe` process with its Id, PriorityClass, PeakWorkingSet64 in MB and CPU seconds. It replaces `C:\Users\<name>` in the command line, so no user name is shown.

```powershell
while ($true) {
  Get-CimInstance Win32_Process -Filter "Name='node.exe'" | ForEach-Object {
    $p = Get-Process -Id $_.ProcessId -ErrorAction SilentlyContinue
    if ($p) {
      $cmd = ($_.CommandLine -replace '(?i)[A-Z]:\\Users\\[^\\\s"]+','USERHOME')
      if ($cmd.Length -gt 110) { $cmd = $cmd.Substring(0, 110) }
      [pscustomobject]@{
        Time      = (Get-Date -Format HH:mm:ss)
        Id        = $p.Id
        Priority  = $p.PriorityClass
        PeakWS_MB = [math]::Round($p.PeakWorkingSet64 / 1MB, 1)
        CPU_s     = [math]::Round($p.CPU, 1)
        Cmd       = $cmd
      }
    }
  } | Format-Table -AutoSize
  Start-Sleep -Seconds 2
}
```

3. In window 1 run the large-room leg. Keep the full output.

```powershell
node scripts/real-room-run.cjs --large-room-only --json
```

4. While it runs, open Task Manager, Details tab. Find the busiest `node.exe` process. Note how many cores it uses. One core is about 100 divided by the number of logical cores, in percent of the CPU column. Write the highest core count you see.
5. In window 2, find the row whose `Cmd` contains `gsd-graph-derive-drain.cjs --worker`. That row is the drain worker. Write down:
   - The `Priority` value on that row.
   - The highest `PeakWS_MB` on that row, from the last lines before the process ends. `PeakWorkingSet64` only grows, so the last sample is the peak.
6. The leg also runs the scout. Its rows are other `node.exe` rows. Do not mix them with the worker row.
7. When window 1 prints its result, stop the monitor with Ctrl+C.

Pass rules (the existing limits; no limit is changed to pass):

- PriorityClass is `BelowNormal` or `Idle`.
- The VALIDATION row says: "confirm the drain node process stays below 3 cores and shows Below Normal priority". So the worker uses fewer than 3 cores at any time (no more than 3 cores busy is the sheet limit; below 3 is the VALIDATION wording).
- For reference, the release limits for the same run are clock 300,000 ms and CPU 600,000 ms.

If `status` is `inconclusive` (the encoder was not available), paste the output and write that line. Do not repeat the run with other settings.

## 3. Check B: session-start hook time under a running drain

Warning: do this check with a drain running. A hook that is fast on an idle machine can be slow under load.

Steps:

1. Start the same large-room drain as in Check A in PowerShell window 1: `node scripts/real-room-run.cjs --large-room-only --json`.
   - The drain phase is the first part of the run. If the run ends before you finish the timing steps, start it again.
2. In window 2 set the plugin folder variable for this shell. Use the real path of your plugin folder.

```powershell
$env:CLAUDE_PLUGIN_ROOT = (Get-Location).Path
```

3. While the drain runs, time each hook below, one by one, from window 2. Each line sends an empty JSON object on stdin. The result is the `TotalMilliseconds` value.

```powershell
function T($name, [scriptblock]$b) { $m = Measure-Command { & $b | Out-Null }; "{0}`t{1} ms" -f $name, [math]::Round($m.TotalMilliseconds) }
T 'sessionstart-npm-reconcile'          { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\sessionstart-npm-reconcile.cjs" }
T 'sessionstart-post-update-preflight'  { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\sessionstart-post-update-preflight.cjs" }
T 'run-hook.cmd session-start'          { '{}' | cmd /c "$env:CLAUDE_PLUGIN_ROOT\hooks\run-hook.cmd" session-start }
T 'sessionstart-coordinator'            { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\sessionstart-coordinator.cjs" }
T 'sessionstart-reference-now-seed'     { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\sessionstart-reference-now-seed.cjs" }
T 'check-pending-breakthrough'          { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\check-pending-breakthrough.cjs" }
T 'check-pending-ambiguous'             { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\check-pending-ambiguous.cjs" }
T 'gsd-graph-derive-drain (hook entry)' { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\gsd-graph-derive-drain.cjs" }
T 'agentshield-sessionstart-scan'       { '{}' | node "$env:CLAUDE_PLUGIN_ROOT\scripts\agentshield-sessionstart-scan.cjs" }
```

   - The hook entry of `gsd-graph-derive-drain` starts a detached worker and exits. If a drain already holds the lock, it does nothing. Both cases are fine.
   - `sessionstart-npm-reconcile` can run `npm` in the plugin folder. This is normal behavior at session start.
4. Then start one Claude Code session in a bound room, while the drain still runs. Look at the start-up output. Note any line that says a hook timed out. Answer yes or no. The session room must be a test room, not a room with private content.
