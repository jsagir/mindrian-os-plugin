<objective>
Close finding F-3: pre-commit hard-blocks on the same `>= error` threshold that both F-2 breaches already meet, tied to a repair ladder whose value is still being established.

`runPreCommit` today enumerates violations to stderr and then `return 2`, which `scripts/hooks/pre-commit-room-minto-guard.sh` propagates as a commit rejection. Note the ordering that makes this urgent rather than theoretical: the threshold is `>= error`, and both F-2 breaches were ALREADY at `error` before plan 241-03 raised them. So a missing MINTO.md or a missing `governing_thought` has been blocking commits all along, and plan 241-03 does not change that (critical also satisfies `>= error`). F-3 is therefore a genuinely separate change to exit behavior, not something F-2's severity bump incidentally causes or fixes.

Purpose: satisfy success criterion 3, which demands the demotion be demonstrated by a REAL commit run, not by calling `runPreCommit()` as a function.

Output: a pre-commit guard that still tells you everything it found and stops taxing the commit.

**Resolution R-06, permanent advisory with a strict opt-in, not a temporary hold.** RESEARCH.md's Assumptions Log A3 flags SC3's phrase "Until the repair loop is live" as genuinely ambiguous between a permanent demotion and a demotion that reverts once F-0 ships in this same phase. This plan adopts the permanent reading, per RESEARCH.md's own recommendation, for three reasons. It matches the only precedent this repo has for this exact problem shape, `scripts/check-shape-declaration.cjs` at Phase 210, which is also the reuse-before-build source under Canon Part 7. It decouples SC3 from F-0's fate, so a future change to the repair loop cannot silently re-arm a commit block nobody re-approved. And Canon Part 11 already records that the sibling shape-declaration gate is advisory-with-`--strict`, so two neighbouring commit-time guards will now behave the same way instead of disagreeing. The `--strict` flag and the `MINTO_PRECOMMIT_STRICT` env var are the documented path back to hard-fail whenever the navigator wants it.

**Resolution R-07, how Pitfall 4 is avoided outright.** RESEARCH.md warns that Phase 235 is in flight in a neighbouring wave and explicitly plans to consolidate the pre-commit hook to one canonical source, retiring the divergent `setup-hooks.sh` and `install-pre-commit.sh` authoring. Editing `scripts/hooks/pre-commit-room-minto-guard.sh` here risks one phase's change being moved or overwritten by the other. This plan sidesteps that entirely: because the fix makes `runPreCommit` return 0 by DEFAULT, the hook script's existing exit-code propagation already does the right thing with zero edits, and the strict opt-in rides an environment variable that needs no hook-script passthrough. The contested file's diff for this phase is empty. Task 1 still requires the executor to check Phase 235's landing status before starting, because if 235 changed which file installs the hook, the real-commit test in Task 2 must install the CURRENT canonical one.
</objective>
