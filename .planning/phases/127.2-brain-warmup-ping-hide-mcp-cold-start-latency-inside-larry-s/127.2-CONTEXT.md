# Phase 127.2: Brain Edge Bundle (Warmup Ping + Three Windows-Audit Cleanups)

## Scope expansion note (2026-05-23)

Originally scoped as warmup-ping-only. Expanded same-day to bundle three small Brain-edge RCAs surfaced by the Windows beta-tester deep audit (2026-05-23). All four ship together in v1.13.1-beta.2 because each individual fix is too small to warrant its own beta gate, they all touch the Brain MCP surface, and bundling preserves "one Brain-edge cleanup beta" narrative discipline.

Absorbed RCAs (all `severity: low`, all surface-cross [cli, desktop, cowork]):
- `brain-ask-contract-mismatch-rename` — description rewrite (D-08)
- `brain-topk-uncapped-advisory` — additive cap guard (D-09)
- `stale-install-cache-audit-anti-pattern` — Source-of-Truth Preamble for QA (D-10)

Source debug files (in `.planning/debug/`) carry the per-RCA RCA template; this CONTEXT.md is the umbrella that closes them.

## JTBD

When a user opens a fresh MindrianOS session, the Brain MCP server is lazy-loaded -- not connected until the first tool call. That means Larry's turn 1 response is **Brain-blind**: no methodology directive, no chain recommendation, no contextualization. The user typically does not see Brain-informed responses until turn 4 or 5, by which point trust in Larry's "thinking partner" framing has eroded.

The job: make turn 2 land with a hot Brain connection, without making the user wait for it.

## Goal

Fire a non-blocking `brain_ask("warmup")` call the moment Larry's first-question response renders to the screen. The MCP server's stdio handshake (~300-1500ms) happens silently in the background while the user reads Larry's question and types their first answer. By the time the user submits turn 2, the Brain connection is hot, and Larry's response carries full methodology context.

Zero perceived latency cost. Zero blocking startup. Zero user-data egress. Zero Brain-quota burn if the call is tagged correctly server-side.

## Architectural model

| Layer | Today (Brain-blind turn 1) | After 127.2 (warm turn 2) |
|---|---|---|
| Session start | Plugin loads, MCP servers defer | Plugin loads, MCP servers defer |
| Larry's turn 1 response | Renders immediately (no Brain) | Renders immediately (no Brain) -- IDENTICAL TO TODAY |
| Background (during user read+type) | Idle | Fire `brain_ask("warmup")` -- non-blocking, silent |
| User submits turn 2 | Brain still cold -- first real call pays the handshake cost | Brain hot -- first real call returns directive in ~50ms |
| Larry's turn 2 response | Contextualizes via Brain on turn 4-5 | Contextualizes via Brain on turn 2 |

The Brain-side handler recognizes the `"warmup"` sentinel payload and returns a tiny acknowledgment without consuming Pinecone/Neo4j budget. Tag the call with `warmup: true` in the DirectiveEnvelope so telemetry never pollutes engagement metrics.

## Design decisions (locked from 2026-05-23 discussion)

### D-01: Implementation path -- warmup ping, NOT `alwaysLoad: true`
Rejected the Anthropic-blessed `alwaysLoad: true` flag because the docs confirm it BLOCKS session startup until MCP handshake completes. User latency tolerance is "immediate" -- session prompt-build must never block. Warmup-ping achieves the same turn-1-contextualization goal without paying the blocking-startup cost.

### D-02: Fire anchor -- AFTER Larry's first response renders
The ping must fire AFTER the initialPrompt response renders, not before. Firing earlier moves blocking latency from MCP startup into the warmup hook itself, defeating the purpose. Likely implemented as a `setTimeout(0)` or background process spawn pattern inside the SessionStart hook chain, gated on "first response rendered" signal.

### D-03: Payload shape -- fixed sentinel `"warmup"`
The warmup call carries the literal string `"warmup"` as the query field of the DirectiveEnvelope. No user content. No room state. No artifact bytes. Part 8 forbidden-substring scan MUST pass against the warmup code path.

### D-04: Server-side recognition -- no Pinecone/Neo4j cost
Brain's request handler recognizes the `"warmup"` sentinel and short-circuits: skip embedding, skip graph traversal, return a 50-byte ack. Warmup pings do not count against any user's Brain quota.

### D-05: Telemetry -- `warmup: true` flag
Every warmup ping emits a Phase 121 telemetry event tagged `warmup: true`. The trajectory-telemetry aggregator filters these out of engagement and methodology-call metrics. They remain visible in a separate "warmup-success-rate" panel for diagnostic use.

### D-06: Failure silence -- die quietly
If Brain is unreachable, the warmup ping must fail SILENTLY. No error surfaced to user. No statusline flash. No retry storm. No log entry visible in the normal `/mos:doctor` output (only in `--verbose` mode). Fallback to current lazy-load-on-first-real-call behavior is graceful and indistinguishable from "no Phase 127.2 installed."

### D-07: Kill-switch -- env var
Provide `MINDRIAN_WARMUP_PING=false` env var (or `~/.mindrian.env` entry) that disables the warmup ping for testers debugging Brain cold-start issues. Default: enabled.

### D-08: brain_ask description rewrite (absorbs `brain-ask-contract-mismatch-rename`)

The current `brain_ask` tool description at `mcp-server-brain/lib/brain-ask.cjs:506` reads "ask the Brain anything in natural language; use this instead of brain_query or brain_search." This sets the wrong expectation -- the tool actually returns a `DirectiveEnvelope` (routing decision, GUIDED mode, framework-chain suggestions) per Phase 127 + Canon Part 10, NOT a synthesized answer. Windows beta-tester (2026-05-23) flagged the mismatch verbatim.

Fix: rewrite the description (~2 lines) to name the actual return contract -- routing envelope, default GUIDED mode, framework-chain payload shape -- so LLM consumers of the tool registry build correct mental models on first read. Single-file edit. No behavioral change. Zero risk to warmup-ping path.

### D-09: BRAIN_MAX_TOPK cap on brain_ask + brain_search (absorbs `brain-topk-uncapped-advisory`)

Today the Brain forwards caller-supplied `topK` directly to Pinecone with no Brain-side cap (verified at `brain-ask.cjs:545` + `pinecone-tools.cjs:42`). The moat against runaway result sets is INHERITED from Pinecone's server-side cap, not OWNED by the Brain. D-MOAT-2 (timeout + row cap + byte cap) is enforced on the Neo4j curated-op path, on `brain_query`, and on `brain_schema` -- but the Pinecone path on `brain_ask` and `brain_search` is uncapped at the Brain layer. Windows deep-audit (2026-05-23) ran `brain_ask({topK: 999999})` to confirm.

Fix: ship a `BRAIN_MAX_TOPK` env var with a sensible default cap (recommend 100), wired into both call sites via `Math.min(topK, BRAIN_MAX_TOPK)`. ~5 lines across two files. Brain owns its moat; Pinecone's cap becomes belt-and-suspenders not the only line of defense.

**Why this lives in the warmup-ping phase:** the warmup ping is the FIRST `brain_ask` call every session makes (per D-04). If the cap fix lands in the same beta as the warmup ping, every cold-start session is also the first to exercise the new cap -- highest test coverage from the same change set.

### D-10: Source-of-Truth Preamble for QA harnesses (absorbs `stale-install-cache-audit-anti-pattern`)

The 2026-05-23 deep audit surfaced two false-positive findings (NF-2026-05-23-01 + curated-op-surface-missing) because the auditor read source from the marketplace install cache (`~/.claude/plugins/mindrian-os/`, frozen at beta.24) while their wire probe hit the post-fix deployed Brain server (beta.25). Two findings died on reconciliation. This is a recurring class -- every time a fix chain lands after a marketplace cut, the same delta can reproduce.

Fix (process, not code): every QA / audit prompt template must state explicitly which source-of-truth its claims will be read against. Any source-code claim must be re-verified against `origin/main` HEAD before it is filed as a finding. Lands as a Source-of-Truth Preamble section added to `docs/RCA-TEMPLATE.md` + a checklist row in the QA-harness prompt that the auditor uses.

**Why this lives in the warmup-ping phase:** the warmup ping itself is auditable behavior (turn-1 latency, telemetry, kill-switch). Without the Preamble fix landing in the same beta, the warmup ping's acceptance audit on Windows could trip the same install-cache-vs-deployed false-positive pattern -- making the warmup-ping verdict unreliable. Preamble first -> audit verdict trustable -> 127.2 ships clean.

## Open design questions (carry into /gsd:plan-phase 127.2)

### Q-01: Where exactly does the warmup ping fire from?
Candidates: (a) extend `scripts/session-start` to spawn the ping as a backgrounded `node` subprocess after the initialPrompt response renders; (b) wire into the `lib/core/navigation.cjs` chokepoint as a side-effect of the first memory_event after SessionStart; (c) hook into Larry's response-rendered signal (does one exist? if not, can we add one cheaply via Phase 114's larry-default-activation surface?). Path (c) is cleanest but requires Phase 114 to expose a render-complete callback.

### Q-02: What is the "first response rendered" signal?
Phase 114 (larry-default-activation) ships in v1.13.1-beta.2 alongside this phase. Coordinate with Phase 114's design to expose a usable render-complete hook. If 114 cannot expose this in time, fall back to a `setTimeout(N)` heuristic where N is tuned from observed render-complete-to-user-type-start measurements (Phase 121 telemetry).

### Q-03: How is server-side warmup recognition implemented?
The Brain MCP server lives in a separate codebase (mindrian-brain.onrender.com). Coordinate with the Brain server maintainer to add the `"warmup"` sentinel short-circuit in the request handler. Without server cooperation, the warmup ping still works as a connection-prewarmer but burns a tiny amount of Brain compute per session.

### Q-04: Cross-surface behavior (CLI / Desktop / Cowork)
Per Tri-Polar design rule: how does this work on Claude Desktop and Cowork where the session lifecycle differs from CLI? Desktop spawns MCP servers as child processes via `claude_desktop_config.json` -- does the warmup ping mechanism need to be re-implemented on each surface, or can it ride a shared `lib/core/*` entry point? Plan must address all three surfaces.

### Q-05: Telemetry schema for warmup events
Phase 121 trajectory-telemetry defines the event schema. Adding `warmup: true` requires either (a) extending the existing event schema with an optional boolean field, or (b) emitting warmup events to a separate `warmup-telemetry.jsonl` sink. Discuss with Phase 121's design.

## Why this exists (one sentence)

The Brain is the moat -- but a moat the user does not feel on turn 1 is a moat the user does not value, a moat whose tool description lies to its consumers is a moat that breeds wrong mental models, a moat whose result-set cap is inherited rather than owned is a moat that can disappear when its upstream changes, and a moat whose audits read stale source while probing live wire is a moat whose verdicts cannot be trusted; this phase closes all four edges in one beta so v1.13.1-beta.2 ships with the Brain surface clean.
