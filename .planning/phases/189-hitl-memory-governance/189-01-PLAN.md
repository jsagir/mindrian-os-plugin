## NEEDS-DISCUSS (surfaced, not invented around)

1. **Edge-vocabulary mint ceremony.** Recent additive extensions to `ALLOWED_EDGE_TYPES` split into two
   idioms: a routine additive-comment-only idiom (STATES/SUPPORTS/DESCRIBES at 150-01; UMBILICAL_TO at
   195-04; SHARES_JOB/ELEVATES_TO at 205-02 -- no separate navigator-gated checkpoint recorded in the
   comment block) versus a NAVIGATOR-GATED blocking-AskUserQuestion idiom (REFINES/ROOT_CAUSES/
   INSTANTIATES at 150.8; the 163-01 quad; the 168-01 trio; NESTED_WITHIN at 169-00; DISCOVERED/
   AUTHORED_BY at 200-02). This plan defaults to the LIGHTER idiom (comment-only, no fresh blocking
   checkpoint task) because SEED-040's own Provenance line already records navigator-direction
   (2026-06-30, Shape-F explainer session) and the two MOST RECENT precedents (195-04, 205-02) used the
   lighter idiom. If the navigator wants the heavier ceremony instead, say so before Task 1 lands.
2. **MEMORY_LAYER: edge type or edge property?** The roadmap/seed phrase "new edge-property vocabulary
   REMEMBERED_AS / ATTRIBUTED_TO / MEMORY_LAYER / NOT_REMEMBERED_BECAUSE" reads three of the four as
   directed verb-edges (mirroring the shipped REJECTED_BECAUSE/STATES/SUPPORTS idiom) but MEMORY_LAYER
   does not read as a directed relationship between two nodes -- it reads as an attribute of WHERE a
   memory lives. This plan's DEFAULT: mint only THREE new edge types (REMEMBERED_AS, ATTRIBUTED_TO,
   NOT_REMEMBERED_BECAUSE); carry `memory_layer` as an ENUM-scalar PROPERTY on the ATTRIBUTED_TO edge
   (values: `within-session` | `across-session` | `cross-room`, reusing the exact three strings the
   shipped `/mos:memory` three-layer model already uses -- see `commands/memory.md` "Layers" section and
   `lib/hmi/across-session-memory.cjs`). Task 1 mints exactly three edge types, not four. If the
   navigator wants a literal 5th `MEMORY_LAYER` edge type instead, flag it before Task 1's commit.
