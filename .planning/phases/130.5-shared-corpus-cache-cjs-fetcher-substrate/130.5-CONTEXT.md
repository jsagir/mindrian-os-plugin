# Phase 130.5: Shared Corpus-Cache + CJS Fetcher Substrate

## Goal

Build ONE CJS-native external-corpus module - the shared fetcher + cache over OpenAlex / arXiv / PubMed / Tavily that every research surface uses. This closes the duplicate-fetcher drift the 2026-05-15 deep-research audit flagged (`/mos:research` hits OpenAlex via Tavily; `rs-discovery-engine` hits OpenAlex directly; same paper, two code paths, no shared cache, duplicate API quota), and it is the substrate Phase 131 consumes and Phase 134 reuses.

The decisive reason this is its OWN phase (not a 131 deliverable): without it, Phase 131 builds CJS fetchers + a private cache, and Phase 134 later re-ports the Python `rs_corpus.py` to a SECOND CJS fetcher. Built here once, 134 deletes its Python corpus and reuses this module, and rs-discovery-engine migrates onto it.

## Why this matters (from the 131/132 re-baseline review)

- 131-REVIEW-4.8 section 3 (highest-leverage coupling): 131 and 134 touch the same corpus surface and will build it twice unless coordinated.
- Cross-phase coherence change 1: "Make it one module - extract a tiny shared corpus-cache unit that 131, 134, and rs-discovery-engine all consume."

## Scope

1. **`lib/core/research-corpus.cjs`** - the unified fetcher. Native Node `fetch` only (no `requests`, no Python, no new deps). Sources: OpenAlex, arXiv, PubMed, Tavily, Brain Cypher (the last via the Phase 110 packet). Per-source adapters behind one `fetchCorpus({source, query, limit})` interface. Adding a source HERE propagates to every consumer (HSI / reverse-salient / `/mos:research`) - the build-once benefit.

### Candidate source adapter: Sci-Bot (sci-bot.ru) -- OPT-IN, DISABLED BY DEFAULT

Added 2026-06-01 at the user's request, researched + flagged (Tavily-validated 2026-06-01).

**What it is:** Sci-Bot (https://sci-bot.ru, agent: https://sci-bot.ru/agent-a2c5) is an AI research assistant POWERED BY Sci-Hub (Alexandra Elbakyan). Natural-language question in, citation-backed synthesized answer + paper references out. Distinct from a paper index: it returns a reasoned, sourced answer, which is high-value for the "search for insights" job HSI / rs / research do.

**Integration reality (the reason it is opt-in, not a default adapter):**
- **No documented public API.** It is a login + token + queue web UI (alpha; observed "184 queued"; per-account tokens). There is no clean REST endpoint to call. An adapter would need a user-supplied credential/token and must respect the queue + token budget. NO headless browser (stack rule) - only proceed if/when an official API or token-authenticated endpoint exists.
- **Sci-Hub provenance is a legal/compliance flag.** Sci-Hub bypasses paywalls and is legally contested in many jurisdictions. The plugin is a COMMERCIAL product shipping to academic testers (pre-publication-priority + grant personas, Canon Part 8 protections). Per the canon, "any feature that is ambiguous on this boundary goes through separate legal review." Routing research through a Sci-Hub-powered service is exactly that. **MUST clear legal review before it can be enabled by default.**
- **Canon Part 8 egress.** The query sent to sci-bot.ru is an external SIGNAL fetch; the 130.5 shared pre-egress audit applies (no user-content / no proprietary framing in the query string). Provenance (the returned DOIs/citations) is preserved on the EvidenceClaim, not the synthesized prose alone.

**Recommended shape (for plan-phase):** register `sci-bot` in the source enum but ship it `enabled: false`, gated behind (a) an explicit user opt-in, (b) a user-supplied token, and (c) a legal-review sign-off flag. Default sources stay OpenAlex / arXiv / PubMed / Tavily. When enabled, treat Sci-Bot's answer as a Practitioner/None-tier lead that MUST be re-grounded against an Academic-tier primary source (Canon Part 5) before it can inform a confirmed claim - never file a Sci-Bot synthesis as Academic evidence on its own.
2. **`lib/core/research-cache.cjs`** - a shared on-disk cache (TTL + source-keyed) so a paper fetched by `/mos:research` is not re-fetched by `rs-discovery-engine`. Closes the duplicate-API-quota drift.
3. **Pre-egress audit hook** - Canon Part 8: every outbound query string passes the no-user-content audit before the fetch. This is the shared chokepoint for the audit (131 and 134 both inherit it).
4. **rs-discovery-engine migration** - repoint its OpenAlex fetch at this module (delete its private fetcher path). Keep behavior byte-compatible (a fixture-room regression proves identical results).

## Explicitly NOT in scope (stays where it belongs)

- Embeddings / HSI scoring: NOT here. This module is fetch + cache only, Python-free. The embedding/HSI surface belongs to Phase 134 (the `@huggingface/transformers` CJS port). Keeping embeddings out is what lets 130.5 ship in v1.13.1 with zero Python and zero `@huggingface/transformers` dependency.
- The semantic-dedup query (Pinecone) stays a Brain-side call via the Phase 110 packet; this module only passes the handle, it does not embed locally.

## Acceptance criteria

- [ ] `lib/core/research-corpus.cjs` fetches from OpenAlex / arXiv / PubMed / Tavily via native `fetch`; zero Python; zero new npm deps
- [ ] `lib/core/research-cache.cjs` returns a cached result for a repeat (source, query) within TTL; cache is shared (one path for `/mos:research` and `rs-discovery-engine`)
- [ ] Pre-egress Part 8 audit rejects any query string containing user-content patterns (planted-violation test fails closed)
- [ ] `rs-discovery-engine` produces byte-identical results on a fixture room after migrating onto this module (no behavior change)
- [ ] Pre-commit substrate guard (Phase 128) passes against the new code

## Forward contracts (consumed downstream)

- **Phase 131** calls `fetchCorpus` + the shared cache for its Stage-4 source-lens rotation; it adds NO fetcher of its own.
- **Phase 134** REUSES `research-corpus.cjs` + `research-cache.cjs` verbatim and DELETES `lib/core/rs_corpus.py`; its only net-new is the in-process embedding/HSI layer (`@huggingface/transformers`), not a second fetcher.
