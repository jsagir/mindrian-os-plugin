## Summary

This phase's three requirements have radically different difficulty profiles, and the biggest planning risk is that they read as equally-sized siblings when they are not.

**CTXL-01 is the dangerous one, because the requirement text is ambiguous across two different files both named `STATE.md`.** The symptom the ROADMAP describes (`stopped_at` vs `Current Position` self-contradiction) happened in `.planning/STATE.md`, which is written by **gsd-core, an external tool this repo does not own** (`~/.claude/gsd-core/bin/lib/state.cjs`). Two RCAs have already root-caused that class and both concluded "Required Code Changes: None in this repo." Meanwhile the phrase "compute-state artifact" is the literal name of an **in-repo** script (`scripts/compute-state`) that generates a **per-room** `STATE.md`. I found, and empirically proved this session, a real in-repo drift bug there: compute-state blind-overwrites the room's `STATE.md` and **destroys the `gsd_state_version` stamp that `scripts/room-registry` seeded at room birth**. That is a genuine, fixable, in-scope CTXL-01 target. The planner must pick a target explicitly.

**CTXL-02 needs no schema change.** room.db is a generic property graph (`nodes(id, type, properties)`, `edges(source, target, type, properties)`) with no structural layer separation and no `PRAGMA user_version`. But the semantic/context distinction **already exists operationally** and is already load-bearing: Phase 236's `INDEXER_OWNED_NODE_TYPES` allowlist is precisely the line between "derivable structure, safe to wipe and rebuild" and "irreplaceable institutional knowledge." The requirement is to NAME what the code already does, in two existing docs. This is the cheapest of the three.

**CTXL-03 is not a new pattern for this repo.** Two production eval harnesses already exist with the same two-layer architecture (`scripts/huji-eval.cjs` from Phase 229, `scripts/skillopt-eval.cjs` from Phase 230), and huji-eval already implements judge calibration, graded anchors, a correlation gate, a cost ledger, and a before/after comparison. Canon Part 7 says reuse this, not invent a third shape.

**Primary recommendation:** Scope CTXL-01 to the **per-room** `STATE.md` (the in-repo, provable, fixable half), reuse `lib/core/install-state.cjs::migrateIfNeeded` for the mismatch semantics and `scripts/frontmatter-schema-validator.cjs` for the notification surface; treat CTXL-02 as documentation-only over the existing `INDEXER_OWNED_NODE_TYPES` boundary; build CTXL-03 as the third instance of the huji-eval/skillopt-eval idiom.

**The version stamp already exists and is completely inert.** `buildStateFrontmatter` writes it as a hardcoded literal on every single regeneration, never reading or comparing the on-disk value:

- `~/.claude/gsd-core/bin/lib/state.cjs:918` - `const fm = { gsd_state_version: '1.0' };`
- `~/.claude/gsd-core/bin/lib/state.cjs:1485` - the ONLY place it is preserved: `gsd_state_version: existingFm['gsd_state_version'] || '1.0'` (milestone-switch path only)
- `~/.claude/gsd-core/templates/state.md:11` - the template's own comment admits it: `gsd_state_version: '1.0'  # placeholder; syncStateFrontmatter overwrites on first state.* call`

**There is a real concurrency defect here, and I traced it.** gsd-core HAS a lockfile mechanism (`acquireStateLock` at `state.cjs:1006`, `releaseStateLock` at `:1057`), and `readModifyWriteStateMd` (`:1122`) correctly holds the lock across the whole read-modify-write cycle. But `writeStateMd` does NOT:

```

state.cjs:1092   const lockPath = acquireStateLock(statePath, clock); // lock acquired AFTER
```

The frontmatter is derived from a `_diskScanCache`-backed scan **before** the lock is taken. Two concurrent sessions can each derive frontmatter from the same pre-write disk state and then serialize their writes, producing exactly the self-contradicting frontmatter the ROADMAP describes. `[VERIFIED: source read at ~/.claude/gsd-core/bin/lib/state.cjs:1085-1098]`

### 1E. The notification surface already exists (and explains why the bug is invisible)

`scripts/frontmatter-schema-validator.cjs` is a **live, registered** PostToolUse hook:

```
hooks/hooks.json:258-263
  "matcher": "Write|Edit|MultiEdit",
  "command": "node \"${CLAUDE_PLUGIN_ROOT}/scripts/frontmatter-schema-validator.cjs\"",
  "timeout": 2000
```

Its documented contract (`scripts/frontmatter-schema-validator.cjs:7-23`) is precisely CTXL-01's "surfaces a notification":

- ADVISORY, NOT BLOCKING
- emits a one-line `systemMessage` advisory on violation
- appends one JSON line per violation to `${CLAUDE_PLUGIN_DATA}/schema-violations.jsonl`
- ALWAYS exits 0

**And here is the root cause of the invisibility:** the matcher is `Write|Edit|MultiEdit` - it fires on *Claude tool calls*. Every one of the six compute-state write sites uses a **programmatic** `fs.writeFileSync` or a **shell redirect**. None of them is a Claude tool call. **The existing drift-notification surface is structurally blind to the exact writer that causes the drift.** That is the seam CTXL-01 should close.

### CTXL-01 recommendation

Target the **per-room** `STATE.md` (1B). Concretely:
1. Add a `SCHEMA_VERSION` to the compute-state render path and a preserve-or-notify read step, following `install-state.cjs:186-231`.
2. Because there is no single chokepoint (1C), the check must live where all six sites converge - most plausibly a small `lib/core/` module that every site calls, or a validation applied to the emitted content. Do not assume `state-ops.cjs` alone is sufficient; the CHANGELOG's "single chokepoint" claim is measurably false.
3. Add `gsd_state_version` (or the chosen key) to `lib/core/frontmatter-schemas.cjs`'s `'STATE.md'` optional list to close the second drift.
4. Mutation proof: seed a stale version number, assert the gate reddens (SC1 requires exactly this).
5. Record the `.planning/STATE.md` half (1A) as an explicitly deferred, out-of-repo item citing both existing RCAs, so the phase does not silently appear to have fixed the symptom that motivated it.

## Common Pitfalls

### Pitfall 1: Fixing the wrong STATE.md
**What goes wrong:** the plan targets `.planning/STATE.md`, writes tests against gsd-core behavior, and lands nothing because the code is not in this repo.
**Why it happens:** the ROADMAP's motivating symptom and the requirement's wording point at different files that share a name.
**How to avoid:** make the target an explicit locked decision before planning. Cite both RCAs for the deferred half.
**Warning signs:** a task description containing `~/.claude/gsd-core`, or a test that shells out to `gsd-tools.cjs`.

### Pitfall 2: Assuming `state-ops.cjs` is the single chokepoint
**What goes wrong:** the version stamp is preserved on one path and silently destroyed on the other five; the phase gate passes while the bug persists in the hook-driven paths users actually hit.
**Why it happens:** `CHANGELOG.md:806` explicitly (and now inaccurately) calls it "the single Node chokepoint."
**How to avoid:** enforce against the census in Finding 1C. Prove coverage at a hook-driven site (`scripts/on-stop:145` or `on-task-complete:53`), not only at `computeState()`.
**Warning signs:** a test that only calls `computeState()` directly.

### Pitfall 3: The truncating shell redirect
**What goes wrong:** any check that reads the room's existing `STATE.md` to compare versions reads an EMPTY file at `scripts/on-agent-complete:133`, because `> "${ROOM_DIR}/STATE.md"` truncates before compute-state runs.
**Why it happens:** documented at `scripts/compute-state:29-33` - this is a known, already-bitten trap that the `current_room` field had to work around by re-deriving from the registry.
**How to avoid:** read the prior version BEFORE the redirect, or convert that site to the capture-then-write shape used at `on-stop:144-145`. Do not assume the file is readable at render time.
**Warning signs:** a version comparison implemented inside `scripts/compute-state` itself.

### Pitfall 4: A doctrine gate that passes vacuously
**What goes wrong:** the CTXL-02 presence gate asserts the strings "semantic" and "context" appear, which they already do (9 and 11 times in MWP-SPECIFICATION.md) - so it is green before any work is done.
**Why it happens:** naive `mustContain` on common words.
**How to avoid:** anchor on the *distinguished* terms and their distinguishing prose, and confirm the gate is RED before the doc edit. `tests/test-143.2-doctrine-presence.cjs:14-19` documents this exact failure mode as the "false-clean-illusion."
**Warning signs:** the gate passes on the first run.

### Pitfall 5: Reintroducing KuzuDB while editing MWP-SPECIFICATION.md
**What goes wrong:** a layer-distinction section written from the doc's own surrounding prose repeats "KuzuDB" as a current claim, contradicting the correction banner at `:3`.
**Why it happens:** the body still says KuzuDB in 9 places; the kuzu gate will NOT catch it because it skips `.md` (`check-kuzu-reintroduction.cjs:37, :82`).
**How to avoid:** write new prose against SQLite/room.db. Consider adding a `mustNotContain: ['KuzuDB']` scoped to the NEW section only, not the whole file.
**Warning signs:** the phrase "KuzuDB edge types" in new content.

### Pitfall 6: A CTXL-03 gate that fails on a null result
**What goes wrong:** the benchmark measures no accuracy delta at MindrianOS's small scale and the gate goes red, so the phase looks broken.
**Why it happens:** treating "improvement" as the assertion instead of "measurement occurred and was recorded."
**How to avoid:** SC3 is explicit - a null delta is a finding to record, not a skip and not a failure. Assert that a measurement ran and a result was written; do not assert its sign.
**Warning signs:** an assertion of the form `assert(withContext > withoutContext)`.

### Pitfall 7: Part 8 breach in the benchmark
**What goes wrong:** the A/B harness sends real room content to a judge model, egressing user data.
**Why it happens:** a benchmark needs room context by definition; that is the whole manipulated variable.
**How to avoid:** reuse `lib/core/part8-egress-guard.classify` as huji-eval's D4 does; use a seeded synthetic fixture room, never a live user room. Phase 239 just hardened this boundary (BRAIN-02) - a regression here would be a constitutional breach.
**Warning signs:** the harness reading from `~/MindrianRooms/`.

### Pitfall 8: Writing plans into the orphan phase directory
**What goes wrong:** artifacts land in the truncated duplicate dir and the orchestrator does not find them.
**Why it happens:** two `240.1-*` dirs exist (see Runtime State Inventory).
**How to avoid:** delete the truncated one first; `init.phase-op` resolves to `.planning/phases/240.1-context-layer-drift-detection`.
