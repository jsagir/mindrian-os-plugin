## Planning decisions (resolving 225-RESEARCH.md Open Questions - binding for this plan)

- **PD-1 (Open Question 1 - default + sticky):** the zero-score gate fires ONCE per
  session per room even when the binding's `sticky` flag is set (a total-miss is a
  strong-enough new-project signal to prompt once, per the research recommendation and
  the seed's open-fork #1 leaning). "continue in `<primary>`" is the pre-checked default
  at confidence 0.71 (primary-as-default with one-key reassign). After the user answers,
  the existing `consumeSessionBinding` sticky handling applies unchanged.
- **PD-3 (planner-added, anti-overfire, Phase 210 lesson):** zero-score messages are
  common ("thanks", "do it") - firing a gate on each would repeat the over-enforcement
  mistake Phase 210 reverted. The gate therefore requires BOTH a substantiality floor
  (`messageTokens.length >= ZERO_SCORE_GATE_MIN_TOKENS`, default 8, env-overridable via
  `MINDRIAN_ZERO_SCORE_GATE_MIN_TOKENS`) AND a once-per-session-per-room suppression via
  a decision-trace scan for a prior `kind: 'zero_score_gate'` entry. proving_case_2's
  reframe is a long, content-rich message; it clears the floor by construction.
- **PD-4 (Open Question 3):** requirements are locally numbered REQ-1..REQ-6, matching
  225-RESEARCH.md's Rec IDs verbatim (the Phase 224 precedent; no global REQ-XX ids map
  to this phase).
- **PD-5 (answer consumption):** the new gate persists its payload under the SAME
  `binding_gate_payload` key the shipped `consumePriorBindingAnswer` scans for (it keys
  on `e.binding_gate_payload`, NOT on `e.kind` - verified at intent-classifier.cjs:2249+),
  with the trace entry's `kind` set to `'zero_score_gate'` for trace disambiguation. The
  consumer is reused with ZERO changes. `labelToSlug` maps both "start a new project" and
  the `NO_ROOM_LABEL` option to the reserved `__no_room__` sentinel (`NO_ROOM_SLUG`, line
  173): picking "new project" unbinds the write path from the old primary (the actual
  proving_case_2 failure) and the gate's additionalContext instructs the assistant to
  offer `/mos:new-project` - the gate itself NEVER auto-creates a room (Part 7
  reuse-before-build).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user prompt -> UserPromptSubmit hook | Untrusted free text enters the classifier via stdin |
| session/trace files on disk -> hook | Locally writable JSON state is read back into the hook every turn |
| gate decision -> session binding write | The user's answer decides where subsequent writes land |

Mitigating constraint called out explicitly: this phase is room-local only (Canon
Part 8, no egress). The gate reads and writes local files exclusively; additionalContext
carries room slugs only, never message content; zero Brain/network tokens are introduced
(the Part 8 source-grep tripwires cover the edited file).
