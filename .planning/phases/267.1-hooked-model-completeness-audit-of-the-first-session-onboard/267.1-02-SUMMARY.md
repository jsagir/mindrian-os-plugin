## A1 and A2: SessionStart context delivery and the card-fire backstop

**Scope discipline note:** this executor's toolset did not include a Task/subagent-invocation tool, so the `claude-code-guide` agent itself could not be spawned. Per the plan's own fallback instruction ("do your own best-effort research via the Claude Code docs/config you can inspect locally... clearly label any residual uncertainty rather than inventing an answer"), Q1 was answered by fetching the actual current Claude Code hooks reference (`https://code.claude.com/docs/en/hooks`, fetched this session, `dateModified: 2026-08-26T16:14:25Z` per its own JSON-LD metadata -- one day before this research) rather than by inference, and Q2 was answered by a direct trace of this repo's own `scripts/check-card-fire.cjs`, exactly as the plan instructs ("The repo's own implementation is authoritative for what THIS backstop does").

**Q1 (A1), verbatim:** "When several SessionStart hooks are registered on the same matcher and more than one emits `hookSpecificOutput.additionalContext`, how does Claude Code combine them? Specifically: are the envelopes concatenated, does a later hook's envelope replace an earlier one, is there a size cap or truncation behavior, and does a non-zero exit or an `async` setting on one hook suppress another's context? The concrete case is a roughly 3000-character `additionalContext` payload emitted by hook number 2 of 9."

**A1 answer -- HIGH confidence, provenance: documented.**

Quoted directly from the current Claude Code hooks reference, "Add context for Claude" section: "When several hooks return `additionalContext` for the same event, Claude receives all of the values. If a value exceeds 10,000 characters, Claude Code writes the full text to a file in the session directory and passes Claude the file path with a short preview instead."

Applied to the concrete case:
- **Combination behavior: concatenation, not replacement.** All values are delivered, not just the last or the first. Confirmed independently by the same reference's `Setup` event row for the identical field: "String added to Claude's context. Multiple hooks' values are concatenated."
- **Size cap: a 10,000-character PER-VALUE threshold, not a shared budget across the 9 hooks, and not silent truncation.** Above that threshold the value is written to a session-directory file and Claude gets a path plus a short preview. FIRST_INSTALL's ~3000-character payload (`scripts/session-start:666`) is well under this threshold on its own and is delivered as full inline text, not redirected to a file.
- **Exit codes: SessionStart's own exit-code table entry reads "SessionStart: No [block] / Shows stderr to user only."** A non-zero exit on any of the 9 hooks does not block the session, does not suppress the other 8 hooks' output, and its stderr is shown to the human user, never to Claude -- it cannot silently eat a sibling hook's `additionalContext`.
- **Async: not actually in play for this repo's configuration.** All 9 `hooks/hooks.json` SessionStart entries are `async:false` (verified by direct read), so they run synchronously to completion before the session's first turn. Noted for completeness per the docs: an `async:true` hook's `additionalContext` can still reach Claude, but only once the background hook completes, which is immaterial here since none of the 9 are async.

**Effect on the audit (Trigger External / Action B=MAP):** **No downgrade.** A1 was the one leg of the audit's stated risk that could have weakened the Trigger or Action legs if context delivery were unreliable. It is not -- the FIRST_INSTALL prose reaches the model whole, unmodified, and un-suppressed, regardless of the other 8 hooks or their exit codes. RESEARCH.md's existing HIGH-confidence rating on the Trigger (external) leg stands unchanged; the Action leg's existing MEDIUM-HIGH confidence rating (downgraded only by A2, addressed next) is unaffected by A1.

**Q2 (A2), verbatim:** "On turn 1 of a session, does the `Stop` hook's card-fire backstop have anything to act on when the model rendered a three-option menu as prose because its SessionStart instruction did not name `AskUserQuestion`? Put concretely: can a Stop-hook backstop convert an already-emitted prose menu into an `AskUserQuestion` card, or can it only flag/log the miss for a subsequent turn?"

**A2 answer -- HIGH confidence, provenance: repo-code-read (this repo's own implementation is authoritative per the plan).**

Two independent reasons the backstop does NOT rescue FIRST_INSTALL's menu on turn 1, both confirmed by direct trace:

1. **Not a registered gate (`primaryHit` is false).** `classifyCardFire` first checks `gateReachingEntries(registry)` -- the set of `data/render-coverage-registry.json` entries flagged `render_coverage: 'card-emission'`. Direct read of that file (220 total entries) shows zero entries referencing `session-start` or `first_install`. FIRST_INSTALL is a raw prose block injected by a bash hook, never wired into the registry `lib/hmi/selector-dispatcher.cjs` tracks.
2. **The backstop's bare-numbered-list detection arm is RETIRED (`backstopHit` is false).** `computeBackstopHit` (line 472-477 of `scripts/check-card-fire.cjs`) tests ONLY `ASCII_BOX_UNCONDITIONAL_RE` -- a literal `[1] ... [2]` bracket-box shape, or the literal string "type 1, 2, or 3". The function's own header comment states plainly: "The Phase 209-07 bare numbered-prose alternative is RETIRED... it was an ~86% false-positive net in the live log... A real numbered-prose fork is now the model's own Phase-210 / SEED-021 judgment." FIRST_INSTALL's menu (`scripts/session-start:666`, "Offer three approaches: 1. Conversational Q&A... 2. Document paste... 3. Skip...") is exactly the bare-numbered-prose shape this arm no longer catches -- it contains neither a `[1]...[2]` bracket box nor the "type 1, 2, or 3" literal.

With both `primaryHit` and `backstopHit` false, `classifyCardFire` hits its first branch and returns `{ intercept: false, reason: 'no-gate-signal', degrade: false }` -- the pass-reason the plan's acceptance criteria requires be named. There is nothing for the backstop to act on.

**Even in the hypothetical where the model happened to render a literal `[1]...[2]` bracket box instead of the plain "1. / 2. / 3." the prose actually specifies**, the backstop still could not *convert* the already-shown message into an `AskUserQuestion` card. `buildEnforcementEnvelope`'s own header states the intercept branch produces `{ decision: 'block', reason, systemMessage, continue: false }` -- a Stop-hook block that forces the agentic loop to continue for another turn, not a retroactive edit of a message the user already read. A 2026-07-23 fix (documented in the file, `stop-hook-invalid-hookspecificoutput-schema`) additionally REMOVED the only machine-readable instruction this branch used to carry ("You MUST fire the AskUserQuestion card NOW") because Stop-hook `hookSpecificOutput`/`additionalContext` is not a valid schema variant for that event; the intercept branch today carries only a calm, human-facing `reason`/`systemMessage`, with no model-directive re-fire instruction left in any valid delivery channel.

**Effect on the audit (Action B=MAP / SEED-021 finding severity):** The finding does **not** soften from "defect" to "undeclared reliance on a backstop" -- it stays a **defect**, and the evidence sharpens rather than weakens it. Two independent, verified structural facts (unregistered gate, retired detection arm) both fail closed against FIRST_INSTALL on turn 1, and even the theoretical rescue path can only force a re-prompt, never fix an already-rendered message, and currently lacks any machine channel to tell the model what to fix. Plan 267.1-01's SEED-021 remediation (declaring the `AskUserQuestion` mandate explicitly in the FIRST_INSTALL prose, matching the two sibling branches at `:608` and `:707`) remains the correct and now more clearly necessary fix -- there is no backstop to lean on if that declaration is ever regressed.
