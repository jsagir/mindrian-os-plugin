## Summary

The FIRST_INSTALL onboarding surface is `scripts/session-start` lines 665-666: a single interpolated bash string injected into Claude's `additionalContext` as prose instructions to the model. It is not a program. Every behavior it describes is an instruction the LLM may or may not follow, and nothing downstream verifies compliance. That single structural fact is the spine of this entire audit: three of the four TARI legs are asserted as prose and only one of them has any deterministic machinery behind it.

The audit's two open legs resolve as follows. **Reward is a PROMISE, not a payoff.** The FIRST_INSTALL prose contains one reward-shaped line ("Based on your work in [domain], here is what I already know about your space") which maps to no wired call. The repo's two real variable-reward engines - `sweepDomainInsights` (`lib/core/domain-insight-sweep.cjs`, explicitly documented as "THE single entry point for the Hooked variable-reward leg") and the breakthrough scan (`scripts/check-pending-breakthrough.cjs`) - are both structurally unreachable at first install: the sweep is only invoked from `/mos:ignite`, and the breakthrough scan returns `{continue:true}` silently when no active room exists. The cold-start menu the first-time user is shown (line 657) does not mention `/mos:ignite` at all, even though `skills/ignite/SKILL.md:50` calls ignite "the canonical front door... for the full Hooked first-cycle experience." The reward machinery is built, shipped, tested - and not routed to from the one surface that needs it most.

**Investment is asserted and has no writer.** The prose tells the model to "build a USER.md file in their home directory (`~/.mindrian-user.md`)". `lib/core/user-archetype.cjs:64` READS that exact path. Nothing in `lib/`, `scripts/`, `hooks/`, `commands/`, or `skills/` ever WRITES it. The only deterministic USER.md writer, `writeUserMdAtomic` (`lib/core/user-md-ops.cjs:440`), is called from exactly one place - `lib/core/navigation/room-birth.cjs:572` and `:801` - and writes to `roomDir/USER.md`, which by definition does not exist at first install. The dogfood machine confirms it: `~/.mindrian-onboarded` exists (dated 2026-04-05), `~/.mindrian-user.md` does not. The only durable side effects of a completed first session are `touch ~/.mindrian/auto-update` (line 662) and `check-onboard --write` writing a version string and a date (`scripts/check-onboard:18-19`). Neither is user Investment in the Hooked sense; neither loads a next Trigger; neither creates a switching cost.

**Primary recommendation:** Plan this as AUDIT-ONLY, deliverable = a scored `/70` Hooked scorecard document plus a cited gap register, following the established precedent of `.planning/research/2026-06-09-hooked-model-larryreach-loop-audit.md` (45/70) and the `/mos:ignite` audit (38/70) in `.planning/debug/beta13-curing-sequence-persona-and-commands-bisect.md:187-209`. Register remediation as follow-up phases, do not build it here - Phase 269 will materially change the onboarding Trigger/Reward/Investment legs by removing Brain-key friction (see ROADMAP.md:564), so remediation built now risks throwaway work.

### GAP R-1: Reward is a promise, not a payoff (HIGH confidence)

**What the prose says:** "If they provide context, follow up with domain intelligence: 'Based on your work in [domain], here is what I already know about your space' -- then suggest relevant frameworks and room sections."

**What is behind it:** nothing. No tool call, no script invocation, no library reference. The model is asked to improvise domain knowledge from its own weights.

**Test against the rule's own four-part reward definition** (`reward-before-investment-rule.md:52-56`):

| Criterion | Verdict | Reasoning |
|-----------|---------|-----------|
| Unpredictable (user could not produce it in <30s) | FAIL | Generic domain commentary is exactly what a user expects from any LLM |
| Intelligible | PASS | It is prose |
| Valuable | WEAK | Depends entirely on model improvisation quality, unmeasured |
| **Attributable to MindrianOS uniquely** | **FAIL** | This is the decisive criterion. "Not something ChatGPT could do in the same time budget" - a generic domain-knowledge paragraph is precisely what ChatGPT does. Zero MindrianOS machinery is engaged. |

Two of four criteria fail, including the decisive one. Under the repo's own definition, **FIRST_INSTALL delivers no qualifying variable reward.**

**The machinery exists and is unreachable.** Two shipped reward engines:

1. `lib/core/domain-insight-sweep.cjs:5-7` header, verbatim: "THE single entry point for the Hooked variable-reward leg of the blank-slate persona." It consumes generic domain handles from `extractDomains`, drives Tavily SIGNAL search per handle, derives cross-domain adjacency insights locally, files them as proposed claims and opportunity candidates. Its only invocation site is `skills/ignite/SKILL.md:209` / `commands/ignite.md:213`. It requires an open `db` handle (line 106 signature `{domains, roomDir, sessionId, db}`) - the header at line 33-36 states the pre-room degradation explicitly: without a db handle, only `extractDomains` runs and the handles surface as text. FIRST_INSTALL never calls either.

2. `scripts/check-pending-breakthrough.cjs` - registered as a SessionStart hook, and its own header (line 27) cites "Canon Part 10 sub-claim 5: variable reward fires automatically; the math IS the surface; no user-facing trigger required." But `resolveRoomsHome()` returns `null` when `~/MindrianRooms` does not exist, and the documented flow step 4 is "If top === null -> emit `{continue: true}` (D-16 empty-state silence)." **On a genuine first install there is no rooms directory at all, so the repo's flagship automatic variable reward is structurally silent on the exact session where a first reward matters most.**

### GAP G-1: the enforcement mechanism has no jurisdiction here (HIGH confidence)

`docs/reward-before-investment-rule.md:97-108` describes the detection mechanism: every command declares `interactive_first_reward` in frontmatter; `lib/core/mva-rule-linter.cjs` validates it; `scripts/check-reward-before-investment.cjs` runs it; the pre-commit hook gates it.

**`scripts/session-start` is a bash hook, not a command `.md`. This is a governance gap, not just a content gap, and it is arguably the most actionable finding in the audit because it explains *why* the other gaps survived: nothing was ever built to catch them.

## Common Pitfalls

### Pitfall 1: Confusing prose instruction with implementation

**What goes wrong:** Reading `scripts/session-start:666` and concluding "the flow builds a USER.md" because the string says so.
**Why it happens:** The FIRST_INSTALL block is a single 3000-character bash string that reads like a specification. It is a request to an LLM.
**How to avoid:** For every behavioral claim in the prose, grep for a writer/caller. If the only hits are the prose itself and a reader, the leg is ASSERTED, not IMPLEMENTED.
**Warning signs:** A claim you cannot trace to a `.cjs` function or a shell command.

### Pitfall 2: Treating the retired Hooked ratification gate as retiring the Hooked design mandate

**What goes wrong:** Reading Canon Appendix D entry 31 ("the Hooked ratification gate is RETIRED") and concluding this audit is obsolete.
**Why it happens:** The word "retired" appears next to "Hooked" in canon text, in a heavily-worded passage.
**How to avoid:** Entry 31 retires the composite AS A MEASUREMENT GATE for Part 10 ratification. Decision 8 (design rule) and `reward-before-investment-rule.md` (architectural constraint) are separate instruments and remain binding. The Manipulation Matrix is explicitly KEPT.
**Warning signs:** Presenting the `/70` as a pass/fail threshold. It is diagnostic only.

### Pitfall 3: Auditing `/mos:onboard` instead of FIRST_INSTALL

**What goes wrong:** `/mos:onboard` is a rich, well-documented 400+ line command with declared reward frontmatter. It is a tempting subject and it is NOT the phase subject.
**Why it happens:** They cover overlapping ground and `onboard.md` is easier to read than a bash string.
**How to avoid:** The Goal names `scripts/session-start`'s FIRST_INSTALL branch. `/mos:onboard` is a user-invoked command a first-time user may never run; FIRST_INSTALL fires automatically. Reference `/mos:onboard` for comparison, do not substitute it.
**Warning signs:** Findings citing only `commands/onboard.md` line numbers.

### Pitfall 4: Auditing the dev-repo session instead of a real first install

**What goes wrong:** Reasoning from what happens in this repo's own sessions, which have `~/.mindrian-onboarded` present, a populated `~/MindrianRooms`, and an active room - the exact opposite of a first install on every input.
**Why it happens:** It is the environment in front of you.
**How to avoid:** Trace the code path with `ROOM_DIR=""`, no `~/MindrianRooms`, no marker file. See Runtime State Inventory below for the exact state to simulate.
**Warning signs:** Any claim that a room-dependent surface (breakthrough scan, JTBD nudges, opportunity bank, scratchpad) contributes to first install. None of them do.

### Pitfall 5: Assuming the shipped repo equals the running plugin

**What goes wrong:** Auditing `main` and reporting on what users experience.
**Why it happens:** Documented recurring failure in this project.
**How to avoid:** Per the standing hard rule (`feedback_dev_repo_fix_not_live_until_released.md`), a commit on `main` is not live until a release ships AND is picked up. State explicitly which version the audit describes: read `.claude-plugin/plugin.json` version and say so in the deliverable header.
**Warning signs:** Any sentence of the form "users currently see X" without a version pin.

### Pitfall 6: Missing the rethinking-room mirror

**What goes wrong:** Filing the audit only in `.planning/` and calling the phase done.
**Why it happens:** `.planning/` is where GSD artifacts live.
**How to avoid:** CLAUDE.md's Dev-Research Compositing rule is explicit: research touching MindrianOS's own architecture files in BOTH `.planning/phases/267.1-.../` and `~/MindrianRooms/rethinking-mindrianos/research/<dated-entry>/`, cross-linked, mirrored to `mindrianOS/research/`. A one-home filing "counts as incomplete."
**Warning signs:** No room-side path in the completion summary.

### Pitfall 7: Scope creep into Phase 269

**What goes wrong:** The Brain-key friction (GAP S-1) is a real and severe first-session Hooked violation, and it is very tempting to fix.
**Why it happens:** It is the biggest single friction number in the tester data.
**How to avoid:** ROADMAP.md:564 assigns it to Phase 269. Document it, quantify it, hand it over.
**Warning signs:** Any task touching install docs, key provisioning, or `mindrian-website`.

### Pitfall 8: Missing the ~3000-character prose block by reading the file with line-based tools

**What goes wrong:** `scripts/session-start` has "very long lines (2207 max)" per `file(1)`. Line 666 is the entire FIRST_INSTALL payload on one line. Line-window reads truncate or mislead.
**How to avoid:** Read line 666 in isolation and unescape the `\n` sequences before analyzing.
**Warning signs:** A quoted excerpt of the prose that stops mid-sentence.
