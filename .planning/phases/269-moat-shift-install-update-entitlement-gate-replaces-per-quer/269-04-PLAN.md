  <decision>
Under the moat shift, what is the install/update entitlement credential: a replacement for the Brain API key, the same credential with a second authorized use, or a promotion of the existing per-install registration token?
  </decision>

  <context>
Two `mbr_`-prefixed shapes already coexist in the SAME Supabase `brain_api_keys` table, split only by the `plan` column. Shape A: the dashboard trial key (`plan: 'free'`, 30-day `expires_at`, `daily_limit: 50`, minted by `provisionTrialKey` behind Google OAuth on `/brain-access`). Shape B: the per-install token (`plan: 'install'`, read-tier ceiling, idempotent per `install_id`, cached at `~/.mindrian-install.json` mode 0600, minted by an unauthenticated `POST /register`). They are already one credential type with two issuance paths, so the real question is which path survives and what authorizes it.

Two constraints bear on the choice. First, `MINDRIAN_BRAIN_KEY`, `commands/setup.md`, `bin/cli.js:206-208`, `docs/install/BRAIN-SETUP.md`, and the byte-locked `reason: 'MINDRIAN_BRAIN_KEY not set'` in `lib/core/refusal-messaging.cjs` all encode the current name; Option A breaks every one. Second, an install gate wants a PER-INSTALL credential, because the thing gated is an install; a per-person credential means one leaked key entitles unlimited installs, which is the failure mode SEED-011 Option B was formally rejected for.

One precondition applies only to Option C: assumption A2 records that `POST /register` is documented as shipping but its production deploy on `pws-brain-mcp.onrender.com` was NOT probed. If C is chosen, that probe is a precondition, not a later detail.
  </context>

  <options>
    <option id="option-a">
      <name>Replace outright</name>
      <pros>One credential, one purpose. The `mbr_` prefix and Supabase schema survive unchanged.</pros>
      <cons>Breaks every keyed user's mental model and every doc string. The byte-locked refusal reason becomes a declared wire-contract amendment. Rewrites needed in setup, cli, and BRAIN-SETUP docs. Still per-person, gating a per-install action.</cons>
    </option>
    <option id="option-b">
      <name>Unify: one credential, two authorized uses</name>
      <pros>Smallest blast radius. Only the check LOCATION moves. Zero schema change, existing keyed users unaffected, matches ROADMAP.md's own "two authorized uses" phrasing.</pros>
      <cons>Leaves `expires_at`, `daily_limit`, `total_requests` as dead per-query metering weight. A variable named `BRAIN_KEY` that no longer gates Brain access is semantically muddy. Still per-person.</cons>
    </option>
    <option id="option-c">
      <name>Promote the per-install token (research finding, not a verdict)</name>
      <pros>Roughly 80 percent of the plumbing exists: per-install identity, idempotency, mode-0600 storage, revocation by flipping one row, a threat model on the record, an opt-out contract, a register-specific rate cap. Per-install granularity fits an install gate: revoke one machine, not one person. Keeps every env var name.</pros>
      <cons>Making `POST /register` authenticated inverts its documented "Unauthenticated by design" contract, so `docs/BRAIN-IDENTITY-DESIGN.md` needs a formal amendment. Coordinated changes across three repos. Carries the A2 deploy-status precondition.</cons>
    </option>
  </options>

  <action>
Present the three options with the two constraints and the A2 precondition stated. Do NOT pre-select. `269-RESEARCH.md` names Option C as a research finding and states plainly it is not a decision, because ROADMAP.md defers the call to this phase's own planning.

Capture: the chosen option id, a one-paragraph rationale in the navigator's own framing, and for EACH unchosen option the specific reason it lost. If Option C is chosen, also capture whether the A2 probe (confirming `POST /register` is live in production) blocks locking the option or is a follow-up.

Also surface, without forcing an answer, open question Q2: whether "install gate" means privatising distribution (repo visibility, private npm, an authenticated marketplace) or letting anyone install and refusing to OPERATE without an entitlement (client-side, forkable, backed by a BSL license whose grant (d) may not support it, per FLAG 3). The two readings produce completely different Family E plans. Record the answer, or record it as still open.
  </action>
