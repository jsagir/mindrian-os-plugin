Tri-polar stance: the controller is pure CJS with in-process fetch, but deep runs need the model to read each lane's records, which on CLI is the Read-only `research-lane-analyst` agent dispatched by `/mos:research` (363-18). On Desktop and Cowork the deep plan is composed, reviewed and saved, and the run itself executes in Claude Code, said plainly (D-14 honest degrade, 363-RESEARCH.md Assumption A8). Deep runs are never ambient (D-03).

Egress audit (Part 8): outbound strings are only the round-one approved q strings and composed follow-ups and falsifiers from families.cjs, each checked by validateExecutedQuery against the run grant and audited again at the corpus dispatch. The lane payload handed to the analyst contains a records file path, the leaf question (LOCAL), the falsifier and the lane id, never room content beyond the leaf and never a network capability.

State persistence (so the CLI can step across separate Bash calls): `<room>/.mindrian/research-runs/<run_id>/state.json` (atomic writes), `lanes/<lane>.records.json`, `lanes/<lane>.rows.json`; the state carries plan_hash, and every step refuses to continue if the plan file's hash no longer matches (tamper). Steps and payload shapes:
- fetch_round -> payload {round, lanes:[{lane, leaf_id, queries:[q_hash...]}]}; fetchRound fetches every approved query for the round.
- dispatch_lanes -> payload {lanes:[lanePayload]} for the host to hand to analysts; the controller waits for recordLaneRows per lane.
- validate -> internal after every lane recorded.
- reflect -> payload {leaves_open, unused_records_digest (record ids fetched but not cited, the Co-STORM steering pattern)}; the host may call proposeFollowups with [{leaf_id, lens, slots}].
- extend_card -> payload {card (F.3), new_queries} when any follow-up is outside the approved family, provider or remaining budget.
- counterevidence -> payload {queries} (mandatory pass).
- synthesize -> the controller builds the RunResult.
