# Phase 365.1 planning input: edge-derived verification rung, after the ladder is ratified

## Why this is its own phase

Phase 365 shipped everything that does not depend on the exact rungs: the approval floor at the human gate, the never-do list, the pulled portrait and the standing words on every rendered claim surface. The rest of the original spec needs the verification ladder to be final, because it writes rung numbers, rung names and a new node type into the record. Plans written against an unratified ladder would be rewritten the day the paper author amends it (D-25). So that work waits here, behind a data fence (`data/verification-ladder.json`, `ratified: false`) and a fence test (`tests/test-365-ladder-fence.cjs`) that fails if any of it lands early.

## Scope

- **B1 derivation.** The rung is derived from edges, never declared by the filer. Rung 3 and up needs an outbound provenance edge to a node that carries `url` and `retrieved_at`. Rung 4 additionally needs a `locator` (page, section, DOI, clause). Rung 5 needs an edge to a person node. A declared rung that the edges do not support is written at the supported rung and the discrepancy is recorded, not discarded. The four locked provenance fields (`source`, `url`, `retrieved_at`, `evidence_tier`) are extended, never renamed or dropped.
- **B1a person node.** A node type for a person with standing who checked a claim or dissented from it. Adding a node type is a canon amendment under the Appendix D entry 24 precedent (the same route the truth-claim type set took), so it needs its own ruling and its own Appendix D entry. The person floor in 365 always holds (no person node exists), by D-22.
- **B4 split of the unsupported scan.** `findUnsupportedClaims` reports silence as one kind. Split it by the kind of silence: no check at all, checked only by asking a model, checked against a source but not the deciding part. The 365 fence (F6) fails if a silence-shaped export lands in insights.cjs before ratification.
- **Phase 358 record migration.** Existing checking records carry the provisional 1 to 5 rung numbers (`own_intuition`, `model_counter_argument`, `database_or_document`, `primary_source`, `dissenting_person`). Map them onto the ratified ladder, or re-record. The mapping is one of the questions in the ratification ask.

## What 365 left ready

- `claimStanding(db, claimId)` in `lib/core/navigation/verification.cjs` is the ONE function the derived rung replaces. Every surface (the gate why-line, the floor check, the portrait, both Zone 3 signals, room home, graph export, the claim view) reads it, so nothing else has to change when its body changes.
- `STANDING_WORDS` and `HELD_WORDS` (the PROVISIONAL(365) block in `verification.cjs`) freeze on ratification. Tests build their expectations from those exports, so a wording change is a one-place edit.
- `FLOOR_IDS` already uses the draft ladder ids, and the floor is stored in ROOM.md as an id, never a number, so renumbering costs nothing.
- The locator currently counts on the source node properties or on the SOURCED_FROM edge properties; 365.1 may choose one home.
- `DEPENDS_ON` and `ASSUMES` are named in `PROVENANCE_EDGE_TYPES` but are inert until a ruling admits them to `ALLOWED_EDGE_TYPES`.

## The gate that opens it

Flip `data/verification-ladder.json`: `ratified` to `true`, with `ratified_at` and `ratified_by_role` filled. `tests/test-365-ladder-fence.cjs` then prints `RATIFIED: the ladder fence is released; open Phase 365.1` and exits 0. Only after that does `/gsd-plan-phase 365.1` run. If the paper author amends the ladder, the amended ids replace the draft in that file first, and `FLOOR_IDS` follows.
