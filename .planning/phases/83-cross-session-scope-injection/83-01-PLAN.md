# Plan 83-01: Ship statusline-mos wrapper as plugin file and auto-configure migration

## Goal

Ship the statusline-mos wrapper (currently only at ~/.claude/statusline-mos on Jonathan's machine) as a first-class plugin file at scripts/statusline-mos. Patch scripts/session-start so every session installs the wrapper to ~/.claude/statusline-mos (cp + chmod +x) and rewrites settings.json statusLine to the wrapper path. Migration is detection-driven and idempotent: only fires when the current statusLine command contains "context-monitor" but does NOT already point at a wrapper. Users who hand-fixed their settings are not re-migrated. Closes the wrapper half of SCOPE-INJ-04 and SCOPE-INJ-05 and establishes the backwards-compat baseline for SCOPE-INJ-06.

## Scope

1. Create scripts/statusline-mos (NEW, bash). Mirror the version Jonathan installed at ~/.claude/statusline-mos on 2026-04-14. The wrapper:
   - Resolves $HOME/.claude/plugins/cache/mindrian-marketplace/mos/
   - Lists subdirectories, filters to semver-like names
   - Sorts via `sort -V`, picks the highest version
   - Exports MINDRIAN_OS_ROOT to match
   - execs `scripts/context-monitor` from that resolved version
   - If no cache version is found, falls back to printing an empty statusline and exits 0 (never error out the status bar)
2. Patch scripts/session-start auto-configure block (currently lines 446-468):
   - Replace MONITOR_PATH usage with a two-step install-and-point sequence
   - Step A: `cp "${PLUGIN_ROOT}/scripts/statusline-mos" "${HOME}/.claude/statusline-mos" && chmod +x "${HOME}/.claude/statusline-mos"` (idempotent refresh on every session)
   - Step B: detection-driven settings.json rewrite. Read current statusLine.command. Migrate only when command contains "context-monitor" AND does not already contain "statusline-mos". Point the command at `"${HOME}/.claude/statusline-mos"` (literal expansion at write time, not a template string).
   - Preserve the existing `_savedStatusLine` backup behavior for first-time migration.
   - Never clobber a command that is already pointing at the wrapper.
3. Ensure shellcheck-clean bash, no em-dashes, no emoji.

## Out of Scope

- Any change to scripts/context-monitor itself (the wrapper only execs it)
- Any change to settings.json fields other than statusLine
- Removing the `_savedStatusLine` field on migration rollback (no rollback in this phase)
- Active room scope injection (that is 83-02)
- Sealed room walking (that is 83-03)

## Task Breakdown

1. Write scripts/statusline-mos (bash, executable, ~40 lines). Cache resolution, sort -V, exec.
2. Patch scripts/session-start auto-configure block (lines 446-468). Add wrapper install step before the python3 rewrite block. Update the python3 block so the target command is the wrapper path, and add the "does not already contain statusline-mos" guard to the detection condition.
3. Ensure the patched block still exits 0 on failure (trailing `|| true` survives).
4. Local smoke: run the wrapper by hand from the plugin repo, confirm it prints something sensible or exits 0 silently.

## Tests

Tests land in 83-04, not here. This plan only writes the production files. Plan 83-04 covers:
- Wrapper resolution via sort -V across three synthetic cache versions
- Wrapper migration idempotency (run session-start twice, settings.json identical after first migration)
- Wrapper non-clobber when settings.json already points at a wrapper
- Wrapper fallback when no cache versions exist

## Risks

- Risk: `sort -V` behavior differs between BSD and GNU sort on macOS versus Linux. Mitigation: test on both, fall back to `ls | sort -r` if sort -V is unavailable.
- Risk: The `_savedStatusLine` backup collides if the user already has one from a prior failed migration. Mitigation: only set `_savedStatusLine` when it is not already present.
- Risk: A user on Windows with no bash available cannot run the wrapper. Mitigation: run-hook.cmd already handles the no-bash case by exiting 0 silently; statusLine stays on whatever the pre-migration command was.
