## Decision map

See `275-01-PLAN.md`'s Decision map for the full D-01 through D-13 table. This plan implements
**D-10** (L1 `STATEMENT` is a frontmatter key in each section's `ROOM.md`, not a separate
`STATEMENT.md`), and builds the two mechanisms that **D-07**, **D-08**, **D-09**, **D-04** and
**D-12** need in order to land as content in plans 275-05, 275-06 and 275-07.

### D-10 rationale (a Claude's Discretion item, resolved here, on the record)

`275-CONTEXT.md` names two options and locks neither: a YAML frontmatter key, or a tiny
`STATEMENT.md` file per section. Resolved in favour of the frontmatter key for four reasons:

1. **Canon Part 7, reuse before build.** `ROOM.md.section.tmpl` already has a `{{KEY}}`
   substitution mechanism with four keys wired through `sectionSubs`. `statement` is a fifth key,
   not a new file class, a new writer, or a new discovery surface.
2. **It inherits validation for free.** `lib/core/frontmatter-schemas.cjs`'s `ROOM.md` schema
   already governs the `section` / `purpose` / `stage_relevance` / `default_methodologies`
   vocabulary. A `STATEMENT.md` file would fall through to `artifact-default` and be validated as
   an artifact, which it is not.
3. **A twelfth file per section adds a surface with no reader.** Canon Decision 15 already
   guarantees every directory has a `ROOM.md`; every tool in this repo that inspects a section
   opens that file. Nothing opens a `STATEMENT.md`.
4. **The body render, not the frontmatter key, is what closes the self-guiding-room gap.**
   SEED-084's own item 6 is the foreign host with no MCP tools reading raw markdown. So the
   statement is rendered TWICE: once as a machine-readable frontmatter key, once as a blockquote
   directly under the H1 where a stranger reading the file sees it first.

<objective>
Build the three ICM layer mechanisms in the scaffold: L1 renders each section's `statement`, L2
writes each section's `CONTEXT.md` contract, and L3 materialises the per-room `references/`
factory directory.

Purpose: `MindrianRooms/CLAUDE.md` has claimed L0 through L4 for months while no room implements
past L0/L1. This plan is where the claim becomes machinery. It is deliberately content-agnostic:
the contract text (275-05, 275-06) and the reference documents (275-07) are authored in parallel
plans against the conventions fixed here.

Output: a scaffold that produces, per room, 11 section `ROOM.md` files carrying a visible
statement, 11 section `CONTEXT.md` contracts, and one `references/` directory with an identity
file and the two schema documents.
</objective>
