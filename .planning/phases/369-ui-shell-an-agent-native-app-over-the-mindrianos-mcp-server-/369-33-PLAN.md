<objective>
Make a gate raised anywhere visible to the shell: every mint for a bound session records the card in its room, and a read-only gate_list tool lists the open ones and reads any one gate's state. This is the first half of gap 1 and the read surface gap 2 needs.

Design (the ruled direction of 369-ADAPTER-RULING.md: "the shell raises the gate on the browser session"; this paragraph governs plans 369-33, 369-36, 369-41, 369-42 and 369-44):
Why a durable record: Claude Code runs the MindrianOS server as its own stdio process (`.mcp.json` starts it directly; 369-SESSION-CONTRACT.md section 4), so a gate Larry raises with gate_render lives only in that process's in-memory ledger. The shell talks to a different process, the flag-ON daemon, and can never see that ledger. The one medium both processes share is the room's room.db, the same medium the change feed already uses across processes (D-18). So: (1) this plan: every mint for a bound session writes a gate_raised record (a memory_event through navigation.logMemoryEvent, event type mcp_client_event_logged, label gate_raised, dedupe key gate_raised:<id>) carrying the card contract and no session identity; a take that leaves without a recorded answer writes gate_closed; a read-only gate_list tool lists the open ones for the caller's bound room and reads one gate's state. (2) Plan 369-36: the shell re-mints a MIRROR of the gate on the browser session through gate_render with mirror_of, the card drawn from the room's record and not from the caller; the person answers the mirror through the existing nonce-bound, human-only, durable path (D-15, plans 21 and 26); gate_answer on the mirror writes the source gate's answer anchor in the same transaction, so the source's owner gets "answered elsewhere" with the recorded verdict when it answers, a halted chain step resumes once with that verdict, and the shell list drops it. (3) Plans 369-42 and 369-44 wire listOpenGates, readGate and the views to it.
Why not loosen the ledger instead: letting the browser answer the source id needs the browser session to pass a session check it does not own, or a hand-off token. That is the failure class of spike 007 and Phase 289 (one session consuming another's gate), it breaks the owner-after-stranger guarantee, and it is impossible across processes anyway, because the daemon does not hold the source entry.
Tradeoffs, stated: one extra room write when a gate is raised for a bound session (and one at a take without an answer), visible as activity rows in the change feed; gate_render becomes a room write when a room is bound (its description says so; the 276 honesty sweep is re-measured in plan 369-41); a gate whose owning process ends before an answer stays listed until its 30-minute window closes, and answering its mirror records the decision but cannot resume a step that process held (said plainly in plan 369-36's response and in 369-REVIEW-FIX.md); a chain halt answered in the browser resumes only when its owner next calls gate_answer.

Purpose: SHELL369-12 (visibility half) and the GREC369-05 read surface for gap 2.
Output: lib/mcp/gate-raised.cjs, the ledger observers, the gate_list tool, three room readers, a Claude Code shaped stdio test helper and tests/test-369-gate-raised.cjs.
</objective>
