# Phase 369 - UI Design Contract

> Visual and interaction contract for the UI shell (the fourth MindrianOS surface). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Every value is either quoted from a named source or marked **(contract default)**, meaning this contract chose it and the executor builds it as written.

**What this contract governs:** the browser shell only (D-01). Shipped v1.1 generators, the three MCP App views and every other HTML surface are untouched (D-01, D-02).

This contract therefore names tokens as CSS custom properties and describes components by behaviour, markup semantics and tokens. It never names a library class. Both bake-off candidates must render this contract identically.

## Spacing Scale

Base unit: **4 px**. Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| `--space-xs` | 4px | Gap between a state mark and its written status; focus-ring offset |
| `--space-sm` | 8px | Gap inside a row (rank, label, Recommended tag); gap between stacked status lines |
| `--space-md` | 16px | Default element spacing; CTA internal padding and column gap; phone page margin; phone grid gutter; option-row horizontal padding |
| `--space-lg` | 24px | Panel padding (desktop); desktop grid gutter; space between a heading and its content block |
| `--space-xl` | 32px | Space between blocks inside one region (question block to "Since you were here") |
| `--space-2xl` | 48px | Space between page regions; desktop page margin; top padding below the nav row |
| `--space-3xl` | 64px | Desktop page margin at 1280 px and wider; header bar height |

Layout grid (Canon s8: strict 12-column desktop grid, four-column phone grid; breakpoint from website `globals.css` line 187):

| Viewport | Columns | Gutter | Outer margin | Max container |
|----------|---------|--------|--------------|---------------|
| below 768 px | 4 | 16px | 16px | fluid |
| 768 px to 1279 px | 12 | 24px | 48px | fluid |
| 1280 px and wider | 12 | 24px | 64px | 1280px content width (contract default) |

Fixed heights (contract default, multiples of 4): header bar 64px; primary-nav row 48px; option row minimum 56px; list row minimum 48px.

Exceptions (each is a canon-locked or accessibility number, not a spacing choice):
- Rules are 1px or 2px ink (Canon s3, s8). Structural borders (header bottom, panel frames, fieldset, CTA border) are 2px; row dividers inside a list or fieldset are 1px.
- Primary CTA minimum height 56px; marker column 24px (Canon s9). Compact CTA minimum height 44px (website `globals.css` line 253).
- Touch targets 44px or more on phones, 24px minimum anywhere (Canon s9).
- CTA hover moves the whole control 6px right, active 8px total, the triangle leads 4px (Canon s9; website lines 258-262). These are motion displacements, not spacing.
- Section-enter motion rises 12px (Canon s11).
- Ochre triangle geometry 15px wide by 18px tall (v3 spec `.action-marker`: border-left 15px, top and bottom 9px).
- Glyph geometry, not spacing: the custom radio and checkbox are 20px with a 10px inner square (website `.step-done` precedent, `globals.css` line 678); the StateMark is 12px. These follow the website's drawn marks, not the 4px grid.
- Note: the v3 spec's sample CSS pads the CTA `14px 18px` with a 14px gap. Canon s9 text does not fix those values, so the shell rounds them to the 4px grid: padding 12px vertical, 16px horizontal, column gap 16px, inside the 56px minimum height. This is the only deliberate departure from the website's CTA metrics.

## Typography

Exactly four sizes and two weights. Italic is a style, not a third weight.

| Role | Family | Size | Weight | Line Height | Where |
|------|--------|------|--------|-------------|-------|
| Label | DM Sans or JetBrains Mono | 12px | 400 | 1.35 | Status words, legends, eyebrows, timestamps, ids, CTA consequence line, field hints. Mono for machine labels and status (Canon s7); DM Sans for the consequence line and hints |
| Body | DM Sans | 16px | 400 (700 for emphasis, row titles, CTA label) | 1.5 (CTA label 1.15) | Running text, list rows, option labels and descriptions, nav tabs, buttons |
| Heading | Fraunces | 24px | 700 | 1.2 | Region headings ("Since you were here", "Next decision", "Evidence"); the wordmark uses this size in Bodoni Moda |
| Display | Fraunces | 40px (the same Display role renders at 32px below 768px: a responsive step of one role, not a fifth size) | 700 | 1.05 | The one H1 per view: the room's current question, or the decision's question |

Sources for the numbers: weights 400 and 700 match the shipped canon implementation (`globals.css` line 247 CTA label 700, line 248 consequence 400, line 453 `.mos-h1` 700); 12px label and 16px body match lines 247, 248, 295-297, 379; Display line height 1.05 matches spike 007's gate H1; the 40px Display and 24px Heading steps are **(contract default)** sized for a work tool rather than a marketing hero.

Rules:
- One unmistakable H1 per view (Canon s7). Region headings are H2. No H3 styling distinct from Body 700.
- Display uses `font-variation-settings: "opsz" 100` and `letter-spacing: -0.015em` (`globals.css` `.mos-h1`, lines 452-457).
- Uppercase letter-spaced labels used sparingly (Canon s7): at most one eyebrow per region, `letter-spacing: .06em` (`globals.css` `.tr-title`, line 316).
- Accent word: Fraunces italic in ink, used only in system-authored H1s (for example the empty states below). Never on room content (the shell cannot know which word of a user's question deserves emphasis) and never in rust (rust carries meaning only).
- Body copy is left-aligned, maximum line length 68ch **(contract default)**. No centred paragraphs (Canon s7).
- Bodoni Moda appears only in the wordmark. The shell has no editorial interruptions.
- Room content renders as text, never as raw HTML (RESEARCH Security: XSS from room content). Claim bodies render Markdown as plain text with line breaks preserved (spike 007 precedent); full documents render through the read-only BlockNote display.

## Color

Canon s3 sets the split as about 70 percent paper by area, which overrides the template's 60/30/10 default.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (about 70 percent) | `--paper` #F5F0E6 | Page background, list surfaces, the document reader, the gate view |
| Secondary (about 25 percent) | `--paper-deep` #E9DFCF and `--ink` #14202B | paper-deep: the Next decision panel, the status panel, table heads, the selected-option plane, the floor notice band. ink: all type, all rules, the primary CTA bar, the black tile |
| Accent (under 10 percent, meaning only) | `--rust` #A8462D, `--cobalt` #2457A5, `--ochre` #D49A20 | Reserved lists below; never decoration (Canon s3, s5) |
| Destructive | none styled as destructive | v1 has no action that destroys room data. `--error` #A12E2E is reserved for error text, error borders and the inline error block only |
| Confirmation | `--success` #2F6849 | The status line that confirms a recorded decision ("Decision recorded in the room.") and nothing else |

Accent reserved for (exhaustive; any other use is a defect):
- **Rust:** (1) the completion square that snaps into place when a decision is recorded; (2) the red tile mark (challenged or fixed, always with a written status). Rust is never small text on `--paper-deep` (Canon s4: 4.45:1, large text and UI only).
- **Cobalt:** (1) the 2px bar under the current primary-nav tab (Canon s5: a current page in a navigation list is a 2px cobalt bar); (2) the one current circle per view (see View composition); (3) the blue tile mark. Cobalt is never used for "Recommended", links or hover.
- **Ochre:** (1) the triangle inside the primary CTA, on ink (6.6:1); (2) the yellow tile mark, always with a 1px ink outline; (3) the focus ring (2px ochre outline with a 1px ink edge, Canon s4). Ochre is never text on any background in the shell, and never a fill on paper without a 1px ink outline (Canon s4: ochre on paper 2.2:1, ochre on paper-deep 1.9:1).

Links: ink, underlined 1px, `text-underline-offset: 3px` **(contract default)**; hover thickens the underline to 2px; visited links do not change colour.

Contrast pairs the shell uses (all measured in Canon s4; body text 4.5:1 or better, large text and UI 3:1 or better):

| Pair | Ratio | Used for |
|------|-------|----------|
| ink on paper | 14.5 | all primary text |
| ink-soft on paper | 7.0 | secondary text, captions, legends |
| ink-soft on paper-deep | 6.0 | captions inside panels |
| paper-light on ink | 15.7 | CTA label |
| ochre on ink | 6.6 | CTA triangle |
| rust on paper | 5.2 | rust marks; never needed as text |
| cobalt on paper | 6.2 | cobalt bar and circle |
| success on paper | 5.8 | confirmation line |
| error on paper | 6.3 | error text and borders |

Forbidden pairs (fail Canon s4): ochre on paper, ochre on paper-deep (without ink outline), cobalt on ink, rust on ink. The CTA consequence line on ink is `color-mix(in srgb, var(--paper) 75%, transparent)` exactly as `globals.css` line 248, and must measure 4.5:1 or better against ink in the CANON369 check.

#### Gap closure 2026-10-04: Ask Larry about this (SHELL369-13)
Gap 1, the browser half (369-VERIFICATION.md): nothing in the shell asked Larry for a proposal, so a person could not start the Approve flow from the shipped shell. The Evidence reader now carries one control, `AskLarry` (`ui/shell/client/views/evidence/AskLarry.tsx`). It follows the ruled room-proposal flow (369-ADAPTER-RULING.md): the shell shows one reference line, the person pastes it to Larry in their own Claude Code, Larry files a proposed claim in the room, and the control reads it back and opens the decision. No model runs in the shell (SEED-067, D-14) and the control never approves anything: a click on its one action calls `askClaude` only, and only a person's click in the Gate view answers a decision (D-15). No new shell action is registered.

- **Placement:** in the reader, under the provenance block and above the document. A phone sees it in the same place (the reader replaces the list).
- **Anatomy, top to bottom:** H3 "Ask Larry about this"; a lead line; a labelled single-line field "Your question" (default text, at most 1000 characters); the label "Line to paste" over the reference line in a read-only mono 12 block (paper field, 1 px ink rule, radius 0, selectable); the TextAction "Copy the line"; the view's one primary action (ochre triangle, two-line label and consequence); an InlineError (What, Why, Fix) only when a check came back empty or failed. The block sits on a paper-deep field with a 2 px ink rule on top, radius 0, v3 tokens only, no inline style, no ochre text on paper. The Evidence view keeps one H1, one primary action and one triangle (C8).
- **Copy (verbatim, `ASK_LARRY` in `client/copy.ts`):**
  - Lead: "Larry answers in Claude Code. Copy this line, paste it to him there, and he files his answer in this room as a proposal."
  - Question label "Your question"; default text "Does this have enough evidence to confirm it?"; line label "Line to paste".
  - Copy action "Copy the line"; announced after copying "Line copied."; when the clipboard refuses "Select the line above and copy it."
  - Primary action label "Check for Larry's proposal", consequence "Opens the decision when Larry has filed one. Nothing is approved until you choose."; while checking "Checking the room..."
  - No proposal yet: What "Larry has not filed a proposal about this yet." Why "The room has no proposed claim that names this item." Fix "Paste the line into Claude Code, wait for Larry to file it, then check again."
  - Arrived (once per copy, through the one LiveRegion): "Something new arrived in this room. Check for Larry's proposal."
  - No room open: What "No room is open in this browser." Why "A proposal is read from the open room." Fix "Open the room, then check again."
  - Room not readable (room_unavailable, proposal_invalid, proposal_failed, mcp_unavailable, a failed request): What "The room could not be read just now." Why "MindrianOS did not answer this check." Fix "Nothing changed. Check again in a moment."
- **States:** idle (button ready); checking (the triangle becomes the progress line, the label reads "Checking the room...", clicks are ignored); none (the no-proposal InlineError, button ready again, no gate opened, nothing guessed); arrived (a live announcement only; the person still presses the button, a click starts every gate, D-15); no-room and unreadable (their InlineError, button ready again); opened (the page goes to /gate/<id>, where the decision shows "Proposal from Claude Code. Only a person can approve it.").
- **Arrived rule:** after the person presses "Copy the line" the control remembers the read copy's change number; when the number rises, the arrived sentence is announced once for that copy. It never opens a gate by itself.
- **The reference line** is `copyReference(nodeId, question)` from `ui/shared/src/copy-reference.ts`: the opaque local node id and the question (300 characters at most in the line), never a nonce or a cookie. It lives in its own module because the proposal schema pulls in zod, which probes for eval at load and makes the page's CSP report a violation.

- H1 "Decisions". Three groups, in this order, each an H2: "Waiting for you" (open gates), "Proposed" (claims with status proposed or needs evidence), "Settled" (confirmed, validated, rejected, superseded, invalidated, stale).
- Settled rows carry human attribution in words: "Confirmed by you, 2 Oct 2026" (the `confirmed_by` field) and the verdict.
- Selecting a "Waiting for you" row opens the Gate view. Selecting any other row opens it in a reader region (desktop cols 6-12).

### Gate view (one decision per view, D-11)
- Desktop: `GateCard` in cols 1-7; the evidence region in cols 8-12 lists the gate's `evidence_node_ids`, each openable inline. Evidence is reachable, never hidden behind a separate page (D-11).
- Phone: `GateCard` first; directly under the subject block a disclosure "Evidence (3)" (native `<details>`, open by default when there are 3 items or fewer, **contract default**), then the options, then the actions.
- If other gates wait, the eyebrow says "1 more waiting" in text. No list of other gates appears in this view.

### Deliverables view
- H1 "Deliverables". Ruled list of deliverable artifacts with the white tile and the written status "Delivered", title, filed date; selecting opens it in `DocumentDisplay`. Display only in v1 (D-08, D-13). No export or publish control unless a plan explicitly includes `publishDeliverable`.

### Graph tab (secondary, D-12)
- Text-only in v1: the selected item's relations as a ruled list (relation type in mono 12, target title, target status). One caption line in ink-soft: "Relations shown here are only as complete as the room's typed links." No canvas, no node diagram (first-class graph view deferred, SEED-026).

### Rooms (context selector, D-10)
- Opening the selector shows a listbox: each row is the room name (Body 16/700), its purpose (Body 16/400, ink-soft) and its child-room path (mono 12). The bound room carries the written status "Open now".

If a gate is open on the current session, the room-switch confirmation fires first (see Copywriting, destructive confirmations), because a gate is recorded against the room it was minted in and a switch makes it unanswerable (RESEARCH Pattern 10 `room_switched`, Pitfall 11).

### Status surface (secondary, D-10)
- A right-side panel (desktop: 400px wide **contract default**, 2px ink left rule, `--paper-deep` background; phone: full screen), opened by the "Status" control in the header; closes with Esc and a "Close status" text button. Not a modal: the page stays readable.

- One secondary action: "Rebuild the browser copy" with a 12px helper line "Deletes the copy in this browser and reads it again from the room. The room is not touched." No confirmation (the projection is disposable, deliverable 4).
- When anything fails, the failing row shows its `InlineError` here AND a one-line banner appears at the top of the view body (see Error states). Diagnostics stay visible when something fails (review: "must remain visible when something fails").

### Parts
1. **Eyebrow:** black TileMark (the decision-gate square) with the written status "WAITING FOR YOU", then "DECISION / {room name}". Right-aligned "N more waiting" when other gates are open.
2. **H1:** `card.header` at Display size. Focus moves here (tabindex -1) when the view opens, so a screen reader hears the question first.
3. **Subject block:** the subject's text, its TileMark and written status, provenance (source file, filed date) in mono 12.
4. **Provenance line (adapter proposals only):** "Proposal from Claude Code. Only a person can approve it." This is the UI form of Canon Part 9 and D-15 ("Claude can operate MindrianOS. Claude does not become MindrianOS.").
5. **Notice band:** when `card.notice` exists, render it verbatim in a paper-deep band, 2px ink left rule, Body 16 ink, above the options (Phase 365 D-05: the why-line shows before the click).
6. **Answer box:** `<fieldset>` with 2px ink border, `<legend>` "Your answer" (multi-select: "Your answer (choose one or more)").
   - Options ordered by `rank` ascending; rank shown as a two-digit mono prefix ("01").
   - Each row: custom square radio (single) or checkbox (multi) built on the native input with `appearance: none`, 20px square, 2px ink border, radius 0; checked = a 10px ink square inside (website `.step-done input` precedent, `globals.css` line 678). Label Body 16/700; description Body 16/400 ink-soft on the next line; preview, when present, as a "Preview" disclosure that expands below the row.
   - The whole row is the click target (min 56px). Hover or focus: the paper-deep plane expands left to right behind the row in 200ms (Canon s11 card hover). Selected: the plane stays, plus a 2px ink left rule.
   - **Recommended:** the option whose id equals `recommended_id` (or the single `options[].recommended` before Phase 289) carries the tag "RECOMMENDED" (mono 12, uppercase, ink) and is **checked when the view renders**. At most one recommended option (SKILL.md Shape F invariant). The tag is ink, not cobalt: cobalt means "current", and a recommendation is not the current state. (Spike 007 used cobalt; this contract changes it.)
   - **No recommendation** (local-only mode, SKILL.md: "In Mode B (Local Only), no option is marked"): nothing is preselected; the primary CTA is disabled and its consequence line reads "Choose an answer first."
   - The web button renders exactly the options the contract carries. It adds no free-text slot of its own (the `gate_answer` schema has no free-text field). See Open design questions.
7. **Actions (verdicts approve / reject / defer, `gate_answer` schema `z.enum(['approve','reject','defer'])`):**
   - Primary ActionButton (the view's one triangle): label "Approve: {selected option label}", or `card.approve_label` when the server supplies one. Multi-select with several chosen: "Approve {n} answers".
   - Secondary ActionButton: "Reject".
   - TextAction: "Decide later" (defer).
   - One helper line under the group (Label 12 DM Sans, ink-soft): "Reject records your no. Decide later records that you deferred. Nothing else is saved." (Source: `lib/mcp/tools/gate.cjs` around line 536, reject and defer write nothing beyond the answer.)
8. **Keyboard:** Tab reaches the option group, then the actions. Arrow keys move within the native radio group; Space toggles a checkbox. **Enter inside the option group does not submit**; only activating the Approve, Reject or Decide later control answers the gate. This prevents an accidental approval from the keyboard. Esc does nothing in the gate view (it is a page, not a dialog).
9. **Human-only:** the shell's approve request carries the browser session and the single-use render nonce issued with this gate (RESEARCH Pattern 9). Nothing about this is shown to the person; the only visible trace is the provenance line in part 4.

## Egress, Privacy and Offline (Canon Part 8, D-01, RESEARCH Security)
- The browser contacts only `127.0.0.1` (the shell server). No other host, including `localhost` spelled as a name, Google Fonts, `rxdb.info`, analytics or any CDN.
- No third-party iframes. RxDB dev-mode is never imported (it injects an iframe from `rxdb.info`, RESEARCH Pattern 7). Agent-native telemetry off (`DO_NOT_TRACK=1`).
- Content Security Policy served by the shell: `default-src 'self'; connect-src 'self'; font-src 'self'; img-src 'self' data:; style-src 'self'; frame-src 'none'; object-src 'none'` (**contract default**, tighten only). Implementability check owned by the chassis bake-off: `DocumentDisplay` must render under `style-src 'self'`; if its bundled primitives emit inline `style` attributes, the shell moves to a nonce or hash policy, never `'unsafe-inline'` without a navigator ruling.
- Every asset (fonts, scripts, styles) ships in the release-built bundle (D-07: release-built UI assets, never a build on the user's machine).
- No chassis chrome survives: any toast, banner or error surface the chassis brings (spike 007's "Configuration error" toast) is removed or replaced by this contract's LiveRegion and InlineError.

Each has a recommended default that this contract already uses; the executor builds the default unless the navigator rules otherwise.

1. **Reject reason.** Shape F.0 says Reject captures a reason as a `REJECTED_BECAUSE` edge, but the `gate_answer` schema carries only `{gate_id, chosen, verdict}`. Default: no reason field in the web button in v1; Reject records the verdict only.
