Measure first, then choose, then time at the chosen numbers. In `tests/test-369-change-log-compaction.cjs` (house harness), a growth measurement arm builds a fixture room with 200 artifact-indexed nodes, then records: log rows produced by 2,000 insertNode writes; log rows produced by one `rebuildGraph`; total rows after 10 rebuilds. From those, compute `required_rows = rows_per_rebuild * 20 + (rows_per_2000_writes / 2000) * 10000` (the retention promise: a room survives at least 20 full rebuilds plus 10,000 ordinary writes before its first compaction).

Then, in `lib/core/navigation/room-change-log.cjs`, add `RETENTION` (frozen `{ maxRows, keepRows }`): start from the contract defaults `maxRows: 100000`, `keepRows: 50000` (a 2:1 ratio so one compaction halves the log and the next is far away); if `required_rows` exceeds 100,000, set maxRows to required_rows rounded up to the next 10,000 and keepRows to half of maxRows; state the derivation in a comment with the measured numbers. Then time the shipped ratio: a timing arm synthesizes a log of `RETENTION.maxRows` rows by repeated writes and times `compactChangeLog(db, { keepRows: RETENTION.keepRows })` (100,000 to 50,000 at the defaults). Write all numbers to `tests/fixtures/369/retention-measurement.json` with keys `rows_per_2000_writes`, `rows_per_rebuild`, `rows_after_10_rebuilds`, `required_rows`, `retention_max_rows`, `retention_keep_rows`, `compaction_ms_at_retention`, `node_count`, `measured_at`, `node` (counts and milliseconds only; SEED-074).

In the same module add `compactChangeLog(db, { keepRows })` (the timing arm above calls it, so write it before running that arm): owns idiom; cutoff = latest_seq - keepRows + 1; when cutoff > current floor, delete log rows with change_seq below the cutoff and set `change_log_floor` to the cutoff (INSERT OR REPLACE in identity); returns `{ removed, floor }`; never deletes rows at or above the cutoff; a no-op when there is nothing to remove. In `installChangeLog`, after the install, read the retained row count (latest_seq - floor) and call compactChangeLog only when it exceeds `RETENTION.maxRows`. Do not coalesce: snapshot mode reads current nodes and edges, not the log, so a client behind the floor needs a snapshot either way (comment states this).

Compaction arms in the test: (a) a log of keepRows + 1,000 rows compacts by exactly 1,000 and the floor equals the new oldest seq; (b) rows at or above the cutoff are byte-identical before and after; (c) a write after compaction gets a seq above every earlier seq; (d) installChangeLog does not compact below maxRows and does compact above it; (e) the measured `compaction_ms_at_retention` (the shipped maxRows to keepRows ratio) is printed, and the arm fails if it exceeds 2000 ms (spike 003's PreToolUse hook budget, because compaction runs inside installChangeLog on a write-door open a hook can trigger), in which case the SUMMARY must name a smaller batch; (f) the retention promise holds against the recorded JSON: `rows_per_rebuild * 20 + (rows_per_2000_writes / 2000) * 10000 <= RETENTION.maxRows`, and `retention_max_rows` and `retention_keep_rows` in the JSON equal the shipped `RETENTION` values.
