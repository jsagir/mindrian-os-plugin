<objective>
Close the undeclared-key smuggling gap (D-09). The Theo consult surfaced it; it is now MEASURED
present in this repo, not inferred.

MEASURED THIS SESSION against this repo's actual installed pins (`@modelcontextprotocol/sdk` 1.29.0,
`zod` 3.25.76, both matching the `package.json` carets):

  z.object({question: z.string()}).safeParse({question:'x', roomSecret:'LEAK'})
    -> success: true, data: {"question":"x"}          the extra key is silently dropped
  z.strictObject({question: z.string()}).safeParse({question:'x', roomSecret:'LEAK'})
    -> success: false, issue: unrecognized_keys: roomSecret

That resolves 257-RESEARCH.md assumption A3, which was explicitly gated on measuring against this
repo's pins rather than Theo's (Theo measured on SDK 1.30.0 with zod 4.4.3, a different zod major).
The gap is the same one Theo's GUARD-01 docblock records: a call carrying
`{framework:'x', roomSecret:'LEAK'}` is ACCEPTED, the handler receives only the declared field, and
nothing logs, rejects, or traces the extra one. A Part 8 violation that leaves no trace anywhere.

MEASURED MECHANISM, and this is the part that would otherwise cost the executor a dead end. The
obvious fix does not work on the pinned SDK. `server.tool(name, description, schema, cb)` detects
its schema argument with `isZodRawShapeCompat`, which returns FALSE for a ZodObject instance because
a ZodObject is a schema, not a raw shape. Passing `z.strictObject({...})` positionally therefore
falls into the annotations branch and throws:

  Tool t1 expected a Zod schema or ToolAnnotations, but received an unrecognized object

The form that works is `server.registerTool(name, {description, inputSchema}, cb)`, whose
`inputSchema` goes through `getZodSchemaObject`, which returns a ZodObject unchanged. Verified live:
positional-with-strictObject THROWS, `registerTool` with a strictObject inputSchema is ACCEPTED, and
`registerTool` with a raw shape is also accepted (so the migration is uniform across all six tools).

This plan runs AFTER Plan 07 deliberately. The invariant test is the safety net that proves a
registration-API migration did not change what the wire does.

Purpose: close a leak class the content classifier structurally cannot see, because it never
inspects keys the schema did not declare.
Output: six strict registrations and a wire-level proof that an injected key is rejected rather than
dropped.
</objective>
