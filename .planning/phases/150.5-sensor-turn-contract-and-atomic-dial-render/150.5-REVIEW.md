## Warnings

### WR-01: Freshness gate accepts future mtimes forever

**File:** `lib/core/insight-sensors.cjs:126`
**Issue:** `isFreshFile` computes `(Date.now() - st.mtimeMs) <= SIGNAL_FRESHNESS_MS`.
For any file whose mtime is in the FUTURE the difference is negative, so the
predicate is true until the wall clock catches up to mtime + 30 minutes.
Empirically proven on this checkout: a `last-cascade.json` backdated-forward
2 days derives `['artifact_filed']`. Future mtimes are not exotic on this
project's own dogfood platform (WSL2 with Windows-mounted drives is notorious
for mtime skew) and arise from archive extraction, backup restores, and clock
drift. Consequence: a single skewed side-channel re-fires the engine arm on
every turn of every session for days, which is exactly the stale-refire
failure the constant's own doc comment (lines 109-114) says it must prevent.
The firability suite's stale arms only backdate into the past, so this edge is
untested.
**Fix:**
```js
function isFreshFile(filePath) {
  try {
    const st = fs.statSync(filePath);
    const age = Date.now() - st.mtimeMs;
    return age >= 0 && age <= SIGNAL_FRESHNESS_MS;
  } catch (_e) {
    return false;
  }
}
```
Plus one honest-negative arm in test-150-5-sensor-firability.cjs that
forward-dates the marker beyond the window.

## Info

### IN-01: No consume-once marker inside the freshness window

**File:** `lib/core/insight-sensors.cjs:151-188`
**Issue:** deriveTurnSignals re-derives `artifact_filed`/`first_material` on
EVERY dispatch while the side-channel is fresh. One filing therefore fires the
engine arm and renders the dial on every turn for up to 30 minutes, with no
consumed flag and no per-session dedupe at this seam. The phase docs chose the
mtime gate deliberately and the suite asserts only the stale negative, so this
is design-accepted, but the repeat-fire behavior is unasserted and undocumented
at the seam. **Fix:** either document the intentional repeat-fire in the
deriveTurnSignals doc block, or add a consumed-at marker (e.g. compare mtime
against a `.mindrian/last-sensor-fire.json` watermark) in a follow-up phase.

### IN-02: Render-before-persist widens the trace-loss window

**File:** `scripts/intent-classifier.cjs:1735-1741`
**Issue:** Before this phase, persistDecisionTrace ran before the render, so a
throw anywhere in renderEngineDecisionWithDial lost only the stdout block.
After the reorder, the only code OUTSIDE the function's internal try is
`formatEngineDecisionBlock(decision, routing, offerLine)` and the source check;
a throw there now propagates to the promise `.catch(function () { return null; })`
and the fully-composed traceEntry is silently never persisted. Low likelihood
(formatEngineDecisionBlock is defensive and its inputs are engine-shaped), but
the reorder trades a small new loss window for the dial_render_note merge.
**Fix:** wrap the render call site itself:
```js
let block = '';
try {
  block = renderEngineDecisionWithDial(out.decision, routing, offerLine, {...});
} catch (_e) { block = ''; }
persistDecisionTrace(roomDir, sessionId, traceEntry);
```

### IN-03: Empty-string text wins the alias chain

**File:** `lib/core/insight-sensors.cjs:213-217`
**Issue:** `if (typeof base.text === 'string') text = base.text;` accepts an
empty string and never falls through to a populated `userText`. The production
builder never sets `text` (the drift fence enforces this), so the path is dead
today, but a future caller passing `{ text: '', userText: '...' }` would starve
the text-pattern sensors silently. **Fix:** prefer the first NON-EMPTY string:
`if (typeof base.text === 'string' && base.text) ...` (mirrors the sensors' own
`turnText` falsy handling).

### IN-04: Marker-absent path drops text without a fault note

**File:** `scripts/intent-classifier.cjs:916-920`
**Issue:** When `rendered.text` is non-empty but `askuserquestion_marker` is
not a non-empty string, control falls through to `return base`: the dial text
is discarded with no exception and therefore no dial_render_note. This is the
correct atomicity behavior (no card, no picture) but it is a SILENT discard,
which is the exact Phase 140 D-03 class this plan closed for the throw path.
Unreachable today (appendAskUserQuestionTrailer unconditionally sets a
non-empty marker on a truthy envelope). **Fix:** in the `else` of the marker
check, invoke `ctx.onRenderNote({ event: 'dial_render_fault', error_name: 'MarkerMissing' })`
so the non-throw discard is also classified.
