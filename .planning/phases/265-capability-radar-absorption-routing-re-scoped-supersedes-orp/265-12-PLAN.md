<objective>
Turn the frozen three-name allowlist into a reviewed registry, because Phase 265's second pass has
navigator-settled decisions to build five more subagent fan-outs and the current tripwire would
make every one of them look like a silent privilege widening.

Plan 265-03 (wave 1) grants `allowed-tools: Task` to exactly `act`, `persona` and `grade`, each
with a written reason, and pins the set with a hardcoded three-name equality in
`tests/test-265-swarm-task-grant.cjs`. That was the right control for a phase whose only fan-out
work was those three commands. RADAR-09's stated purpose is that "a fourth command cannot acquire
the grant SILENTLY". A reviewed, documented, tested addition is not silent; a hardcoded literal
cannot tell the difference between the two.

Two findings this plan also closes, both from reading the actual frontmatter rather than the
research summary:

- **`commands/deep-grade.md` ALREADY holds a dispatch grant and the 265-03 tripwire cannot see
  it.** Its `allowed-tools` block carries `Agent`, not `Task`. The set-equality arm greps for
  `Task` only, so the repo has four commands with dispatch privilege and a control that reports
  three. That is a false-coverage signal inside the exact control meant to prevent one.
- **The two spellings have never been reconciled.** `deep-grade` says `Agent`; 265-03 adds `Task`.
  The registry records the token each command actually declares rather than pretending one exists.

Purpose: the navigator settled that mos-reason, scout, deep-grade, vault, find-analogies and
file-meeting get subagent fan-outs. They need reviewed rows BEFORE they ship dispatch instructions,
or five plans each fight the same tripwire and one of them eventually weakens it.
Output: a registry, a registry-driven tripwire covering both tokens, and a one-page contract.

**This plan SUPERSEDES the frozen-three literal in RADAR-09, not its intent.** The
anti-silent-widening property is preserved and strengthened, because it now covers a token it used
to miss. Record the supersession explicitly in the SUMMARY and in `.planning/REQUIREMENTS.md`
alongside RADAR-12, which was minted at planning time along with the rest of the RADAR-12..31 range.
</objective>
