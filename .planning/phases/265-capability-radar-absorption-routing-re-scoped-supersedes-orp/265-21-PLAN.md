<objective>
Two fan-outs that are real but conditional, planned together because they share the same shape: a
hard sequential gate up front, a bounded parallel middle, and a consolidation whose reconciliation
step is the whole point.

**VAULT IMPORT REVIEW.** The export path is a single orchestrator invocation with nothing to fan.
The import path has exactly one LLM-shaped loop, in Step 3's interactive review gate: it opens
`room/imports/{id}/02-classify/output/classifications.md` and "for each row, evaluates the
classifier's guess against the file content and the venture context, and edits section or decision
cells with the Edit tool when a better assignment is warranted". Each row is one source file and
judging it requires reading that file. Rows are independent in the sense that file A's correct
section does not depend on file B's.

It scales with the source vault, and that is the whole argument. The command's stated purpose is
converting "any Obsidian vault or folder of Markdown files" into a room. A 20-note vault is trivial
in one context. A 300-note vault is not: verifying 300 classifications by reading 300 file bodies
is exactly the context blowup forking solves, and a single agent will start rubber-stamping the
classifier's guesses somewhere in the middle rather than admit it ran out of room. BELOW the
threshold the review must stay a single pass, because cross-row consistency (two similar notes
landing in the same section) is something one context gives you for free and independent agents
destroy.

**FIND-ANALOGIES --external.** Only ONE of four modes is a loop. Default Tier 0 generates 3 to 5
analogies from training knowledge as ONE comparative reasoning act ("prioritize FAR and
CROSS-DOMAIN analogies" requires seeing the candidate set together). `--brain` is two cheap
queries. `--external` is the loop: the composer emits N audited query strings, step 4 fetches each,
and per result extracts a structural mapping onto the venture, a distance classification, and, when
step 4.5 runs, a full 7-field SAPPhIRE encoding.

This is the smallest speedup and the highest dedup risk of the set, and it is scoped narrowly for
exactly that reason. Query families are deliberately overlapping angles on the SAME abstract
function, so the same source mechanism legitimately surfaces from two or three different queries. A
biomimicry query, a patent query and an academic query all returning the same well-known mechanism
is the EXPECTED case, not the edge case. Dedup on MECHANISM IDENTITY, not on URL: the same
mechanism arriving from three URLs is one candidate, and counting it three times corrupts the
ranking by inflating a popular mechanism's presence.

The constraint that could sink a careless implementation: the file states "The composer is the ONLY
source of outbound query strings. Never hand-compose a query, and never send one it did not
return", and the Tavily fallback rule says fall back to WebSearch "with the SAME
navigator-approved audited strings - never re-compose". A subagent handed a topic and told to
"search for analogies" would silently reinvent query composition and blow the Canon Part 8 egress
fence.

Purpose: both are genuine per-item work; both need a guard that is more interesting than the
fan-out itself.
Output: two threshold-and-dedup-gated fan-outs whose reconciliation steps are specified, not implied.
</objective>
