<objective>
`/mos:scout` has exactly ONE fan-out candidate among its six steps, and the file is unusually clear
about which one.

Step 4b is literally: "For each tracked competitor (max 5): 1. Search for recent news ... 2.
Summarize key findings in 2-3 bullet points 3. Flag any finding that CONTRADICTS an assumption in
the room: check `room/competitive-analysis/*.md` for existing claims about this competitor ... flag
as `CONTRADICTION:[competitor]:[claim]:[new finding]`". That is fetch plus synthesis plus an
adversarial cross-check, per item, and it is the only step in scout with real latency; the other
five are local scripts (`sentinel-snapshot`, `sentinel-health-check`, `sentinel-deadline-monitor`,
`compute-hsi.py`, `detect-reverse-salients.py`, `hsi-to-graph.cjs`,
`scout-telemetry-aggregator.cjs`).

Steps 1, 2, 3, 5 and 5b are NOT candidates and must stay sequential. Step 1 carries a real
dependency the file states outright ("Always run first - this ensures a baseline exists for health
checks") and Step 2 compares STATE.md against the snapshot Step 1 just created. Parallelizing them
would break the health check. This is a HYBRID within one command, not a conversion.

Two things this fan-out must get right, and one of them is not theoretical:

- **DEDUP IS REQUIRED AND THE RISK IS THE NORMAL CASE.** Two tracked competitors are frequently
  parties to the SAME event: an acquisition, a joint venture, a shared funding round, one
  competitor acquiring another. Five agents that never see each other's output will each report it
  as their own finding, and the naive `contradictions_found` count double-counts it.
- **THE HONEST-DEGRADE BEHAVIOR MUST SURVIVE.** If no competitors are tracked, Step 4a already
  refuses with a named next step and no agent should be dispatched at all. A failed search in one
  agent must return a TYPED failure for that competitor, never silently shrink
  `competitors_scanned`. This repo has a tracked bug class for exactly that failure mode.

The fix lands in the shared module. Scout's competitor loop is duplicated almost verbatim in
`commands/scheduled-tasks.md` Task 3, and both call `lib/core/scheduled-scanner.cjs`
(`buildCompetitorQueries`, `fileCompetitorResults`). The dedup and consolidation logic goes there
so both surfaces inherit it. Do NOT implement a second copy inside `scout.md`.

The scheduled surface deliberately does NOT get the fan-out. Canon Part 3 forbids it: cadence runs
never invoke the LLM tier unattended, and the cadence runner is Canon Part 8 zero-egress, emitting
a public-SIGNAL query plan for the surface layer rather than fetching inside the runner. The
fan-out belongs to the attended `/mos:scout` invocation only.

Purpose: smallest blast radius of the five fan-outs, N already capped at 5, and the shared-module
placement means one fix covers two surfaces.
Output: a hybrid step-4b fan-out with real dedup and typed failures.
</objective>

BEHAVIOR, all four required:

1. SAME-EVENT DEDUP ACROSS COMPETITORS. Two findings from DIFFERENT competitors are the same event
   when their `date` matches (same calendar day) AND their named-entity sets intersect on at least
   two entities, or their `source_url` is identical. Merge them into ONE entry carrying
   `cross_referenced: [competitorA, competitorB]` and attribute it to the alphabetically first

   findings: that is a different problem and the fan-out does not create it.

   co-occurrence.

   be counted ONCE. This is the specific arithmetic bug the research names: the naive
   `contradictions_found` count double-counts a shared event.
3. TYPED FAILURE PRESERVATION. Return `failed: [{competitor, error}]` for every `ok: false` entry.
   `competitors_scanned` counts SUCCEEDED competitors, and the return also carries
   `competitors_requested` and `competitors_failed` so the caller can render an honest line. A
   failed competitor must NEVER be invisible. Write that sentence into the function's JSDoc, citing
   the repo's tracked silent-skip bug class.

failed, cross_item_flags}`.
