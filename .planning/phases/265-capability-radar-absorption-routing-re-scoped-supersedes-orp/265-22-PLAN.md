<objective>
`/mos:diffusion` is the ONE genuine online-research gap among the twenty methodology commands, and
the fix is a parameter on an existing composer rather than a new surface.

WHY CHAINING DOES NOT COVER IT. Every other command in the audited set needs research on ONE
subject, known either before the command starts (chain it) or as soon as the navigator names it
(offer it mid-flow). Adoption-Capacity Theory does not have that shape. Read the command's own step
sequence: step 3 codes FI and OC for the INNOVATION (one subject, chainable), but **step 4 profiles
EACH ACTOR's capacity separately** on three axes (FI capacity from budget over GDP, OC capacity from
organizational age versus t0 plus experimental R&D plus task-focus breadth, and conceptual
capacity), and step 5 maps requirement vectors to capacity vectors per actor and assigns one of five
response paths.

The actor roster does not exist before the command runs. It is derived at step 4, after step 3's
FI/OC coding. So a pre-chained `/mos:research` cannot know the targets (at chain-compose time the
roster is empty), and a single mid-flow `requires_evidence:` offer under-serves it (one pass returns
top findings for ONE topic, while a ten-actor roster needs ten independent capacity lookups whose
results stay ATTRIBUTED to their actor to be usable in the step-5 vector mapping).

The two existing fans both fan the wrong axis. `/mos:intel-pipeline` decomposes the room's active
JTBD into research dimensions and has no input for a caller-supplied entity roster. `/mos:bono` fans
a (subdomain x hat) grid, a scrutiny-discipline fan.

THE HONEST CONSEQUENCE TODAY: ACE either runs on the navigator's unaided recall of a dozen public
facts, or the navigator leaves the command, runs `/mos:research` N times by hand, and comes back.
Both produce a low-tier capacity table feeding a QUANTITATIVE vector mapping, which is the worst
place in the methodology for soft numbers.

THE FIX IS A PARAMETERIZATION, NOT A NEW SURFACE. `lib/core/intel-pipeline.cjs`'s frozen
`PIPELINE_STAGES` are already `calibrate, decompose, plan-fan, fan, compute, synthesize, close`.
Give `decompose` an optional caller-supplied roster so each roster entry becomes one fan cell;
`plan-fan` then renders the EXISTING F.1 fan-approve gate over the roster, which is exactly the right
cost control and already ships ("10 actors x 3 axes = 30 lookups, approve?" before a byte is
fetched); `fan` runs the passes through the SAME `fetchCorpus` chokepoint, so the Canon Part 8
pre-egress audit is inherited; and `compute`, `synthesize` and `close` already land each result as a
born-proposed `EvidenceClaim` with `INFORMS` to its row behind the F.5 synthesize gate.

`/mos:diffusion` gains a `requires_evidence:` declaration and a mid-flow offer at step 4. Its
`web_scope` stays `null`, because it never reaches the web itself: `intel-pipeline`, which is
already `green`, does the reaching.

Purpose: the delta bought is ATTRIBUTION and TIMING, not volume. N attributed passes over targets
the command itself derived, behind a cost gate, with per-actor provenance the step-5 vector mapping
can consume.
Output: one optional parameter, one declaration, one offer.
</objective>
