## (a) The question

Does the intelligence cascade (`lib/core/intelligence-cascade.cjs`) fire at SEGMENT
granularity on meeting artifacts end-to-end -- i.e. does each discourse segment of a
filed meeting transcript get its own cascade pass (classify -> graph-index -> artifact-id ->
cross-relationship scan) -- or does the cascade fire only ONCE per filed FILE, treating
the whole meeting artifact as a single unit?

This is the SEED-023 precondition: Phase 150.8 v1 wants the DIKW ladder to run
Data (segments) -> Information (typed claims) per segment. If the cascade only sees
whole files, 150.8 plan 01 must add the segment-level type guard FIRST.

## (b) File:line evidence (the routing + the loop)

**1. The cascade entry points take ONE file path, not a segment list.**

- `runCascade(roomDir, { trigger, filePath, section })` -- `intelligence-cascade.cjs:450`.
  A single `filePath`; the guard at `:467` skips when no `filePath` is provided.
  The flat public return shape carries one `classification`, one `graphIndex`, one
  `gitCommit` -- per FILE, not an array of segment results.
- `queueCascade(roomDir, { trigger, filePath, section })` -- `intelligence-cascade.cjs:555`.
  Same single-`filePath` signature; it batches multiple FILES into the shared
  `_runCascadeSteps` helper, never multiple segments of one file.

**2. The shared body iterates over `artifacts` = whole files.**

- `_runCascadeSteps(roomDir, artifacts, options)` -- `intelligence-cascade.cjs:219`.
  The per-artifact loop `for (const art of artifacts)` at `:236` keys on
  `art.filePath` (`:237`). Steps 1/2/7/7b (classify-insight, graph-index, artifact-id,
  git commit) run once per `fp`, and one `entry` is pushed to `stepsResult.perFile`
  at `:294`. The unit of work is the FILE. There is no inner `for (segment of ...)` loop.
- The HSI / reverse-salient / cross-relationship steps 3-6 + 8-11 run ONCE per
  `roomDir` for the whole batch (comment at `:297`; `anyMd` gate at `:301`), i.e.
  even coarser than per-file -- per-room, never per-segment.

**3. The only `meetings/` branch is section-routing, not segmentation.**

- `detectBinarySection` -- `intelligence-cascade.cjs:185-203`. The `meetings/` check at
  `:197-199` returns the string `'meetings'` as the SECTION label for a binary asset.
  It assigns a routing bucket; it does not split a transcript into segments and does
  not trigger a per-segment cascade. (This is the line CONTEXT cited as ":196 routes
  meetings/ at file level" -- confirmed: it is file/section-level routing.)

**4. The callers pass one file per call.**

- `lib/mcp/tool-router.cjs:289` -- `await runCascade(roomDir, { trigger: 'mcp-tool', filePath, section })`: one `filePath` per write-tool call.
- `bin/mindrian-tools.cjs:558` -- `cascade.runCascade(cascadeRoomDir, {...})`: one filed artifact.
- `scripts/post-write` (Phase 95-02 envelope) writes ONE `<roomDir>/.mindrian/last-cascade.json`
  side-channel per filed file (`write_cascade_side_channel`, post-write:90), i.e. one
  cascade envelope per FILE, never one-per-segment.

**5. Meeting "intelligence" is a separate aggregate pass, not a per-segment cascade.**

- `scripts/compute-meetings-intelligence` scans `meetings/<dir>/metadata.yaml` directories
  (a per-MEETING directory walk) to emit `MEETINGS-INTELLIGENCE.md` + `action-items.md`.
  It is a room-state aggregate over meeting dirs, invoked by `compute-state` -- not a
  segment-level cascade fan-out. No `runCascade` / `queueCascade` call exists in it.
- No script under `scripts/` or module under `lib/` performs a per-segment cascade on a
  meeting file (grep for a meeting+segment+cascade fan-out returns nothing).

## (d) VERDICT

**VERDICT: FILE-LEVEL ONLY (segment granularity NOT present; Phase 150.8 plan 01 must fix the type guard first per 150.8 Section 10).**

The intelligence cascade fires once per filed FILE. It does NOT fire per discourse
SEGMENT on meeting artifacts. A meeting transcript filed as a single `.md` produces a
single file-level cascade pass and a single cascade envelope; the `meetings/` reference
at intelligence-cascade.cjs:197 is section-label routing, not segmentation. Segment-level
cascade firing on meeting artifacts does not exist end-to-end at v1.13.1-beta.15.

## Consequence for Phase 150.8 plan 01

Per 150.8-CONTEXT.md "In scope" item 6 and the SEED-023 proposal's own Section 10 rule:
**because the verdict is FILE-LEVEL ONLY, the FIRST plan of Phase 150.8 must fix the
type guard (add the segment-level firing the DIKW Data->Information rung depends on)
BEFORE anything builds the typed-claim extraction on top of it.** 150.8 cannot assume a
per-segment cascade exists; the Claimify-style 4-pass extraction (150.8 in-scope item 2)
must drive segmentation itself or wire a segment-level cascade pass first. Do not build
the knowledge_type claim layer (item 1) on the false precondition that the cascade already
fans out per segment -- it does not.
