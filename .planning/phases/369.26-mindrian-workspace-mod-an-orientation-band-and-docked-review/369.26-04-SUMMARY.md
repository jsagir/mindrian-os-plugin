## Engine facts (measured in plan 04, throwaway copy of the mod in the scratchpad, `claude plugin validate`)

These affect plans 05 to 18. The README "Engine facts" is plan 01's file, so I did not edit it; the orchestrator should fold these in.

1. **`$` does not cross an import.** `await readViewModel($)` with `readViewModel` imported from another file fails validate: "$ is followed only into a function declared in this same file, never across an import; $ is always spelled $.noun.event(...) at the call site, on is always on("<event>", hook)". A helper declared in the same file as the hook, taking `$`, is fine. `on` passed to an imported registrar that registers the hook inside its own file IS fine (proved: `registerModel(on, options)` with the `on('ui.render', ...)` call inside registrars/model.ts validates and lists the hook). So `openWorkspace($, ...)` (plan 01, `src/runtime/open-workspace.ts`) and any shared `$`-taking helper will fail validate the day a hook calls it from another file.
2. **A state read needs a source the scan can read.** `read($, sampleAtom)` where `sampleAtom` is imported from `src/state/atoms.ts` fails ("a reference whose plugin and key are string literals, or what atom, memberOf or derive made of one, written there or in a const of this file"). Working forms: a literal reference at the call site, `read($, { plugin: 'mindrian-workspace', key: 'sample' } as const)`, or an atom const declared in the same file as the read. The scan checks every module reachable by import, so a single un-readable `read($, importedAtom)` inside an imported module breaks validate for the whole plugin even if no hook calls it (this is why my first `readViewModel` could not stay in read.ts). The `update($, ref, fn)` form with a literal reference validates too (proved with a `command.run` hook). Consequence: `src/state/atoms.ts` atoms (plan 01) cannot be read or updated from other files as constants; plans must spell literal references.
3. **The state contract must be named by the manifest and be self-contained.** Once any hook reads or writes state, `claude plugin validate` fails with "the manifest's types contract must name it in interface PluginState". The fix: `"types": "./types/state.d.ts"` in `.claude-plugin/plugin.json` (the value must start with `./`) and `types/state.d.ts` must have no `import` (it currently imports `TabId`: "line 1: `import` reaches outside the file; the contract must be self-contained"), so the tab type is written inline as a string union. The mod's current manifest has no `types` field and a state.d.ts with an import, so the first plan to add a state-reading hook (plan 05 to 08) will fail validate until plan 01's two files are corrected. I did not edit them (not in my files_modified, owned by plan 01); a one-task fix is recommended before wave 3.
4. **The test engine is bare.** In `claude plugin test` the body's `$` has no `state` and no `env` (`$.state.get` / `$.env.get` are undefined, and the typings say so), and a test's own `ui.render` hook may not call `$.state.get` ("its hooks module does not call it (host rule)"). `mock.env` therefore only takes effect for a mounted plugin hook that reads the env; state can only be exercised through the plugin's own mounted hooks.
5. Positive: with a literal reference and a literal env name written in the hook, validate lists them (`env reads: MOS_WORKSPACE_SAMPLE`, `state reads: mindrian-workspace.sample`, `calls: $.env.get, $.state.get, $.state.set`).

## Decisions Made / Deviations from Plan

### Deviations

**1. [Rule 3 - Blocking] `readViewModel($)` replaced by pure `chooseViewModel`**
- **Found during:** Task 3 (acceptance: validate lists MOS_WORKSPACE_SAMPLE)
- **Issue:** the planned `readViewModel($)` in read.ts calls `read($, sampleAtom)` with imported atoms and takes `$` across a file; the engine scan rejects both, and importing read.ts anywhere would make validate fail (Engine facts 1 and 2).
- **Fix:** read.ts holds no `$`; it exports `chooseViewModel(fromAtom, fromEnv, live)` (the same selection order, pure) and `SAMPLE_ENV`. Each hook spells three reads (the exact snippet is in the read.ts header) and passes the values in. The key_link read.ts -> atoms.ts via `read($, sampleAtom)` therefore does not exist; the contract is the literal reference.
- **Files:** `src/model/read.ts`. **Commit:** `52fadb93d`.

**2. [Rule 3 - Blocking] The readViewModel test arms are covered differently**
- The plan allowed "only the env and live-atom arms if the harness does not let the atom be seeded". The bare test engine has neither `$.env` nor `$.state` (Engine fact 4), so no arm of a `$`-reading function can run in a test. All three selection arms and the invalid-name and not-a-view-model cases are tested through `chooseViewModel`; the end-to-end read is owed to the mount tests of plans 06 and 07 once a registrar hook performs the reads. Acceptance "validate lists MOS_WORKSPACE_SAMPLE" cannot hold for this plan alone (nothing reachable from register.tsx reads it yet); I proved it on a throwaway copy of the mod whose hook spells the read, and it lists the name. ENV GAP in the sense that the lone-plan acceptance cannot be shown on the repo tree; plan 06 should assert it.

**3. Fixture detail choices (within the plan's discretion)**
- `SAMPLES.missing` also sets `next.method` to not_recorded (the plan said "wide except purpose and next.step"); a framework handle for a step that is not recorded would be a guess.
- Option labels of the grant card carry "(sample)" too.
- Fixture clocks are fixed (`readAt` 1760000000000; expiry in 30-minute steps) so every sample draws identically.
