Facts measured while planning (re-read before use):
- The Brain is reached only through the guarded shim `scripts/mindrian-brain-mcp-client.cjs` (bin/mindrian-brain-mcp-client.cjs forwards to it since 369.1); the raw theo server never carries plugin-user content and the mod never addresses it. The egress guard (lib/core/part8-egress-guard.cjs `_proveKnownToolShape`) already allows two handle-only shapes that fit a guidance lookup: `framework_techniques` with exactly `{ framework }` and `framework_step` with `{ framework, step_id? }`, where `framework` must be an exact lowercase-normalized member of the framework-name canon and match `FRAMEWORK_NAME_RE = /^[A-Za-z0-9 '(),./-]{1,128}$/`. A shape outside these is "ambiguous with disclosure", not allowed.
- data/framework-names.json holds the canon as `framework_names: [...]` (stamped at release). `ViewModel.next.method` is the recorded method name for the current step; no live source records it today (369.25's reader is planned), so in real rooms the lookup button is never drawn; the `wide` sample carries a canonical name so the path can be exercised.
- The tool name the shim exposes for `framework_techniques` is read from the shim and the egress guard test fixtures; the executor greps both and uses the exact spelling.

Decisions this plan fixes (Claude's discretion; UI-SPEC pedagogy order preserved):
- Point selection: the point a help button acts on is the picked gap title (one pick), else the first drawn gap title, else, for Why this matters, the recorded step; Connect needs two picks (from the same pick rows) and shows P97 until there are two. No pick control or word is added to the deck: picks are the gap rows themselves, shown selected with `inverse` only.
- Recorded rationale: only Why this matters has one today, the recorded reason `vm.next.reason` when ok; the other four buttons have no recorded rationale in any current source, so they show P91 and offer the lookup (when a handle exists) and the hand-off (when a point exists). The text shown for a help kind therefore follows exactly: rationale if recorded, else (below it) P93 with P94 when a handle exists, else P91; P92 whenever a point exists.
- Hand-off prefill text by kind: Dig uses Q02 with the point, Connect uses Q03 with both picked titles, Another way uses Q04, Why this matters and Show me an example use Q05; always through `prefillPrompt` (fill only, toast P34 or P35).
- Lookup tool: `framework_techniques` with exactly `{ framework: <handle> }` for every kind; the result's text is shown as `Markdown` under P95, cut at 10,000 characters; any failure, refusal or non-text reply is P96. A handle that is not an exact lowercase-normalized member of the derived canon, or fails the charset and length rule, is never sent; the lookup button is then not drawn (no dead control).
- Marks: L02 (red) beside Dig, L01 (blue) beside Connect, L03 (yellow) beside Another way, drawn by `larryMark` with its word; Why and Example have none. Marks appear only on help results and cards (UI-SPEC 7.4, Part 12): they are drawn in the help area once a kind is selected, not on the idle buttons.
- Keys: g, c, a, w, x (kinds), l (lookup), t (hand-off), all unique among everything drawn in Think; `keys(ctx)` returns the full list in the order g, w, a, v (P12), c, x, l, t and the hint line takes the first four entries (g, w, a, v; the shell appends `s` after them, so `s` falls outside the four, matching UI-SPEC 8.4) while the all-keys panel lists every drawn key.
