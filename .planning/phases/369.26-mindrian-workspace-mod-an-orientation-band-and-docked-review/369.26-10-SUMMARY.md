# Phase 369.26 Plan 10: Review answer path Summary

**The mod's one room write, built and tested with no UI: a verdict derived from the recorded card, one press saving once through gate_answer under two guards, every refusal one plain sentence, and "saved" written only after the runtime says ok.**

## What was built

- **verdicts.ts**: `verdictFor` (card.approving first, then a closed table of the repo's own option ids, never a guess; a conflicting record is null; an approve on a card that resumes work is null) and `consequenceId` (D11 defer, D10 general approve or reject, D12 other kinds, null for an option the mod will not save). `OPTION_VERDICTS` has eight rows, each commented with the producer file and line it was read from (chain.cjs, sensors.cjs, ambient.cjs, never-do-gate.cjs, tool-router.cjs, grants.cjs, research.cjs, plan.cjs, planner.cjs, quick.cjs, canon-release.cjs). Rows the code does not settle (revise, edit, run, release, review_filing, file_selected, file_nothing, choose_items, name_limiter, run_deep, extend_run, stop_run) are left out; an id like that is savable only when the card lists it in `approving`.
- **refusals.ts**: unknown_gate E01, gate_expired E02, stale_subject E03, session_mismatch E04, chosen_not_in_card_options E05, 'unreachable' E06, everything else E07; `isForeign` for session_mismatch and unknown_gate. Returns copy ids only.
- **state.ts**: starting values and pure reducers for `reviewPhase`, `reviewLast`, `reviewMirrors`, `reviewDismissed`, `reviewForeign`, `reviewOpen`. No atom, no `$` (the engine would refuse an imported atom).
- **gate-client.ts**: `answerGate` (args exactly `gate_id`, `chosen`, `verdict`), `mirrorGate` (`mirror_of` plus the recorded option ids in order, nothing else), `checkGate` (gate_list for one gate: current, changed, failed), `listedGateIds`. All on `MINDRIAN_SERVER`; none throw.
- **answer-machine.ts**: `pressChoice`, `decideLater`, `runCheck`, `mirrorHere` over a `ReviewIo`.
- **tests/fixtures/review-io-recipe.ts**: how the hook file builds a `ReviewIo` (six atoms spelled in the file, a `makeReviewIo($)` of closures). It is real source under `tsc -p`, and `tests/test-369.26-review-answer.cjs` copies it into a scratch copy of the mod, wires it, and runs the real `claude plugin validate` (it lists the review keys as read and written).

## Deviations from Plan

### Auto-fixed Issues (ENGINE-RULES and the caller's binding facts win over the plan text)

**1. [Rule 3 - Blocking] The machine takes a `ReviewIo`, not `$`; the atoms are keys, not exports**
- **Issue:** `pressChoice($, ...)`, `refreshViewModel($)`, and `phaseAtom` and friends imported by plan 14 all fail the engine scan (`$` across an import, imported atom, `$` in an object).
- **Fix:** `ReviewIo` is an object of closures (mcpCall, claimSaving, setPhase, getLedgerId, setLedgerId, setLast, dismiss, setForeign, toast, refresh, now). The hook file spells each atom and each `update`; `state.ts` exports data and the reducers those closures pass to `update`. Proved with the real engine on a scratch copy (recipe arm).
- **Commits:** `3f1025f74`, `6922ae286`.

**2. [Rule 3 - Blocking] No `types/review-state.d.ts`; six keys added to `types/state.d.ts`**
- The manifest names exactly one types file (measured by plan 07). Added `reviewPhase`, `reviewLast`, `reviewMirrors`, `reviewDismissed`, `reviewForeign`, `reviewOpen`, inline, no import. This forced one edit outside `files_modified`: `tests/contract.test.ts` (plan 01A's compile-time equality over the whole key set), extended with the six keys. Starting values live in `src/pane/review/state.ts` (`reviewInitial()`), not `src/state/atoms.ts`, so plan 01's file is untouched.
- **Where this meets the amended pane-body recipe:** ENGINE-RULES (committed meanwhile by the sibling amendment) prefers a generic `body` state key with `act.patch(tab, partial)`, and says plan 10's review state becomes a `body.review` slice. `body` does not exist yet (plan 11 builds it). My keys are the atomic path available now: the in-flight claim needs a read-modify-write with a function (`update`), which a `patch(tab, partial)` merge cannot do. Plan 14 can take either (see "Notes for later plans").

**3. [Rule 2 - Missing critical] An in-process in-flight guard added next to the state claim**
- The plan's guard is the state claim only. If a later store write is a plain merge (the kit's `act.patch`), two presses could both "win". Added a module-level in-flight set checked before any await, so one press saves once on any store. It also covers a mirrored press. Mutation-tested (each guard removed in turn).

**4. [Rule 1 - Spec conflict] `mirror_source_answered` is D27, not E07**
- Plan: every unmapped code is E07 ("That did not work ... Try again"). For a mirror whose source was answered meanwhile that sentence misleads (trying again gives the same answer). `mirrorHere` special-cases this one code to the existing D27 ("answered somewhere else. Nothing changed here.") and re-reads the model. No new copy invented.

**5. Interpretations inside the plan's wording**
- `consequenceId` returns null when the option is not savable (nothing is saved, so no consequence line); the plan only listed the three arms.
- A Decide-later press sets the card aside through `dismiss` and shows D14; it writes no phase (plan 14 draws D14 from the dismissed list).
- A replayed (D26) or answered-elsewhere (D27) answer does not set `reviewLast` (this press saved nothing) but does re-read the model. A D13 ("stays open") answer also does not set `reviewLast`.
- After a defer, a failed `gate_list` re-read is D24, not D13: the runtime did answer ok, so "saved" is true and "stays open" cannot be shown unconfirmed.
- Multi-answer cards and an option that is not on the card are `not_savable`, even though the runtime would also refuse.
- Mirror labels: the schema requires a label, so the recorded option id stands in for it (ids only leave the machine; the runtime draws the card from the room's record).

## Open questions for the navigator

- **OQ-14 (wait-type copy):** a `defer` or `reject` answer ends the gate in the runtime (it leaves `readOpenRaisedGates`), so UI-SPEC D13 "This decision stays open" is almost never true after a wait-type choice. The machine re-reads `gate_list` and says D13 only when the card is still listed, else D24 "Saved to your data room: {label}". Real runs will show D24 for Defer and Not now. D11 ("Pressing {key} leaves this open. Nothing is decided yet.") is the consequence line shown BEFORE that press and has the same problem; the deck has no sentence for "your wait was saved and the card goes away".
- **OQ-15 (approve on a card that runs work):** `resumes` is true for ANY ledger entry with a resume function, not only chain halts: research gates (approve_run, approve_standing), canon release, ambient and never-do cards all resume server-side on approve. The pane saves none of those approvals (`verdictFor` is null for an approve on `resumes`), because D10 to D12 say "saves your decision", not "runs the step". Reject and defer on those cards are savable. The navigator can rule that D12 may say it runs the work, or that these stay in the conversation (D30's wording is about multi-answer cards, so plan 14 has no honest sentence for them; it must not invent one).
- **Contradiction worth a ruling:** after `stale_subject` the machine runs the check the plan defines (open, same header, same option ids gives D32 "Still current. Nothing has changed since this was drawn."). The check cannot see the subject, which is exactly what changed, so the card can read E03 and then D32. The plan fixed this (no new key, no new copy); noted, not changed.
