# Phase 369.26 Plan 16: Think help and the guarded lookup Summary

**The Think tab now has five guided help buttons, a talk-it-through hand-off and one guarded general-guidance lookup whose payload is exactly `{ framework: <canonical method name> }`, proven unable to carry room text by a static checker, the egress guard's own classifier and a real-engine probe, each with a mutation arm that fails when a room string is planted.**

## What was built

### Task 1: the guarded lookup and the Part 8 test

- **`lookup.ts` (pure, no value import).** `parseCanon(text)` reads `framework_names` into a lowercased list (any parse problem is an empty list, which accepts nothing). `inCanon(handle, canon)` and `isCanonicalHandle(handle, canonText)` accept only a string matching `/^[A-Za-z0-9 '(),./-]{1,128}$/` that equals a canon name after lowercasing (never a prefix, never a substring). `textFromReply` takes the first text block, cut at 10,000 characters; an error reply, no text or a blank text is `failed`. `lookupGuidance(act, handle)` calls `act.guidance` and maps the answer to `ok`, `failed` or `refused`; it never throws.
- **`act.guidance(handle)` in `src/registrars/pane.tsx`.** Reads `assets/framework-names.json` with `$.fs.read`, answers `{ kind: 'refused' }` with NO MCP call unless `isCanonicalHandle(handle, canonText)`, otherwise `$.mcp.call(BRAIN_SERVER, 'framework_techniques', { framework: handle })`, answering `reply` or `failed`. `GuidanceAnswer` and `Actions.guidance` are in `src/pane/types.ts`. `claude plugin validate` lists the call as `$.mcp.call (via makeAct, makeIo)`.
- **`tests/test-369.26-part8.cjs` (15 arms).** Static (3): `checkTree` over `src/` (only `registrars/pane.tsx` and `runtime/ids.ts` name the Brain server or tool; the call is the single literal `{ framework: handle }` with no spread, template or other variable, after the canon check inside the closure; the handle is read only from `next.method` in `handleOf`; the only caller of the lookup passes `handle` declared once as `const handle = plan.handle`; no `prompt.submit` in `src/`). Static mutations (5): a room field in the call args, a room variable as the framework, the canon check removed, a second Brain call in a new file, a room string handed to `runLookup` from the view, a room field read in `handleOf`: each must make `checkTree` fail. Canary (3): the egress guard module (`_proveKnownToolShape`) admits `{ framework: 'Assumption Challenging' }` (also lowercase, and under both the bare and the `mcp__plugin_mos_mindrian-brain__` tool name), refuses a second key or a `step_id`, and refuses an email, a currency amount, a person name with a degree, free text, a newline, 129 characters, an empty string and non-strings; the mod's own `isCanonicalHandle` (loaded by Node type stripping) agrees on all 414 canon names and every canary. Engine (3): a scratch copy of the mod with a probe Think body calls the real `act.guidance` under the real engine; canonical names (and the lowercase form) are the only ones that produce a call, args deep-equal `{ framework }`, every room canary and non-string is `refused` with no call, a down Brain is `failed`; mutation arms remove the canon check from the scratch closure, and add a room key to the scratch call, and the probe FAILS in both.

### Task 2: the help model and the help view

- **`help-model.ts`.** `helpFor(kind, think, vm, picks)` returns `{ rationale, point, handle, needsPicks, titles }` (rationale is the recorded `vm.next.reason` for Why this matters only; point is the most recent pick, else the first drawn gap title, with Why falling back to the recorded step; handle only from `handleOf`; Connect needs two picks). `planFor` decides what to draw in the strict order and checks the handle against the cached canon. `readHelp` / `isHelpState` narrow the `help`, `lookup` and `canon` keys of the think slice; `selectKind`, `runLookup` (loading, then ok or failed) and `loadCanon` write through `act.patch`.
- **`help-actions.tsx`.** Heading P80, the five buttons P81 to P85 with lines P86 to P90 and hotkeys g, c, a, w, x. Under the selected kind: its mark (red L02 Dig, blue L01 Connect, yellow L03 Another way, none for Why and Example; a 2-cell block then a word, the word alone in plain mode), then the recorded rationale, P97 for Connect with fewer than two picks, P91 when there is nothing recorded and no lookup, the P93 button (hotkey l) with P94 beside it only for a canonical recorded handle, P92 (hotkey t) when a point exists, and the lookup result as `Markdown` under P95 (never more than 10,000 characters) or P96 on failure. P92 uses `prefillPrompt` with Q02, Q03 (both titles), Q04 or Q05; there is no submit anywhere in `src/`.

## Deviations from Plan

### Auto-fixed Issues (ENGINE-RULES wins over plan text)

**1. [Rule 3 - Blocking] The real-pane exact-arguments arms moved from task 1 to task 3, and the closure is proved by a scratch-engine probe**
- The plan's task 1 says the exact-arguments arms "drive the real pane and press P93", but the P93 button does not exist until task 2 and is only wired into the Think body in task 3, and a test hook cannot lend the plugin's own `$` to call the closure directly (rule 11; plan 11 measured the same). Task 1 therefore proves the closure itself through `tests/test-369.26-part8.cjs` (scratch copy plus probe body under the real engine, the pattern of `tests/test-369.26-body-kit.cjs`), and the "press P93 and read the captured arguments" arms landed in task 3 on the real pane. Both are there; neither is weaker.

**2. [Rule 3 - Blocking] `Actions.guidance` is a required member, so seven existing test files gained one line**
- `Actions` gained `guidance` (as ENGINE-RULES lists in the kit table), so every test-built `Actions` literal needed it for `tsc -p`. Added `guidance: async () => ({ kind: 'refused' })` to the fake acts in `action-list`, `pane-kit`, `pane`, `review-card`, `room-tab`, `sources` and `think-core` tests (one line each, 8 lines; the spread-based fakes needed none). Not in `files_modified`.

**3. [Rule 3 - Blocking] The canon is cached in the think slice (`canon`) and read in `onOpen`**
- The plan wants the lookup button not drawn for a handle the canon does not hold ("no dead control"), but a view is pure and synchronous and cannot read the canon asset. `thinkBody.onOpen` now also runs `loadCanon(act)` (one `act.readAsset('framework-names.json')`, then `act.patch('think', { canon })`), and the view and the key list decide from that. The closure still reads and checks the canon itself before any call, so a stale cache can only cause a refusal, never a send. The plan listed `help` and `lookup` as the slice keys; `canon` is a third.

**4. [Interpretation] Marks and selection**
- Marks draw once a kind is selected (plan decision, kept). The selected kind's button is `variant="primary"` in color mode; pressing it again closes the area (the plan says nothing about deselecting; without it a person could not dismiss the area from the keyboard except by leaving the tab).

**5. [Interpretation] Several picks for a single-point kind**
- With two picks and a one-point kind (Dig, Another way, Why, Example) the point is the most recent pick, not an error.

**6. [Interpretation] Loading state**
- The deck has no "looking it up" word, so while a lookup is under way the P93 button is hidden and nothing new is drawn (no invented text). It is milliseconds on a real call.
