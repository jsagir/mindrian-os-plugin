# Phase 369.26 Plan 07: Pane shell and workspace command Summary

**A pane shell that draws its frame at every width on four surfaces (tab strip with no hotkeys, three-tier key help, details, notes), closes layer by layer on Esc, and opens from a `workspace` command with plain, sample and live switches, built to the engine's own rules instead of the plan's `$`-passing shape.**

## What was built

- **Tab strip** (UI-SPEC 6.2, 10.6): four Buttons keyed `tab:room|think|sources|review`, labels P01 to P04, no hotkey; the active one is `variant primary` on a blue block (color) or a bold inverse `> Label` (plain). Under 30 columns it is a `Select` (`tab:select`) on terminal and desktop, buttons on vscode and mobile.
- **Notes** each at most once: N04 (sample), N01 or N03 (mode), N05 (under 40 columns), P05 (working).
- **Hint line / all keys / explain / details** (UI-SPEC 8.2 to 8.5): first four tab keys as dim text, then Help (`h`, pressable), Explain (`e`, pressable, only when it fits and the all-keys panel is shut), then Esc; N06 when the pane is not focused. All-keys lists the whole list with H20 to H22. Explain shows X01 to X04. Details shows P60 to P66 from the model with M01 to M04 for missing facts plus the body's `detailsExtra`; its `s` hotkey is armed only in Room, Think and Sources.
- **Esc layering**: `closeDecision` (explain, then keys, then details, else the pane closes) behind a `ui.close` hook that answers `{ value: undefined }` (no `next`) to keep the pane open.
- **workspace command**: `workspace`, `workspace <tab>`, `workspace plain`, `workspace sample <name>`, `workspace live`. Never submits a prompt.

## Deviations from Plan

### Auto-fixed Issues (engine rules; ENGINE-RULES wins over the plan text)

**1. [Rule 3 - Blocking] renderPane($, e, deps) is a pure view + an inline hook**
- **Found during:** design, then measured in a scratch copy of the mod under `claude plugin validate`.
- **Issue:** `$` passed into an imported function is refused; so is a hook that is a factory call (`on('ui.render', m, makeHook(deps))`: "the hook is not a function literal or the name of one"); so is `$` inside an object ("$ itself is put in an object").
- **Fix:** `src/pane/pane.tsx` exports `buildPane(el, input, deps)` (pure); `src/registrars/pane.tsx` holds the hook, reads state, env, store and palette, builds closures and calls it. `deps` is a parameter because a test cannot swap a module the plugin imports (measured: the test and the plugin load separate module instances).

**2. [Rule 3 - Blocking] TabContext has no `$`; bodies get `act`**
- The plan's `TabContext.$` and `onOpen($)` cannot exist. `TabContext` carries `act: Actions` (`setTab`, `fill`, `toast`, all closures over the hook file's `$`); `onOpen` is `(act) => void | Promise<void>`. Plans 11 to 16 as written call `refreshViewModel($)`, `loadThink($)` and similar from imported body files: those will fail validate (see "Notes for later plans").
- `KeySpec.labelId` narrowed again to `Extract<CopyId, 'H...'>` (all key labels are placeholder-free H ids), so `text(labelId)` type-checks.

**3. [Rule 3 - Blocking] No `types/pane-state.d.ts`**
- The plan lists it. The manifest names exactly one contract file (measured: `"types": ["a.d.ts", "b.d.ts"]` leaves the second file's keys undeclared). I avoided a new state key altogether (next item), so no contract change was needed.

**4. [Rule 3 - Blocking] The working note is store-driven, not a `working` state key; and on `turn.start`, not `prompt.submit`**
- Pane props carry no working flag (confirmed in the declaration file). First attempt wrote a `working` state key on `turn.complete`; it broke plan 06's test "turn.complete refreshes again, and never touches the sample or any other key" (the whole plugin chain runs, so my write was caught). Final form: `turn.start` writes `$.store.set('working', sessionId)`, `turn.complete` writes `''`, both call `$.ui.invalidate('ui.render')` (the drawing does not subscribe to the store), and the render hook reads `working = store value === $.session.id()` so a flag a crashed session left behind reads as idle. `turn.start` is used instead of `prompt.submit` because a slash command goes through `prompt.submit` with no turn and would leave the flag stuck.
- `turn.complete{reason: [...]}` is a one-of matcher because plan 06's registrar already hooks `turn.complete` unmatched and the engine refuses two unmatched hooks on one event in one module. Same reason for `session.start{isInteractive: [true, false]}` in the command registrar.

**5. [Rule 3 - Blocking] Pane id as a same-file literal**
- With `requestId: PANE_ID` imported, validate lists `requestId=?`; a same-file `const PANE = 'mindrian-workspace'` lists it. The registrar tests mount the real pane on `PANE_ID` from `ids.ts`, so a drift between the two fails them; plan 18's guard may also assert it directly.

**6. [Rule 3 - Blocking] The press and select arms on a shell drawn by a test hook cannot press**
- `ui.press` on a Button a test hook drew finds no Button (the element is not the plugin's). The shell view arms test structure (keys, labels, variants, hotkeys, colors); every press arm (tab, Select, Help, Explain, details, plain, sample) runs through the real registrar on the real pane id. The `ui.close` hook with a person origin cannot be raised from a test (`$.ui.close` is not on the test `$`); its decision is the pure `closeDecision` tested directly, as the plan allowed.

## Notes for later plans

1. **Bodies cannot import `$`-taking helpers.** Plan 11 to 14 text assumes `refreshViewModel($)`, `loadThink($)`, `loadSources($)`, `pressChoice($, ...)` called from imported body files and `onOpen($)`. The engine refuses that. Options that validate: (a) extend `Actions` in `src/pane/types.ts` and `makeAct` in `src/registrars/pane.tsx` (the one file that holds `$`) with the closures a body needs, as plan 06 did for its `LiveIo`; or (b) a body file that exports a registrar `registerXBody(on)` registering its own hooks (for example on `ui.press` for its keys or `ui.open`) and is called from `registerPane`. Also: any atom a body reads or writes must be declared in the file that calls `read`/`update`, so a body's state needs its own hook file, and `types/state.d.ts` is the one contract.
2. **Same event, two unmatched hooks in one module is refused.** `session.start`, `turn.complete` and `turn.start` may each have one unmatched hook across all registrars; a second needs a one-of matcher on a field the event carries.
3. `ctx.act.fill` is `$.prompt.fill({ text, mode: 'replace' })` and resolves `isFilled`; there is no `submit`.
4. Registering a hook must be inline or a named function: a call that returns a hook (a factory) is refused.
5. Test facts: a module a test imports is a separate instance from the plugin's; the test `$` has no `ui.close`; `ui.press` on a Button drawn by a test hook finds nothing; a pane's state persists across mounts within one test (reset the tab at the end of a loop); a test needs `mock.store` before the render hook reads `$.store`.
