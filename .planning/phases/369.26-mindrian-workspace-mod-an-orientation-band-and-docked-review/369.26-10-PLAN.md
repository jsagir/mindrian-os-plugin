<objective>
Build the domain half of the Review tab: choosing a verdict from the recorded card, calling the runtime, and turning its answer into honest states (UI-SPEC 7.6 ProposalCard behavior and states, 8.6 refusals, C-07, OQ-03, OQ-07, R-16, R-17; CONTEXT Contract: "Nothing optimistic: 'saved' shows only after the runtime confirms" and "one press saves through gate_answer"; WS-12).

Purpose: this is the one place the mod WRITES to a room, so it is built and tested without any UI first. The card UI (plan 14) only draws what this machine reports.
Output: verdict and refusal tables, the state atoms, the gate client, the answer machine and tests that pin never-optimistic, one-press-one-save, and every refusal.

Known runtime facts that bound this plan (measured while planning; re-read the code before relying on them):
- `gate_answer` takes `{ gate_id, chosen: [option ids], verdict: approve | reject | defer }`. It refuses with the gate left open: room_switched, stale_subject, session_mismatch, chosen_not_approving, verdict_chosen_mismatch, card_pending, persistence_failed, replay_lookup_failed; and with nothing to answer: gate_expired, unknown_gate; also chosen_not_in_card_options. A repeat answer returns ok with `replayed: true`; one answered through a mirror says `answered_elsewhere: true` (lib/mcp/tools/gate.cjs lines 1371-1374 and 1404-1430).
- The call records HOW it arrived: a browser click carrying the shell's nonce is `browser_nonce`; every other caller, including this mod's `$.mcp.call`, is recorded `mcp_relayed` (lib/mcp/answer-route.cjs; quick 261004-av2; SEED-114 owns the human-only route and promotes to Phase 369.3). This is the same footing as Desktop and Cowork today. The mod must not claim more than the runtime did, and plan 17 reads the recorded route on a real round trip.
- A `defer` or `reject` answer ends the gate (it leaves the open list: `readOpenRaisedGates` skips a gate with an answer anchor), so the UI-SPEC sentence D13 "This decision stays open" may be FALSE after a wait-type choice. This plan therefore re-reads `gate_list` after a defer and chooses D13 only if the card is still listed, else D24. Recorded as OQ-14 for the navigator.
- A chain-halt card (`resumes: true`) answered with approve RUNS the halted step in the same call. UI-SPEC D10 to D12 do not say that, and CONTEXT says the mod runs no command itself. Recorded as OQ-15; until ruled, the mod does not save an approve on such a card.
</objective>

Decisions this plan fixes (Claude's discretion; UI-SPEC section 15: "which field carries the verdict for each recorded option is UNVERIFIED and is read from the card, never guessed"):
- Verdict rule: if `card.approving` contains the option id the verdict is approve; otherwise look the option id up in `OPTION_VERDICTS`, a closed table built from the option ids the repo's own producers raise (measured: `approve`, `approve_run`, `approve_standing` are approving ids; `reject` and `stop` mean reject; `defer` and `not_now` mean defer; `skip` is a chain step that is not run). The executor re-derives the table by reading every `gate_render` and `renderGate` caller (`grep -rn "id: '" lib/mcp/tools/chain.cjs lib/mcp/tools/research.cjs lib/mcp/tools/sensors.cjs lib/mcp/tools/gate.cjs lib/core` for option objects) and cites file and line for each row in a comment; a row the code does not settle is left out. `skip` is classified from how chain resume treats a non-approve verdict (lib/mcp/tools/chain.cjs RESUME notes: a non-approve verdict returns without running the step), reject being the verdict that records "not run". An option id in neither place is `null`: the mod writes nothing for it and plan 14 draws it as not savable here (the only deck sentence that says "answer it in the conversation" is D30, whose wording is about multi-answer cards; the mismatch is OQ-13/OQ-14's neighbor and is for the navigator, not fixed by inventing copy).
- Consequence id (UI-SPEC 7.6: "D10, D11 or D12 chosen by kind and by the focused or suggested option's verdict"): D11 when the verdict is defer; D10 when the card kind is `general` and the verdict is approve or reject; D12 for any other kind.
- Phases per card (atom `phaseAtom`, keyed by gate id): ready, saving (with a `claim` token), saved (with the copy id and data), refused (with the E id), checking (with D31 then D32, D33 or D34). The in-flight guard is a compare-and-set through `update`: set saving only if the current phase is not saving, then re-read and proceed only if the stored `claim` equals this press's token. If `update` returns the applied value use it; otherwise re-read.
- Stale check (UI-SPEC 7.6 lists "checking D31 then D32, D33 or D34" with no key or trigger): it runs automatically after a `stale_subject` refusal and compares a fresh `gate_list` read of that gate (state open and header and option ids unchanged gives D32; state no longer open or contract changed gives D33; read failed gives D34). No new key, no new copy.
- Card ownership: `gate_list` does not say which session minted a card, so the mod learns a card is foreign only from a refusal: `session_mismatch` or `unknown_gate` adds it to `foreignAtom` (plan 14 then draws P114 and the P115 button). `mirrorHere` calls `gate_render` with `mirror_of` and the recorded option ids in order (read the input schema in lib/mcp/tools/gate.cjs lines 1215-1245 and `_prepareMirror`), stores the returned new gate id in `mirrorsAtom` (recorded gate id to ledger id), and every later answer for that card uses the ledger id (as ui/shell/server/actions.ts does).
