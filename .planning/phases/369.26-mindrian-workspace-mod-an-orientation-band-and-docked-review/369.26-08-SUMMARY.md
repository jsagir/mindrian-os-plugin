# Phase 369.26 Plan 08: Band one row, keys and prefill Summary

**The band is now complete at every size and room state: one row for T1, T0 and any unbound room (compact logo, the name alone in blue, one or two worded alert blocks, a Help button), the o/h/r/k keys that only open the pane or add a sentence to the prompt box, and the all-keys panel carrying the fix keys a short window cannot show.**

## What was built

- **Alerts** (`src/band/alerts.ts`): priority is the context limit (80 or more), then a room problem (drift or broken), then a waiting decision; one slot below 68 columns, two from 68. A value that could not be read is never an alert. `fixFlags` says whether `r` and `k` are armed and whether `o` lands on Review or Room.
- **One row** (`src/band/one-row.tsx`): T1 is compact logo, folder name alone (B16) in the blue block, alert blocks (B50 words bold for the context limit, B41 yellow, B42 red with cream words, B64/B65, B68 below 48 columns), Help as a plain `h: Get help` Button on a cream block. With no alert and 48 columns or more: dim B66 when the count was read and is zero, dim B62 when it could not be read. T0 is B01 and Help. Not bound: B12 (B13 for a remembered room, B14 for an unreadable place) in the blue block and Help. Plain mode brings back the full place line (B10, B11), leads warnings with a bold `! `, and puts a bar between blocks; no color prop exists in the tree.
- **Keys** (`src/band/hint-row.tsx`): row 3 right holds dim plain `o` and `h` at T3-wide and `h` only at T3-compact; `r` (B44) at the end of row 2 only on a room problem; `k` (B55) at the front of row 1 only at the limit. At T1 and T0 the slots add nothing.
- **Prefill** (`src/runtime/prefill.ts`): `prefillPrompt(io, id, data)` fills and toasts P34 or P35 and never throws. The `io` has no submit closure, so it cannot submit.
- **Routing** (`src/band/band.tsx` `drawBand`, `src/registrars/band.tsx`): every tier and case goes through one function; the hook yields only for a survey, a window under four rows, and a null model. `makeBandAct($)` builds the closures: `o` updates the tab (only when the pane is closed) then `$.ui.open` with focus; `h` toggles `keysOpen` with the pane open, or opens Room with the panel open; `r` and `k` call `prefillPrompt` with Q06 and Q07.
- **All-keys panel** (`src/pane/keys-panel.tsx`): `o` always, `r` and `k` only when armed, as pressable buttons (`keys:open`, `keys:checkup`, `keys:save`).

## Deviations from Plan

### Auto-fixed Issues (ENGINE-RULES wins over the plan text)

**1. [Rule 3 - Blocking] `prefillPrompt($, id, data)` is `prefillPrompt(io, id, data)`**
- `$` cannot cross an import (rule 1). The registrar builds `{ fill, toast }` closures over its own `$`; the grep gate and the type both keep submit out (there is no submit closure). Same for `bandSlots($, ...)`, which takes the view model and a `BandActions` closure set, and `renderOneRow`, which takes `{ onHelp }`.

**2. [Rule 3 - Blocking] `openWorkspace($, tab, title)` is not called from the band**
- It no longer exists (plan 07 replaced it); the registrar writes the two calls inline (`update` of the tab atom, then `$.ui.open`) as the ENGINE-RULES recipe says. The tab and `keysOpen` atoms are declared in `registrars/band.tsx` with literal references (rule 2).

**3. [Rule 1 - Plan conflict] Task 2 and Task 3 split of the registrar wiring**
- The mounted key arms (o, h, r, k) cannot pass until the registrar is wired, so the Task 2 commit carries only pure and pane-mounted arms and the mounted band arms landed in the Task 3 commit with the registrar. Every commit is green.

### Interpretations

- **Help block text color.** The plan says Help is drawn "on reading with black text". A `Button` has no color prop, so the Button sits in a cream block and its label color is the host's (R-01, R-18, owed to plan 09). Not invented around.
- **Plain mode name.** UI-SPEC 12.2 says "B01 with B02 read once"; I draw B01 (as plan 05's three-row band does) because B02 is 32 characters and would push the alert off a 55-column row. B02 stays in the deck, undrawn (the OQ-02 allow-list note in plan 02 still applies).
- **Dim filler on an unreadable count.** With no alert and the waiting count unreadable, I draw dim B62 ("Can't check decisions right now") instead of B66, because "Nothing waiting" there would be a false reassurance (UI-SPEC 10.4). Below 48 columns nothing is drawn.
- **Unbound room, no alert.** The plan says place and Help only; I kept that exactly, so a context limit with no room bound shows no alert (the save key has nowhere to save to).
- **Hotkey uniqueness.** The plan's "no hotkey is drawn twice at once across band and shell" cannot hold literally: the pane's hint line and the band both carry `h`. The engine fires a hotkey only while its own site holds the keys, and both `h` do the same thing, so I assert uniqueness inside each site (band tree; pane tree) and note the shared letter here. `o`, `r`, `k` also appear in the keys panel; same reasoning.
- **Pressing `o` with the pane open** only re-calls `$.ui.open` with focus (no tab change). The engine documents that a focus request from a band the person holds can be refused ("opens without the keyboard"), so whether `o` really moves the keyboard is a plan 09 and 17 live item.
