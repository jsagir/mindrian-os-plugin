## Open Question 3 resolved: the local SIGNAL corpus lives in a per-room sidecar

296-RESEARCH.md Open Question 3 left the storage location open between a new room.db table and a
`<room>/research/<slug>/` sidecar, and recommended sidecar-first. This plan ADOPTS that
recommendation. The navigator can override; the reasoning is stated here so an override is a
decision rather than a discovery.

Location: `<room>/research/<topic-slug>/.rs-signal-cache/` containing `vectors.jsonl` and
`manifest.json`.

Five reasons:

1. **Provenance is already there.** `scripts/rs-engine.py` line 1214 computes
   `corpus_dir = room_dir / "research" / slug` and writes `_corpus.jsonl` and
   `.rs-engine-results.json` into it. The embeddings of that same corpus belong beside it, not in a
   different substrate.
2. **It sidesteps the Canon Part 9 question entirely.** A new room.db table would have to justify
   itself under the derived-rebuildable-projection exception that `lib/core/eureka/vector-store.cjs`
   lines 32-45 established, or route through the `navigation.cjs` chokepoint. 296-RESEARCH.md makes
   an `icm-architect` consult a PREREQUISITE for the room.db branch and not for the sidecar branch.
   Choosing the sidecar removes a gate rather than deferring it.
3. **It keeps room.db lean.** `MAX_NAMESPACE_VECTORS` is 10,000 and the local dim is 384, so one
   saturated topic is roughly 15 MB of float data before metadata. room.db is the local mind, not a
   document warehouse.
4. **It avoids F-5's identity-space collision.** `eureka_vec` is keyed by `nodes.id`. The signal
   corpus is keyed by external document ids (DOIs, arXiv ids). F-5 documents that mixing those two
   id spaces produces joins that return zero rows silently. Two corpora, two id spaces, two homes.
5. **Per-room by construction closes SEED-029 F8.** The bleed existed because the Pinecone namespace
   key was the topic alone. A path rooted at `<room>/` cannot express a cross-room key.

Invalidation: the manifest carries `embedding_model` and `embedding_dim`. A model change makes the
cache read as stale and triggers a cold refetch, which is the same self-healing shape
`.rs-engine-cache.json` already uses (it keys on `sha256(text)[:16]` plus the model name). No
migration is required for existing rooms: there is no existing local signal cache to migrate, and
the remote Pinecone index is not deleted by this code change (that is an operator step, tracked in
plan 296-06).
</planner_decision>
