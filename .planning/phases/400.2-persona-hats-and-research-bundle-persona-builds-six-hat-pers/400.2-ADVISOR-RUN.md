## Part B. What leaves the machine

- Labels only. Each request holds one job id, one job summary (the sentence of data/job-vocabulary.json) and 73 questions. Each question names one command (for example `/mos:persona`) and the fixed template `serves_job_v1`.
- 20 requests, one for each vocabulary job, 73 questions each, 1460 questions in total. The transport sends each request in 1 call (the limit is 1000 questions for each call), so the run makes 20 calls.
- No room text, no venture name, no person name, no file content, no install id. The transport checks each request with the labels-only validator before each send and refuses the call if one field is not in the catalog.
- Where it goes: only `https://mindrian-decision-relay.onrender.com` (the one allowlisted origin). The transport refuses any other base before it reads the token.
- What stays on the machine: an audit record in `~/.mindrian/decision-relay-audit/` (counts, status codes, reasons and body hashes; never the token and never a body), and the saved answers of each finished request in `<pairs file>.partial/`.
- Seven jobs are new in this run: build, design-solution, model-business, model-finances, navigate, protect-assets, temporal-correction. The other 13 are asked again, so the new fixture replaces the whole old one (the old run asked 113 commands for each job, the request set asks 73).

## Part C. The commands

Set the two paths once. The directory is outside the repo.

```bash
cd /home/jsagi/dev/MindrianOS-Plugin-399

```

Step 1. Build the 20 request files (no network):

```bash

```

Expected last line: `wrote 20 requests, 73 questions each, to <path>`.

Step 2. Optional dry run of one request (no network, no token, prints the body that the relay would receive):

```bash
node scripts/decision-advisor-transport.cjs --provider relay --dry-run --request "$RUN_DIR/requests/navigate.json" | head -c 600
```

Step 3. The live call. One command, 20 requests, in the order of the file names. This is the only command of this sheet that spends money and sends data:

```bash
args=(); for f in "$RUN_DIR"/requests/*.json; do args+=(--request "$f"); done
node scripts/decision-advisor-transport.cjs --provider relay --operator-release-run "${args[@]}" --base https://mindrian-decision-relay.onrender.com --out "$RUN_DIR/pairs.json"
```

The transport prints one line and the exact JSON body before each POST. It writes `$RUN_DIR/pairs.json` when all 20 requests have answers. Expected last stderr line: `transport --out: wrote 1460 pairs, skipped 0 answers`.

If the run stops part of the way (a network error, a relay refusal), the paid answers are saved. Run the same command again with `--resume` added after `--operator-release-run`. Each request with a saved answer is read from disk and is not sent again:

```bash
node scripts/decision-advisor-transport.cjs --provider relay --operator-release-run --resume "${args[@]}" --base https://mindrian-decision-relay.onrender.com --out "$RUN_DIR/pairs.json"
```

Exit codes: 0 ok; 2 bad usage or labels-only refusal; 4 egress line off; 5 token missing, endpoint not confirmed or audit not writable; 6 http error, bad response, catalog skew or relay refusal. On a catalog skew (409), stop and report: the plugin catalog and the relay catalog differ.

Step 4. Keep `$RUN_DIR/pairs.json`. Give its path in the answer. Do nothing else with the token.

## Part E. The irreversibility re-score (PG-03), owner choice

Why: the irreversibility row of `/mos:persona` is STALE, because the text of the command changed in this phase (its `jtbd_summary`). The shipped ledger scores each command from three inputs only: the command name, `teaching` and `jtbd_summary`. The `teaching` text of `/mos:persona` did not change in this phase, so the score can move only through `jtbd_summary`.

What the live builder does and what it sends:

- It scores all 113 commands of data/command-registry.json, not only `/mos:persona`. The builder has no mode for one command.
- It makes 1 call for each command to `https://api.typesafe.ai/v1/systemone` (model `jev-latest`, 4 calls at one time). Each call carries the written irreversibility policy (data/jev-policies/command-irreversibility.json), the command name, its `teaching` text and its `jtbd_summary`. These are catalog texts of the plugin. No room content is in them.
- The dev-time key is read by the builder only, from the environment or from `~/.secrets/typesafe.env`. The key is never printed and never written into the ledger. Do not open the secrets file in the session.
- Run it with `--out` and `--raw-out` in the run directory. The shipped file `data/command-irreversibility-ledger.json` is not touched by this command. An agent copies the new ledger into place in task 3, after it reads the check result.

```bash
node scripts/build-command-irreversibility-ledger.cjs --out "$RUN_DIR/ledger-new.json" --raw-out "$RUN_DIR/ledger-raw.json"
```

Exit codes: 0 ok; 1 threshold or scoring failure; 2 refused input; 3 no key (nothing is written); 4 appeal gate. Then check the new ledger offline (no network):

```bash
node scripts/build-command-irreversibility-ledger.cjs --check --ledger "$RUN_DIR/ledger-new.json"
```

The check must show no `STALE /mos:persona` line. Other lines may stay (the shipped ledger has 25 warnings today, among them `ANSWER_KEY_DRIFT`; this plan does not clear them).

The choice: answer `ledger-rescored` after you ran the two commands above, or `ledger-deferred`. With `ledger-deferred`, the STALE warning stays (exit code 0 of `--check`), and section 6 of 400.2-OWNER-REVIEW.md records it as open.
