## 1. Problem

## 2. Goals and non-goals

Goals (S1 to S7 plus cycle v2):
- G1. Six personas produced from the room by six fresh `persona-analyst` runs. A persona is built from the room only.
- G2. White researches first and shares its package. Black, Yellow and Green research their own side. Red and Blue never search.
- G3. One approval card for each researching hat with its exact strings and providers. The four cards are shown together in one interaction (owner answer 2). Each hat is approved or refused on its own.
- G4. Six independent readings. A hat cites only the White package and its own sources.
- G5. A merge that records dissent first, uses only the tension map, keeps attribution, and adds nothing.
- G6. Two named modes: deep and quick. Triage is a recommendation on the brief card.
- G7. Personas live until the room changes. Freshness is per hat.
- G8. A recorded comparison of deep and quick on one question, with two real inputs.
- G9. The capability carries nine jobs as equals. Each of the nine reaches `/mos:persona` through the ranker and, after the recorded advisor run of this phase, through the advisor table (owner answer 1).

Non-goals: a new agent; a loop until agreement; any agent-side confirmation; a change of `/mos:bono` behaviour; an MCP tool for the research leg; a fix of `HAT_LENS_BIAS`; a change of the `produces` path; a benchmark suite; a change of `lib/core/synthesizers/tension-map.cjs`; a neutral position 0 of `serves_jtbd`.

## 4. Design

### 4.1 The cycle and the stops

| Step | Who | What | Stop for the navigator |
|---|---|---|---|
| 1 Triage | Larry | a recommendation (deep or quick) with one reason; it is the first line of the brief card | none of its own |
| 2 Brief | Larry, door `start` | target, governing question, 2 to 5 sub-questions, reading list | Stop 1: brief card (confirm, edit, choose mode, cancel) |
| 3 Produce | fresh agents, door `write-persona` | one persona for each hat that is not fresh; built from the room only | Stop 2, only when 1 or more personas were built: accept, rebuild or refuse each |
| 4a Handles | 4 fresh agents (small), door `plan-research` | each researching hat proposes 2 or fewer generic handles for this brief; the door screens and composes the strings | none |
| 4b Approval | navigator | four search cards shown together | Stop 3: each hat approved, edited or refused on its own |
| 4c Shared facts | door `run-research` | White is fetched first; its package is copied to every hat | none |
| 5 Private research | door `run-research` (same call) | Black, Yellow, Green are fetched | none |
| 6 Readings | 5 fresh agents | white, red, black, yellow, green each read the target alone | none |
| 7 Check | door `check` | citation boundary, per-hat rules, not-run list, the counts-only ledger for Blue | none |
| 7b Blue | 1 fresh agent | Blue reads the ledger and the brief only | none |
| 8 Merge | door `merge`, then Larry | deterministic artifact; Larry narrates it | none |
| 9 Rulings | navigator, door `record-ruling` | one ruling for each open tension, in one interaction | Stop 4 |
| 10 Measure | door `compare` | optional comparison record of a deep run and a quick run | none |

True stop count of a deep run (input for Phase 400.1):
- Steady state (all six personas fresh and accepted): 3 stops (brief, search cards, rulings). The search stop holds 4 approval cards.
- First run or stale personas: 4 stops.
- With the follow-up validation round of 4.11 (DEFAULT, owner item O-1): 1 more stop, only when 1 or more hats ask for it.
- Agent runs: produce 0 to 6; handles 0 to 4 (0 when handles for the same brief hash and persona hash are stored); readings 5; Blue 1; follow-up re-reading 0 to 4. Steady state: 6 to 10. First run: 16. Maximum: 20.
- Door shell calls: 8, plus 1 for each card edit round.

Quick mode is steps 1, 2 (same brief card), then one pass of six hats in the main context, then door `merge --quick-result`, then step 9 as an option. It makes no agent run and no fetch.

Triage rule (Larry recommends, the navigator decides on the brief card): quick when the target is one artifact and the question needs no outside fact; deep when the question needs outside evidence, or the decision is costly to reverse. An unattended caller (`/mos:act`, `chain_run`) always gets quick, because it cannot answer a card (precedent `commands/dominant-designs.md:89`). `autonomous_safe: true` stays.

### 4.2 Mode identity

- The two documented names are `deep` and `quick`. `--parallel` (deep) and `analyze` (quick) stay as accepted old spellings, named in one line each. Reason: `tests/test-265-persona-route.cjs:73,155` pin `/mos:persona --parallel`, and the MCP route names it.
- Fixed first line of each output, returned by code and not by prose:
  - Deep: `DEEP_NOTICE` = "Deep review: six isolated hats, own research, own reading." The door adds, when true: "Research not run for: <hats> (<reason for each>)." and "Not run: <hats>."
  - Quick: `QUICK_NOTICE` = "Fast look: six hats in one pass, one context, no research. This is not an independent review."
  - Both are constants in `lib/core/persona-ops.cjs`, in the style of `PREVIEW_NOTICE` (`:103`). `merge` writes the notice as the first line of the artifact and prints it first. `quickLook` (4.10) returns it in the field `notice`.
- A deep step never runs in the main context. If the Agent tool is not present, deep is refused (section 10). The version 1 label "same-context run" is removed: it had no mechanism.
- The old subcommands after the change: `list` and `invoke` are unchanged. `generate` keeps its route answer and its `--preview` mode; the route answer gains 2 additive fields (section 10). `generate` with no flag in Claude Code starts the deep entry at step 2.

### 4.3 The door

`scripts/persona-hats.cjs` is the one CLI door for every deterministic step. Justification under Part 7: the Bono research leg has no door (PROVEN, R-1 item 2), and prose-only wiring is what failed. Precedents: `scripts/dominant-design-research.cjs` (compose, audit, approved file, validate, input by file path never argv text) and `scripts/close-loop.cjs`. The Bono modules are required lazily inside the door only. Each subcommand prints one JSON object. Navigator text and room text enter only by JSON file path.

Ten subcommands. Without folding the flow would need 14 (a plan call for each hat, a check call for each hat, a separate audit of an edited string, a separate quick record).

| Subcommand | Reads | Writes | Refuses when |
|---|---|---|---|
| `status --room` | room, persona files | nothing | never (read-only) |
| `start --room --brief <file> --mode deep\|quick` | brief (S-1), room | run ledger (S-8), private run map, scratch directories, web sentinel (deep only) | brief invalid; room has fewer than 2 sections with an indexable artifact |
| `write-persona --run <id>` | each `<hat dir>/persona.json` (S-2) | `personas/<hat>-<domain>.md` with `persona_status: proposed`; removes other `<hat>-*.md` files of the same hat | step `start` not done; spec invalid (that hat only) |
| `accept-persona --run <id> --answer <file>` | answer (accept, rebuild, refuse for each hat) | `persona_status: accepted` and `accepted_at` in the file; ledger | a hat in the answer has no proposed file of this run |
| `plan-research --run <id> [--edited <file>]` | each `<hat dir>/handles.json` (S-3a), or stored handles; edited strings | plan (S-3); handles store | a researching hat whose persona is not accepted and fresh gets `not_planned:persona_not_accepted`; the identity screen cannot run |
| `run-research --run <id> --approved <file> [--round followup]` | plan, approved (S-4) | evidence packs (S-5), White copy in each hat directory, room.db proposed nodes, ledger | no plan; a string hash outside the plan; more than 2 strings for a hat; the provider set differs from the plan; a red or blue entry (`hat_never_searches`) |
| `check --run <id>` | the 5 reading files (S-6), evidence packs | check results in the ledger; `blue/ledger.json` (S-9) | the research step is not closed |
| `merge --run <id> [--quick-result <file>]` | all readings, packs, rulings store | review artifact, final run record, hat session logs; deletes scratch and the sentinel | `check` not done (deep); it runs every step 7 check again and does not trust the stored result |
| `record-ruling --run <id> --answer <file>` | answer (S-10) | rulings store, ledger, one memory event for each ruling | `merge` not done; a tension id that the run does not hold |
| `compare --room --deep <run id> --quick <run id>` | two final run records | `compare.md` in the deep run folder | brief hashes differ; a run is not merged; modes are not one deep and one quick |

Step order is enforced by the run ledger. Only the door writes it (temp file then rename). Each subcommand reads the ledger first and refuses with `step_out_of_order:<missing step>` when its precondition state is absent. The command prose cannot skip a step: a later subcommand refuses.

Run identity: `run_id` = `<UTC date YYYYMMDD>-<HHMMSS>-<4 hex random>`. The review folder is `personas/hat-reviews/<run_id>-<slug>/`, where `slug` is the first 5 words of the governing question passed through `genericDomainHandle` and joined with hyphens. A same-second collision is avoided by the random part; `start` also refuses an existing folder.

### 4.4 Research: lens set, providers, wrapper and states

Lens set. The door does not use the room-derived lens set (PROVEN defect: a room with only the thesis-build rule gives `[brain]`, and an investor room with no Tavily key searches nothing, `lib/core/research-context-extractor.cjs:142-199`). The door sets a fixed lens set for each hat (DEFAULT CHOSEN, confirmed or changed by the spike of this section):

| Hat | Lens set (provider) | Reason |
|---|---|---|
| white | `scholarly` (openalex), `industry` (tavily) | data and statistics |
| black | `scholarly` (openalex), `industry` (tavily) | failure cases are mostly practitioner reports |
| yellow | `industry` (tavily), `scholarly` (openalex) | success cases are mostly practitioner reports |
| green | `scholarly` (openalex), `patent` (patents) | ideas from other fields |

- The `brain` lens is never in a set. No `brainFn` is passed.
- `plan-research` passes each set through `preflightLenses(lensSet, {roomDir})` (`source-lens-driver.cjs:476`, no network). Only an available lens is written to the plan and shown on the card. The sentence for a lens that cannot run comes from `unavailableAnswerLine` (`:530-549`). openalex needs no key; tavily and patents need a key.
- The provider list is frozen in the plan and bound on the card. `run-research` computes `preflightLenses` again. If the available set differs from the plan, it refuses that hat with `provider_set_changed` and fetches nothing for it.
- The door injects an `extractContextFn` that calls the real `extractContext` for the local `preflight` (relevance scoring is local, `source-lens-driver.cjs:182-195`) and replaces `lens_set` with the frozen set. `hatScopedLensSet` then only reorders it (`persona-research.cjs:69-77`), and every lens of the set still runs.

Spike task (recorded, before the qualifier table and the lens table are trusted): one generic handle, the four hat qualifiers, the lens sets above. The task records, for each pair of hats, the share of result URLs that both hats got. It is run by the owner or with the owner present, because it sends 4 approved strings. Its record is filed with the phase. Decision rule: if 2 hats share more than half of their URLs, the qualifier or the lens set of one of them is changed before slice 4 is closed. The same task records the hook payload of a hat agent's blocked web call (4.6).

Wrapper (pattern of `lib/core/expert-genesis.cjs:325-378`: a dispatch wrapper plus a side map, made for the same `normalizeReading` loss):
- One `runCellFanout` call for each approved hat: `subdomains: approvedStrings` (2 or fewer), `hats: [hat]`, `selfCritique: keep-all`, no `roomDir` (so `planDispatch` does not run; it is a cost note only, `cell-fanout.cjs:224-232`). 2 cells are under the cap of 5.
- `dispatchCell` is the wrapper. For each cell it calls `personaDispatchCell({subdomain: 'personas', hat, handle: cell.handle}, ctx)`. `cell.handle` is `genericDomainHandle(approved string)` and must equal the approved string; `plan-research` proved this for each string.
- `ctx = {db, roomDir, sessionId, extractContextFn, runSourceLensFn, wireAcceptFn}`. `sessionId` = `persona-<hat>-<first 12 hex of the string hash>`. It holds no run id, so a repeated string writes the same node ids and two hats with one URL still get two ids (`lib/core/navigation/evidence-claim.cjs:161-179`). One session id for each string also stops the `lens_finding:source:<sessionId>:<lens>` overwrite. UNVERIFIED: that a second write of the same node id adds no row; a test proves it.
- Injected `runSourceLensFn`: calls the real `runSourceLens` with the same options plus `_substituteFn: async () => null`. It stores the full result for the string: thrown error, `ok:false` reason, `providers[]`, `research_mode`, findings count. Effect of the seam: the Tier 2 room-corpus substitute never runs, so no room corpus item is wired as web evidence. Tier 1 can send the same approved string again to the same provider; this is allowed and is stated on the card ("a failed provider may be asked again with the same string").
- Injected `wireAcceptFn`: calls the real `findingsWirer.wireAccept` and stores, for each finding, the finding summary and the result (`ok`, `node_id`, `reason`).
- `db` comes from `navigation.openRoomDbForCaller` and is closed with `closeRoomDbForCaller`.

State of each (string, provider): the operation state of the driver, reused by name: `executed_with_results`, `executed_empty`, `refused_before_fetch`, `not_executed`. The record also keeps `reason`, `items` and `cache_hit`. The searched and not-searched lens lists of a string come from `lensSummary(result)` (`source-lens-driver.cjs:443-453`), not from new code.

State of each string, derived from the record and never from the reading:

| String state | Rule |
|---|---|
| `ran_with_results` | 1 or more providers `executed_with_results` and 1 or more findings wired |
| `fetched_not_wired:<reason>` | 1 or more providers `executed_with_results` and zero findings wired. Reasons: `wire_failed` (a `wireAccept` result was not ok), `filtered` (the driver returned zero findings from 1 or more items), `no_db` |
| `ran_empty` | no provider has results and 1 or more providers `executed_empty` (a provider answered with zero items; a cached empty answer counts and is marked `cache_hit`) |
| `failed:<reason>` | no provider executed. Reasons: `thrown`, `empty_lens_set`, `provider_failed:<class>`, `provider_unavailable`, `invalid_opts` |

A string with results from one provider and a failure of another is `ran_with_results` with `partial: true` and the failed provider named.

State of each researching hat:

| Hat research state | Rule |
|---|---|
| `ran_with_results` | 1 or more strings `ran_with_results` |
| `fetched_not_wired` | no string with results; 1 or more strings `fetched_not_wired` |
| `ran_empty` | every string is `ran_empty` |
| `failed` | any other case with 1 or more strings `failed` |
| `declined` | the navigator refused the card of the hat |
| `not_planned:<reason>` | no plan for the hat (`persona_not_accepted`, `no_valid_handle`, `identity_screen_unavailable`, `no_available_provider`) |

`ran_empty` is the only state in which a hat may say "searched, found nothing". Every other zero-evidence state is reported as "research not run" or "research failed", with the reason.

Limits stated plainly: `runSourceLens` returns 5 findings or fewer for each call (`TOP_N`, `:115,920`), so a hat has 10 or fewer evidence items. The research cache is in `<room>/.mindrian/research-cache`, key `(source, query)`; a cache hit sends nothing.

Where a finding is filed (DEFAULT CHOSEN, R-3 Q4): a proposed `EvidenceClaim` node plus an `INFORMS` edge to `section:personas`. PROVEN: `writeEdge` probes no endpoint and a new room.db has no foreign key on `edges` (`lib/core/lazygraph-ops.cjs:185-191`; `lib/core/navigation/CONTEXT.md:31-39`). PROVEN: no code mints a node with the id `section:personas`; the indexer's Section node id is the bare section name (`lazygraph-ops.cjs:572`), and `lib/core/research-planner/filing.cjs:848` already writes `INFORMS` to `'section:' + section` with no mint. The edge therefore has a missing endpoint by design, which is a permitted state. On a room.db made before Phase 169 the old foreign key is still present (`lazygraph-ops.cjs:79-86`) and the edge insert is rejected; the door then records `fetched_not_wired:wire_failed` for that string and says so. This is risk K-9.

### 4.5 Search strings

Handles (owner scope S1 names the handles a room part of the persona; the orchestrator direction moves them to a per-run step so that a persona built for one brief never shapes the searches of another):
- A persona file holds no handle. Step 4a asks each researching hat for its handles: one small fresh `persona-analyst` run for each of white, black, yellow, green, dispatched in one message. Input: the brief and the hat's own persona file. Output: `<hat dir>/handles.json` (S-3a), 2 or fewer handles. DEFAULT CHOSEN; the cheaper alternative (Larry proposes the handles, zero agent runs, weaker isolation) is owner item O-4.
- Handles are stored at `<room>/.mindrian/hats/handles/<brief hash 16 hex>.json`, keyed by hat and by the content hash of the hat's persona file. `plan-research` reuses a stored entry when both keys match and then needs no agent run.
- Contract for Green: its handles name a field other than the field of the room, where the same structural problem exists. Code cannot check "another field"; the card shows the handle and the navigator sees it.

Checks on each proposed handle, in this order (the content fence runs on the raw handle, before the shape step can remove the characters that the fence detects):
1. Content fence on the raw handle: `auditQueryString(rawHandle, 'persona-hats')` (`lib/core/rs-egress-prompts.cjs:72-91`). A hit refuses the handle (`egress_violation`).
2. Shape: the raw handle must equal `genericDomainHandle(rawHandle)` and must have 1 to 4 words. A handle with a capital letter, punctuation or more than 4 words is refused (`handle_not_generic_shape`). It is not silently normalised, so nothing is hidden from step 1.
3. Digits: a handle with a digit is refused (`handle_has_digit`). DEFAULT CHOSEN: no year exception.
4. Room identity screen (section 8).
5. Compose: `string = handle + ' ' + HAT_RESEARCH_QUALIFIER[hat]`. The qualifier is a fixed 2-word text, so the string has 6 words or fewer and equals its own `genericDomainHandle` form. Table (provisional until the spike): white `data statistics`; black `failure cases`; yellow `success cases`; green `analogous solutions`.
6. The composed string passes `auditEditedQuery(string, {auditFn})` of `lib/core/dominant-design/lane-queries.cjs:172-192` (length 200, no newline, fence, no echo of the string in the error). `auditFn` is `auditQueryString` with the surface `persona-hats`. `composeLaneQueries` of the same file is not reused: its lane templates are fixed to the dominant-design lanes (`:48`, `:137-157`).
7. `q_hash = qHash(string)` (`lib/core/research-planner/families.cjs:264`) is written to the plan.

Edit path. The navigator may edit a string on its card. The command writes the edited strings to a file (S-3b) and calls `plan-research --run <id> --edited <file>`. The door runs checks 1 to 4 on the edited text with the qualifier removed, and checks 2, 3, 6 and 7 on the full edited string. An edited string must still end with the hat qualifier (`qualifier_removed` otherwise): the qualifier is what makes the search the hat's own. The plan is issued again with the new hash and an `edited: true` mark for the audit record, and the cards are shown again. A refused edit is reported and never sent.

### 4.9 Merge (step 8) and tensions

Sub-questions. The brief lists 2 to 5 sub-questions. `start` gives each a fixed id `sq-<first 8 hex of SHA-256 of the normalised text>`, so the same question text has the same id in every run.

Positions. Each reading gives, for each sub-question, one closed value plus one free line (S-6). Values for white, red, black and yellow: `favours`, `opposes`, `mixed`, `no_position`. Values for green: `alternative_offered`, `no_position` (Green never evaluates). Blue gives no position.

Tension call, with no change to `tension-map.cjs`. For each sub-question the door calls `lensEngine.rotate` once:
- `lensType: 'cognitive'`, `lensSet`: the array of `<hat>-hat` ids of the hats that ran and have a mapped value for this sub-question, `rotationMode: 'parallel'`, `synthesize: 'tension-map'`, `input: {roomDir, topic: <sub-question id>, sessionId: 'persona-merge-<run_id>-<sub-question id>'}` with no `db`, and no `onAccept` or `onReject` hook.
- `perLensFn(lens)` returns `{topic: <sub-question id>, summary: <marker text>}`. The marker text is fixed: `favours` gives `benefit`; `alternative_offered` gives `opportunity`; `opposes` gives `risk`. A hat with `mixed` or `no_position` is not in the lens set of that sub-question.
- PROVEN mechanics: `rotate` accepts a lens array (`lens-engine.cjs:148-152`) and drops a null hat (`:214,381`); `synthesizeTensionMap` reports a pair of `OPPOSING_PAIRS` on one topic when one summary holds a benefit marker and the other a caution marker, and drops a pair whose markers do not oppose (`tension-map.cjs:32-36,41-42,93-113`). With the fixed marker text every node holds exactly one marker, so the result is deterministic and the polarity is always `confirmed`.
- With no `db` the engine writes no `lens_finding` node (`lens-engine.cjs:219-231`). The review artifact is the record. This avoids up to 25 nodes a run whose summary would be one marker word.

Limit stated plainly, in the design and as a fixed line of the artifact: "The tension map knows three hat pairs: yellow and black, green and black, red and white. Opposite positions of any other pair are shown in the dissent register only." So a run has 3 x (number of sub-questions) tensions at most, 15 at most.

Agreement. Deterministic rule, computed by the door outside the tension map as a plain listing: two or more of white, red, black, yellow with the same value (`favours` or `opposes`) on one sub-question are listed as "same position, both attributed: <hats>". Nothing is merged or removed. Green's `alternative_offered` is never counted as agreement.

Settled tensions. Key = SHA-256 of the target content at `start` + sub-question id + hat pair (sorted). The store is `<room>/.mindrian/hats/tension-rulings.json` (S-10). `merge` marks a tension `settled` when its key is in the store with a ruling other than `defer`; the artifact shows "settled on <date>: <ruling>" with the two stored position lines next to the two new ones, and Stop 4 does not ask it again. A changed target or a new sub-question gives a new key and is asked. Only the navigator can re-open a settled key (`record-ruling` with `reopen: true`). Why a JSON file and not room.db: a ruling is a navigator answer about a hat pair, not a venture claim; no node type exists for it and none is added. Each ruling is also logged as one `memory_event` through `navigation.logMemoryEvent` (ids and the ruling value only), so the decision is graph data. UNVERIFIED: the exact payload shape of `logMemoryEvent`.

The artifact. `merge` builds it from reading fields and fixed labels only, in this fixed order:
1. the mode notice and the not-run lines;
2. the brief (target path, governing question, sub-questions);
3. the dissent register: for each sub-question, one line for each hat that ran: hat, closed value, the free line, verbatim. Black's lines are listed first under each sub-question;
4. tensions: for each tension the sub-question, the pair, the two lines, and `open` or `settled`;
5. same position lines;
6. not run: each hat with its state and reason;
7. rule lines of each hat;
8. hat-specific lists, verbatim: White `missing_data`, Green `provocations`, Blue `skipped`, `thin`, `ask_next`, and each hat's `validation_requests` state;
9. sources by hat: evidence id, title, URL, tier, provider, `cache_hit`.
The artifact holds no sentence that is not a reading field, an evidence field or a fixed label. This is the checkable form of "the merge adds no new fact".

Session log. For each hat that ran, `merge` calls `persistPersonaFindings(roomDir, hat, {focus: <target path>, findings: <the hat's position lines, verbatim>, concerns: [], opportunities: []})` (`persona-ops.cjs:589-600`, which calls `hat-persistence.logSession`). ## 8. Part 8 analysis

What can leave the machine in deep mode: the approved search strings only, to the providers bound on the card. Nothing leaves in quick mode. The door sends nothing to the Brain: no `brain` lens, no `brainFn`.

Controls on a handle and a string, with what each can and cannot catch:

| Order | Control | Can catch | Cannot catch |
|---|---|---|---|
| 1 | Content fence on the raw handle (`auditQueryString`, `FORBIDDEN_PATTERNS` of `lib/core/cross-room-aggregator.cjs:207-221`) | every pattern of the list on the text as proposed: email, currency, percent, phone, name-plus-degree, magnitude, venture suffix, the city list | a name or a place that is not in the list |
| 2 | Shape (equal to `genericDomainHandle`, 1 to 4 words) | capitals, punctuation, long text | any lower-case word |
| 3 | Digits rule | figures, years, amounts, counts | a number written in words |
| 4 | Room identity screen | the room's own names (rule below) | a product, person or partner name that the room never states in the screened places |
| 5 | The fence again on the composed string (`auditEditedQuery`) | only the patterns that are case-insensitive and need no punctuation; after controls 2 and 3 the string holds only `a-z` and spaces, so most patterns cannot match. This control is kept for the edit path, where a navigator edit arrives as raw text | most patterns, by construction |
| 6 | The card | everything a careful navigator sees | what the navigator does not notice |
| 7 | Plan binding (`q_hash`, 2 strings, provider list, `plan_seq`) | a string or a provider that was not on the card | nothing about content |
| 8 | `auditWebCredential` inside the corpus (existing) | credential shapes | room words |

The card is the final control for a name that no screen knows. This is the stated residual risk K-3.

Room identity screen (new, small, in the door):
- Sources of screened tokens: (a) the venture name from STATE.md, read as `extractDomainSignals` reads it (`venture:` line, else the first heading); (b) the base name of the room directory; (c) the base names of the files under `team/`; (d) proper-noun candidates of the reading-list files: a token that starts with a capital letter and is not the first token of a sentence or a heading.
- Match rule: both sides are lower-cased and split on every character outside `a-z0-9`. A handle is refused (`room_identity_word`) when any of its tokens equals a screened token of 4 or more letters that is not in the stop-list, or when the full venture name occurs in the handle as a run of consecutive tokens (any length).
- Stop-list: a frozen list in the door of generic words that are common in room and venture names and are valid domain words (for example room, venture, project, company, startup, labs, group, systems, solutions, technologies, global, health, energy, data, market, platform, network, digital, research, design, care, food, water, power, cloud, mobile, smart, green, blue, open, new, test, demo). So "clean room design" is not refused in a room whose directory is `room`. The list is data with its own test.
- The refused handle is shown on the navigator's screen with the reason. It is not written to a file and never sent.
- Fail-closed: when the venture name is absent or is the default `Unknown Venture` (`persona-ops.cjs:183`), the screen cannot run and every researching hat is `not_planned:identity_screen_unavailable`. The navigator adds a `venture:` line to STATE.md and runs again.
- Over-refusal is the accepted side: a venture named after its field refuses that field word. The navigator can type an edited string, which passes the same screen. There is no override of a refusal, because the CONTEXT constraint is "no room text in a web query".
