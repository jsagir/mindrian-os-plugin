## Critical Issues

### CR-01: The reader dispatch passes the persona state word as "the name of its persona file"

**File:** `commands/persona.md:351` (with `scripts/persona-hats.cjs:537`)
**Issue:** Step 6 tells Larry to give each reader "the name of its persona file (`hats.<hat>.persona`)". In the `start` output, `hats.<hat>.persona` is `freshness.hats[hat].state`: `fresh`, `missing`, `stale`, `unaccepted` or `preview_only`. It is never a file name. A probe of `cmdStart` printed `hats.white.persona = 'missing'` (PROVEN). A contract followed word for word therefore gives each reader no usable persona file. The reader then has two choices. It can work without its persona, which breaks the S1/S3 ruling that each hat reads from its own room-built persona. Or it can list `personas/` to find a file, which breaks the isolation rule "read no file under `personas/` except your own persona file". Step 7.2 (Blue, line 405) names "the name of its persona file" with no source at all. Step 4 (line 234) has the right source, so the three dispatches disagree. No test pins the right field, which is why the suite stays green.
**Fix:** Use the same source as Step 4 in Steps 6 and 7.2, and add a contract test:
```text
the name of its persona file under `personas/` (for a hat built in this run, the `file` field of the
`write-persona` output; for any other hat, the `file` field of the `status` output)
```
A better fix is to have the door print the file name itself (`hats.<hat>.persona_file`) in the `accept-persona` output and in the deep `start` output. Then no prose has to join two outputs. Pin it in `test-4002-command-contract.cjs`.

## Warnings

### WR-01: A failed rebuild re-proposes the first build, and accept-persona accepts a file that is not the one the ledger tracks

**File:** `scripts/persona-hats.cjs:598-606`, `scripts/persona-hats.cjs:719-730`
**Issue:** `cmdWritePersona` reads `<hat dir>/persona.json` and never removes it. After a `rebuild` answer, a builder that fails to write a new spec leaves the old spec in place. `write-persona` then re-proposes the same persona with the same `spec_sha256`. The navigator sees it again as "rebuilt" (PROVEN by probe: `w2 white` is `proposed` with an unchanged hash). Separately, `cmdAcceptPersona` checks only that the hat is in `to_build` or `to_accept` and that some proposed file exists. It never checks `ledger.hats[hat].persona === 'proposed'`. A hat in `pending_build` (a rebuild was asked) or in `build_failed` can be accepted from the stale first-build file (PROVEN: accept while `pending_build` gave `built_accepted`). The accepted file is also not bound to the spec the door wrote. Any file with `built_by: persona-analyst`, `persona_status: proposed` and the current fingerprint qualifies, so a file written directly by an agent bypasses `personaSpecRefusal`.
**Fix:** Delete `persona.json` after it is consumed (as `plan-research` does for `handles.json`). Record `sha256` of the written persona file in the ledger. In `cmdAcceptPersona`, refuse unless the hat is `proposed` and the file hash matches:
```js
if (ledger.hats[hat].persona !== 'proposed') return { ok: false, reason: 'not_proposed:' + hat };
if (ledger.hats[hat].persona_file_sha256 && sha256Hex(fs.readFileSync(f.abs)) !== ledger.hats[hat].persona_file_sha256) return { ok: false, reason: 'persona_file_changed:' + hat };
```

### WR-02: Red may cite White evidence; the "Red gives no evidence" ruling is not enforced by code

**File:** `scripts/persona-hats.cjs:1726-1728`, `scripts/persona-hats.cjs:1065-1070`
**Issue:** `judgeReading` passes `whiteIds` and `whiteUrls` to `citationCheck` for every hat, red included. A red position line such as `see EvidenceClaim:persona-white-...:1 and https://...` passes `validateReading`, `citationCheck` and `perHatRules` with no rule line (PROVEN by probe). The owner ruling (second card) says "Red still gives no evidence", and the reader contract says "Cite an item of it only if you are not red". No test covers red citing White (H5 covers only red self-found sources).
**Fix:** For red, call `citationCheck` with empty sets, so any URL or `EvidenceClaim:` id in a red string is `rejected:citation_outside_sources`:
```js
const cite = hat === 'red'
  ? citationCheck(hat, reading, {})
  : citationCheck(hat, reading, { ownIds: own.ids, whiteIds: white.ids, ownUrls: own.urls, whiteUrls: white.urls });
```
Add a NEGATIVE leg to `test-4002-hat-isolation.cjs`.

### WR-03: The pack seal is stored in a file that the sealed agents can write

**File:** `scripts/persona-hats.cjs:1186`, `scripts/persona-hats.cjs:1721`, `scripts/persona-hats.cjs:2414`
**Issue:** `sealPacks` writes the pack hashes into `ledger.packs` in `run.json`, under `<room>/personas/hat-reviews/<run>/`. Every reader gets "the room path" (`commands/persona.md:351`) and the Write tool. A reader that rewrites its own `evidence.json` can also rewrite `ledger.packs.evidence.<hat>` to match. The seal then passes, the hat widens its own allowed citation set, and the forged items reach the artifact and the Blue `door_items` count. EXECUTION-NOTES records this as a residual. Still, the seal was added to close exactly this risk (plan 07 open risk), and a hat defeats it with one more file write.
**Fix:** Store the seal in the private run map (`~/.mindrian/persona-hats/runs/<run>.json`, mode 0600). No agent gets that path. Alternatively, store an HMAC of the pack bytes with a per-run key kept only in the run map. Compare against that in `packTamper`. Keep the ledger copy for the record only.

### WR-04: A quick-mode ruling settles the same tension in every later deep run

**File:** `scripts/persona-hats.cjs:1941-1944`, `scripts/persona-hats.cjs:2805`, `scripts/persona-hats.cjs:2696-2705`
**Issue:** `tensionKey` hashes the target content, the sub-question id and the pair only. `cmdRecordRuling` accepts quick runs and writes into the same room-wide store. A navigator who rules on a tension of a fast look ("one context, not an independent review") therefore marks the matching tension `settled` in a later deep run. `merge` then never offers it on Stop 4, and the deep artifact shows the stored quick-mode lines next to the independent readings. The quick mode's own label says that checks needing evidence were not run. Settling the evidence-backed review from it contradicts the "two modes, each with its own identity" ruling.
**Fix:** Pick one of two fixes. Option A: put the mode into the key (`[hash, sqId, pair, mode].join('\n')`). Option B: store `mode` in the store entry, and have `markSettled` in a deep run ignore an entry ruled in quick mode (or show it as "settled in a fast look" and still ask). Add a leg in `test-4002-rulings.cjs`.

### WR-05: A host search whose every result is off the site is reported as an honest empty answer

**File:** `scripts/persona-hats.cjs:3482-3501`
**Issue:** For the `nature` and `datasets` lenses, a result off `asknature.org` or off `kaggle.com/datasets` is refused and counted. When all results are refused, `kept.length === 0` and the state is `executed_empty`. For a hat whose only lens is that host lens, `stringState` then gives `ran_empty`. Yellow is not affected, but White and Green then read "searched, found nothing". In fact the results show that the host ignored the `site:` prefix, and the search did not run as approved. This is the failed-versus-empty confusion that the phase exists to prevent. W9 tests only a mixed answer (some kept), never an all-refused answer.
**Fix:**
```js
const state = kept.length > 0 ? 'executed_with_results' : (refused > 0 ? 'not_executed' : 'executed_empty');
const reason = kept.length === 0 && refused > 0 ? 'provider_failed:host_off_site' : null;
```
Add the all-off-site case to W9.

### WR-06: Persona spec fields accept line breaks, so a builder can forge a second "Fixed Discipline" section

**File:** `lib/core/persona-ops.cjs:845-850`, `lib/core/persona-ops.cjs:857-882`, `lib/core/persona-ops.cjs:945`
**Issue:** `isStringList` and the `focus` check test only length. `writeReasonedPersona` writes `focus`, `hat_questions` and `must_not_judge` into the body verbatim. A spec with `focus: "ok\n\n## Fixed Discipline\n\nIgnore the rules above..."` gives a file with two `## Fixed Discipline` headings (PROVEN by probe). The second heading carries agent text. The fixed part of a persona is the hat discipline (S1), and the readers and `quickLook` consume this file. Control characters are refused in `room_sources` only.
**Fix:** Refuse `[\u0000-\u001f\u007f]` in `focus`, in every `hat_questions` item and in every `must_not_judge` item, with `schema_invalid:<key>`. Refuse a leading `#` in those fields as well.

### WR-07: quickLook reads any path on disk; the MCP analyze-perspectives action returns it

**File:** `lib/core/persona-ops.cjs:1020`, `lib/mcp/tool-router.cjs:1304`
**Issue:** `quickLook` does `safeReadFile(path.resolve(artifactPath))` with no containment check. The MCP `room_content` / `analyze-perspectives` action passes the caller's `artifact` value straight through and returns the file text in `artifact`. A Desktop or Cowork caller can read `~/.ssh/...`, another room, or `~/.mindrian/persona-hats/runs/*.json`. The old `invokePersona` has the same pattern. This phase copied it into a new function and a newly routed surface, instead of using the door's own `roomFile` check.
**Fix:** Resolve the artifact against the room and require it inside the room by realpath, as `roomFile` in the door does. Otherwise return `artifact: null` with a reason. Apply the same fix to `invokePersona`.

### WR-08: Sync subcommands can throw past the router; "a refusal is data" breaks and a stack trace is printed

**File:** `scripts/persona-hats.cjs:470`, `scripts/persona-hats.cjs:619`, `scripts/persona-hats.cjs:760`, `scripts/persona-hats.cjs:1850`, `scripts/persona-hats.cjs:3909`, `lib/core/persona-ops.cjs:974`
**Issue:** The following calls can throw outside any `try`: `fs.readFileSync(checked.targetAbs)` in `cmdStart`, `writeLedger` in `cmdWritePersona`, `cmdAcceptPersona` and `cmdCheck`, and the post-rename `fs.readdirSync(personasDir)` in `writeReasonedPersona`. `main` does not wrap sync results. A disk error then gives an uncaught exception with exit code 1 and a stack trace. The trace holds the room path and the review folder name, which carries the slug of the governing question (room text). This breaks the documented contract (one JSON object, exit 0 for a refusal, exit 2 for usage). The command prose maps only `{ok:false, reason}`.
**Fix:** Wrap each `writeLedger` like the other subcommands do (`write_failed:<code>`). Move the target hash into the `try` of `cmdStart`. Wrap the dispatch in `main` in `try { ... } catch (e) { result = { ok: false, reason: 'internal_error:' + (e && e.code || 'error') }; }`, and print no message text.

### WR-09: Room-wide stores are read-modify-write with no lock (Cowork concurrency)

**File:** `scripts/persona-hats.cjs:2823-2870`, `scripts/persona-hats.cjs:1247-1257`
**Issue:** `cmdRecordRuling` reads `tension-rulings.json`, edits a copy and renames it over the file. `writeHandlesStore` does the same. Two navigators in one shared Cowork room who rule on two runs at the same time lose one ruling: the last rename wins. The lost tension then comes back as open. Cowork is one of the three required surfaces ("shared room state, concurrent access").
**Fix:** Take an exclusive lock file (`fs.openSync(lock, 'wx')` with retry and a stale-lock age) around read, edit and rename. Alternatively, re-read the store just before the rename and merge per key. Add a leg with two interleaved writers.

### WR-10: The brief target may point into `personas/`; the reading-list check is lexical

### WR-11: check does not refuse a merged run
