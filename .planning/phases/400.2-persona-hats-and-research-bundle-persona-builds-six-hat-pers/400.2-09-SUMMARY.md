## What record-ruling does (as built)

- Answer file (by path only): `{schema: "mos.persona-ruling-answer/1", run_id, rulings: [{tension_id, ruling, reason?, reopen?}]}`; closed keys; 1 to 75 entries; ruling is side_a, side_b, both_hold or defer; reason 280 characters at most; a tension id twice is refused.
- Order of refusals, all before any write: room, ledger, mode deep, `step_out_of_order:merge`, answer file, schema, `tension_not_in_run`, `tension_already_settled` (a settled tension needs `reopen: true`), `rulings_store_invalid`.
- side_a is `pair[0]` of the sorted pair and side_b is `pair[1]`; the output field `recorded[].side_hat` names the hat (null for both_hold). The store holds the sorted pair.
- A stored ruling writes the store entry `{ruling, reason, ruled_at, run_id, sub_question_text, pair, lines}` through a temporary file and a rename. A defer writes `ruling: defer` into the run record tension and keeps its state `open`. `reopen: true` removes the key and puts the tension back to `open` in the run record.
- The ledger is written, then one `decision_captured` event is logged for each stored ruling through `navigation.logMemoryEvent` (room.db opened and closed through `openRoomDbForCaller` and `closeRoomDbForCaller`, required lazily). Payload keys: source, tension_id, ruling, run_id, sub_question_id, pair, dedupe_key. No reason and no line text. With no room.db that opens, the output says `memory_event: {state: "not_logged", reason: "no_room_db"}` and the ruling stays stored.
- Output: `ok, run_id, recorded, deferred, reopened, memory_event, remaining_open`. The step `record_ruling` is marked done; a second call for other tensions of the same run is allowed.
- Merge: reads the store before any write; each tension whose id is in the store gets state settled, the stored ruling, its date and the stored lines. The artifact prints `settled on <date>: <ruling>` and one `stored <hat>: <line>` line for each hat of the pair, between the new position lines and `state:`. The merge output adds `open` and `settled` lists (the `tensions` list stays).

## Deviations from Plan

1. [Process] The ruling answer file is written to a `mktemp -d` directory, not the inbox. The inbox sits in the scratch tree, and merge deletes the scratch tree, so the inbox is gone when Stop 4 runs (found at the first test run: ENOENT). Step 9 of the command and the tests say so.
2. [Rule 2 - correctness] A corrupt or malformed rulings store makes merge return `{ok: false, reason: "rulings_store_invalid"}` before any write. Reading it as empty would bring a settled tension back by accident.
3. [Rule 2 - correctness] `tension_already_settled` refuses a ruling on a settled tension without `reopen: true`, so only the navigator's reopen changes a stored ruling (T-4002-41). Not in the plan list; covered by G11.
