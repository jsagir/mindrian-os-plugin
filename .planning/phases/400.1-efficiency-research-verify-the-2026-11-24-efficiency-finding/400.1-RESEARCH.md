## Summary

The study's main numbers hold, and the host transcripts settle four of its open checks. The host writes the real API request shape (`api-request-shape` records) into each session transcript under `~/.claude/projects/`. This research read those records (read only) for the owner's sessions on Claude Code 2.1.325 and 2.1.326. That gives host-side proof instead of estimates: the main-thread Larry agent does NOT preload its 4 skills (K1), all 73 to 76 mindrian-os tools load up front in the CLI and in the Desktop Code tab (K2, L-DC1), mixed hook stdout is read as plain text (K3), and an unscoped `mcp__mindrian-brain__*` name never exists as a tool (K6).

Three new defects came out of the transcripts. (1) The host closes YAML frontmatter at the FIRST `---` it finds, and 253 of 256 plugin markdown files carry a `# --- Phase ...` comment line inside their frontmatter. Every key after that line is not parsed and is injected as body text: 165,546 B of frontmatter leaks into skill, command and agent bodies, and `allowed-tools` is dead in 109 files (55 commands, 54 skills). (2) check-card-fire sends `continue:false` with `decision:"block"`; the doc rule makes `continue:false` win, so 88 of 99 blocks in 30 days ended the turn with "Re-rendering your choices as a selectable card..." and no card. (3) The session-start hook context is 8,825 characters against the host cap of 10,000 characters per hook output; a larger room will cross the cap and the host then keeps only a 2,000-character preview.

Theo coverage is as the study said: 30 of 38 registry frameworks have steps (169 steps), 1 is active, 29 are draft. A raw `framework_step` answer is 29 KB on average (about 7.3k tokens); a 7-field whitelist keeps 22 percent (192,112 of 873,930 B). Only 2 frameworks mark any step optional, so a "quick versus deep" branch cannot come from Theo marks.

**Primary recommendation:** Plan 401 to fix the frontmatter split first (it changes what every later size number means), plan 402 to fix the card-fire `continue:false` envelope before any rate tuning, and keep the 402 alwaysLoad change gated on the owner steps for Desktop chat and Cowork.

## K3: hook stdout with a JSON line plus a plain line

**Verdict: PROVEN. The host reads the whole stdout as plain text. The JSON is injected as raw escaped text and `systemMessage` is never shown.**

- Doc rule (CITED, https://code.claude.com/docs/en/hooks, "Exit code 0"): stdout counts as JSON "only when you print one JSON object, on one line or several, with nothing around it but whitespace"; "Output that doesn't start with `{`, or that starts with `{` and doesn't end with `}`: plain text". For UserPromptSubmit and SessionStart, plain text is added as context.
- Local reproduction (PROVEN): scripts/intent-classifier.cjs on an unbound session printed `{"hookSpecificOutput":{...binding card...},"systemMessage":"session unbound: choose which room(s) this session writes to"}` then `\n` then the voice reminder line (1,432 B). The order comes from `main()` then `emitVoiceReminder()` (scripts/intent-classifier.cjs:3696-3720).
- Host record (PROVEN): owner transcripts 6d4d4493 (2.1.312) and 1ab40b09 record this output as `hook_success` with `content` equal to the raw string, JSON envelope included. Those sessions have `hook_system_message` records for SessionStart (pure JSON there) and none for the UserPromptSubmit binding card.
- Effect: the model reads `\n` escapes and JSON keys instead of the card text; the navigator never sees "session unbound". The same mixing happens whenever the nav block or the `[NAV DECISION unchanged]` marker follows a JSON envelope (seen in both transcripts).
- Fix shape for 402: put the reminder and nav text inside `additionalContext` of the one JSON object, or print plain text only. Do not print two objects (the doc calls that a parse failure when one sets a field).

## K4: card-fire false-block rate

**Verdict: rate and mechanism PROVEN; fork classification MEDIUM (heuristic).**

Sources:
- ~/.mindrian/card-fire-intercepts.log (read only): 7 records, 2026-11-19 to 2026-11-20, all `reached-registry-gate-no-card`, all from `scripts/intent-classifier.cjs`, 5 with an empty `gate_signature`. By hand: 1 has a real prose fork ("send now ... or have me re-cut the ending first"), 1 ends on an open question, 5 have no fork. The log is too small for a rate. PROVEN.
- Owner transcripts, 30 days, 100 top-level sessions: 99 card-fire blocks in 59 sessions (each block shows as `hook_blocking_error` + `hook_system_message` "Re-rendering your choices as a selectable card..." + `hook_stopped_continuation`). PROVEN. The study's "699 blocks in 30 days" does not match this source; its origin is unknown.
- Classification of the last assistant text before each block (regex, last 220 characters): 51 fork-likely (8 with a literal "Your call:" line), 33 open question only, 15 no fork. So 48 of 99 (48 percent) are blocks on a turn with no fork. MEDIUM: a heuristic on a text tail. Rows: scratch file cardfire-30d.jsonl.

Mechanism defect (PROVEN, more important than the rate):
- scripts/check-card-fire.cjs builds `{ decision:'block', reason, systemMessage, continue:false }` (:869-876). The doc says `continue: false` means "Claude stops processing entirely" and the common fields "take precedence" (CITED, https://code.claude.com/docs/en/hooks, JSON output table and "Exit code 2" note). `decision:"block"` alone "prevents Claude from stopping" (Stop decision control).
- Host record: after 88 of 99 blocks there is no assistant turn before the next real user prompt; 9 had an AskUserQuestion call and 2 a text turn. The record order is `hook_stopped_continuation` then a meta user line "Stop hook feedback: rendering your choices as a selectable card" then the session waits.
- Effect: the block never forces the card it promises. The navigator sees "Re-rendering your choices as a selectable card..." and no card. The study's "each block forces one more model turn" is wrong: the cost is a broken promise on screen, not a model turn.
- For 402: drop `continue:false` (keep `decision:"block"` plus `reason`, or use Stop `additionalContext`), respect `stop_hook_active`, then measure again. A precise fork label set can come from the existing Jev profile `card_fire_replay` (scripts/jev-devtime-client.cjs:481).

## Common Pitfalls

### Pitfall 1: a `# ---` comment inside frontmatter
**What goes wrong:** every key after it becomes body text; `allowed-tools`, a new `omitClaudeMd` or a 400 job-sentence key is silently lost. **How to avoid:** no `---` in comments; add the split test in 401. **Warning sign:** the skill body in a transcript starts with frontmatter text.

### Pitfall 2: per-tool marks under server-level alwaysLoad
**What goes wrong:** server-level `alwaysLoad: true` loads all tools; the `_meta` marks change nothing. **How to avoid:** omit the server key. **Warning sign:** the request shape still has 76 tools up front.

### Pitfall 3: `continue:false` in a Stop block
**What goes wrong:** the turn ends; the promised re-prompt never runs. **How to avoid:** use `decision:"block"` plus `reason`, or Stop `additionalContext`.

### Pitfall 4: mixed hook stdout
**What goes wrong:** JSON is read as text; `systemMessage` is lost. **How to avoid:** print one JSON object only.

### Pitfall 5: trusting the guard for framework_step
**What goes wrong:** an extra key gives `ambiguous`, which proceeds. **How to avoid:** the shim validates the exact payload first.

### Pitfall 6: the doctor MCP row cannot see deferral
**What goes wrong:** lib/core/doctor/mcp-surface-module.cjs counts the whole tools/list; it reports the same number after deferral. **How to avoid:** measure the host request shape in a transcript for the 402 acceptance figure.
