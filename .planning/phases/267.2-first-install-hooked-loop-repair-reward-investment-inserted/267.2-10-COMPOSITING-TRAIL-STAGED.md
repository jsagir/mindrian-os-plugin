## The Six Critical Corrections (267.2-RESEARCH.md)

Research found, before planning locked, that CONTEXT.md's own evidence base was already stale -
two shipped phases (270-11, 267.3) had landed after the 2026-08-27 audit that motivated this phase
and changed what "build" meant here. Each correction below is VERIFIED (source read or executed
command), not asserted.

### C-1: `~/.mindrian-user.md` already had a writer. The "zero writers" premise was stale.

CONTEXT.md's D-05 and the ROADMAP both stated the file had zero writers repo-wide and that a new
home-directory writer was needed. Phase 270-11 had already shipped one:
`lib/mcp/tools/identity.cjs:71-73`'s `USER_MD_PATH()` calling `writeUserMdAtomic(userMdPath, data)`
at line 121. `.planning/REQUIREMENTS.md` MEMOP-08 made it binding: "MECHANISM half only; Phase
267.2 W2 still owns the TRIGGER and must not build a second writer." This reframed W2 from a writer
task into a TRIGGER task - the central architectural pivot of the whole phase.

### C-2: `tests/test-267-1-first-install-hooked-audit.cjs` was ALREADY RED on `main`.

Running it at `main` @ `17a60439` (before any 267.2 edit) threw at its very first assertion (GAP
I-1, line 31): `expected exactly one lib/scripts/hooks source reference to ~/.mindrian-user.md,
found 4`. The three new matches were all inside `lib/mcp/tools/identity.cjs` - Phase 270-11's own
shipment, not a 267.2 regression. Because the file aborts on its first uncaught assertion (Node
throws, exits 1), every leg below GAP I-1 - including the Action-leg pin W0 was scoped to invert -
was UNEXECUTED, not passing, at baseline. This is why Phase 267.2-01 recorded a dedicated
`267.2-BASELINE.md` before touching anything, and why every later "green after my change" claim in
this phase states explicitly which specific legs the green run exercised.

### C-3: `writeUserMdAtomic`'s output broke its only reader.

`buildFrontmatter` (`lib/core/user-md-ops.cjs:392-398`) unconditionally emits ALL SEVEN
`role_blend` axis names, including zero-valued ones (`founder: 0.9, researcher: 0, operator: 0,
investor: 0, mentor: 0, domain_expert: 0, student: 0`). `lib/core/user-archetype.cjs:62-77` read
that file as raw text and regex-scanned it, +2 per archetype on first match - its signal lists
contain `/founder/i` and `/investor/i` (venturist), `/researcher/i` (researcher), `/student/i`
(student), all three of which the axis names above match unconditionally, on every write,
regardless of the actual user. Reproduced empirically in an isolated HOME: a founder writing
`canonical_role: founder` read back as `archetype: "student"` (a three-way tie broken only by
`Object.entries` iteration order, which starts at `student`). This was a pre-existing latent
defect of the shipped `identity_write` tool - Phase 267.2 is what made it FIRE, because no
first-install session had ever written the file before.

### C-4: A five-option greeting card was doubly illegal.

CONTEXT.md's D-02 listed five candidate answers (new project / continuing / curating / first time
/ just talk), read at plan time as five user-facing card options. Two independent ceilings blocked
that reading: (1) `docs/reward-before-investment-rule.md` names "picking from any menu longer than
3 options" as a violation, and `data/first-reward-surfaces.json`'s own `session-start:MODE_ROUTING`
record already convicted the EXISTING three-option routing card on exactly that basis; (2)
`AskUserQuestion` renders at most 4 options per question (cited: anthropics/claude-code issues
#12420, #26183). The corrected reading (ratified in `267.2-DECISIONS.md` D-B): the five items are
the LOCAL CLASSIFIER'S OUTPUT SPACE, not a card design. The greeting is one open free-text
question; local classification of the answer replaces any card.

### C-5: Phase 267.3 had pinned the FIRST_INSTALL prose with anchor literals and a tripwire.

`data/first-reward-surfaces.json` (shipped by Phase 267.3, which completed eight plans after
CONTEXT.md's evidence base was gathered) registered all four `scripts/session-start` prose
branches with anchor literals and a live-substring assertion in
`tests/test-267.3-session-start-declaration.cjs`. Replacing `COLD_START_MENU` (W1's literal scope)
would have broken the `session-start:COLD_START_MENU` anchor unless handled carefully; delivering
a real reward meant the `session-start:FIRST_INSTALL` record had to flip from `--none (diagnostic
surface)` to a truthful `REWARD_TYPES` member. Both were treated as required Phase 267.2 tasks
(D-F: `COLD_START_MENU` stays byte-identical, only FIRST_INSTALL's interpolation changes via a new
`FIRST_INSTALL_HANDOFF` variable; plan 267.2-08 flips the registry record to `instant_brief`).

### C-6: A room-free, already-shipped qualifying reward existed that CONTEXT.md had not considered.

CONTEXT.md's Claude's Discretion assumed the only reward candidates were `domain-insight-sweep`
(needs a `db` handle) and `check-pending-breakthrough` (needs a rooms directory). Both findings
were correct but incomplete: the 30-Second MVA Instant Brief pipeline
(`lib/core/mva-orchestrator.cjs::runPipeline`) is a THIRD path and is not room-coupled - grep for
`roomDir`/`openRoomDb`/`room.db` across the file returns zero matches; all state lives under
`_mvaDir() = path.join(_homeDir(), '.mindrian', 'mva')`. `docs/reward-before-investment-rule.md`
names it explicitly: "The Instant Brief IS a reward." The gap was not a missing mechanism - it was
a mechanism with no hook caller (see the headline finding below). This became the strongest
Part-7 answer to GAP R-1: give `runPipeline` a deterministic caller on the first-install path,
rather than author a new reward mechanism.

## Headline finding: in this repo, the failure mode is almost never a missing mechanism

`267.2-RESEARCH.md`'s "Don't Hand-Roll" section states this as the single most load-bearing
pattern discovered across the whole research pass:

> In this repo the failure mode is almost never a missing mechanism. It is a mechanism with no
> caller.

Three separate, independently-discovered instances in this one phase's research:

1. **`identity_write` had no trigger.** Phase 270-11 shipped a real MCP tool the model COULD call
   to write `~/.mindrian-user.md`, but nothing made it fire deterministically on a first install -
   an MCP tool the model must CHOOSE to call is model-compliance dependent, and a first install may
   have no MCP session at all (`lib/mcp/tools/identity.cjs:25-31`, in its own header).
2. **`runPipeline` had no hook caller.** `lib/core/mva-orchestrator.cjs::runPipeline` was room-free,
   tested, and already had an `instant_brief` legal `REWARD_TYPES` declaration - but grep across
   `hooks/`, `lib/`, `scripts/` found it invoked only from `scripts/mva-run.cjs`, itself invoked
   only from prose command/skill instructions to the model. The sentence WAS classified
   deterministically and the pending state WAS written by the already-shipped `mva-detect.cjs` hook
   - and then nothing rendered it unless the model happened to run a command nobody told it about.
3. **`renderShapeF1`'s `personaContext` seam** "shipped but was never wired by anything in this
   repo until now" (per `commands/ignite.md:178`, cited in research).

The practical consequence for how this phase was planned: search for the mechanism before scoping
a build. All three legs of Phase 267.2 (W0/W1/W2) turned out to be wiring problems, not missing-
capability problems - which is also why the phase minted a `HOOK-` requirement family: every one of
its three workstreams turns a prose assertion into a wired hook-or-tool call.

## Decision D-D: the architecture call, and the measured number that confirmed it

**The call itself** (`267.2-DECISIONS.md` D-D): the reward is the Instant Brief, fired OUT OF BAND
via a detached, unref-ed child spawn (`scripts/first-install-router.cjs` spawns
`scripts/mva-run.cjs`, stdout redirected to a capture file, parent returns immediately), and
drained on a LATER `UserPromptSubmit` turn as `additionalContext`. `runPipeline` is never called
inline from a hook.

**The design constants that settled it in advance of measurement:**

- `lib/core/mva-dispatcher.cjs`'s header states binding decision B2 (HARD): a **45-second global
  wall-clock budget, 35-second per-agent budget**. `runPipeline` dispatches through it.
- The longest `timeout` value on any entry in the `UserPromptSubmit` chain in `hooks/hooks.json` is
  **3000ms**.

A 45-second design budget cannot fit a 3000ms hook by any margin - this alone ruled out "hook calls
`runPipeline` synchronously" on documented constants, before any measurement.

**The measured number plan 267.2-01 recorded** (per RESEARCH.md's own Open Question 3, confidence
LOW, "measure in Wave 0, do not assume"): three timed runs of `node scripts/mva-run.cjs` under an
isolated `fs.mkdtempSync` HOME (both `HOME` and `USERPROFILE` overridden, `ANTHROPIC_API_KEY` and
`TAVILY_API_KEY` explicitly deleted from the child env - the real fresh-install no-key path):
**4921ms, 3122ms, 5337ms (max 5337ms)**, all exit 0, all wrote the expected state and brief side
files.

**Verdict: max measured 5337ms versus hook ceiling 3000ms - the detached-spawn architecture is
CONFIRMED, not merely argued from constants.** The residual honesty note this measurement carries:
this is the NO-KEY path only; a Brain-reachable run could add real network latency (up to the 35s
per-agent budget), but because the no-key path alone already fails to fit the hook budget by ~2.3x,
a slower Brain-reachable run can only strengthen the same conclusion, not weaken it - so the
no-key measurement alone is sufficient to confirm the architecture without needing to also run the
slower case.

**The honest residual this design accepts:** the reward lands ONE TURN AFTER the sentence that
triggers it, not the same turn. Delivered by machinery instead of a prose promise, but not
same-turn. Recorded explicitly in `267.2-DECISIONS.md` so the phase does not over-claim, and named
again in the phase-closing checkpoint (267.2-10 Task 3) as one of the four judgment calls the
navigator is asked to rule on.

## Decision D-K: the stated Tri-Polar gap

`hooks/hooks.json` fires on Claude Code CLI only. Claude Desktop and Cowork do not run these
hooks - consistent with CLAUDE.md's own Tri-Polar table and this repo's MCP server instructions
("on surfaces without hooks (Claude Desktop, Cowork), YOU run it").

**The call:** ship the classifier (`lib/core/greeting-intent-detector.cjs`) as a pure, exported,
side-effect-free function so ONE implementation can serve both a CLI hook and a future MCP handler.
Ship the CLI hook wiring in this phase. Do NOT ship an MCP-tool counterpart here - it would
materially expand scope (a new tool schema, a new born-wired descriptor, a new `hitl_shape` ruling,
and a Desktop-side test surface this phase has no harness for) for a surface whose gap is already
the pre-existing status quo.

**The stated gap, in the phase's own words:** on Claude Desktop and Cowork the first-install
greeting router is model-invoked, not hook-invoked, and therefore carries the same
model-compliance exposure the original audit scored 2/10. This phase repairs the CLI surface and
leaves the other two named - a deliberate, recorded call, not an oversight. Registered as a
carried-forward item at phase close (see D-N item 4 below) with a named owner: a Tri-Polar
follow-up phase, plausibly alongside the blocked Phase 267 MCP-tool transition.

## The six D-N carried-forward findings (registered, deliberately not fixed this phase)

Each has a named owner and evidence, so none is silently dropped:

1. **`writeUserMdAtomic` does not merge frontmatter, so a second `identity_write` call clobbers.**
   `buildFrontmatter` does `Object.assign(emptyUser(), data)`; only the body below the `---`
   delimiter is preserved, so two `identity_write` calls in one session lose every field the second
   call does not re-supply. Discovered at plan time by source read, not previously recorded by
   270-11, 267.1, or this phase's own research. This phase's hook-side trigger avoids it via
   read-modify-write (D-E); the MCP tool itself is untouched. **Owner:** a follow-up against
   `lib/mcp/tools/identity.cjs`.

2. **`lib/core/user-archetype.cjs`'s `score > maxScore` tie-break silently resolves ties to the
   first-declared archetype.** Not changed by this phase's C-3 fix (D-G scopes the READ surface,
   never touches the tie-break itself). **Owner:** a follow-up against `lib/core/user-archetype.cjs`,
   to be taken together with a persona-selection regression harness.

3. **Portfolio Manager has no frozen `ROLE_BLEND_KEYS` entry.** Considered and explicitly NOT
   minted (D-J) - a five-file, order-sensitive vocabulary extension plus a Canon ratification, out
   of this phase's scope. `investor` remains the closest existing alias. **Owner:** Canon review.

4. **Desktop and Cowork have no hook-side first-install router.** (D-K, detailed above.) **Owner:**
   a Tri-Polar follow-up phase, plausibly alongside the blocked Phase 267 MCP-tool transition.

5. **`check-onboard --write` is itself a model instruction**, so the onboarding state machine's
   advance step depends on model compliance (a fragility item the ROADMAP already names). This
   phase does NOT add a second dependency on it - the router owns its own idempotent one-shot state
   under `~/.mindrian/first-install/` and never re-reads the marker as its sole gate once armed. The
   underlying fragility in `scripts/session-start` is left as-is. **Owner:** a follow-up.

6. **W0's revert is partly superseded by W1's own prose rewrite two waves later.** Plan 267.2-03
   inverts the SEED-021 pin against the navigator's own scope-correction ruling; plan 267.2-08
   rewrites the surrounding FIRST_INSTALL prose entirely two waves later, superseding part of W0's
   literal restored wording (the "Offer three approaches:" string). This is DELIBERATE, not an
   optimization missed - W0 is a navigator-ORDERED scope correction that had to ship as its own
   recorded act against a measured baseline, per the 267.1-06 Task 2 checkpoint. The two edits were
   deliberately not collapsed into one.
