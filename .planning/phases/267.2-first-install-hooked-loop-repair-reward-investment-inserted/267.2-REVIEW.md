# Phase 267.2: Code Review Report

**Reviewed:** 2026-09-03T19:00:00Z
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

This phase wires a real UserPromptSubmit hook (`scripts/first-install-router.cjs`) that
classifies a first-install user's opening sentence locally, fires an out-of-band Instant
Brief, and then seeds/asks for identity data through the pre-existing `writeUserMdAtomic`
path. The state-machine plumbing itself is well-built: the `armed -> routed ->
reward_pending -> reward_delivered -> investment_asked -> done` ladder is genuinely
enforced by the `main()` dispatch (not just documented), the reward-before-investment
ordering (D-L) is real and is proven by `tests/test-267-2-user-md-roundtrip.cjs`'s
per-turn assertion, MEMOP-08 (no second writer for `~/.mindrian-user.md`) holds, and the
`user-archetype.cjs` reader fix (research finding C-3) is correctly scoped to only the one
production caller of `detectArchetype` and correctly narrows its scan to `canonical_role`'s
value plus the prose body, leaving every other frontmatter field (including the always-
zero `role_blend` axes that caused the original bug) out of the scan.

Two real defects change the outcome for a live user, though, both found by tracing the
call chain the router's own prose instructs the model to follow (Canon Part 8 / MEMOP-08
compliance did not extend to checking whether the thing MEMOP-08 protects actually stays
correct once it's called a second time, or whether the router's own state machine
coordinates with the multi-turn `/mos:ignite` flow it fires). A handful of narrower
robustness and code-quality gaps round out the warnings; `scripts/session-start`'s
`COLD_START_MENU` three-branch sharing (the specific regression class this repo has hit
before) was checked directly against the diff and is NOT regressed here.

## Critical Issues

### CR-01: `identity_write` clobbers every previously-written `~/.mindrian-user.md` field the current call does not re-supply, destroying the router's own seed

**File:** `scripts/first-install-router.cjs:679-724` (the caller/prose), root cause in `lib/mcp/tools/identity.cjs:109-122` (out of this review's file list but directly invoked by the reviewed prose)

**Issue:** `_seedIdentityFile()` (first-install-router.cjs:656-673) correctly does a
read-modify-write: `readUserMd()` then `Object.assign({}, existing, delta)` then
`writeUserMdAtomic()`, specifically because (per its own code comment) "`buildFrontmatter`
... does NOT merge with the existing file -- a bare write would clobber every field the
caller does not re-supply." That seed writes `journey_stage: 'ordinary_world'` and
`last_detected_at`.

The very next step this phase wires up, `_buildInvestmentContext()` (first-install-
router.cjs:679-694), instructs the model: "Whatever they answer, call the `identity_write`
MCP tool with it, using ONLY the fields that tool actually accepts: `canonical_role,
journey_stage, problem_type, venture_stage, larry_persona, brain_persona, user_id,
role_blend`." But `identity_write`'s handler (`lib/mcp/tools/identity.cjs:109-122`) builds
`data` from ONLY the fields present in that one call and passes it straight to
`writeUserMdAtomic(userMdPath, data)` with **no `readUserMd()` call at all** -- it is a bare
write, exactly the hazard `_seedIdentityFile`'s own comment names and defends against in
its own write, but the tool it deputizes the model to call for every subsequent identity
update does not defend against it.

Verified empirically (not just read from source):

```
AFTER SEED:                         journey_stage: "ordinary_world", last_detected_at: "2026-09-03T..."
AFTER identity_write-style bare write: journey_stage: null,            last_detected_at: null
```

A single `identity_write` call with only `{canonical_role, role_blend}` -- exactly what the
router's own prose instructs the model to send -- silently resets `journey_stage`,
`last_detected_at`, `user_id`, `larry_persona`, `brain_persona`, `detection_confidence`,
and `consecutive_signal_count` back to their empty defaults. This directly contradicts
`identity_write`'s own tool description ("Records durable, cross-room facts... into ONE
home-directory file every room reads") and defeats the router's carefully-designed seed
the moment the model follows the router's own instructions.

**Fix:** Make `identity_write`'s handler do the same read-modify-write
`_seedIdentityFile()` already does:

```js
// lib/mcp/tools/identity.cjs
const { readUserMd, writeUserMdAtomic } = require('../../core/user-md-ops.cjs');
...
const userMdPath = USER_MD_PATH();
try {
  const existing = readUserMd(userMdPath);
  const merged = existing ? Object.assign({}, existing, data) : data;
  writeUserMdAtomic(userMdPath, merged);
} catch (_e) {
  return textResponse({ ok: false, reason: 'write_failed' }, true);
}
```

(`role_blend` needs its own nested merge, mirroring `buildFrontmatter`'s own
`Object.assign(emptyUser().role_blend, data.role_blend)` re-merge, so a partial
`role_blend` supplied to one `identity_write` call does not zero out axes set by an
earlier call.)

### CR-02: The investment ask has no coordination with the in-flight `/mos:ignite` flow it itself triggers, risking a duplicate "who are you" ask mid-birth-gate

**File:** `scripts/first-install-router.cjs:288-317` (`_buildAdditionalContext`), `:679-724` (`_askInvestment`/`_buildInvestmentContext`), cross-referenced against `commands/ignite.md` Gate B1 (Door 1, two-step persona pick)

**Issue:** When `greeting-intent-detector.cjs` scores the opening sentence `new_venture`,
`outcome='ignite'` fires on turn 1 and instructs the model to invoke `/mos:ignite` in that
same turn. `/mos:ignite`'s own Gate B1 Door 1 is itself a multi-turn identity capture: a
two-step `AskUserQuestion` sequence ("Who are you arriving as?" then a role-specific
follow-up), typically consuming 2+ further user turns before B2 (blueprint approve) and B3
(first move) follow.

Independently of whatever the user is doing inside that flow, `scripts/first-
install-router.cjs` is a `UserPromptSubmit` hook that fires and advances its own state
machine on **every** subsequent turn, with no signal read from or written to `/mos:ignite`'s
own gate state (scratchpad birth answers, `room-chooser.cjs`, or any shared marker). Tracing
the state machine: turn 1 = routed, turn 2 = outcome_observed, turn 3 = fire, turns 4..8
(bounded by `DRAIN_MAX_RETRIES = 5`) = drain, and the very next turn after
`reward_delivered` unconditionally calls `_askInvestment`, which seeds the identity file and
injects: "Now make ONE investment ask... Ask what best describes them and where they
currently stand. Whatever they answer, call the `identity_write` MCP tool..."

Given B1's own two-step card plus B2/B3 typically span more than the ~5-8 turns the reward
leg consumes, this investment-ask prose is very likely to land on a turn where the user is
still mid-way through answering `/mos:ignite`'s own persona pick or blueprint approval --
injecting a second, unrelated "who are you" identity ask into the middle of a flow that
already asked (and is using) the same information. Nothing in either surface checks for
this collision.

**Fix:** Before firing `_askInvestment`, check for an in-flight ignite/birth session (e.g.
a fresh `scratchpad-ops.cjs` birth answer for the current session, or a `state.json`
`ignite_in_progress` flag the model is instructed to clear on B3 completion) and, if one is
detected, either defer the investment ask (advance straight to `done` without asking, since
`/mos:ignite`'s own B1 already captured `role_blend`) or fold the ask into `/mos:ignite`'s
own B3 completion instead of injecting a second, competing prompt.

## Warnings

### WR-01: One-shot onboarding-marker gate is not write-failure safe

**File:** `scripts/first-install-router.cjs:213-224` (`_atomicWriteState`), `:748-761`
(`main()` arm block)

**Issue:** `_atomicWriteState` swallows every filesystem error and returns `false`
(`scripts/first-install-router.cjs:221-223`), but `main()` never checks that return value
anywhere it is called, including the very first write on the arm path:

```js
const armedState = { phase: 'armed', armed_at_ms: armedAtMs, schema_version: 1 };
_atomicWriteState(armedState);          // return value ignored
return _classifyAndRoute(armedState, prompt, t0);
```

If `~/.mindrian/first-install/state.json` cannot be created (permissions, a full disk, a
read-only home directory), `state.json` never actually persists. `_readState()` keeps
returning `null` on every subsequent turn, so the "ONE-SHOT GATE" invariant the file's own
header documents ("the onboarding marker is read EXACTLY ONCE, at arm time") breaks down:
`_checkOnboardStatus()` is re-invoked and `_classifyAndRoute` re-fires on every turn for the
rest of the session, including injecting "invoke `/mos:ignite`" prose (outcome=`ignite`)
into any later, unrelated turn whose sentence happens to score `new_venture`.

**Fix:** Check `_atomicWriteState`'s return value at the arm step; on failure, either retry
once against a fallback location or fail the turn closed (`emitEmpty()` without ever
re-checking the marker), rather than silently re-running the one-shot logic every turn.

### WR-02: `_fireReward` trusts a shared, per-turn-overwritable pending record with no correlation to the sentence that triggered the route

**File:** `scripts/first-install-router.cjs:416-490` (`_fireReward`), cross-referenced
against `lib/core/mva-state.cjs` (`writePending`/`readPending`) and `scripts/mva-detect.cjs`

**Issue:** `_fireReward` reads `lib/core/mva-state.cjs`'s session-scoped `pending` record
to decide what sentence to render the Instant Brief for. That record is written
independently by `scripts/mva-detect.cjs` on **every** `UserPromptSubmit` turn (it runs
immediately before this router in the hook chain, per `hooks/hooks.json`'s own ordering
note), guarded only by `isAlreadyRunning()` -- not by "already consumed" or "matches the
sentence that drove this router's routing decision."

The router's own state machine takes at least 2 additional user turns between the routing
decision (turn 1, which reads the triggering sentence) and the fire turn (turn 3, which
reads whatever `pending` currently holds). If the user's turn-2 message is independently
classified as venture-shaped by `mva-detect.cjs`'s own classifier, `pending.sentence_sha256`
is silently overwritten before the fire leg ever reads it, and the "Instant Brief"
delivered on a later turn is generated for the wrong (later, unrelated) sentence. None of
the `tests/test-267-2-pre-room-reward.cjs` or `tests/test-267-2-router-telemetry.cjs`
assertions exercise this: every test seeds `pending` directly and never simulates
`mva-detect.cjs` running concurrently on the intervening turns.

**Fix:** Have the router capture and check the specific `sentence_sha256` it observed at
routing time (already available from `_classifyAndRoute`'s telemetry write) against
`pending.sentence_sha256` at fire time, and treat a mismatch as `skip_reason:
'pending_sentence_mismatch'` rather than silently firing against whatever is currently
pending.

### WR-03: `_seedIdentityFile`'s read-modify-write is silently redirected by an active persona override

**File:** `scripts/first-install-router.cjs:656-673`, cross-referenced against
`lib/core/user-md-ops.cjs:222-253` (`readUserMd`'s override seam) and
`lib/core/persona-override.cjs`

**Issue:** `readUserMd()` checks `persona-override.cjs`'s `getOverride()` *before* even
looking at the `userMdPath` argument (`lib/core/user-md-ops.cjs:235-253`): while an
override is active, `readUserMd(anyPath)` returns a synthetic struct built from the
override, not the real file. `_seedIdentityFile()`'s `existing = readUserMd(userMdPath)`
would therefore merge its `{journey_stage, last_detected_at}` delta onto that synthetic
struct instead of the real `~/.mindrian-user.md`, and the subsequent
`writeUserMdAtomic(userMdPath, merged)` call writes that merged (override-shaped) record
over the real file -- silently resetting every field the override does not carry
(`user_id`, `larry_persona`, `brain_persona`, timestamps, etc.) back to empty defaults.

This is a pre-existing sharp edge in `readUserMd`, not new code in this phase, but this
phase is a new, headless-hook caller into that hazard where nobody is positioned to notice
the divergence.

**Fix:** Either have `_seedIdentityFile()` bypass the override seam (read the file directly
via `fs.readFileSync` + the frontmatter parser, not `readUserMd`), or have `readUserMd`
accept an explicit `{ ignoreOverride: true }` option for callers -- like this one -- that
genuinely need the real on-disk record rather than the display-time override.

### WR-04: `isValidTransition` is dead code, and the comment crediting it with an enforcement guarantee is misleading

**File:** `scripts/first-install-router.cjs:104-118` (definition), `:625` (misleading
comment), `:811` (export)

**Issue:** `isValidTransition(fromPhase, toPhase)` is documented as "Exported so tests...
can drive the machine without spawning the hook as a child process," and a later comment
(line 625) states: "This leg is UNREACHABLE from any earlier phase... PHASES/isValidTransition
enforce that 'reward_delivered' can only be reached via the fire/drain legs plan 267.2-07
shipped." In fact, `isValidTransition` is never called anywhere in the router's own
`main()` dispatch (which uses ad-hoc `if (existingState.phase === '...')` checks instead),
and a repo-wide grep confirms no test file calls it either -- the actual enforcement is real
(by construction of the `if`/`else` chain), but it is not provided by the function the
comment credits.

**Fix:** Either wire `isValidTransition` into `main()`'s dispatch as a defense-in-depth
guard on every phase write (reject an out-of-sequence transition rather than trusting the
`if`/`else` structure alone), or remove the function and the misleading comment reference to
avoid a future reader trusting a guarantee that isn't actually enforced.

## Info

### IN-01: `word_count` feature is computed on the untruncated input, inconsistent with the file's own stated truncation boundary

**File:** `lib/core/greeting-intent-detector.cjs:129-138`

**Issue:** The file's header comment states: "The input is also truncated to the first 2000
characters before any regex runs; `features.char_count` still records the untruncated
length" -- explicitly calling out `char_count` as the one deliberate exception. But
`word_count` (`const words = trimmed.split(/\s+/).filter(Boolean);` at line 130) is also
computed from `trimmed` (derived from the untruncated `text`), not from `truncated`. This
is not a security issue (`split(/\s+/)` has no backtracking risk), but it is undocumented
and inconsistent with the file's own stated contract, which names only `char_count` as
untruncated.

**Fix:** Either compute `word_count` from `truncated` to match every other feature, or add
`word_count` to the header comment's explicit untruncated-fields list.
