# CR-02: investment ask / in-flight /mos:ignite coordination

## What shipped (the part that was genuinely reachable, low risk, no new primitive)

`scripts/first-install-router.cjs`'s `_askInvestment` now calls `_checkIgniteBirthCaptured(state)`
before building the investment-ask prose. That function reads `lib/core/scratchpad-ops.cjs`'s
`birth_gate_answers` journal (the same journal `commands/ignite.md`'s Gate B1 already writes via
`writeScratchpadBirthAnswer` the instant the navigator completes the two-step persona pick,
`commands/ignite.md:160`) and looks for a `gate_id: 'B1'` entry whose `ts` is at or after this
first-install session's own `armed_at_ms` (this router's own `state.json`, set once at arm time).

When such an entry is found, `/mos:ignite`'s own B1 has already captured `role_blend` for this
session, so:

- the investment prose ask ("who are you") is skipped entirely -- `emitEmpty()` instead of
  `emitContinueWithContext(_buildInvestmentContext())`;
- the deterministic identity seed (`journey_stage: 'ordinary_world'`, `last_detected_at`) still
  fires as always, PLUS the `role_blend` B1 already resolved is folded in for free (no model
  round-trip needed for information that is already known);
- the state machine still advances `reward_delivered -> investment_asked -> done` on the normal
  cadence, with `investment_ask_skipped: true` / `investment_ask_skip_reason:
  'ignite_birth_captured'` recorded on `state.json` and in telemetry, so the skip is visible, not
  silent.

This closes the most common real occurrence of the collision the review found: by the time the
reward leg's own turns (armed -> routed -> outcome_observed -> reward_pending -> reward_delivered,
typically 5-8 turns given `DRAIN_MAX_RETRIES = 5`) have elapsed, `/mos:ignite`'s B1 two-step pick
has frequently ALREADY completed, since B1 is the very first thing `/mos:ignite` does after the
router's own prose invokes it. In that case the old code injected a redundant, competing identity
ask into whatever gate (B2 blueprint approve, B3 first move) the user had since moved on to. The
fix now recognizes "we already have this" and stays silent.

No new writer, no new marker file, and no edit to `commands/ignite.md` or the birth-gate machinery
was needed -- `birth_gate_answers` and `armed_at_ms` both already existed for other reasons.

Regression tests: `tests/test-267-2-cr-02-ignite-birth-coordination.cjs` (3 legs: same-session B1
answer suppresses the ask and folds role_blend into the seed; no birth answer at all leaves the
ordinary ask path unchanged; a STALE B1 answer from before this session armed does NOT suppress
the ask, proving the `armed_at_ms` scoping is real, not "any B1 answer ever").

## What did NOT ship (the honest residual)

The fix above only detects a birth that has ALREADY COMPLETED B1 by the time `_askInvestment` runs.
It does **not** close the harder half of the window the review names: the case where the investment
leg lands WHILE `/mos:ignite`'s own two-step `AskUserQuestion` card for B1 is still PENDING (the
user has not yet answered either step). In that window:

- `writeScratchpadBirthAnswer` has not been called yet, so `birth_gate_answers` carries no entry
  for this session at all -- there is nothing on disk to read.
- Claude Code's `UserPromptSubmit` hook contract exposes no signal that an interactive card is
  currently rendered and awaiting an answer. A hook only ever sees a completed turn's prompt text;
  it cannot observe "a card is mid-render, unanswered."
- The review's own second suggested signal -- "a `state.json ignite_in_progress` flag the model is
  instructed to clear on B3 completion" -- does not exist today. Building it would mean editing
  `commands/ignite.md`'s own Gate B1/B2/B3 prose to write (and reliably clear) a NEW marker file at
  the start and end of the birth trace, which is real cross-surface coordination-primitive design:
  it has to survive a crashed/abandoned birth (so it cannot be "clear on success only" -- it needs a
  staleness bound too), it has to be readable from a room-less first-install hook the same way
  `birth_gate_answers` is, and it changes a file (`commands/ignite.md`) this review's own scope
  (`scripts/first-install-router.cjs`) does not otherwise touch. That is deeper architectural work
  than a focused code-review fix pass should responsibly take on in the same sitting as the other
  six findings in this pass, per this task's own instruction not to force a fix that requires
  inventing a new coordination primitive.

So the residual, stated plainly: a first-install user who answers `/mos:ignite`'s B1 persona pick
slowly enough that the reward leg's own investment turn lands BEFORE B1 completes can still see a
second, competing identity prompt land mid-pick. The fix shipped here narrows the window (closes the
common post-B1 case) but does not eliminate it.

## Concrete recommendation for the follow-up

Two independent options, either sufficient on its own; the first is smaller:

1. **Narrow the classifier's `outcome='ignite'` cases the investment leg even fires against.**
   `_askInvestment` already knows `state.outcome` (persisted at routing time). When
   `state.outcome === 'ignite'`, the router already knows it told the model to invoke
   `/mos:ignite` on turn 1 -- meaning EVERY turn from routing onward is, structurally, plausibly
   inside an ignite birth trace, whether or not `birth_gate_answers` has caught up yet. A cheap,
   still-no-new-primitive tightening: when `state.outcome === 'ignite'` AND
   `_checkIgniteBirthCaptured` finds nothing, skip the investment ask unconditionally (advance to
   `done` silently) rather than falling through to the ordinary ask -- since `/mos:ignite`'s own B1
   is *going* to ask the identical question moments later regardless, the router's ask is always
   redundant on this outcome, whether B1 has completed yet or not. This is a narrower, more
   conservative version of the same "we already have this handled elsewhere" reasoning already
   used above, and needs no new file, no new marker, and touches only this same function.
   Estimated risk: low; needs its own test proving the ordinary ask still fires for `outcome !==
   'ignite'` (larry/clarify), where no ignite flow is ever in play.

2. **A real cross-surface coordination primitive**, only if option 1 is judged insufficient: have
   `commands/ignite.md`'s Gate B1 write a small `~/.mindrian/ignite-in-flight.json` marker
   (`{started_at_ms, session_id}`) the moment B1 begins (before firing the first `AskUserQuestion`
   step) and delete it on B3 completion or on an explicit Defer/Reject exit. The router would check
   for a fresh (bounded-staleness, e.g. under 30 minutes) marker before asking. This closes the
   full window, including the still-pending-card case, at the cost of a new writer/marker contract
   that needs its own crash-safety design (a marker that never gets cleared because the session
   ended mid-B1 must not permanently suppress ALL future investment asks) and touches
   `commands/ignite.md` directly. Recommend scoping this as its own follow-up phase or plan, not a
   drive-by addition to a code-review fix pass.

Given the two options, (1) is the recommended next step if the residual is judged worth closing
further before (2)'s larger design is undertaken.
