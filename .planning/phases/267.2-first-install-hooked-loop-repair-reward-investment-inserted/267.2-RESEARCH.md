## Summary

This phase looks like two greenfield builds (a router, a writer). It is not. The single most
important research result is that **both mechanisms this phase was scoped to build already exist
in the repo, shipped by phases that landed after CONTEXT.md's evidence base was gathered** - and
the real work is wiring triggers and resolving three constitutional collisions, not authoring new
machinery.

For **W2 (Investment)**: `~/.mindrian-user.md` is no longer writer-less. Phase 270-11 shipped
`lib/mcp/tools/identity.cjs` (`identity_write`), an MCP tool that calls `writeUserMdAtomic` against
`path.join(os.homedir(), '.mindrian-user.md')` with zero room coupling. Its own header explicitly
hands this phase the remaining half: "Phase 270 ships the caller; Phase 267.2 W2 owns the TRIGGER."
`.planning/REQUIREMENTS.md` MEMOP-08 states the same in binding language: "MECHANISM half only;
Phase 267.2 W2 still owns the TRIGGER **and must not build a second writer**." CONTEXT.md's D-05
premise ("`~/.mindrian-user.md` has zero writers repo-wide today") is stale, and building the new
home-directory writer it describes would violate both Part 7 and an explicit prior-phase constraint.

For **W1 (Reward)**: CONTEXT.md's Claude's Discretion section considered only two reward candidates
(`domain-insight-sweep`, `check-pending-breakthrough`) and correctly found both room-coupled. It
missed a third that is not: the 30-Second MVA **Instant Brief** pipeline
(`lib/core/mva-orchestrator.cjs` -> `runPipeline`), which keeps all state under `~/.mindrian/mva/`,
takes no `roomDir` and opens no `db`. `docs/reward-before-investment-rule.md` names it by name as a
qualifying variable reward ("The Instant Brief IS a reward"). Its detector,
`scripts/mva-detect.cjs`, is **already wired deterministically** on the `UserPromptSubmit` hook
chain and already fires on a first install. The gap is that `runPipeline` is invoked only by
`/mos:mva-brief` or the `mva-pipeline` skill - both model-compliance dependent. So the first
install's reward is half-wired: detection is deterministic, delivery is not.

Three collisions must be resolved at plan time, not discovered at execution time. (1) A five-option
greeting card is doubly illegal: `docs/reward-before-investment-rule.md` names "picking from any
menu longer than 3 options" as a violation of the reward-before-investment rule, and Claude Code's
`AskUserQuestion` renders at most 4 options per question. D-01's own wording ("the user's free-text
response to Larry's light greeting question") already points at the legal shape - one sentence of
free text, classified locally - and the planner should follow D-01's wording over D-02's five-answer
framing. (2) `writeUserMdAtomic`'s frontmatter always emits all seven `role_blend` axis names, and
`lib/core/user-archetype.cjs:64` reads `~/.mindrian-user.md` as raw regex-scanned text; empirically
reproduced this session, that produces a three-way archetype tie on every write. (3) Phase 267.3
(shipped after CONTEXT.md was written) registered all four `scripts/session-start` prose branches in
`data/first-reward-surfaces.json` with grep-able anchor literals and a tripwire test; rewriting the
FIRST_INSTALL payload reds `tests/test-267.3-session-start-declaration.cjs` unless the registry is
updated in the same change.

Also verified: `tests/test-267-1-first-install-hooked-audit.cjs` is **already RED on `main`** (its
GAP I-1 leg counts 4 references where it asserts 1, because Phase 270-11 added three). W0 is
therefore not a clean two-part revert against a green baseline; the planner must measure the
baseline first.

**Primary recommendation:** Make W1's reward the existing pre-room Instant Brief pipeline delivered
by a new deterministic `UserPromptSubmit` hook (mirroring `scripts/intent-classifier.cjs`'s shipped
hook shape), make W1's classifier a new `lib/core/` sibling of `dual-path-detector.cjs` with zero
Brain calls in MVP, and make W2 a trigger that calls the already-shipped `identity_write` path
rather than a second writer. Do not put the router's behaviour in `scripts/session-start` prose.

### C-3: `writeUserMdAtomic`'s output breaks the only reader of `~/.mindrian-user.md`. [VERIFIED: reproduced empirically this session]

`buildFrontmatter` (`lib/core/user-md-ops.cjs:392-398`) unconditionally emits ALL SEVEN role_blend
axis names, including zero-valued ones:

```yaml
role_blend:
  founder: 0.9
  researcher: 0
  operator: 0
  investor: 0
  mentor: 0
  domain_expert: 0
  student: 0
```

`lib/core/user-archetype.cjs:62-77` reads that file as **raw text** and regex-scans it, +2 per
archetype on first match. Its signal lists contain `/founder/i` and `/investor/i` (venturist),
`/researcher/i` (researcher), and `/student/i` (student) - all three of which the axis names above
match unconditionally, on every write, regardless of the actual user.

Reproduced in an isolated `HOME`:
```
detectArchetype -> {"archetype":"student","confidence":"medium",
  "signals":["USER.md:student:student","USER.md:researcher:researcher","USER.md:venturist:founder", ...]}
```
The three-way tie is broken only by `Object.entries` iteration order, which starts at `student`
(`ARCHETYPES` is declared student -> researcher -> venturist at lines 16-47). A founder writing
`canonical_role: founder` is detected as a **student**.

Note this is a pre-existing latent defect of `identity_write`, not something this phase introduces -
but this phase is what makes it fire, because before W2 no first-install session ever wrote the
file. `identity.cjs:8-13` states the opposite belief in its own header ("it does not care which
exact field this tool populates as long as an identifying word lands somewhere in the file"), which
is true for the positive case and wrong for the false-positive case.

**Planner action:** W2 needs a task that makes the write and the read agree. Cheapest honest fixes,
in Part-7 order: (a) have the writer append a prose body line under the frontmatter (e.g.
`# USER.md\n\nRole: founder`) that the regex scan can key on - the writer already preserves a body,
so this costs nothing structurally; or (b) scope `user-archetype.cjs`'s USER.md scan to the body
below the frontmatter, or to `canonical_role`'s value specifically. Option (b) is the real fix but
touches a shared reader; option (a) is contained. Either way it needs a test, and it is a genuine
W2 sub-requirement, not a nice-to-have - shipping W2 without it makes archetype detection
systematically wrong for every new user.

### C-4: A five-option greeting card is doubly illegal. [VERIFIED: rule doc + Claude Code issue tracker]

D-02 lists five answers (new project / continuing / curating / first time / just talk). Two
independent ceilings block rendering that as one card:

1. **`docs/reward-before-investment-rule.md`, "What counts as user input beyond one sentence"**
   lists as a **violation**: "Picking from any menu longer than 3 options". And as a
   **non-violation**: "Typing one sentence about the venture" / "Pressing a single number to pick
   from 3 options". A five-option pick before any reward is exactly the ordering the rule exists to
   prevent - and `data/first-reward-surfaces.json`'s own `session-start:MODE_ROUTING` record already
   convicts the existing three-option routing card on that basis ("it asks the user to pick an entry
   mode before anything is handed back, which is investment before reward").
2. **`AskUserQuestion` supports 2-4 options per question** (max 4 questions per call). More than 4
   falls back to text input. [CITED: anthropics/claude-code issues #12420, #26183]

**These are not in tension with D-01 - they confirm it.** D-01's own wording is "the user's
**free-text response** to Larry's light greeting question ... is classified locally first." A single
open question answered in one sentence is a rule non-violation, has no option cap, and is precisely
what a `dual-path-detector`-shaped classifier consumes. D-02's five items are best read as the five
**intent buckets the classifier outputs**, not five options the user picks from.

**Planner action:** Design the greeting as ONE open question + local classification of the free-text
answer. If a card is wanted anywhere, it belongs AFTER the first reward lands, and it must carry at
most 3-4 options. Record this reading explicitly in `267.2-DECISIONS.md` so it is not re-litigated.

### Pattern 1: The local additive-score classifier (D-01's named precedent)

**What:** A pure function over a text string returning `{ path, score, features }`. Features are
scalars and booleans only - never matched substrings - so the output is safe to carry in telemetry
under Canon Part 8.

**When to use:** Any turn-1 intent decision that must be deterministic, sub-millisecond, and
egress-free.

**The actual shape** (`lib/core/dual-path-detector.cjs`, read in full):

```js
// Source: lib/core/dual-path-detector.cjs (in-repo, Phase 115-02)
const SECTION_HEADER  = /^(Education|Experience|Summary|...)\b/im;
const DOMAIN_MARKER   = /(IRB#?\s*\d|NCT\d{8}|NIH\b|\$[\d.]+[MBK]\b|ARR|Series\s*[A-Z]\b|runway|...)/i;
const STUCK_LANGUAGE  = /(I'?m stuck|I can'?t|I don'?t know|I'?m trying to|help me think|I keep)/i;

function classify(text) {
  if (!text || typeof text !== 'string') return { path: 'ambiguous', score: 0, features: {} };
  const words = text.trim().split(/\s+/).filter(Boolean);
  const wc = words.length;
  const density = wc > 0 ? (text.match(/\n/g) || []).length / wc : 0;

  let score = 0;
  const features = { word_count: wc, newline_density: density,
                     section_header: false, domain_marker: false, stuck_language: false };

  if (wc < 80) score -= 2;            else if (wc > 300) score += 2;      // F1
  if (density > 0.10) score += 2;     else if (density < 0.05) score -= 1; // F2
  if ((features.section_header = SECTION_HEADER.test(text))) score += 3;   // F3
  if ((features.domain_marker  = DOMAIN_MARKER.test(text)))  score += 2;   // F4
  if ((features.stuck_language = STUCK_LANGUAGE.test(text))) score -= 3;   // F5 NEGATIVE

  let path;
  if (score >= 3) path = 'upload'; else if (score <= -3) path = 'type'; else path = 'ambiguous';
  return { path, score, features };
}
module.exports = { classify, SECTION_HEADER, DOMAIN_MARKER, STUCK_LANGUAGE };
```

**Five properties the new classifier should inherit, and one it must not:**

1. **Single symmetric axis with two thresholds.** `dual-path-detector` is a 3-way split produced by
   ONE score and two cut points (`>= +3` / `<= -3` / else). That works because upload-vs-type is
   genuinely one-dimensional.
2. **At least one NEGATIVE-weight feature.** F5 (`STUCK_LANGUAGE`, -3) exists specifically as
   "Pitfall 3 safety net" so a thoughtful 250-word answer containing one domain marker cannot be
   misclassified. Whatever the new buckets are, at least one feature must be able to pull AWAY from
   the aggressive outcome (here: away from firing `/mos:ignite` at someone who just wants to talk).
3. **Regex constants exported.** Testable in isolation, and greppable when they drift.
4. **A named `ambiguous` bucket.** Not a fallback - a first-class outcome that maps to a real
   behaviour (D-02: "clarify-first"). Never force a decision the signal does not support.
5. **Features are scalars/booleans only.** Explicitly so telemetry can carry the payload
   (`dual-path-detector.cjs:19-21`: "NO matched substrings in features. Safe for Phase 121
   trajectory telemetry"). This is what makes the Discretion instrumentation item cheap AND
   Part-8-legal.

**The property it must NOT inherit:** a single score axis cannot cleanly produce FIVE buckets. Two
cut points give three regions; four cut points on one axis would force an artificial ordering of
"new project < curating < continuing < just talk" that does not exist. **Recommended shape:
per-bucket scores** (one accumulator per intent, highest wins, with an explicit margin threshold
below which the answer is `ambiguous`) - i.e. `lib/core/user-archetype.cjs`'s `scores` +
margin-to-confidence structure (lines 154-172) applied to intents instead of archetypes. That
combines both in-repo precedents: `dual-path-detector`'s purity and feature discipline with
`user-archetype`'s multi-class scoring and honest `low` confidence on a thin margin. **Note the
tie-break bug in `user-archetype`'s version** (`score > maxScore` means first-declared wins every
tie silently, which is precisely what produces C-3's wrong answer) - the new classifier must return
`ambiguous` on a tie, not the first-declared bucket.

### Pattern 2: The deterministic `UserPromptSubmit` hook (the shape that beats prose)

**What:** A CJS script wired in `hooks/hooks.json` that reads a JSON payload from stdin, does local
work under a hard millisecond budget, and writes an envelope to stdout that Claude Code injects as
`additionalContext`.

**When to use:** Whenever a behaviour must happen and cannot depend on the model choosing to obey an
instruction. This is the central architectural lever available to W1 and W2.

**Two shipped exemplars, both readable in full:**

- `scripts/intent-classifier.cjs` - 200ms budget, zero dependencies, pure inline helpers, "advisory
  only, never blocks, never exits non-zero on scope mismatch." Its header states the design rules
  verbatim: "No dependencies. CJS only. Inline helpers. Speed beats accuracy."
- `scripts/mva-detect.cjs` - 1500ms budget, 200ms stdin timeout, "Mirrors
  `scripts/auto-explore-drain.cjs` exit-0-on-any-error pattern," and a Part-8 discipline note worth
  copying verbatim: "the raw prompt lives ONLY in the in-memory `prompt` variable for the
  classification call; never written to fs, never logged."

**The envelope contract** (`scripts/check-pending-breakthrough.cjs:48-59`, the cleanest in-repo
example):

```js
// Source: scripts/check-pending-breakthrough.cjs
function emitContinueWithContext(additionalContext) {
  try {
    process.stdout.write(JSON.stringify({
      continue: true,
      hookSpecificOutput: {
        hookEventName: 'SessionStart',   // or 'UserPromptSubmit'
        additionalContext: additionalContext,
      },
    }) + '\n');
  } catch (_e) { /* swallow */ }
  process.exit(0);
}

process.on('uncaughtException', function () {
  try { process.stdout.write(JSON.stringify({ continue: true }) + '\n'); } catch (_e) {}
  process.exit(0);   // the hook NEVER blocks session start
});
```

**The non-negotiable invariant across all three exemplars: the hook never blocks and never exits
non-zero.** Any failure degrades to `{continue: true}` and exit 0.

### Pattern 3: The atomic home-directory write (W2's mechanism, already built)

**What:** `openSync('wx')` on a per-pid + random temp name, `writeSync`, best-effort `fsyncSync`,
`closeSync`, `renameSync`. Atomic on POSIX and Windows-NTFS.

**Documented at** `lib/core/user-md-ops.cjs:412-439` and implemented at `:440-501`. It preserves any
user-authored body below the frontmatter delimiter (lines 444-460), defaulting to `'\n# USER.md\n'`.
The `fsyncSync` is wrapped in try/catch for `ENOTSUP` on tmpfs/overlayfs/Windows ImDisk, with a
stated rationale: "not load-bearing across power loss; persona will re-detect on next session."

`identity.cjs:65-73`'s `USER_MD_PATH()` resolves `os.homedir()` at CALL time, not module-load time,
specifically so an isolated-`HOME` test fixture takes effect (threat T-270-13). **Any new caller must
do the same** - a module-load-time constant silently writes to the developer's real home directory
for the rest of the process. (I hit exactly this while probing; see Pitfall 6.)

### Anti-Patterns to Avoid

- **Asserting behaviour in prose and calling it wired.** This is the entire finding of the 267.1
  audit and the reason this phase exists. A prose instruction is a hope, not a mechanism. Every task
  in this phase should be answerable with "which file executes this?"
- **Building a second `~/.mindrian-user.md` writer.** Explicitly forbidden by MEMOP-08 (C-1).
- **Rendering more than 4 options in an `AskUserQuestion` card, or any menu >3 options before the
  first reward.** (C-4.)
- **Hardcoding a Brain or Theo query shape in the classifier.** D-07 forbids it, and the
  2026-09-01 handoff names a live, verified bug that makes it actively dangerous:
  `brain-client.cjs`'s `brain_query` normalization will silently return `{records: []}` for Theo's
  actual response shape after the flip, with zero error signal. A classifier that silently gets an
  empty result and routes on it is worse than one that never called out at all.
- **Changing FIRST_INSTALL prose without updating `data/first-reward-surfaces.json`.** (C-5.)
- **A single-score classifier forced to produce 5 buckets.** (Pattern 1.)

## Common Pitfalls

### Pitfall 1: Session-start prose gates are documented to get silently skipped

**What goes wrong:** W1's whole design ("Larry-led greeting", "clarifying exchange") assumes Larry
reliably executes an instruction injected at session start. There is direct, filed, reproduced
evidence that he does not.

**Why it happens:** `.planning/debug/intern-qa-week1-bug-sweep.md` Row A:

> Decision-gate card firing - mode-selection gate (`Just Talk / Explore+Capture / Build a Room`):
> **Skipped entirely at session start on a session-start hook instruction; the usual stop-hook catch
> that fired for 2 OTHER missed gates in the SAME session did not fire for this one.** NEW FAILURE

And Row C: 3 of 4 genuine two-option forks in one session rendered as flat prose, zero caught. The
sharpest characterisation, from Intern-3 in the same file:

> "I fire the card reliably when a command's own skill file explicitly instructs it... but I don't
> fire it reliably on my own organic closings - exactly the failure mode the hook exists to catch,
> and it only caught one of three."

`.planning/debug/intern-w1-card-discipline-decay.md` diagnosed the backstop's own blind spot:
`computeBackstopHit`'s shape gate (`ASCII_BOX_GLYPH_RE`) "never matches free-flowing narrative prose
with no numbered-list/bracket structure at all," so `GATE_FRAMING_RE` is never even reached for
prose-shaped forks. That RCA is `status: diagnosed`, explicitly `Do NOT fix` (diagnose-only session),
and its `next_action` names narrative-prose fork detection as still **out of scope entirely**.

**How to avoid:** put the router's *decision* in a hook (deterministic) and leave only the *verb*
that must be model-executed (invoking `/mos:ignite`) in prose. Do not design a flow whose correctness
depends on a session-start prose instruction firing a card.

**Warning signs:** any plan task phrased "instruct Larry to..." with no accompanying file that
executes it.

### Pitfall 2: A hook-first design silently skips two of the three surfaces

**What goes wrong:** `hooks/hooks.json` fires on Claude Code CLI. Claude Desktop and Cowork do not
run these hooks. A hook-only router repairs the first-install experience on one surface of three and
leaves the other two exactly as broken as the audit found them.

**Why it happens:** CLAUDE.md's Tri-Polar Design Rule is a strong default, and the MCP-plugin
instructions in this repo's own MCP server description say it out loud: "on surfaces without hooks
(Claude Desktop, Cowork), YOU run it" - i.e. Desktop parity is achieved by making Larry run the loop,
which lands right back in Pitfall 1's territory.

**How to avoid:** put the classifier in `lib/core/` as a pure exported function so ONE
implementation serves the CLI hook and an MCP tool handler. `identity_write` already demonstrates the
MCP half of exactly this split. Then state the residual gap explicitly rather than leaving it
implicit: on Desktop/Cowork the router is model-invoked, and that is a deliberate, named call.

**Warning signs:** a plan where the only new executable file is under `scripts/` and nothing under
`lib/mcp/tools/`.

### Pitfall 3: FIRST_INSTALL is one-shot and its advance step is itself model-compliance dependent

**What goes wrong:** `scripts/check-onboard` returns `FIRST_INSTALL` only while
`~/.mindrian-onboarded` is absent. The marker is written by `check-onboard --write`, which is invoked
**by a prose instruction at the end of the FIRST_INSTALL payload** ("After the onboarding conversation
completes or the user skips, run: bash .../check-onboard --write"). If the model runs it early, the
router never gets its turn. If it never runs it, FIRST_INSTALL fires on every subsequent session.

**Why it happens:** the ROADMAP already names this: "Fragility item: `check-onboard --write` is itself
an LLM instruction, so the onboarding state machine's advance step depends on model compliance."

**How to avoid:** if W1 moves the router to a `UserPromptSubmit` hook, that hook has to decide for
itself whether this is still the first-install turn - and it cannot rely on the marker, because the
model may already have written it. Give the hook its own idempotent one-shot state (the
`mva-state.isAlreadyRunning()` pattern is the in-repo precedent), or have the hook itself own the
marker write. Do not add a second dependency on the model running a bash command.

**Warning signs:** a plan that reads `check-onboard` from a `UserPromptSubmit` hook without asking
what happens when the marker was already written earlier in the same session.

### Pitfall 4: The `gate-is-simple-binary` exemption and the clarify-first branch

**What goes wrong:** D-02's third outcome is "one clarifying exchange before routing." If that
clarifying exchange renders as a 2-option card, `classifyCardFire` may exempt it from the force-fire
requirement entirely.

**Why it happens:** `scripts/check-card-fire.cjs:710-734`. The exemption was originally a bare
`gateLabels.length === 2` cardinality check; the `intern-w1-card-discipline-decay` RCA showed it
swallowed 3 genuine forks. It has since been narrowed to `gateRelevance.isYesNoShapedGate(gateLabels)`
- so a genuine 2-option fork with non-yes/no labels now force-fires correctly. **This one is fixed**;
the risk is only that a clarifying question phrased as yes/no ("Want me to set that up?") falls back
into the exemption and is never enforced.

**How to avoid:** phrase the clarify-first exchange as a named-choice fork, not a yes/no. Or accept
prose for it deliberately and say so.

**Warning signs:** a routing table whose "clarify" branch is a confirmation question.

### Pitfall 5: `/mos:ignite` is not reliably reached even when the user wants it

**What goes wrong:** W1's success case routes the user into `/mos:ignite`. There is a filed defect
where Larry bypasses ignite's front door.

**Why it happens:** `.planning/debug/ignite-frontdoor-bypassed-methodology-overfire.md` - "Larry
bypasses ignite's F.1 front door and over-fires a methodology orchestrator on an explore-invitation."
The RCA is explicit that ignite's own Gate B1 is correctly designed and the failure is upstream
prompt-level routing. `fix_remaining` lists four open items, including a SYSTEMIC sweep for the same
bypass class. Independently, the navigator's own 267.1 observation is that `/mos:ignite` "has never
actually started a session in practice."

**How to avoid:** treat "route to ignite" as an outcome whose success must be MEASURED, not assumed -
which is exactly what the Discretion instrumentation item asks for. Log the bucket AND whether ignite
actually ran. That single data point turns the navigator's empirical-data instruction from a blocking
pre-phase into a byproduct of W1.

**Warning signs:** a plan that treats "routes to `/mos:ignite`" as a terminal success state with no
observation of whether ignite ran.

### Pitfall 6: `os.homedir()` resolved at module load writes to the developer's real home

**What goes wrong:** a test or probe that overrides `HOME` after requiring the module still writes to
the real home directory.

**Why it happens:** this is threat T-270-13, already mitigated in `identity.cjs:65-73` by resolving
the path inside a function. **I reproduced the hazard live in this session** while probing C-3: a
`node -e` call that resolved `process.env.HOME` before the override wrote a real
`~/.mindrian-user.md` on this machine, on a path that had no writer and therefore no file. I removed
it (`rm -f ~/.mindrian-user.md`); the pre-existing state was "file absent," which is restored. Noting
it because a plan task that probes this path can do the same damage less visibly.

**How to avoid:** resolve `os.homedir()` at call time. Run every W2 test under `fs.mkdtempSync` +
`HOME`/`USERPROFILE` override, the way `tests/test-267-1-first-install-hooked-audit.cjs:127-141`
already does for its `check-onboard` reachability leg.

**Warning signs:** `const USER_MD = path.join(os.homedir(), ...)` at module scope.

### Pitfall 7: The 267.1 test file is a shared surface between W0 and W2

**What goes wrong:** W0 inverts the Action-leg pin. W2 closes GAP I-1, which is the same file's FIRST
assertion - the one already failing (C-2). Two plans editing the same test file in different waves
will collide, and because the file aborts on first failure, a green run after W0 proves nothing about
the legs below it.

**How to avoid:** sequence W0 and the GAP I-1 pin repair in the same wave, and measure the baseline
before either.

## Security Domain

`security_enforcement` is not set in `.planning/config.json`, so it is treated as enabled.

### Applicable ASVS categories

| ASVS category | Applies | Standard control in this repo |
|---------------|---------|------------------------------|
| V2 Authentication | no | This phase authenticates nothing. Brain entitlement moved to install/update time (Phase 269) and is out of scope. |
| V3 Session management | no | No sessions are minted or validated here. |
| V4 Access control | no | No multi-user boundary; all state is the local user's own home directory. |
| V5 Input validation | **yes** | The classifier consumes untrusted free text from stdin. Existing controls to reuse: `auditQueryString` (`lib/core/rs-egress-prompts.cjs`) for anything that could egress; `zod` schemas with `.max(120)` bounds on the `identity_write` surface; explicit length guards (`mva-classifier`'s `MIN_LEN 12` / `MAX_LEN 600`); the `candidates.size >= 20` runaway cap in `extractDomains` ("avoid runaway on adversarial text"). Regex features must be anchored/bounded - an unbounded backtracking pattern in a 1500ms hook is a self-inflicted denial of service on session start. |
| V6 Cryptography | **yes (hashing only)** | `crypto.createHash('sha256')` over the user sentence for telemetry keys, exactly as `scripts/mva-detect.cjs` does. Never hand-roll; never store the raw sentence alongside the hash. |
| V12 File handling | **yes** | Atomic write with `openSync('wx')` + `renameSync`, temp-file cleanup on every error path. Already implemented in `writeUserMdAtomic`; do not reimplement. |

### Known threat patterns for this stack

| Pattern | STRIDE | Standard mitigation | Status in-repo |
|---------|--------|---------------------|----------------|
| User content egressing to the Brain (Canon Part 8 breach) | Information disclosure | Local classification, generic handles only; `auditQueryString` throws `ExternalEgressViolation` before a byte leaves the process | Enforced; D-01/D-07 keep the new classifier clear of the wire entirely |
| Raw prompt written to disk via telemetry | Information disclosure | sha256 only; "the raw prompt lives ONLY in the in-memory `prompt` variable" | `scripts/mva-detect.cjs` pattern - copy it verbatim |
| Filesystem path leakage in an error message | Information disclosure | `identity.cjs:122-125` catches and returns `{ok:false, reason:'write_failed'}` without echoing the caught message (threat T-270-30) | Mitigated; any new writer path must do the same |
| Catastrophic regex backtracking on adversarial input inside a hook budget | Denial of service | Bounded quantifiers, length guards before matching, hard ms budget with silent exit-0 | Precedent in `mva-classifier` (length guards) and `intent-classifier` (200ms budget) |
| Hook failure blocking session start | Denial of service | `process.on('uncaughtException')` -> `{continue:true}` + exit 0, on every hook | Universal invariant across all three exemplar hooks |
| Stale temp file from a crashed write | Tampering / integrity | Per-pid + random temp suffix, `'wx'` flag, EEXIST unlink-and-retry | `user-md-ops.cjs:466-483` |
| Model-authored text treated as a trusted command | Tampering | `commands/ignite.md`'s T-204-06 precedent: values passed to side-effecting primitives come only from a resolved pick, never from raw navigator free text | Apply to the router: the classifier's BUCKET routes, the user's raw sentence never becomes a command argument |

**One phase-specific note:** the router necessarily reads the user's first sentence, which on a first
install is likely to be self-descriptive personal information (the prose literally asks for
"name, role, domain"). That raises the stakes on the telemetry design specifically. The instrumentation
the Discretion item asks for must log the BUCKET and outcome, never the sentence - and the classifier's
scalar-only `features` contract is what makes that safe by construction rather than by discipline.

## Open Questions

1. **Should W1's router be a hook, prose, an MCP tool, or all three?**
   - *What we know:* prose alone is documented to fail (Pitfall 1); hooks are CLI-only (Pitfall 2);
     an MCP tool is model-compliance dependent and may have no session on a first install
     (`identity.cjs:26-28`). Only the `/mos:ignite` invocation strictly requires the model.
   - *What's unclear:* whether the phase should ship all three paths now or ship CLI-first with a
     stated Tri-Polar gap.
   - *Recommendation:* pure classifier in `lib/core/` (one implementation), CLI hook as the primary
     wiring, MCP handler if budget allows, and an explicit stated gap otherwise. Make this an
     explicit `267.2-DECISIONS.md` entry rather than an implicit outcome.

2. **How many intent buckets, and what is the routing table?** (Discretion item)
   - *What we know:* D-02 names five answers and three outcomes. A single-axis classifier cannot
     produce five buckets cleanly (Pattern 1). `user-archetype.cjs`'s per-class scoring can, and its
     tie-break bug is a known trap to avoid.
   - *What's unclear:* whether "curating a few" and "continuing" are separable from free text with
     any reliability, or whether they collapse into one "has prior work" bucket that always takes the
     clarify-first path.
   - *Recommendation:* start with 4 buckets (`new` / `prior_work` / `just_talk` / `ambiguous`) mapping
     to 3 outcomes, and let instrumentation (W1d) tell you whether `prior_work` needs splitting. This
     is exactly the empirical-data instruction satisfied inside the phase rather than before it.

3. **Can `runPipeline` fire inside a hook budget?** (see A6)
   - *Recommendation:* measure it in Wave 0. If it cannot, the pattern is a hook that writes pending
     state + emits `additionalContext` telling the model to render, which reintroduces model
     compliance for the render step only - materially better than today but not fully deterministic.
     Say so honestly in the plan rather than claiming a full fix.

4. **Does W2 write before or after the reward?**
   - *What we know:* `docs/reward-before-investment-rule.md` is unambiguous that reward precedes
     investment, and `skills/ignite/SKILL.md:52-54` implements the check ("Before any gate fires,
     check whether this session has already delivered an MVA brief reward"). A USER.md write is an
     investment.
   - *Recommendation:* reward first, always. Sequence W1's reward strictly before W2's ask, and
     test-pin the ordering. This is the one place where getting the order wrong reproduces the exact
     defect the phase exists to fix.

5. **Portfolio Manager: alias or vocabulary extension?** (folded todo item 3)
   - *What we know:* extending `ROLE_BLEND_KEYS` is a five-file, order-sensitive change
     (`f-selector-ranker`, `shallow-doc-parser`, `session-register`, `user-md-ops`,
     `persona-override`) plus Canon ratification. The todo explicitly logs it as a Canon-review
     candidate, not an inline mint.
   - *Recommendation:* out of scope for this phase. Fix `mentor` (already frozen-legal), add the
     coverage test, and carry Portfolio Manager forward as an open Canon question. Do not mint a key.

6. **Is the 267.1 GAP I-1 pin repair W0's or W2's?**
   - *What we know:* it is the same assertion, currently red, and both workstreams have a claim on it
     (Pitfall 7).
   - *Recommendation:* assign it to W0 explicitly (as part of "restore the suite to a known state")
     and have W2 flip it positive. Two edits, one file, sequenced in one wave.
