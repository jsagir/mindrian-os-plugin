<decisions>
## Implementation Decisions

### W1 - Greeting router logic

- **D-01:** The router is **Brain-classified intent, but Part-8-clean by construction**: the
  user's free-text response to Larry's light greeting question ("are we starting a new project /
  continuing / curating a few / first time / just want to talk?") is classified **locally first**
  - the same shape as Phase 115's `lib/core/dual-path-detector.cjs` (a 5-feature additive-score
  classifier, no LLM call required for the classification step itself). If a Brain consult is used
  at all downstream of that classification, it receives only the generic intent bucket / problem-
  type handle - **never the user's raw text**. This was an explicit navigator call after a direct
  question about how "Brain-classified" squares with Part 8 (user content never egresses to
  Brain): local classifier, Brain-shaped signal only, is the answer, not "the model just judges
  inline" and not "send raw text to Brain for classification."
- **D-02:** Router outcomes: some classified intents trigger `/mos:ignite` (new project / curating
  with clear room-building intent), some stay as plain Larry conversation (just talk / ambiguous),
  some need one clarifying exchange before routing (continuing an existing venture - which room?).
  This mirrors the navigator's own framing verbatim from the 267.1 checkpoint ("some cases should
  trigger ignite, some should just be Larry, some should be a conversation that figures out what
  to trigger based on context") - the exact routing table (which of the 5 answers maps to which of
  the 3 outcomes) is left to planning/research, not re-litigated here.
- **D-03 (rejected alternative, recorded so it isn't silently re-proposed):** An "empirical-gated"
  approach - ship telemetry on the current static-menu path first, gather real ignite-vs-plain-
  Larry engagement data, THEN design the router in a follow-up phase - was explicitly considered
  and rejected in favor of building the local-classifier router now. The navigator's own prior
  instruction (267.1 checkpoint) to "get empirical data... before building either fix candidate"
  is not abandoned by this call; it becomes a `Claude's Discretion` item below on HOW to satisfy it
  without a second phase (e.g., instrument the new router itself rather than blocking on a
  telemetry-only pre-phase).

### W2 - Investment leg mechanism

- **D-04:** `~/.mindrian-user.md` gets written **during the FIRST_INSTALL onboarding conversation
  itself**, before any room exists - not deferred until `/mos:ignite`/`/mos:new-project` births a
  room. This directly targets GAP I-1 (the audit's finding that the FIRST session has zero
  investment ask) rather than leaving that specific session type unaddressed.
- **D-05:** This requires a **new home-directory writer** - the existing `writeUserMdAtomic`
  (`lib/core/user-md-ops.cjs:440`) only reaches `roomDir/USER.md` via
  `lib/core/navigation/room-birth.cjs`, which requires a room to exist first. The new writer
  should reuse `writeUserMdAtomic`'s atomic-write pattern (Part 7 reuse-before-build), targeting
  `~/.mindrian-user.md` instead of a room path - not a second, divergent write mechanism.
- **Hard constraint carried forward from 267.1's own audit:** `/mos:profile-user` is referenced by
  USER.md stubs in production rooms and **does not exist**. It must not be adopted as part of this
  mechanism.

### W0 - Revert scope

- **D-06:** Exactly as scoped by the 267.1 checkpoint - the one-line revert in
  `scripts/session-start` (undo commit `f39f24d9`) plus the test-pin inversion in
  `tests/test-267-1-first-install-hooked-audit.cjs`. Nothing else rides with it.

### Theo forward-compatibility (resolves the phase's own standing-rule question)

- **D-07:** This phase's `.planning/ROADMAP.md` entry carries a standing 2026-09-02 navigator rule
  requiring confirmation of whether the reward/investment repair should target the current
  key-gated Brain flow or the post-cutover keyless Theo flow, before research locks. **Resolved
  here, explicitly confirmed by the user:** Phase 269 (already shipped) moved entitlement checking
  to install/update time, so an entitled install already queries methodology with zero per-query
  key friction - the "key-gated first session" concern is largely already closed. What remains is
  narrower: **the router's classifier (D-01) must never call the Brain/Theo backend directly or
  hardcode either backend's specifics.** Any downstream consult goes through the existing shared
  chokepoint (`bin/mindrian-brain-mcp-client.cjs` -> `lib/core/brain-client.cjs`, the exact
  abstraction Phase 257 just hardened) so that Theo's cutover requires zero changes to this
  phase's code - the chokepoint simply starts pointing at a different backend. Research/planning
  should treat this as a hard constraint, not a preference: no Theo-specific query shape gets
  designed now, and no current-Brain-specific query shape gets hardcoded either.

### Claude's Discretion

- Exact routing table for D-02 (which of the 5 greeting-question answers maps to ignite / plain

- Merge behavior when a later room-birth write (`roomDir/USER.md`) meets an earlier home-directory
  write (`~/.mindrian-user.md`) from the same user in the same session - planning's call, informed
