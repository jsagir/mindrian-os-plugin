# Plan 84-09: Self-update script rewrite for versioned-cache model (clone to sibling, preserve .env)

## Goal

Rewrite `scripts/self-update` to stop fighting the versioned-cache model. The current script computes `STAGE="$CACHE_DIR/.update-stage"` where `$CACHE_DIR` is the version-named directory (e.g., `mos/1.10.5/`), then does `mv $CACHE_DIR $OLD_DIR` followed by `mv $STAGE $CACHE_DIR`. The first `mv` takes `.update-stage` with it (because it lives inside `$CACHE_DIR`), so the second `mv` reads a stale path and fails. This was observed live on 2026-04-14 during an attempted v1.10.5 -> v1.10.7 update on the project lead's machine and left the cache in a broken state that required manual recovery.

The rewrite drops the atomic-swap dance entirely: clone the target version into `mos/<new-version>/` as a new sibling directory, never touch the previous version's directory, let the 83-01 statusline-mos wrapper resolve the highest-semver version automatically. Preserve `.env` and user modifications from the previous version via a copy step before the new version is handed off. Closes SCOPE-NB-14.

## Scope

1. Read the current `scripts/self-update` end to end. Catalog every variable and every `mv` / `cp` / `rm` it performs. Confirm the failure mode described in the Goal section matches the code.
2. Rewrite the script as a four-step procedure:
   - **Step A: Clone to external staging.** Create a staging directory OUTSIDE any version dir: `STAGE_DIR=/tmp/mos-update-$$` (the `$$` process id keeps it unique). `git clone <repo-url> "$STAGE_DIR"` then `git -C "$STAGE_DIR" checkout "$TARGET_VERSION_TAG"`. On failure, clean up `$STAGE_DIR` and exit non-zero with a clear error.
   - **Step B: Validate staged copy.** Confirm `$STAGE_DIR/.claude-plugin/plugin.json` exists and reports the expected `$TARGET_VERSION`. Confirm `$STAGE_DIR/scripts/context-monitor` exists. Any validation failure cleans up and exits non-zero.
   - **Step C: Move staged copy to sibling.** Compute `NEW_CACHE_DIR="$CACHE_ROOT/mos/$TARGET_VERSION"`. If `$NEW_CACHE_DIR` already exists, exit non-zero with a "version already installed" message (idempotent no-op). Otherwise: `mv "$STAGE_DIR" "$NEW_CACHE_DIR"`.
   - **Step D: Preserve `.env` and run `npm install`.** Find the previous highest-semver version via the same logic the 83-01 statusline-mos wrapper uses (list semver dirs under `mos/`, `sort -V`, pick the second-highest now that the new version is highest). If that previous version has a `.env`, copy it to `$NEW_CACHE_DIR/.env` via `cp -n` (no-clobber; new version's own `.env`, if any, wins). Then `cd "$NEW_CACHE_DIR" && npm install` (production install, no dev deps).
3. No renaming of the old version. No `mv $CACHE_DIR $OLD_DIR`. No `.old-<pid>` backup directories. The old version stays exactly where it is and the statusline-mos wrapper's `sort -V` picks the new one.
4. Error handling: every step uses `set -euo pipefail`. On failure in Step A/B, `$STAGE_DIR` is `rm -rf`'d. On failure in Step C after the `mv`, the partial new directory is left in place for manual inspection (user-visible, intentional: it is a sibling, not a corrupt cache; the user can retry).
5. Backwards compatibility: keep the existing top-level CLI interface (`scripts/self-update install`, `scripts/self-update check`, and whatever other subcommands exist today). Only the `install` path is rewritten. Inspect the current script first to preserve the rest.
6. Honor a test-only env override `SELF_UPDATE_SOURCE_DIR`: if set, Step A clones from that local filesystem path instead of the git URL. This is what the 84-08 fixture tests use to validate the behavior without a real git operation.
7. Logging: every step emits a single informational line to stderr prefixed with `[self-update]`. No emoji. No em-dashes.
8. Preserve the existing pre-update backup path if one exists today (inspect first). Do NOT remove any working backup behavior; only replace the atomic-swap sequence.

## Risks

- Risk: `git clone` requires network access at update time. Mitigation: unchanged from current behavior; update has always required network. The `SELF_UPDATE_SOURCE_DIR` test override sidesteps this for tests.
- Risk: `/tmp/mos-update-$$` collides with another running self-update on the same machine. Mitigation: `$$` is a unique process id; extremely unlikely to collide. If it does, `mv` to `NEW_CACHE_DIR` will fail cleanly and the user retries.
- Risk: `cp -n` of previous `.env` could leave the new version with stale env vars if the user's env schema has evolved. Mitigation: `.env` migration is a user concern; the script preserves content as-is. CHANGELOG [1.10.8] (plan 84-10) notes the preservation behavior so users know to review.
- Risk: `npm install` in the new version fetches fresh deps and can fail. Mitigation: if `npm install` fails, the new `mos/<version>/` directory still exists without node_modules; the script exits non-zero with a clear message and the user can `cd` in and retry.
- Risk: disk space accumulates from uncollected old versions. Mitigation: out of scope for v1.10.8; document in CHANGELOG that users can `rm -rf` old versions; future plan adds `scripts/self-update gc`.
- Risk: the rewrite itself has bugs. Mitigation: 84-10 (5-gate release) only proceeds after 84-08 cases 17 and 18 pass (spec Risk 8). If this plan has bugs, 84-10 is held until this plan is re-executed.
- Risk: shellcheck warnings on `$$` process id usage or `set -euo pipefail` interactions with existing trap handlers. Mitigation: iterate until shellcheck is clean, or document unavoidable exceptions inline.
