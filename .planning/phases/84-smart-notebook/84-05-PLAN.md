# Plan 84-05: Stakeholder node type in lazygraph-ops plus readGraphFindings bridge wired to both cascade call sites

## Goal

Three tightly coupled pieces in one plan, because splitting them would force two commits touching the same file boundaries:

**Part A: Stakeholder node type in `lib/core/lazygraph-ops.cjs`.** Additive schema extension: new `stakeholders` table with the minimal + metadata JSON blob shape (id UUID, type, name, canonical_ref, notes, metadata JSON, created_at, updated_at), indexes on `type` and `canonical_ref`. New helpers `createStakeholder`, `getStakeholder`, `findStakeholdersByClaim`, `upsertStakeholder`. No new edge types; existing `INFORMS`, `BELONGS_TO`, `CONTRADICTS` are sufficient.

**Part B: The bridge `readGraphFindings(roomDir, sinceTimestamp)` in `lib/core/proactive-intelligence.cjs`.** New function that queries lazygraph for recent edges of type `CONTRADICTS`, `CONVERGES`, `INVALIDATES`, walks to Stakeholder nodes via existing `INFORMS` edges, gathers up to 5 other claims per linked stakeholder, and maps the result into insight records using the EXACT shape `parseAnalyzeOutput()` produces (same field set, same ID derivation). Returns the merged insight array. Wrapped internally in try/catch so any graph failure returns `[]`.

**Part C: Integration at both cascade call sites.** Extend `persistIntelligence(roomDir, analyzeOutput)` in `proactive-intelligence.cjs` to call `readGraphFindings()` after the bash-script parse, merge the two arrays, run existing `shouldSuppress()` dedup, and write the union to `.proactive-intelligence.json`. **Both** call sites in `lib/core/intelligence-cascade.cjs` must be covered: L507 (single-write cascade path) AND L788 (batched-write cascade path). This is reviewer finding I1, not optional.

Closes SCOPE-NB-03, SCOPE-NB-04, SCOPE-NB-05, SCOPE-NB-06, SCOPE-NB-07.

## Scope

### Part A: Stakeholder node type

1. Edit `lib/core/lazygraph-ops.cjs`. In `initSchema()`, add `CREATE TABLE IF NOT EXISTS stakeholders ( id TEXT PRIMARY KEY, type TEXT NOT NULL, name TEXT NOT NULL, canonical_ref TEXT, notes TEXT, metadata TEXT, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL )`. Add `CREATE INDEX IF NOT EXISTS idx_stakeholders_type ON stakeholders(type)` and `CREATE INDEX IF NOT EXISTS idx_stakeholders_canonical_ref ON stakeholders(canonical_ref)`.
2. `type` is a free-form string keyed off `person | org | coalition | role` by convention; no CHECK constraint so v1.11.x can extend without migration.
3. `metadata` holds a JSON string (parsed/stringified at the helper boundary) carrying power/interest/stance hints and any forward-compat fields. Power/interest/stance are NOT columns and are NOT indexed here; they move to edge properties in v1.11.x when Initiative and Claim node types land.
4. Helpers added to the public exports:
   - `createStakeholder({ type, name, canonical_ref, notes, metadata })` returns new `id` (UUID v4 via `crypto.randomUUID()`; no new dep). Insert is idempotent via `INSERT OR IGNORE`, using `(type, canonical_ref)` as the uniqueness key when `canonical_ref` is provided.
   - `getStakeholder(id)` returns the row (with parsed `metadata`) or `null`.
   - `findStakeholdersByClaim(claimId)` returns the array of Stakeholder rows connected to the claim via `INFORMS` edges (walk existing edges table). Caps at 20 rows.
   - `upsertStakeholder(canonical_ref, fields)` finds by `canonical_ref`, updates in place if present, otherwise calls `createStakeholder`. Updates `updated_at`.
5. JSDoc on every new helper. Failure path returns the safe fallback (`null`, `[]`); never throws up.
6. Run `grep -n 'require.*lazygraph-ops' -r lib/ scripts/` to enumerate existing callers (reviewer finding M2). Confirm the new helpers are additive and no existing call site breaks.

### Part B: readGraphFindings bridge

1. Edit `lib/core/proactive-intelligence.cjs`. Add new function `readGraphFindings(roomDir, sinceTimestamp)` that:
   - Opens the room's lazygraph via `room-db.cjs` from 84-02.
   - Queries `edges` table for rows with `type IN ('CONTRADICTS', 'CONVERGES', 'INVALIDATES')` and `created_at > ?` bound to `sinceTimestamp`. Orders by `created_at DESC`, caps at 50 rows.
   - For each edge, resolves both endpoints in the `nodes` table. If either endpoint is a Claim node, calls `findStakeholdersByClaim()` from Part A to find up to 5 other claims authored by the same stakeholder.
   - Maps each edge + stakeholder context into an insight record with the EXACT shape `parseAnalyzeOutput()` produces today. Inspect the existing `parseAnalyzeOutput()` in the same file BEFORE writing, confirm the field set (`type`, optional `subtype`, optional `section`, `confidence`, `message`) and the ID derivation. The graph insight's `id` MUST be computable from `type + section + message` (or whatever the existing derivation is) so `shouldSuppress()` dedup keys align. This is reviewer finding I4, non-negotiable.
   - Returns the array of insights. Returns `[]` on any internal error. Wraps the whole function body in try/catch.
2. Export `readGraphFindings` so the cascade call sites can import it (even though internal to `persistIntelligence()` it is called directly, exporting keeps it testable from 84-08 fixtures).

### Part C: Cascade integration

1. Extend `persistIntelligence(roomDir, analyzeOutput)` (existing in `proactive-intelligence.cjs`). After the existing `parseAnalyzeOutput()` call:
   - Compute `sinceTimestamp` from the previous run's high-water mark (persisted in a small sibling file `.proactive-intelligence.watermark` next to the JSON; create if missing).
   - Call `readGraphFindings(roomDir, sinceTimestamp)` inside a try/catch. On any throw, log to stderr debug and fall through with empty graph insights.
   - Merge graph insights with bash-script insights into a single array.
   - Call the existing `shouldSuppress()` dedup. Because of reviewer finding I4 alignment in Part B, dedup naturally folds graph findings with matching bash findings.
   - Write the union to `.proactive-intelligence.json`.
   - Update `.proactive-intelligence.watermark` with `Date.now()`.
2. Edit `lib/core/intelligence-cascade.cjs`. At BOTH call sites where `persistIntelligence()` is invoked (L507 single-write path AND L788 batched-write path), verify the extended behavior fires. Both sites already call `persistIntelligence()` so the extension is transparent, but the plan MUST include explicit verification of both lines (grep, visual review, and a note added as a comment above each call referencing "graph-bridge: see plan 84-05"). Reviewer finding I1.
3. Error discipline: any failure in readGraphFindings or the merge step leaves the bash-script insights untouched. Cascade never breaks.

## Risks

- Risk: graph query in the hot cascade path degrades write latency. Mitigation: indexed query, caps at 50 edges, wrapped in try/catch with empty-array fallback, Phase 54 batch-queue already rate-limits cascade per room.
- Risk: insight ID mismatch silently breaks `shouldSuppress()` dedup. Mitigation: SCOPE-NB-07 is a hard requirement; 84-08 test case 4 validates dedup on synthetic input that overlaps bash and graph sources.
- Risk: enumerating `require.*lazygraph-ops` callers may surface an existing consumer that breaks on the new exports. Mitigation: helpers are purely additive, no existing export is changed or removed; enumeration is a safety check, not a migration.
- Risk: edge walk from claim to stakeholder produces spurious connections when INFORMS edges point at the wrong endpoint. Mitigation: walk is bounded to 5 other claims per stakeholder and 50 edges total; any spurious insight is then caught by `shouldSuppress()` repeat-count filter.
- Risk: both cascade call sites drift over time and one gets a new `persistIntelligence()` call that does not go through the bridge. Mitigation: the `// graph-bridge` comment is visible evidence; the 84-08 test cases 6 and 7 exercise both paths.

## Deviation Notes

- Revision 1 split the Stakeholder node type and the bridge across two plans. The spec explicitly folds them into one plan (spec Plan chain table, spec line 257) to avoid two commits touching the same file boundaries.
- The L507/L788 comment lines are added here as explicit reviewer-I1 evidence. Revision 1 did not require them.
- `metadata` is stored as a JSON string column, not a JSONB type, because better-sqlite3 does not have JSONB; `json_extract()` works over the TEXT column for forward-compat queries.
