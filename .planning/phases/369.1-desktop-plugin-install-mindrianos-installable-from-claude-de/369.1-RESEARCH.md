## Summary

The measured failure is real, but the npm source is only the first of four walls between our marketplace and Claude Desktop's Customize > Plugins. I read the official docs, the Claude Code 2.1.289 binary, and the Desktop logs on this machine's Windows host (`/mnt/c/Users/jsagi/AppData/Local/Claude/Logs/`), and found that (1) Customize > Plugins is the claude.ai account surface, synced server-side (`[remoteMarketplaceOps]`), not a local Claude Code; (2) claude.ai and Cowork refuse any plugin with a top-level `bin/` directory, and ours ships `bin/mindrian-mcp-server.cjs` and friends; (3) the preferred candidate, the npm `.tgz` as an `archive` source, is refused by the CLI itself ("invalid zip data", reproduced live) because the archive extractor is zip-only; and (4) in Chat, local stdio MCP servers are ignored by design, so "Larry plus room tools" through a plugin is possible in Cowork and the Desktop Code tab, never in plain Chat.

The good news is that the payload already fits the claude.ai limits once `bin/` is gone: 1,997 entries and 33.1 MB unpacked against 5,000 files and 200 MB, with no file above a 30:1 compression ratio. The earlier Desktop failures (July: "too many files (10665, maximum 5000)", then "exceeds maximum uncompressed size of 200MB (515MB)", and the stale upload's "Suspicious compression ratio ... 536:1") were all the old git-repo payload, which Phase 341 already slimmed.

Dependencies cannot travel with the Desktop artifact: with `node_modules` the plugin is 8,187 files (beta.55 dependency set) and, after 369-19 added `next`, 14,978 files and 511 MB of `node_modules` alone, over every ceiling. So the loading path must be the self-install, and the existing self-heal (`lib/core/mcp-dep-heal.cjs`) is close but wrong in two ways: it runs `npm install` with lifecycle scripts enabled (now that `sharp` has an install script, that diverges from the loader's `--ignore-scripts` rule), and when the install cannot finish inside its 15-second connect budget the SDK `require` throws and the server dies with no in-band message. A cold `npm ci` of today's dependency set took 13.3 s on this fast x64 box; a Cowork VM (arm64 here) will be slower.

**Primary recommendation:** Ship the Desktop source as a relative-path entry (`./plugins/mos-desktop`) inside the marketplace repo, built by `release.sh` after Step 6.7 from the exact npm pack payload minus `bin/`, after relocating the five runtime executables from `bin/` to `scripts/` (compat shims stay in `bin/` for the CLI). Make both MCP entry points install with `npm ci --ignore-scripts` and answer in-band while installing. Gate the source choice on a Wave 0 live spike, because whether Desktop tolerates the `npm` entry beside a valid one is not documented.

Why `scripts/`: it is the directory the claude.ai docs name ("Keep executables in another directory, such as `scripts/`, and reference them as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>`") [CITED: claude.com/docs/plugins/org-sync], it already ships in `package.json` `files`, and it sits at the same depth as `bin/`, so `path.resolve(__dirname, '..')` (server line 150, brain client line 73) and every `require('../lib/...')` keep working [VERIFIED: grep of bin/*.cjs]. No name collision exists in `scripts/` [VERIFIED: ls].

### Pattern 1: One payload, two entries
**What:** `mos` keeps the npm source for the CLI (D-02). `mos-desktop` is a relative-path entry whose tree is the npm payload minus `bin/`. Both carry the same `version`; both have manifest name `mos`, so commands namespace as `/mos:*` everywhere.
**Why two entries, not one:** one entry carries exactly one `source` object; there is no alternatives field, and two entries with the same `name` fail validation ("Duplicate plugin name") [CITED: code.claude.com/docs/en/plugins/marketplace-reference].
**Name conflicts on CLI:** if a user also installs the Desktop copy on claude.ai, it reaches Claude Code as `mos@synced` and is shadowed by the marketplace copy. Verified on this machine: `claude plugin list --json` reports `"mos@synced" from claude.ai not loaded - "mos@mindrian-marketplace" on this machine has the same name and takes precedence` [VERIFIED: local run].

### Pattern 2: Derive the Desktop tree from the real pack, never from the working tree
`npm pack --pack-destination <tmp>` then extract `package/`, delete `package/bin/`, copy into `plugins/mos-desktop/` after `git rm -r` of the old tree. The npm `files` allowlist (and the payload ceiling's FORBIDDEN_PREFIXES) therefore governs Desktop too, so no `.planning/`, `tests/` or Brain code can leak (Canon Part 8, RULE 9). Must run after Step 6.7, because the tree must contain the fresh `npm-shrinkwrap.json`.

### Pattern 3: Install-or-answer at the MCP entry
On missing deps: take the existing install lock, run `npm ci --ignore-scripts --no-audit --no-fund` (when `npm-shrinkwrap.json` is present) bounded by the connect budget; if it completes, continue normally; if not, leave a detached install running (holding the lock, its own longer timeout) and serve a dependency-free stdio JSON-RPC responder that answers `initialize`, `tools/list` (one status tool) and `tools/call` with the honest line, then exits when the client disconnects. The next session (a new Cowork task) gets the full server.

### Anti-Patterns to Avoid
- **Using the npm tarball URL as `archive`:** refused by the CLI ("invalid zip data") and the tarball contains `bin/`.
- **Rewriting `bin/` paths at build time inside the Desktop copy:** Desktop would run code no test ran. Move the files in source instead.
- **Building the Desktop tree from the working tree:** bypasses the `files` allowlist; leaks dev files.
- **Blocking `initialize` on a full cold `npm ci`:** the host connect window is about 30 s (CHANGELOG 2.1.242, cited in `lib/core/mcp-dep-heal.cjs` header); a cold install of the current set took 13.3 s on a fast x64 box.
- **`npm install` without `--ignore-scripts` in the heal:** runs `sharp`'s install script (the shrinkwrap marks `node_modules/sharp` `hasInstallScript`), diverging from the loader's rule and pulling native downloads into a VM.

## Answers to the Research Questions

### Q1. The `archive` source schema (documented vs unknown)
- Fields: `url` (must be `https://`, not loopback, link-local or cloud-metadata) and optional `sha256` ("64 hex characters, uppercase or lowercase. When you set it, Claude Code refuses a download that doesn't match"). Type row: "`archive` | `url`, `sha256` | Zip archive over HTTPS. Requires Claude Code v2.1.224 or later." [CITED: code.claude.com/docs/en/plugins/marketplace-reference]
- Wrapper directory: "The plugin root may be at the top of the zip or one directory down." No `strip`/`path` field exists. [CITED: same]. Binary confirms: if the extracted root has one directory containing `.claude-plugin`, it is promoted (`Plugin archive had a wrapper directory; using ... as the plugin root`) [VERIFIED: 2.1.289 binary]. So `package/` would be fine inside a ZIP.
- Formats: zip only. The extractor is a zip reader (`Extracted ZIP to ...`) and an isolated live install of the npm `.tgz` failed with `invalid zip data` [VERIFIED: probe 2026-10-04]. `claude plugin validate` PASSED that manifest, so validation does not catch it.
- Limits: 256 MiB download, 120 s, at most five https redirects; extraction caps 100,000 entries, 512 MiB per file, 1 GiB total, 50:1 ratio [CITED: code.claude.com/docs/en/plugins/host-marketplace].
- Version for archive without a `version`: first 12 hex of the `sha256` pin [CITED: code.claude.com/docs/en/plugins/loading].
- Desktop/claude.ai acceptance of `archive`: NOT documented. Org sync lists only `github`, `url`, `git-subdir`, relative `./` paths [CITED: claude.com/docs/plugins/org-sync]. The INPUT's claim that Desktop accepts archive came from the claude-code-guide agent and is unverified. Settle in the spike.
- Alternative sources per entry: not supported; second entry or second marketplace.

### Q2. Can the CLI and Desktop share one entry?
Only if the entry is not `npm`, which D-02 forbids. The CLI accepts zip `archive`, `github`, `url`, `git-subdir` and relative paths; claude.ai accepts at least `github`, `url`, `git-subdir`, relative paths. Least-surprising shape: `plugins[0]` = `mos` (npm, unchanged), `plugins[1]` = `mos-desktop` (relative path). Keep `mos` at index 0 because four readers hard-code it (Pitfall 3). If the spike shows Desktop rejects the whole marketplace when one entry is `npm`, the fallback is a second Desktop-only marketplace repo, which contradicts the phase goal's `jsagir/mindrian-marketplace` string and needs a navigator ruling.

### Q3. How Desktop and Cowork launch plugin parts
- Customize > Plugins is the claude.ai account surface for "Chat and Cowork"; installs attach to the account and also reach Claude Code as `<name>@synced` [CITED: claude.com/docs/plugins/platform-support, overview].
- Hooks: Chat ignored, Cowork loads, Claude Code loads [CITED: platform-support].
- Local stdio MCP servers: Chat ignored; Cowork "Loads when the Cowork session runs on your computer"; Claude Code loads [CITED: platform-support]. The Desktop app's Code tab is Claude Code [CITED: same, "Claude Code: the terminal, the IDE extensions, and the desktop app's Code tab"].
- `${CLAUDE_PLUGIN_ROOT}`: the claude.ai docs tell authors to reference executables as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>` "from your hooks or MCP server configs" [CITED: org-sync], so it is expanded on those surfaces.
- Where it lands: Windows host `%APPDATA%\Claude\local-agent-mode-sessions\<org>\<account>\rpm\<plugin_id>` and `...\cowork_plugins\marketplaces` [VERIFIED: main.log path lines]; Claude Code terminal `~/.claude/plugins/synced/<bucket>/<name>` [VERIFIED: local disk]. macOS path is the same layout under `~/Library/Application Support/Claude/` [ASSUMED].
- Cowork on this machine runs in a local VM (Windows on ARM: `Claude_2.19675.0.0_arm64` package, VM `memory=4GB`) with Claude Code SDK 2.1.286 installed inside it [VERIFIED: cowork_vm_node.log 2026-10-04]. So Cowork MCP servers run under Claude Code in the VM; whether `node` is on that VM's PATH is not visible in logs [ASSUMED].
- Does the Phase 341 loader run on Desktop? On the Code tab, yes: the Windows-side cache `C:\Users\jsagi\.claude\plugins\cache\mindrian-marketplace\mos\2.0.0-beta.{47,49,51}` each hold `node_modules` (121 entries) [VERIFIED: /mnt/c listing]. ## Common Pitfalls

### Pitfall 1: Trusting `claude plugin validate`
**What goes wrong:** the npm `.tgz` archive manifest validated green and then failed at install ("invalid zip data"). **Why:** "Errors fetching a `source` also appear only after install, not in validation" [CITED: marketplace-reference]. **Avoid:** an install-level test (isolated `CLAUDE_CONFIG_DIR`) and the Desktop spike. **Signal:** a green Step 5 with a red user install.

### Pitfall 2: The generic Desktop error hides the real one
**What goes wrong:** "Marketplace sync failed. Check the repository URL and try again." says nothing. **Avoid:** read `claude.ai-web.log` for `MARKETPLACE_ERROR:REMOTE_SYNC_FAILED ... {"plugins":[{"name":...,"error":...}]}`. Paths: Windows MSIX `%LOCALAPPDATA%\Claude\Logs\` (current on this box), older `%APPDATA%\Claude\logs\`, macOS `~/Library/Logs/Claude/` [VERIFIED: local logs; CITED: anthropics/claude-code#61271]. Today's Oct 4 attempt is not in this box's log (last `addMarketplace` lines are July), so it likely ran on another machine.

### Pitfall 3: Readers that assume `plugins[0]`
`release.sh` Step 4, `scripts/verify-release:70`, `scripts/doctor.cjs` (version-of-record-published, ~line 1048 and line 796), `tests/test-341-marketplace-npm-source.cjs:120,154` all read `plugins[0]` [VERIFIED]. Append the Desktop entry at index 1, and harden readers to `find(p => p.name === 'mos')`.

### Pitfall 4: Desktop tree drifts from the CLI payload
**Avoid:** build only from `npm pack`; a test compares file lists and hashes minus `bin/`.

### Pitfall 5: Rollback leaves a half-written Desktop tree
Every abort path restores only `marketplace.json` today. Extend each restore to the tree, or place Step 6.8 last before Commit A so only its own failure needs handling.

### Pitfall 6: Runtime references still pointing at `bin/`
Hooks (`scripts/session-start:554`, `scripts/post-write:256`, `scripts/compute-opportunity-state:14`), lib runtime (`lib/mcp/daemon-lifecycle.cjs:288`, `lib/core/doctor/mcp-surface-module.cjs:82-83`, `lib/core/doctor/class-m-brain-smoke.cjs:315`, `lib/import/smoke-test.cjs:117`, `scripts/vault-import.cjs:412`), and skill/command instructions (`node bin/mindrian-tools.cjs ...` in skills/room-proactive, persona, vault, room, conversation-mode, setup and commands/room, vault, setup) [VERIFIED: grep, about 40 non-comment lines]. In the Desktop tree these break silently because Cowork runs hooks. Gate: no file in the Desktop tree references `bin/mindrian` or `'bin', 'mindrian`. About 69 test files reference `bin/` paths; the shims let them keep passing, and they can migrate later.

### Pitfall 7: Self-heal runs install scripts
`npm install` without `--ignore-scripts` runs `sharp`'s install script in a Cowork VM. Use `ci --ignore-scripts` whenever the shrinkwrap exists.

### Pitfall 8: Promising Larry's room tools in Chat
Chat ignores local MCP servers by design. Copy, handoff note and verification must say "Cowork or the Code tab"; Chat gets skills and commands.

### Pitfall 9: Verifying the production marketplace before a cut
The Desktop tree only reaches `master` at a release, and beta.56 is held for Theo's write-1 commit. Prove the shape on a probe marketplace built by the same builder; the production check is a post-cut human item.

### Pitfall 10: Payload growth from 369-28
`lib/ui-shell/dist` lands after this research; re-measure the Desktop file count after 369-28 and keep a gate with headroom (for example fail at 4,500).
