## Locked Decisions

D-01 (navigator 2026-10-04, priority): critical, inserted directly after Phase 369; it executes IN PARALLEL with the remaining Phase 369 plans (27-31) on the same working tree. Plans therefore split by file ownership: marketplace-repo work (`~/dev/mindrian-marketplace`, a different git repo) runs any time; plugin-repo files that Phase 369 plans 28-31 also edit (`scripts/release.sh`, `docs/RELEASE-CEREMONY-RULING-SYSTEM.md` RULE 5 and RULE 8 text, `CHANGELOG.md`) are touched only by a plan that declares `depends_on_external: ["369-28"]` and waits for it; everything else must name files no 369 plan names.

D-02 (measured 2026-10-04): the Desktop "Add marketplace" dialog fails on our manifest because Desktop's sync resolves only github / git / git-subdir / relative-path / archive plugin sources, never `npm`; the repo is public and the manifest is reachable on `master` (HTTP 200). The npm source STAYS (the CLI path and RULE 5's version pin depend on it); the fix is a second, Desktop-syncable source for the same plugin version. Research must verify, not assume, which second source Desktop accepts: preferred candidate an `archive` source whose URL is the already-published npm tarball `https://registry.npmjs.org/@mindrian_os/cli/-/cli-<version>.tgz` with a sha256 pin (does Desktop accept a .tgz whose files sit under `package/`?); fallback a GitHub release asset (tgz or zip) on the marketplace repo; last resort a `github` source to a public mirror repo of the built package.

D-03 (release ceremony): any new marketplace.json field is written by `scripts/release.sh` in the RULE 5 lockstep, never by hand, and its presence is checked by the same `--check` gate shape the ceremony already uses; the lockstep count lives only in `docs/RELEASE-CEREMONY-RULING-SYSTEM.md` RULE 5. The marketplace.json `version` pin per cut stays.

D-04 (the bigger question, research first): Phase 341 / RULE 8 ship dependencies as `npm-shrinkwrap.json` inside the tarball and the loader installs them per machine with `npm ci --ignore-scripts`; on the CLI that runs from a hook. Desktop is the hookless surface. Measure on a real Desktop install (or the closest reproducible equivalent, documented as such) whether `bin/mindrian-mcp-server.cjs` and `bin/mindrian-brain-mcp-client.cjs` start with their packages present after a Desktop marketplace install. If they do not, design the Desktop-safe loading path (candidates: the MCP server entry self-checks `node_modules` and runs the install once before registering tools, printing an honest line while it does; or the Desktop archive carries production dependencies within the release payload ceiling). Honest refusal everywhere: a server that cannot load its packages says so in-turn, never a silent partial toolset (CLAUDE.md decision 8).

D-05 (tri-polar): CLI install path unchanged and re-proven (`claude plugin marketplace add` + `claude plugin install mos@mindrian-marketplace` still work from the same manifest); Desktop and Cowork each verified by a real install, recorded with the host build number; a surface that cannot be verified in this session is a human-verification item, never a claimed pass.

D-06 (clean-up): remove the `.next/` directory committed at the marketplace repo's top level (`git ls-tree origin/master` shows `.claude-plugin`, `.next`, `README.md`); add it to that repo's `.gitignore`.

D-07 (interim path, documented not built): until this phase ships, Desktop users add the two MCP servers to `claude_desktop_config.json` by hand (`node <plugin cache>/bin/mindrian-mcp-server.cjs` and `.../bin/mindrian-brain-mcp-client.cjs`; `wsl.exe -e node ...` when Desktop is on Windows and the plugin in WSL). The phase records this in its research and the handoff note for the website, and does not spend a plan on it.

D-08 (Canon Part 8): the install path carries no room content anywhere; nothing in this phase opens a Brain wire.
