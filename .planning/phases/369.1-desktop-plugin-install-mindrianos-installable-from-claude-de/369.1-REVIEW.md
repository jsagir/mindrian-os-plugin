**Reviewed:** 2026-10-04

## Summary

The release-side machinery (builder, prune, desktop-copy gate, ceiling gate, by-name readers, `.mcp.json`, `scripts.mcp`, shims) is mostly sound: `--check` passes on the real tree (2270 files, 43.8 MB, worst ratio 18.2), the two committed lockfiles are already pruned and carry zero `hasInstallScript` entries, the reachability walk handles nested and scoped keys correctly, and the shims keep argv and env identical (the `local-chain-recommender` shim spawns with inherited stdio and exit-status passthrough because the real file uses `require.main`).

The weak half is the runtime self-install. Three defects are serious: (1) the install status file is a predictable, world-writable `/tmp` path that is written through symlinks and whose contents are echoed into model context, (2) a half-installed `node_modules` is trusted by the presence probe whenever the installer died, and (3) `requireWithHeal` still runs a blocking in-process `npm ci` on the connect path and SIGKILLs it at the connect budget, which manufactures exactly the half-installed tree (2) then trusts. Several lesser issues (wrong-directory env precedence, an unfrozen install form that runs lifecycle scripts, retry on every connect, a 120 s SIGKILL inside the "never killed" installer, no responder on the HTTP transport) weaken the decision-8 guarantee. On the release side, abort paths after Step 6.8 do not roll the payload back, and a failed marketplace commit is masked.

## Critical Issues

### CR-01: Install status file is hijackable (predictable /tmp path, symlink-following writes, untrusted content echoed to the model)

**File:** `lib/core/mcp-install-responder.cjs:59-62`, `lib/core/mcp-install-responder.cjs:106,116-118,184-186`, `lib/core/dep-install-detached.cjs:51-59,66-91`
**Issue:** The status file is `os.tmpdir()/mindrian-dep-install-<sha256(root)[0:12]>.json`. On Linux `os.tmpdir()` is `/tmp` (shared, sticky). The name is derivable by any local user (the plugin cache path is predictable). Consequences:
1. Symlink clobber: `writeStatus` writes `file + '.' + process.pid + '.tmp'` and `claim` writes `file + '.' + pid + '.claim'` with plain `fs.writeFileSync` (follows symlinks, no `wx`, no mode). The pid is guessable, so an attacker pre-plants symlinks at the next few pids pointing at any file the victim can write; the installer overwrites it with status JSON.
2. Denial of the self-install: the attacker pre-creates the file as `{"state":"installing","pid":1}`. `installInFlight` (`mcp-dep-heal.cjs:455-461`) sees a live pid with no `finishedAt`, so `startDetachedInstall` never starts an installer; `claim()` in the child sees a "live" owner and exits; the victim cannot `unlink` the attacker-owned file in a sticky dir (EPERM swallowed at `dep-install-detached.cjs:84`). The MCP servers serve "installing, start a new task in a minute" until reboot.
3. Prompt injection: `reason` (line 106) is `String(st.reason)` from the file, unbounded, and is placed into `instructions` on `initialize` (line 184), the tool `description` (line 195) and the tool result (line 210). A planted `{"state":"failed","reason":"<arbitrary text>"}` becomes model-visible instruction text from a server the user trusts.
4. Leak: the file holds the absolute plugin path (home directory and user name) and is created world-readable (0644); the tool text also prints the tmp file path (line 116).
**Fix:**
```js
// status location: a per-user private dir, never the shared tmpdir
function statusFilePath(root) {
  const base = path.join(os.homedir(), '.mindrian', 'run');   // mkdir 0700
  const h = crypto.createHash('sha256').update(path.resolve(String(root))).digest('hex').slice(0, 12);
  return path.join(base, 'dep-install-' + h + '.json');
}
// writes: fs.openSync(tmp, 'wx', 0o600); never follow a pre-existing path
// reads: lstat first; refuse symlinks and files whose st.uid !== process.getuid()
// content: whitelist state in {installing,done,failed,npm-not-found}; reason must match
//          /^(exit-\d{1,3}|timeout|npm-not-found|installer-error|incomplete: [\w@\/., -]{0,80})$/ else 'unknown';
//          do not store pluginRoot, do not print the file path in tool text
```

### CR-02: A half-installed node_modules is trusted whenever the installer died (dead pid, status "installing")

**File:** `lib/core/mcp-dep-heal.cjs:435-442,455-470,514-516,570-573`, `lib/core/dep-install-detached.cjs:104-116`, `scripts/sessionstart-npm-reconcile.cjs:54-62`
**Issue:** The presence probe checks only that each top-level dependency directory exists. The guard added in 369.1-03 only distrusts the tree while an installer is alive (`installInFlight`). If the detached installer is killed (host teardown of the process group or Job Object on Windows, a Cowork VM suspend or teardown, a laptop shutdown, or the SIGKILL in WR-06), `status.state` stays `installing`, the pid is dead, and `node_modules` holds a partial tree with many top-level dirs already present. On the next connect `depsPresent` is true and `installInFlight` is false, so `ensureDepsPresent` returns `{ok:true}` (line 573), the full server starts, and the first deep `require` throws MODULE_NOT_FOUND (the bug_011 failure the probe was written for), with no responder because `ok` was true. The responder itself already recognises this exact state (`installStatusLine` line 121, `isErrorState`), so the knowledge exists but is not used by the probe.
**Fix:** Treat the tree as untrusted unless the last install provably finished.
```js
function treeTrusted(dir, probe) {
  if (!depsPresent(dir, probe)) return false;
  const st = readStatus(dir);
  if (st && st.state === 'installing' && !st.finishedAt) return false;      // dead or alive: not finished
  // npm writes this hidden lockfile as the LAST step of a successful reify
  return fs.existsSync(path.join(dir, 'node_modules', '.package-lock.json'));
}
```
Use `treeTrusted` in `ensureDepsPresent`, `connectPathInstall` and `sessionstart-npm-reconcile.cjs`. When an interrupted install is detected, remove `node_modules` before re-installing so a partial tree can never pass again.

### CR-03: `requireWithHeal` still runs a blocking in-process `npm ci` on the connect path and SIGKILLs it at the connect budget

**File:** `lib/core/mcp-dep-heal.cjs:357-372` (with `286-320`), call sites `scripts/mindrian-mcp-server.cjs:123-124`, `scripts/mindrian-brain-mcp-client.cjs:78-80`
**Issue:** D-14 says the connect path never installs in-process. `requireWithHeal(..., {connectPath:true})` still does: it computes `installOpts = {timeoutMs: remainingMs}` and calls `runGuardedInstall`, which `spawnSync`s `npm ci` with `timeout: remainingMs, killSignal: 'SIGKILL'`. A cold install takes 17-26 s against a budget of at most 15 s, so the install is killed mid-extraction. `npm ci` has already deleted `node_modules`, so the kill leaves a partial tree (the case CR-02 then trusts), and the process throws MODULE_NOT_FOUND and exits inside the host window with no responder. This path is reached precisely when `ensureDepsPresent` returned ok but a require still fails, i.e. in the CR-02 state, so the two defects compound: a partial tree is first trusted, then "healed" by an install that is guaranteed to be killed.
**Fix:** In the `connectPath` branch do not call `runGuardedInstall`. Call `startDetachedInstall(dir)`, wait at most the remaining budget exactly as `connectPathInstall` does, and on failure throw a typed error that the entry points catch and route to `serveInstallingResponder` (stdio) instead of crashing. Keep `runGuardedInstall` for the hook path only.

## Warnings

### WR-01: Install target comes from env, not from where the code lives (wrong-directory install, wipes an unrelated `node_modules`)

**File:** `lib/core/mcp-dep-heal.cjs:250-257`, `scripts/sessionstart-npm-reconcile.cjs:36-39`, vs `scripts/mindrian-mcp-server.cjs:185`
**Issue:** `resolvePluginRoot()` prefers `CLAUDE_PLUGIN_ROOT`, then `MINDRIAN_OS_ROOT`, and only then `__dirname`. `require()` resolves against the real file location, and the servers compute `pluginRoot = path.resolve(__dirname, '..')`. `install.sh:338` writes `MINDRIAN_OS_ROOT` into `~/.claude/settings.json` env for dev clones. On any surface that does not export `CLAUDE_PLUGIN_ROOT` to MCP children (it is substituted in args; export is not guaranteed on Desktop or Cowork), a machine with a dev clone runs `npm ci` in the clone: that deletes the clone's `node_modules` (including dev dependencies), the probe then sees the clone's tree and reports healthy, while the real cache directory stays empty and every require fails forever.
**Fix:** Derive the root from the file: `path.resolve(__dirname, '..', '..')` in `lib/core`. Use env only when it resolves (`fs.realpathSync`) to the same directory, otherwise ignore it and log once.

### WR-02: The unfrozen install form runs lifecycle scripts

**File:** `lib/core/npm-cli-resolve.cjs:176`, `lib/core/mcp-dep-heal.cjs:307-311`, `scripts/sessionstart-npm-reconcile.cjs:101-103`
**Issue:** `frozen` is decided by `fs.existsSync(npm-shrinkwrap.json)`. When it is absent (truncated cache, hand-assembled copy), the fallback is `npm install --no-audit --no-fund --silent` with no `--ignore-scripts`, so every dependency's install and postinstall script runs, contradicting the header claim ("neither do we") and the whole reason sharp was pruned. It also resolves floating ranges, so it is not the same dependency set the release asserted.
**Fix:** Add `--ignore-scripts` to the fallback argv (`['install','--ignore-scripts','--no-audit','--no-fund','--silent']`) in `buildInstallArgs` and in the last-ditch spawn; consider failing with reason `no-lockfile` instead of resolving ranges on a user machine.

### WR-03: A failed install is re-attempted on every connect; a spawn failure is reported as "installing"

**File:** `lib/core/mcp-dep-heal.cjs:484-500,507-527`
**Issue:** After `state:'failed'` (offline, registry error) the next connect finds deps missing, `installInFlight` false (finishedAt set), and spawns another detached `npm ci` (which first wipes `node_modules`). Two servers per session, every session or task, forever, with no backoff or attempt counter. Separately, `startDetachedInstall` returns `started: true` whenever `spawn` does not throw synchronously; with a bad `cwd` or exec error `child.pid` is `undefined` and the async `error` event is swallowed, so the entry waits the whole budget and the responder says "installing, usually under a minute" when nothing is running.
**Fix:** Record `attempts` and `finishedAt` in the status; if the last status is `failed` and younger than N minutes, do not respawn (serve the responder with the stored reason). Treat `typeof child.pid !== 'number'` as `{started:false, reason:'spawn-failed'}`.

### WR-04: A stale "installing" status or recycled pid blocks the self-install permanently

**File:** `lib/core/mcp-dep-heal.cjs:455-470`, `lib/core/dep-install-detached.cjs:40-48,80-83`
**Issue:** In-flight detection is `pidAlive(pid)` with no age bound. After a reboot or long uptime the recorded pid is reused by an unrelated live process; both the status signal and the lock signal then report "in flight" forever, no installer starts, and the connect path serves "installing" indefinitely. `isReclaimable` (age AND dead) in the lock has the same recycled-pid hole, now exposed to the status path too.
**Fix:** Add an age ceiling: treat `installing` as dead when `Date.now() - Date.parse(startedAt) > 150000` (120 s install budget plus slack) regardless of pid, and likewise treat a lock older than `STALE_THRESHOLD_MS` as dead in `installInFlight`.

### WR-05: Status path is hashed from an un-normalised root, so the child and the server can disagree

**File:** `lib/core/mcp-install-responder.cjs:59-62`, `lib/core/dep-install-detached.cjs:96-97`, `lib/core/mcp-dep-heal.cjs:485`
**Issue:** The child hashes `path.resolve(root)`; the server hashes the raw `resolvePluginRoot()` string. A trailing slash, a `..`, or on Windows forward slashes or drive-letter case in `CLAUDE_PLUGIN_ROOT` yields two different files. The server then never sees the child's `failed` or `done` state, `installInFlight` is blind (so every connect spawns another child), and the responder shows "installing" forever.
**Fix:** Normalise inside `statusFilePath`: `crypto.createHash('sha256').update(path.resolve(String(pluginRoot))).digest('hex')`, and use `process.platform === 'win32' ? lower-case : as-is`.

### WR-06: The "never killed" detached installer SIGKILLs npm at 120 s and leaves the partial tree

**File:** `lib/core/dep-install-detached.cjs:104`, `lib/core/mcp-dep-heal.cjs:286-312`
**Issue:** The child calls `runGuardedInstall(pluginRoot)` with the default 120000 ms, which is a `spawnSync` timeout with `killSignal: 'SIGKILL'`. The header and D-14/A12 promise the installer is never killed so a slow Cowork VM can finish. On a slow link the install is killed at 120 s mid-extraction (status `failed: timeout`, partial `node_modules` that CR-02 may trust), and the next connect starts from zero and is killed again, so the install can never complete on exactly the machines the design targets.
**Fix:** Give the detached installer its own larger ceiling (for example 600000 ms) and, on any non-zero outcome or timeout, `fs.rmSync(path.join(root,'node_modules'),{recursive:true,force:true})` before writing `failed`, so no partial tree survives. Keep 120 s only for the hook path.

### WR-07: No in-band answer on the HTTP transport (the Cowork surface)

**File:** `scripts/mindrian-mcp-server.cjs:112-130`
**Issue:** The responder is served only when `!isHttpTransport()`. `surface-detect` returns `http` for Cowork (`/sessions` dir, `COWORK_SESSION_ID`, `CLAUDE_SURFACE=cowork`), and Cowork is the headline surface of the Desktop copy. There, with packages missing, the code logs and falls through to `requireWithHeal`, which (budget spent) rethrows MODULE_NOT_FOUND and the process dies with a stack on stderr. The room tools are then silently absent, a decision-8 violation, while the sibling brain server (`if (true)` branch) does answer. The user sees brain say "installing" and the OS server simply missing.
**Fix:** Serve the responder for both transports when packages are not ready (on http, bind it on the stdio the host opened, or keep the HTTP listener alive with a single status route), or exit with a deliberate non-zero code after writing the status line to stderr in a form the host surfaces.

### WR-08: Release abort paths after Step 6.8 leave a half-written payload or manifest; a failed marketplace commit is masked

**File:** `scripts/release.sh:957-967` (Step 7 race-guard `exit 1`), `scripts/release.sh:971-974`, `scripts/release.sh:905-909,924-936`, `scripts/release.sh:1016,1027,1063`
**Issue:**
1. The Step 7 race-guard abort (line 967) calls neither `mos_rollback_marketplace` nor any plugin rollback, so `plugins/mos-desktop` (staged, up to 2270 files) and the bumped, staged `marketplace.json` stay in the marketplace index. The stated intent is "every abort rolls the payload back with the manifest".
2. Line 974: `git commit ... || echo "Nothing to commit in marketplace"` masks any commit failure (identity, hook, lock). Unlike the plugin repo there is no guard that the marketplace HEAD carries `mos-desktop` at `$NEW_VERSION`, so the run proceeds to `npm publish` and `git push`, and npm ships vN while the Desktop catalog never gets it (lockstep silently broken).
3. Aborts at 1016, 1027 and 1063 occur after the marketplace commit and have no unwind, so the next cut's `mos_rollback_marketplace` restores the committed bytes of the aborted release (`git checkout HEAD`), not the last pushed state.
4. Rollbacks at 907, 926 and 934 restore `plugin.json package.json CHANGELOG.md` but not `npm-shrinkwrap.json`, which Step 6.7 modified and `git add`ed, so the next run starts from a dirty, staged tree and trips the clean-tree gate.
**Fix:** Call `mos_rollback_marketplace "$MARKETPLACE_DIR"` (and `git -C "$PLUGIN_DIR" checkout HEAD -- npm-shrinkwrap.json`) before the `exit 1` at 967 and in the 6.7/6.8 rollbacks. Replace the masked commit with
```bash
git -C "$MARKETPLACE_DIR" commit -m "release: sync to v$NEW_VERSION" || true
node -e "const m=require(process.argv[1]+'/.claude-plugin/marketplace.json');process.exit(m.plugins.some(p=>p.name==='mos-desktop'&&p.version===process.argv[2])?0:1)" "$MARKETPLACE_DIR" "$NEW_VERSION" \
  && git -C "$MARKETPLACE_DIR" diff --quiet HEAD -- plugins/mos-desktop .claude-plugin/marketplace.json \
  || { echo "ABORT: marketplace commit missing mos-desktop"; exit 1; }
```
Also install `trap 'mos_rollback_marketplace "$MARKETPLACE_DIR"' INT TERM` for the window between Step 4 and Step 7 so Ctrl-C during the builder's `rmSync` plus `cpSync` does not leave a half tree.

### WR-09: The prune silently removes hard (non-optional) dependency edges

**File:** `scripts/release-lib/prune-shrinkwrap.cjs:97-107`
**Issue:** Step (1) deletes the named package from `dependencies`, `optionalDependencies`, `peerDependencies` and `peerDependenciesMeta` of every entry alike; only a direct root dependency is refused. If any future dependency lists `sharp` in its `dependencies` (a hard requirement, as several image and embedding libraries do), the prune deletes the edge and the package, `npm ci` succeeds against the edited lockfile, the ceiling gate passes (nothing has an install script), and the plugin fails at runtime with `Cannot find module 'sharp'`. The reachability argument holds only for optional edges.
**Fix:** Cut the name only from `optionalDependencies` and from `peerDependencies` entries whose `peerDependenciesMeta[name].optional === true`. If any entry lists it under `dependencies` or as a non-optional peer, exit 1 naming the entry.
```js
if (entry.dependencies && hasOwn(entry.dependencies, n)) throw new Error(key + ' hard-depends on "' + n + '"; cannot prune');
```

### WR-10: The builder removes whatever `--out` names; its guard is path-lexical only

**File:** `scripts/release-lib/build-desktop-artifact.cjs:242-247,263`
**Issue:** The only guards are: not a filesystem root, not the source, not an ancestor of the source (computed lexically with `path.relative`, no `realpath`). `--out ~/mindrian-marketplace` (a typo that drops `plugins/mos-desktop`), `--out $HOME` with the source elsewhere, or any other unrelated directory is `rmSync(..., {recursive:true, force:true})`ed wholesale, including a `.git` with unpushed commits. The ancestor test also has a hole: `rel.startsWith('..')` is true for a relative path whose first segment is a directory literally named `..foo`.
**Fix:** Require `path.basename(outDir) === 'mos-desktop'` (or a marker file written by the builder inside previously built outputs), refuse when `fs.existsSync(path.join(outDir,'.git'))`, compare real paths (`fs.realpathSync` on the deepest existing ancestor), and test ancestry with `rel === '..' || rel.startsWith('..' + path.sep)` the other way round (`!rel.startsWith('..' + path.sep) && rel !== '..'`).

### WR-11: The Desktop-layout exemption neuters the "PATH bin vanished" doctor check

**File:** `lib/core/doctor/shared.cjs:419-423`
**Issue:** `pathBinVanished` now returns false whenever `.claude-plugin/plugin.json` and `scripts/mindrian-mcp-server.cjs` exist. Every valid install has both, so a CLI or marketplace-cache install whose `bin/` was deleted (the real failure this check detects: the `mindrian-os` PATH entry and the shims are gone) is now reported healthy. The Desktop copy is never the active root the check inspects, so the exemption buys nothing and removes the signal.
**Fix:** Discriminate by identity, not by file presence: exempt only when `path.basename(activeRoot) === 'mos-desktop'` or the real path contains `/plugins/mos-desktop`; otherwise keep `return !fs.existsSync(binPath)`.

## Info

### IN-01: The runtime-bin-ref gate has pattern gaps

**File:** `scripts/release-lib/build-desktop-artifact.cjs:60-73,176-182`
**Issue:** The six patterns miss an unbraced `$CLAUDE_PLUGIN_ROOT/bin/...` (only `${CLAUDE_PLUGIN_ROOT}` is anchored; `\$\{?PLUGIN_ROOT` does not match `$CLAUDE_PLUGIN_ROOT`), `${pluginRoot}/bin/...` and `${root}/bin/...` template forms, `./bin/...` after `node`, and `bin/cli.js`. JS block-comment bodies not starting with `*` are flagged (false positive), and a path split across two lines is missed. Today a grep of the shipped tree finds no violating reference, so this is a latent gap, not a live defect.
**Fix:** Add a catch-all `/(^|[^\w.-])(\.\/)?bin\/(mindrian-|local-chain|cli\.js)/` over non-comment lines of non-test files, keeping the allow-list.

### IN-02: The ratio gate has no headroom and the file gate counts files only

**File:** `scripts/release-lib/build-desktop-artifact.cjs:51-57,153,168`
**Issue:** Files and bytes gate with headroom (4500 of 5000, 180 MB of 200 MB) but the ratio gate is 50 against a limit of 50, measured with Node's `deflateRaw` at level 6; a different zip compressor can score the same file above 50. Directory entries are not counted although the 5000 limit may count them. Current worst ratio is 18.2, so no live risk.
**Fix:** Gate the ratio at about 40 and add the directory count to the file total.

### IN-03: Dead `if (true)` with an unreachable `else` in the brain client

**File:** `scripts/mindrian-brain-mcp-client.cjs:66,80-82`
**Issue:** `if (true) { ... } else { healLog('... the HTTP daemon continues ...') }` is copy-pasted from the OS server; the `else` is unreachable and its message is wrong for this file.
**Fix:** Drop the conditional and the `else` branch.

### IN-04: A remaining `plugins[0]` writer depends on ordering

**File:** `lib/update-bootstrap.sh.template:118-119`
**Issue:** Writes `m.plugins[0].version`. It works only because `release.sh` (line 669) and `mos_write_desktop_entry` keep `mos` first; it is the one reader left that does not find `mos` by name.
**Fix:** `const e = m.plugins.find(p => p && p.name === 'mos'); if (e) e.version = process.argv[2];`

### IN-05: Test seams ship in the runtime path and a build hook bypasses every limit

**File:** `lib/core/npm-cli-resolve.cjs:111-128`, `lib/core/mcp-dep-heal.cjs:218-223`, `scripts/release-lib/desktop-copy-gate.sh:119`
**Issue:** `MINDRIAN_TEST_MODE=1` plus `MINDRIAN_TEST_NPM_CLI` makes the shipped self-install run an arbitrary script as `node <seam>`; `MOS_DESKTOP_BUILD_HOOK` replaces the builder, and with it every limit and the runtime-bin-ref scan, with no loud log during a real cut. Env control is already game over locally, so this is hygiene.
**Fix:** Echo a red line in `release.sh` when either `MOS_*_HOOK` is set outside `MOS_TEST_DRY_RUN=1`.

### IN-06: The prune accepts lockfileVersion 2

**File:** `scripts/release-lib/prune-shrinkwrap.cjs:81-82`
**Issue:** The message says "need lockfileVersion 3" but only `packages` presence is checked. A v2 lockfile also carries a legacy `dependencies` tree that this script does not edit, leaving sharp behind and the file inconsistent.
**Fix:** `if (lock.lockfileVersion !== 3) throw new Error('lockfileVersion 3 required');`

### IN-07: The responder never tells the host when the install finishes

**File:** `lib/core/mcp-install-responder.cjs:143-258`
**Issue:** It declares `listChanged:false` and keeps serving after `done`; the host session never gains the real tools. Acceptable by design ("start a new task"), but a `notifications/tools/list_changed` plus a clean exit on `done` would let hosts that respawn pick the full server up in the same session.
**Fix:** Poll the status on a timer; on `done` send `notifications/tools/list_changed`, then `process.exit(0)`.

### IN-08: Nothing asserts the Desktop copy's version after the cut

**File:** `scripts/verify-release:70`, `scripts/doctor.cjs:1058-1064`
**Issue:** Both readers now find `mos` by name and check only that entry. No check compares `mos-desktop.version` or `plugins/mos-desktop/.claude-plugin/plugin.json` to the released version, so a stale or missing Desktop copy (see WR-08.2) is invisible to `verify-release` and `doctor --acceptance`.
**Fix:** Extend `verify-release` step 3 to read the `mos-desktop` entry and its tree's `plugin.json`, and fail on a mismatch.
