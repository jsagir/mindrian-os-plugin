## Summary

Phase 150.8 ships the v1 slice of SEED-023: typed micro-knowledge claims (knowledge_type x6 + conditions/counter_conditions + temporal validity), a Claimify-style 4-pass extraction in the meeting filing path, a navigator-gated 3-edge taxonomy amendment (REFINES/ROOT_CAUSES/INSTANTIATES), and the any-transcript DIKW trigger invariant with `/mos:build-knowledge` as the Wisdom render.

The single most important architectural finding: **the meeting filing path today is entirely LLM-driven prose** (`commands/file-meeting.md`, no extraction CJS). It writes markdown artifacts to `room/{section}/` and does NOT write graph claim nodes directly. The only graph projection of meeting content is the **file-level intelligence cascade** (`runCascade`, FILE-LEVEL ONLY per the GATE-0 verdict) plus the separate aggregate `compute-meetings-intelligence`. There is no `claim` truth-claim node writer in the codebase today; the closest precedents are `writeEvidenceClaim` (research lens, `lib/core/navigation/evidence-claim.cjs`) and `writeDecisionNode` (`lib/core/navigation/memory-artifacts.cjs:340`). The phase must mint a NEW claim-node writer following these precedents.

The second critical finding: **`nodes.properties` is schemaless JSON (`TEXT DEFAULT '{}'`)**, so `knowledge_type`/`conditions`/`counter_conditions`/`valid_from`/`valid_until` are ADDITIVE inside the JSON blob with **zero column migration** - exactly the D-10 `artifact_path` precedent (`evidence-claim.cjs:90-100`). The ONLY column with a CHECK constraint is `review_status` (`phase-109-nodes-provenance.cjs:300-301`); `knowledge_type` stays out of the DDL.

The third critical finding: **the edge taxonomy is extended additively per-phase WITHOUT canon amendment today** (every prior addition - INFORMS, CONTRADICTS, SUPERSEDES, STATES, etc. - landed via additive comment blocks in `edges.cjs`, explicitly "without canon amendment"). The CONTEXT's requirement that REFINES/ROOT_CAUSES/INSTANTIATES need a navigator-gated Canon Part 4 + Phase 108 amendment is a POLICY decision (a frozen constitutional set is moving), NOT a code constraint. The C3 fence (`claim-c3.cjs`) does NOT currently assert the closed set; it asserts CONTRADICTS mints + a made-up type rejects. The mechanical lockstep is small; the navigator gate is the load-bearing requirement.

**Primary recommendation:** Plan 01 wires the segment-level type guard (GATE-0 consequence) AND mints the net-new claim-node writer (`writeClaimNode` in a navigation submodule, mirroring `writeEvidenceClaim`). The 4-pass extraction stays LLM-prose in `file-meeting.md` (Part 7: extend, don't rebuild). The edge amendment is one atomic additive wave in `edges.cjs` + a new floor test + canon docs, gated by AskUserQuestion. The selector element rides the SHIPPED `dispatchSensors` -> `cortex-reach-adapter` -> `dial-reach-orchestrator` -> `selector-dispatcher` spine; the ambiguous queue rides the SHIPPED `check-pending-breakthrough.cjs` SessionStart resurfacing pattern.

### Pattern 1: Truth-claim node writer (copy evidence-claim.cjs)
**What:** A navigation submodule that takes a caller-owned db handle, validates inputs, mints a `proposed` node with additive JSON properties.
**When to use:** For `writeClaimNode` (KT-01).
**Example:**
```javascript
// Source: lib/core/navigation/evidence-claim.cjs:65-130 (the precedent)
// Mirror for typed claims:
const KNOWLEDGE_TYPES = Object.freeze(new Set([
  'fact', 'causal', 'heuristic', 'anomaly_cue', 'mental_model', 'assumption',
]));
function writeClaimNode(db, params) {
  const { text, knowledge_type, conditions, counter_conditions,
          valid_from, valid_until, sourceSpeaker, sourceSegment, sessionId } = params;
  if (typeof knowledge_type !== 'string' || !KNOWLEDGE_TYPES.has(knowledge_type)) {
    return { ok: false, reason: 'invalid_knowledge_type' };
  }
  const props = { knowledge_type, /* additive keys, no DDL */
    conditions: conditions || '', counter_conditions: counter_conditions || '',
    valid_from: valid_from || '', valid_until: valid_until || '',
    source_speaker: sourceSpeaker || '', source_segment: sourceSegment || '' };
  // INSERT ... type='claim', created_by='system', review_status='proposed'
  // (TRUTH-CLAIM: never auto-confirmed; Part 9 role 5). ON CONFLICT excludes review_status.
}
```

### Anti-Patterns to Avoid
- **Building a CJS extractor.** Extraction is judgment; it lives in `file-meeting.md` prose. A standalone `extract-claims.cjs` would fight the LLM-driven design and add untestable surface.
- **Adding a `knowledge_type` COLUMN with a CHECK.** That forces the 12-step SQLite table rebuild (`phase-109-nodes-provenance.cjs:270-341`). Keep it a JSON property.
- **Moving any frozen 148 constant.** MAX_K/DIAL_REACH_K/0.70/0.15 are constitutional; this phase touches none.
- **Inventing a `review_status: 'ambiguous'`.** The closed set (`phase-109-nodes-provenance.cjs:301`) has 8 members and no 'ambiguous'. Adding one is a CHECK-constraint migration. Use a `disambiguation` JSON property on a `proposed` node instead (no DDL).
- **The dismissal-canary anti-pattern (Phase 120 lesson).** An ambiguous queue that re-surfaces the same item forever, or that has no [Dismiss] verb, becomes noise. The F.7 breakthrough renderer makes [Dismiss] mandatory (`selector-dispatcher.cjs:738-742`) - mirror that.

## Common Pitfalls

### Pitfall 1: Assuming the cascade fans out per segment (GATE-0)
**What goes wrong:** Building the typed-claim Data->Information rung on the false precondition that `runCascade` already produces per-segment events.
**Why it happens:** The proposal's Section 10 flagged this as unverified; the GATE-0 verdict resolved it: FILE-LEVEL ONLY (`150.6-GATE-0-CASCADE-VERDICT.md`, VERDICT line 100).
**How to avoid:** Plan 01 fixes the type guard FIRST. `intelligence-cascade.cjs:236` is the per-artifact loop (`for (const art of artifacts)`); there is no inner segment loop. Either (a) the 4-pass extraction drives segmentation itself in `file-meeting.md` and calls `writeClaimNode` per atomic claim (recommended - extraction is already the segmentation authority), or (b) add a segment-level cascade pass. Option (a) is simpler and aligns with the LLM-driven design.
**Warning signs:** A claim count that equals the file count instead of the segment count.

### Pitfall 2: knowledge_type as a column instead of a JSON property
**What goes wrong:** A CHECK-constrained column forces the canonical 12-step SQLite table rebuild and a migration sentinel.
**Why it happens:** Copying the `review_status` column pattern (`phase-109-nodes-provenance.cjs:300-301`) instead of the `artifact_path` JSON-key pattern.
**How to avoid:** Follow `evidence-claim.cjs:90-100` (D-10) - additive JSON key inside `properties`, validated in the writer, never in DDL. `nodes.properties` is `TEXT DEFAULT '{}'`.
**Warning signs:** A new `ALTER TABLE nodes ADD COLUMN` or a new migration file.

### Pitfall 3: The C3 fence does not currently assert the closed set
**What goes wrong:** The CONTEXT says "rewrite C3 to assert the new closed set," but `claim-c3.cjs` today asserts CONTRADICTS mints + a made-up type rejects - it never enumerates ALLOWED_EDGE_TYPES.
**Why it happens:** The CONTEXT describes intent; the live fence is narrower.
**How to avoid:** Add the closed-set assertion to a NEW floor test (`test-edges-refines-rootcauses-instantiates-floor.cjs`) mirroring `test-edges-affiliated-with-floor.cjs:38-46` (which IS the canonical FLOOR test: asserts new members present + all prior members preserved + frozen Set instance). Optionally extend C3 to mint a REFINES edge on the fixture. Do NOT assert an exact `.size` - every prior phase asserts a FLOOR so additive extension never regresses.
**Warning signs:** A test that hardcodes `ALLOWED_EDGE_TYPES.size === N` (none exist today; do not introduce one).

### Pitfall 4: Surfacing the ambiguous queue too aggressively (dismissal canary)
**What goes wrong:** Re-surfacing the same unresolved segment every session train-wrecks trust (the Phase 120 lesson).
**Why it happens:** No throttle, no [Dismiss], no resurface cadence.
**How to avoid:** Mirror the breakthrough scanner's throttle + mandatory [Dismiss] (`scanner.cjs` + F.7's `[Dismiss]` guard). Surface at SessionStart, degrade silently when the queue is empty (`check-pending-breakthrough.cjs:115-119` D-16 silence).
**Warning signs:** The same `ambiguous` node id surfacing across >2 sessions with no dismissal path.

### Pitfall 5: A write-only ladder with no visible next-move (the verification-theater failure class)
**What goes wrong:** Filing mints N claims + M ambiguous + K edges but nothing surfaces a selector - exactly the failure this milestone keeps finding.
**Why it happens:** The selector element is treated as optional polish.
**How to avoid:** The post-filing F.1 selector is load-bearing (CONTEXT/navigator-flagged). The cascade already feeds SENS-06; the plan must wire the ladder's outputs into F.1 footer verbs via `selector-dispatcher.pickShape` with `payload.verbs`. Acceptance test asserts the rendered F.1 contract carries the three verbs.
**Warning signs:** A filing flow whose acceptance test stops at "claims exist in room.db" without asserting a rendered selector.

## Open Questions

1. **Does any shipped selector currently drive proposed->confirmed for plain `claim` nodes?**

2. **Should the ambiguous queue surface at SessionStart, post-filing, or both?**
   - What we know: breakthrough surfaces at SessionStart; the post-filing F.1 selector is the immediate next-move.
   - What's unclear: cadence.
   - Recommendation: surface the count in the post-filing F.1 footer ("M ambiguous segments - review?") immediately, AND a SessionStart resurface hook for the persistent queue (mirror `check-pending-breakthrough.cjs`). Throttle + mandatory Dismiss to avoid the canary.

3. **Aura Free 50K node limit vs typed-claim volume.**
   - What we know: CLAUDE.md constraint "LazyGraph must work within 50K node limit." A meeting can produce dozens of atomic claims.
   - What's unclear: real per-room claim volume at scale.
