<objective>
Re-point `chain_run`'s halt and resume path onto the shared ledger, carry the rendered card in the mint payload so the resume path can validate against it, and make the resume path actually read `chosen` instead of ignoring it.

Purpose (GATE-01 G-1, chain side): `238-RESEARCH.md` reproduced live that `chain_run` mints its gate id into `chain.cjs`'s private `_resumeLedger` while `gate_answer` looks in `gate.cjs`'s `_liveGates`, so the documented resume flow fails at step two with `unknown_or_expired_gate`. This plan is the chain-side half of joining them; 238-03 did the gate side. The end-to-end proof that mint id equals ratified id lands in 238-06.

Purpose (GATE-01 G-2, chain side, the worse instance): `_resumeFromGateAnswer` reads only the gate id and the verdict. It never reads `chosen` at all. So on the chain path a payload of verdict approve with any arbitrary `chosen` executes the halted material step. Unvalidated is bad; entirely ignored is worse.

Purpose (GATE-03 half A, chain side): `_mintResumeLedger` DOES store `sessionId` and `_consumeResumeLedger` never reads it back. The field exists and is inert. The resume entry carries `roomDir` and `onStepFn` bound to the MINTING session, so a cross-session resume executes session A's material step in session A's room with session A's callbacks. That is the concrete cross-consume.

Output: `chain.cjs` on the shared ledger with the resume-side allow-list reject, an honest tool description, and a test proving the halted step does not run on either reject path.
</objective>
