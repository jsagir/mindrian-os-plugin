<objective>
Prove the seam GATE-01 exists to repair, end to end, on the real tool surfaces rather than on internal helpers, and give the seam-liveness helper a real production consumer so the proof cannot rot.

Purpose (GATE-01 G-1, the actual success criterion): ROADMAP.md's SC1 says "mint id equals ratified id, asserted on a real chain run". `238-RESEARCH.md`'s Pitfall 3 warns exactly how to get this wrong: `tests/test-198-chain-run-halt.test.cjs` passes today because it drives `chainRun` with a gate answer internally and never crosses to `gate_answer`. A Phase 238 test written the same way would pass without the ledgers ever being joined. This plan drives the registered `gate_answer` handler against an id minted by a real `chain_run` halt.

Purpose (the Phase 235 dependency, discharged): ROADMAP.md's Phase 238 "Depends on" line is "Phase 235 (shared seam-liveness helper proves the mint-to-ratifier seam live)". `lib/core/seam-liveness.cjs`'s `checkMintRatifierLiveness` was written for this phase by name. Wiring it here means enumerating the gate kinds minted against the kinds a ratifier can consume, and proving a mutation turns it red.

Output: the end-to-end ledger proof, a production seam gate, its unit proof with the anti-vacuity assertion, and the release-gate wiring.
</objective>

<phase_decisions>
- **D-08 (the seam wire needs a production consumer):** This milestone exists to close one recurring failure shape, a mechanism wired at one end and inert at the other. A seam-liveness call that lives only inside a test file would be that exact shape. So the check ships as `scripts/check-gate-seam.cjs` and is wired into `scripts/verify-release` as a numbered section, following the Phase 242 MOAT-02 precedent verbatim (`scripts/check-kuzu-reintroduction.cjs` wired as section 17, exit 0 clean, 1 violation, 2 scanner failure).
- **D-13 (vacuity is the named trap):** `assertSeamLive` returns ok true with a claim count of zero by design, because a seam that claims nothing cannot be dead. A wiring bug producing an empty claims array would therefore read green forever. Every assertion in this plan pairs `ok === true` with `claimedCount > 0`, and the production gate exits non-zero on a zero claim count rather than treating it as success.
- **D-04 (in-memory ledger, restated):** the ledger is per-process, so this plan's proofs run inside one process. That is the correct scope for SC1, which is about mint-to-ratify identity, not about cross-process durability.
</phase_decisions>
