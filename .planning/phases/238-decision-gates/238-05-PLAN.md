<objective>
Close the measured lost-update defect on the shared retry counter, and separately close the torn-read defect on the same file. They are two different bugs with two different fixes and this plan ships both.

Purpose (GATE-03 half B): `238-RESEARCH.md` measured this live, not inferred it. Twenty forked processes, each calling `bumpRetryCount` ten times against an isolated `MINDRIAN_HOME`, produced a final count of 3 instead of 200. That is 197 lost updates. The cause is that `writeRetryStore` is a plain `fs.writeFileSync` of a store that `bumpRetryCount` read a moment earlier: a read-modify-write with no fence, no compare-and-swap, and no lock, where the last writer wins and discards every increment that landed in between.

Why this matters beyond tidiness: these counters ARE the bounded escape. `MAX_FORCE_RETRIES` (3) and `MAX_SESSION_INTERCEPTS` (12) are compared against exactly these values. If concurrent Stop evaluations shred the count, the ceilings become effectively unreachable and the force loop never releases, which is the live symptom the open card-fire RCA reports. The concurrency is production-real: `scripts/check-card-fire.cjs`'s `main()` drives these accessors in the per-turn Stop hook process, and `lib/mcp/stop-gate-handler.cjs` was deliberately wired to the SAME exported accessors so the two enforcement paths spend ONE shared budget. The RCA that made the budget shared did not notice the budget cannot survive being shared.

Output: a fenced, atomic retry store, and a 20-forked-process proof asserting the EXACT expected total.
</objective>

<phase_decisions>
- **D-05 (fence primitive and bounded wait):** Reuse `lib/core/write-lock.cjs`'s `acquireLock` and `releaseLock` unchanged, wrapped in a bounded-wait spin local to `check-card-fire.cjs`. Canon Part 7: `acquireLock` already closed the TOCTOU race with `fs.openSync(lockPath, 'wx')` and already handles stale locks, dead PIDs, corrupt lock files and same-PID re-acquire. Do not re-derive it and do not shell out to flock.

  **The trap, named up front:** `acquireLock` THROWS when a live PID holds the lock. It does not wait. Dropped unchanged inside `bumpRetryCount`'s existing swallow-everything try/catch, 19 of 20 contenders would throw and silently drop their increment, taking the measured count from 3 down toward 1. The bounded spin is the whole point, not an optimization.

  **Why waiting is affordable:** Phase 241 verified against real Claude Code documentation that the actual default Stop-hook timeout is 600 seconds per hook command, not the roughly 3000ms this repo's own comments assume and never checked. A worst-case wait of about one second is 600 times inside the real budget. Do not skip the fence for latency reasons.
- **D-11 (two defects, two fixes, both required):** Atomic tmp-and-rename fixes torn READS. It does NOT fix lost updates. A plan that shipped only tmp-and-rename would pass a torn-read test and leave 197 of 200 losses intact. Both land here and both are tested.
- **D-12 (degrade direction on fence exhaustion):** If the bounded wait is exhausted, perform the unfenced read-modify-write anyway rather than dropping the increment. That is exactly today's behavior, so the change can never be worse than the status quo on any path, and the alternative (dropping) is the defect being fixed.
</phase_decisions>

  <action>
Add a bounded-wait fence helper to `scripts/check-card-fire.cjs` and route every read-modify-write on the retry store through it.

Define `retryStoreLockRoot()` returning `path.dirname(retryFilePath())`. Note in a comment that `acquireLock(roomDir)` derives its lock path as roomDir joined with `.mindrian` joined with `write.lock`, so passing the retry file's directory yields a lock file nested one level inside the mindrian home. State plainly that the nesting is an artifact of reusing the room-shaped primitive unchanged (Canon Part 7) and that it can never collide with a real room's SQLite write lock, because `MINDRIAN_HOME` is never a room directory. Do not invent a second lock module to make the path prettier.

Define `RETRY_LOCK_MAX_ATTEMPTS` and `RETRY_LOCK_SLEEP_MS` as named constants sized so the worst-case total wait is on the order of one second (for example 50 attempts at 20 milliseconds). Justify the sizing in a comment with the real number: Phase 241 verified Claude Code's default Stop-hook timeout is 600 seconds per hook command, so a one-second worst case is roughly 600 times inside the budget, and the roughly-3000ms figure repeated in this file's older comments is a self-imposed estimate that was never verified against the platform.

Define `withRetryStoreLock(fn)`. It loops up to `RETRY_LOCK_MAX_ATTEMPTS` times attempting `acquireLock(retryStoreLockRoot())`. On success it runs `fn()` inside a try and calls `releaseLock` in a `finally`, then returns `fn`'s value. On an acquire throw it sleeps `RETRY_LOCK_SLEEP_MS` synchronously and retries. Use `Atomics.wait` on a one-element `Int32Array` backed by a `SharedArrayBuffer` for the synchronous sleep; Node permits `Atomics.wait` on the main thread and it needs no dependency. If every attempt fails, run `fn()` UNFENCED and return its value (D-12): that is exactly today's behavior, so the change is never worse than the status quo, and dropping the increment is the defect being fixed. Increment nothing and log nothing on that path beyond an optional stderr line, because this runs inside a Stop hook.

Do NOT swallow the fence failure silently inside the existing best-effort catch. The write fault stays swallowed; the fence exhaustion falls through to the unfenced call so the increment still lands.

Route these four functions through `withRetryStoreLock`, with the READ moved INSIDE the fence in each case (a read taken before the lock reintroduces the exact race being fixed): `bumpRetryCount`, `clearRetryCount`, `bumpSessionCount`, `clearSessionCount`. Leave the pure readers `readRetryCount` and `readSessionCount` unfenced: they are reads of an atomically-renamed file after Task 1, and fencing them would add contention with no correctness gain.

Leave `MAX_FORCE_RETRIES`, `MAX_SESSION_INTERCEPTS`, `SESSION_KEY_PREFIX`, `RETRY_TTL_MS`, the store SCHEMA (still count plus ts), `normalizeRetryEntry`'s legacy bare-integer tolerance, and every existing export name unchanged. No data migration is needed and none should be attempted.

No em-dashes on any line this task adds.
