<phase_decisions>
- **D-03 (ledger location):** `lib/mcp/gate-ledger.cjs`, NOT `lib/mcp/tools/gate-ledger.cjs`. Both tool modules already require `../gate-render.cjs` one directory up, and `chain.cjs`'s own header blesses that as not a tools-to-tools collision. Source: `238-PATTERNS.md` pattern assignment for this file. Accepted as designed.
- **D-04 (ledger stays in memory):** No SC requires persistence, and in-memory keeps today's "server restart clears pending gates" behavior, which is correct for a 30-minute single-use token. Consequence, stated rather than glossed: SC2's "two concurrent sessions never consume each other's cards" is proven as two session ids inside ONE process. SC2's separate "two-process fence" clause is about the retry-counter FILE and is proven in 238-05. The two proofs are not conflated. Source: `238-RESEARCH.md` Open Question 5.
- **D-09 (null session is not a wildcard):** `resolveEffectiveSessionId` can return `null`. A bare `null === null` comparison would make every null-session caller match every other, which is the exact `NO_SESSION_KEY` bleed `lib/core/card-fire-sidechannel.cjs` already had to fix. The ledger therefore stores a process-scoped sentinel at mint time.
</phase_decisions>

Module state: one `Map` named `_ledger`, and `const LEDGER_TTL_MS = 30 * 60 * 1000;` (30 minutes, identical to both retired constants `LIVE_GATE_TTL_MS` and `RESUME_TTL_MS`).

`ledgerSessionKey(sessionId)`: returns the normalized session key. When `sessionId` is a non-empty string, return it unchanged. Otherwise return `NO_SESSION_PREFIX + process.pid`, where `const NO_SESSION_PREFIX = 'no-session:';`. This is the D-09 process-scoped sentinel: two different processes that both resolve a null session id get different keys and therefore cannot consume each other's gates, while the same process's own null-session calls still round-trip. Export `NO_SESSION_PREFIX`.

`mintGate(gateId, entry)`: store `Object.assign({ mintedAt: Date.now() }, entry, { sessionKey: ledgerSessionKey(entry && entry.sessionId) })` under `gateId`. Use the payload-merging form so `chain.cjs`'s full resume payload rides along unchanged, and so `gate.cjs` can mint with just `{ card, sessionId, kind }`. Compute `sessionKey` LAST in the assign so a caller cannot pass a pre-cooked `sessionKey` that overrides the derived one (the verdict-cannot-be-overridden discipline).

`consumeGate(gateId, sessionId)`: look up the entry. If absent, return `null`. Delete the entry from the Map IMMEDIATELY after lookup and BEFORE any further check, so a gate is single-use whether or not the TTL held and whether or not the session matched (this preserves both current ledgers' semantics exactly). Then, in this order: if `Date.now() - entry.mintedAt > LEDGER_TTL_MS` return `null`; if `entry.sessionKey !== ledgerSessionKey(sessionId)` return the string-tagged reject object `{ ok: false, reason: 'session_mismatch' }`; otherwise return the entry. Callers distinguish the two failure modes by checking `result === null` versus `result.ok === false`.

`consumeGate` takes exactly two positional parameters. No options object, no force flag, no allowlist argument, no bypass of any kind, per the `seam-liveness.cjs` doctrine quoted in the read_first list. Carry that rule as a comment on the function.

`mintedGateKinds()`: return a sorted, de-duplicated array of the `kind` values currently present in `_ledger`. `ratifiableGateKinds()`: return the frozen array of kinds a ratifier can consume, which for this phase is `['general', 'binding', 'material_step']`. Both feed 238-06's seam-liveness wire; declare them here so the ledger, not a test, is the source of truth for what it mints.

Export a `_internal` object carrying `_ledger` so tests can inspect Map size directly, matching the `_internal` convention both tool modules already use.

Header comment: carry the T-198-10 / T-198-12 anti-spoofing doctrine forward from `gate.cjs` lines 70-75 verbatim in intent (a forged or replayed answer never reaches `navigation.cjs`), and add one paragraph stating that this module exists because the two ledgers were minted separately under the same doctrine and never joined, per `238-RESEARCH.md` Finding 1, and that the session key closes the cross-consume vector in Finding 3. No em-dashes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client to MCP server | An untrusted `gate_id` and an untrusted `chosen` array arrive from the client and reach a ratified write |
| session to session (one server process) | Under Cowork or a shared Streamable-HTTP server instance, one process serves multiple sessions; a `gate_id` that leaked into a transcript or a shared artifact is replayable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-238-03 | Spoofing | `lib/mcp/gate-ledger.cjs::consumeGate` | mitigate | ASVS V3/V4. Single-use in-memory ledger with a 30-minute TTL (carried forward unchanged) PLUS a session-key comparison on consume. Entry is deleted on lookup so a rejected consume also burns the token. |
| T-238-04 | Elevation of Privilege | cross-session consume executing another session's material step in another session's room | mitigate | The chain resume payload binds `roomDir` and `onStepFn` to the minting session; `consumeGate` rejects on session mismatch before the entry is ever returned to a caller, so no `onStepFn` can run. |
| T-238-05 | Spoofing | null-session consume becoming a wildcard | mitigate | D-09: `ledgerSessionKey(null)` returns `NO_SESSION_PREFIX + process.pid`, a process-scoped sentinel, not a shared literal. Named test case 5 asserts a different pid yields a different key. |
| T-238-06 | Tampering | `mintGate` caller supplying a forged `sessionKey` | mitigate | `sessionKey` is computed LAST in the `Object.assign`, so a caller-supplied value is always overwritten. Asserted directly. |
| T-238-07 | Tampering | out-of-domain `chosen` reaching a persisted decision | mitigate | ASVS V5. `validateChosenAgainstCard` is the server-side allow-list built from the minted card's own options. This plan creates it; 238-03 and 238-04 wire it into the two ratification paths. |
| T-238-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed. `238-RESEARCH.md`'s Package Legitimacy Audit records "Not applicable"; every primitive is a Node built-in or already vendored. |
