## Known Issue: tests/272-rank-agreement.test.cjs measures 0.06 against the >=0.95 gate (root-caused, not a port defect)

**This is the phase's single most important acceptance bar, and it did not pass numerically. Per this plan's own instruction ("if you cannot get it above the 0.95 gate threshold after genuine debugging effort, STOP and report the actual measured number plus your best diagnosis rather than weakening the test or the gate"), this was not forced past. It requires a navigator decision.**

### Measured result

```
rank-agreement: top-50 pair overlap = 0.0600 (gate >= 0.95)
```

### Root-cause investigation (full trail, reproducible)

1. **Isolated the LSA/structural leg.** Recomputed `scripts/rs_math.py`'s ARPACK pipeline (`TfidfVectorizer` + `TruncatedSVD(algorithm="arpack", random_state=256)` + `extract_topic_keywords`/`count_topic_membership`/`normalize_and_l1_similarity`, IDENTICAL parameters to `generate-baseline.py`) in a fresh standalone Python process, fed the SAME 96 artifact texts my `discoverArtifacts` produces (byte-verified identical to `generate-baseline.py`'s own `discover_artifacts` output -- 0 title mismatches, 0 text mismatches, 0 id mismatches across all 96 artifacts). Compared this fresh Python LSA matrix element-by-element (all 9216 cells) against `rs-math.cjs::buildLsaMatrix`'s output on the same input: **avg delta 0.0016, max delta 0.0196.**
2. **Isolated the semantic leg with a controlled substitution.** Ran `all-MiniLM-L6-v2` (Python's OWN encoder, exact model name) via `sentence-transformers` on the same 96 texts, injected those exact vectors into a direct cosine computation (bypassing `MongoDB/mdbr-leaf-ir` entirely). Spot-checked against `baseline-python.fixture.json`'s stored `semantic_score` for a known pair (`research/authentication-01` vs `-02`): **0.9419 vs 0.9419, exact match.** Broader 200-pair sample: **avg delta 0.00003, max delta 0.00005** -- MiniLM is fully cross-process deterministic.
3. **The critical finding: even a pure Python-vs-Python comparison shows the same low overlap.** Reran the ENTIRE baseline algorithm (fresh ARPACK LSA + fresh MiniLM embeddings, zero JavaScript involved) in an independent process and compared its own top-K pairs against the ORIGINAL stored `baseline-python.fixture.json` (272-02's committed snapshot, generated hours earlier in a DIFFERENT process): **top-50 overlap = 0.42, top-100 = 0.44, top-500 = 0.47, top-2000 = 0.50.** This is Python compared against itself, same code, same parameters, same `random_state=256`, and it does NOT reach 0.95.
4. **Direct diagnosis of the LSA delta's cross-process character:** the fresh-Python-vs-stored-baseline LSA delta (avg 0.0018, max 0.0167) is statistically indistinguishable from my CJS port's LSA delta against a fresh Python recompute (avg 0.0016, max 0.0196) -- both are ~0.002 avg / ~0.02 max. **My CJS port is at numerical parity with Python's own cross-process reproducibility of itself.**
5. **Confirmed the mechanism, not just the symptom.** `scikit-learn`'s `TruncatedSVD(algorithm="arpack", random_state=256)` is deterministic WITHIN a single Python process (272-02's own NOISE-FLOOR.md correctly measured 1.0000 overlap, run1 vs run2 in the SAME process/interpreter instance) but is NOT deterministic ACROSS independent process invocations, even with a fixed `random_state` -- almost certainly because ARPACK's iterative Lanczos eigensolver has some process-level numerical sensitivity (BLAS/LAPACK threading, floating-point summation order, or an implicit restart vector) that `random_state` does not fully pin down end to end through scikit-learn's wrapper. This small-but-systematic per-cell noise (avg 0.0016-0.0018, max ~0.02) is large enough to reshuffle roughly half of the exact top-K pair-ID SET on the fixture room, because the fixture room's synthetic topic-clustered content produces a densely-tied score distribution near the top of the ranking (the `abs_diff` value only drops from 0.398 at rank 1 to 0.268 at rank 500 -- a narrow band with many pairs closely competing for rank position).

### Why this is not a defect in this port

- The LSA leg (the actual novel numerical work of this phase -- TF-IDF, SVD, topic-keyword extraction, topic-membership counting, L1 similarity) matches a fresh independent Python recomputation to within noise-floor-equivalent precision, and matches the ORIGINAL stored baseline to the SAME magnitude any two independent Python runs match each other.
- The semantic leg, when using the identical encoder, is cross-process deterministic to 5 decimal places -- there is no bug in the embedding orchestration, caching, or cosine computation either.
- The D-01-mandated encoder swap (`MongoDB/mdbr-leaf-ir` vs Python's `all-MiniLM-L6-v2`) is a SECOND, separate, expected source of legitimate difference on top of the cross-process ARPACK noise -- it is not being conflated with the ARPACK finding above; both are real and both are accounted for.
- The `writeReverseSalientEdges`, `.rs-engine-results.json` schema, atomic writes, and every other acceptance criterion this plan specified pass exactly as written.

### What this means for the gate itself (not resolved in this plan, out of this plan's scope)

`RANK_AGREEMENT_GATE_THRESHOLD = 0.95` (set in `tests/fixtures/272/noise-floor.json` by 272-02) was calibrated by measuring Python-ARPACK-vs-itself WITHIN one process (`generate-baseline.py`'s run1-vs-run2 loop, which reuses the SAME semantic-leg vectors and runs both LSA computations in the same interpreter instance). That measurement is real and was correctly executed for what it tested, but it does not represent the noise floor for the comparison the gate is actually used for: **any CJS-vs-Python comparison is necessarily cross-process and cross-language**, and this session's controlled experiment shows that axis of variance alone (Python vs Python, cross-process) already produces only ~0.42-0.50 top-K overlap on this specific fixture room -- well below 0.95, before any CJS involvement at all.

This is a genuine finding about 272-02's noise-floor methodology, not something 272-08 can retroactively fix without redoing that measurement (out of this plan's task scope, which was port + generate + run the existing tests). Flagging for navigator decision. Candidate directions, not decided here:
1. Re-measure the noise floor using a genuinely cross-process comparison (e.g., two independent `python3` invocations of `generate-baseline.py`'s algorithm) rather than same-process reuse, and set a threshold justified by THAT number.
2. Reconsider the D-03 validation metric itself -- a rank-correlation measure (e.g., Spearman) may be far more robust to this kind of dense-tie churn than a raw top-50 set-membership overlap, since the underlying scores are highly correlated (the LSA leg's 0.0016 avg delta is tiny) even though the exact top-50 SET differs substantially.
3. Consider whether `TruncatedSVD(algorithm="arpack")`'s cross-process non-determinism is itself the real defect to fix (in the Python baseline generator, not this CJS port) -- e.g., pinning additional BLAS/thread-count environment variables might restore true cross-process reproducibility, which would also make `rs-math.cjs` vs a re-generated baseline agree far more closely (my port already tracks a fresh Python recompute closely; it is the STORED baseline snapshot specifically that carries this generation-time noise).
