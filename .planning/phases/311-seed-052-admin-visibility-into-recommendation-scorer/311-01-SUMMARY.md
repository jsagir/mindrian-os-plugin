# Phase 311 Plan 01: Admin Visibility Into the Recommendation Scorer Summary

**Wired the already-declared `visibility: admin` command frontmatter field through the command registry into the D4 recommendation scorer, closing a live leak where `/mos:admin` was the #2 recommendation for every navigator, admin or not.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-08
- **Tasks:** 3/3 (plus one pre-existing unrelated fix picked up at start)
- **Files modified:** 7 (3 created, 1 more created for deferred-items, 1 config regen, 3 core source, 1 test infra)

## Accomplishments

- `data/command-registry.json` now carries a `visibility` field on all 113 command entries (`"admin"` on exactly `/mos:admin` and `/mos:dogfood-flush`, `null` on the other 111), generated by an extension to `scripts/build-command-registry.cjs`'s `buildRegistry()` that mirrors the existing `teaching` field pattern. Regeneration diff: exactly 113 additions, 0 deletions.
- `lib/workflow/f-selector-ranker.cjs`'s `rankForSelector` now accepts `opts.isAdmin` (strict `=== true`, fail-closed default `false`) and excludes any `visibility: 'admin'` candidate from the ranked output entirely (filter, not deprioritize) unless the caller declares admin. The scorer stays pure: still exactly 2 module-level `process.env` reads, zero references to any admin-identity module.
- The three navigator-facing call sites (`lib/core/navigation-engine-offer.cjs`, `lib/core/unknowns/orchestrator.cjs`, `scripts/suggest-next-command.cjs`) now each compute `isAdmin` per call via the already-shipped `scripts/check-admin-identity.cjs`'s `checkAdminIdentity().admin` and pass it into `rankForSelector`. No second admin-identity heuristic was written anywhere (machine-verified, zero matches for `MOS_ADMIN`/`process.env.USER|USERNAME|HOME`/`jsagi`/`jonathan` across all five touched source files).

## Live before/after evidence

Before this phase (measured against this tree, 2026-09-08, pre-change):
```
rankForSelector({ roomState: {}, k: 3 }) -> ['/mos:act', '/mos:admin', '/mos:agentshield']
```
`/mos:admin` was the number 2 recommendation for every navigator, admin or not.

After this phase:
```
rankForSelector({ roomState: {}, k: 3 })                    -> ['/mos:act', '/mos:agentshield', '/mos:analyze-needs']
rankForSelector({ roomState: {}, k: 3, isAdmin: true })      -> ['/mos:act', '/mos:admin', '/mos:agentshield']
```
Non-admin callers never see `/mos:admin` or `/mos:dogfood-flush`; admin callers still get it when it scores into the top-3.

## Fourth call site left untouched (by design)

`lib/hmi/dial-reach-orchestrator.cjs`'s `_d4SignalFloor` call (the fourth production `rankForSelector` call site) was deliberately NOT wired. Its own code comment states plainly that the returned commands are not what the dial renders -- it calls the ranker only to extract a D4 scoring-signal float for the dial's provenance decomposition, never to surface a command recommendation to the navigator. Because the ranker's `opts.isAdmin` defaults to `false` (fail-closed), this call site was already safe by construction even before this phase, since its output never reached the navigator. This phase proves the boundary held rather than just asserting it: `lib/hmi/dial-reach-orchestrator.cjs` and the sibling execution-time gate `scripts/admin-command-gate.cjs` both match their pinned pre-phase sha256 hashes exactly (`2efb5d6...` and `2407b78...`), verified both before and after all three tasks landed.

## Decisions Made

- Registry field position is load-bearing: `visibility` sits directly after `surface` in both the extraction order and the push-object literal, keeping the regeneration diff pure-additive (113/0) rather than rewriting the `jtbd_summary` line on all 113 entries.

- Strict `=== true` on `opts.isAdmin`: proven by test case 4 (the string `'true'` does NOT grant admin).
- Scope boundary held by construction and proof, not assertion: `lib/hmi/dial-reach-orchestrator.cjs` and `scripts/admin-command-gate.cjs` sha256-pinned, checked both pre- and post-change.
