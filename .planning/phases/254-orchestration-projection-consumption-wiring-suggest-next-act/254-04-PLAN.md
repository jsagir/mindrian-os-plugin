<objective>
Close COMP-01: every `mindrian-os`-named tool handler that reaches the Brain is enumerated in one
place and provably routes through the `callTool` belt.

Read the framing carefully, because getting it wrong is 254-RESEARCH.md's named Pitfall 2. Server-
side composition is NOT a proposal this phase introduces. It SHIPPED, twice, and both sites are
released and tested: `lib/mcp/tool-router.cjs:1460-1462` dispatches `orchestration act` /
`act-chain` / `act-dry-run` / `act-swarm` into `lib/mcp/brain-router.cjs::recommend()`, whose Tier 3
makes a live `brainClient.ask()` call with a 2s hard timeout; and `lib/mcp/tools/sensors.cjs:196-201`
(`suggest_next`) calls `chainRecommender.chainOfferForReach()`, which calls
`brainClient.recommendChain()`. D-01 RATIFIED both. This plan governs what already runs; it does
not green-light something new, and the enumeration's own prose must say so.

The container is the planner's discretion under CONTEXT ("research names the requirement, not the
container"). Chosen: a small declaration module (`lib/mcp/brain-composition-census.cjs`) plus
provenance comments at each site. Rationale for choosing both rather than either: a doc table goes
stale invisibly and inline comments alone cannot be reconciled by a test. The module is the single
source of truth the test reconciles against; the comments make it discoverable from the call site,
which is where a future editor is standing when they add the fourth one.

Scope fence, stated because each is the exact wrong turn available here: this plan changes NO
handler body, adds NO new Brain call, does NOT remove either shipped site (rejecting composition
would have been a removal decision with a blast radius, and D-01 ruled the other way), and does NOT
render a gate from anywhere.

Purpose: two ungoverned sites become three governed entries with an owner, which is precisely the
condition 254-RESEARCH.md Section 3.5's APPROVE column attaches to ratification.
Output: one declaration module, one census suite, three comment-only site edits.
