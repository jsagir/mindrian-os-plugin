<objective>
Make the dependency self-heal fit inside the budget the host actually gives it, so a
first-post-update session degrades honestly instead of being reported as a failed MCP server.

Both entry points call `ensureDepsPresent()` at module load, before the SDK require
(`bin/mindrian-mcp-server.cjs:53`, `bin/mindrian-brain-mcp-client.cjs:38`). On a cold plugin cache
that runs a blocking `spawnSync('npm install')` with `timeout: 120000`
(`lib/core/mcp-dep-heal.cjs:104`). Claude Code's connect timeout for an MCP server is about 30
seconds (CHANGELOG 2.1.242). A 120-second internal ceiling can therefore never fire usefully: the
host gives up roughly four times sooner and reports the server as failed. Worse, the LOSER of the
install-lock race is capped by `WAIT_TIMEOUT_MS = 200 * 1000` in `lib/core/npm-install-lock.cjs:57`,
so the peer-wait path can block for over three minutes on a 30-second clock.

The audit's preferred option, healing asynchronously after `initialize` is answered, was checked
against the code and is NOT available without a rewrite. `bin/mindrian-mcp-server.cjs:55-56`
requires the MCP SDK at module scope immediately after `ensureDepsPresent`, and `createServer()`
runs at module scope too, so on the exact failure this heal exists for (a missing
`@modelcontextprotocol/sdk`) there is no server object capable of answering `initialize` at all.
Deferring the heal would just move the crash. Option (b) from the locked scope is therefore the
fit: cap the connect path well under the host's budget and fail gracefully. Record that finding in
the module header so the next reader does not re-litigate it, and note the deeper fix (making the
transport connect independent of dependency resolution) as a follow-up, not as work for this phase.

Purpose: this is a first-session-after-update failure that currently resolves only by the user
restarting Claude Code. The symptom is already on record in
`.planning/debug/resolved/mcp-servers-cache-missing-node-modules.md:58`; the RCA named the race but
never adjusted the ceiling that guarantees the host loses it.
Output: an explicit connect-path budget, a per-call wait override on the lock, both entry points
opted in, the hook path untouched, and wall-clock tests that prove the bound.
</objective>

## The budget arithmetic (write this into the module header, do not re-derive it)

| Quantity | Value | Source |
|---|---|---|
| Host MCP connect timeout | ~30,000 ms | Claude Code CHANGELOG 2.1.242 |
| Connect-path heal budget | 15,000 ms | This plan: leaves ~15,000 ms for module load, tool/resource/prompt registration, and answering initialize |
| Hook-path install timeout (unchanged) | 120,000 ms | `mcp-dep-heal.cjs:104` today, used by `scripts/sessionstart-npm-reconcile.cjs` |
| Lock STALE_THRESHOLD_MS (unchanged) | 180,000 ms | `npm-install-lock.cjs:53`; must stay strictly above the hook-path install timeout |
| Lock WAIT_TIMEOUT_MS default (unchanged) | 200,000 ms | `npm-install-lock.cjs:57`; must stay strictly above STALE |

15,000 is comfortably below STALE_THRESHOLD_MS, so a connect-path process always releases its lock
long before any peer could consider reclaiming it. The bug_001 invariant chain
(install timeout < STALE < WAIT) is therefore preserved by lowering only the connect path, never
the defaults.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host connect handshake to plugin process | The host spawns the server and counts down ~30 seconds for `initialize`. Anything the process does before answering is spent from that budget. |
| Plugin process to npm registry via `spawnSync('npm install')` | The only child process this module launches. It runs in the plugin cache root and is the sole reason the connect path can block at all. |
| Two concurrent MCP servers to one node_modules tree | Both servers can spawn at the same instant; the file lock is what stops two concurrent installs from corrupting the tree. |
