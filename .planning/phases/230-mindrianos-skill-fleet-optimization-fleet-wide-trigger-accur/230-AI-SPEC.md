## 1. System Classification

**System Type:** Hybrid (Multi-Agent Workflow + Code Automation)

**Description:**
A fleet-wide skill-quality pipeline for MindrianOS-Plugin's own 124 `SKILL.md` files. Workstream 1 measures and improves trigger-accuracy (does an agent load the right skill for the right prompt) via a per-family eval-query generation pass, a cheap roster-wide judge funnel, and -- for flagged skills only -- agentskills.io's literal real trigger-test loop with iterative description revision. Workstream 2 runs an adversarially-verified code-quality review over the ~10-20 skills backed by real `.cjs` machinery. The user (Jonathan, maintainer of MindrianOS-Plugin) is the sole consumer; "good" is a single merged report with proposed description diffs and code-quality findings that is accurate enough to approve changes from, with nothing ever auto-applied to a real `SKILL.md` or script.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. A proposed description "fix" is applied (even after approval) and it regresses trigger accuracy on a skill that was already working -- the funnel/loop reports improvement that isn't real (overfitting to the eval set, not caught by train/validation split).
2. A code-quality finding is reported as CONFIRMED when it would not survive independent scrutiny (a false positive presented with unwarranted confidence, mirroring the exact check-card-fire.cjs over-enforcement class already logged three times this session).
3. A skill's failure to evaluate (query-generation error, judge timeout, agent crash) is silently absorbed as a pass/no-finding instead of surfacing as "not evaluated" -- silent skip is the single most-flagged failure mode in this repo's own recent memory (feedback_false_success_silent_skip_gates, feedback_1_15_enforcement_regression_watch).
4. Any write lands on a real `SKILL.md` or script without an explicit, itemized human approval step immediately preceding it.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Internal developer tooling / AI-agent-platform self-maintenance. This is not a customer-facing or regulated-industry system -- it is a maintenance pipeline the plugin runs on its own 124-skill catalog. The "domain" is the craft of authoring Claude Code plugin skills: writing frontmatter descriptions that trigger correctly under progressive disclosure, and keeping the `.cjs` machinery behind script-backed skills sound.

**User Population:** A single practitioner -- Jonathan, the MindrianOS-Plugin maintainer -- wearing two expert hats: (a) the **skill-description author** who decides whether a skill's description reads clearly and would fire for the right prompt and stay quiet for the wrong one, and (b) the **careful code reviewer** who judges whether a flagged `.cjs` file actually has the defect the pipeline claims. The pipeline stands in for these two judgment calls at fleet scale; the human still makes the final call at the approval gate.

**Stakes Level:** Medium-High. Nothing auto-applies -- an explicit, itemized human-approval gate sits in front of every write to a real `SKILL.md` or script (Critical Failure Mode 4), which caps the downside. But the failure surface is real: a wrongly-CONFIRMED code finding or a description rewrite that regresses trigger accuracy on an already-working skill wastes genuine maintainer time and, if approved without enough scrutiny, ships a live regression into the plugin every user installs. This is not low-stakes throwaway automation (its output changes shipped code) and not critical/regulated (no external party, no compliance exposure, human gate before any effect).

**Output Consequence:** One merged report -- per-skill trigger verdicts with proposed description diffs, plus adversarially-verified code-quality findings for the script-backed subset. Acted on, an approved description diff is written to a real `SKILL.md` (changing how progressive disclosure routes that skill for every installed user); an approved code finding becomes a bug-fix task against shared `scripts/*.cjs` machinery. The report's job is to be accurate enough that the maintainer can approve from it without independently re-verifying every claim -- a report that cries wolf forces full manual re-review and defeats its own purpose.

### What Domain Experts Evaluate Against

```
Dimension: Trigger-routing clarity of the description (WHAT + WHEN)
Good: The description states both what the skill does AND the concrete situations/phrases that should invoke it, names its inputs/outputs, and reads distinctly from its namespace siblings -- a routing rule, not a capability blurb.
Bad: A vague capability line ("helps with connections") with no trigger conditions, or wording so close to a sibling skill that an agent cannot tell which one the query wants.
Stakes: High
Source: Anthropic skill-authoring best practices (description is what Claude matches the request against; say what it does and when to use it); agentskills.io "Optimizing skill descriptions."
```

```
Dimension: Near-miss discrimination within a namespace family
Good: On a query that shares keywords with a sibling but needs a different skill (mos:find-connections vs mos:find-analogies), the correct skill fires under full-roster progressive disclosure and the sibling stays silent.
Bad: A near-miss sibling steals the fire, or nothing fires when one sibling clearly should -- the competitive false-positive / false-negative the funnel exists to catch.
Stakes: High
Source: agentskills.io near-miss negative-example guidance (highest-value test cases share keywords but need a different skill); this repo's own dense mos:/gsd- families.
```

```
Dimension: Do-no-harm on already-working skills (measured on held-out queries)
Good: A proposed rewrite raises the validation-set trigger rate without dropping any query the old description already passed, and "best" is selected by validation pass-rate, not by taking the last loop iteration.
Bad: The rewrite improves train-set numbers while silently regressing a phrasing that used to trigger -- an improvement that is real on the eval set but fake in production (overfitting).
Stakes: Critical (Critical Failure Mode 1)
Source: agentskills.io train/validation split methodology (overfitting risk called out explicitly in the source); the design spec's "select best-by-validation, not last iteration" rule.
```

```
Dimension: Code finding survives independent refutation (high-precision defect discovery)
Good: A CONFIRMED finding quotes the verbatim offending line from the actual `.cjs`, is grounded in what the code really does (not an assumed requirement), and survives a second adversarial pass that genuinely tried to refute it.
Bad: The finding asserts a bug from an imagined/hallucinated requirement, overweights an unreachable edge case, or is a confident-sounding false positive -- the exact check-card-fire.cjs over-enforcement class already logged three times this session.
Stakes: Critical (Critical Failure Mode 2)
Source: "Are LLMs Reliable Code Reviewers? Systematic Overcorrection in Requirement Conformance Judgement" (2026); "Refute-or-Promote" adversarial stage-gated defect-discovery methodology; in-repo check-card-fire over-enforcement incidents (`.planning/todos/pending/2026-07-05-fix-stop-hook-forcing-irrelevant-decision-gate-cards.md`).
```

```
Dimension: Honest not-evaluated accounting (no silent skip)
Good: A query-generation error, judge timeout, or agent crash is reported explicitly as "not evaluated" with its failure reason; pass/finding counts reflect only units that actually ran.
Bad: A killed, timed-out, or errored unit is quietly absorbed as a pass or a no-finding, letting a fabricated "clean" result ride into the report the maintainer trusts.
Stakes: Critical (Critical Failure Mode 3)
Source: "Compaction as Epistemic Failure: How Agentic LLM Tools Fabricate Confirmed Results from Killed Processes" (arXiv 2607.13071); this repo's own silent-skip memory (feedback_false_success_silent_skip_gates, feedback_1_15_enforcement_regression_watch).
```

### Known Failure Modes in This Domain

- **Eval-set overfitting on the rewrite loop.** The description-optimization loop climbs the train-set numbers while a real user phrasing that used to fire now silently misses. Manifests as "improved" reports that regress in the field -- the reason the source methodology mandates a held-out validation split and best-by-validation selection.
- **Systematic overcorrection in code review (confident false positives).** LLM reviewers hallucinate requirements, overweight edge cases, and make unsupported assertions -- and, counter-intuitively, asking the reviewer to also explain and suggest fixes *raises* the misjudgment rate. Left unchecked this produces the "denial-of-service" report volume that shut curl's bug bounty and paused HackerOne's IBB in 2026. Here it manifests as CONFIRMED findings that would not survive a skeptical human read.
- **Epistemic laundering of killed/errored units.** A subagent that times out, crashes, or returns unparseable output has its partial or absent result recorded as a confirmed pass, propagating a false "clean" verdict across the run without re-verification. Domain-specific here because the pipeline spawns ~800-1,000 isolated subagents, each a chance for a transport failure to masquerade as a real result.
- **Near-miss cannibalization in dense namespaces.** Sibling skills with overlapping descriptions (the mos:find-* and mos:explore-* families) steal each other's triggers -- a failure invisible when each skill is tested in isolation and only visible when every query is judged against the full 124-skill roster.

## 2. Framework Decision

**Selected Framework:** Claude Agent SDK / Claude Code native agent-orchestration primitives (`@anthropic-ai/claude-agent-sdk` surface: subagents, the `Skill` tool, hooks, MCP) -- zero new third-party AI framework

**Version:** Whatever `@modelcontextprotocol/sdk` (^1.29.0) and the current Claude Code plugin runtime pin already in `package.json` -- no new package added for this decision.

**Rationale:**
Phase 230's pipeline is Claude-native by construction: subagent fan-out for per-family query generation and the roster-wide judge funnel, real `Skill`-tool invocation for the literal trigger-test loop on flagged skills, and the repo's own existing `code-review` skill pattern reused for Workstream 2. The Claude Agent SDK is precisely this surface already, so it clears every hard constraint from `CLAUDE.md` (Anthropic-native, CJS-only no TypeScript, no server infrastructure, no auto-apply, reuse-before-build per Canon Part 7) with zero new dependency. A third-party orchestrator would add abstraction over primitives Claude Code already ships.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| CrewAI / Haystack / AutoGen (AG2) | Python-only; this repo is CJS-only (`CLAUDE.md` hard rule) |
| Google ADK | Gemini lock-in; this repo is Anthropic-committed |
| OpenAI Agents SDK | OpenAI lock-in; this repo is Anthropic-committed |
| LangChain | Abstraction overhead for an already well-defined use case (anti-pattern #5 in the framework decision matrix) |
| LangGraph.js (`@langchain/langgraph`) | Not ruled out -- carried as the explicit alternative below, not eliminated |

**Vendor Lock-In Accepted:** Yes, consciously -- Anthropic/Claude-native by design (subagents ARE Claude; the plugin itself only runs inside Claude Code). Matches the existing repo-wide commitment, not a new trade-off introduced by this phase.

**Alternative (deferred, not selected):** LangGraph.js -- only becomes worth it if the deferred, opt-in fleet-wide Workflow-tool run (124-skill batch) needs durable per-node checkpointing to stay resumable, which maps to this repo's own harness-as-code canonical-architecture "resumable" property. Not warranted for this phase; native subagent fan-out + JSON artifacts on disk cover it.

### Core Imports
```javascript
'use strict';
const matter = require('gray-matter');          // SKILL.md frontmatter -> {data, content}
const { z } = require('zod/v4');                 // NOT bare 'zod': the v4 subpath gives z.toJSONSchema
const { spawnSync } = require('node:child_process'); // spawn one isolated `claude` subagent per unit
const fs = require('node:fs');
const path = require('node:path');
```

### Entry Point Pattern
```javascript
// Minimal WS1-funnel worker: one isolated headless subagent judges ONE eval query
// against the full 124-skill roster, returns a zod-validated verdict. Mirrors the
// two-stage huji-run-one.cjs orchestrator (build args -> spawn -> unwrap -> validate).

// 1. The verdict contract (zod v4 -> JSON Schema for the CLI, safeParse for us).
const JudgeVerdictSchema = z.object({
  query: z.string().min(1),
  predicted_skill: z.string().nullable(),        // the skill the roster would fire, or null
  expected_skill: z.string().nullable(),         // the label from eval_queries.json
  confidence: z.enum(['high', 'medium', 'low']), // 'low' or 'medium' => flag, never a silent pass
  reasoning: z.string().max(600),
});

function inlineSchemaJson(schemaObj) {
  // CLI 2.1.211 wants the schema INLINE (a path makes it JSON-parse the leading '/'
  // and fail with "Unrecognized token '/'"). zod v4 stamps a draft/2020-12 $schema
  // meta-ref the CLI validator rejects -> strip it (our schema is draft-07-compatible).
  const obj = z.toJSONSchema(JudgeVerdictSchema);
  delete obj.$schema;
  return JSON.stringify(obj);
}

function judgeOneQuery({ query, rosterText, expected, pluginDir, model }) {
  const args = [
    '-p', `Given this full skill roster:\n${rosterText}\n\nUser query: ${query}\n` +
          `Which ONE skill (by name) would fire under progressive disclosure, or null if none? ` +
          `The expected label is "${expected}".`,
    '--plugin-dir', pluginDir,                    // keychain/OAuth auth path, NOT --bare
    '--model', model,                             // sonnet for the judge; haiku for inventory
    '--output-format', 'json',
    '--json-schema', inlineSchemaJson(),          // CLI self-corrects output to the schema
    '--permission-mode', 'dontAsk',
    '--allowedTools', 'Read',                     // judge reads nothing that mutates
    '--max-turns', '2',
    '--max-budget-usd', '0.05',                   // per-query fuse
    '--no-session-persistence',                   // zero cross-query bleed
  ];
  const res = spawnSync('claude', args, { encoding: 'utf8', maxBuffer: 8 * 1024 * 1024, timeout: 120000 });
  if (res.error) return { ok: false, reason: 'spawn_failed', detail: String(res.error.message) };

  // Unwrap the --output-format json envelope; prefer structured_output.
  let env = null; try { env = JSON.parse(res.stdout); } catch (_e) { /* ignore */ }
  const raw = (env && env.structured_output) ||
              (env && typeof env.result === 'string' ? JSON.parse(env.result) : null);

  // Double-validate (belt + suspenders): CLI already self-corrected, we re-check.
  const parsed = JudgeVerdictSchema.safeParse(raw);
  if (!parsed.success) return { ok: false, reason: 'schema_fail', issues: parsed.error.issues };
  return { ok: true, verdict: parsed.data, cost: env && env.total_cost_usd };
}
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| Headless subagent (`claude -p --output-format json`) | One isolated, non-interactive `claude` invocation spawned via `spawnSync`; its own context, its own cost line | Per-query funnel judge (WS1 step 3), per-skill code-review (WS2) |
| `--json-schema` + zod `safeParse` | CLI self-corrects output to the inlined JSON Schema; the orchestrator re-validates with the same zod source | Every structured verdict: judge prediction, code-quality finding |
| stream-json + `--verbose` JSONL | Line-delimited events; `system/init` carries loaded `plugins`, `assistant` messages carry `tool_use` blocks | Detecting a REAL Skill-tool invocation (WS1 step 5) and plugin preflight |
| Bounded concurrency pool (`runPool`) | Dependency-free N-worker pool (`Promise.race` over a running set), limit re-read each iteration | Fleet fan-out across 124 skills without unbounded 429 storms |
| `gray-matter` parse | `matter(fileText)` -> `{ data: frontmatter, content: body }` | WS1 inventory step 1: extract `name`/`description`/body, grep body for `scripts/*.cjs` backing |

### Common Pitfalls
<!-- Every one of these is a real, logged gotcha from scripts/huji-*.cjs (Phase 229), not doc theory -->
1. **`--output-format json` has no reliable `.messages[]` tool trace.** agentskills.io's reference `check_triggered` pipes `--output-format json | jq '.messages[].content[]'` looking for `tool_use` where `name == "Skill"`. The current CLI envelope (2.1.211) returns `{ result, session_id, total_cost_usd, ... }` with no `.messages` array. To observe a genuine Skill fire you MUST use `--output-format stream-json --verbose` and parse the JSONL line by line (this repo's `preflightPluginLoad` in `huji-batch.cjs` already does exactly this). This is the single most load-bearing implementation detail in the phase; get it wrong and every "trigger" in WS1 step 5 is unverified.
2. **`--json-schema` wants the schema INLINE, never a path.** Passing a file path makes the CLI JSON-parse the leading `/` and die with "Unrecognized token '/'". Read the schema, `JSON.stringify` it, pass the string (`inlineSchemaJson`).
3. **zod v4 stamps a `$schema` meta-ref the CLI validator rejects.** `z.toJSONSchema` emits `"$schema":"https://json-schema.org/draft/2020-12/schema"`; CLI 2.1.211 cannot resolve that meta-schema and rejects the whole thing. Use only draft-07-compatible keywords and `delete obj.$schema` before inlining.
4. **`--bare` skips the keychain and needs `ANTHROPIC_API_KEY` (unset here).** Always spawn with `--plugin-dir` (loads the plugin AND uses the OAuth/keychain session). One auth mechanism for the whole pipeline, zero keys to rotate.
5. **Parallel sessions share one key's rate limit.** An unbounded `Promise.all` over 124 skills triggers 429 storms. Cap concurrency at 3-4 (`runPool`), and always pass `--no-session-persistence` (never `--continue`/`--resume`) so units cannot bleed into each other (also the Part-8 containment guarantee).

## 4. Implementation Guidance

**Model Configuration:**
Anthropic-only, routed by cost per sub-task (all set via the `--model` spawn flag; temperature is not exposed by the headless CLI, so it is left at the model default and behavior is bounded by schema + `--max-turns` instead):

| Sub-task | Model | Why |
|----------|-------|-----|
| WS1.1 inventory / family classification | `claude-haiku` tier | Deterministic parse + grouping; cheapest tier is plenty |
| WS1.2 per-family eval-query generation | `claude-sonnet` tier | Needs to see all siblings and craft near-miss negatives (judgment) |
| WS1.3 funnel judge (1 call per query) | `claude-sonnet` tier | The roster-wide prediction is the accuracy-critical call; keep it consistent |
| WS1.5 real trigger-test invocation | default user model (`claude-sonnet` tier) | We are measuring REAL triggering under the model a user actually runs, not a proxy |
| WS2 code-review + adversarial verify | `claude-opus` tier | The adversarial refutation pass is where confidence is earned; spend here |

Per-call fuses on every spawn: `--max-turns` (2 for the judge, higher for code-review), `--max-budget-usd` (per-unit cost ceiling), `--permission-mode dontAsk`, and an explicit `--allowedTools` allowlist.

**Core Pattern:**
Two-stage isolated-subagent orchestration, one `claude` process per unit of work, exactly as `huji-run-one.cjs` proves it:

1. **Build the spawn arg array** (no shell, no string interpolation into a command line). Large inputs (a skill body, a `.cjs` file) are passed as a FILE PATH the session `Read`s, never inlined into `-p` (avoids argv bloat and prompt-injection surface).
2. **`spawnSync('claude', args)`** with `--no-session-persistence` so each unit is hermetic.
3. **Unwrap the envelope** (`parseEnvelope`): prefer `structured_output`, fall back to JSON-parsing `result`, then the first `{...}` in the text.
4. **`Schema.safeParse`** the structured output. A failure is logged as `not_evaluated`, never absorbed as a pass (directly answers Critical Failure Mode 3).
5. **Guardrail gate** before the artifact is trusted: schema pass, no-silent-skip, and for WS2 the adversarial-verify survival check.

WS1 step 5 is the one exception to "unwrap json": to observe a genuine Skill fire, spawn with `--output-format stream-json --verbose`, then scan the JSONL for an `assistant` event whose `message.content[]` holds a `{ type: 'tool_use', name: 'Skill', input: {...} }` block matching the expected skill. Trigger rate = fraction of the 3 runs where that block appears. (Verify the exact input field name against a live `stream-json` capture: agentskills.io documents `input.skill`, but the field may surface the namespaced command like `mos:find-connections` in this plugin; do not hard-code until confirmed.)

**Tool Use:**
The pipeline itself uses `Read`, `Glob`, `Bash(node scripts/*)`, and `Write` (into `.planning/out/` only, never `skills/`). Each spawned subagent gets a locked allowlist:
- Funnel judge: `--allowedTools Read` (it only reasons over the roster text).
- Real trigger-test subagent: default tool set WITH the flagged skill installed via `--plugin-dir`, plus the full roster present, so progressive disclosure runs under real conditions. Preflight the plugin load once with `stream-json` and assert `system/init.plugins` contains mos and `plugin_errors` is empty (fail the run closed otherwise).
- Code-review subagent: `Read, Glob, Bash(node scripts/*)`, no `Write`/`Edit` (review, never rewrite - WS2 scope).

**State Management:**
No database, no server. State is JSON artifacts on disk under the phase's `.planning/.../out/` directory: `eval_queries.json` (per skill, with the fixed train/validation split), `funnel-results.json`, per-flagged-skill iteration logs, and the merged report. A `.done` sentinel per unit (written only after all guardrails pass) makes the batch resumable without a checkpoint library. Nothing pipeline-generated is ever written under `skills/` so a run artifact can never be mistaken for a shipped skill. Every write to a real `SKILL.md` or `.cjs` happens only after the explicit human-approval gate (Critical Failure Mode 4).

**Context Window Strategy:**
The funnel judge deliberately loads the FULL 124-skill roster every call, but only `name` + `description` per skill (the exact bytes progressive disclosure shows the model), never skill bodies - loading bodies would both blow the window and stop mirroring real triggering conditions. The real trigger-test loads one skill's full body plus the roster stubs. Code-review reads one `.cjs` file at a time, chunked by file, so no single subagent ever holds the whole `scripts/` tree.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with zod (this repo's Pydantic equivalent)

Pydantic is Python; this repo is CJS, so the structured-output contract is a `zod/v4` schema, which serializes to JSON Schema for the CLI (`--json-schema`) AND validates the returned object (`safeParse`). Same discipline, same belt-and-suspenders, different language. The schema is the single source of truth for both halves (proven in `lib/core/pitch-feedback-schemas.cjs`).

```javascript
// lib/core/skillopt-schemas.cjs -- the verdict contracts for both workstreams.
'use strict';
const { z } = require('zod/v4');

// WS1 funnel verdict: which skill fires for one query, and how sure.
const JudgeVerdictSchema = z.object({
  query: z.string().min(1),
  predicted_skill: z.string().nullable(),
  expected_skill: z.string().nullable(),
  // 'low'/'medium' does NOT pass -- it flags the skill for the full loop (fail open).
  confidence: z.enum(['high', 'medium', 'low']),
  reasoning: z.string().max(600),   // .max() so a verdict cannot balloon (token budget IS a contract)
});

// WS2 code-quality finding: only CONFIRMED/PLAUSIBLE survivors of adversarial verify are reported.
const CodeFindingSchema = z.object({
  skill: z.string().min(1),
  file: z.string().min(1),
  severity: z.enum(['critical', 'high', 'medium', 'low']),
  claim: z.string().max(800),
  evidence_quote: z.string().max(800),          // verbatim from the .cjs -- the anti-fabrication anchor
  verdict: z.enum(['confirmed', 'plausible', 'refuted']), // 'refuted' is dropped, never downgraded silently
  refutation_attempt: z.string().max(800),      // what the adversarial pass tried and why it failed to refute
});

module.exports = { JudgeVerdictSchema, CodeFindingSchema };
```

**How the framework uses it:** `z.toJSONSchema(schema)` (drop `$schema`, draft-07 keywords only) is inlined into `--json-schema` so the CLI self-corrects the model output; then `Schema.safeParse(structured_output)` in the orchestrator re-checks, catching CLI-version regressions and envelope corruption the CLI-side validation would miss.

**Retry logic:** one retry on `safeParse` failure or spawn error. If the second attempt also fails, the unit is written to the report as `not_evaluated` with the failure reason, and it is NEVER counted as a pass or a no-finding. This is the direct, coded answer to Critical Failure Mode 3 (silent skip) and to the two logged silent-skip incidents in this repo's own memory. Log: the raw stdout, the zod `error.issues`, the model, and the cost, so a triage pass can tell a real miss from a transport failure.

### Async-First Design

The unit call is `spawnSync` (synchronous per subagent) - deliberate, because each unit must be hermetic and its cost/exit must be observed before the next decision. Concurrency comes from a bounded pool (`runPool`: `Promise.race` over a `running` set, limit re-read each iteration), NOT from making the individual call async. **The one mistake to avoid: an unbounded `Promise.all` over all 124 skills** - every session shares one API key's rate limit, so that produces a 429 storm and skews every cost line. Cap at 3-4 concurrent. **Stream vs. await:** await the unwrapped JSON envelope for structured verdicts (WS1 funnel, WS2 findings) where you only want the final validated object; use `stream-json --verbose` for WS1 step 5 where you must inspect intermediate `tool_use` events to see the Skill actually fire (the final result text alone cannot tell you whether the Skill tool was invoked).

### Prompt Engineering Discipline

- **System vs. user separation:** the frozen instruction (the judge rubric, the code-review rubric) goes in `--append-system-prompt-file` so the prompt cache bites across the ~800-1000 funnel calls and provenance stays stable; the per-unit variable (the query, the roster, the file path) goes in `-p`. Never concatenate the rubric into `-p` - you lose the cache and the provenance.
- **Few-shot:** inline for query generation - the per-family generator sees every sibling skill at once so its negative examples are real near-misses (`mos:find-connections` vs `mos:find-analogies`), which is the whole point of grouping by family. No dynamic retrieval needed at this fleet size.
- **Token budget:** bounded explicitly, never left open. Every free-text schema field carries a `.max()`, `--max-turns` caps the loop, and `--max-budget-usd` is the hard per-unit fuse. A verdict that wants 4,000 tokens for a one-line trigger decision is a failure, not a feature.

### Context Window Management

This is a multi-agent workflow, so the lever is per-subagent scoping, not summarization. The funnel judge holds the full roster but only `name`+`description` per skill (progressive-disclosure-exact, ~124 short stubs, well within window); it never holds skill bodies. The real trigger-test holds one full skill plus roster stubs. Code-review holds one `.cjs` at a time. Because every subagent is spawned fresh with `--no-session-persistence`, there is no growing conversation to compact - the isolation boundary is the context-management strategy. If a single `.cjs` is too large for one code-review pass, chunk by function/export and review each chunk against the same `CodeFindingSchema`.

### Cost and Latency Budget

Volume at fleet scale (124 skills):
- WS1 funnel: ~800-1,000 calls (roughly 1 per eval query, ~6-8 queries x 124 skills), sonnet tier. This is the deliberate cheap-funnel design that replaces agentskills.io's literal ~7,500-call per-skill isolated loop.
- WS1 real trigger-test: flagged skills only (~10-20), ~20 queries x 3 runs = ~60 calls each -> ~600-1,200 calls, but only on the flagged subset.
- WS2 code-review: ~10-20 skills x 2 passes (review + adversarial verify) = ~20-40 calls, opus tier.

Estimate the run before spending it: multiply each bucket's call count by the `total_cost_usd` the envelope reports on the smoke-test units, and gate the full run on that projection.

**Caching:** exact-match via the frozen `--append-system-prompt-file` prefix (prompt caching on the stable rubric across every funnel call is the single biggest saver). No semantic cache needed - the queries are distinct by design. **Sub-task routing:** haiku for inventory/classification, sonnet for the judge and query generation, opus reserved for the adversarial-verify pass where the confidence is actually earned. Do not run the whole fleet on opus; do not run the adversarial verify on haiku.

## 5. Evaluation Strategy

> The system under evaluation is the pipeline itself. "Correct" means the merged report is accurate enough for the maintainer to approve description diffs and code findings from it without re-verifying every claim by hand. The dimensions below are the direct measurable form of the domain rubric ingredients in Section 1b, each tied back to a Critical Failure Mode where one exists.

### Dimensions

| # | Dimension | Rubric (PASS / FAIL) | Measurement | Priority |
|---|-----------|----------------------|-------------|----------|
| D1 | **Trigger-routing clarity of proposed descriptions (WHAT + WHEN)** | PASS: a proposed description states both what the skill does AND the concrete phrases/situations that should invoke it, names its inputs/outputs, and reads distinctly from its namespace siblings (a routing rule). FAIL: a vague capability blurb ("helps with connections") with no trigger conditions, or wording indistinguishable from a sibling. | LLM Judge (funnel judge predicts routing) + Human (Jonathan calibrates on the smoke set) | High |
| D2 | **Near-miss discrimination within a namespace family** | PASS: on a query that shares keywords with a sibling but needs a different skill (`mos:find-connections` vs `mos:find-analogies`), the correct skill is predicted under full-124-roster context, and on flagged skills a genuine Skill-tool fire is observed for the right one and not the sibling. FAIL: a near-miss sibling steals the fire, or nothing fires when a sibling clearly should. | LLM Judge (full-roster funnel) + Code (real `tool_use`/Skill-fire detection via `stream-json --verbose` on the flagged subset) | High |
| D3 | **Do-no-harm on already-working skills (held-out validation)** | PASS: a proposed rewrite raises the validation-set trigger rate and drops **zero** queries the old description already passed; "best" is selected by validation pass-rate, never by taking the last loop iteration. FAIL: the rewrite improves train-set numbers while regressing >=1 validation query that used to fire (eval-set overfitting). | Code (fixed train/val split + per-query pass tracking + best-by-validation selector, `regressed_query_count == 0` is a hard gate) + Human (approval gate) | **Critical** (CFM1) |
| D4 | **Code finding survives independent refutation** | PASS: a CONFIRMED finding quotes the verbatim offending line from the actual `.cjs`, is grounded in what the code really does (not an assumed requirement), and survives a second adversarial pass that genuinely tried to refute it. FAIL: the finding asserts a bug from an imagined/hallucinated requirement, overweights an unreachable edge case, or is a confident false positive (the `check-card-fire.cjs` over-enforcement class). | LLM Judge (opus adversarial-verify subagent, Refute-or-Promote) + Code (`evidence_quote` must be a verbatim substring of the real file) + Human (edge-case review of survivors) | **Critical** (CFM2) |
| D5 | **Honest not-evaluated accounting (no silent skip)** | PASS: a query-generation error, judge timeout, agent crash, or budget cutoff is reported explicitly as `not_evaluated` with its reason; pass/finding counts reflect only units that actually ran. FAIL: a killed, timed-out, or errored unit is quietly absorbed as a pass or no-finding. | Code (`safeParse` failure -> `not_evaluated` after one retry; spawned-vs-resolved unit reconciliation) | **Critical** (CFM3) |
| D6 | **No-auto-apply gate integrity (safety)** | PASS: every pipeline write resolves under `.planning/.../out/` only; the merge step STOPs and no real `SKILL.md`/script is touched without an explicit itemized approval immediately preceding it. FAIL: any pipeline-generated content lands under `skills/` or `scripts/` without the gate. | Code (write-path assertion rejecting any target outside `.planning/.../out/`; the merge step halts before any real write) | **Critical** (CFM4) |
| D7 | **Judge + measurement calibration on the smoke set** | PASS: before the full 124-skill spend, the funnel judge's verdicts match Jonathan's pre-labels within tolerance on the smoke set, AND the real-fire detector observes a known-firing skill fire and a known-non-firing skill stay silent. FAIL: judge disagrees with the pre-labels beyond tolerance, or the detector reads triggers off the `--output-format json` envelope (which carries no reliable `messages[]` trace) so every "trigger" is unverified. | Human (Jonathan pre-labels) + Code (agreement-rate computed; assert `stream-json` path; field name verified against a live capture) | **Critical** (run gate) |

Loop-level concerns from the Multi-Agent lens (task decomposition per family, handoff between funnel -> flag -> loop, 5-iteration non-convergence / loop detection, per-unit budget) are covered operationally in Section 6 (Guardrails) and Section 7 (metrics) rather than as standalone dimensions, since here they are throughput/safety fuses, not report-accuracy judgments.

### Eval Tooling

**Primary Tool:** The repo's own CJS eval harness (three layers), reusing the Phase 229 `scripts/huji-eval.cjs` + `scripts/huji-pin-smoketest.cjs` precedent (Canon Part 7, reuse-before-build):
- **Code-based layer** - `zod/v4` `safeParse` on every verdict (`lib/core/skillopt-schemas.cjs` is the single source of truth), plus a new `scripts/skillopt-eval.cjs` that computes smoke-set agreement, not-evaluated reconciliation, the `regressed_query_count == 0` do-no-harm gate, and the `evidence_quote`-is-a-real-substring check.
- **LLM-judge layer** - the funnel judge (sonnet) and the adversarial-verify subagent (opus) are the in-pipeline judges; they are calibrated against the smoke set before the full run, not trusted blind.
- **Human layer** - Jonathan's pre-labels (calibration) and the terminal approval gate (every real write).
- **Trace layer** - one JSON unit-record per spawned subagent under `.planning/.../out/` (query/file, model, `total_cost_usd`, `session_id`, exit, zod `error.issues`, verdict/finding, `not_evaluated` reason) plus a `.done` sentinel; the envelope's `total_cost_usd` + `session_id` are the native per-spawn spans.

**Override note (Arize Phoenix default NOT used, and why):** the framework reference defaults to Phoenix + RAGAS + Promptfoo. All three are genuinely unusable here, not merely dispreferred: Phoenix and RAGAS are Python (this repo is CJS-only, a `CLAUDE.md` hard rule), Phoenix launches a local server (the repo forbids server infrastructure), and every one of them is a new dependency (the Section 2 framework decision is explicitly zero-new-dependency). The in-repo harness already proven by `huji-eval.cjs` does the same job under the repo's constraints.

### Reference Dataset

Two datasets, distinct roles. The pipeline's operating data is the generated eval-query set; the *reference* dataset for evaluating the pipeline itself is the small hand-labeled **smoke-test calibration set**.

**Size:**
- Reference (smoke) set: **10-15 already-known skills**, hand-labeled by Jonathan before any full-fleet spend.
- Operating set (not the reference): ~6-8 eval queries per skill x 124 skills (~800-1,000), generated per family, split train ~60% / validation ~40%, stratified so both carry a proportional should-trigger / should-not-trigger mix. The full 20-query treatment is reserved for flagged skills.

**Composition (of the smoke reference set):**
- Critical path: 1-2 skills that clearly should fire for an obvious query (funnel true-positive).
- Near-miss edge cases: 2-3 sibling pairs from a dense family (`mos:find-connections` / `mos:find-analogies`, `mos:explore-domains` / `mos:explore-trends`) - competitive discrimination (D2).
- Do-no-harm guards: 1 skill with a known-weak description (should surface a proposed diff) AND 1 known-good description (should return "unchanged", guarding against over-editing / systematic overcorrection on WS1).
- Code-review adversarial pair: 1 script-backed skill with a real logged defect (the `check-card-fire.cjs` over-enforcement bug) that WS2 must catch, AND 1 clean `.cjs` the adversarial pass must NOT flag (false-positive guard for D4).
- Not-evaluated probe: 1 deliberately induced failure (forced timeout or oversized file) to confirm it lands as `not_evaluated`, never as a pass (D5).

**Labeling:**
- Domain expert = Jonathan, wearing both hats (skill-description author + code reviewer), pre-labels expected funnel verdicts and expected code-finding outcomes before the full run.
- The adversarial-verify subagent is the automated calibration proxy that the human then spot-checks (per Section 1b's expert-roles table).
- Timeline: build the smoke set DURING harness implementation, before the full 124-skill spend (matches the design spec's "Testing / rollout safety" gate) - never labeled after the fact from the pipeline's own output.

## 6. Guardrails

> "Real-time" here means on every spawned unit during a pipeline run (there are ~800-1,000 of them, each a fresh isolated `claude` subagent). These are the fast, per-unit fuses that must fire before a unit's output is ever trusted. Keep them minimal - each one is code, not another model call.

### Online (Real-Time, per unit)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Schema-validation gate** | `structured_output` fails `zod safeParse` after one retry | Record the unit as `not_evaluated` (never a pass); log raw stdout + `error.issues` + model + cost (D5) |
| **No-silent-skip reconciliation** | spawn error, timeout, non-zero exit, or empty/unparseable envelope | Record `not_evaluated` with the reason; exclude from pass and finding counts; `spawned == passed + flagged + not_evaluated` must hold (D5) |
| **Write-path containment** | any write target resolves outside `.planning/.../out/` | Block the write, fail closed - nothing pipeline-generated may land under `skills/` or `scripts/` (D6) |
| **Real Skill-fire detector integrity** | a trigger-test run reads triggers off `--output-format json` (no reliable `messages[]` trace) instead of `stream-json --verbose` | Block the trigger-rate computation as unverified; require the `stream-json` JSONL `tool_use`/Skill-block path (D2, D7) |
| **Per-unit cost / turn fuse** | `--max-budget-usd` or `--max-turns` exceeded | Kill the unit, record `not_evaluated (budget)`, never bank a partial as a pass |
| **Evidence-quote anchor** | a CONFIRMED/PLAUSIBLE finding's `evidence_quote` is not a verbatim substring of the real `.cjs` | Drop the finding as fabricated; do not report it (D4) |
| **Plugin preflight** | `system/init.plugins` is missing `mos` OR `plugin_errors` is non-empty | Abort the whole run closed before spending any budget (D7) |
| **Human-approval gate (terminal)** | the merge step reaches a proposed real `SKILL.md`/script write | STOP; require explicit, itemized human sign-off before any real write - the one guardrail that is 100% human (CFM4) |

### Offline (Flywheel, sampled batch across runs)

| Metric | Sampling Strategy | Action on Degradation |
|--------|-------------------|-----------------------|
| **Funnel-vs-manual agreement on smoke set** | full smoke set every run + a re-label drift check | Below tolerance -> recalibrate the judge rubric BEFORE trusting the run; do not proceed to the full spend (D7) |
| **Fleet trigger-accuracy rate** (`predicted == expected`) | all funnel verdicts, every run | Trending down across reruns -> descriptions are drifting; open a re-optimization pass |
| **Flag rate per family** | all families | A family flagging abnormally high -> systemic near-miss collision in that namespace; redesign those descriptions together, not one at a time |
| **CONFIRMED-finding survival rate** (`confirmed / (confirmed + refuted)`) | all WS2 findings | Near 100% (nothing ever refuted) -> the adversarial pass may be rubber-stamping; near 0% -> the reviewer is noisy. Calibrate against Jonathan's edge-case reviews (D4) |
| **Over-edit rate** | all skills whose description was pre-labeled "already good" | The pipeline proposing diffs on known-good skills -> WS1 over-eagerness (the systematic-overcorrection analogue for descriptions); tighten the "propose a change only on a real miss" rule |
| **Not-evaluated rate** | all units, every run | Rising -> transport/rate-limit instability; investigate before re-running rather than accepting a thinner report (D5) |
| **Per-run cost vs. smoke projection** | smoke-projected total vs. actual | Overrun -> re-estimate before the next fleet run (Section 4 cost-budget discipline) |

## 7. Production Monitoring

> There is no live service to monitor - "production" for this system is each batch run of the pipeline that the maintainer kicks off by hand. So monitoring means per-run observability plus fail-closed gates, not pagers and uptime dashboards.

**Tracing Tool:** In-repo JSON artifact trace under `.planning/phases/230-.../out/`. Each spawned subagent writes one unit record (query or file, model, `total_cost_usd`, `session_id`, exit code, zod `error.issues`, the verdict/finding, and any `not_evaluated` reason); a `.done` sentinel per unit plus a run manifest form the trace index. The `--output-format json` envelope's `total_cost_usd` + `session_id` are the native per-spawn spans - no OpenTelemetry, no Phoenix, no server (same CJS-only / no-server / zero-new-dep reason as Section 5's override).

**Key Metrics to Track (per run):**
- **Fleet trigger-accuracy rate** - fraction of funnel verdicts where `predicted == expected`.
- **Flag rate** - fraction of skills sent from the cheap funnel into the full trigger-test loop.
- **Not-evaluated rate** - the honesty metric; units that errored/timed-out/failed-schema, reported as such (never absorbed as passes).
- **CONFIRMED code-finding count + survival rate** - `confirmed / (confirmed + refuted)` from the adversarial pass.
- **Best-by-validation lift per flagged skill** - validation pass-rate after vs. before, and `regressed_query_count` (which must be 0).
- **Total run cost vs. smoke projection** - actual spend against the smoke-test-projected estimate.

**Alert Thresholds (fail-closed gates, not pages):**
- Not-evaluated rate `> ~5%` -> halt; investigate transport/rate-limit before trusting the report.
- Smoke-set funnel agreement below tolerance -> do NOT proceed to the full 124-skill spend (hard run gate, D7).
- Any proposed rewrite that regresses `>= 1` validation query it previously passed -> block that diff from the report (do-no-harm hard rule, D3/CFM1).
- Actual run cost `> ~1.5x` the smoke projection -> pause and re-estimate.
- Plugin preflight error (`mos` not loaded, or `plugin_errors` non-empty) -> abort the run before spending.
- Adversarial survival rate anomaly (0% refuted across many findings, i.e. rubber-stamping) -> hold WS2 findings for manual review before they enter the report (D4/CFM2).

**Smart Sampling Strategy (which units get Jonathan's eyes):**
- Weight human review toward the concerning-signal units: low/medium-confidence funnel verdicts (already flagged), CONFIRMED findings on high-severity code, near-miss sibling collisions, skills whose rewrite loop did-not-converge after 5 iterations, and **every** `not_evaluated` unit.
- Do not hand-review the high-confidence / "unchanged" / clean-code majority - spot-check only a few as a control.
- The terminal approval gate is 100% human on every proposed real write, so sampling here is about triage priority, not coverage - the gate guarantees no change ships unseen (CFM4).
