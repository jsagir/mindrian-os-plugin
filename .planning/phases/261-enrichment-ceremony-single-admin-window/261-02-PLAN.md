<objective>
Author CER-01: the Tier A payload that lifts every `:Framework` sitting at readiness 3/4 with an
absent `pattern_type` to 4/4, as ONE guarded `UNWIND` write plus its dry-run, verify and undo files.

Purpose. `pattern_type` is the cheapest of `orchestration_readiness`'s four dimensions: a single
string property on a node that already has structure, techniques and flow. The planner measured 19
such nodes live on 2026-08-21 (the roadmap's "20 frameworks at 3/4" is a stale count; plan 261-01's
`[W-4]` supplies the authoritative list and its size may differ again by window time). Nothing is
authored, no node is created, no edge is minted. This is a classification pass.

The trap this plan exists to avoid, named. `pattern_type` looks like a field a model can fill in
from a framework's name, and filling it in that way would be an unsourced assertion at 19x scale,
the payload template's own rule ("NO named read source = NO payload") violated at the property
level. A framework whose source document does not assert a shape does not get one. It is rejected
from the payload, recorded as rejected, and stays at 3/4, which already clears the `readiness >= 3`
floor. Chasing 4/4 on 19 rows is not worth manufacturing one false classification.

Output: `payloads/tier-a-pattern-type-2026-08-21/`, committed locally, `compile_only: true`,
NEVER executed by this plan.
</objective>

| Boundary | Description |
|----------|-------------|
| authoring time to window time | an internal id is not a stable identifier; a node can be renamed or replaced between the two |
