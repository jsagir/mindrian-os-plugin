# Phase 127 + 127.1 -- External Research Validation

## Summary

External validation **largely confirms** the architectural design but **flags three concrete adjustments** to make before `/gsd:plan-phase 127` runs.

1. **A127.1.3 has a factual error in the CONTEXT.md** -- per Neo4j Cypher Manual 2026, the vector index defaults to **cosine** similarity, not Euclidean. The phase context says "Pinecone default for e5-large is cosine; Neo4j default is Euclidean." This is incorrect for Neo4j 5.13+. The explicit `'cosine'` lock is still correct and defensive, but the rationale text needs a one-line fix.
2. **A127.1.2 (multilingual-e5-large) is mid-pack in 2026 benchmarks** -- mE5-large-instruct and BGE-M3 outperform it on multilingual benchmarks. The "preserve byte-identical embeddings" discipline for the migration is correct (isolate the ANN-algorithm delta as the only variable), but a v1.14.0 follow-up phase should evaluate upgrading to mE5-large-instruct (an in-family successor that minimizes drift) or BGE-M3.
3. **A127.3 (auto-migration) is the highest-risk single item** -- Anthropic GitHub issue #15797 (Nov 2025) documents a near-miss where an agent attempted to overwrite `.claude.json` and would have lost 919 bytes of state. The phase's auto-migration must use the supported `claude mcp remove --scope user` CLI command, never raw file edits to `~/.claude.json`. Add an idempotency safeguard and a JSONL audit log (already specified -- good).

Most other assumptions hold cleanly. The Neo4j 5.13+ HNSW substrate is production-mature, stdio remains the recommended transport for plugin-bundled MCP servers, and plugin-distributed `.mcp.json` is the documented Anthropic pattern.

## Phase 127 Findings

### A127.1 -- MCP SDK version + stdio recommendation

**Status:** Confirmed with weakening signal

**Findings:**
- `@modelcontextprotocol/sdk` v1.x is the current production line; v2 expected Q2 2026 per the digitalapplied tutorial (noqta.tn). Migration will be import-path-only (`@modelcontextprotocol/server` + `@modelcontextprotocol/node`). v1.27.1 is a defensible pin for v1.13.0.
- **Material change to be aware of:** In a recent release the SDK **dropped zod from peerDependencies** and now keeps it as a direct dependency (release notes, GitHub #1824 by @felixweinberger). Plus tools/prompts now accept Standard Schema (Zod v4, Valibot, ArkType). This does NOT break v1.27.1 with zod 3.x but unblocks a future upgrade.
- Stdio remains the recommended transport for plugin-bundled MCP servers per Anthropic's official plugin-dev SKILL.md (`claude-code/plugins/plugin-dev/skills/mcp-integration/SKILL.md`): "Focus on stdio for custom/local servers, SSE for hosted services with OAuth."
- The `CLAUDE_PLUGIN_ROOT` env var is the canonical way to reference plugin files inside `.mcp.json`. The phase should use `${CLAUDE_PLUGIN_ROOT}/bin/mindrian-brain-mcp-client.cjs` if cross-platform path resolution is needed (currently uses `bin/...` relative).

**Recommendation:**
- Keep v1.27.1 pin for v1.13.0. Note the upcoming v2 + Standard Schema migration in the phase's "deferred" section (already implicit; make explicit).
- Consider using `${CLAUDE_PLUGIN_ROOT}/bin/mindrian-brain-mcp-client.cjs` in `.mcp.json` for explicit plugin-root resolution per Anthropic's documented pattern.

### A127.2 -- Plugin-distributed `.mcp.json` wiring

**Status:** Confirmed

**Findings:**
- This is exactly the Anthropic-documented pattern. Per systemprompt.io guide (2026): "Plugin-Provided MCP Servers. Some Claude Code plugins bundle their own MCP servers. When you install one of these plugins, the MCP server is managed automatically. It starts when Claude Code starts, stops when Claude Code stops, and updates when the plugin updates."
- MCP scope precedence (per code.claude.com docs): **local > project > user**. Plugin-bundled `.mcp.json` is treated as project-scope. This means a user's existing user-scope `mindrian-brain` registration would NOT be overridden -- it would coexist with the plugin's project-scope entry, and based on the precedence rule (local > project > user), the project-scope plugin entry wins.
- **However** -- the duplicate-name handling per StackOverflow #79821195 (Nov 2025) shows that `claude mcp` CLI surfaces conflicts when servers exist in multiple scopes. The same name CAN exist in two scopes simultaneously; resolution is via precedence.
- Pluto Security audit (2026) confirms: "In Claude Code, MCP servers are configured via `.mcp.json` (project-scoped), `~/.claude.json` (user-scoped), or bundled inside a plugin."

**Recommendation:**
- Architecture holds. Worth verifying empirically in the synthetic-install acceptance gates (Acceptance gate #3 already covers this).
- Document the precedence explicitly in `docs/install/BRAIN-SETUP.md` once Phase 127 rewrites it.

### A127.3 -- Auto-migration from HTTP-transport to stdio

**Status:** Should revisit (highest risk surface in the phase)

**Findings:**
- No documented precedent for plugin-driven auto-migration of user-scope MCP entries. This is novel territory.
- Anthropic GitHub issue **#15797** (2025) documents a near-miss: an agent attempted to copy `~/.claude/mcp.json` to `~/.claude.json` which would have overwritten 919 bytes of critical config (auth tokens, usage history, project settings). The issue was filed by a Claude instance that caught its own mistake. Risk profile of editing `~/.claude.json` directly is **HIGH**.
- The supported path is `claude mcp remove <name> --scope user`. The phase already specifies this approach in Deliverable 3 -- good.
- Idempotency log (`~/.mindrian/migrations.jsonl`) is the right pattern.
- The "two-key" case (Lawrence's: user-scope key 4131ed5b differs from `~/.mindrian.env` key 107a31b4) is well-handled by the "do not auto-migrate, surface warning" branch.

**Recommendation:**
- Add to phase plan: **NEVER edit `~/.claude.json` directly under any code path.** All scope-user mutations go through `claude mcp <add|remove> --scope user` CLI.
- Add a fail-safe: before migration, snapshot the relevant `~/.claude.json` entry to `~/.mindrian/pre-migration-snapshots/<timestamp>.json` for manual restore if needed.
- Add a dry-run mode to `scripts/migrate-brain-mcp-from-http-to-stdio.cjs` so the user can preview the operation on Tier-1 testers' boxes before live runs.
- Acceptance gate #3 should include a step that verifies `~/.claude.json` is byte-unchanged outside the targeted `mcpServers.mindrian-brain` entry.

### A127.4 -- DirectiveEnvelope typed packet + GUIDED default

**Status:** Confirmed (no direct precedent, but well-grounded design)

**Findings:**
- No published MCP-ecosystem pattern for typed-response envelopes wrapping tool outputs.
- The nearest official analogue is MCP's **elicitation capability** (Speakeasy MCP release notes 2025): "Elicitation allows servers to pause tool execution and ask users for specific information using structured JSON schemas." This is conceptually adjacent to GUIDED mode but inverted -- elicitation is the server asking the user; DirectiveEnvelope is the server telling the client how to render the response.
- GUIDED-default has direct precedent in pedagogical software (Khan Academy, Codecademy hints-first design) but is not standard in agentic SDKs. Cursor and Continue.dev default to autonomous suggestion/completion. Aider and Claude Code itself sit closer to autonomous-by-default. The GUIDED-default choice for Mindrian is a **deliberate differentiator**, not a copy of an existing pattern.

**Recommendation:**
- Document DirectiveEnvelope as a Mindrian-proprietary contract in the capability map (already planned per phase's "Capability map registration" section).
- Consider future alignment with MCP's elicitation capability when GUIDED mode requires a confirmation step from the user. The two patterns compose well.
- The GUIDED-default rule (per `feedback_larry_pedagogical_guided_first.md`) is sound from a product-philosophy standpoint and now memorialized in the canon -- no external blocker.

## Phase 127.1 Findings

### A127.1.1 -- Neo4j 5.11+ HNSW vector index production-readiness

**Status:** Confirmed (production-mature, with version cadence updates)

**Findings:**
- Per Neo4j Cypher Manual 2026: vector indexes hit **5.13 GA**, **2025.10** added native `VECTOR` value property type with dim validation, **2026.01** added multi-label/relationship-type indexes with `SEARCH ... WHERE` filtering, and **2026.04** deprecates the legacy `db.index.vector.queryNodes()` procedure in favor of the Cypher `SEARCH` clause.
- HNSW backed by Apache Lucene's implementation per Neo4j Developer Blog ("Introducing Neo4j's Native Vector Data Type"). Lucene's HNSW is competitive but not best-in-class (FalkorDB, Milvus, and Qdrant generally outperform Neo4j on pure-vector benchmarks per ArcadeDB's 2026 comparison; Neo4j is positioned as graph-first with vector-as-feature).
- For a 1,427-vector corpus, Lucene HNSW is **massively over-provisioned for scale**. The choice is correct for "one substrate" architectural cleanup, not for raw vector performance.
- The `SEARCH` clause should be preferred over the deprecated `db.index.vector.queryNodes()` procedure when the Brain side migrates. If Render is running Neo4j 2026.04+, use SEARCH; if older, use the procedure.

**Recommendation:**
- Verify what Neo4j version is deployed on the `mindrian-brain` Render service before plan-phase. If <2026.01, schedule the Neo4j version bump as part of Phase 127.1 (likely already there but make explicit).
- Use `SEARCH` clause syntax in `brain_search_semantic` if version permits; fall back to `db.index.vector.queryNodes()` for older deployments. Add a version-detect at server boot.
- Migrate to native `VECTOR` value property type (2025.10+) rather than storing as `LIST<FLOAT>` -- gives free dimension validation and similarity-function enforcement.

### A127.1.2 -- multilingual-e5-large embedding model lock

**Status:** Weakened (model is mid-pack in 2026, but lock is correct for migration discipline)

**Findings:**
- Per AfriMTEB benchmark (ACL 2026 paper, aclanthology.org/2026.eacl-long.171.pdf), on 13 multilingual datasets average:
  - mE5-large-instruct: **62.0** (top of <1B class for AfriE5 reference)
  - BGE-M3: 55.0
  - mE5-large (plain, what Mindrian uses): **57.8**
  - mmBERT-base: 34.2
- Per aimultiple.com benchmark on 606K Amazon reviews (Feb 2026): e5_base (110M params) outperforms many models 5-70x larger. Models trained for retrieval (e5 family) outperform general-similarity models (LaBSE). This is actually a positive signal for the e5 family.
- Per ZenML 2026 RAG embedding model guide: BGE-M3 is "the strongest open-source option for multilingual search" and supports hybrid dense+sparse retrieval natively.
- Per Cohere's 2026 line: embed-v4 supports 100+ languages with English-level quality at $0.10/1M tokens.
- Mindrian's e5-large was a reasonable 2024-2025 choice; in 2026 it sits behind mE5-large-instruct (in-family upgrade with minimal drift risk) and BGE-M3 (out-of-family but multifunctional).

**Recommendation:**
- For Phase 127.1 (this phase), **preserve e5-large**. The byte-identical embedding lock is the correct migration discipline -- isolating the ANN-algorithm delta as the only variable.
- Add to v1.14.0 backlog: "Phase TBD -- embedding-model upgrade evaluation." Candidates in order of risk:
  - mE5-large-instruct (1024 dims, in-family, minimal vector-space drift)
  - BGE-M3 (1024 dims, hybrid dense+sparse retrieval, MIT-licensed)
  - Cohere embed-v4 (cost-paid, multimodal, 128K context)
- Pre-design the model-swap protocol now (shadow mode, top-5 overlap harness extension, re-embedding cost) so v1.14.0's evaluation phase starts from a known shape.

### A127.1.3 -- Cosine similarity vs Euclidean on Neo4j vector index

**Status:** Confirmed -- and the CONTEXT.md has a factual error to fix

**Findings:**
- Per Neo4j Cypher Manual 2026 vector indexes page, the `vector.similarity_function` option defaults to **`'cosine'`** (sample index config in the docs shows `\`vector.similarity_function\`: "COSINE"` as a typical default).
- The Phase 127.1 CONTEXT.md states: "Pinecone default for e5-large is cosine; Neo4j default is Euclidean. Silent metric mismatch would re-rank everything in a way that LOOKS like demotion but is actually a configuration bug." This is **incorrect for Neo4j 5.13+** -- cosine is the default in modern Neo4j vector indexes.
- The explicit `'cosine'` lock in the migration Cypher is still correct (defensive, makes the intent explicit, survives a future Neo4j default change).
- Cosine is the canonical choice for sentence-transformer embeddings (including e5-large), regardless of the underlying vector DB. e5-family models normalize to unit length, making cosine and inner product mathematically equivalent.

**Recommendation:**
- Fix the rationale text in Lock #3 of Phase 127.1 CONTEXT.md before plan-phase. Replace "Neo4j default is Euclidean" with "Older Neo4j versions defaulted to Euclidean; modern Neo4j 5.13+ defaults to cosine, but the explicit lock makes the intent durable across version upgrades and removes any chance of a silent default change."
- Keep the explicit `OPTIONS { indexConfig: { 'vector.similarity_function': 'cosine' }}` -- correct defensive practice.

### A127.1.4 -- 80% top-5 overlap as cutover threshold

**Status:** Reasonable but not industry-standard

**Findings:**
- No canonical industry threshold for vector-engine migration overlap. The closest published benchmark is ann-benchmarks.com which targets **95-99% recall** vs ground truth (brute-force kNN) for production-grade ANN systems.
- 80% top-5 overlap between two ANN engines (Pinecone HNSW and Neo4j Lucene HNSW) on identical embeddings is **lower than typical recall@k targets** but **not unreasonable for a migration**. The two engines have different HNSW implementations, different default `M` and `ef_construction`, and may yield non-identical top-k even with byte-identical inputs.
- 20 queries on 1,427 vectors gives roughly 100 result observations (5 results x 20 queries), which is statistically thin but acceptable for a small corpus and a directional migration check.
- Per the dbi-services pgvector tuning study (March 2026): doubling `m` doubled build time on 25K rows without changing index size -- at 1,427 vectors, Neo4j defaults (m=16, ef_construction=100) are likely fine.

**Recommendation:**
- Keep the 80% top-5 overlap gate but **supplement** with a parallel recall@10 against a brute-force ground-truth set. Compute `recall@k = |neo4j_topk ∩ brute_force_topk| / k` for both engines vs the same ground truth. Target: recall@10 >= 0.95 for both engines on the harness.
- This adds rigor without adding test cases -- same 20 queries, just measured against ground truth too.
- Consider expanding the harness to 50 queries if telemetry permits (still small but materially more statistical signal).
- Document the HNSW param choice: start with Neo4j defaults `m=16, ef_construction=100, quantization.enabled=true`. Per the Cypher Manual, quantization is the recommended default for memory efficiency.

### A127.1.5 -- Pinecone retirement risk

**Status:** Confirmed with 2026 hybrid-retrieval caveat

**Findings:**
- The 14-pattern brain-query audit (Pattern #8 = only Pinecone consumer) is empirically supported by the phase's evidence chain: `agents/brain-query.md` + `references/brain/query-patterns.md` + `.planning/research/navigation-engine-brain-interface.md` Section 3.2.
- **2026 hybrid-retrieval industry consensus** (per blog.starmorph.com RAG Techniques 2026, cubitrek.com 2026, NVIDIA/BlackRock HybridRAG paper): the production-default is dense + BM25 + reranker, not pure dense. Recall improves 26%, precision 28% on BEIR benchmarks vs BM25 alone.
- Neo4j 2026.01 supports vector search **with filters** (in-index filtering, post-filtering, Cypher pre-filtering) per the Neo4j blog "Vector search with filters in Neo4j v2026.01 (Preview)". This means Cypher pre-filter + ANN vector + post-filter is a viable hybrid-retrieval path inside Neo4j alone.
- Pinecone's market position has weakened significantly per VentureBeat April 2026: "Pinecone is reportedly exploring a sale, struggling to break out amid fierce competition and customer churn." Internal "incumbents like Postgres (with pgVector) and Elasticsearch simply added vector support as a feature." This is a **tailwind** for Phase 127.1 -- retiring Pinecone is on-trend with industry direction, not against it.

**Recommendation:**
- The Pinecone retirement is sound. The 14-pattern audit holds.
- **Consider a Phase TBD (v1.14.0)** for hybrid retrieval inside Neo4j: BM25 (full-text index) + vector (HNSW) + Cypher graph filtering, fused via Reciprocal Rank Fusion (RRF). This would make `brain_search_semantic` strictly more capable than the Pinecone version it replaced. Per Neo4j docs, all three primitives exist; the fusion logic is the only missing piece.
- The phase's Pattern #8 preservation (fuzzy-match semantics unchanged at API boundary) is the right contract for the v1.13.0-beta.20 cutover. Hybrid uplift is a v1.14.0 enhancement, not a v1.13.0 blocker.

## Cross-cutting Findings

### X1 -- Ship-date trade-off (promoting 127 + 127.1 into v1.13.0)

**Status:** Recommend (with caveats)

**Findings:**
- Industry trend in 2026 across plugin marketplaces (VS Code, Claude Code marketplace, npm) favors **smaller, more frequent releases** (continuous-delivery cadence). Most popular VS Code extensions release weekly or biweekly minor versions.
- Counter-argument: **narrative-driven releases** still work when the narrative compresses multiple changes into a thematic milestone. "v1.13.0: The Closed Loop + Brain Goes Native" is a strong release headline. "v1.13.0: The Closed Loop" + "v1.13.1: Brain Goes Native" is two weaker headlines.
- The 2-week ship-date slip is material but bounded. The pre-promotion plan (v1.13.0 ships now, v1.13.1 ships 3 weeks later) totals ~4 weeks. The post-promotion plan (v1.13.0 ships +2 weeks) totals ~2 weeks. Net: **+2 weeks to first ship, ~2 weeks shorter to "Brain native" available to users.**
- The 14-zero-request silent-cohort gets unblocked **2 weeks sooner** under the promoted plan (per Track C in the phase context).

**Recommendation:**
- The promotion decision is defensible. The trade-off is "marginally slower v1.13.0 first-ship" vs "materially faster Brain-native-to-users." The latter is more valuable for product-market-fit signal.
- Caveat: keep the v1.13.0-beta.18 -> beta.19 -> beta.20 sequencing tight. If beta.19 (Phase 127) reveals integration issues, revert the promotion and ship v1.13.0 without 127/127.1 to preserve the 2-week guard rather than letting the milestone slip 4+ weeks.
- Communicate the release plan to existing Wave-1 testers (Lawrence, Gary, Rea, Natan) ahead of beta.19 so their wiring is the auto-migration target, not a surprise.

### X2 -- Migration coordination (client-side 127 + server-side 127.1)

**Status:** Recommend shadow-mode pattern

**Findings:**
- No canonical case study for plugin client + cloud server coordinated rollouts in the Claude Code ecosystem.
- The general pattern in mature SaaS deployments (per Confident-AI's Pinecone -> pgvector migration writeup, NetApp's HybridRAG production rollout): **dual-write phase + shadow-read phase + cutover + soak period + retire**.
- Applied to Phase 127 + 127.1:
  - beta.19 (Phase 127): client stdio shim ships. Existing remote Brain still serves Pinecone-backed `brain_search_semantic`. No server change.
  - beta.20 (Phase 127.1): server-side substrate swap. Client-server contract unchanged at the API boundary. Shadow mode (both engines run in parallel, log divergence) is desirable for one beta cycle before the Pinecone client is removed.
- Per Phase 127.1's Open Design Decision D-04: "Pinecone API key removal timing -- delete from Render env vars at cutover (irreversible) or leave dormant for one beta cycle as a rollback safety net?" The shadow-mode pattern argues strongly for **dormant for one beta cycle**.

**Recommendation:**
- Resolve D-04 as "dormant for one beta cycle." Concretely:
  - beta.20: Neo4j HNSW becomes the source of truth for `brain_search_semantic`; Pinecone client stays loaded; log every query's results from both engines to a divergence log for one week.
  - beta.21 (or final v1.13.0): if divergence log shows no anomalies, remove Pinecone API key from Render env vars and uninstall the Pinecone client.
- Rollback story: if beta.20 surfaces a regression mid-cycle, flip a feature flag (`USE_NEO4J_VECTOR=false`) and the Pinecone client takes over again. Zero re-deploy needed if the flag is read at request time.
- Add divergence-log analysis to the Phase 127.1 acceptance gates.

## Validation Architecture

Distilled from `127.1-CONTEXT.md` Lock 4 + acceptance criteria; consumed by Nyquist Dimension 8 in `/gsd:plan-phase`.

### Test surfaces (4 surfaces, all required)

1. **Embedding integrity surface** -- byte-identical migration from Pinecone to Neo4j
   - **Check:** for each of 1,427 embeddings, assert `sha256(pinecone_vector) == sha256(neo4j_vector_property)` after load
   - **Failure mode:** any drift means re-embedding crept in; isolate before cutover
   - **Tooling:** Node script reading both backends, dumping a checksum manifest

2. **Index configuration surface** -- Neo4j vector index DDL matches contract
   - **Check:** `SHOW INDEXES` returns one vector index with `dim=1024`, `vector.similarity_function: cosine`
   - **Failure mode:** wrong dim or wrong metric -> all ranking silently broken
   - **Tooling:** Cypher introspection assertion in deploy smoke test

3. **Non-regression query surface** -- top-5 overlap >= 80% across 20 representative fuzzy queries
   - **Check:** harness runs each query against Pinecone (pre-cutover snapshot) AND Neo4j HNSW; computes set-intersection size on top-5 node IDs; reports per-query overlap + aggregate
   - **Failure mode:** <80% overlap on any query class -> tune HNSW `m` / `ef_construction`, re-run, OR document divergence in phase summary
   - **Tooling:** dedicated harness script `tests/127.1-graphrag-overlap.cjs` (or equivalent) -- BLOCKING for cutover
   - **Tier:** acceptance gate (must pass before flipping the `brain_search_semantic` server-side router from Pinecone to Neo4j)

4. **Tool surface stability** -- `brain_search_semantic` MCP contract unchanged
   - **Check:** existing MCP integration tests for `brain_search_semantic` continue to pass; tool name, signature, response shape identical at the client-visible boundary
   - **Failure mode:** silent client breakage during the cutover
   - **Tooling:** existing MCP integration test suite (no new tests needed for this surface; assertion is "no test changes")
