# Phase 127.1 Plan 03: Server-Side Query-Embedder + Text-Query Path Summary

**Built the real new step the re-scoped CONTEXT.md demands: the Brain server now converts a query string into a 1024-dim multilingual-e5-large vector server-side (with the mandatory e5 `query: ` prefix), and `brain-vector-search.cjs` exposes a text-in path that embeds-then-searches -- so `brain_search` keeps its Pinecone-era string API boundary while the embedding step Pinecone gave for free becomes an explicit internal step.**

## Did the live cutover / embedding path run, or is it blocked on operator config?

This is a code-and-test plan, not a live-cutover plan. The plan's own objective states it plainly: "This plan does NOT wire `brain_search` onto Neo4j (that is Plan 127.1-04's cutover act). It delivers the embedding helper and the text-query entry point on `brain-vector-search.cjs`, fully tested, so the cutover is a clean wiring."

- **The embedding code is complete and proven** by a hermetic 9-test harness with a mocked transport -- it runs with zero live network calls.
- **The live embedding path did NOT run end-to-end** and was not expected to. Path A calls a hosted multilingual-e5-large HTTPS endpoint configured by the Render env vars `EMBEDDING_API_URL` + `EMBEDDING_API_KEY`. Those two env vars were ADDED to `render.yaml` (both `sync: false`) by this plan, but they are operator-provisioned -- the operator must populate them on the Render dashboard before a live `brain_search` call can embed query text. This is not a blocker for this plan: the plan explicitly scopes the live wiring + the actual endpoint provisioning to Plan 127.1-04 (the cutover). The code is written correctly so the cutover is a clean wiring once the operator sets the two env vars.
- **No authentication gate blocked execution.** The harness is hermetic by design; it never needs the live endpoint. No checkpoint was raised. The plan authorized a `checkpoint:decision` ONLY if strategy A were genuinely impossible (forcing a 200MB+ ML dependency onto the Render free tier). Strategy A is not impossible -- a hosted e5-large endpoint is the standard hosted-inference pattern and is exactly what Pinecone itself used -- so the code path was implemented directly, no checkpoint.

## Accomplishments

- **`mcp-server-brain/lib/query-embedder.cjs`** (created) -- exports `embedQuery(text)` returning a Promise of a 1024-element finite-number array. The real new step: Pinecone embedded query text via integrated inference, Neo4j has none, so the Brain server now embeds query text itself before the Neo4j HNSW search.
  - Module constants grep-locked to the migrated corpus: `MODEL = 'multilingual-e5-large'`, `EMBEDDING_DIMS = 1024`, `QUERY_PREFIX = 'query: '` (Lock 2).
  - `embedQuery` validates a non-empty string input (throws naming the observed type), prepends the e5 `query: ` prefix, calls the embedding backend, validates the returned vector is exactly 1024 finite numeric elements (the error names both the expected 1024 and the observed length), and re-frames any transport failure (network error, non-2xx, 5-second `AbortController` timeout) as a single deterministic `embedding backend unavailable` error.
  - Strategy A: a hosted multilingual-e5-large HTTPS endpoint via Node 18+ global `fetch` -- zero new runtime dependency. The transport (`httpEmbedTransport`) is a swappable internal function assigned to a module-scoped `activeTransport`, so a future ONNX-local path B can replace it without changing the `embedQuery` signature; path B is documented in the header comment as the fallback.
  - Canon Part 8: a header comment states the embedder embeds the query string only -- no logging of query text, no persistence, a single hosted-embedding HTTPS call, no new egress surface beyond it.
- **`tests/127.1-query-embedder.test.cjs`** (created) -- a `node:test` + `node:assert/strict` hermetic harness. The embedding transport is mocked via the `_test._setTransport` seam, so the harness runs with NO live network call. 9 tests cover the full `<behavior>` block: locked constants, the 1024-length numeric contract, the e5 `query: ` prefix (the mock captures the sent payload and asserts it begins with `query: `), non-string + empty-string rejection, a wrong-length backend vector rejected with both lengths named, a non-numeric vector rejection, and the `embedding backend unavailable` failure on both a transport error and a non-2xx response. Final grep-able line: `OK 127.1-query-embedder 1024-dim e5-large verified`.
- **`mcp-server-brain/lib/brain-vector-search.cjs`** (modified) -- added the exported async `searchSemanticByText({ query, topK, namespace, session })`: it lazily `require`s `query-embedder.cjs`, `await embedQuery(query)`, then delegates to the unchanged vector-in `searchSemantic`. The original `searchSemantic({embedding,...})` path is untouched; both are exported. `registerVectorSearchTool`'s `brain_search` MCP tool schema changes from `query_vector: z.array(z.number()).length(1024)` to `query: z.string()` -- restoring the Pinecone-era API boundary (GRAPHRAG-COLLAPSE-127.1-16: `brain_search` takes a string, the embedding step is internal). The handler calls `searchSemanticByText`; an `embedding backend unavailable` error reaches the handler unswallowed and is surfaced as an explicit `isError: true` content block naming the embedding outage, never a silent empty result. G-3 held: the search still queries only `mindrian_methodology_vec`; `:Command` is never named.
- **`mcp-server-brain/render.yaml`** (modified) -- added `EMBEDDING_API_URL` + `EMBEDDING_API_KEY` (both `sync: false`) to the `mindrian-brain` service `envVars` list, with a comment explaining the server-side query-embedding rationale. `PINECONE_*` env vars left in place -- their retirement is Plan 127.1-05.
- **`tests/run-all-127.sh`** (modified) -- `127.1-query-embedder.test.cjs` added to `CJS_SUITES` in the Phase 127.1 family block; the header comment names the new suite and its producing plan (127.1-03).
