<objective>
Pinecone's `brain_search` used INTEGRATED INFERENCE: the Pinecone index embedded
the query text server-side, so the MCP tool accepted a plain string. Neo4j has
NO integrated inference. The re-scoped CONTEXT.md states this explicitly: "the
rewired path MUST embed the query text with e5-large server-side before the
Neo4j vector search. This is a real new step, not a rename."

The Brain server (`mcp-server-brain/`, deployed on Render) currently has no
embedding model -- `package.json` declares only `@modelcontextprotocol/sdk`,
`@pinecone-database/pinecone`, `express`, `neo4j-driver`, `zod`. After Pinecone
is retired (Plan 127.1-05) there is nothing left to embed query text. This plan
adds the server-side query-embedding capability so the cutover (Plan 127.1-04)
has a complete text-to-vector-to-search path.

This plan does NOT wire `brain_search` onto Neo4j (that is Plan 127.1-04's
cutover act). It delivers the embedding helper and the text-query entry point
on `brain-vector-search.cjs`, fully tested, so the cutover is a clean wiring.

Purpose: give the Brain server the e5-large query-embedding step Pinecone used
to provide for free.
Output: a tested `query-embedder.cjs` + a text-query path on the vector library.
</objective>

<interfaces>
The Brain server runtime (the deployment target):
- Render free-tier Node web service; `rootDir: mcp-server-brain`; `buildCommand: npm install`.
- Memory-constrained (free tier). The embedding solution must be modest in
  footprint; a 560M-parameter PyTorch model loaded in-process is NOT acceptable.

The migrated corpus's embedding contract (Lock 2, from Plan 127.1-01/02):
- multilingual-e5-large, 1024 dims, cosine.
- e5-family models REQUIRE the `query: ` prefix on search queries and the
  `passage: ` prefix on documents. The Pinecone corpus was embedded by Pinecone's
  hosted `multilingual-e5-large` integrated inference. The query-side embedding
  MUST apply the SAME `query: ` prefix convention so the query vector lands in
  the same e5 space as the migrated passage vectors. A prefix mismatch silently
  degrades recall -- this is the single most likely correctness bug in this plan.

From mcp-server-brain/lib/brain-vector-search.cjs (the library this plan extends):
```
searchSemantic({embedding, topK, namespace, session})  -- takes a PRE-COMPUTED vector
registerVectorSearchTool(server)  -- registers brain_search; takes query_vector currently
EMBEDDING_DIMS = 1024
```
This plan adds a TEXT entry point alongside the existing vector entry point.

Two viable server-side embedding strategies (the plan must pick one and a
fallback; D-03):
  A. HOSTED EMBEDDING API -- call a hosted multilingual-e5-large endpoint over
     HTTPS (the same hosted-inference family Pinecone itself used). Zero local
     model weight, modest latency, an API key in Render env vars. This is the
     RECOMMENDED primary path: it matches what Pinecone did (hosted e5-large
     inference) most exactly and keeps the Render free-tier footprint small.
  B. LIGHTWEIGHT LOCAL ONNX -- a quantized multilingual-e5-large ONNX model via
     a JS runtime. Heavier cold-start + memory on Render free tier; viable as a
     fallback only if no hosted endpoint is available.
The plan implements path A as primary, with the embedder written so the
strategy is swappable behind the `embedQuery` interface.
</interfaces>
