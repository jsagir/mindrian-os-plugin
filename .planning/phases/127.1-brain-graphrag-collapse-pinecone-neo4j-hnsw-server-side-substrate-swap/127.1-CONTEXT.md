# Phase 127.1: Brain GraphRAG Collapse -- Pinecone -> Neo4j HNSW (server-side substrate swap)

## Goal

Collapse the dual-substrate Brain GraphRAG (Neo4j 21K nodes + Pinecone 1,427 embeddings) into Neo4j-only by migrating the embeddings to a native Neo4j 5.11+ HNSW vector index inside the `mindrian-brain` Render service. Preserve byte-identical embeddings, lock the embedding model (`multilingual-e5-large`, 1024 dims) and similarity metric (cosine) going forward, and gate the cutover behind a 20-query non-regression harness with top-5 overlap >= 80%.

This is a server-side architectural change. The client-side MCP tool surface (`brain_ask`, `brain_search_semantic`, the 14 Cypher patterns) is unchanged at the API boundary. Testers see no client behavior change beyond potential slight re-ranking of fuzzy-match results (the irreducible delta between Pinecone's ANN and Neo4j's HNSW with same embeddings).

## The audit that motivates this phase

Empirical audit (this room's session, 2026-05-16) confirmed:

- **Pattern verdict:** Pattern B (graph-first-then-vector-rerank) -- HIGH CONFIDENCE 92%
- **Evidence path 1:** `agents/brain-query.md` -- multi-hop protocol: "Cypher first (patterns 1-7, 9-15), then If results need semantic context, use brain_search_semantic". Graph-first sequencing is explicit.
- **Evidence path 2:** `references/brain/query-patterns.md` Pattern #8 -- "brain_search_semantic" is documented as SECONDARY: "Use for fuzzy matching when exact node names are unknown."
- **Evidence path 3:** `.planning/research/navigation-engine-brain-interface.md` Section 3.2 -- BRAIN.md derivation weights (pattern_matches 0.35, framework_chain_predictions 0.20, cross-domain_analogies 0.15) all sourced from Neo4j Cypher; zero section bodies sourced from Pinecone.
- **Asymmetry:** 21K nodes / 65K relationships in Neo4j vs. 1,427 embeddings in Pinecone.
- **Load-bearing verdict:** Pinecone is NOT load-bearing; the system degrades gracefully to Neo4j-only.

## The four-lock non-demotion protocol

All four locks REQUIRED. Lock 4 (harness) is a BLOCKING SUB-TASK -- no cutover until top-5 overlap >= 80% across 20 representative fuzzy queries.

| # | Lock | Why it protects |
|---|------|----------------|
| 1 | **Byte-identical embeddings** -- export all 1,427 float arrays from Pinecone with their node IDs, metadata, raw float vectors; load as a vector property on the corresponding Neo4j nodes. Do NOT re-embed. | Re-embedding introduces a NEW vector space drift; ranking changes become indistinguishable from infrastructure changes. Byte-identical vectors isolate the ANN-algorithm delta as the only variable. |
| 2 | **Same embedding model forward** -- lock `multilingual-e5-large` (1024 dims) in `mindrian-brain` server config. Any new node embedded uses the same model. | Otherwise the methodology graph drifts node-by-node into mixed vector spaces; ranking degrades silently. |
| 3 | **Same similarity metric (cosine)** -- Neo4j vector index created with `OPTIONS { indexConfig: { 'vector.similarity_function': 'cosine' }}`. Pinecone default for e5-large is cosine; Neo4j default is Euclidean. | Silent metric mismatch would re-rank everything in a way that LOOKS like demotion but is actually a configuration bug. |
| 4 | **Non-regression harness (BLOCKING)** -- 20 representative fuzzy queries from tester telemetry (or hand-built if telemetry is thin) run against both engines pre-cutover. Top-5 overlap >= 80% gates the flip. Below 80% -> tune HNSW params (`m`, `ef_construction`) before flipping. | The only irreducible delta is Pinecone's ANN vs. Neo4j's HNSW; harness measures the delta empirically before testers ever see it. |

## Out of scope

- The rs-external Pinecone index (OpenAlex/arXiv metadata, used by Phase 89 reverse-salient-engine cross-domain mode) is SEPARATE infrastructure with public-data content. This phase does NOT touch it. v1.14.0 may revisit.
- Tier 0.5 offline bundled snapshot (per `project_brain_mcp_three_track_transition.md`) remains DEFERRED to v1.14.0; methodology graph still lives in the cloud Brain.
- Client-side `brain_search_semantic` tool behavior change. The tool name + signature stays identical. Internal behavior delta is bounded by Lock 4.

## Acceptance criteria

- [ ] All 1,427 embeddings present on Neo4j nodes as a `vector` property (1024 dims, byte-identical to the Pinecone export)
- [ ] Neo4j vector index created with `vector.similarity_function: cosine`, dim=1024
- [ ] Non-regression harness passes: 20 queries, top-5 overlap >= 80% between Pinecone (pre-cutover) and Neo4j HNSW (post-cutover)
- [ ] `brain_search_semantic` returns results from the Neo4j-only path (Pinecone client removed from `mindrian-brain` Render service)
- [ ] Pinecone API key removed from `mindrian-brain` Render env vars
- [ ] README, onboarding doc, and `docs/testers/STYLE-GUIDE.md` strip Pinecone references where applicable
- [ ] gsd-debugger failure taxonomy updates (remove Pinecone-related rows; document the substrate change)
- [ ] No tester reports "different fuzzy-match behavior" in the first beta cycle after cutover (or, if they do, the report references a known harness divergence already characterized in the phase summary)

## Open design decisions (resolve in /gsd:plan-phase 127.1)

- D-01: HNSW parameter choice -- start with Neo4j defaults (`m: 16`, `ef_construction: 100`)? Or pre-tune based on the 1,427-node scale? (Cost: smaller graph, default params likely fine. Risk: tuning later means a second cutover.)
- D-02: Migration mechanism -- one-shot Cypher LOAD CSV from a Pinecone export dump? Or streaming via the Neo4j Python driver? (Cost: dump approach is simpler + reproducible; streaming is more flexible for large graphs but unnecessary at 1,427 vectors.)
- D-03: Shadow-mode soak duration -- if Lock 4 harness passes, do we still want a beta cycle of shadow-mode (both engines run, log divergence) before deleting the Pinecone client? Or can the harness pass alone gate the flip?
- D-04: Pinecone API key removal timing -- delete from Render env vars at cutover (irreversible) or leave dormant for one beta cycle as a rollback safety net?
- D-05: Wave-1 tester communication -- do testers (Wave-1 cohort) get a notification ahead of the cutover, or is the swap invisible enough that no comms are needed? (Per the conversation that scoped this phase: invisible is the goal, but Lawrence may notice re-ranking. Pre-comm prevents a 45-minute debug session.)
