# Phase 127.1: Brain GraphRAG Collapse -- Pinecone -> Neo4j HNSW (server-side substrate swap)

> **Re-scoped 2026-05-20.** The original CONTEXT.md described a migration into a
> vector-empty Neo4j, from a 1,427-vector Pinecone, byte-identical. A live Neo4j
> read proved all three numbers wrong. This file is the LIVE, re-scoped context.
> The goal (one substrate, Neo4j) is unchanged; the method is corrected. Full
> evidence: `deferred-items.md` DI-127.1-01 + DI-127.1-02.

<domain>
## Phase Boundary

Collapse the Brain's dual semantic-search substrate to Neo4j-only.

**What this phase delivers:**
- Exports all 12,401 vectors from the Pinecone `pws-brain` index (1024-dim,
  e5-large, 5 searchable namespaces) as a byte-identical dump.
- Creates a NEW 1024-dim HNSW vector index in the Brain's Neo4j and loads the
  12,401 vectors as a dedicated node family, carrying a `namespace` property.
- Rewires the `brain_search` MCP tool to query that Neo4j index instead of
  Pinecone, including server-side e5-large embedding of the query text (Pinecone
  did this via integrated inference; Neo4j does not).
- Gates the cutover behind a 20-query non-regression harness (top-5 overlap
  >= 80%, Pinecone vs Neo4j).
- Retires Pinecone: removes `lib/pinecone-tools.cjs`, the `PINECONE_*` Render
  env vars, and the `@pinecone-database/pinecone` dependency.

**What this phase explicitly does NOT touch:**
- The pre-existing 384-dim entity-embedding layer in Neo4j (6,007 nodes, 7 HNSW
  indexes: concept/creativework/entity/framework/person/product/Chunk-`vector`).
  It is a separate, orthogonal layer. Its fate is a future decision, not 127.1.
- The generic Cypher tools `brain_schema` / `brain_query` / `brain_write`.
- The `:Command` node family and its routing edges (reserved -- see below).
- The rs-external Pinecone index (Phase 89 cross-domain; public-data metadata).

This is a server-side change. The MCP tool surface (`brain_ask`, `brain_search`,
`brain_query`, `brain_schema`, `brain_write`, `brain_stats`) keeps its names and
signatures. The only client-visible delta is bounded re-ranking, gated by the
harness.

## Ground truth (live read 2026-05-20)

| | Pinecone `pws-brain` | Neo4j (Brain teaching graph) |
|---|---|---|
| Scale | 12,401 vectors | 15,298 nodes / 19,713 relationships |
| Vector dim | 1024 (e5-large, integrated inference) | 384 (a different, smaller model) |
| Vector layer | the live `brain_search` corpus | 6,007 nodes / 7 HNSW indexes -- NOT in the search path |
| Namespaces | core 8,543 / materials 1,775 / reference 1,690 / tools 242 / graphrag 144 / books 7 | n/a |

The two stores were never the same corpus. Pinecone is chunk/record-level RAG;
the Neo4j 384-dim layer is entity-level. 127.1 migrates the Pinecone corpus and
leaves the 384-dim layer alone.

<decisions>
## Implementation Decisions

### Embedding space -- the keystone

- **D-EMB:** The canonical embedding space is **1024-dim e5-large**. The collapse
  builds a NEW 1024-dim Neo4j HNSW index; the 12,401 Pinecone vectors (already
  1024-dim e5-large) migrate into it **byte-identical, no re-embedding**.
  Rationale: `brain_search` already runs on this space; Pinecone's vectors move
  unchanged; the smaller corpus is not re-embedded; the stronger model is kept.
  Rejected: 384-dim native (commits the Brain to the weaker model and re-embeds
  the larger corpus); fresh-model re-embed-both (turns a cleanup into a quality
  initiative -- that is a separate v1.14.0 phase).

### The four-lock non-demotion protocol -- corrected, and RESCUED

The locks were never wrong. The wrong facts were the count and the assumption
that Neo4j had no vector layer. With D-EMB, all four hold:

| # | Lock | Status |
|---|------|--------|
| 1 | **Byte-identical embeddings** -- the 12,401 Pinecone float arrays load into the new Neo4j 1024-dim index unchanged. No re-embedding. | VALID. Pinecone is 1024-dim e5-large; the new index is 1024-dim. The dimensions match because the index is NEW, not the pre-existing 384-dim layer. |
| 2 | **Same embedding model forward** -- `multilingual-e5-large` (1024 dims) locked in `mindrian-brain` server config; every newly-embedded methodology node uses it. | VALID. |
| 3 | **Same similarity metric (cosine)** -- the new Neo4j vector index created with `vector.similarity_function: 'cosine'`, explicit in the DDL. | VALID. Pinecone e5-large default is cosine; the explicit lock stays defensive. |
| 4 | **Non-regression harness (BLOCKING)** -- 20 representative fuzzy queries, top-5 overlap >= 80% between Pinecone (pre-cutover) and Neo4j HNSW (post-cutover). Below 80% -> tune HNSW `m` / `ef_construction` before flipping. | VALID, and now a genuine apples-to-apples test: same vectors in both engines, so the harness isolates exactly the Pinecone-ANN vs Neo4j-HNSW delta. |

### Cross-stream constraints (command-routing dependency) -- BINDING

A downstream command-routing workstream traverses Neo4j Cypher and stands on
127.1 making Neo4j the single trusted substrate. 127.1 owes it three guarantees.
These are hard constraints on every plan and every migration script:

- **G-1 -- Migration is additive, idempotent, and reversible.** NO
  `MATCH (n) DETACH DELETE n`. NO full-graph reload on cutover. The new 1024-dim
  HNSW index and the 12,401 nodes land ALONGSIDE the existing graph. Every
  migration / export / load script must be safe to re-run (idempotent) and
  reversible. A third node family (`:Command`) will share this database later;
  nothing 127.1 does may assume it owns the graph.
- **G-2 -- Do not collapse the Brain to brain_search-only.** Retiring Pinecone
  means retiring `lib/pinecone-tools.cjs` (which registers `brain_search` +
  `brain_stats`) and rewiring `brain_search` onto Neo4j. The generic Cypher
  tools `brain_query` and `brain_schema` (in `lib/neo4j-tools.cjs`) MUST survive
  untouched. The command-routing traversal is a Cypher query; if the Pinecone
  retirement quietly drops the generic Cypher path, it kills the downstream
  routing build. `brain_write` likewise stays.
- **G-3 -- Reserve `:Command` and never scan it.** The `:Command` label and its
  `SERVES_STATE` / `ANSWERS_JTBD` / `BELONGS_TO_METHODOLOGY` edges are
  off-limits: not vector data, not part of any (re-)index, not touched by the
  migration loader, not touched by the regression harness. `:Command` does not
  exist yet -- this is a forward reservation so the two streams do not collide.
  Every 127.1 query that scans or re-indexes nodes must scope itself to the
  migrated vector node family explicitly, never `MATCH (n)` graph-wide.

### The handshake signal

127.1 emits exactly ONE signal to the command-routing stream:
**"Neo4j single-substrate cutover verified"** -- raised when Lock 4 passes AND
Pinecone is retired. That signal is the sole trigger for the downstream stream
to wire its routing query. The phase's final SUMMARY.md must state this signal
explicitly as a named exit artifact.

### Parallel-stream coordination (non-binding, informational)

The command-routing stream designs the `:Command` schema and hand-authors the
edges for 8 starter commands IN PARALLEL -- pure modeling, zero dependency on
127.1, no Neo4j writes until wire-up. The two streams converge only at the
verified gate above. 127.1 does not wait for, and is not blocked by, that work.

### Claude's Discretion

- New node label for the migrated vector corpus (must not collide with the
  384-dim layer's labels or with `:Command`). Plan-phase decides; `:Command` is
  forbidden, the existing labels are forbidden as the vector target.
- Whether `brain_stats` is rewired to Neo4j or retired with the rest of
  `pinecone-tools.cjs`.
- HNSW `m` / `ef_construction` starting values (Neo4j defaults m=16 /
  ef_construction=100 are the live 384-dim layer's values and a safe start).
</decisions>

## Scope addition 2026-05-20: Brain-query moat guard (Plan 127.1-05)

> Added by navigator direction 2026-05-20, mid-execution, after a security
> finding in this session. Folded into Phase 127.1 (rather than a standalone
> phase) by explicit navigator choice. The pedagogical guide recommended a
> dedicated inserted phase; the navigator decided 127.1. Recorded honestly per
> Canon Part 3 (the navigator decides at every material gate) and Part 6
> (dog-fooding -- drift is recorded, not hidden).

### The finding

`mcp-server-brain/lib/neo4j-tools.cjs` registers `brain_query`, which runs
arbitrary caller-supplied Cypher with only `defaultAccessMode: neo4j.session.READ`.
That is an integrity control (writes are rejected) but NOT a confidentiality
control: any Brain keyholder can run `MATCH (n) RETURN n` and read the entire
27,699-node methodology graph. The moat (per `CLAUDE.md`, the teaching graph is
SECRET IP) is copyable through the served `brain_query` tool. `brain_schema`
compounds it by handing over the full label / relationship / property taxonomy.

### Validated against the official Neo4j sources (Tavily, 2026-05-20)

Checked `github.com/neo4j-contrib/mcp-neo4j`, `neo4j.com/docs/mcp`, and the
Neo4j blog "Production-Proofing Your Neo4j Cypher MCP Server":
- `NEO4J_READ_ONLY=true` is the official read-only flag; it removes the WRITE
  tool only. Neo4j's own blog frames it as anti-write (the LLM becomes "an
  observer ... exploring and retrieving data"). It is not a confidentiality guard.
- The official server ships safeguards that DO bound exfiltration:
  `NEO4J_CYPHER_MAX_ESTIMATED_ROWS` (rejects a query at EXPLAIN-plan time on
  estimated row count), `NEO4J_CYPHER_MAX_ROWS`, `NEO4J_CYPHER_MAX_BYTES`,
  `NEO4J_RESPONSE_TOKEN_LIMIT`, `NEO4J_CYPHER_TIMEOUT`.
- The official production recipe pairs read-only mode with a dedicated
  `neo4j_reader` database user; fine-grained read scoping needs Neo4j RBAC
  (Enterprise; Aura Professional has it, Aura Free does not).
- The Brain does NOT run `mcp-neo4j-cypher`. `neo4j-tools.cjs` is hand-rolled
  (105 lines) and has none of these safeguards.

### Plan 127.1-05 scope (the moat guard)

- D-MOAT-1: `brain_query` authorization gate. Add `if (plan !== 'admin')` to
  `brain_query` in `neo4j-tools.cjs`, mirroring the existing `brain_write` gate.
  Non-admin keys lose raw arbitrary Cypher. Stop-the-bleeding change, ships first.
- D-MOAT-2: Cypher execution safeguards ported into `neo4j-tools.cjs` per the
  official Neo4j recipe: row cap, EXPLAIN-plan estimated-row rejection, response
  byte/token cap, read timeout. Bounds any read the gate still permits.
- D-MOAT-3: scoped served credential. A dedicated `neo4j_reader` Neo4j user for
  the served read path; on Aura Professional, a role that DENIES reading the
  `embedding` vectors and the methodology body text.
- D-MOAT-4: Aura-tier check FIRST. Confirm the Aura tier of
  `5b8df33f.databases.neo4j.io`. Professional+ -> D-MOAT-3 uses RBAC. Free ->
  RBAC unavailable, D-MOAT-3 falls back to a curated / parameterized query
  surface. The plan forks on this answer.
