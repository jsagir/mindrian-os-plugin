# Phase 127.1 Plan 05: Brain-query Moat Guard Summary

**The served `brain_query` MCP tool ran arbitrary caller Cypher under READ access only, so any Brain keyholder could copy the whole 27,699-node methodology graph. Plan 127.1-05 closed that confidentiality hole: `brain_query` is now admin-gated, every read the gate still permits is bounded by four ported Neo4j safeguards, the Aura tier was confirmed, and the scoped-credential decision was resolved as a deferral. The graph IS the moat (Canon Part 9), and it is no longer copyable through `brain_query` by a non-admin caller.**

## What shipped

### D-MOAT-1 -- brain_query admin gate (SHIPPED v1.13.0-beta.21, commit 0d1416a6)

`brain_query` is gated to the `admin` plan, mirroring the existing `brain_write`
gate verbatim. A non-admin keyholder calling `brain_query` receives an
authorization-denied `isError` response and runs zero caller Cypher; the caller
is pointed at `brain_search` and `brain_ask` for methodology lookups. An admin
keyholder still gets results. The tool stays registered and functional, so Canon
G-2 holds (`brain_query`, `brain_schema`, `brain_write` all survive -- 3
`server.tool(` registrations).

### D-MOAT-2 -- Cypher execution safeguards (SHIPPED v1.13.0-beta.21, commit dd0d3ef7)

Four execution safeguards, ported from the official Neo4j `mcp-neo4j-cypher`
recipe, bound any read the admin gate still permits (an admin call can still be a
runaway query). The timeout and byte cap also bound `brain_schema`; the EXPLAIN
reject and row cap do not apply to `brain_schema` because it runs fixed
`CALL db.*` procedures, not caller Cypher.

| Knob | Default | What it bounds |
|------|---------|----------------|
| `BRAIN_CYPHER_MAX_ESTIMATED_ROWS` | 5000 | EXPLAIN-plan estimated-row reject, before execution |
| `BRAIN_CYPHER_MAX_ROWS` | 1000 | Hard cap on returned records |
| `BRAIN_CYPHER_MAX_BYTES` | 524288 | Response size cap |
| `BRAIN_CYPHER_TIMEOUT_MS` | 5000 | Read transaction timeout |

The defaults are declared on the `mindrian-brain` Render service in `render.yaml`
and documented in `.env.example`. The server falls back to these values if the
vars are unset, so the safeguards are live with no operator action. The `BRAIN_*`
prefix is intentional: the official Neo4j server uses `NEO4J_*` names, but the
Brain runs a hand-rolled `neo4j-tools.cjs` and already uses a `BRAIN_API_KEYS`
convention, so `BRAIN_` keeps the namespace consistent.

## Task 3 outcome (D-MOAT-4 then D-MOAT-3)

### D-MOAT-4 -- Aura tier confirmed: Aura Free

The Brain's Neo4j instance (`5b8df33f.databases.neo4j.io`) was confirmed on the
Neo4j Aura console as running on the **Aura Free** tier.

### D-MOAT-3 -- scoped neo4j_reader credential: DEFERRED

D-MOAT-3 planned a scoped `neo4j_reader` credential that DENIES READ on the
embedding property and the methodology body text. This is **not achievable on
Aura Free**: Free has no role-based access control -- no custom roles
(`CREATE ROLE` fails), no additional database users, and no property-level
`DENY READ`. The built-in `reader` role exists on every tier but cannot deny the
`embedding` property or the body text, so it would not actually protect the
moat. The plan's Task 3 Fork B (create a built-in `reader` user) was therefore
overridden: no credential was created.

D-MOAT-3 is DEFERRED. It needs one of:

- the Brain's Neo4j moved to **Aura Professional** or higher, where RBAC allows
  a scoped `neo4j_reader` role with property-level `DENY READ`; or
- a curated / parameterized-query surface shipped as a future phase, so the
  served read path never accepts arbitrary caller Cypher in the first place.

No `NEO4J_READER_USER` / `NEO4J_READER_PASSWORD` env vars were added to
`render.yaml` or `.env.example`, because no scoped credential exists to point
them at. The served read path continues to use the existing `NEO4J_USER`
credential. Until D-MOAT-3 lands, the D-MOAT-1 admin gate plus the D-MOAT-2
safeguards are the live scoping levers.

## Soak-independence (the load-bearing property)

Plan 127.1-05 shipped standalone with zero dependency on Plan 127.1-04 or its
~7-day cutover soak. It declared `depends_on: []` and `wave: 1`, modified only
the four declared files (`lib/neo4j-tools.cjs`, `render.yaml`, `.env.example`,
`CLAUDE.md`), and never touched `server.cjs` or `brain-ask.cjs` -- those belong
to Plan 127.1-04. The moat exposure was live in production, so the fix was not
chained behind the soak. D-MOAT-1 and D-MOAT-2 were already in main and rode out
in v1.13.0-beta.21.

## Follow-up for Plan 127.1-04

Re-pointing the live served read path onto a least-privilege reader credential
is out of this plan's scope (it is a `server.cjs` concern). It is also currently
blocked by the D-MOAT-3 deferral: there is no scoped credential to re-point onto
while the Brain's Neo4j stays on Aura Free. When the Brain moves to Aura
Professional, the scoped `neo4j_reader` role can be created and the served read
path re-pointed -- at which point `NEO4J_READER_USER` / `NEO4J_READER_PASSWORD`
should be declared and consumed.
