<planner_findings>
Five findings from reading the actual code and the actual Phase 230 corpus at plan time. The
executor does not need to re-derive them, but MUST carry findings 1, 2 and 5 into the SUMMARY.

**Finding 1 (the headline, must reach the SUMMARY).** The real Phase 230 corpus at
`.planning/phases/230-.../out/queries/*.json` holds 105 queries across 14 skill sets, and every
one of the 105 query texts is distinct. There are 23 null-labeled `should_not_trigger` negatives
and ZERO of them exactly match a foreign positive. So the exact-match rule locked in D-02
corrects 0 of 23 on the smoke corpus. It is not a no-op fix in general (it is the correct guard
for the case, and duplicate probability rises sharply at 124-skill fleet scale where the corpus
is roughly ten times larger), but it does NOT by itself move the 30 percent D7 number. The
load-bearing follow-up for D7 is SEED-061 step 2, the human relabeling pass, not this code fix.
Record that honestly rather than implying this phase repairs the gate.

**Finding 2 (why exact match misses, evidence for the step 2 handoff).** The 23 residual null
negatives include 4 that are near-miss wordings of a foreign positive, for example `jtbd`'s
negative "what's the status of my room" against `status`'s positive "show me the current status
of my room". These are the actual false-alarm generators in the smoke run. D-02 deliberately
refuses to touch them, because catching them needs either a live judge call (deferred spend) or a
similarity heuristic only a human should arbitrate. Do NOT ship a similarity scorer. The audit
mode in Task 3 reports the residual null negatives as a plain list, with no scoring and no
ranking, which is raw material for step 2 and stays inside D-02.

**Finding 3 (the `--skills` trap, changes the implementation).** CONTEXT.md says
`enumerateQueries` "already reads every skill's generated query file into one array, roster-wide".
That is only true when no filter is passed. `enumerateQueries(queriesDir, skillsFilter)` skips
whole query-set FILES whose `set.skill` is outside the filter, and the 13-skill smoke runs exactly
that path via `--skills`. A reconciliation built from the filtered array would be blind to
positives owned by the other 111 skills, which is the majority of the collision surface. The
implementation therefore enumerates UNFILTERED, builds the positive index from the full array, and
only then applies the caller's skill scope. `enumerateQueries`'s own signature and filter
behavior stay unchanged so nothing else regresses.

**Finding 4 (second consumer checked, answer is clean).** The scope brief asked whether a second
consumer of the on-disk query files also needs the corrected label. There is one:
`scripts/skillopt-triggerloop.cjs::runLoopsFromFunnel` reads `out/queries/<skill>.json` directly.
It does NOT need the correction. Verified by grep: triggerloop scores negatives purely by `kind`
(`scripts/skillopt-triggerloop.cjs:514`, `if (kind === 'should_not_trigger') return triggerRate === 0`)
and never reads `expected_skill`; line 638 derives its `expected` display value from `kind` too.
Its semantics are per-skill trigger behavior, where a negative that legitimately belongs to another
skill still correctly must not fire the skill under test. So the in-memory-only correction is
complete for the current codebase, and NOT writing back to `queries/*.json` is right, not a
shortcut. If a future consumer starts reading `expected_skill` off disk, this conclusion expires.

**Finding 5 (a real hole in the fix, must be closed in Task 1, must reach the SUMMARY).** The
correction only reaches scoring through the verdict object. For a fresh judge call that is
automatic, because `judgeOneQuery` already force-writes `expected_skill: o.expected` onto the
parsed verdict ("Force the expected label onto the verdict so scoring never depends on the model
echoing it back correctly"). The RESUME path does not: `runFunnel`'s `onSettle` pushes
`verdict: unit.payload` straight from the persisted unit JSON, whose `expected_skill` is whatever
label the PRIOR run used, that is the stale null. `classifySkills` reads
`u.verdict.expected_skill`, never `u.item.expected_skill`. So without a fix, any resumed unit
(and a smoke re-run over an existing `out/funnel/units/` directory is exactly that) would keep
false-alarming and the fix would look present while being inert. Task 1 closes this by forcing
the item label onto the resumed verdict in memory, mirroring the invariant `judgeOneQuery` already
documents. No persisted unit file is rewritten.
</planner_findings>
