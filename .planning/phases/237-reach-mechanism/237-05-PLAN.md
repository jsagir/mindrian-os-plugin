<objective>
Give the chain-step dispatcher a declarative, build-time-generated allowlist of what is actually executable, and prove that allowlist is not lying.

Purpose: REACH-01's dispatcher must resolve a step's command to something runnable. There is no `executable` field in `data/command-registry.json` today, and parsing `node "${CLAUDE_PLUGIN_ROOT}/scripts/X.cjs"` lines out of 44 command bodies at runtime is brittle (most carry model-filled parameters that are not machine-resolvable) and is explicitly rejected by the research. The declarative option is one generated source of truth, discoverable, and gives the mutation leg a clean target: delete the join and the artifact stops appearing.

This is also where the phase's one genuine privilege increase gets its safety property. The dispatcher in Plan 07 will spawn a child process from the MCP server. The property that makes that acceptable is that the executable set is a CLOSED, BUILD-TIME-GENERATED ALLOWLIST, never a string derived from a step field or from MCP tool input. That property is established here, not there.

Research assumption A3 is unverified: nothing has tested whether the born-wired, shape-declaration or projection check gates tolerate an unknown frontmatter key. Task 1 probes that first and the plan states the fallback honestly rather than discovering it mid-implementation.

Output: an optional `executable: { script, args, produces }` frontmatter block picked up by the registry builder, populated on `commands/snapshot.md`, a regenerated `data/command-registry.json`, and a seam-liveness gate over every claim.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| command markdown frontmatter -> generated registry | Author-controlled YAML crosses into a build artifact that will later drive a child-process spawn |
| generated registry -> future dispatcher allowlist | This is the boundary that makes Plan 07's spawn acceptable: the executable set is closed and build-time generated |
| declared script path -> filesystem | Read-only existence check in this plan; execution happens only in Plan 07 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-237-05-01 | Elevation of Privilege | arbitrary command execution via an attacker-controlled string | mitigate | The executable set is a CLOSED, BUILD-TIME-GENERATED ALLOWLIST derived only from command markdown frontmatter committed to the repo. No runtime string, no MCP tool argument, no step field can add an entry. Plan 07's dispatcher may only run commands present in this generated registry. Established here so Plan 07 inherits it. |
| T-237-05-02 | Tampering | path traversal via a declared script path | mitigate | Task 2's `isLive` resolves the declared script with `path.resolve` against the repo root and asserts the resolved path stays under the repo root before any filesystem call, following the `write-scope-check.cjs::targetRoomUnderRoot` precedent. |
| T-237-05-03 | Elevation of Privilege | the seam check itself becoming an execution vector | mitigate | `isLive` performs only `fs.existsSync` and `fs.statSync(...).isFile()`. No `require`, no `eval`, no `new Function`, no `child_process`. Asserted as a grep acceptance criterion so a future edit cannot quietly add one. |
| T-237-05-04 | Tampering | hand-edited generated registry | mitigate | `data/command-registry.json` is regenerated by `scripts/build-command-registry.cjs` and the diff is reviewed to confirm only `executable` keys were added. The three `--check` gates are re-run after regeneration. |
| T-237-05-05 | Denial of Service | a malformed frontmatter block failing the whole build | mitigate | The builder emits `null` for any non-conforming `executable` block rather than throwing. A build that fails closed on one bad command markdown is a worse failure mode than a null join. |
| T-237-05-06 | Repudiation | a dead executable claim reading green | mitigate | Task 2's `claimedCount > 0` assertion plus the seeded-dead fixture plus the live rename-and-restore demonstration. Zero claims is vacuously live in the primitive, so the count assertion is what makes the gate real. |
| T-237-05-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan. `scripts/generate-hub.cjs` declares zero npm dependencies in its own header and node built-ins only; no dependency manifest is touched, so the package legitimacy gate has nothing to evaluate. |
</threat_model>
