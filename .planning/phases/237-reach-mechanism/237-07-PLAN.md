<objective>
Build the module that makes an approved chain step actually do something, and that tells the truth when it cannot.

Purpose: `lib/mcp/tools/chain.cjs::makeDefaultOnStep` is the wired default executor for every `chain_run` step. It opens room.db, writes one `memory_event` row labelled `chain_step_executed`, and returns `quality: 'high'`. It never resolves the step's command to anything runnable. The fabricated `quality: 'high'` is the load-bearing defect, not the missing execution: the chain-executor halts on `quality === LOW_QUALITY` and gates the next step on a low prior output, so returning `'high'` from a stub makes the entire chain read successful. Approving a Decision Gate today produces a log line and a green trace.

The hard constraint that shapes this module, and the single most important thing not to get wrong: **the MCP server process cannot execute a `/mos:` methodology command.** A methodology command is a markdown prompt with no executable behind it. Its designated executor is `agents/framework-runner.md`, a Claude Code SUBAGENT dispatched by the HOST from a command body. Claude Code exposes no mechanism for an MCP server to invoke a subagent, a slash command, or a model turn (elicitation is documented and supported; sampling is not documented anywhere and is treated as unavailable). Any implementation that claims to run a methodology command server-side will have faked it a second time, in the exact shape this milestone exists to remove.

So the design is two honest tiers. Tier 1, a script-backed command, genuinely spawns and verifies its artifact. Tier 2, a prompt-backed command, logs, returns `quality: null`, and hands back a machine-readable directive naming exactly what the host must dispatch. `null` rather than `'high'` is what makes the honesty structural: the chain stops propagating a fabricated success.

Output: `lib/core/chain-step-dispatcher.cjs` (new, shared, CJS) plus the unit gate that proves both tiers.
</objective>
