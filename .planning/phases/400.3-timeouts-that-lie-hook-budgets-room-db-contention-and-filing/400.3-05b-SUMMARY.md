# Phase 400.3 Plan 05b: The Part 8 room lexicon comes from a cached file while the room is unchanged

The guard hook no longer reads every node row and rebuilds every lexicon entry on each Brain or Theo call. A successful room.db build is saved inside the room as part8-lexicon-cache.json and used by any later process while its key still matches. The key reads the change feed of room.db (epoch and latest sequence), so a new node, a ROOM.md change, a moved room or changed code always rebuilds. A 0-byte, garbage or unreadable room.db fails closed and writes nothing.

## What changed (lib/core/part8-room-lexicon.cjs)

- The builder stamp: the plugin version of .claude-plugin/plugin.json and the sha256 of 7 files (see decisions), computed once per process; a read failure gives no cache read and no cache write.
- With a room.db: roomDbPresent first (a 0-byte or non-file room.db fails closed); one handle through openRoomDbReadOnlyForCaller; BEGIN; the trigger names, then readChangeLogMeta (epoch, latest sequence); the key {schema 1, builder, realpath, epoch, seq, ROOM.md head sha256, slug}. The key is usable only with the stamp, the change log and all 6 triggers.
- A usable key and a matching cache file give {ok: true, entries, source: 'cache'} with no node-row read. Otherwise the BASE rows are read on the same handle (_readDbEntries now takes the handle; its SQL, the table_info check and ROW_CAP are unchanged).
- After a successful room.db build with a usable key, the file is written to a temp name (pid and a random suffix, mode 0600, flag wx) and renamed over the cache file; any failure is ignored. Never for 'names', 'none', a failed build or an unusable key.
- Without a room.db: the BASE names-only path and its BASE memo key; no cache file.
- No new DatabaseSync site, no node:sqlite require, no network call (grep counts 0, 0 at BASE and after); lib/core/part8-egress-guard.cjs and hooks/hooks.json unchanged.

## Deviations from Plan

- [Rule 2 - correctness] The builder stamp also hashes lib/core/part8-script-proof.cjs and lib/core/part8-normalize.cjs. Both shape the folded fields of each entry (quick 261118-x1g), so a change in either must rebuild the cache. L11 checks the 5 files of the plan, which the key holds.
- [Rule 2 - correctness] With an unusable key (an older room without all 6 triggers, or a stamp failure) the in-process memo key also holds the db, wal and ROOM.md stat, as at BASE. A key without a moving sequence could keep a stale memo in a long-lived process (the MCP shim).
- The hook group (L12-L14) was written in the same RED step as the cache group, so Task 2 has no separate commit; the 1 feat commit holds both groups.
- In-process cost: the memo check now needs one read-only open per call (the key reads room.db). That is the OA-1 rule (the key read through the same door).

## Residual risks and follow-ups

- Every guard call still opens room.db read-only for the key values (OA-1).
- FOLLOW-UP: a writer-side refresh of the cache (for example after the post-write index) would make the first Brain call after a write cheaper; not built.
- A planted cache file with a matching key is trusted to the same degree as room.db (T-400.3-52, accepted).
