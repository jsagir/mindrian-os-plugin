## Open conflict (NEEDS_HUMAN)

- File: tests/test-261118-vbv-hook-telemetry-queue.cjs (not in files_modified of this plan). First new failing line: `FAIL - Q2 module load: the hook process never loads part8-egress-ontology.cjs or navigation.cjs and never calls openRoomDb: the queue module was not loaded (no enqueue ran)`. Rerun at load average 5.76: the same failure (deterministic, not a timing arm). Q1, Q3-Q10 pass.
- Cause (PROVEN by a spy run): Q2 starts the hook with `-r <spy>`. The spy writes `Object.keys(require.cache)` with fs.writeFileSync at process exit. After this plan the hook is 2 processes and both load the spy (review B-a, execArgv). The --inner child exits first (15 modules, the check and the queue enqueue run there); the parent exits last (3 modules: the hook, hook-deadline.cjs and their built-ins) and overwrites the file. So the reader sees the parent list, which never holds part8-egress-telemetry-queue.cjs. Q1 of the same file proves the enqueue still runs (exactly 1 queue line per hook spawn).
- This is the same class of test-harness assumption that the plan fixed in tests/test-386-web-credential-hook.cjs (Task 2 Step 4): one record per process. The product behaviour is the one the plan requires.
- Recommended fix (test only, 2 lines): in the Q2 spy, change the exit writer to `fs.appendFileSync(out, JSON.stringify(Object.keys(require.cache)) + '\n')`, and change the reader to the union of the lines (`fs.readFileSync(out, 'utf8').split('\n').filter(Boolean).map(JSON.parse).flat()`), with `fs.unlinkSync(out)` before each run. The 3 checks (the hook seen, ontology and navigation absent, the queue module present) then cover both processes. That edits a file outside files_modified (OR-9), so this executor did not make it.
