<objective>
Close FIX-04: all Phase 260 fixes ship in ONE batched push, the deployed surface is round-tripped
live, and a push freeze is declared before the Phase 261 ceremony window opens.

Purpose: `render.yaml` autodeploys `pws-brain-mcp` on every commit to `main` (autoDeploy on commit,
confirmed). Pushing 260-01, 260-03 and 260-04 separately would deploy a half-repaired ingest
pipeline to production two or three times, each time for the duration of a Docker build that pulls
torch. Worse, the Phase 261 admin window runs payloads THROUGH this pipeline; a deploy landing
mid-ceremony would swap the ingest code under a running window. One push, then a freeze, is the
whole point of the requirement.

Output: `scripts/verify-deployed-build.mjs`, the freeze declaration, the execution record, and one
`git push origin main` behind a navigator approval.

**Why a deploy-identity check is needed at all, and how it works.** Nothing on the HTTPS surface
exposes a code commit SHA. `/health` returns `{status, graph}` plus key-gated
`backend/nodeCount/vectorCount/indexName`; `brain_graph_version` is a GRAPH version, not a code
version. But a TOOL DESCRIPTION is code, served by the running build. Plan 260-03 rewrote
`normalize_framework_name`'s description and pinned it with a test, precisely so this plan can
scrape the string from `src/server.mjs`, call `tools/list` over HTTPS, and compare. Equal means the
deployed build is the pushed build. That is a measurement, not an assumption.

**What this plan can and cannot round-trip, stated before it starts.**

| Fix | Deployed-surface round-trip possible from here | Why |
|---|---|---|
| FIX-03 (`normalizeName`) | **YES** | `normalize_framework_name` is a registered MCP tool on the HTTPS surface; a read-tier key calls it |
| FIX-02 (alias self-loop guard) | **NO** | the guard lives in `resolveFramework`'s emitted statement; exercising it requires `ingestFramework`, which is admin-gated and deliberately not on the MCP surface |
| FIX-01 (additive props) | **NO** | same reason, plus it requires a real write against canon Memgraph, which is on Render's private network |

FIX-02 and FIX-01 are therefore DEPLOYED and then verified in the Phase 261 admin window via the
carry documents plans 260-01 and 260-04 produced. The execution record states this in those words.
Do not write "verified" next to a fix that was not exercised.

**Canon Part 8 check, stated not assumed:** this plan pushes Brain-repo code and calls a read-tier
methodology tool. No LOCAL room data is read, written, or referenced.
</objective>
