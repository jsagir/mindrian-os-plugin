## The plan 18 carry-over: toTierCandidates against the real decide() (the finding)

Plan 18 left `toTierCandidates` tested for shape only. Run against the real ranker and decide():

1. **Bare ids never steer.** The ids `toTierCandidates` returns are bare command names (`root-cause`); the ranker's rows and the ledger's ids are `/mos:root-cause`. `_applyTierFusion` drops any fused id that is not a ranker row, so the bare list is a silent no-op: on problem-definition and solution-design `rankForSelector` returned exactly the unsteered top three (`/mos:act, /mos:agentshield, /mos:analyze-needs`) with the bare list. The producer therefore writes `'/mos:' + name` (engine-local mapping; `toTierCandidates` and plan 18's NM3, which asserts `items[0].id === primary.command`, are left as they were). X6 pins both sides: bare leaves the ranker untouched, the producer's ids move it.
2. **Fusion keeps the face's set, not its order.** The ranker fuses by reciprocal rank with the registry list, and the registry position dominates the single face position, so the face's primary is not reliably first. Measured on a born room with the phase-109 seed graph, a DECISION_GATE turn, for the 14 nest folders of the fixture room: 11 compose a primary (assets, references and team compose none and fall back with reason `no_runnable_primary`); `decide()` produced a non-null `offer_next_step` for only 3 of the 14 either way (the margin gates, unchanged by this plan, null the rest). For those 3, the unsteered offer was `/mos:act` each time; with the face the offer became `/mos:analyze-timing` (market-analysis, in the face set, composed primary `/mos:user-needs`), `/mos:beautiful-question` (problem-definition, in the face set, primary `/mos:root-cause`) and `/mos:find-analogies` (solution-design, equal to the primary). So: offer inside the face's set 3 of 3, offer equal to the composed primary 1 of 3. A direct ranker probe over all 11 face-sourced nests showed the same shape (the fused top three holds the face's items; the primary is first in 5 of 11).
   **What this means:** ctx.tierCandidates carries the composed move first and the engine's offer follows the face's set, but "the engine proposes exactly the brief's primary" does not hold at the offer level. Making it hold needs the face list weighted in `_applyTierFusion` (lib/workflow/f-selector-ranker.cjs, outside this plan's files). I did not touch the ranker. This is the recommended follow-up; it is a Rule 4 call (a change to the shared ranker's fusion), so it is handed back, not done.

## Decisions and interpretations

- **The producer fires on any composed primary, with or without a keyed face.** The plan says "with no face it falls back to the ledger", but `nextMoveForSection` composes a primary from the contract, ledger, navigator table and job even when BRAIN.md is legacy or absent, and the brief (plan 18) shows that same primary. Falling back to the ledger there would make decide() disagree with the brief, which is the thing this plan removes. So "no face" is read as "no runnable primary": assets, references and team here, and any section outside the registry. For those the ledger has no row either (measured: `getSectionJob` is null for all four), so the fallback is a byte-identical no-op; X2 pins that and the sectionJobId and no-roomDir ledger paths deep-equal `buildLedgerCandidates`.
- **The surface fence stays in formatSuggestedNext.** The plan allowed deleting the `filterToNavigator` branch; `tests/test-205-surface-fence.cjs` pins that tool-router.cjs calls `filterToNavigator(`, so I kept it: a call site that offered a plumbing command still emits no footer, and nothing it offered is echoed.
- **formatSuggestedNext is not exported**, so X5 cuts the function from the shipped source and runs it in a vm sandbox with a pass-through `filterToNavigator`, rather than adding an export.
- **X2 split** into X2 (the fallback equals today's output; passes at RED, as the plan requires) and X2b (the reason is named; RED).
