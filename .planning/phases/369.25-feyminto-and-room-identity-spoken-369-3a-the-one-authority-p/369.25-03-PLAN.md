Decisions this plan fixes (Claude's discretion per CONTEXT "the storage shape of the identity rows beyond the seven named columns"; RESEARCH Assumptions A1, A2):
- The identity table is key/value (`key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL`, lib/core/memory-ops.cjs:25-29), so the seven named columns are seven keys: `room.room_id`, `room.slug`, `room.canonical_path`, `room.parent`, `room.depth`, `room.created_at`, `room.birth_version` (the `room.` prefix keeps them apart from the 7 migration and change-log rows measured on a born room).
- `room_id` is an opaque `crypto.randomUUID()` minted once at birth (ASVS V6: never a hand-rolled id), not `room:<slug>`: a renamed folder keeps its id, and a copy is caught by canonical_path, not by the id. The Room node id stays `room:<slug>` as the ruling names it.
- A value with no source is the literal string `unknown` (the column is NOT NULL); a top-level room's parent is the literal `none` (a known fact); depth is an integer string or `unknown`, never a default (the `_computeDepth` "defaults to 1" anti-pattern, room-birth.cjs:442-447).
- Repair may mint exactly one key, `room.room_id`, and only when no row, sentinel or ROOM.md carries one; the result names it `minted_by_repair` (RESEARCH Pitfall 9: a minted id is a new identity, not a recovered fact).
