<objective>
Close the GRAPHDB-01 data-loss hole at BOTH of its source sites.

**Site 1 (the RCA's site).** `rebuildGraph`'s unconditional
`DELETE FROM edges; DELETE FROM nodes;` (`lib/core/lazygraph-ops.cjs:545`) wipes every row in
both tables, including the `memory_event` append-only audit journal, human-confirmed
truth-claim nodes, decision nodes, and opportunity nodes carrying D-17 append-only
`stage_history[]`. The reindex that follows restores only the filesystem-derived
`Artifact`/`Section` subset, so every other population is permanently gone once the enclosing
transaction commits.

**Site 2 (found by adversarial verification, absent from the RCA and from 236-RESEARCH.md).**
`scripts/build-ecosystem-graph.cjs:146` runs the byte-identical statement
`conn.exec('DELETE FROM edges; DELETE FROM nodes;')` against the SAME
`<roomDir>/.mindrian/room.db` file (it resolves that path at `:139` and opens it through
`lazygraph-ops.cjs`'s `openGraph` at `:143`). It carries the same unscoped-DELETE data-loss
defect AND, unlike `rebuildGraph`, has no transaction at all: the wipe and the whole rewrite run
as bare autocommit statements, so a crash mid-run leaves a permanently emptied room and a
concurrent reader can observe the torn state. This site is in scope for Phase 236 because it is
the same unscoped-DELETE shape, not the HSI-specific shape Phase 242 owns.

This plan replaces both statements with an ownership-scoped DELETE driven by two exported
allowlist constants, adds the missing transaction to site 2, and proves each fix with a
mutation-provable survival test that is written FIRST and must be observed RED against the
current unscoped code before the fix lands.

**This is NOT a missing-transaction fix at site 1.** The `BEGIN`/`COMMIT`/`ROLLBACK` wrap at
`lazygraph-ops.cjs:542` / `:614-618` already exists, is already correct, and is preserved
byte-for-byte. See 236-RESEARCH.md Pitfall 1 and Pattern 3. Site 2 is the opposite case: it has
NO wrap, so adding one there is new work, not a modification of a working one.

Purpose: a destructive reindex is safe exactly to the degree its ownership scope is explicit
and enforced. Neither site has any, at any layer.
Output: two exported constants, two scoped DELETEs, one new transaction, one shared phase
fixture helper, two mutation-provable survival tests.
</objective>

Phase 242 ("The Moat", MOAT-01) owns the HSI-to-graph rewrite. This section exists so a human
can diff the two phases' write-paths before either executes.

**Explicitly NOT touched by Phase 236: `scripts/hsi-to-graph.cjs`.**

That file runs its own un-transacted wipe-then-rewrite at lines 61-62
(`DELETE FROM edges WHERE type = 'HSI_CONNECTION'` and the `'REVERSE_SALIENT'` equivalent) as
bare autocommit statements with a real torn-read window under WAL. The routed-in RCA names it
verbatim as "Named follow-up, out of scope here", and ROADMAP.md assigns it to Phase 242 via
the soft-dependency line ("242 reuses 236's proof pattern"). No plan in Phase 236 modifies,
imports from, or gates on `scripts/hsi-to-graph.cjs`.

**Why `scripts/build-ecosystem-graph.cjs` IS in scope while `scripts/hsi-to-graph.cjs` is NOT.**
Both live under `scripts/`, so the boundary is not the directory. It is the DEFECT SHAPE.
`hsi-to-graph.cjs` deletes through an already-scoped `WHERE type = 'HSI_CONNECTION'` predicate:
its only defect is the missing transaction, and its rewrite logic is the HSI scoring layer Phase
242 is rewriting wholesale, so fixing it here would collide with that rewrite.
`build-ecosystem-graph.cjs` carries the identical UNSCOPED `DELETE FROM edges; DELETE FROM
nodes;` statement this plan exists to eliminate, and Phase 242 does not touch it. Leaving it
would mean shipping a phase whose stated goal ("graph rebuild cannot erase memory rows") is
false the moment a user runs the ecosystem builder.

Note the edge types `hsi-to-graph.cjs` deletes (`HSI_CONNECTION`, `REVERSE_SALIENT`) are
deliberately absent from this plan's `INDEXER_OWNED_EDGE_TYPES`, so Phase 236's scoped rebuild
stops destroying Phase 242's scoring layer as a side effect. That is a one-way benefit and
creates no code coupling between the phases.
