Facts read while planning (re-prove each):
- A doctor module is a file under lib/core/doctor/ that exports check(ctx). data/doctor-modules.json lists it with these fields: id (kebab-case, unique), introduced_version (valid semver), cadence (always or once), flag (a string or null), fix_supported (an explicit boolean), runner (a repo path), description. tests/test-doctor-module-contract-parity.cjs enforces 9 rules, including: fix_supported false means the module must NOT export fix; check(scratch ctx) must not throw and must return a status in ok, warn, error or skip and a non-empty detail string; action_lines, when present, is a string array.
- scripts/doctor.cjs runs the registry through runAccumulativeEngine. That loop is synchronous, so check must be synchronous (no promise). A module whose introduced_version is above the running plugin version is deferred, so set introduced_version to the value printed by node lib/core/repo-version.cjs at execution time.
- The sibling eureka-fts-health-module.cjs is the style model: a long header with the contract, the Part 9 and Part 8 statements, and a check-only export.
- eureka-engine-enable.cjs exports checkEngine(root, deps), which spawns only uv --version and uv python find --no-project, and reads pyproject.toml by string matching. resolveEngine(env) and describeEngineState come from the resolver.
- The acceptance roll-up (node scripts/doctor.cjs --acceptance) reduces its own checklist points, not the registry rows. A registry row with status warn or skip does not fail it (verify this by running it before and after).
