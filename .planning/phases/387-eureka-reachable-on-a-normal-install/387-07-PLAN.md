<objective>
Add the doctor point that reports Eureka readiness (PRD scope item 5). Today the doctor has Eureka rows for the local measuring tool (class S smoke), the opt-in state and the lexical index, and none for the engine. A person who cannot reach the engine tools has no place to ask why.

Purpose: one honest line in /mos:doctor that says whether the engine is not set up (and that this is fine), ready for the graph tools, or set up but not ready, with the cause and the fix. The engine audits show why a naive check would lie: a prepared .venv does not show which package groups are installed, so a green check could still end in a refusal on the scout or the decision routes. The point therefore reads the installed package groups and names every route family that is not ready.
Output: a doctor module, its registry row, and a test written first.
</objective>

Decision recorded here: the doctor point uses the tool-to-extra probe (a read of the installed package groups) and not the engine's own eureka doctor. Reason: the engine doctor runs engine code, needs the encoder libraries (so it fails on a graph-only setup) and takes seconds; a doctor point must be fast, must not run engine code and must not fail a valid minimal setup. The engine's doctor stays available as the deep check of /mos:eureka enable engine --check --deep (Plan 387-09).

- A doctor module is a file under lib/core/doctor/ that exports check(ctx). data/doctor-modules.json lists it with these fields: id (kebab-case, unique), introduced_version (valid semver), cadence (always or once), flag (a string or null), fix_supported (an explicit boolean), runner (a repo path), description. tests/test-doctor-module-contract-parity.cjs enforces 9 rules, including: fix_supported false means the module must NOT export fix; check(scratch ctx) must not throw and must return a status in ok, warn, error or skip and a non-empty detail string; action_lines, when present, is a string array.
