<objective>
Implement D-05's two-axis capability floor (model capability AND host-tier, detected and stated honestly on both) by extending the existing `surface-detect.cjs` chokepoint with host-tier detection via the MCP SDK's `getClientVersion()`, and close Gap D (the Tier-0 write-path hole: `graph_write`/`memory_event`/`artifact_file` default OFF, so a foreign host reads but cannot write).

Purpose: `getClientVersion()` is only populated AFTER the `initialize` handshake completes, but tool REGISTRATION happens once at boot (`createServer()`, before any client connects) in every transport this codebase runs. This is a real, unavoidable timing conflict, not a style choice -- registration-time host-based gating is structurally impossible. This plan resolves it by moving the write-path gate from REGISTRATION time (visibility) to CALL time (permission): the three write tools are now always listed in `tools/list`, and each call evaluates a live, per-call host-tier lookup. This directly fixes the "silent one-way mirror" RESEARCH.md names as Gap D's actual failure mode (a foreign-host model today cannot even see graph_write exists to try it) and is the honest-degradation form D-05 requires, not the current invisible one.
Output: `detectHostTier()` in surface-detect.cjs; `isWritePathEnabled()` in mcp-first-flag.cjs; three tool handlers moved from registration-gate to call-gate; `status_read` extended with a capability_floor segment; `tests/test-234-host-tier.cjs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| MCP client clientInfo.name -> host-tier trust decision | `clientInfo.name` is CLIENT-SUPPLIED, unauthenticated data. Treat it as a UX/routing signal only, never a security boundary -- it determines DEFAULT write-path convenience, not whether writes are validated (navigation.cjs's own input validation/CAS checks are unaffected and still run on every write regardless of how the call was gated in). |
| Foreign host write call -> room.db | The write path itself is unchanged (still exclusively through navigation.cjs); this plan only changes WHO gets the default permission to reach it, not what happens once they do. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-234-08 | Elevation of Privilege | `isWritePathEnabled` trusting client-supplied `clientInfo.name` | accept | `clientInfo.name` only changes a DEFAULT convenience gate (whether MINDRIAN_MCP_FIRST-equivalent behavior applies), not authentication or authorization; the underlying write still goes through navigation.cjs's existing validation/CAS guard. A spoofed `clientInfo.name` at worst grants the same write path a legitimate Cursor user already gets by design -- this is a UX default, not an access-control boundary, matching D-04's framing that governance is enforced in the tool handler via room-scoped session binding, not via client self-identification. |
| T-234-09 | Denial of Service (silent) | Unknown/unrecognized host defaulting write path OFF | mitigate | This is the deliberate, documented resolution of the defensive-default-vs-no-silent-skip tension: the tool remains VISIBLE in tools/list and returns an informative `{ok:false, reason:'write_path_disabled', hint:...}` on call, never a silent catalog omission. A human or model reading the response can act on it (set MINDRIAN_MCP_FIRST). |
