## Observed vs Expected: What Deviated and Why

The plan expected Mode A3 (successful pull + atomic cache write + 1024-dim embeddings per entry). Observed Mode B3 (tier-0 empty substrate + warning "Brain offline and no cache"). Brain is NOT actually offline; the deviation root cause is a response-shape mismatch between `lib/core/brain-client.cjs` (search returns `{result: {hits: [...]}}`) and `lib/core/rs-brain-substrate.cjs::pullFromBrain` (expects `{matches: [...]}`). The shape mismatch trips the `!Array.isArray(result.matches)` guard in pullFromBrain, which returns `{ok: false, reason: 'malformed_response'}`, which loadSubstrate correctly translates to Mode B3 graceful-degradation.

Direct probe of the brain-client response captured for reference:

```
direct_result_top_keys: result, usage
direct_result.result_keys: hits
direct_result.hits_count: 3
direct_result.hits[0] keys: _id, _score, fields
direct_result.hits[0]._score: 0.8089869022369385
direct_result.hits[0]._id: mindrian-knowledge_t2-trending-absurd_2cddc6ac2cf58ea0
direct_result.hits[0].has_values: false (no embedding vector returned; only metadata and score)
direct_result.hits[0].has_fields: true (source_file, framework, content_hash, text, etc.)
direct.matches isArray: false (the shape pullFromBrain expects is not what brain-client returns)
```

Two findings from the direct probe:

1. Brain IS reachable and returns real data (3 hits with 0.8+ scores on a simple 'reverse salient' probe); the outage in the smoke test is NOT a network issue.
2. Even if the shape were adapted, the Brain search endpoint does NOT return embedding vectors in the `values` field; hits carry `fields` metadata (title, framework, content_hash, text) and a `_score` but no 1024-dim vector. The 1024-dim vector assertion in the plan's expected table assumed a search mode that returns Pinecone vectors directly, which is not what brain-client's default `search()` path produces.

## What This Smoke Proved (Positive Evidence)

All the Phase 89.1a architectural invariants under LIVE Brain conditions:

- **I1 (Canon Part 8 boundary).** preSendAudit ran, JSON.stringify scanned payload against FORBIDDEN_PATTERNS, produced `outcome:pass` with ONLY generic handles logged. Zero forbidden-regex hits. Zero user content on the wire.
- **I3 (Atomic write).** Zero orphan tmpfiles in `.mindrian/` after the call. Atomic semantics hold even on Mode B3 (no cache file written, no partial file left behind).
- **I4 (Graceful degradation).** loadSubstrate NEVER threw despite the response-shape mismatch. Returned structured `{success: true, mode: 'B3', substrate: [], warning: ...}`.
- **I5 (Frozen mode enum).** result.mode === 'B3' which is a member of RESULT_MODES = ['A1','A2','A3','B1','B2','B3'].
- **I7 (Chokepoint exclusivity).** The single outbound query went through buildBrainSubstrateQuery (verified by the audit line caller=pullFromBrain).

## What This Smoke Did NOT Prove (Deferred)

Two items cannot be asserted from this run and defer to a future post-ship plan:

- **I2 (1024-dim vector shape).** substrate is empty; no embedding[].length observation possible. Requires a pullFromBrain shape-adapter update AND a brain-client search mode that returns vectors (either `include_values=true` on a raw Pinecone query, or an alternate brain-client method).
- **Mode A3 happy-path cache write.** The cache file never landed because pullFromBrain returned `{ok: false}` and loadSubstrate took the offline-no-cache branch. The atomic-write path was not exercised end-to-end against real Brain data on this run (it IS exercised in Plan 03 Scenario 09 against a mocked pullFromBrain that returns the correct `{matches: [...]}` shape).

These two deferrals are NOT Phase 89.1a bugs. They are consumer-side integration work for the next phase that actually calls loadSubstrate against real Brain data and needs to reconcile the brain-client search shape with pullFromBrain's expected `matches[]` shape. Phase 89.1 (domain analysis consumer) or Phase 89.5 (engine orchestrator) is the natural landing site.
