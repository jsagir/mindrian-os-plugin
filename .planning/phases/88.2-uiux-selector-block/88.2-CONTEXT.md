# Phase 88.2: Selector Block Rollout (AskUserQuestion)

## Release target: v1.10.15 (tentative) or v1.11.0

## Goal

Wire `AskUserQuestion` (Shape F Selector Block) into every /mos: command with a genuine decision fork. Confidence-gated RECOMMENDED. Telemetry from day one. Polish remains (no prose-to-prose rewrites). This is the interactive primitive that the 71-command engine has been missing.

## Commands with framework forks (rollout targets)

Primary (must-have):
- `/mos:act` -- framework selection from 77-framework chain; plan mode renders here
- `/mos:suggest-next` -- next-move recommendation
- `/mos:diagnose` -- problem type classification
- `/mos:file-meeting` -- section routing
- `/mos:pipeline` -- step-to-step transitions
- `/mos:analyze-needs` -- which JTBD lens to apply
- `/mos:grade` / `/mos:deep-grade` -- which rubric dimension to probe next

Secondary (nice-to-have):
- `/mos:status` -- which section to drill into
- `/mos:find-analogies` -- which domain to cross
- `/mos:think-hats` -- which hat next

Not applicable (no fork):
- `/mos:help`, `/mos:rooms list`, `/mos:visualize`, display-only commands

## Risks (preview, not final)

- **R1 Over-rollout.** Adding selectors to commands that do not have genuine forks creates friction, not help. 88.2 audit must distinguish fork commands from one-shot commands.
- **R2 Confidence gating miscalibration.** If 0.7 threshold is too strict, no options ever carry RECOMMENDED and users lose the Brain's pedagogical nudge. Too loose, and wrong-default training returns. Telemetry from day one is the fix, not guessing.
- **R3 Plan-mode collapse confusion.** Users who expected a `--plan` flag may be surprised that plan mode lives inside a selector. Release note and /mos:help examples mitigate.

## Spec Amendment 2026-04-29 -- F.0 Mini Decision Gate + F.6 Plan Review Round

Added after the UI/UX moat survey (`.planning/research/uiux-moat-survey.md`) revealed that Shape F.1-F.5 cover the conventional next-move / path-control / depth / insight / branch decision moments but leave two high-leverage moments unspecified:

- **F.0 Mini Decision Gate** -- the smallest possible auq surface (1-2 questions, optional reject-reason capture) that fires INSIDE other shapes when a sub-decision needs typed-edge production without breaking the parent shape's flow.
- **F.6 Plan Review Round** -- a bounded round (15-30 questions) that converts long-form artifact review into a stream of typed edges. Mixes real questions sourced from the artifact's structural decomposition with calibration decoys. Implements the gamified-review pattern.

Both shapes are siblings of F.1-F.5, not replacements. They share the AskUserQuestion primitive and the existing invariants (3-5 options on F.0, 15-30 questions per F.6 round, Free-text always last where applicable, RECOMMENDED only at confidence >= 0.7).

### F.0 Mini Decision Gate -- spec

**Purpose:** capture a sub-decision as a typed edge without forking the parent shape. Most useful inside F.4 (Insight Extraction) when a single insight needs accept/reject with reason, or inside cascade approve/reject/defer flows where the legacy prose-confirmation pattern was leaking edges.

**Shape:**

```
                     ┌─ MINI ─────────────────────────────────────────┐
                     │  This insight changes your financial model     │
                     │  assumption. Apply the cascade?                │
                     │                                                │
                     │    1) Approve  -- cascade now                  │
                     │    2) Reject   -- capture reason -> graph data │
                     │    3) Defer    -- queue for milestone audit    │
                     └────────────────────────────────────────────────┘
```

**Invariants:**
- Exactly 3 options. Approve / Reject (with reason) / Defer. No Free-text slot (the reason field on Reject IS the free-text path).
- Reject-with-reason is one keystroke + one prompt. The reason becomes a `REJECTED_BECAUSE` typed edge property on the rejection edge.
- F.0 ALWAYS produces a typed edge. There is no silent dismiss path. (Silent rejections are the system's failure mode per Canon Part 4.)
- F.0 is composable. It can render INSIDE F.4 (Insight Extraction), inside cascade flows, inside session-start banner consolidation (Phase 96.5), and inside browser graph node clicks (Phase 96).

**Cool-UI/UX direction:** the F.0 box is rendered with a thin border (single-line ASCII), tighter than the standard F.1-F.5 box (double-line). Visual cue: this is a sub-decision, not a fork. The reject-with-reason field accepts inline editing without re-prompting.

### F.6 Plan Review Round -- spec

**Purpose:** convert long-form artifact review into a typed-edge stream. The CLI surface is boring when reading 200-line plans. Twenty short auq questions consume the same total cognitive effort as one long-form read but break it into compressible chunks the navigator can stop, resume, and re-enter without losing place. Each answer becomes a `REVIEWED` typed edge.

**Shape (one question render, 1-of-N):**

```
                     ┌─ ROUND 7 of 20 -- PLAN REVIEW ─────────────────┐
                     │  Phase 89 reverse-salient-engine               │
                     │                                                │
                     │  As a navigator, I confirm:                    │
                     │  "Phase 89 ships rs-external Pinecone with     │
                     │   only public OpenAlex/arXiv metadata."        │
                     │                                                │
                     │    1) Confirm                                  │
                     │    2) Reject  -- capture reason                │
                     │    3) Discuss -- park for synchronous review   │
                     │                                                │
                     │  ▶ progress  ━━━━━━━━░░░░░░░░░░░░  35%         │
                     │  ⚠ reject 1   ◆ discuss 0   ✓ confirm 5         │
                     └────────────────────────────────────────────────┘
```

**Invariants:**
- Round size: 15-30 questions. Default 20. Real:decoy ratio 4:1 by default (16 real + 4 calibration decoys per 20-question round).
- Real questions are user-stories sourced from the artifact's structural decomposition (tasks, gates, dependencies, acceptance criteria, success metrics).
- Decoys are NOT disclosed during the round. Debrief surface (Shape A Action Report) renders at round end with full decoy disclosure. See `room/decisions/decision-decoy-ethics.md` for the ethics contract.
- Each response writes one `REVIEWED` typed edge with properties `{round_id, position, latency_ms, was_decoy, response, confidence_self_report}`. Position-aware so debrief can identify which decoys were caught vs missed.
- Cowork concurrency: parallel actor responses captured per `actor_id`. Divergence triggers F.5 Branch Resolution. See `room/decisions/decision-cowork-round-locking.md` for the concurrency contract.
- Round can be paused mid-stream via `q` keystroke. Resume continues where the round paused, no progress lost. Pause state persists across session restarts (the round-state graph node survives).

**Decoy generation tiers:**
- Tier 0 (Brain unreachable): pattern-based perturbation from the artifact itself. Substitute wrong owner / wrong dependency / wrong success criterion. Algorithmic.
- Tier 1 (Brain reachable): teaching-graph-aware decoys keyed off framework chaining rules. Pulls plausible-but-wrong substitutions calibrated against student-grading data.
- Tier 2 (cross-session): personalized decoys keyed off the navigator's prior comprehension profile. Harder decoys in weak spots, easier in strong spots. Profile is graph-local per Canon Part 8.

**Cool-UI/UX direction:** the round box is double-line border (parent shape, not sub-decision). The progress bar is the cool surface -- it animates per response and the count chips (`reject 1 / discuss 0 / confirm 5`) update inline. The debrief Shape A at round end carries the moat density: comprehension tier, trend across last N rounds, missed-decoy review surface.

### Three-surface compatibility for F.0 + F.6

| Surface | F.0 | F.6 |
|---------|-----|-----|
| CLI | Native AskUserQuestion render. Single-line ASCII border (F.0) / double-line border (F.6). | Native AskUserQuestion chained back-to-back. Round state in `<roomDir>/.mindrian/round-<round_id>.json`. |
| Desktop | Larry voice presents the F.0 / F.6 question conversationally. Selector still rendered as auq under the hood. Cool surface: Larry varies the framing per hat. | Round renders as a Larry-narrated review session. Larry voices the user-stories. Less mechanical than CLI, same edges produced. |
| Cowork | F.0 fires per actor. Divergence captured per decision-cowork-round-locking.md. | Multi-actor rounds capture parallel responses per `actor_id`. Divergence detection at round-end. |
