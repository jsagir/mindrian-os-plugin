<objective>
Close OQ-5 and produce the phase's token baseline.

**OQ-5, the Part 11 R1 born-wired gap.** `detect_dual_path` and `extract_shallow` are registered
inline at `bin/mindrian-mcp-server.cjs:187` and `:199` with no `connectors` export.
`scripts/build-connector-registry.cjs` discovers only `lib/mcp/tools/*.cjs` plus
`lib/mcp/tool-router.cjs` plus `lib/mcp/contract-version.cjs` (`:328-420`), so a tool registered
inline in `bin/` is structurally invisible to it. Those two therefore appear in neither
`data/mcp-tool-connectors.json` (21 entries, enumerated in RESEARCH.md 2.1) nor
`data/connector-registry.json`, and carry no hitl_shape at any granularity. The fix is not a
registry edit. It is moving the registration into the shape the generator already discovers.

**The token baseline.** RESEARCH.md's Known Gap says it plainly: "I did not measure actual token
counts for any tool schema. The phase needs real before/after numbers and the harness exists, but
running it was outside this research pass. The plan's Wave 1 must produce them."

Pitfall P2 is why this is a task and not an assumption: fewer tools does not automatically mean
fewer tokens, and a single unified schema over N operations can exceed N small schemas. And
RESEARCH.md 2.3 corrected Phase 268's framing: `alwaysLoad` is a SERVER-level flag in
`.mcp.json:6` and `:11`, not a per-tool one (exhaustive grep, three hits, all accounted for), so
per-tool deferred loading is not expressible against this codebase. Reducing the number and size of
registered descriptions is the ONLY token lever this repo has. Measuring it is therefore the only
honest way to know whether this phase's net effect is positive.

Purpose: no dark surfaces, and no unmeasured claims.
Output: one new tool module, two regenerated registries, one measured baseline.
