<objective>
Close the finding that originated this whole phase: `~/.mindrian-user.md`, the promised cross-room
"who is this user" file, has zero writers anywhere in the repo despite onboarding prose asserting it
exists (Phase 267.1's GAP I-1).

**RESEARCH.md 4.3 is a correction that collapses the task, and this plan must not undo it.** The
grounding, the Phase 267.1 audit and the ROADMAP all framed this as needing a net-new mechanism. It
does not:

- `writeUserMdAtomic(userMdPath, data)` (`lib/core/user-md-ops.cjs:442`) takes an ABSOLUTE FILE PATH
  as its first parameter and has ZERO room coupling. Verified by negative grep:
  `grep -n "roomDir\|room_dir\|ROOM.md\|resolveActiveRoom\|MindrianRooms" lib/core/user-md-ops.cjs`
  returns nothing. It is a pure path-taking atomic writer (tmp with `openSync('wx')`, `writeSync`,
  best-effort `fsyncSync`, `renameSync`, unlink-on-error, per-pid plus random tmp suffix, documented
  at `:420-440`) that preserves any user-authored body below the frontmatter.
- The room coupling is entirely in its two production CALL SITES,
  `lib/core/navigation/room-birth.cjs:572` and `:801`, both writing to
  `path.join(roomDir, 'USER.md')`.
- **Therefore `writeUserMdAtomic(path.join(os.homedir(), '.mindrian-user.md'), data)` works today,
  unmodified.**
- The READ side is already wired: `lib/core/user-archetype.cjs:64` already does
  `safeReadFile(path.join(require('os').homedir(), '.mindrian-user.md'))` as the third fallback in
  the archetype signal chain.
- Home-directory writes are ubiquitous and precedented: roughly 20 call sites under `~/.mindrian/`,
  including atomic tmp-plus-rename patterns at `lib/core/scratchpad-ops.cjs:302-303`,
  `lib/core/persona-override.cjs:189-215` and `lib/core/card-fire-sidechannel.cjs:217-223`.

**What is actually missing is a caller and a trigger, not a mechanism.** This plan ships the caller.
It does NOT ship the trigger.

**The caveat that must be written down, not glossed.** RESEARCH.md 4.3's own closing paragraph: a
first install may have no MCP session at all, and the FIRST_INSTALL surface is a bash hook injecting
prose (`scripts/session-start`). An MCP tool the model must CHOOSE to call is still
model-compliance-dependent, which is exactly the fragility Phase 267.2's own goal text names about
`check-onboard --write`. **Making it a tool does not by itself make it deterministic.** A hook-side
writer may be more deterministic. That decision overlaps Phase 267.2 W2 and Phase 267.3 and must be
made once across all three phases. This plan hands them a working mechanism and an honest note.

Purpose: give Phase 267.2 something concrete to trigger, instead of asking it to build both halves.
Output: one new born-wired Tool, a cross-reference note, and the pre-room reachability pin green.
</objective>
