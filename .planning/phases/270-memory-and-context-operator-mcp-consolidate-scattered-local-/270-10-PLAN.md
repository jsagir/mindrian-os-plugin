<objective>
Add the genuinely graph-native capability: two reads that a flat tree or a KV store structurally
could not answer.

RESEARCH.md 3.3 tested the grounding claim that only one query is genuinely multi-hop and found the
grounding **undercounts**. Three already are:

| Query | Where | Hop character |
|---|---|---|
| `findContradictions` | `insights.cjs:43-66` | `getNeighborhood(db, focus, {maxDepth:2, topK:200})`, builds a reachable set, filters `CONTRADICTS` edges where BOTH endpoints are inside it |
| `findBlockingAssumptions` | `insights.cjs:85-108` | `WITH RECURSIVE cascade(id, depth)` over `DEPENDS_ON` plus `ASSUMES`, `WHERE c.depth < 5`. A true recursive CTE |
| `rollupSubRooms` | `graph-derivation.cjs:33-40` | Recursive, transitive, cross-room-db `ATTACH`, cycle-guarded, arbitrary depth. The only cross-room traversal in the system |

And several adjacent ones in the same file are left flat. `findUnsupportedClaims` (`:68-83`) asks
only `NOT EXISTS (SELECT 1 FROM edges e WHERE e.target = n.id AND e.type='SUPPORTS')`: edge-aware,
single-hop. `findStaleDecisions` (`:110-125`) is a node-table scan with no edge predicate at all.

**The two capabilities this plan adds, both from RESEARCH.md 3.3's ranked candidate list:**

1. **Transitive support closure** (candidate 2). The genuinely graph-native version of
   `findUnsupportedClaims` asks "is this claim supported TRANSITIVELY through intermediate nodes, or
   supported only via a different edge type such as `EVIDENCES`." The recursive-CTE pattern to do it
   already exists two functions away. This is Canon Part 7 reuse of an IN-FILE pattern, not new
   machinery.
2. **Structural-distance-gated relevance across the ICM forest** (candidate 1, ranked first).
   `NESTED_WITHIN` makes the room tree a graph, and `rollupSubRooms` already traverses it
   transitively across room.db boundaries. A flat filesystem walk can tell you a folder exists; only
   the graph can answer "which sub-room's decisions are structurally nearest to the claim I am
   looking at, across the room boundary."

**The hard constraint this plan must carry.** `graph-derivation.cjs:44-46` states the rollup
"READS, never writes a cross-room row into the parent," and `edges.cjs:45` records "Cross-room
aggregation forbidden (Phase 8 cross-room fence)." The operator may READ across rooms and must NOT
materialize a cross-room edge. Design to that line explicitly; `tests/test-270-cross-room-fence.cjs`
legs 3, 4 and 5 enforce it.

**What this plan must NOT do.** RESEARCH.md 3.3's closing line: do not re-expose `graph_query` (a
bare `getNeighborhood` wrapper) under a new name and call it graph-native. It already exists and is
already thin.

Purpose: earn the word "graph-native" with two queries a flat store cannot express.
Output: two new core functions, one new born-wired Tool, and the cross-room fence proven green.
</objective>
