<objective>
Expose the ICM forest as a Resource, and make the resource list change when the forest does.

**Why a Resource and not a Tool.** RESEARCH.md 3.4 derives the rule and 4.1 item 1 applies it: a
capability belongs behind a Resource when it is a pure read, its result is browsable, it takes at
most path-like parameters expressible in a URI template, and it has no fork. The tree is all four.
And it matters materially: `lib/mcp/resources.cjs:4-5` states the reason verbatim, "Resources let
Desktop users browse room state without tool calls (application-controlled, zero token cost)". Given
RESEARCH.md 2.3's correction that `alwaysLoad` is server-level and the only token lever this repo
has is the number and size of registered tool descriptions, moving read surface OFF the tool schema
budget is the whole point.

**Why this is not blocked on Phase 267.** RESEARCH.md 3.4a is the most important unblocking finding
in the phase and this plan is where it cashes out. `node_modules/@modelcontextprotocol/sdk/dist/cjs/server/mcp.js:451-524`
shows `resource()` and `registerResource()` both call `this.sendResourceListChanged()`, and
`_createRegisteredResource` returns a handle with `enable()`, `disable()`, `remove()` and `update()`,
where `update()` also fires the notification. The repo is on `@modelcontextprotocol/sdk: ^1.29.0`.
So a resource list that changes mid-session is buildable TODAY, on the currently vendored SDK, with
zero dependency on Phase 267's blocked `ext-apps` pin. Phase 270 sits numerically near a BLOCKED
phase and the association is easy to assume; it does not apply.

**Why dynamic discovery needs no registration step.** RESEARCH.md 3.4b: a `ResourceTemplate`'s `list`
callback ALREADY re-evaluates per `resources/list`. `lib/mcp/resources.cjs:69-81` proves it,
calling `discoverSections(roomDir)` fresh each time. Extending that to the forest is a direct
analogue of a shipped pattern, not an invention.

**Why the watcher is the token-budget lever.** `docs/research/RESEARCH_19_MCP_PERSISTENT_AGENTS.md:159`,
verbatim: "MCP uses a modified pub-sub pattern. The server sends a lightweight 'something changed'
notification; the CLIENT then decides whether to fetch updated content via `resources/read`. This
decouples notification from data transfer." That decoupling IS the "let the caller see and control
the cost of pulling context into the window" affordance the navigator asked for.

Purpose: browsable, live, zero-per-turn-cost awareness of the room forest.
Output: two new Resources, one watcher module, one boot wiring.
</objective>
