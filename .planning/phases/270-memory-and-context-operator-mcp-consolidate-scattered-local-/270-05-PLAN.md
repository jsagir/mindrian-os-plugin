<objective>
Fix the Resource boot-binding defect. This is the correctness-first plan RESEARCH.md's Pitfall P3
insists must land before any new Resource is added, or every new Resource inherits stale room
resolution.

The defect, verified end to end in RESEARCH.md 3.4d:

- **Resources** bind once at boot. `bin/mindrian-mcp-server.cjs:214` calls
  `registerResources(s, roomDir)` where `roomDir = path.resolve(process.env.MINDRIAN_ROOM || './room')`
  (`:119`), and `lib/mcp/resources.cjs:33` closes over that string for the life of the process.
- **Tools** resolve per call. Every handler runs `resolveSessionRoomDir(sessionId, ctx)`
  (`lib/mcp/session-room.cjs:116`), the single MCP resolver Phase 248-01 introduced to replace nine
  independent copies, whose header at `:11-16` records that "binding reads are now UNCONDITIONAL"
  so `room_bind` is finally honored.

Consequence: after a `room_bind`, `room_state_bound` returns the newly bound room's STATE.md while
`room://state` still returns the boot room's. Both call the same `stateOps.getState(roomDir)`
(`room.cjs:223-224` and `resources.cjs:42`). Same data, same reader, divergent room, and the
Resource is the wrong one.

This is also the concrete instance of OQ-4: Resources are the Desktop-facing surface and Tools are
the CLI-facing surface, and they disagree about which room the session is in. The langtalks corpus
returned nothing on multi-surface memory consistency, so this phase treats the parity as a designed
invariant with a test rather than as a researched pattern, and cites no external source for it.

**This plan adds NO new Resource.** `mos://tree` lands in plan 270-08, after this.

Purpose: make the Resource layer trustworthy before building on it.
Output: `registerResources(server, ctx)` with per-read resolution, and one changed call site.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| MCP session -> room directory | A session must read only the room it is bound to. Before this plan, a Resource read whatever room the process booted with, regardless of binding. |
| MCP client -> MCP server | The `extra` argument carrying `sessionId` is client-supplied. It selects a room; it must never select a path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-270-01 | Tampering | `lib/mcp/resources.cjs` room binding | mitigate | Per-read `resolveSessionRoomDir(sessionId, ctx)` through the single MCP resolver; pinned by `tests/test-270-resource-session-room.cjs` legs 1-3 |
| T-270-14 | Spoofing | a client-supplied `sessionId` selecting an arbitrary directory | mitigate | The session id is never joined into a path. `resolveMcpSessionRoom` looks it up in the room registry and falls back through `reg.active` -> `ctx.fallbackRoomDir` -> `process.cwd()`. No new path construction is added by this plan (ASVS V5) |
| T-270-15 | Elevation of Privilege | a read-side resolver acquiring the write-path `.room-root` cwd walk-up | mitigate | Resources call `resolveSessionRoomDir(sessionId, ctx)`, which does NOT set `forWrite`, so the `resolveWriteRoom` leg (`session-room.cjs:74-79`) is structurally excluded. That exclusion is the resolver's own documented purpose; do not pass `forWrite` |
| T-270-07 | Information Disclosure | Part 8 egress from a Resource handler | accept | This tool family is Part-8-inert by construction (RESEARCH.md 2.4) and this plan adds no network call. Guarded by the acceptance grep and by the three existing enforcement layers, which this plan neither adds to nor claims to |
| T-270-SC | Tampering | npm/pip/cargo installs | accept | Zero package installs. No dependency change; `git diff --stat package.json` is empty. |
