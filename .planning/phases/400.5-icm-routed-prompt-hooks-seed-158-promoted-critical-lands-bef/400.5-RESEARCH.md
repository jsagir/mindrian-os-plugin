## E. Process-wide state that a long-lived server must manage

- F-12 PROVEN. `lib/core/hook-busy-cap.cjs:17-39`: `_cap` and `_tripped` are module state. `setHookBusyCap(ms)` keeps the smaller value and never clears a trip (:20-26). `capBusyMs` returns 0 after a trip (:28-33). - F-13 PROVEN. `lib/core/room-db.cjs:304-310`: `new DatabaseSync(dbPath, { timeout: busyTimeout })`. ## I. Risks found by reading (not yet in any earlier report)

- F-27 GUESS. Two hook outputs (command + mcp_tool) reach the model as two system reminders, one per hook, each starting with the hook name (plan 13 :91 records that rule for command hooks). The text per check is the same; the framing changes from six reminders to two. Check: the spike leg of DESIGN section 9 records the attachment text.
- F-28 GUESS. In MCP-first mode (`MINDRIAN_MCP_FIRST` on, HTTP daemon), one server process can serve several sessions. The classifier serialization (F-15) then queues prompts of different sessions. The default is off, and the CLI path is stdio. Check: name the mode in the design and test only stdio.
- F-29 GUESS. SQLite locks are per connection, not per process. Moving the writers into the server removes the lock waits between the six hook processes, but not the waits against other sessions, other hook events (PostToolUse, Stop) or a server tool that holds a write transaction across an await. The gain is "fewer contenders", not "no lock wait". Check: the D1-shaped budget leg with a lock held by a separate process.
- F-30 PROVEN. The mcp_tool hook cannot pass a secret: `input` substitutes only from the hook JSON input (F-04), which the host builds. A tool call from the model can supply the same fields. Any discriminator between a hook call and a model call must come from the host request itself (GUESS: `extra._meta` or request ids differ; check in the spike).
