# Phase 400.5 CONTEXT: prompt hooks inside the running server

## 1. Phase goal

Source: `.planning/ROADMAP.md:4307` (navigator text, 2026-11-26).

Prompt-time help (the F.1 card, the statusline cue, the per-turn navigation context) is made inside the MindrianOS MCP server that is already running. A cold user on a loaded machine then gets that help on every prompt, with no cold start and no cross-process lock wait. The safety checks stay command hooks, and nothing can switch them off.

Problem it solves: on 2026-11-26 all six UserPromptSubmit hooks timed out together on one prompt. Two of them do no database work. The host was starved (IO pressure about 13 %, load average 20 on 12 cores), and six node cold starts per prompt multiplied the exposure (`.planning/debug/userpromptsubmit-hook-timeouts-under-load.md:37-42`).

## 4. New facts found in this elephant step (they change the design)

Full evidence is in 400.5-RESEARCH.md. The facts with most effect:

1. Matching hooks of one event run in parallel, and the host gives no order (RESEARCH F-03). Thus the words "the invariant tier runs first" in G5 cannot hold across two hook entries. Today the six hooks also run in parallel, so parity with today holds. See OR-1.
2. The busy cap of plan 10 (`lib/core/hook-busy-cap.cjs:17-39`) is process-wide module state. It only gets smaller and it never clears. Inside the long-lived server, the first hook call would cap every later room.db open of every MCP tool in that session at 750 ms, and after one busy result at 0 ms (RESEARCH F-12). The design scopes the cap to the hook call (DESIGN section 5.3).
3. The MCP-tool connector projection has no EXCLUDED branch. Every MCP tool is projected with `connects_to_spine: true` (`scripts/build-connector-registry.cjs:477-505`; RESEARCH F-20). G7 needs a small generator change. See OR-5.
4. The tool budget test pins the exact tool count, 76 (`tests/test-270-tool-schema-budget.cjs:532-542`). One new tool needs an authorised re-baseline to 77 (RESEARCH F-21). See OR-7.
5. The ROADMAP lists the routable tier in an order that is not the hooks.json order (RESEARCH F-02). See OR-2.
6. The docs say that on an event that can block, the host waits for a connecting server up to MCP_TIMEOUT (RESEARCH F-04). The spike did not force this case. The first-prompt loss can be smaller than the spike suggests, or the hook can wait past its timeout. A measurement leg is required (DESIGN section 7).
7. `400.4-QA-SOURCE-F11-hook-timeouts.md` is not in this worktree or in git history (RESEARCH F-00). The same RCA content is in `.planning/debug/userpromptsubmit-hook-timeouts-under-load.md`. This CONTEXT cites that file.

## 5. Open owner rulings

Each item needs an owner answer before /gsd-plan-phase. The DESIGN uses the recommended option and names the alternative.

### OR-1. "Runs first" in G5, given that the host runs hooks in parallel
- Option A (recommended): accept parallel execution, as the six hooks run today. A block from admin-command-gate still blocks the prompt (exit 2 from its command hook). The routable checks can still run on a blocked admin prompt, which is today's behaviour. Reword G5 to "the invariant tier is a separate command hook; nothing in the routable tier can stop it or replace it".
- Option B: make the routable tool wait for an invariant-tier record of the same turn before it runs. This adds the cold start of the command hook to the routable path again. That removes most of the gain of the phase.
- Option C: run the admin gate inside the server as well. Not recommended: a timeout or tool error is silent (spike result 5), and block semantics from a tool are unproven.

### OR-2. Order of the routable tier
- Option A (recommended): the hooks.json order of today and of plan 13: intent-classifier, brain-derivation-drain, jtbd-update (userprompt), auto-explore-drain (`hooks/hooks.json:342-397`; INPUT plan 13 line 29). The classifier has the largest output and the largest user value (the NAV block), so it gets the first share of the deadline.
- Option B: the order written in ROADMAP.md:4315 (brain-derivation-drain, auto-explore-drain, jtbd-update, intent-classifier). The classifier then runs last and is the first to lose time under load.

### OR-3. Shape of the invariant tier
- Option A (recommended): one new command entry, `scripts/userprompt-invariant.cjs`, that calls run() of admin-command-gate and then of first-install-router in one process, and also writes the turn ledger for OR-4. UserPromptSubmit then starts one node process and one MCP call per prompt, not six processes.
- Option B: keep the two existing command entries unchanged and add the turn-ledger write to one of them. This gives two processes per prompt and changes the admin gate least.

### OR-4. First-prompt and server-down behaviour (G8, G13)
- Option A (recommended): typed skip note. The invariant command hook keeps a per-session turn ledger. The server tool records each turn that it served. When the command hook sees that an earlier turn was not served, it adds one plain line of context, for example "MindrianOS prompt help was skipped on 1 earlier prompt (server_not_answering)". The note comes from the command hook, so it also works when the server is down. No prewarm (Stage 8 S4).
- Option B: command fallback. The invariant hook also runs the four routable checks when the session has no "server answered" record. Risk: on the first prompt both paths can run the checks, and the drains and the classifier then run twice.
- Option C: raise the mcp_tool timeout above 3 s to cover the cold connect. This conflicts with G13 if G13 binds 400.5. The owner must say whether G13 binds 400.5.
- In all options: a measurement leg forces a slow server start and records what the host does (wait up to MCP_TIMEOUT, cancel, or skip). The result goes in the SUMMARY.

### OR-5. How to declare an MCP tool EXCLUDED (G7)
- Option A (recommended): add `excluded: true` and a required `reason` to the MCP-tool connector descriptor. The generator projects the entry with `excluded: true`, the reason, and no spine wiring. A missing reason fails `--check`, the same rule as for commands and skills (`scripts/build-connector-registry.cjs:737-774`). The tool still counts in the tool budget.
- Option B: register the tool WIRED with `hitl_shape: 'none'` and `layer: 'harness'`, as `stop_gate_check` does today (`lib/mcp/tools/stop-gate.cjs:80-88`). No generator change, but this does not meet the word EXCLUDED in G7.

### OR-6. What makes a direct model call harmless (G7)
- Option A (recommended): first a spike leg that compares a hook call and a model call of the same tool (request `_meta`, `extra` fields). If a reliable marker exists, the tool refuses a call without the hook marker with a typed reason `not_a_hook_call`.
- Option B (fallback when no marker exists): per-session replay guard plus a transcript check. A second call for the same session and prompt returns the stored context and writes nothing. A call whose prompt is not the last user prompt in `transcript_path` is refused. Whether the host has written the prompt to the transcript when UserPromptSubmit fires is UNVERIFIED; the spike leg must check it.
- Option C: accept the residual risk. A model call runs the four checks on a prompt that the model wrote. Effects stay local (the per-turn JTBD intent and the cue record get a wrong value until the next real prompt). The owner must accept this in writing, because G7 says "harmless".

### OR-7. Tool-budget re-baseline
- Option A (recommended): authorise one pin move of `tests/test-270-tool-schema-budget.cjs` AFTER from 76 to 77 tools, with the byte delta recorded in the file, by the 374-13 precedent (`tests/test-270-tool-schema-budget.cjs:506-531`). Keep the description short (target under 600 bytes) so that the per-turn token cost on Desktop and Cowork stays small.
- Option B: fold the hook entry into an existing router tool as a sub-command. No count change, but the hook then depends on a router tool that the model uses for real work, and the EXCLUDED declaration (G7) has no single tool to attach to.

### OR-8. The hook timeout of the mcp_tool entry
- Option A (recommended): 3 s, the value of five of the six hooks today. The tool answers inside 2,500 ms of receipt (plan 13 DEADLINE_MS). This does not raise a budget.
- Option B: 5 s, the old intent-classifier value. Within "do not raise", because the classifier had 5 s, but it lets a starved prompt wait longer.

### OR-9. Engineering choice for the busy cap in the server (delegable)
The plan 12 hand-off asks 400.5 to decide (`400.4-12-SUMMARY.md`, "Risks and hand-off"). The owner may delegate this item.
- Option A (recommended): scope the cap to the hook call with `AsyncLocalStorage`, so only room.db opens made inside a hook call are capped, and the trip is per call. Other MCP tools keep the 5,000 ms wait.
- Option B: reset the cap before and after each hook call. This is racy: an MCP tool call that runs during the hook call's awaits also gets the cap.
- Option C: keep the process-wide cap. Not recommended (CONTEXT section 4 item 2).

## 6. Out of scope

- Per-nest routing, applies_when predicates, a precompiled routing record, a nest-declared check list, suggest_next changes (G2).
- Every hook event other than UserPromptSubmit. Phase 402 keeps hook consolidation for SessionStart, PreCompact, PostCompact, Stop, SessionEnd, PreToolUse, PostToolUse, FileChanged, CwdChanged, SubagentStop and TaskCompleted.
- Changes to the output of any check. Parity is the contract (G10).
- A prewarm or keep-alive mechanism for the server (Stage 8 S4), unless the OR-4 measurement shows that the loss matters and the owner asks for it.

## 7. Tri-polar statement

UserPromptSubmit hooks run on Claude Code CLI only. Claude Desktop and Cowork run no UserPromptSubmit hook, so their behaviour does not change. The new MCP tool is visible on all three surfaces, because the same server serves them. Its description cost is paid on every surface (OR-7), and the EXCLUDED declaration and the refusal of a direct call (OR-6) apply on every surface.
