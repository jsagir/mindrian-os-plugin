### 2.2 hostView rules (ported from plan 13 P5, INPUT plan 13 line 206)

`hostView({code, stdout, stderr})` returns `{kind: 'none' | 'context' | 'block', context, systemMessage, stop, blockText}`:
1. Code 2: a block; `blockText` = the stderr text.
2. Code 1 or any other non-zero code except 2: nothing.
3. Stdout empty or only whitespace: nothing.
4. Stdout that is exactly one JSON object with only whitespace around it: a JSON view. Read `hookSpecificOutput.additionalContext` (string), `systemMessage` (string), `continue === false` with `stopReason`, and `decision === 'block'` with `reason` (a block with `blockText` = reason).
5. Stdout that starts with `{` and ends with `}` but does not parse (for example `{bad}`): nothing (a host parse failure).
6. Any other stdout (for example a JSON object plus a trailing plain line): the whole stdout is plain-text context.
7. Trailing whitespace of a context string is trimmed. The parity comparison trims both sides.

`mergeViews(views)`: `additionalContext` = the non-empty context strings in check order, joined with `CONTEXT_SEPARATOR`; `systemMessage` = the non-empty values joined with "\n"; the first stop wins; the first block wins and later views are not read. A joined context over `CONTEXT_CAP_CHARS` gives the note `context_over_cap <total>: <id>=<len>, ...` and is never truncated (plan 13).

### 2.3 Output of each tier (exact)

| Tier | Case | Output |
|---|---|---|

| invariant | context or note | exit 0, stdout `{"continue":true,"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"<router context>\n\n<note>"}}` (only the parts that exist) |
| invariant | nothing | exit 0, stdout `{"continue":true}` (plan 13 empty rule, unchanged) |
| routable (tool) | context | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"<joined>"}}`, plus `"systemMessage":"<joined>"` only when a check gave one (the classifier does, `scripts/intent-classifier.cjs:595`, `:917`, `:3268`, `:3530`) |
| routable | nothing | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":""}}` (UNVERIFIED, L4) |
| routable | refusal | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":""},"refused":"not_a_hook_call"}` (section 6.2) |

Change from plan 13, stated on purpose: the tool never returns plain text, `{"continue":true}` or `{}`, because the spike shows that only the `hookSpecificOutput` shape reaches the model (F-07) and G6 requires that shape on every result. The tool never emits `continue` or `stopReason` (Z-05). A stop view from a routable check becomes the note `routable_stop_ignored <id>`; no routable check returns a stop today. A routable block view (none exists today) stops the later routable checks (plan 13 rule) and is not sent to the host; the note is `routable_block_ignored <id>`.

## 5. Running the scripts inside a long-lived server (G9)

### 5.1 Clock origin, late start, cancel (R1 #2, #13)

- The tool file starts one heartbeat at `register()`: `setInterval(tick, 50).unref()`, `tick` sets `lastTick = Date.now()`. Cost: one timer per server.
- On receipt, `origin = Math.min(Date.now(), lastTick + 50)`. When the event loop was blocked before the request was read, `lastTick` is old, so `origin` moves back to the last time the loop ran. That is the earliest time the request could have arrived. GUESS: the host send time is later than `lastTick`; the error is at most the heartbeat interval plus the read delay. When the loop was not blocked, `origin` is within 50 ms of receipt.
- `dispatch()` measures every deadline from `origin`. A check starts only when `now < origin + DEADLINE_MS - OUTPUT_RESERVE_MS`. When no check can start, the answer is empty with the note `late_start` and the turn is not served.
- The cancel signal: `signalFromExtra(extra)` (`lib/mcp/eureka-tool-contract.cjs:393-395`). When the host sends `notifications/cancelled`, the SDK aborts the signal (UNVERIFIED that the host sends it on a hook timeout; L6). `dispatch()` stops at the next check boundary, aborts the running check (5.6), and returns with `aborted: true`.
- Cold module load: the first served call pays the require of the four scripts inside its deadline. T7 reports the first served call apart. Only if T7 shows that the first call misses its deadline, the tool loads the four modules on `setImmediate` after `register()` (one require each, no process, so not a Stage 8 S4 prewarm). This is conditional and the SUMMARY records the decision (R1 #13).

### 5.3 The busy cap (OR-9 A, R1 #6)

API in `lib/core/hook-busy-cap.cjs`:
- `hookCapStore` = `new AsyncLocalStorage()` from `node:async_hooks` (a built-in; the zero-requires rule protects against a cycle with `room-db.cjs`, and a built-in makes no cycle; CD-24).
- `runWithHookCap({cap, deadlineAt}, fn)` runs `fn` inside a store `{cap, tripped:false, deadlineAt}`.
- `setHookBusyCap(ms)`: inside a store, it changes the store only (keep the smaller cap); outside a store, today's module state. This matters, because the four scripts call it inside run() (`scripts/intent-classifier.cjs:52`, `scripts/jtbd-update.cjs:161`, `scripts/brain-derivation-drain.cjs:273`, `scripts/auto-explore-drain.cjs:177`).
- `capBusyMs(requested)`: inside a store, `tripped ? 0 : min(requested, cap, max(0, deadlineAt - OUTPUT_RESERVE_MS - Date.now()))`; outside a store, today's rule.
- `noteBusy()`: inside a store, set `store.tripped`; outside, today's rule.

`dispatch()` runs inside `runWithHookCap({cap: HOOK_BUSY_MS, deadlineAt: origin + DEADLINE_MS}, ...)`. Timers and promises created inside the store keep the store, so a late callback of a cut check sees a passed deadline and gets 0 ms. Every other tool call has no store and keeps the 5,000 ms wait. The command path (no store) is unchanged, so the plan 10 tests do not change. A detached child (brain-derivation-drain, F-18) is a new process and keeps the default.

### 5.6 The classifier inside the server (R1 #7, #8)

Three changes in `scripts/intent-classifier.cjs`. None changes the output of the check.
1. Abort signal. `run(input, opts)` accepts `opts.signal`. `runOnce` keeps it in a module variable for the turn. The three late writes skip when the signal is aborted: `persistDecisionTrace` (:4221), `writeNavBlockHash` (:4226-4228), and the cue writes `persistFromDecision` (:2672, :3881). `dispatch()` gives each check its own AbortController, aborts it on `over_deadline` or on the host cancel, and passes the signal. The other three checks accept and ignore `opts.signal` (they are short and write before they return).
2. Real chain. `RUN_CHAIN` holds the un-raced `runTurn()` promise, not the race (:4248-4252). A new run() first waits for the old turn inside its own deadline. If the wait passes the deadline, run() returns `{code:0, stdout:'', stderr:''}` and `dispatch()` notes `classifier_busy`. So `setTurnInput` (:508) never runs while an old engine runs.
3. `forgetLastNavBlock()`: a new export that deletes the NAV hash sidecar that the last completed turn wrote (the classifier keeps `{roomDir, sessionId}` of that write). The tool calls it when a turn is not served, because the model saw nothing; the next turn then renders the full block, not `NAV_UNCHANGED_MARKER` (:4219).

The CLI main (:4282-4288) does not pass a signal, so the CLI path and the golden are unchanged.

### 5.7 Server survival (R1 #9)

- Audit (a plan task before any code): list every `setTimeout`, `setInterval`, `on(`, `once(` and floating promise in the run() path of the four checks. Wrap each callback that can throw in try/catch. Record the list in the SUMMARY.
- `lib/mcp/tools/userprompt-hook.cjs` `register()` installs one `process.on('unhandledRejection', ...)` handler, once per process. It writes `[mindrian-os] unhandled_rejection <error name>` to stderr (no message bytes, which can carry prompt text) and keeps the process running. Without a handler, Node 22 ends the process on an unhandled rejection, which stops every tool of the session.
- No `uncaughtException` handler: swallowing a synchronous throw can leave module state half changed. The audit covers that case.

## 6. A direct model call (G7, OR-6 A with fallback B, R1 #12)

### 6.1 OR-6 A: host marker (spike L2)

Compare a hook call and a model call of the same tool: `extra.mcpReq._meta`, `extra._meta` (read in the shape of `proofFrom`, `lib/mcp/answer-route.cjs:73-83`), the request id shape, and `extra.sessionId`. If a stable marker exists that a model call cannot carry, the handler refuses a call without it.

### 6.2 Refusal shape

A refused call runs no check and writes nothing (no ledger entry, no room write). It returns the JSON envelope of 2.3 with empty context and `"refused":"not_a_hook_call"`, so G6 holds on every result (D-10). A hook call that is refused by error (a false negative) is not served; the next prompt shows the note.

### 6.3 OR-6 B: fallback when L2 finds no marker

All four rules must pass, else the call is refused:
1. Session bind: when L1 or L2 shows that the server env has `CLAUDE_CODE_SESSION_ID` equal to the hook `session_id`, refuse a call whose `session_id` differs. If the server env does not carry it, this rule is not available, and the SUMMARY says so.
2. Cwd check: refuse unless input `cwd` resolves to the server start directory or a directory under it (GUESS that the server cwd is the session project directory; L1 records it).
3. Transcript rule: `transcript_path` must be a file under `~/.claude/projects/` whose base name is `<session_id>.jsonl`. The tail of the file must match the hook state that L3 records (for example: the last entry is the new user prompt, or the last entry is not an assistant `tool_use`). A model call happens inside a turn, so the tail then holds assistant entries of that turn (UNVERIFIED, L3).
4. Replay key: `sha256(session_id + "\0" + transcript size + "\0" + last entry uuid)`, not the prompt. A second call with the same key returns the stored text and writes nothing. A repeated real prompt ("yes", "continue") has a new transcript size, so it runs in full (this removes the G10 break of r1).

Residual risk (PROVEN by reasoning, ASSUMED tool permissions): a model with Bash and Write can read its env and its transcript and can write a forged transcript file. Then all four rules can pass, and the four checks run once per forged key on a model-written prompt. The effects stay local: the per-turn JTBD intent, the cue record and one ledger entry get a wrong value until the next real prompt. So B is "harmless except to a deliberate forgery". G7 says "harmless". That is a ruling-level choice:

NEEDS_HUMAN: If spike L2 finds no host marker, does the owner accept OR-6 B with the stated residual risk (a deliberate model forgery can run the four checks once on a model-written prompt, effects local and overwritten on the next real prompt), or must the phase stop for an OR-6 C acceptance in writing?

### 7.1 Files

Directory `~/.mindrian/userprompt-turns/`. A session id must match `SAFE_SESSION_RE` (`lib/statusline/next-move-cache.cjs:58`; the plan exports it and the prune helper, :426-443, with no behaviour change). Atomic write (temp file plus rename; on EPERM or EBUSY retry 3 times with 20 ms between; D-12). Prune: the cue-record rule (files older than 7 days, at most 200 per write). Each file has one writer.

- `<sid>.seen.json` (writer: the invariant script) = `{v:1, last:{k, at} | null, missed_run:n, at}`.
- `<sid>.served.json` (writer: the tool) = `{v:1, recent:[{k, at, served:true|false, reason}], at}`, the last 8 entries.

The key `k = turnKey(input)` = `sha256(session_id + "\0" + prompt)`, hex, 16 characters. If L1 finds a per-turn host field that both entries receive, it is added to the key (removes the residual risk of 7.4). The files hold hashes, counts, codes and times only, never prompt bytes (Part 8, Part 9).

### 7.2 Rules

Invariant script, on a prompt that is not blocked, at step 3 of section 3, with `t0` from step 1:
1. Read both files. A read or parse failure of a file means "unknown": no note, no count change, and the write of step 4 still happens.
2. If `seen.last` exists and `t0 - seen.last.at < 24 h`: find in `served.recent` an entry `e` with `e.k == seen.last.k` and `e.at >= seen.last.at - 3000` (3,000 ms is the hook timeout; the two entries of one turn start at the same host time, so the tool entry of that turn is at most 3 s older than the invariant record).
   - `e` found with `served:true`: `missed_run = 0`.
   - else: `missed_run = missed_run + 1`; reason = `e.reason` when `e` exists, else `hook_not_called` when `served.json` has no entry at all for this session, else `server_not_answering`. Add one context line: `[MindrianOS] Prompt help (navigation card, next-move cue) was skipped on <missed_run> earlier prompt(s): <reason>.`
3. If `seen.last` is older than 24 h, ignore it (a new start; `missed_run = 0`).
4. Write `seen = {v:1, last:{k: key(this turn), at: t0}, missed_run, at: now}`.

Tool, after `dispatch()`: append `{k, at: answer time, served, reason}` to `served.recent` (keep 8). `served` is defined in 7.3.

Why there is no race: the invariant script of prompt N checks only the key of its own turn N-1. The tool call of turn N-1 ends (answer, cancel or timeout) before prompt N exists, because the model answers between prompts. The tool call of turn N is never read on prompt N.

### 7.3 Served

`served = true` only when all hold: `dispatch()` returned, `signal.aborted` is false, and `answerAt - origin <= DEADLINE_MS` (5.1). Reasons when false: `late_start` (no check could start), `cancelled` (signal), `deadline` (answer after the window), `refused` is never written (a refused call writes nothing). A tool call that the host cancelled and that never reached the handler writes nothing; the invariant then reports `server_not_answering` or `hook_not_called`.

### 7.4 Truth table (T4a proves each row)

| Case | Prompt 1 | Prompt 2 | Prompt 3 | Later |
|---|---|---|---|---|
| Cold first prompt, then served | no NAV block, no note | note "1 earlier prompt(s): hook_not_called" (or the L6 reason) | no note | no note |
| Server down all session | no note | note 1, `hook_not_called` | note 2 | note n (growing), the T4 rule |
| Server answered, then died before prompt 3 | normal | normal | normal (prompt 2 served) | prompt 4: note 1, `server_not_answering` |
| Blocked admin prompt as prompt 2 | normal | block, no ledger write | checks prompt 1 | no note from the block |
| Invariant cancelled on prompt 2 before its write | normal | no output | checks prompt 1 (already counted; prompt 2 untracked) | normal |
| Late start on prompt 2 (loop blocked) | normal | no context | note 1, `late_start` | no note |
| Same text twice within 3 s, second missed | normal | missed | may count as served (residual risk) | normal |
| No safe `session_id` in the invariant input | no ledger, stderr note `ledger_no_session` | same | same | same |

Residual risk: two identical prompts in one session inside 3 s can hide one miss. The SUMMARY records it.

### 7.5 What the user sees

On a cold first prompt: no NAV block on prompt 1, and on prompt 2 one plain line that says it was skipped and why. No silent loss (G8). On an older host that ignores the `mcp_tool` entry (L7 pass branch): every prompt gets the note with `hook_not_called` and a growing count. That is loud, not silent; the SUMMARY names the version floor.
