### 2.2 hostView rules (ported from plan 13 P5, INPUT plan 13 line 134)

`hostView({code, stdout, stderr})` returns `{kind: 'none' | 'context' | 'block', context, systemMessage, stop, blockText}`:
1. Code 2: a block; `blockText` = the stderr text.
2. Code 1 or any other non-zero code except 2: nothing.
3. Stdout empty or only whitespace: nothing.
4. Stdout that is exactly one JSON object with only whitespace around it: a JSON view. Read `hookSpecificOutput.additionalContext` (string), `systemMessage` (string), `continue === false` with `stopReason`, and `decision === 'block'` with `reason` (a block with `blockText` = reason).
5. Stdout that starts with `{` and ends with `}` but does not parse (for example `{bad}`): nothing (a host parse failure).
6. Any other stdout (for example a JSON object plus a trailing plain line): the whole stdout is plain-text context.
7. Trailing whitespace of a context string is trimmed. The parity comparison trims both sides.

`mergeViews(views)`: `additionalContext` = the non-empty context strings in check order, joined with `CONTEXT_SEPARATOR`; `systemMessage` = the non-empty values joined with "\n"; the first stop wins; the first block wins and later views are not read. A joined context over `CONTEXT_CAP_CHARS` gives the note `context_over_cap <total>: <id>=<len>, ...` and is never truncated (plan 13).

A routable block view (none exists today) stops the later routable checks (plan 13 rule) and is not sent to the host; the note is `routable_block_ignored <id>`.

## 3. The invariant tier (G5, OR-1 A, OR-3 A amended by CONTEXT 5c)

`scripts/userprompt-invariant.cjs`, one hooks.json entry: `node "${CLAUDE_PLUGIN_ROOT}/scripts/userprompt-invariant.cjs"`, timeout 3, no async key (Windows: node direct).

Order (CONTEXT 5c, locked): admin gate, then turn ledger, then first-install router.

1. `const t0 = Date.now()`. Read fd 0 once (empty on error). Call `setHookBusyCap(HOOK_BUSY_MS)` (D-17: the transitive requires of first-install-router are not audited for room.db, so the cap stays on as a guard).
2. `admin-command-gate.run(input)`. A block view: write the stderr, no stdout, exit 2, stop. The ledger is not written, so a blocked turn is never checked (section 7). A throw in the gate fails open (T-400.4-43), as today.
3. Ledger (section 7.2): check the previous turns, compute the note, write `seen.json`. This runs before the router, so a host cancel during the router keeps the turn record (5c reason).
4. `first-install-router.run(input)` (its 400 ms spawnSync stays, F-17).
5. Merge the router view and the note with `mergeViews`. Write the envelope with `process.stdout.write(text, cb)`. In `cb`: when a note was in the envelope and `Date.now() - t0 <= NOTED_LIMIT_MS` (2,500 ms), call `markNoted(sid, key)` (sets `noted:true` in `seen.json`); after that limit, `noted` stays false, because the host can time out after the flush and drop the output (R3 #9, UNVERIFIED host behaviour). Then call `finishCli({code:0, stdout:'', stderr})`. The worst case is one repeated note. `lib/core/hook-io.cjs` does not change.

CLI net (CD N9): the `require.main` block installs the same last-resort `uncaughtException` net as `scripts/first-install-router.cjs:1020-1028`. It writes `{"continue":true}` and exits 0. A throw after the admin block cannot happen, because the block path exits at step 2.

Plan 13 budgets for these two checks (admin 300 ms, router 500 ms) are reported in the SUMMARY, not enforced: both are synchronous in one process and cannot be cut (IR-17). Order between the two entries: none (F-03, OR-1 A). A block from the admin gate still blocks the prompt (G10). The routable tier can still run on a blocked prompt, as today.

## 5. Running the scripts inside a long-lived server (G9)

### 5.1 Clock origin, late start, cancel (R1 #2, #13, R2 #8, #10, R3 #1)

Why r3 failed (R3 #1): libuv runs due timers before the poll phase that reads stdin (ASSUMED uv_run order; L0 measures it). After any block, the overdue tick runs first and sets `lastTick = now` just before the request is read, so `min(receipt, lastTick + 50)` gives `receipt`. On a cold connect the host also sends initialize, notifications/initialized and tools/list before tools/call (ASSUMED protocol order), and ticks run during those idle waits. So r3 could mark a cancelled cold turn `served:true`.

The heartbeat (`lib/mcp/process-guards.cjs`):
- `installProcessGuards({startedAt})` sets `lastTick = startedAt`, `gapStart = gapEnd = null`, `connectAt = null`, `firstCallDone = false`, and starts one `setInterval(tick, TICK_MS).unref()` (50 ms). A module flag makes a second call a no-op.
- `tick()`: `now = Date.now()`; if `now - lastTick > GAP_MS` (100 ms), set `gapStart = lastTick` and `gapEnd = now`; then `lastTick = now`. A block of any length therefore leaves its start and end in `gapStart` and `gapEnd`, even when the overdue tick runs before the read.
- `markConnect()`: sets `connectAt = Date.now()` once.
- Call site: the stdio branch of `main()` (`scripts/mindrian-mcp-server.cjs:653-661`). First statement of the branch: `installProcessGuards({startedAt: Math.round(performance.timeOrigin)})` (ASSUMED Node semantics of `performance.timeOrigin`; L0 checks it). Directly after `serveStdio(...)` returns (`:656`), in the same synchronous block: `process.stdin.once('data', markConnect)`. ASSUMED: a second `data` listener gets the same chunks as the SDK transport (`node_modules/@modelcontextprotocol/server/dist/stdio.cjs:74`) and changes nothing it reads, because both listeners attach before any I/O callback runs. L0 checks it. Fallback if L0 fails: pass `options.transport` (`stdio.cjs:286-288`) as a `StdioServerTransport` whose `onmessage` setter is wrapped to call `markConnect()` on the first message. The HTTP branch installs nothing.

`clockOrigin(receipt)` (called with `receipt = Date.now()` at handler entry), first match wins:
1. Cold: `!firstCallDone` and `receipt - (connectAt ?? startedAt) < SERVED_LIMIT_MS` (2,900 ms): `origin = startedAt`. Reason: a prompt that was waiting while the server loaded is sent right after the handshake, so its tools/call is read soon after `connectAt`; the host clock can have started as early as session start, and the server starts at session start (F-19). With `origin = startedAt`, a cold call after a 3.2 s load is always `late_start` and never served. When `connectAt` is null (no stdin data seen), the uptime rule `receipt - startedAt < SERVED_LIMIT_MS` applies.
2. Gap: `gapEnd !== null` and `receipt - gapEnd < GAP_MS`: `origin = gapStart`. The request was read right after a block, so it can have arrived at any time in the block; `gapStart` is the earliest time that cannot be excluded (conservative).
3. Else `origin = receipt`.
`firstCallDone` becomes true after the first hook call returns. Not installed (tests, HTTP): `origin = receipt`.

Stated cost (R3 #1): a user prompt sent less than 2.9 s after the connect gets no routable context and one note on the next prompt ("late_start"), even when the host waited for the server (L6 branch W). A request read just after an unrelated block gets an early origin and can be marked not served although the host got the answer in time (IR-14, a false note). Both are loud, not silent (G8).

Other rules:
- `dispatch()` measures every deadline from `origin`. A check starts only when `now < origin + DEADLINE_MS - OUTPUT_RESERVE_MS`. When no check can start, the answer is empty with the note `late_start` and the turn is not served.
- The cancel signal: the copied `signalFromExtra(extra)` line (2.1). When the host sends `notifications/cancelled`, the SDK aborts the signal (UNVERIFIED that the host sends it on a hook timeout; L6). `dispatch()` stops at the next check boundary, aborts the running check (5.6), and returns with `aborted: true`. The served rule (7.3) does not depend on this signal: the clock rule above decides a cold or blocked turn by itself.
- Alternative not chosen: `perf_hooks.monitorEventLoopDelay` gives a delay histogram, not the start and end of the last block, so it cannot give `gapStart`.
- Cold module load: the first served call pays the require of the four scripts inside its deadline. T7 reports the first served call apart. Only if T7 shows that the first warm call misses its deadline, `main()` (stdio branch, after `installProcessGuards`) requires the four modules on `setImmediate`. This runs outside any busy-cap store (D-12), it is one require each and no process, so it is not a Stage 8 S4 prewarm. This is conditional and the SUMMARY records the decision (R1 #13).

### 5.3 The busy cap (OR-9 A, R1 #6, R2 #12, R3 #4)

API in `lib/core/hook-busy-cap.cjs` (it keeps zero requires of project files; `node:async_hooks` is a built-in and makes no cycle with `room-db.cjs`; CD-24):

### 7.2 Rules

Invariant script, on a prompt that is not blocked, at step 3 of section 3, with `t0` from step 1:
1. Read both files. A read or parse failure of a file means "unknown": no note, no count change, and the write of step 5 still happens.
2. If `seen.last` exists and `t0 - seen.last.at < 24 h`: find in `served.recent` an entry `e` with `e.k == seen.last.k` and `e.at >= seen.last.at - 3000` (3,000 ms is the hook timeout; the two entries of one turn start at the same host time).
   - `e` found with `served:true`: the previous turn was served; `newMiss = 0`.
   - else: `newMiss = 1`; reason = `e.reason` when `e` exists, else `hook_not_called` when `served.json` has no entry at all for this session, else `server_not_answering`.
3. Unrecorded turns (R2-D-02, R3 #3): count the entries `u` in `served.recent` that meet all of: `u.served === false`; `u.k !== k` (the key of this turn); `u.at < t0 - 3000` (excludes the tool entry of this turn, which can already exist when the warm tool answers before the invariant reaches step 3); `u.at > t0 - 24 h`; and, when `seen.last` exists, `u.at > seen.last.at + 3000` and `u.k !== seen.last.k`. When `seen.last` is null, only the first four conditions apply. These are turns that the tool saw and did not serve, and whose invariant record was lost (invariant cancelled before step 3). Add the count to `newMiss`; take the reason of the newest such entry when no reason is set yet.
4. Count (a missing `noted` field reads as `true`): if `newMiss === 0` and `seen.noted !== false`, then `missed_run = 0`. Else `missed_run = seen.missed_run + newMiss`. In words: the count resets only after a served turn whose note was shown; an unshown note is carried and shown again; a new miss adds to the count (the growing count of the "server down" row).
5. If `seen.last` is older than 24 h, ignore it (a new start; `missed_run = 0`).
6. When `missed_run > 0`, add one context line: `[MindrianOS] Prompt help (navigation card, next-move cue) was skipped on <missed_run> earlier prompt(s): <reason>.` For reason `deadline` the text is "may have been skipped" (D-04).
7. Write `seen = {v:1, last:{k: key(this turn), at: t0}, missed_run, reason, noted: missed_run === 0, at: now}`. Step 5 of section 3 sets `noted: true` after the stdout write, and only when that write ends by `t0 + NOTED_LIMIT_MS` (2,500 ms; R3 #9). A later write keeps `noted: false`, so the note shows again on the next prompt.

Tool: the `setImmediate` step of 4.1 appends `{k, at: answerAt, served, reason}` to `served.recent` (keep 8).

Why each tool entry is counted once (R3 #3): rule 2 on prompt N reads only the entry whose key is `seen.last.k` (turn N-1, recorded by the invariant on N-1). Rule 3 on prompt N reads only entries whose time is between `seen.last.at + 3000` and `t0 - 3000` and whose key is neither `seen.last.k` nor the key of N. So the tool entry of turn N itself is not read on prompt N; on prompt N+1 it is read by rule 2 only (its key is `seen.last.k`). An entry counted by rule 3 on prompt N is older than `t0(N) - 3000`; on prompt N+1 rule 3 needs `u.at > t0(N) + 3000`, so it is not counted again, and rule 2 needs the key of N, which it does not have. The tool call of turn N-1 ends (answer, cancel or timeout) before prompt N exists, because the model answers between prompts.

Residual case (recorded in the SUMMARY): a tool miss on a turn whose invariant record was also lost, followed by the next prompt less than 3 s later, is never counted. It needs two failures on one turn and a prompt sent inside 3 s of the previous answer.

Known limit (R2-D-02): a prompt that neither tier recorded (the invariant cancelled before step 3 and the tool call never reached the handler) leaves no trace. No note covers it. This needs both tiers to fail on the same prompt before any write. The SUMMARY records it.

### 7.3 Served

`served = true` only when all hold: `dispatch()` returned, `signal.aborted` is false, the call was not `late_start` or `dispatch_busy`, and `answerAt - origin <= SERVED_LIMIT_MS` (2,900 ms = the 3 s hook timeout minus `OUTPUT_RESERVE_MS`; D-04), with `origin` from the clock rule of 5.1. Reasons when false: `late_start`, `dispatch_busy`, `cancelled` (signal), `deadline` (answer after the limit). A refused call writes nothing. A tool call that the host cancelled and that never reached the handler writes nothing; the invariant then reports `server_not_answering` or `hook_not_called`.

Cold-connect assertion (R2-D-01, R3 #1): a turn whose mcp_tool hook result is `hook_cancelled` must have no `served:true` entry. L0 proves the clock rule in a scratch process; L6 and T4b assert the rule live; T7 asserts it for every prompt. This holds without `notifications/cancelled`: the cold branch of 5.1 puts `origin` at process start, so a call after a 3.2 s load is `late_start`. If L6 still finds a `hook_cancelled` turn with `served:true`, the fallback rule `COLD_FIRST_CALL` replaces the cold branch: the first hook call of a server process is never served (`late_start`), whatever its timing. Its cost is one note per server start. W0 records which rule ships.

Known limit (IR-14): a loop block in the server just before the read moves `origin` back to `gapStart` (5.1) and can mark a turn not served that the host did receive in time. The user then sees a false note and the next NAV block renders in full. T5b and T7 count these false positives apart (9.3) and the SUMMARY reports the count.

## 12. Simpler alternative considered (input for the scope reviewer, not a decision)

The smallest design that would also stop the UserPromptSubmit timeouts is the plan 13 command dispatcher (`400.5-INPUT-former-400.4-13-dispatcher-plan.md`): one command hook entry, `scripts/userprompt-dispatch.cjs`, that calls the six plan 12 `run()` exports in one node process, in the fixed order, with the plan 13 per-check deadlines and one 2,500 ms total deadline from process start, timeout 3 s. A variant keeps the server out and adds only a small turn ledger in the same process, so that a host timeout of that one process shows a note on the next prompt.

What it removes from r4: the MCP tool and its connector declaration (4.2), the tool-budget re-pins (4.3, four tests), OR-6 and its spike legs L2 and L3 (section 6), the clock rule and L0 (5.1), the busy-cap store (5.3; the process-wide cap of plan 10 is already per process), the classifier abort, chain, journal and `forgetUnservedTurn` (5.6; process exit ends a late engine, as today), the dispatch lock (5.8), the process guards (5.7), the env snapshot (5.2), and the second ledger file. GUESS: about one quarter of the r4 code and two of the seven plans.

What it keeps or loses against the rulings:
- It fails G5 as written: G5 requires the routable tier to run through ONE `mcp_tool` hook into the MCP server. G6 and G7 then have no object. G3 and G2 record that 400.5 supersedes plan 13 and keeps the transport slice, so this alternative needs the owner to reopen G5 (and G2 or G3 by consequence).
- It meets G9-G11 in form (per-check deadlines, parity, one process per prompt), but it keeps one cold node start per prompt. The RCA names starvation of the host (load average 20 on 12 cores, IO pressure about 13 %) and six cold starts per prompt as the cause (`.planning/debug/userpromptsubmit-hook-timeouts-under-load.md:37-42`). One cold start is one sixth of that exposure, not zero. UNVERIFIED: whether one cold start plus the require of the four scripts fits 3 s under that load. The cold-start baseline (`tests/fixtures/369/hook-cold-start-baseline.json`) and a T7-shaped run of the dispatcher would answer it in about one W0 leg.
- G8 (first-prompt behaviour) mostly disappears, because there is no cold connect; a timeout of the one process is still silent unless the small ledger variant is used.
- G12 to G14 hold with less work (no new invocable surface for Part 11; the cue and room rules of plan 14 do not move).

A second, smaller step inside r4 ("kill a late check inside the server") is not much simpler: a check that blocks the loop synchronously cannot be killed inside one process, and a cut async check keeps running, so the abort, journal and served rules of 5.6 and 7.3 are needed for G8 and Part 9 either way.

Position of r4: under the locked rulings G1-G14, r4 is preferred, because only the server tier meets G5, and the r4 extra parts each answer a stated ruling (G7: section 6; G8: 5.1 and 7; G9: 5.3; Part 9: 5.6). Against the problem alone (G11), the dispatcher alternative is cheaper and its residual risk (one cold start per prompt) is measurable in one leg. This trade is for the scope reviewer and the owner.
