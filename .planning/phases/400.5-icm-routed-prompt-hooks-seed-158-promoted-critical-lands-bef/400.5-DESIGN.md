### 2.2 hostView rules (ported from plan 13 P5, INPUT plan 13 line 134)

`hostView({code, stdout, stderr})` returns `{kind: 'none' | 'context' | 'block', context, systemMessage, stop, blockText}`:
1. Code 2: a block; `blockText` = the stderr text.
2. Code 1 or any other non-zero code except 2: nothing.
3. Stdout empty or only whitespace: nothing.
4. Stdout that is exactly one JSON object with only whitespace around it: a JSON view. Read `hookSpecificOutput.additionalContext` (string), `systemMessage` (string), `continue === false` with `stopReason`, and `decision === 'block'` with `reason` (a block with `blockText` = reason).
5. Stdout that starts with `{` and ends with `}` but does not parse (for example `{bad}`): nothing (a host parse failure).
6. Any other stdout (for example a JSON object plus a trailing plain line): the whole stdout is plain-text context.
7. Trailing whitespace of a context string is trimmed. The parity comparison trims both sides.

`mergeViews(views)`: `additionalContext` = the non-empty context strings in check order, joined with `CONTEXT_SEPARATOR`; `systemMessage` = the non-empty values joined with "\n"; the first stop wins; the first block wins and later views are not read. A joined context over `CONTEXT_CAP_CHARS` gives the note `context_over_cap <total>: <id>=<len>, ...` and is never truncated (plan 13).

A routable block view (none exists today) stops the later routable checks (plan 13 rule) and is not sent to the host; the note is `routable_block_ignored <id>`.

## 3. The invariant tier (G5, OR-1 A, OR-3 A amended by CONTEXT 5c)

`scripts/userprompt-invariant.cjs`, one hooks.json entry: `node "${CLAUDE_PLUGIN_ROOT}/scripts/userprompt-invariant.cjs"`, timeout 3, no async key (Windows: node direct).

Order (CONTEXT 5c, locked): admin gate, then turn ledger, then first-install router.

1. `const t0 = Date.now()`. Read fd 0 once (empty on error). Call `setHookBusyCap(HOOK_BUSY_MS)` (D-17: the transitive requires of first-install-router are not audited for room.db, so the cap stays on as a guard).
2. `admin-command-gate.run(input)`. A block view: write the stderr, no stdout, exit 2, stop. The ledger is not written, so a blocked turn is never checked (section 7). A throw in the gate fails open (T-400.4-43), as today.
3. Ledger (section 7.2): check the previous turns, compute the note, write `seen.json`. This runs before the router, so a host cancel during the router keeps the turn record (5c reason).
4. `first-install-router.run(input)` (its 400 ms spawnSync stays, F-17).
5. Merge the router view and the note with `mergeViews`. Write the envelope with `process.stdout.write(text, cb)`. In `cb`: when a note was in the envelope, call `markNoted(sid, key)` (sets `noted:true` in `seen.json`), then call `finishCli({code:0, stdout:'', stderr})`. `lib/core/hook-io.cjs` does not change.

CLI net (CD N9): the `require.main` block installs the same last-resort `uncaughtException` net as `scripts/first-install-router.cjs:1020-1028`. It writes `{"continue":true}` and exits 0. A throw after the admin block cannot happen, because the block path exits at step 2.

Plan 13 budgets for these two checks (admin 300 ms, router 500 ms) are reported in the SUMMARY, not enforced: both are synchronous in one process and cannot be cut (IR-17). Order between the two entries: none (F-03, OR-1 A). A block from the admin gate still blocks the prompt (G10). The routable tier can still run on a blocked prompt, as today.

## 5. Running the scripts inside a long-lived server (G9)

### 5.1 Clock origin, late start, cancel (R1 #2, #13, R2 #8, #10)

- `lib/mcp/process-guards.cjs` `installProcessGuards({startedAt})` keeps `lastTick = startedAt` and starts one `setInterval(tick, 50).unref()`; `tick` sets `lastTick = Date.now()`. A module flag makes a second call a no-op. The stdio branch of `main()` (`scripts/mindrian-mcp-server.cjs:652-660`) calls it once with `startedAt = Math.round(performance.timeOrigin)`, the epoch time of process start (ASSUMED Node semantics of `performance.timeOrigin`; W0 checks it with one `node -e` line). The HTTP branch does not call it.
- On receipt, `origin = isInstalled() ? Math.min(Date.now(), lastTick() + 50) : Date.now()`.
- Cold connect: the server loads its modules for about 3.2 s (F-07) with the loop busy, so no tick runs. A hook request read before the first tick gets `origin = process start + 50 ms`. Then `now >= origin + DEADLINE_MS - OUTPUT_RESERVE_MS`, the handler returns `late_start`, and the turn is not served. A cold call can therefore never write `served:true` (R2-D-01). Cost: when the host waits for the connection and starts its 3 s clock only after it sends the call (L6 branch W), prompt 0 still gets no routable context and prompt 1 gets the note "may have been skipped". This is loud, not silent (G8). L6 records which branch holds.
- Warm path: when the loop was blocked before the request was read, `lastTick` is old, so `origin` moves back to the last time the loop ran. GUESS: the host send time is later than `lastTick`; the error is at most the heartbeat interval plus the read delay. When the loop was not blocked, `origin` is within 50 ms of receipt.
- `dispatch()` measures every deadline from `origin`. A check starts only when `now < origin + DEADLINE_MS - OUTPUT_RESERVE_MS`. When no check can start, the answer is empty with the note `late_start` and the turn is not served.
- The cancel signal: the copied `signalFromExtra(extra)` line (2.1). When the host sends `notifications/cancelled`, the SDK aborts the signal (UNVERIFIED that the host sends it on a hook timeout; L6). `dispatch()` stops at the next check boundary, aborts the running check (5.6), and returns with `aborted: true`.
- Cold module load: the first served call pays the require of the four scripts inside its deadline. T7 reports the first served call apart. Only if T7 shows that the first warm call misses its deadline, `main()` (stdio branch, after `installProcessGuards`) requires the four modules on `setImmediate`. This runs outside any busy-cap store (D-12), it is one require each and no process, so it is not a Stage 8 S4 prewarm. This is conditional and the SUMMARY records the decision (R1 #13).

### 5.3 The busy cap (OR-9 A, R1 #6, R2 #12)

API in `lib/core/hook-busy-cap.cjs` (it keeps zero requires of project files; `node:async_hooks` is a built-in and makes no cycle with `room-db.cjs`; CD-24):
- `hookCapStore` = `new AsyncLocalStorage()`.
- `runWithHookCap({cap, deadlineAt, reserveMs}, fn)` runs `fn` inside a store `{cap, tripped:false, deadlineAt, reserveMs}`. `reserveMs` is a store field, so the file does not import `OUTPUT_RESERVE_MS` (CD N6, D-13, IR-07).
- `setHookBusyCap(ms)`: inside a store, it changes the store only (keep the smaller cap); outside a store, today's module state. This matters, because the four scripts call it inside run() (`scripts/intent-classifier.cjs:52`, `scripts/jtbd-update.cjs:161`, `scripts/brain-derivation-drain.cjs:273`, `scripts/auto-explore-drain.cjs:177`).
- `capBusyMs(requested)`: inside a store, `tripped ? 0 : min(requested, cap, max(0, deadlineAt - reserveMs - Date.now()))`; outside a store, today's rule.
- `noteBusy()`: inside a store, set `store.tripped`; outside, today's rule.

The per-statement rule (R2-D-07). The `DatabaseSync` `timeout` is set once at open (`lib/core/room-db.cjs:305-310`) and applies to every later statement of that connection. A WAL open succeeds under a held write lock, so the wait happens at the first write, not at open. Therefore:
1. `lib/core/room-db.cjs` gets one new export, `refreshBusyTimeout(db)`. Inside a store it runs `db.exec('PRAGMA busy_timeout = ' + capBusyMs(5000))`; outside a store it does nothing. Each call computes the remaining time again, so the sum of all waits in one hook call is at most the time to the deadline: a wait that ends in success leaves less time for the next one, and a wait that ends in busy trips the store and makes every later wait 0 ms.
2. The navigation write chokepoint calls `refreshBusyTimeout(db)` before each write statement: `lib/core/navigation/spine-events.cjs` (the `logEvent` write path near `:470-484`) and the node and edge writers that `lib/core/navigation.cjs` exports. The same sites trip the store on any SQLITE_BUSY (the `_isBusy` test that `spine-events.cjs:480` already uses).
3. W0 audit item: list every room.db statement that the four checks reach. Each one is either behind the chokepoint (covered by rule 2) or is listed in the SUMMARY with its maximum wait. A listed statement outside the chokepoint is a refresh site in W1 when it can run more than once per call; else it is a known limit (one wait of at most the open-time value, which is already `min(cap, remaining)`).

`dispatch()` runs inside `runWithHookCap({cap: HOOK_BUSY_MS, deadlineAt: origin + DEADLINE_MS, reserveMs: OUTPUT_RESERVE_MS}, ...)`. Timers and promises created inside the store keep the store, so a late callback of a cut check sees a passed deadline and gets 0 ms. Every other tool call has no store and keeps the 5,000 ms wait. The command path (no store) is unchanged, so the plan 10 tests do not change. A detached child (brain-derivation-drain, F-18) is a new process and keeps the default. There is no handle cache in `room-db.cjs` (PROVEN by grep), so a handle opened by another tool with 5,000 ms is never reused inside a hook call.

### 6.2 Refusal shape

A refused call runs no check and writes nothing (no ledger entry, no room write). It returns the refusal shape of 2.3, so G6 holds on every result (D-10). A hook call that is refused by error (a false negative) is not served; the next prompt shows the note.

### 6.3 OR-6 B: fallback when L2 finds no marker (CONTEXT 5b)

CONTEXT 5b (locked): when L2 finds no host marker, fallback B ships with no stop, and the residual risk below is accepted.

All four rules must pass, else the call is refused:
1. Session bind: when L1 or L2 shows that the server env has `CLAUDE_CODE_SESSION_ID` equal to the hook `session_id`, refuse a call whose `session_id` differs. If the server env does not carry it, this rule is not available, and the SUMMARY says so.
2. Cwd check: refuse unless input `cwd` resolves to the server start directory or a directory under it (GUESS that the server cwd is the session project directory; L1 records it).
3. Transcript rule: `transcript_path` must be a file under `~/.claude/projects/` whose base name is `<session_id>.jsonl`. The tail of the file must match the hook state that L3 records (for example: the last entry is the new user prompt, or the last entry is not an assistant `tool_use`). A model call happens inside a turn, so the tail then holds assistant entries of that turn (UNVERIFIED, L3).
4. Replay key: `sha256(session_id + "\0" + transcript size + "\0" + last entry uuid)`, not the prompt. A second call with the same key returns the stored text and writes nothing. A repeated real prompt ("yes", "continue") has a new transcript size, so it runs in full.

Residual risk accepted in CONTEXT 5b (PROVEN by reasoning, ASSUMED tool permissions): a model with Bash and Write can read its env and its transcript and can write a forged transcript file. Then all four rules can pass, and the four checks run once per forged key on a model-written prompt. The effects stay local: the per-turn JTBD intent, the next-move cue and one ledger entry get a wrong value until the next real prompt. Nothing leaves the machine and nothing is deleted.

SUMMARY duty (5b): the W0 SUMMARY and the phase SUMMARY each carry the field `or6_branch_shipped: A | B`, and for B the list of rules that are available (1, 2, 3, 4).

### 6.4 The one cell that 5b does not cover

When L2 finds no marker AND rule 3 is not available (L3 finds no stable tail rule, or `transcript_path` is not substituted), rule 4 also loses its transcript key. Only rules 1 and 2 remain. Then a model call that copies the session id and the cwd can run the four checks with no forged file. That risk is larger than the risk that 5b accepted. This design does not decide it. Default: W0 stops for the owner at that cell.

NEEDS_HUMAN: If spike L2 finds no host marker and rule 3 is not available (L3 finds no stable tail rule, or `transcript_path` is not substituted), does the owner accept OR-6 B with rules 1, 2 and 4 only (a model call that copies the session id and the cwd can then run the four checks once with no forged file), or must the phase stop at that point?

### 7.2 Rules

Invariant script, on a prompt that is not blocked, at step 3 of section 3, with `t0` from step 1:
1. Read both files. A read or parse failure of a file means "unknown": no note, no count change, and the write of step 5 still happens.
2. If `seen.last` exists and `t0 - seen.last.at < 24 h`: find in `served.recent` an entry `e` with `e.k == seen.last.k` and `e.at >= seen.last.at - 3000` (3,000 ms is the hook timeout; the two entries of one turn start at the same host time).
   - `e` found with `served:true`: the previous turn was served; `newMiss = 0`.
   - else: `newMiss = 1`; reason = `e.reason` when `e` exists, else `hook_not_called` when `served.json` has no entry at all for this session, else `server_not_answering`.
3. Unrecorded turns (R2-D-02): count the entries `u` in `served.recent` with `u.served === false`, `u.at > seen.last.at + 3000` and `u.k != seen.last.k`. These are turns that the tool saw and did not serve, and whose invariant record was lost (invariant cancelled before step 3). Add the count to `newMiss`; take the reason of the newest such entry when no reason is set yet.
4. Count (a missing `noted` field reads as `true`): if `newMiss === 0` and `seen.noted !== false`, then `missed_run = 0`. Else `missed_run = seen.missed_run + newMiss`. In words: the count resets only after a served turn whose note was shown; an unshown note is carried and shown again; a new miss adds to the count (the growing count of the "server down" row).
5. If `seen.last` is older than 24 h, ignore it (a new start; `missed_run = 0`).
6. When `missed_run > 0`, add one context line: `[MindrianOS] Prompt help (navigation card, next-move cue) was skipped on <missed_run> earlier prompt(s): <reason>.` For reason `deadline` the text is "may have been skipped" (D-04).
7. Write `seen = {v:1, last:{k: key(this turn), at: t0}, missed_run, reason, noted: missed_run === 0, at: now}`. Step 5 of section 3 sets `noted: true` after the stdout write.

Tool: the `setImmediate` step of 4.1 appends `{k, at: answerAt, served, reason}` to `served.recent` (keep 8).

Why there is no race: the invariant script of prompt N checks only the keys of turns before N. The tool call of turn N-1 ends (answer, cancel or timeout) before prompt N exists, because the model answers between prompts. The tool call of turn N is never read on prompt N. The rule-3 scan uses `seen.last.at + 3000`, so the tool entry of turn N-1 itself is never counted twice.

Known limit (R2-D-02): a prompt that neither tier recorded (the invariant cancelled before step 3 and the tool call never reached the handler) leaves no trace. No note covers it. This needs both tiers to fail on the same prompt before any write. The SUMMARY records it.

### 7.3 Served

`served = true` only when all hold: `dispatch()` returned, `signal.aborted` is false, the call was not `late_start` or `dispatch_busy`, and `answerAt - origin <= SERVED_LIMIT_MS` (2,900 ms = the 3 s hook timeout minus `OUTPUT_RESERVE_MS`; D-04). Reasons when false: `late_start`, `dispatch_busy`, `cancelled` (signal), `deadline` (answer after the limit). A refused call writes nothing. A tool call that the host cancelled and that never reached the handler writes nothing; the invariant then reports `server_not_answering` or `hook_not_called`.

Cold-connect assertion (R2-D-01): a turn whose mcp_tool hook result is `hook_cancelled` must have no `served:true` entry. L6 and T4b assert it; T7 asserts it for every prompt. A failure stops W3 until the served rule is fixed.
