# Phase 400.5 DESIGN: prompt hooks inside the running server

This design satisfies the given rulings G1-G15. Where an owner ruling is open (OR-n), the design uses the recommended option and names the alternative. A guess is marked GUESS.

## 1. The shape in one picture

```
UserPromptSubmit (host runs both entries in parallel, F-03)
|
+-- entry 1: command hook (invariant tier, OR-3 A)
|     node scripts/userprompt-invariant.cjs        timeout 3
|       1. admin-command-gate.run()   -> block: exit 2 + 3-line stderr (unchanged)
|       2. first-install-router.run() -> its context or nothing
|       3. turn ledger: record this turn; if an earlier turn was not served,
|          add one typed note line (OR-4 A)
|
+-- entry 2: mcp_tool hook (routable tier)
      server plugin:mos:mindrian-os, tool userprompt_hook     timeout 3 (OR-8 A)
      input {prompt, session_id, cwd, transcript_path, hook_event_name}
        in the server, lib/core/userprompt-routable.cjs dispatch():
          intent-classifier -> brain-derivation-drain -> jtbd-update(userprompt)
          -> auto-explore-drain   (OR-2 A, the hooks.json order)
          per-check deadline, skipped_deadline, over_deadline (plan 13)
        returns ONE text: {"hookSpecificOutput":{"hookEventName":
          "UserPromptSubmit","additionalContext":"..."}}  (G6)
        records "turn served" for the turn ledger
```

Per prompt the host starts 1 node process (was 6) and makes 1 MCP call into a process that is already warm.

## 2. One transport-independent core (G5, G3)

New module `lib/core/userprompt-routable.cjs` (CJS, no Brain call, no network). It is the plan 13 dispatcher core with the transport removed.

- `CHECKS` (a code constant, never read from a room file; G2, Stage 8 S1/S2):
  `[{id:'intent-classifier', budgetMs:1800}, {id:'brain-derivation-drain', budgetMs:1000}, {id:'jtbd-update', argv:['userprompt'], budgetMs:400}, {id:'auto-explore-drain', budgetMs:900}]`. Each check loads by a string-literal lazy require (`require('../../scripts/intent-classifier.cjs')` inside a function), so `tests/test-369-hook-require-graph.cjs` can walk it (F-25).
  Alternative (OR-2 B): the ROADMAP order, with intent-classifier last.
- `dispatch(input, opts)` runs the checks one at a time, by the plan 13 rules (F-23, F-24): start rule, per-check deadline, env snapshot and restore, stop after a block (no routable check blocks today; the rule stays for safety), notes on a `notes[]` list. `opts.startedAt` is the clock origin (receipt time of the tool call, not process start, because the server process is long-lived). `opts.checks` is the test seam.
- `hostView(result)` and `mergeViews(views)` are the plan 13 functions (F-24). `mergeViews` returns `{additionalContext, systemMessage, stop}`.
- `toHookText(merged)` returns exactly one JSON text: `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext": <joined>}}`, plus `systemMessage` and `continue`/`stopReason` keys only when present. With no context it returns `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":""}}` (GUESS that an empty string is accepted; the alternative is `{}`, which F-04 names as a non-failure answer; the spike leg decides). It never returns plain text.

The invariant command script uses the same `hostView` and `mergeViews` for its two checks, so both tiers share one output model.

## 3. The invariant tier (G5, OR-1 A, OR-3 A)

New script `scripts/userprompt-invariant.cjs`, one hooks.json entry: `node "${CLAUDE_PLUGIN_ROOT}/scripts/userprompt-invariant.cjs"`, timeout 3, no async key, the form of the other node hooks (Windows: node direct, no cmd or bash step).

1. Read fd 0 once. `setHookBusyCap` is not needed: neither check opens room.db (F-11 shows 0-37 ms; GUESS that first-install-router opens no room.db; check with the plan 10 lock leg).
2. Run `admin-command-gate.run(input)`. On a block view: write the gate stderr, no stdout, exit 2, and stop. The turn ledger is not written for a blocked prompt, because the host erases a blocked prompt.
3. Run `first-install-router.run(input)` (keeps its 400 ms spawnSync, F-17).
4. Turn ledger (section 7), then write one envelope with the router context plus the optional note, through `finishCli`.

Order between the two entries: none (F-03). The words "runs first" in G5 hold inside the invariant script only. Parity with today holds, because the six hooks run in parallel today. A block from admin-command-gate still blocks the prompt (G10). The routable tier can still run on a blocked admin prompt, as today. This needs OR-1. Alternative OR-1 B (the tool waits for the invariant ledger record) is not designed, because it puts the command cold start back on the routable path.

Alternative OR-3 B: keep the two existing entries unchanged. Then put the turn-ledger code in `first-install-router` (2 processes per prompt).

## 4. The hook tool (G6, G7)

New file `lib/mcp/tools/userprompt-hook.cjs`, auto-discovered by `register-core-tools.cjs` (F-19).

- Name `userprompt_hook`. Description (target under 600 bytes, OR-7): "Internal: the MindrianOS UserPromptSubmit hook calls this tool. Do not call it yourself. A direct call is refused." Input schema (zod): `prompt`, `session_id`, `cwd`, `transcript_path`, `hook_event_name`, all optional strings.
- hooks.json `mcp_tool` entry: `{"type":"mcp_tool","server":"plugin:mos:mindrian-os","tool":"userprompt_hook","input":{"prompt":"${prompt}","session_id":"${session_id}","cwd":"${cwd}","transcript_path":"${transcript_path}","hook_event_name":"${hook_event_name}"},"timeout":3}`. No `onFailure: "block"`: a failure of the routable tier must never block a prompt (F-04: with block, any non-empty answer counts as a failure).
- A field that arrives as a literal `${...}` text is treated as absent (F-05 GUESS guard).
- Handler steps: (1) the call-origin check of section 6; (2) rebuild the hook stdin JSON `{session_id, cwd, prompt, hook_event_name:'UserPromptSubmit', transcript_path}` as the plan 12 `input` text; (3) `await dispatch(...)` inside the hook context of section 5.3; (4) write "turn served" (section 7); (5) return `{content:[{type:'text', text: toHookText(merged)}]}`. It never returns `isError`, because an error is silent to the model (F-07). A thrown error inside a check becomes a `check_threw` note and the other checks go on.
- Notes (skipped_deadline, over_deadline, room_db_busy, check_threw) go to the server stderr with the prefix `[userprompt_hook]`, never to stdout (stdout carries JSON-RPC). They are not put in additionalContext, which keeps parity (G10).
- Connector declaration (OR-5 A): `connectors: [{tool:'userprompt_hook', surface:'userprompt_hook', connector:'mcp-tool', excluded:true, reason:'Hook plumbing: called only by the UserPromptSubmit mcp_tool hook; not a user or model surface.', layer:'harness', layer_why:'...'}]`. Generator change in `scripts/build-connector-registry.cjs` `normalizeMcpToolEntry` (F-20): when `excluded === true`, emit `excluded: true`, `reason`, and `connects_to_spine: false`; a missing reason is a `--check` error, the same as for commands (:737-774). `scripts/check-shape-declaration.cjs` treats an excluded MCP tool as exempt from `hitl_shape`, the same as an excluded skill. Alternative OR-5 B: WIRED with `hitl_shape:'none'`, the `stop_gate_check` precedent (F-19c); no generator change.
- Tool budget (OR-7 A): re-baseline `tests/test-270-tool-schema-budget.cjs` AFTER from 76 to 77, with a dated block that records the byte delta, as the 374-13 block does (F-21).

## 5. Running the scripts inside a long-lived server (G9; plan 12 hand-off)

### 5.1 Deadlines
- Clock origin: the receipt of the tool call. Overall deadline 2,500 ms, output reserve 100 ms (F-23). The hook timeout is 3 s (OR-8 A), so the tool answers about 400 ms before the host cancels it.
- Per-check budgets from plan 13 (F-23). A check whose turn starts after 2,400 ms is skipped with `skipped_deadline <id>`. An async check over budget is cut with `over_deadline <id>`; its late output goes to a dead sink (plan 12 classifier rule, F-10).
- No queue, no worker thread (G9, Stage 8 S5). A synchronous section cannot be preempted (F-13). The known synchronous waits are the room.db busy waits, bounded by the scoped cap (5.3).
- If the server is busy with a long synchronous tool call when the hook call arrives, the hook call starts late. When it starts after its deadline window, it answers at once with no context and a `skipped_deadline all` note, and the turn is recorded as not served (section 7), so the next prompt gets the typed note.

### 5.2 Environment
- Snapshot `process.env` before each check and restore it after the check (plan 13 P6). This covers F-14.
- Known limit (GUESS impact: low): the classifier awaits its navigation engine block. Another MCP tool call that runs during that await sees the changed env. The changed value is the same path under a second name (`MINDRIAN_ROOMS_HOME = MINDRIAN_ROOMS_ROOT`, F-14). Record it in the SUMMARY.

### 5.3 The busy cap (OR-9 A)
- Change `lib/core/hook-busy-cap.cjs` to keep its state in an `AsyncLocalStorage` store when one is active, and in module state otherwise. `dispatch()` runs inside `hookCapStore.run({cap: null, tripped: false}, ...)`. Every room.db open made inside the hook call (including its awaits) sees the per-call cap; every other tool call sees no cap and keeps the 5,000 ms wait. The command-hook path (no store) keeps today's module-state behaviour, so plan 10 tests do not change.
- `node:async_hooks` is a built-in, so the zero-requires rule of the file holds for non-built-in modules. GUESS: the file header says "Zero requires on purpose" (F-12); requiring a built-in keeps the reason of that rule (no cycle with room-db.cjs). The reviewer should check it.
- Alternative OR-9 B: reset `_cap` and `_tripped` before and after each hook call (racy with tool calls that interleave). Alternative OR-9 C: no change (every tool in the session gets the cap; not acceptable).

### 5.4 Room and session
- The plan 12 run() of the classifier, jtbd-update and brain-derivation-drain read `session_id` and `cwd` from the input JSON (plan 14 resolveSessionRoom: binding, then `cwd.room_root`, then the registry active room). The tool passes the host `session_id`, not the server stdio key (F-19b).
- auto-explore-drain takes its room from `MINDRIAN_ROOM_DIR` or `process.cwd()` (F-16). Change: run() accepts `opts.roomDir`; `dispatch()` passes the room that the input `cwd` resolves through the same plan 14 resolver. The CLI path is unchanged (golden X5 stays green). Do not set `MINDRIAN_ROOM_DIR` in the server env, because env changes leak (5.2).

### 5.5 Concurrency
- stdio: one server per session (F-19). The classifier serialization (F-15) then only orders hook calls of one session, which arrive one per prompt.
- MCP-first HTTP mode (`MINDRIAN_MCP_FIRST`, default off): not supported by this phase. The tool answers with no context and a `mcp_first_http_unsupported` note when the server runs on the HTTP transport (F-28). This keeps one session per process for every hook call.

## 6. A direct model call (G7, OR-6)

- OR-6 A (recommended): spike first. Compare the request of a hook call and of a model call (the `extra` argument, `_meta`, request id shape). If a stable host marker exists, the handler refuses a call without it. The refusal is the plain text `refused: not_a_hook_call` (a model call receives plain text normally; the plain-text drop of F-07 applies only to hook calls). A refused call runs no check and writes nothing.
- OR-6 B (fallback if no marker): (1) replay guard: the server keeps the last `(session_id, sha256(prompt))` it served; a second call with the same pair returns the stored text and writes nothing; (2) transcript check: refuse unless the prompt equals the last user message in `transcript_path`. Whether the prompt is in the transcript when UserPromptSubmit fires is UNVERIFIED (spike leg L3).
- OR-6 C: accept the residual risk in writing.

## 7. First prompt and a server that does not answer (G8, OR-4 A)

Turn ledger: two small JSON files per session, each with one writer only, so no update is lost between the two parallel entries.
- `~/.mindrian/userprompt-turns/<session_id>.seen.json` = `{v:1, seen:<n>, noted:<k>, at}`. Only the invariant script writes it.
- `~/.mindrian/userprompt-turns/<session_id>.served.json` = `{v:1, served:<m>, at}`. Only the tool writes it.
- Same directory rules as the plan 14 cue records: safe session slug, atomic write (temp file plus rename), 24 h stale rule.

Rules:
- The invariant script, on a prompt that is not blocked: read `seen`, `noted` and `served`. Let `missed = seen - served`. If `missed > 0` and `noted < seen`, add one context line: `[MindrianOS] Prompt help (navigation card, next-move cue) was skipped on <missed> earlier prompt(s): server_not_answering.` and set `noted = seen`. Then set `seen = seen + 1`.
- The tool, after `dispatch()` answers inside its deadline: set `served = served + 1`. A call that answers with `skipped_deadline all` does not count as served.
- Why the parallel run is safe: the previous prompt's tool call ends before the next prompt exists (the model answers between prompts). On prompt N the tool can count N before the command hook reads; then `missed` undercounts by 1 at most and never shows a false note. A silent miss can come only from a tool call that finished after the host cancelled it: it counts as served while the model saw nothing. The 400 ms reserve between the 2,500 ms deadline and the 3 s timeout makes that rare (GUESS; T4 measures it). The tool counts a turn as served only when it answers before `startedAt + 2,500 ms`.
- A blocked admin prompt increments neither file, so it creates no note.

- What the user sees on a cold first prompt: no NAV block on prompt 1, and on prompt 2 one plain line that says it was skipped and why. No silent loss (G8).
- Measurement leg (all options): start the server with an injected boot delay (env `MOS_TEST_BOOT_DELAY_MS`, test only) of 4,000 ms, send one prompt, and record whether the host waits up to MCP_TIMEOUT (F-04), cancels at 3 s, or skips. Record the result in the SUMMARY. If the host waits and the hook then answers, OR-4 needs no note on the first prompt, and the note covers only a down server.
- Alternative OR-4 B (command fallback): the invariant script also runs the four routable checks when the ledger shows `served == 0` for the session. Risk of a double run on prompt 1 when the server does answer. Alternative OR-4 C: a longer mcp_tool timeout (needs the owner to say that G13 does not bind 400.5).

## 8. Output parity (G10)

- Unit of parity: for each parity case E1-E6 (F-26), the list of non-empty per-check context strings, in check order, from the six separate CLIs equals the list from the two tiers (invariant list, then routable list). The block decision and the block text of E4 are equal.
- Framing that changes and is recorded, not hidden: 2 system reminders instead of up to 6 (F-27); the order between the two tiers is not fixed by the host (F-03); a blocked prompt can still run the routable tier, as today.
- `context_over_cap` rule of plan 13 applies per tier (F-24).
