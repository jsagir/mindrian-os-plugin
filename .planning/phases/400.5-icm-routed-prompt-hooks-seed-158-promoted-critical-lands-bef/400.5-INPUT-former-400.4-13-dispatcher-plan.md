Claude Code hook facts (planner read https://code.claude.com/docs/en/hooks on 2026-11-26):
- The matching hooks of one event run in parallel. A hook that reaches its timeout (in seconds) is cancelled and its output is discarded.
- On exit 0, UserPromptSubmit plain-text stdout is added as context. Stdout counts as JSON only when it is exactly one JSON object with only whitespace around it; any other stdout is plain text. A text that starts with { and ends with } but is not valid JSON is a parse failure and adds nothing.
- Exit 2 blocks the prompt; the block message is the hook's stderr. JSON {decision: "block", reason} on exit 0 also blocks, with the reason as the message.
- "When several hooks return additionalContext for the same event, Claude receives all of the values." The order and separator are not specified. Each value is injected as a system reminder that starts with the hook's name.
- additionalContext, systemMessage and plain stdout are capped at 10,000 characters each, measured per hook. A value over the cap is saved to a file, and Claude gets the path and a 2,000-character preview.

Planner decisions from those facts:
- One process has one stdout, so the dispatcher writes one JSON envelope: {continue: true, hookSpecificOutput: {hookEventName: 'UserPromptSubmit', additionalContext}} where additionalContext is the non-empty per-check context strings in check order joined with CONTEXT_SEPARATOR ("\n\n"). systemMessage values join with "\n"; the first continue false wins with its stopReason. With no context, no systemMessage and no stop, it writes {"continue":true}. The reminder now starts with the dispatcher's name; the text is the same. Record this in the SUMMARY.
- The cap is per string, so six strings that each fit can sum to more than CONTEXT_CAP_CHARS (10,000). Do not drop or truncate a check's context. When the joined string is longer, write "[userprompt-dispatch] context_over_cap <total>: <id>=<len>, ..." to stderr. Record the largest joined length of the parity cases in the SUMMARY.
- Block: when a check's view is a block (code 2, or a JSON block decision), write the block text to stderr, write no stdout, exit 2 and run no later check. The host erases a blocked prompt, so the later context never reached the model. The difference: drains after the gate run on the next prompt, not on the blocked one. Record it in the SUMMARY.
- A check that misses its deadline gives no output, the same as a host-killed hook.
- One process cannot preempt synchronous code. A synchronous check that runs past its budget finishes; the dispatcher keeps its output only when it ends before the overall deadline, else it notes over_deadline and drops it. Plan 10 bounds the room.db waits (750 ms once, then 0, shared by every check in the process).

Constants (export them; the SUMMARY records the measured time of each check on the parity fixture):
