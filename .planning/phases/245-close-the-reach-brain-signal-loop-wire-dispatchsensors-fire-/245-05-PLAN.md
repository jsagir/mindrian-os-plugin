<objective>
Compute Brain's `pattern_matches` verb unconditionally and surface it on the decision trace, so
Requirement 1's third fusion input exists at all (D-24, D-25, 245-RESEARCH.md F-2).

Purpose: `resolveFireSkill` (`lib/core/navigation-engine.cjs:596-660`) has a strict precedence
order: wicked escalation, then a fired sensor reach (step 2, which returns early), then the
Brain `pattern_matches` verb (step 3, additionally gated on
`tierMode === 'mode_a' && weightApplied > 0`). A sensor fired on essentially every observed turn
this session, so step 3 never runs. D-24 diagnosed the Brain verb as STARVED. F-2 sharpened it:
`extractTopCandidateVerb(pm.body)` is called at only two places, `resolveFireSkill` step 3 (line
646, unreached on a sensor-fires turn) and the RECOMMENDED-marker gate (line 1237, which is
itself gated on `tierMode === 'mode_a' && !attributionBreach && recommendedConfidence >= 0.7` and
which discards the verb after using it as a boolean). On a normal sensor-fires turn the verb
string exists NOWHERE downstream. Requirement 1's third blend input needs real plumbing, not a
reordering of the existing chain.

Correction to F-2 worth recording: F-2 states `extractTopCandidateVerb` has "exactly ONE caller
in the entire codebase". A live grep finds TWO (lines 646 and 1237). The substance is unaffected:
neither surfaces the verb downstream, and line 1237's caller is gated behind a 0.70 confidence
floor that a merely-present verb does not clear. Line 1237 is nonetheless the right neighborhood
for this plan's work, because it already sits inside `decide()`'s trace assembly and already
reads `brain.sections.pattern_matches`.

This plan changes NO routing behavior. `resolveFireSkill` is not touched. `fire_skill` must come
out byte-identical on every existing fixture.

Output: two new decision-trace fields and a test that proves the verb survives a sensor-fires
turn.
</objective>
