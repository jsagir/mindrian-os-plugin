## Summary: top 3 moves ranked by impact x fit

1. **Replace the all-pairs drain with a top-k cosine pruner over the Float32Array cache; the cursor stays as the safety net.** Measured here: the full N x (N-1) = 4,676,406 dot products for N=2163, D=384 took 10,832 ms in plain JS (PROVEN probe, below). The symmetric half is about 5.4 s (ASSUMED, half of the measured pass). The candidate set becomes N x k = 21,630 pairs at k=10; at 3.5 ms per scored pair (RESEARCH.md line 64, PROVEN there) that is about 76 s instead of 137 min (ASSUMED arithmetic). No library is needed: every pure-JS or WASM index checked in Q1 is either unmaintained since 2023, browser-first, or a brute-force scan the repo can write in 40 lines.
2. **Swap the scout's cyclic Jacobi eigensolver for a randomized or subspace-iteration truncated SVD, in a bounded follow-up gated by the 272 parity test; keep the cap as this phase's floor.** Halko, Martinsson and Tropp: "For a dense input matrix, randomized algorithms require O(mn log(k)) flops in contrast with O(mnk) for classical algorithms" (PROVEN https://arxiv.org/pdf/0909.4061). Measured here: a 120-line plain-JS randomized truncated SVD on a 2163 x 2000 matrix, k=80, oversampling 10, 2 power iterations, 2 percent density took 3,381 ms (PROVEN probe), against 11 to 19 min per Jacobi sweep and 10 to 14 sweeps (CONTEXT.md addendum item 2). Do not drop LSA: the scout's product is the disagreement between the LSA leg and the embedding leg (Q2).
3. **Do not import RxDB into lib/core; borrow three of its ideas.** The QueryCache page describes a runtime cache of query objects with an idle-time replacement policy (PROVEN https://rxdb.info/query-cache.html). The vector article proposes "Distance to Samples" indexing and a resumable embedding pipeline (PROVEN https://rxdb.info/articles/javascript-vector-database.html). Root package.json has no rxdb (PROVEN grep); rxdb 17.6.0 carries 24 runtime dependencies and 11.26 MB unpacked (PROVEN registry). The transferable ideas are: resume from a checkpoint (the CPU379-02 cursor), invalidate by content hash and model (D-379.1-06), run maintenance when idle (Q5).

## Q3 incremental computation and the RxDB query cache

What RxDB QueryCache does (PROVEN https://rxdb.info/query-cache.html): it keeps `RxQuery` instances for reuse "especially when RxDB is used in UI-applications where people move for- and backwards"; with the event-reduce algorithm "cached queries are even valuable for optimization, when changes to the database occur between now and the last execution"; the cache replacement policy "runs regularly, depending on when queries are created and the database is idle"; the default policy never uncaches queries with subscribers, keeps "less than 100 queries without subscriptions", prefers to uncache queries "that have never executed and are older than 30 seconds" and those "not been used for longer time"; a custom policy is a function set as `cacheReplacementPolicy` on the collection. RxDB depends on `custom-idle-queue` 5.0.2 and `event-reduce-js` 7.0.1 (PROVEN https://raw.githubusercontent.com/pubkey/rxdb/master/package.json).

What transfers to a pair-score memo keyed by (hash_a, hash_b, scorer_version):
- Invalidate by key, not by time: a changed artifact changes hash_a, so only its rows die; with top-k pruning that is at most k rows where it is the query plus the rows where it was a candidate (ASSUMED design).
- Run eviction when idle, and bound the memo (RxDB: fewer than 100 idle queries). For the drain: a memo of N x k rows (21,630 at k=10) is small; the all-pairs memo (2,338,203 rows) is the thing to avoid (ASSUMED).
- From the vector article: "resume processing documents from where it left off if it's closed or interrupted" through the pipeline plugin, and "when you change your model, you have to recreate all embeddings" (PROVEN) = the CPU379-02 cursor and D-379.1-06.

What does not transfer: RxDB caches query objects over a document store with a change stream, and event-reduce patches a query's result set from document change events; a pair score is a function of two contents and cannot be patched, only recomputed. RxDB's policy is about memory of live UI queries, not CPU of a batch job.

RxDB in the repo (PROVEN by grep on 2026-10-21): root package.json has no rxdb; rxdb is pinned at 17.5.0 in ui/shared/package.json:13 and ui/shell/package.json:24 (walled UI packages) and `^17.5.0` in .planning/spikes/006-room-pull-checkpoint/package.json:12; no rxdb in npm-shrinkwrap.json; lib/ui-shell/dist carries it only inside built Next.js chunks. Importing RxDB into lib/core would be a NEW root dependency: 24 runtime dependencies including graphql, ws, simple-peer and nostr-tools, 11.26 MB unpacked, engines node >= 20 (PROVEN registry and master package.json). CLAUDE.md keeps UI packages out of the root package.json. Verdict: do not import; borrow the ideas.

Salsa (PROVEN https://docs.rs/salsa): tracked functions are memoized; dependencies are "the queries and fields read by their body"; "If a query's dependencies have not changed, Salsa reuses its memoized result"; backdating: "If they are equal, Salsa preserves the memo's previous 'changed at' revision" so invalidation does not propagate; an `lru` option evicts least-recently-used results. Adapton (PROVEN https://www.cs.tufts.edu/~jfoster/papers/cs-tr-5027.pdf): a dirtying phase marks nodes that transitively depend on a changed input; a propagation phase re-evaluates only demanded dirty nodes. Transfer: the memo key is the Salsa query key; backdating means: if a re-embedded artifact's cosine to each neighbor moves less than the CONVERGES and INFORMS floors, keep the existing edges and do not rewrite room.db (ASSUMED design, floors in RESEARCH.md line 301). Does not transfer: Salsa traces dependencies inside one process at run time; the drain is a detached process with a JSON queue and a SQLite graph, so dependencies must be explicit in the key.

LangChain CacheBackedEmbeddings (PROVEN https://docs.langchain.com/oss/javascript/integrations/embeddings and https://reference.langchain.com/python/langchain-classic/embeddings/cache): "the text is hashed and the hash is used as the key in the cache"; `namespace` "Helps avoid collisions (e.g., set it to the embedding model name)"; "by default only document embeddings are cached". LlamaIndex IngestionCache (PROVEN https://www.llamaindex.ai/blog/announcing-llamaindex-0-9-719f03282945 and the Ingestion Pipeline guide): "it caches a hash of the input nodes + transformations and the output of that transformation"; with a docstore, "If a duplicate doc_id is detected and the hash is unchanged, the node is skipped". Does not transfer: both caches are per text; neither caches a pairwise score.

## Q5 background CPU budgeting

- Node `os.setPriority` (PROVEN https://nodejs.org/api/os.html): priority is an integer from -20 to 19 mapped to six constants; `PRIORITY_LOW` is `IDLE_PRIORITY_CLASS` on Windows and nice 19 elsewhere; `PRIORITY_BELOW_NORMAL` is `BELOW_NORMAL_PRIORITY_CLASS` and nice 10; `PRIORITY_HIGHEST` on Windows needs elevation or is "silently reduced to PRIORITY_HIGH". RESEARCH.md line 352 already proved on WSL that lowering works and that raising back throws EACCES.
- ONNX Runtime threading (PROVEN https://onnxruntime.ai/docs/performance/tune-performance/threading.html): `session.intra_op.allow_spinning` "0" stops workers from spinning; `session.intra_op.spin_duration_us` caps the spin window in microseconds, "0 disables spinning entirely", "1000 for 1 ms" caps it; the defaults keep spinning on. JS `SessionOptions.extra` is documented as "available only in WebAssembly backend. Will support Node.js binding and react-native later" (PROVEN https://onnxruntime.ai/docs/api/js/interfaces/InferenceSession.SessionOptions.html). The Node binding source on main contradicts the doc: `IterateExtraOptions` walks `sessionOptions.extra`, joins nested keys with ".", requires string values ("sessionOptions.extra value must be a string in Node.js binding") and calls `sessionOptions.AddConfigEntry` (PROVEN https://raw.githubusercontent.com/microsoft/onnxruntime/main/js/node/src/session_options_helper.cc). Whether onnxruntime-node 1.30.0 carries this code is UNVERIFIED (open question 1). transformers.js 4.3.0 forwards `pipeline(task, model, { session_options })` to `from_pretrained` and spreads it into `InferenceSession.create` (PROVEN /home/jsagi/.mindrian/eureka-deps/node_modules/@huggingface/transformers/src/pipelines.js:114,175 and src/backends/onnx.js:281-290). So `session_options: { intraOpNumThreads: 2, interOpNumThreads: 1, extra: { session: { intra_op: { allow_spinning: "0" } } } }` is the full form to probe.
- git maintenance (PROVEN https://git-scm.com/docs/git-maintenance): `--auto` runs "only if certain thresholds are met" (gc.auto loose objects, gc.autoPackLimit); `start` schedules `git maintenance run --scheduled` "on an hourly basis"; `maintenance.autoDetach` decides foreground or background; scheduled runs take a lockfile so that no other maintenance runs concurrently (PROVEN quote of git's source at https://stackoverflow.com/questions/45426297). Pattern: threshold-triggered work, a schedule, one lock. That is CPU379-02 (bound), CPU379-05 (lock) plus a "nothing to do" check before any embedder load.
- Linux nice and cgroups: cgroup v2 `cpu.weight` 1 to 10000 with default 100, `cpu.weight.nice` as the nice-valued alias (PROVEN https://docs.kernel.org/admin-guide/cgroup-v2.html); `cpu.max "50000 100000"` limits a group to 50 percent (PROVEN https://labs.iximiuz.com/tutorials/controlling-process-resources-with-cgroups). Writing cgroup files needs root and a mounted cgroup2 tree (ASSUMED), so an unprivileged plugin cannot plan on it under WSL2; nice through `os.setPriority` is the portable lever.
- Idle-time patterns: RxDB runs its cache policy "when the database is idle" through `custom-idle-queue` (PROVEN above). VS Code extension host and Obsidian indexer scheduling: no authoritative page was read (the search returned issue threads only); UNVERIFIED, not cited.
