<objective>
Extend THEO-01's executable-chain-validation fix (354-09) with the navigator-directed TypeSafe/Jev addition (354-CONTEXT.md Addendum 2026-09-23, "any part that falls into the typesafe ai realm of capabilities, utilize it"): a sibling of the already-shipped Phase 353 `scripts/build-section-command-ledger.cjs` pattern, scoring every (Theo framework label x real `data/command-registry.json` command id) pair ONCE at dev time with TypeSafe's Jev (typed choice/score, no text generation, calibrated confidence), shipped as static `data/framework-command-ledger.json`, read at runtime with zero vendor calls.

Why this plan exists on top of 354-09, not instead of it: 354-09 makes brain-router.cjs accept a chain candidate only when it is an exact `KNOWN_METHODOLOGIES` slug -- this is the complete safety fix (no invalid id can ever enter a chain, by construction). Its cost is recall: a Theo framework label with no already-exact slug candidate now silently drops to `rejected_candidates`, even when a correct label-to-command mapping exists. This plan recovers that recall WITHOUT touching the safety property, by consulting a pre-scored, dev-time-vetted, human-reviewable ledger -- never a live runtime guess. This is precisely the shape the spike-findings skill rules IS a Jev seat (finite input space, scored once, shipped as data) and precisely NOT the shape ruled OUT (a live per-turn vendor call, or the Part 8 egress guard itself).

Out of scope: any change to 354-09's exact-slug safety check itself (byte-unchanged), any live runtime call to TypeSafe from plugin code (the builder is navigator-invoked pre-release only, exactly like its sibling), any change to `recommendChain`'s own normalization (untouched, per CTX-CORRECTED).
</objective>
