# Phase 355.1: Code Review Report

**Reviewed:** 2026-09-27
**Depth:** deep
**Files Reviewed:** 12 (plus scripts/on-stop and lib/core/verification-stamp.cjs / lib/core/brain-client.cjs read for call-chain tracing)
**Status:** issues_found

## Summary

Scope: every non-`.planning` file touched by the 63 commits between `6e0401525~1` and `HEAD` whose subjects contain "355.1" (`git diff --stat` against that range: 33 lib/scripts/hooks/data files plus 28 test files, ~12.3k insertions). This review focuses on the ambient-trigger evaluator, the ambient-run child lifecycle, the cadence-guard ledger/lock/delta-state machinery, the two seams that start it (the CLI Stop hook and the MCP close-out), and the fingerprint-hook material path.

The module-level discipline (never-throw, closed enums, Part 8 hygiene, atomic temp-then-rename writes) is real and mostly held to. The genuine defect is architectural, not cosmetic: **the claim/lock/release protocol that is supposed to guarantee "one ambient run at a time per room" has real gaps**, and the two independent seams that start an ambient run (the standalone `ambient-stop.cjs` Stop hook and the MCP daemon's `_closeOutAmbientTrigger` close-out) are wired to fire on the **same Stop event, for the same CLI session**, whenever `MINDRIAN_MCP_FIRST` is set — which is exactly the collision the claim protocol needed to be airtight against, and isn't.

Four BLOCKER-level findings below are all provable by direct code reading (no speculation): a TOCTOU race in the claim path, a claim that leaks (never released) on three distinct abort paths, a lock that has no owner/token so a slow run's own cleanup can silently evict a different run's active lock, and the double-registration of the ambient evaluator on the CLI Stop event under `MINDRIAN_MCP_FIRST`.

## Critical Issues

### CR-01: `claimAmbientRun` has no compare-and-swap — two concurrent evaluators can both "claim" the same delta and both spawn a child

**File:** `scripts/scout-cadence-guard.cjs:656-684` (`claimAmbientRun`), consumed by `lib/core/ambient-trigger.cjs:277-290` (`evaluateAndClaim`)

**Issue:** `claimAmbientRun` is a plain read-modify-write: `readAmbientLedger` (read) → mutate `ledger.in_flight` / `ledger.runs_window` in memory → `atomicWriteJsonAmbient` (write). The "atomic" part only protects the write itself (temp+rename); it does nothing to prevent two processes from both reading the ledger *before* either has written, both concluding `claimed: true`, and both proceeding to spawn a child. There is no `fs.openSync(path, 'wx')`-style exclusive claim anywhere in this function — contrast with `acquireAmbientLock` two hundred lines later in the same file, which *does* use the correct atomic primitive for the same problem.

**Concrete failure scenario:** `hooks/hooks.json` registers `scripts/ambient-stop.cjs --stop` as its own independent Stop hook entry (seam `stop_hook`). Separately, `scripts/on-stop` (also a Stop hook, run in the *same* Stop event dispatch) has a `MINDRIAN_MCP_FIRST` branch (`scripts/on-stop:57-135`) that queries the MCP daemon's `stop_gate_check` tool, which runs `lib/mcp/stop-gate-handler.cjs:handleStopEvent` → `closeOutRoom` → `_closeOutAmbientTrigger` (seam `closeout`, `lib/mcp/stop-gate-handler.cjs:221-229`). Both processes call `ambientTrigger.evaluateAndMaybeSpawn(roomDir, ...)` for the *same room* within milliseconds of each other, driven by the *same* Stop event. Both read the ledger with `in_flight: null`, both compute the same `delta_hash` (same room, same instant), both call `claimAmbientRun` and get `claimed: true`, both write the delta-state side channel to `run_state: 'started'`, and both spawn a Phase-117 fire child in `--ambient` mode with the same `ambient-<hash>` id. This is precisely the "double run, double card" scenario named in the review brief, and it is reachable in normal operation any time `MINDRIAN_MCP_FIRST` is set for the CLI surface — not just under adversarial conditions.

**Fix:** Make the claim itself the atomic primitive, not just the write. Either (a) acquire `acquireAmbientLock` *before* calling `claimAmbientRun` (i.e. move the lock to guard the claim, not just the composition), or (b) implement `claimAmbientRun` with an exclusive-create sentinel file keyed by `delta_hash` (mirroring `acquireAmbientLock`'s `wx` idiom) so a second claimant's write is rejected rather than silently succeeding.

### CR-02: A spawn failure (and two other abort paths) never releases the in-flight claim — a transient failure blocks all ambient triggering on the room for up to 8 minutes

**File:** `lib/core/ambient-trigger.cjs:337-372` (`evaluateAndMaybeSpawn`'s `!spawned` branch); also `lib/core/ambient-run.cjs:700-708` and `lib/core/ambient-run.cjs:689-698` (the two `tamper_or_stale` early returns in `runAmbientInChild`)

**Issue:** When `evaluateAndClaim` succeeds, `ledger.in_flight` is populated (`scripts/scout-cadence-guard.cjs:665-670`) with a `started_at` timestamp. The *only* place that clears it before a full run completes is `releaseAmbientClaim`, and the *only* caller of `releaseAmbientClaim` in the whole ambient-run lifecycle is the `!lockResult.ok` branch of `runAmbientInChild` (`lib/core/ambient-run.cjs:724-728`). Walk every other path that can end a claimed run without ever spawning/finishing a composition:

- `evaluateAndMaybeSpawn`'s spawn-failure branch (`ambient-trigger.cjs:350-372`): on `spawnImpl` throwing (missing fire script, `EAGAIN`/`ENOMEM` from `child_process.spawn`, a transient OS fork failure) it writes `run_state: 'spawn_failed'` to the delta-state side channel and returns `spawn_failed` — but **never calls `releaseAmbientClaim`**. The ledger's `in_flight` stays set with the original `started_at`.
- `runAmbientInChild`'s ambient-mode tamper check (`ambient-run.cjs:700-708`): if the delta-state side-channel write from `evaluateAndClaim` was itself soft-failed (best-effort, `ambient-trigger.cjs:293-308` swallows the write error) or lost a race with another writer, the spawned child sees `run_state !== 'started'` and returns `tamper_or_stale` **without releasing the claim**.
- `runAmbientInChild`'s post-lock re-verification (`ambient-run.cjs:714-717`) has the identical gap.

**Concrete failure scenario:** `spawnImpl` throws once (e.g. the OS is momentarily out of process slots, or `firePath` doesn't exist because of a mid-update plugin state). `evaluateAndMaybeSpawn` returns `spawn_failed`, `ledger.in_flight` is left populated. For up to `AMBIENT_LOCK_STALE_MS` = 8 minutes (`scripts/scout-cadence-guard.cjs:367`), `shouldRunAmbient`'s ladder checks `in_flight` *before* anything else (`scripts/scout-cadence-guard.cjs:609-618`) and returns `{run:false, reason:'in_flight'}` for every subsequent evaluation — even though no child is actually running and even though genuinely new material has since been added to the room. The user gets zero ambient runs for up to 8 minutes after one transient spawn hiccup, with no self-healing other than waiting out the stale window.

**Fix:** Every non-completing exit from a claimed run must call `releaseAmbientClaim(roomDir, deltaHash)`. Add it to the spawn-failure branch in `ambient-trigger.cjs` and to both `tamper_or_stale` returns in `ambient-run.cjs`, or better: wrap the whole claimed lifecycle in a single `try/finally` that releases unless a downstream success path (recordAmbientRun) has already superseded the claim.

### CR-03: The ambient lock has no owner/token — stale-reclaim by a new run followed by the original (slow) owner's own `finally`-block release deletes the new owner's live lock

**File:** `scripts/scout-cadence-guard.cjs:824-866` (`acquireAmbientLock` / `releaseAmbientLock`), consumed by `lib/core/ambient-run.cjs:724-810`

**Issue:** `acquireAmbientLock` writes the PID into the lock file (`fs.writeSync(fd, String(process.pid))`, line 834) but **nothing ever reads it back** — not the stale-reclaim check (`(nowMs - st.mtimeMs) > AMBIENT_LOCK_STALE_MS`, mtime-only) and not `releaseAmbientLock`, which unconditionally does `fs.rmSync(lockPath, {force:true})` regardless of which process created the file currently at that path.

**Concrete failure scenario:**
1. Child A acquires the lock at T=0 and begins `runAmbientComposition`. Its per-producer wall-clock check (`ambient-run.cjs:517`, `(Date.now() - wallStart) >= budgetMs`) only fires *between* producers — it cannot interrupt a single `await adapterFn(...)` call already in flight. A producer's own Theo call (`verification-stamp.cjs` → `brain-client.cjs`) can retry up to 3 attempts × a 20s timeout for transport errors (`BRAIN_REQUEST_TIMEOUT_MS=20000`, `RETRY_MAX_DEFAULT=2`, `lib/core/brain-client.cjs:47,59-60`), or up to 4 attempts on rate-limiting — and `verificationStamp.stampFindings` fans this out with `pool(4)` over up to `AMBIENT_TOP_N=10` pairs per producer, across up to 5 producers. Under a degraded/rate-limited Brain, real wall-clock for one composition can exceed the nominal `AMBIENT_TOTAL_BUDGET_MS` (4 min) and approach or exceed `AMBIENT_LOCK_STALE_MS` (8 min) — the review brief's own baseline (166s max observed) assumed a healthy Brain; nothing in this file bounds the unhealthy case.
2. Once the lock file is older than 8 minutes, a fresh Stop event's `evaluateAndMaybeSpawn` reaches `shouldRunAmbient` → sees the lock file exists but is stale → does **not** block (`scripts/scout-cadence-guard.cjs:629-641`, `lockFresh=false`) → returns `{run:true}`. A new claim is taken and Child B spawns, calls `acquireAmbientLock`, sees the stale file, `fs.rmSync`s it, and writes its own lock file. Child B is now genuinely, legitimately running.
3. Child A's slow producer call eventually resolves (or its retries exhaust). Child A finishes its composition and reaches its `finally { releaseAmbientLock(roomDir) }` (`ambient-run.cjs:809-811`). This unconditionally removes **whatever lock file currently exists** — which is now Child B's, not Child A's own (Child A's was already removed by Child B's reclaim in step 2). Child B's lock is silently deleted while Child B is still actively running its own composition.
4. A third evaluation can now acquire the lock and start Child C concurrently with the still-running Child B: two compositions writing to the same room.db (`navigation.openRoomDbForCaller`) and racing to file the same SENS-13 opportunity node at once.

**Fix:** Store a random nonce (not just the PID, which is meaningless across the reclaim boundary and never validated) in the lock file at acquire time, and require both `releaseAmbientLock` and the reclaim-then-acquire retry to verify that the caller's own nonce is still the one on disk before removing it — a "release my lock only if it's still mine" compare-and-delete, the standard fix for ownerless advisory locks.

### CR-04: The ambient evaluator is wired to fire twice on the same Stop event for CLI sessions running under `MINDRIAN_MCP_FIRST`

**File:** `hooks/hooks.json:200-209` (the new `ambient-stop.cjs --stop` Stop-hook entry) vs. `scripts/on-stop:57-135` (the `MINDRIAN_MCP_FIRST` thin adapter) → `lib/mcp/stop-gate-handler.cjs:221-229,388` (`_closeOutAmbientTrigger`, called from `closeOutRoom`, called from `handleStopEvent`, called by the `stop_gate_check` MCP tool the thin adapter queries)

**Issue:** `hooks/hooks.json`'s `Stop` array now has eight independent hook-group entries, each invoked on every Stop event regardless of the others. One of them is the pre-existing `run-hook.cmd on-stop` (i.e. `scripts/on-stop`); a *new, separate* entry is `node scripts/ambient-stop.cjs --stop`. `scripts/on-stop`, when `MINDRIAN_MCP_FIRST` is set for the `cli` surface, delegates its entire business close-out — including the ambient trigger — to the MCP daemon via `stop_gate_check` → `handleStopEvent` → `closeOutRoom` → `_closeOutAmbientTrigger`. Both of these independent code paths call `ambientTrigger.evaluateAndMaybeSpawn` for the same room, from the same Stop event dispatch, with only the `seam` label differing (`'stop_hook'` vs `'closeout'`) — a label that plays no role in the claim/lock protocol (`SEAMS` is used only for bookkeeping in `in_flight.seam`, never as a partition key). This is not a rare edge case; it is the designed, always-on behavior of any CLI install with `MINDRIAN_MCP_FIRST` enabled, and it is the direct trigger for CR-01.

**Fix:** Either make `ambient-stop.cjs` a no-op when `MINDRIAN_MCP_FIRST('cli')` is active for this session (mirroring the flag check `scripts/on-stop` itself does at line 69, `isMcpFirst('cli')`), or make `_closeOutAmbientTrigger` skip the evaluator when hooks.json's own hook already ran it this turn — but do not rely on CR-01's claim path to arbitrate between the two once CR-01 is fixed to be a true mutex, since a true mutex would then make one of these two calls simply wasted work (spawning `node` + the whole `ambient-trigger` require graph) on every single CLI Stop event under `MINDRIAN_MCP_FIRST`, not just a rare race.

## Warnings

### WR-01: `evaluateAndClaim`'s delta-state write and `claimAmbientRun`'s ledger write are two separate non-atomic file operations — a crash or kill between them leaves an inconsistent claim

**File:** `lib/core/ambient-trigger.cjs:277-308`

**Issue:** `evaluateAndClaim` first calls `cadenceGuard.claimAmbientRun` (writes the ledger's `in_flight`), then separately calls `cadenceGuard.writeRoomDeltaState` (writes the delta-state side channel with `run_state: 'started'`). If the process is killed between these two writes (plausible: this runs inside a Stop-hook process under a hard `setTimeout` exit in `ambient-stop.cjs:86-90`, and inside the MCP daemon under whatever supervisory timeout the daemon itself imposes), the ledger says a run is in flight but the delta-state side channel never reaches `'started'` — so a spawned child (if one was reached) would see stale/absent delta-state and bail via `tamper_or_stale` (CR-02's third path), leaking the claim for 8 minutes with no code path ever having observed the actual spawn attempt.

**Fix:** Write the delta-state side channel *before* (or as part of) the ledger claim, or accept the current ordering but make the recovery symmetrical: any `tamper_or_stale` outcome should release the claim (see CR-02).

### WR-02: `_findBottlenecksAdapter`'s outcome ternary is a no-op that always evaluates to the same value

**File:** `lib/core/ambient-run.cjs:298`

**Issue:** `return { outcome: findings.length > 0 ? 'no_candidate' : 'no_candidate', findings: findings };` — both branches of the ternary are the literal string `'no_candidate'`. This compiles and runs fine (matching every other adapter's behavior of reporting `'no_candidate'` even when findings exist, since the true per-producer outcome is only ever upgraded to `'filed'`/`'guard_not_cleared'`/`'error'` later for the single card-winning producer), but the ternary itself is dead code that signals an incomplete thought — a future reader will reasonably assume the two branches used to differ and that the difference was lost, which is exactly the kind of thing that hides a real regression on the next edit.

**Fix:** Either delete the ternary (`outcome: 'no_candidate'`) to match the other four adapters' style honestly, or, if the intent really was to distinguish "found candidates but none selected" from "found nothing," introduce that outcome value in `AMBIENT_PRODUCER_OUTCOMES` and use it consistently across all five adapters (currently none of them do).

### WR-03: `runs_window.count` is bumped by every `claimAmbientRun` call regardless of whether the claim ever leads to a completed run

**File:** `scripts/scout-cadence-guard.cjs:672-678`, consumed by the `shouldRunAmbient` throttle check at `scripts/scout-cadence-guard.cjs:620-627`

**Issue:** Because `claimAmbientRun` always increments `runs_window.count` on a successful claim, and because CR-01/CR-02 both describe paths where a claim is taken but the run never actually executes to completion, `AMBIENT_MAX_RUNS_PER_HOUR` (currently `1`, `scripts/scout-cadence-guard.cjs:359`) can be exhausted by claims that never produced a real ambient run — the room then goes a full hour with the honest per-hour cadence unable to fire even once, for reasons invisible to the user (nothing surfaces "your one hourly slot was spent on a phantom claim"). This compounds CR-01/CR-02/CR-04 rather than mitigating them, and is worth fixing independently of the claim-atomicity fix, since a legitimate but interrupted run (process killed mid-composition) hits the same starvation.

**Fix:** Only advance `runs_window.count` from `recordAmbientRun` (i.e. on an actual attempt that reached composition), not from `claimAmbientRun`, or explicitly decrement/refund the count from the release path when a claim is abandoned before composition starts.

### WR-04: No timeout wraps a single producer adapter's `await` inside `runAmbientComposition`'s loop

**File:** `lib/core/ambient-run.cjs:515-550`

**Issue:** The budget check (`(Date.now() - wallStart) >= budgetMs`) is evaluated only at the top of each loop iteration, before starting the next producer. A single `await adapterFn(roomDir, {...})` call that itself hangs (a Theo network stall not bounded by `brain-client.cjs`'s own per-request timeout — e.g. a `rs-engine.py` subprocess spawned by `_findBottlenecksAdapter`'s `rsEngine.runModeInternal`, which is a child process, not a network call, and has no visible timeout in this file) blocks the entire composition indefinitely, defeating the documented 4-minute budget and feeding directly into CR-03's stale-lock scenario.

**Fix:** Wrap each `adapterFn` call in a `Promise.race` against the remaining budget so a single hung producer degrades to `'skipped'`/`'error'` rather than stalling the whole child.

### WR-05: Detached-child survival under `spawnImpl` is unverified on native Windows (Job Object semantics)

**File:** `lib/core/ambient-trigger.cjs:337-348`

**Issue:** `spawnImpl(process.execPath, argv, { detached: true, stdio: 'ignore', windowsHide: true, ... })` followed by `child.unref()` is the correct Node idiom for POSIX (Linux/WSL) detachment, which is what this environment runs under and where the test suite presumably executes. On native Windows, `detached: true` only affects console-group membership; if the parent process (the Stop hook, or the Claude Code host that spawned it) is itself running inside a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (a common default for process-supervision hosts), child processes are still terminated when the job closes unless `CREATE_BREAKAWAY_FROM_JOB` is explicitly requested — which Node's `child_process.spawn` does not set. The review brief specifically calls out "detached-child behavior on Windows/WSL" as a risk; nothing in this file or its tests demonstrates the child actually outlives the parent on native Windows.

**Fix:** Either confirm (with a real Windows test, not WSL) that the ambient child survives Claude Code's own process teardown, or document the known limitation; if it doesn't survive, the whole ambient-trigger feature silently never completes a single run on native Windows installs.

## Info

### IN-01: `debugLog`'s `AMBIENT_DEBUG_ENV` name is duplicated (not shared) across three files

**File:** `lib/core/ambient-trigger.cjs:91`, `scripts/ambient-stop.cjs:30`, `lib/core/ambient-run.cjs:804` (inline literal `'MINDRIAN_AMBIENT_DEBUG'`)

**Issue:** The env var name `MINDRIAN_AMBIENT_DEBUG` is declared as a named constant in two files and used as a bare string literal in the third (`ambient-run.cjs:804`: `process.env.MINDRIAN_AMBIENT_DEBUG === '1'`). A future rename of the constant in one place will silently desync the other two call sites since nothing imports a shared value.

**Fix:** Export `AMBIENT_DEBUG_ENV` from one module (e.g. `ambient-trigger.cjs`) and import it in the other two, or move it to a small shared constants file.

### IN-02: `evaluateRoomDelta`'s `no_room` catch-all masks genuinely different failure classes

**File:** `lib/core/ambient-trigger.cjs:256-258`

**Issue:** The outermost `try/catch` in `evaluateRoomDelta` maps *every* uncaught exception (a bug in `readFactsFn`, a `classifyFn` throwing something the inner try/catch didn't anticipate, a `navigation.closeRoomDbForCaller` throwing outside its own inner guard, etc.) to the decision `'no_room'`, which is semantically "the room directory doesn't exist or isn't valid" — a misleading label for what could be a real internal defect. This makes production debugging harder: an operator grepping `MINDRIAN_AMBIENT_DEBUG=1` output for `no_room` will reasonably assume a room-resolution problem, not a crash three layers deep in the classifier.

**Fix:** Introduce a distinct terminal decision (e.g. `'internal_error'`) for this outermost catch, reserving `'no_room'` for the actual `isValidRoomDir` check that already exists at the top of the function.
