# Phase 355.1 Hooked Audit: The Room Starts the Breakthrough Run

Filed by plan 355.1-08 Task 1 (AMB-05), the mandatory Hooked-model lens for
the first step this phase changes. This is a clean filed deliverable: no
conversation banter, no score, no grade, no count of findings. Read this
file top to bottom before answering `355.1-CHECKPOINT.md`.

The Hooked mapping in one line (355.1-CONTEXT.md `<specifics>`): internal
trigger = the delta; action = one card; variable reward = the stamp tier;
investment = the gate answer that writes the edge the next run reads.

## What changes for the navigator

The room, not the user, starts the breakthrough run. A room delta starts a
background check behind the scenes; if a stamped finding clears the bar,
one card is waiting on the next turn, framed to the room's own problem
type. Nothing is typed, nothing is scheduled, and nothing appears unless a
delta actually happened and a producer found something worth showing.

## Trigger

The internal trigger is a room delta, never a clock and never a command.
Five delta classes count: (a) N or more claim nodes added since the last
run, where N is the disclosed claim floor (5, the measured median claims
per active room-hour); (b) a CONTRADICTS edge surfaced since the last run;
(c) a venture-stage change recorded in STATE.md; (d) a sub-room created;
(e) a new artifact filed (the existing Phase 117 class, kept unchanged).
There is no external trigger: no notification arrives outside the card
itself, and an idea the room has not yet produced is deferred, never
manufactured. "Not on every turn" is held by two mechanics together, the
delta itself (nothing fires on an unchanged room) and the hourly throttle
(at most one ambient run per room per hour), never by gating on a moment
in a workflow.

## Action

One card, once per delta hash, and one gate answer. The finding is filed as
a proposed opportunity through the existing 355-20 writer before it ever
reaches a surface; SENS-13 shows it once, keyed on the opportunity handle,
so the same delta never produces a second card. On class (e), a filed
artifact, the stamped SENS-13 card wins over the older Phase 117
domain-decomposition card (SENS-01) when both would fire for the same
material; the 117 card stands down for that material. On a surface where
the ambient run could not start at all (a spawn failure, a missing
python or scikit-learn dependency), SENS-21 offers the single, honest
fallback: it never carries the finding itself, only the fact that a run
could not start.

[NAVIGATOR RULING 5: the stamped SENS-13 card wins on a class (e) double-card
collision; the Phase 117 SENS-01 card shows only when no stamped finding
exists for that material_id.]

## Variable reward

The reward is the stamp tier, strong or indirect, always rendered with its
canon path, and never a score or a count. An unverified stamp never reaches
the card; it stays in the run ledger and the log only. The honest limit
this audit states plainly: only 14 percent of live artifacts (472 of
3,333) carry the framework: or methodology: frontmatter a stamp needs to
resolve an endpoint, so most real-room ambient findings will stamp
unverified and never reach the card until rooms carry that frontmatter.
The reward is sparse by design, and this audit says so rather than
implying the card arrives often.

## Investment

The navigator's gate answer is the investment. Approve confirms the
proposed opportunity, and that confirmation becomes graph state the next
ambient run reads. Reject writes a REJECTED_BECAUSE edge, which is data
too: the next run's delta reads see that this pairing was already judged
and do not blindly re-surface it. Either answer writes something the next
run reads; neither answer is optional decoration.

## Framing by problem type

Three phrases, proposed for the PWS author's confirmation, live beside the
direction phrases in `lib/core/direction-convention.cjs`:

- `find_the_problem`: "This connection might help name the real problem."
  Shown when the room's problem type resolves undefined or ill-defined.
- `pursue_or_drop`: "This connection might be worth a decision: pursue it
  or drop it." Shown when the room's problem type resolves well-defined.
- `neutral`: "The room changed, and this connection came out of it."
  Shown when the room's problem type resolves wicked or unknown.

Most live rooms land on undefined or unknown today (0 rooms carry a
ratified `goal.rung` or a `ROOM.md` `pws_stage` yet), so the neutral
framing must read well on its own; it is written to stand alone, not as a
fallback that sounds like an error.

## Surfaces

On CLI, the existing PostToolUse fingerprint hook still covers class (e); a
new async Stop-hook entry evaluates classes (a) through (d) and
self-bounds its own time budget, since hook timeouts are seconds, not
milliseconds, and an async hook's timeout is not enforced by the harness.
On Desktop and Cowork, the MCP server's own `stop_gate_check` close-out
(`closeOutRoom`, right after `_closeOutStateMd`) evaluates the same delta
and starts the same detached child; there is no PostToolUse hook on those
surfaces. Stamping on Desktop and Cowork is disclosed here as a refinement
of 355 D-50: the child runs inside the MCP server's own Node process and
calls `brain-client` directly, so it can compute a real stamp on any
machine with a resolvable key, including a keyless machine performing
355's existing one-shot silent registration. Fire-once on hookless
surfaces is recorded at the Stop-time close-out, not inside `decide()`
(which only runs on CLI), so `suggest_next` stays a pure read on every
surface.

[NAVIGATOR RULING 1: stamping on Desktop and Cowork is allowed; the child
computes the stamp, the surface only renders it; a keyless machine's
background child may perform the one-shot silent registration.]

[NAVIGATOR RULING 2: fire-once on hookless surfaces is recorded at the

## Open risks

Three assumptions from research carry real risk and are named here rather
than hidden:

- A1/A2 (Cowork server locality, Desktop child sandboxing): if the MCP
  server on Cowork does not run as a local process able to spawn a
  detached child, or if Desktop sandboxes child processes, the ambient
  child never starts on that surface; the degrade path is the same one
  already built, SENS-21's honest fallback offer.
- A3 (missing python or scikit-learn on a user machine): the HSI,
  whitespace and rs-engine producers degrade to `deps_missing`; the same
  SENS-21 fallback covers this case, and the card may never fire on that
  surface until the dependency is present.

None of these three risks block filing this audit; each already resolves
to the same honest degrade this phase built for the spawn-failure case,
named once here instead of three times.
