# Phase 121.5 -- Terminal Coherence Capstone (the JTBD product, made coherent in the terminal)

**STATUS:** STUB. CONTEXT.md scaffolded 2026-05-10 so `/gsd:plan-phase 121.5`
has a starting point. Plans (121.5-00 through 121.5-NN) not yet written.

**This is the last phase before the v1.13.0 FINAL RELEASE GATE.** It does not
introduce a new product surface. It takes everything v1.13.0 already built --
Larry-by-default, the owned emotion, the tension hook, the auto-explore reward,
the selector library, the context-aware renderer, the statusline broadcast, the
JTBD engine -- and makes the **Claude Code terminal** express it as ONE coherent
product instead of N independently-shipped surfaces. Acknowledge first. Plan
second. Ship third. Then the gate.

## The single design statement

> The MindrianOS terminal IS the product surface. Every glyph, every status
> segment, every cold-start line, every injected directive, every command's
> output shape -- they all encode the same thing: *you are navigating a wicked
> problem with Larry, and here is the job you are doing right now.* If a user
> reads the terminal and can't tell what job they're in, who they're talking to,
> how much runway they have, or what the next move is -- the product is leaking.

This phase closes the leaks.

## Why this phase exists (the accumulated debt)

Two parallel audits + one external reference doc + one foundation review across
this milestone surfaced a consistent picture: the terminal-UI story is
**fragmented across ~18 phases of independent shipping**, each one correct in
isolation, none of them reconciled. The capstone exists to pay that down in one
deliberate pass before v1.13.0 final, rather than carrying it into v1.14.0.

Concrete debt this phase acknowledges and resolves:

1. **SessionStart injection flood.** ~11 SessionStart hook entries, ~9 capable of
   injecting `additionalContext` into Larry's turn-1, ~4 composing competing
   "Larry-voice directives" -- with **no coordinator and no combined budget**.
   This is the direct cause of Larry occasionally opening a session incoherent
   ("lost in the middle"). The repair is a single SessionStart Coordinator with a
   precedence ladder and a hard token budget. (Note: the "10,000 chars per hook"
   figure cited in the parallel research is illustrative, not a confirmed
   documented cap -- VERIFY before citing externally; the architecture is wrong
   regardless of the exact number.)

2. **The ruling system is ~45% enforced.** `skills/ui-system/SKILL.md` is canon,
   but only ~38 of ~85 command files carry `body_shape:` frontmatter. Phase 105's
   `/mos:hmi-status` can flag the other ~47 as "missing body shape" forever. The
   `body_shape:` sweep makes the compliance signal honest for the first time.

3. **`force-for-plugin` output style is unused.** Claude Code supports plugin
   output styles with `force-for-plugin: true` (auto-applies, overrides user
   setting) and `keep-coding-instructions: true` (preserves the coding system
   prompt). This is the strongest UI-enforcement lever Claude Code offers and the
   plugin doesn't use it. Shipping `output-styles/destijl.md` makes the 4-zone
   format system-prompt-enforced, not skill-instruction-suggested. This is the
   multiplier on the `body_shape:` sweep.

4. **SKILL.md has drifted from its own implementation.** SKILL.md §2 documents 5
   Shape-F sub-shapes; Phase 88.2 shipped 7 (added F.0 Mini Gate, F.6 Plan
   Review). SKILL.md does not mention Phase 102's dual De Stijl palette
   (`lib/render/JTBD-PALETTES.md`) even though Phase 102 D-06b explicitly queued
   the amendment. Reconcile SKILL.md to reality.

5. **`lib/render/render-v2.cjs` is built, tested, and almost unused.** Only
   `selector-dispatcher.cjs` and the agentic surfaces route through it; ordinary
   Larry prose still follows SKILL.md by instruction. Decide explicitly: wire it
   into the real prose path, or document it as agent-surface-only and let SKILL.md
   remain the canonical prose contract. Also: Phase 102 never got a VERIFICATION.md
   (`102-VALIDATION.md` still `status: draft`) -- close it.

6. **The statusline is one unreadably-long line.** Split into Row 1 (identity:
   Larry / Brain / context %) + Row 2 (situation: room / section / stage /
   governing thought / JTBD). Multi-line statuslines are a real, documented Claude
   Code feature. (`refreshInterval` is NOT real -- do not add it.)

7. **De Stijl palette + glyph set have no single source of truth.** Hex values
   live in `scripts/banner`, `lib/core/visual-ops.cjs` (`DS_HEX`),
   `templates/destijl-base.css`, `templates/shared.css`,
   `references/vault-kit/snippets/mindrian-destijl.css` -- and the external
   reference doc proposes a *different* (brighter, more literal-Mondrian) palette.
   Pick one. Create `references/visual/palette.json` as canon; every surface
   derives from it; CI asserts agreement.

8. **`🎯` is overloaded three ways** (JTBD broadcast / Phase 109 active-focus
   prefix / problem-definition stage emoji) and "JTBD" the word names two
   unrelated systems (Phase 37 bash nudge templates vs Phase 100 typed engine).
   Either disambiguate the glyphs/terms or document the overload as an explicit
   exception in SKILL.md §3 alongside the emoji carve-out.

9. **Stale version copy in first-touch surfaces (SEED-007).** A v1.12.0 "Three
   ways to do this" greeting was still rendering on a stale Windows install with
   no version-of-record visible. Absorbed here: every first-touch surface stamps
   the running version; a scanner catches stale version-tied copy.

10. **The Phase 88.7 / `/mos:power-demo` ROADMAP lie.** ROADMAP says "1/1 plans
    complete"; only `scripts/power-demo-prompt.md` exists, `commands/power-demo.md`
    does not. And the stray empty directory `.planning/phases/40-hook-expansion/`
    actively corrupts `scripts/context-monitor`'s active-phase mtime scan. Both
    are truth-telling / cleanup items folded into this capstone's housekeeping
    sub-plan.

## Explicitly REJECTED (do not build these)

The external "De Stijl Full UI/UX Implementation Guide" (filed as
`121.5-REFERENCE-destijl-guide-annotated.md`) contains good ideas wrapped around
fabricated or wrong ones. Verified against Claude Code docs:

- **Custom theme JSON files** (`~/.claude/themes/destijl.json`, `/theme
  mindrian-destijl`, hot-reload, configurable token list) -- **NOT REAL.** No
  user-facing custom-theme-file mechanism exists. Do not build against it.
- **Room/Stage state via `export MINDRIAN_ROOM` in a `UserPromptSubmit` hook** --
  **ARCHITECTURALLY WRONG.** Hook subprocess `export` dies with the subprocess.
  Env-var persistence works only in `SessionStart` / `Setup` / `CwdChanged` /
  `FileChanged` hooks, and only by writing to `$CLAUDE_ENV_FILE`. The codebase
  already solved room/stage state correctly with the bridge file
  (`~/.mindrian/bridge/{md5}.json`, Phase 54-02) + `statusline-mos`. The doc's
  approach is a regression. NOTE: `$CLAUDE_ENV_FILE` + `CwdChanged`/`FileChanged`
  IS a real mechanism the codebase may not be using -- worth evaluating, but not
  as a replacement for the bridge file.
- **`SessionStart` hook declared in a SKILL.md frontmatter** -- **NOT REAL** for
  session-level hooks. Skill `hooks:` frontmatter is skill-scoped only;
  session-level hooks must live in `hooks/hooks.json`.
- **`statusLine.refreshInterval`** -- **NOT REAL.** The statusline is event-driven.
- **Silently adopting the doc's brighter palette / new glyph set** -- that is a
  rebrand, not an alignment. It requires an explicit design decision (see scope
  item below), not a copy-paste.

## Explicitly ADOPTED from the reference doc (verified real)

- **`output-styles/destijl.md` with `force-for-plugin: true` + `keep-coding-instructions: true`** -- real, the best idea in the doc, the enforcement multiplier.
- **Two-row statusline** -- real, buildable, fixes readability.
- **The consolidated semantic vocabulary** -- 4-zone anatomy, 12-glyph table with
  one-meaning-each, 5-color semantics (RED=identity/Larry/error, BLUE=Brain/data/
  plan, YELLOW=context/memory/stage/caution, WHITE=default, BLACK=structure),
  anti-patterns list (no emoji, no padding phrases, no decorative dividers,
  no center-align) -- adopt as the SKILL.md v2 reconciliation, mapped onto the
  EXISTING glyph/palette values unless the design decision below says otherwise.
- **`PostCompact` as the correct event** for post-compaction context re-injection
  (vs the current SessionStart-with-`compact`-matcher, which may not be a real
  matcher) -- evaluate migrating the half-wired Phase 95.5 re-injection here.
- **`Notification` hook** for ANSI/desktop alerts on idle + permission -- real
  event; verify the payload var name (`CLAUDE_NOTIFICATION_MESSAGE` is not in the
  documented env-var table) before relying on it. Low priority.

## Scope (provisional, to be refined in 121.5-00)

### IN SCOPE

**Sub-plan A -- SessionStart Coordinator (the unlock).**
- Single script `scripts/sessionstart-coordinator.cjs` (or analogous) that owns
  the SessionStart `additionalContext` composition. Every current injector
  (room-context, sealed-room guardrails, MINTO banner, JTBD nudges, operator
  state, memory-resume-nudge, tension hook, auto-explore preflight,
  post-compact restore, onboarding gate, install-drift / preflight-doctor
  warnings, statusline-fallback-echo) becomes a *contributor* that returns a
  scored fragment; the coordinator ranks by a **precedence ladder** (the ladder
  is a design decision for Jonathan -- see "Open Design Decisions"), enforces a
  **hard combined token budget** (default ~2,000 chars; tune in 121.5-00), and
  emits one consolidated `additionalContext` block.
- Contributors that don't make the budget are dropped or compressed to a
  one-line pointer ("1 unresolved tension pending -- ask Larry") rather than
  injecting their full payload.
- Telemetry: every coordinator decision (which contributors fired, which were
  dropped, total bytes) mirrors to Phase 121's trajectory store.

**Sub-plan B -- `body_shape:` frontmatter sweep + output-style enforcement.**
- One agent pass adds `body_shape:` to the ~47 commands missing it, using the
  fixed command-to-shape mapping table from Phase 21 (extended for any new
  commands).
- Ship `output-styles/destijl.md` with `force-for-plugin: true` +
  `keep-coding-instructions: true` -- the 4-zone format becomes system-prompt
  enforced. `/mos:doctor` self-checks that its OWN output follows the 4-zone
  format (if it doesn't, the output style isn't loaded).
- After this, `/mos:hmi-status` reports a clean baseline for the first time.

**Sub-plan C -- SKILL.md v2 reconciliation.**
- Add Shape F.0 (Mini Decision Gate) and F.6 (Plan Review Round) to SKILL.md §2.
- Fold in Phase 102's dual-palette rule (the D-06b amendment that never landed).
- Document the `🎯` overload + "JTBD" word collision as explicit exceptions, OR
  disambiguate them (design decision -- see below).
- Cross-reference Canon Part 3 (UI Ruling System) + Part 10 (Conversation as
  Product). Result is the single source of truth for the terminal, accurate to
  the shipped code.

**Sub-plan D -- Statusline RE-DESIGN (co-design mandatory, JTBD-driven) + canonical palette token file.**

> **BINDING REQUIREMENT (added 2026-05-14 by Jonathan):** the statusline shape is NOT pre-decided by this CONTEXT.md. The current `🏠 MindrianOS-Plugin ▶ 📂 product-evolution │ 🔍 PRODUCT EVOLUTION │ 🧠 MindrianOS v1.13.0-beta.13 🔄 /mos:update │ 🧬 BRAIN │ Opus 4.7 (1M context) 📊 ████░░░░░░ 47%` line is one accumulated artifact across ~8 phases (Phase 5, 17, 23, 54, 83, 88.1, 94, 106, 109), each adding a segment in isolation. Phase 121.5 must **co-design** the new shape with the navigator (Jonathan) in the discuss-phase pass before any code lands. The framing question is: **for each JTBD, what does the user need to see at a glance, and what is noise?** The layout may VARY by JTBD (different ambient cues for "exploring a problem" vs "validating an idea" vs "building a thesis" vs "comparing ventures" vs "running an audit"). Two-row is a candidate, not a foregone conclusion -- N-row or single-row-with-rotation are on the table if a JTBD demands it.

- **Step 1 (discuss-phase work, BEFORE plans are written):** the discuss-phase pass for 121.5 MUST include a live co-design session with Jonathan on the statusline. Inputs:
  - The 13-JTBD taxonomy from `lib/hmi/jtbd-taxonomy.json` (shipped Phase 100-01)
  - The `serves_jtbd:` frontmatter coverage from Phase 104 (every command declares its job)
  - The operator state machine from Phase 105 (JUST_TALK / EXPLORE_CAPTURE / BUILD_ROOM / METHODOLOGY / DECISION_GATE)
  - Audit of the current line's segments + which JTBD each segment serves (or fails to serve)
  - The accumulated debt from this CONTEXT.md item 6 (the line is unreadable as one row)
- **Step 2 (output of co-design):** a written layout spec (or set of per-JTBD specs) in `121.5-STATUSLINE-DESIGN.md` capturing:
  - Per-JTBD what the user MUST see (the load-bearing segments)
  - Per-JTBD what is noise (drop or hide when not in that JTBD)
  - The transition behavior when the JTBD changes mid-session (does the line morph, or stay fixed for the session?)
  - Surface adaptation: CLI vs Desktop vs Cowork (Desktop has no statusline -- prose echo per the existing pattern)
  - Palette + glyph choices tied to the per-JTBD layout
- **Step 3 (implementation):** `scripts/context-monitor` is refactored per the design. Multi-row + per-JTBD adaptation, NOT a pre-locked two-row split. Preserve the `📊` context-budget glyph + compaction-imminent blink-red at >=80% behavior. Preserve the emoji carve-out (SKILL.md §3) for surfaces where it applies; the design spec confirms or revises this.
- **Step 4 (palette).** Create `references/visual/palette.json` as the canonical De Stijl palette per Open Design Decision 3. `lib/core/visual-ops.cjs` (`DS_HEX`), `scripts/banner`, `templates/destijl-base.css`, `templates/shared.css`, and `references/vault-kit/snippets/mindrian-destijl.css` all derive from it (or a CI check asserts they agree).
- **Step 5 (wrapper migration).** Wire `statusline-mos` (the version-resolving wrapper, Phase 83) as the canonical `settings.json` `statusLine.command` so plugin updates don't strand users on a stale path. `migrate-stale-user-settings.cjs` migrates toward it.

**Why this is co-design and not orchestrator-decided:** the statusline is the user's primary peripheral-vision interface for "what job am I in, who am I talking to, how much runway, what's next" (Canon Part 10). Asking an agent to redesign that surface in isolation reproduces the exact failure mode this phase exists to fix: N independent decisions, none reconciled to the user's actual job. The navigator decides; the agent implements. Per Canon Part 3 (the Decision Gate) + Canon Part 1 (the user is the wicked navigator), the statusline shape is a navigator-owned design call.
