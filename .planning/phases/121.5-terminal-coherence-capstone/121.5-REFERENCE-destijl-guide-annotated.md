## Original doc — 6 "surfaces" — with verdicts

### Surface 1 — Theme tokens (`~/.claude/themes/destijl.json`, `/theme mindrian-destijl`, hot-reload, token list `claude`/`permission`/`remember`/`error`/`warning`/`success`/`planMode`/`bashBorder`/`diffAdded`/`diffRemoved`/`briefLabelClaude`/`rate_limit_fill`)

>>> ANNOTATION — **DROP. NOT REAL.** Claude Code has no user-facing custom-theme-file
>>> mechanism. There is no `/theme <name>` that loads a JSON file, no documented
>>> hot-reload of theme files, and the token list is not documented as configurable.
>>> Themes are a built-in selection (dark/light/daltonized/ansi) plus a plugin-UI
>>> concept — not a `.claude/themes/*.json` user feature. Building against this
>>> would be building against fiction.

### Surface 2 — Two-row statusline HUD + `statusLine` settings (`command`, `padding`, `refreshInterval`)

>>> ANNOTATION — **KEEP THE TWO-ROW IDEA. DROP `refreshInterval`.** Multi-line
>>> statuslines are real and documented (the official example shows a two-line
>>> statusline). `refreshInterval` is NOT real — the statusline is event-driven,
>>> it refreshes when Claude Code wants to. `padding` is not confirmed in the docs.
>>> ACTION in 121.5 sub-plan D: split `scripts/context-monitor` output into Row 1
>>> (identity: Larry / Brain / context %) + Row 2 (situation: room / section /
>>> stage / governing thought / JTBD). This fixes the "one unreadably long line"
>>> problem. Preserve the emoji carve-out (SKILL.md §3) and the `📊` context-budget
>>> glyph with compaction-imminent blink-red at ≥80%.

### Surface 3 — Output style (`.claude/output-styles/destijl.md` / `~/.claude/output-styles/destijl.md` / `plugin/output-styles/destijl.md`), frontmatter `force-for-plugin: true` + `keep-coding-instructions: true`, enforces 4-zone anatomy (HEADER / BODY / STATUS / NEXT)

>>> ANNOTATION — **KEEP. THIS IS THE BEST IDEA IN THE DOC.** All of it is real:
>>> output styles are a documented feature; `keep-coding-instructions` (boolean,
>>> default false — keeps Claude Code's coding system prompt) and `force-for-plugin`
>>> (boolean, default false — plugin output styles only; auto-applies on enable,
>>> overrides the user's `outputStyle`; first enabled plugin with the flag wins)
>>> are both real frontmatter keys. ACTION in 121.5 sub-plan B: ship
>>> `output-styles/destijl.md` with `force-for-plugin: true` + `keep-coding-instructions: true`.
>>> This makes the 4-zone format system-prompt-enforced rather than
>>> skill-instruction-suggested — the multiplier on the `body_shape:` sweep.
>>> `/mos:doctor` should self-check that its own output is 4-zone compliant (if not,
>>> the output style isn't loaded).

### Surface 4 — `ui-system` SKILL.md v2 (full 12-glyph semantic table, 5 body shapes, anti-patterns list, RED/BLUE/YELLOW/WHITE/BLACK color semantics, **`SessionStart` hook embedded in skill frontmatter** printing a load-confirmation signal)

>>> ANNOTATION — **KEEP THE VOCAB CONSOLIDATION. DROP THE FRONTMATTER-SESSIONSTART-HOOK.**
>>> Skills *can* declare a `hooks:` field in SKILL.md frontmatter, but it is
>>> skill-scoped only — a session-level `SessionStart` hook must live in
>>> `hooks/hooks.json`. Do not move the load-confirmation signal into skill
>>> frontmatter where it won't fire. The vocabulary content (12-glyph table with
>>> one-meaning-each, 5 body shapes, anti-patterns: no emoji / no padding phrases /
>>> no decorative dividers / no center-align, 5-color semantics) IS the SKILL.md v2
>>> reconciliation 121.5 sub-plan C needs anyway — but it must be mapped onto the
>>> EXISTING glyph set and palette unless the design decision says otherwise, AND it
>>> must add the things the doc omits: Shape F.0 (Mini Decision Gate) and F.6 (Plan
>>> Review Round) from Phase 88.2, and Phase 102's dual-palette rule.

### Surface 5 — Hooks for room/stage state: `UserPromptSubmit` hooks doing `export MINDRIAN_ROOM=$ROOM` / `export MINDRIAN_STAGE=$STAGE`; `PostCompact` hook re-asserting the skill; `Notification` hook for ANSI/desktop alerts

>>> ANNOTATION — **DROP the env-var approach. KEEP `PostCompact` and `Notification` as candidates.**
>>> `export` inside a `UserPromptSubmit` hook subprocess does nothing beyond that
>>> subprocess — it cannot persist to the statusline or to later hooks. Env-var
>>> persistence works ONLY in `SessionStart` / `Setup` / `CwdChanged` / `FileChanged`
>>> hooks, and ONLY by writing to `$CLAUDE_ENV_FILE` (then visible to all subsequent
>>> Bash commands in the session, not to other hooks/tools). The codebase already
>>> solved room/stage state correctly with the bridge file
>>> (`~/.mindrian/bridge/{md5(workspaceDir)}.json`, Phase 54-02) read by
>>> `statusline-mos` — the doc's approach is a regression. HOWEVER: `$CLAUDE_ENV_FILE`
>>> + `CwdChanged`/`FileChanged` is a real mechanism the codebase may not be using;
>>> 121.5 sub-plan G should evaluate it (not as a bridge-file replacement). `PostCompact`
>>> IS a real, dedicated hook event — and is the *correct* event for post-compaction
>>> context re-injection, vs the current SessionStart-with-`compact`-matcher (the
>>> `compact` matcher on SessionStart is not clearly documented; `source: "resume"`
>>> is the documented SessionStart property). Evaluate migrating the half-wired
>>> Phase 95.5 re-injection to `PostCompact`. `Notification` is a real event; the
>>> specific env var `CLAUDE_NOTIFICATION_MESSAGE` is NOT in the documented env-var
>>> table — verify the payload before relying on it. Low priority.

### Surface 6 — ANSI glyph palette for hook scripts (foreground-only ANSI 256-color codes; note: Powerline-style background-color segments do NOT render reliably in the statusline script)

>>> ANNOTATION — **KEEP, with a caveat on the palette VALUES.** Foreground-only ANSI
>>> in hook output is fine and renders in all modern terminals. The "Powerline
>>> background segments are unreliable" note matches what Phase 106 found
>>> independently — it's correct. BUT the doc's specific hex values (RED `#E63329`,
>>> BLUE `#0057A8`, YELLOW `#E6B800`) DIFFER from the codebase's current De Stijl
>>> palette (`#A63D2F / #1E3A6E / #C8A43C / #2A6B5E` in `scripts/banner` and
>>> `lib/core/visual-ops.cjs` `DS_HEX`). Adopting the doc's palette is a REBRAND, not
>>> an alignment — it's an explicit design decision (121.5 Open Design Decision #3),
>>> not a copy-paste. The doc's palette is brighter / closer to literal Mondrian
>>> primaries; the codebase's is muted / earthy. Lean: keep the existing values
>>> (more distinctive). Either way, 121.5 sub-plan D creates
>>> `references/visual/palette.json` as the single source of truth so this is never
>>> a multi-file manual edit again.

### Doc's "Implementation Checklist" (deploy order: theme.json → statusline.sh → output-styles/destijl.md → skills/ui-system/SKILL.md → hook snippets)

>>> ANNOTATION — Step 1 (theme.json) is fiction, skip it. Steps 2–5 map roughly onto

## What this doc got RIGHT that the codebase should internalize regardless

1. The terminal is a *communication protocol*, not decoration — every glyph/color/segment encodes identity + state + intention. (This is already Canon Part 3 spirit; the doc states it cleanly.)
2. `force-for-plugin` output styles exist and the plugin should use one. (New — genuinely actionable.)
3. The 5-color semantic mapping (RED=identity/Larry/error, BLUE=Brain/data/plan, YELLOW=context/memory/stage/caution, WHITE=default, BLACK=structure) is clean and worth adopting as the canonical semantic table in SKILL.md v2.
4. `PostCompact` is the right event for post-compaction re-injection.
5. Powerline background segments are unreliable in statuslines — stick to foreground ANSI.

## What this doc got WRONG that 121.5 must NOT propagate

1. Custom theme JSON files (fiction).
2. Env-var room/stage state via `UserPromptSubmit` hooks (regression — the bridge file already exists for exactly this reason).
3. `SessionStart` hooks in skill frontmatter (not real for session-level hooks).
4. `statusLine.refreshInterval` (not real).
5. Silently swapping the palette / glyph set (that's a rebrand decision, not an implementation detail).
