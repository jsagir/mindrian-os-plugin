## Measured shape of a missing tool

- PROVEN: a call to a tool that does not exist in the session is not a deny and not an isError result. The engine throws. Measured with a throwaway mod in a scratch HOME and scratch config folder (login by symlink only). Evidence: 380-16-evidence/probe-missing-tool.txt.
- The thrown text is: `mos-probe: $.tool.call: no tool named "mcp__plugin_nonexistent__brain_ask" in this session`.
- Effect on the plan. The plan guessed a returned isError. The measured shape is a throw. So the G1 root cause is in the catch path of askTheo, not in the isError path. Both paths set the excerpt as sent. See the SUMMARY for file and line.
- Decision: outcomeOf maps a throw whose message matches `no tool named "..." in this session` to unavailable (the call never left the machine, the text proves it). Any other throw is failed (the call may have left). This differs from the plan sentence that says "treated as failed". Root cause for the change: the message proves the call was never dispatched, so "may have been received" would be a false statement.
- ASSUMED: a returned isError result with the text `No such tool available` is the same case. It was not measured. It stays in the table of outcomeOf as a second pattern.
- Test harness fact (PROVEN, red run): a `tool:` handler in tests/support.ts cannot throw from `$.tool.call`. A throwing hook is skipped, and the engine reports "hook was skipped". So the thrown paths (S2, S3, S4) run through askTheo with a fake engine. The pane tests (S2p, S3p, S4p) use the returned shapes and reach the same render.

## G4: why the Job line stays "no guess yet"

The question: after two real prompts the Job line said "no guess yet". Why?

The two prompts of the real screen (PROVEN, from the shots): panel stems of the form `About the "<folder>" section of the room: ` plus the typed words `explain feymen`. They hold no cue of the taxonomy.

The threshold (PROVEN, read now):
- hooks/job.ts line 159: `return bestCount >= 2 && bestCount > second ? best : null`. A job is guessed only when it has at least 2 distinct cues in the prompts and a strict lead over every other job.
- hooks/register.tsx line 309 (jobNow): `guessJob(recentUser, JOBS)`. Input is recentUser only.
- The input (PROVEN): recentUser is filled at prompt.submit, hooks/register.tsx line 834, last 6 prompts, never a command, never injected text.
- The cue list is lib/hmi/jtbd-taxonomy.json, copied to hooks/jobs.ts. Example: decide-pursue has "should we pursue", "pivot", "double down".

The plugin's own classifier (PROVEN, read): lib/hmi/jtbd-classifier.cjs lines 193 to 195 uses a weighted score with threshold 0.6 (0.8 in JUST_TALK). It is a different method. The panel rule is the simpler "2 distinct cues" of plan 14 J3.

Scratch result (PROVEN): guessJob on the two prompts returns null. Pinned by tests/job-guess.test.ts J1 to J7 (J1 to J6 pass before and after the fix; J7 pins the new hint).

Verdict: BY DESIGN. D-09 asks for a guess from local data, labelled, never forced. Plan 14 J3 chose the 2-cue rule. It is not a defect against D-09, so the rule has no code change.

One open point (PROVEN by reading hooks/job.ts lines 19 and 20): the room state (stage, open section) shapes only the sentence, not the prediction. D-09 allows this and does not require more.

An observation (UNVERIFIED, not reproduced): a click stem carries the folder name into the prompt text. A folder named like a cue pair (for example "pivot" and "double down") could produce a guess from a word that the panel wrote. Not fixed. Recorded.
