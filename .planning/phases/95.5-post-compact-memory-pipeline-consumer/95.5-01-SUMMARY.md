## macOS date fallback chain

```bash
written_at=$(date -u +%Y-%m-%dT%H:%M:%S.%3NZ 2>/dev/null) || \
  written_at=$(date -u +%Y-%m-%dT%H:%M:%SZ 2>/dev/null) || \
  written_at="unknown"
```

- GNU date (Linux, modern shells): `%3N` works, emits millisecond ISO (e.g. `2026-05-06T21:57:41.325Z`).
- BSD date (macOS): `%3N` rejected; falls to second-precision (`2026-05-06T21:57:41Z`).
- Broken date binary: literal string `unknown`.

The consumer (Plan 95.5-02) compares `written_at` to `Date.now()` for staleness; second precision is sufficient for the 600-second staleness window. Millisecond precision is opportunistic but not required.

## Decisions Made

- **D-04 stamp uses 4 fields, not 3.** CONTEXT.md D-04 spec listed `source_room_path` + `source_room_slug` + `written_at`. Plan added `schema_version: 1` as the fourth field. Rationale: future-proofs against schema bumps (e.g. v2 might add `source_machine_id` for cross-machine sync deferred to v1.14.0 / Phase 110); consumer can guard on `schema_version === 1` and reject (or warn-and-still-parse) on mismatch.
- **macOS fallback: literal `unknown` as third tier.** If both date invocations fail (extremely unlikely on any sane shell), the stamp still has all 4 fields with `written_at: unknown`; the consumer treats `unknown` as "always stale" which is correct conservative behavior.
- **Brace-group + printf chain for atomicity.** Used `{ printf ...; printf ...; printf '%s' "$body" } > "$tmp"` instead of multi-step `echo -e >> "$tmp"`. Single redirection; entire content lands before the `mv -f`; no race windows even if a signal interrupts mid-write.
