## Security Domain (from RESEARCH.md, ASVS L1)

`security_enforcement` is not set in `.planning/config.json`, so it is treated
as enabled by default; each PLAN.md's `<threat_model>` block should carry
this forward, with special weight on the D-04 mutation-avoidance finding
(the actual security-relevant discovery this phase made):

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | no | Local CLI diagnostic; no auth surface |
| V3 Session Management | no | No sessions touched |
| V4 Access Control | yes (weakly) | Reads whatever `~/MindrianRooms/.rooms/registry.json` names; path resolution reuses `resolveRoomPath`, joins against `roomsHome`, never a caller-supplied path |
| V5 Input Validation | yes | Only inputs are registry-derived paths; both count queries are fixed literals, zero parameters, zero SQL-injection surface by construction |
| V6 Cryptography | no | None used |
| V10 Malicious Code | yes | Zero new dependencies |
| V12 File Handling | yes | Read-only file access (D-04's whole point), `existsSync`/`fileMustExist` guards, per-room try/catch |
| V14 Configuration | yes | `MINDRIAN_ROOMS_HOME` is an existing, already-trusted override |

The dominant threat this phase's own research surfaced was NOT in the ASVS
checklist above — it was the D-04 finding itself (a "read-only" diagnostic
silently mutating 30 live rooms via the wrong door). That finding and its
resolution (the new read-only sibling door) IS this phase's threat model;
each plan's `<threat_model>` block must reference it explicitly, not just
the generic ASVS table.
