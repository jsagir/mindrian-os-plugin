**Gathered:** 2026-07-25

<domain>
## Phase Boundary

Add a density read (node count, edge count per `room.db`) so SEED-074's own gate
condition -- "measured room.db density crossing a real threshold" -- becomes
something the system reports on its own, instead of something a human has to
remember to go check by hand (as SEED-074's own author had to do on 2026-07-25,

<decisions>
## Implementation Decisions

### Surface placement (the one gray area discussed)
- **D-01:** Both surfaces ship, per navigator choice over three options (doctor-only /
  room_state-only / both). Doctor module is the primary deliverable (system-wide
  census, closes SEED-074's gate); room_state gets a lightweight single-room
  addition for in-conversation visibility.
- **D-02:** Doctor side reuses Phase 217's per-class module registry pattern exactly:
  one new `lib/core/doctor/room-graph-density-module.cjs` + one new entry in
  `data/doctor-modules.json` ("new organ module = ONE entry, no engine code
  change"). `cadence: 'always'` (per-invocation diagnostic, not a one-time heal).
  `fix_supported: false` (a density count is check-only; there is nothing to
  "fix" about a measurement).
- **D-03:** Room iteration reuses `lib/core/doctor/cascade-rooms-module.cjs`'s
  pattern verbatim: `readRegistry()` + `resolveRoomPath()` from
  `lib/core/doctor/shared.cjs`, one try/catch per room so a single bad room
  soft-fails without aborting the sweep (same T-217-01 self-DoS guard cascade-rooms
  already uses).
- **D-04 (SUPERSEDES the original D-04 -- research invalidated it, navigator
  re-confirmed 2026-07-25):** `openRoomDbForCaller` is NOT read-only -- it
  delegates to `openRoomDb`, which `mkdirSync`s, runs 13 `CREATE TABLE IF NOT
  EXISTS`, and runs 5 migrations on every open. Research reproduced this on a
  real room copy (before/after schema diff added a table + a column). Using it
  for a system-wide census would silently migrate all 30 mid-migration-chain
  rooms (of 38 live registered rooms) the first time this check runs. Decision
  (navigator-confirmed over two explicit options with stated implications):
  add a NEW, genuinely read-only sibling door -- `better-sqlite3`'s
  `{ readonly: true, fileMustExist: true }` open mode, living inside
  `lib/core/navigation.cjs`'s module (a second MODE of entry through the same
  Part-9 chokepoint, not a second chokepoint; zero existing callers touched).
  This is a mechanical guarantee (the OS file handle rejects writes before any
  migration code runs), not a code-level promise. `fileMustExist: true` means
  a room with no `room.db` yet throws immediately on open -- exactly the
  schema-less case, handled without ever touching disk. See
  `232.1-RESEARCH.md` for the full before/after diff evidence and the
  rejected "reuse + declare loudly" alternative.
- **D-05 (UPDATED per research's re-measurement):** `room.db` absent or
  schema-less still reports `node_count: 0, edge_count: 0`, never throws --
  that part of the original decision holds. BUT: SEED-074's own "both sampled
  rooms came back 0 tables" is NOT today's reality. Research's read-only
  census of all 45 registered rooms (2026-07-25) found 38 have a `room.db`,
  zero have 0 tables (21,304 nodes / 8,663 edges total, max 4,146 in one
  room). This phase's own output/docs must NOT restate "0 tables" as a
  present-tense fact -- report whatever the live census actually finds. This
  does NOT license a "dense"/"at risk" claim either way (D-06 still holds;
  4,146 nodes is still trivial for the algorithms SEED-074 gates) -- it only
  means the specific "0 tables" number from the seed's original measurement
  is stale and must not be repeated as current.
- **D-08 (Claude's Discretion resolved by research, promoted to a locked
  decision):** the doctor module rides the always-on module registry
  (`data/doctor-modules.json`, `cadence: 'always'`, `flag: null`), NOT the
  existing `--acceptance` 7-point checklist. Research traced `scripts/doctor.cjs`'s
  dispatch: `--acceptance` calls `runAcceptance()` and `process.exit()`s before
  the accumulative engine (module registry) ever runs -- they are two
  definitively separate, non-merging output streams. `commands/doctor.md`'s
  documented flag surface confirms the module registry is the general-purpose
  always-on diagnostic surface `--acceptance` is not.
- **D-06:** No risk or density-adjective framing in any output copy -- report raw
  counts only. This is SEED-074's own "Hard guard on any downstream claim"
  section, binding on this phase's own output, not just future artifacts: never
  imply room graphs are "dense" or "at risk" today.
- **D-07 (UPDATED):** `room_state` side folds ONE additional line (this bound
  room's own node/edge count) into its existing status assembly point (see
  `232.1-RESEARCH.md` for the exact file/function located at research time).
  Same D-04 read-only sibling door as the doctor module -- not the mutating
  `openRoomDbForCaller` -- for the same reason: a status line should not be
  able to trigger a schema migration as a side effect.

### Claude's Discretion
- Exact node/edge counting query shape -- resolved by research:
  `SELECT count(*) FROM nodes` / `SELECT count(*) FROM edges` (one generic
  `nodes` table + one generic `edges` table per `lib/core/lazygraph-ops.cjs`'s
  `initSchema` -- there are no per-type node tables to enumerate).
- Exact `data/doctor-modules.json` `id` slug and new module filename.
- Whether `--json` output carries a per-room breakdown (room names only,
  never paths) alongside the aggregate total -- research recommends yes, so
  the census is independently checkable per-room, not just as one opaque
  number; not escalated to the navigator as it carries no safety/mutation
  risk either way.

## Existing Code Insights

### Reusable Assets
- `lib/core/doctor/shared.cjs` `readRegistry()` -- returns every registered
  room from `~/MindrianRooms/.rooms/registry.json` (`MINDRIAN_ROOMS_HOME`
  override honored). Directly reusable for the system-wide census.
- `lib/core/doctor/cascade-rooms-module.cjs` `resolveRoomPath(roomsHome, info)`
  -- room path resolution (absolute `path` used verbatim, else joined against
  `roomsHome`); directly reusable.
- `lib/core/navigation.cjs` -- NOT `openRoomDbForCaller`/`closeRoomDbForCaller`
  (that door mutates on open, see D-04); this phase adds and uses a NEW
  read-only sibling door in the same module instead.

### Established Patterns
- Doctor per-class module contract: `check(ctx) -> { status, detail, ... }`,
  optional `fix(ctx)`. `fix_supported` is an explicit boolean (D-03 from Phase
  217) -- this phase's module sets it `false`.
- Per-room try/catch so one bad/corrupt room soft-fails without aborting the
  whole sweep (cascade-rooms-module.cjs's T-217-01 self-DoS guard) -- apply the
  same shape here, since a density read touches every registered room's
  `room.db`.
- `data/doctor-modules.json` is hand-maintained, one entry per module; "new
  organ module = ONE entry here, no engine code change" is the explicit design
  intent (see the file's own `$schema_note`).

### Integration Points

  TBD at plan time), registered as one new entry in `data/doctor-modules.json`.
- `room_state` side: the existing status assembly point (exact file/function
  located and cited in `232.1-RESEARCH.md`) gains one additional read via the
  D-04 read-only sibling door, for the single currently-bound room only.
