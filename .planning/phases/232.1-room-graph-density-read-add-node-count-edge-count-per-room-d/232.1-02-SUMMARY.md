## Decisions Made

- **The count idiom is duplicated on purpose.** `lib/core/doctor/room-graph-density-module.cjs` has a `countTable` helper doing exactly this, but `lib/mcp/` importing from `lib/core/doctor/` would invert the layering. Two lines of duplication is the correct cost, and the header says so explicitly so a future reader does not "DRY it up" into a dependency.
- **The rendered copy avoids the word "density" entirely**, matching the doctor module's own `detail`. The registry `id`, the phase name, and this plan's own title use the word because they are stable identifiers; the thing a user reads is `Local graph: N nodes, M edges.`
- **The empty case is stated, not silent.** A bound room with no `room.db` renders `Local graph: 0 nodes, 0 edges (no room.db yet).` rather than an omitted line, so a cold room reads as a normal state (D-05) rather than as a missing feature. Any thrown error still degrades to the empty string, so a broken read can never break a `room_state` response.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Scenario 6 as specified did not bite, so it was not actually a regression pin**

- **Found during:** Task 2
- **Issue:** The plan specified scenario 6 reuse "scenario 1's seeded room" for the byte-identical non-mutation assertion. That room is created through `room-db.cjs::openRoomDb`, so it is already at head schema. A second open through the MUTATING door then runs the same 13 idempotent `CREATE TABLE IF NOT EXISTS` statements and 5 migrations against a db that already satisfies all of them, changing nothing observable. Verified empirically: with `roomDensityLine` deliberately swapped to `openRoomDbForCaller`, scenario 6 still reported `ok`. The scenario was green in both the correct and the incorrect world, which is the definition of a test that does not pin anything. Note this is a property of the FIXTURE, not of the plan's intent: the D-04 mutation evidence in RESEARCH was gathered on a copy of a REAL room, which is mid-migration-chain (232.1-RESEARCH.md: 30 of 38 live rooms are).
- **Fix:** Added `seedMidMigrationRoom(roomDir, n, e)`, which writes `room.db` directly with only the pre-migration `nodes` (the bare id/type/properties triple, per `lazygraph-ops.cjs::initSchema`) and `edges` tables. Scenario 6 now runs against that room. A mutating open against it adds the other 11 tables plus the phase-109 / phase-160 node columns, so `sqlite_master` visibly changes. Also added an in-scenario precondition assert (`before.length < 13`) so that if a future change accidentally makes the fixture head-schema, the scenario fails loudly instead of silently disarming itself.
- **Files modified:** `tests/test-232.1-room-state-density.cjs`
- **Verification:** With the fix in place, swapping `roomDensityLine` to `openRoomDbForCaller` now FAILS scenario 6; restored, all 6 pass. Scenario 3 was mutation-tested the same way (swap `activeRoomDir` for `roomDir` -> fails; restored -> passes).
- **Committed in:** `c4ddea9e` (Task 2 commit)

**2. [Rule 3 - Blocking] The plan's inline Task 1 smoke command used a non-insertable `nodes` INSERT**

- **Found during:** Task 1 verification
- **Issue:** The plan's `<automated>` verify command seeds with `INSERT INTO nodes (id,type,properties)`. That is the same schema drift Plan 232.1-01 hit and documented: the fully migrated `nodes` table carries NOT NULL `source_path` / `created_by` / `created_at` / `last_seen_at` plus a CHECK on `created_by`, so the bare triple fails.
- **Fix:** Ran the smoke with the seven-column INSERT (`created_by = 'system'`), the exact form Plan 232.1-01 settled on. Also extended the smoke to assert the cold-room `(no room.db yet)` form. Verification command only, zero shipped-code impact.
- **Files modified:** none (verification command)
- **Verification:** Smoke prints `OK`; mutating-door grep count unchanged at 1.
- **Committed in:** n/a (no file change)

## Issues Encountered

- The interesting finding of this plan is deviation 1, and it generalizes beyond Phase 232.1: **a non-mutation regression can only pin anything if its fixture is in a state the mutation would visibly change.** A fixture built through the mutating door is, by construction, already in the post-mutation state. Plan 232.1-01's own scenario 2 has the same fixture shape; it was not touched here (out of scope, and its door-level coverage is real), but it is worth knowing that the strong evidence for D-04 came from a real mid-migration room, not from that scenario.
- `resolveWriteTargetDir` falls back to the passed boot-time `roomDir` on a registry miss, which is what lets scenarios 1, 2, 4 and 6 run without a scratch registry at all. That behavior is already pinned by `tests/test-tool-router-active-room-misroute.cjs`, so this suite consumes it rather than re-asserting it.
