## Warnings

### WR-01: `resolveRoomPath` silently drops registry entries that use `abs_path` (or no path at all), understating the census

**File:** `lib/core/doctor/room-graph-density-module.cjs:97-101` (definition), `:139-140` (call site)
**Issue:** `resolveRoomPath` reads only `info.path`; when it is falsy it returns `null`, and `check()` responds with a bare `continue` -- the room silently disappears from `rooms[]` with no `unreadable` marker and is not counted in `totals.rooms`. That differs from the corrupt-path case (`{ path: 5 }`), which correctly surfaces via `unreadable: true` (test 6). But `scripts/room-registry`'s own canonical resolution precedence checks `abs_path` FIRST, falling back to `path`, falling back to a slug-derived default -- `abs_path`-only is a legitimate, first-class registry shape (used elsewhere in this exact phase's own room-state test fixture: `tests/test-232.1-room-state-density.cjs:239` writes `{ slug: 'room-b', abs_path: roomB }` with no `path` key at all). Feed that same shape through the registry `resolveRoomPath` reads and the room vanishes from the doctor census entirely, contradicting the module's own docstring ("for every registered room, counts the rows") and SEED-074's "self-reported" framing -- a room that silently disappears is not self-reported, it is mis-reported. (On the current dev box's real registry all 45 entries use `path`, so this has not bitten in practice yet, and the gap is copied verbatim from the pre-existing, accepted `cascade-rooms-module.cjs`, so it is not a defect unique to this phase -- but this module is a fresh census surface where completeness is the entire point.)
**Fix:**
```javascript
function resolveRoomPath(roomsHome, info) {
  if (!info) return null;
  if (typeof info.abs_path === 'string' && info.abs_path.length > 0) return info.abs_path;
  const relPath = info.path;
  if (!relPath) return null;
  return path.isAbsolute(relPath) ? relPath : path.join(roomsHome, relPath);
}
```
and in `check()`, replace the silent `continue` for a null `roomPath` with an explicit unreadable entry so `totals.rooms` always accounts for every registry key:
```javascript
if (!roomPath) {
  out.push({ room: name, node_count: 0, edge_count: 0, has_db: false, unreadable: true });
  continue;
}
```

### WR-02: `_fileUriPath` has no Windows path handling; a Windows room silently misreports as "no room.db yet"

**File:** `lib/core/navigation/spine-events.cjs:102-104` (escaper), `:413-425` (door)
**Issue:** `_fileUriPath` escapes only `%`, `?`, `#`. On Windows, `path.join` (used by `_roomDbPath`) produces backslash paths like `C:\Users\...\.mindrian\room.db`; `'file:' + _fileUriPath(dbPath) + '?mode=ro'` yields `file:C:\Users\...\room.db?mode=ro`, which is not a form SQLite's URI-filename parser normalizes the same way a forward-slash / triple-slash form would (no drive-letter or separator handling is performed anywhere in this idiom). If the `DatabaseSync` constructor throws or misresolves on that string, `openRoomDbReadOnlyForCaller`'s catch returns `null`, and both consumers (`room-graph-density-module.cjs` and `roomDensityLine`) treat a `null` handle identically to "genuinely no room.db yet" -- so a Windows install with real, populated rooms would silently report 0/0 across the board rather than erroring loudly. This is an inherited idiom (`session-presence.cjs:291`, `coverage-rollup.cjs:93`, and the original `_fileUriPath` in `graph-derivation.cjs:335-337` all share the same gap; grepped the repo for `pathToFileURL` and found zero uses anywhere), so it predates this phase -- but 232.1 duplicates the same unescaped-backslash pattern into a fourth call site without addressing it, and neither `tests/test-232.1-room-graph-density.cjs` nor `tests/test-232.1-room-state-density.cjs` exercises a Windows-shaped path (both only cover `#`, `%`, `?` on POSIX). Given this repo explicitly maintains Windows-specific regression fences elsewhere (`tests/test-room-registry-windows-path.cjs`, `tests/test-self-update-platform.cjs`), this gap is a plausible real-world miss, not a hypothetical.
**Fix:** use Node's own `url.pathToFileURL`, which already handles backslash-to-forward-slash conversion and drive-letter normalization, instead of hand-rolled concatenation:
```javascript
const { pathToFileURL } = require('node:url');
function _fileUriPath(p) {
  // pathToFileURL handles POSIX and win32 path forms (drive letters,
  // backslash separators) correctly; still escape ? and # since SQLite's
  // URI parser treats them as query/fragment delimiters within a href.
  return pathToFileURL(String(p)).href;
}
```
(adjust the call site since `.href` already carries the `file://` prefix -- drop the hand-written `'file:' + ... ` concatenation and append `?mode=ro` to the href directly).

### WR-03: read-only door opens with no busy-timeout; a lock collision can silently read as a zero count instead of retrying

**File:** `lib/core/navigation/spine-events.cjs:420-421`; `lib/core/doctor/room-graph-density-module.cjs:109-115`; `lib/mcp/tool-router.cjs:602-603`
**Issue:** `room-db.cjs::openRoomDb` (the mutating door) explicitly passes `{ timeout: 5000 }` to `DatabaseSync`, with a comment explaining this was added (Phase 218-02, D-05) specifically because an un-timed-out connection fails a contended operation immediately with `SQLITE_BUSY`. `openRoomDbReadOnlyForCaller` passes no options at all, so the read-only connection has the default (no) busy-wait. Both consumers swallow a thrown query into a value of `0`: `countTable`'s catch-all (`room-graph-density-module.cjs:109-115`) and `roomDensityLine`'s per-query try/catch (`tool-router.cjs:602-603`) cannot distinguish "genuinely empty table" from "query threw because another connection held the lock." WAL mode (which every real room.db runs under) makes true `SQLITE_BUSY` contention rare for a reader, but not impossible (e.g., mid-checkpoint), and neither 232.1 test suite exercises a concurrent-write-during-read scenario, so this path is unverified either way.
**Fix:** pass the same timeout the write door uses (or a shorter read-appropriate bound) so a rare lock collision degrades to a bounded wait instead of a silent, indistinguishable-from-empty zero:
```javascript
return new DatabaseSync('file:' + _fileUriPath(dbPath) + '?mode=ro', { timeout: 2000 });
```

### IN-01: count-query logic is duplicated between the doctor module and `roomDensityLine`

**File:** `lib/core/doctor/room-graph-density-module.cjs:109-115` vs `lib/mcp/tool-router.cjs:594-610`
**Issue:** `countTable` (SELECT count(*) over `nodes`/`edges`, catch-to-0) and the two inline count queries inside `roomDensityLine` are functionally identical, hand-duplicated. The duplication is explicitly justified in both files' comments as a deliberate Canon Part 8/9 layering cost (`lib/mcp/` must not depend on `lib/core/doctor/`), which is a reasonable call given the constraint -- flagging only because a future schema change to the counting semantics (e.g., excluding soft-deleted rows) would need to land in both places by hand, with nothing to catch a divergence.
**Fix:** none required given the documented architectural constraint; if the counting logic ever needs to change, consider lifting the two-line count helper into a neutral `lib/core/` module both sides can import without crossing the doctor boundary.
