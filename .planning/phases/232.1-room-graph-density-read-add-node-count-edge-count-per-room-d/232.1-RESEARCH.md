# Phase 232.1: Room-Graph Density Read - Research

**Researched:** 2026-07-25
**Domain:** MindrianOS internal architecture (doctor module registry + `room.db` substrate chokepoint + MCP room_state router)
**Confidence:** HIGH (every claim below is read directly out of this repo's source or measured on this machine; zero external-library research was needed)

## Summary

This phase adds one read-only count of `nodes` and `edges` rows per `room.db`, exposed on two surfaces (a new `/mos:doctor` registry module for the system-wide census, and one line folded into the `room_state` MCP tool for the currently bound room). Every question CONTEXT.md left open at discuss-time is now answered by reading the code, and three findings materially change what the plan must do.

**Finding 1 (the schema is trivially simple).** There is no per-type node table and no per-type edge table. `room.db` carries exactly one generic `nodes` table and one generic `edges` table, both created by `lib/core/lazygraph-ops.cjs::initSchema`. The correct query is literally `SELECT count(*) FROM nodes` and `SELECT count(*) FROM edges`. The typed-claim / typed-opportunity / typed-frame modules under `lib/core/navigation/` are *writers into those two tables*, not separate tables.

**Finding 2 (the sanctioned door mutates, and this is the phase's central design decision).** `openRoomDbForCaller` delegates to `lib/core/room-db.cjs::openRoomDb`, which is not a read-only open. It `mkdirSync`s `.mindrian/`, runs `initSchema` + `initMemorySchema` (13 `CREATE TABLE IF NOT EXISTS`), and then runs five idempotent migrations. I verified this empirically on a copy of a real room: opening it added a `ranker_weights` table and an `edges.review_status` column. So a "read-only diagnostic" sweeping all 45 registered rooms through this door would silently migrate every one of them. Every other doctor `check()` in this repo declares itself non-mutating (`cascade-rooms-module.cjs`: "read-only sentinel scan. NEVER mutates"). The plan must consciously resolve this, not stumble into it.

**Finding 3 (SEED-074's own measurement does not survive re-measurement).** SEED-074 records `rethinking-mindrianos -> 0 tables` and `iris2026 -> 0 tables`. A read-only census taken today (2026-07-25) across all 45 registered rooms found those two rooms carry 15 tables each, with 3,714 and 4,146 node rows respectively, and found **zero** rooms with 0 tables anywhere. This does **not** license a "dense" or "at risk" claim (SEED-074's hard guard still holds and is still correct), but it does mean the phase's own framing text ("both sampled rooms came back 0 tables") must not be repeated as present-tense fact in shipped code, docs, or output copy.

**Primary recommendation:** Ship the doctor module as `id: "room-graph-density"`, `cadence: "always"`, `flag: null`, `fix_supported: false`, `runner: "lib/core/doctor/room-graph-density-module.cjs"`, returning status `ok` (never `warn`) with raw counts in `detail`; resolve the mutation question explicitly (recommended: add a read-only sibling door in `lib/core/navigation/spine-events.cjs`, which keeps Canon Part 9 intact and keeps `check()` honestly non-mutating); and fold the single-room line into `lib/mcp/tool-router.cjs`'s `room_state` `status` / `get-state` branches, which are the only Node-level seams that exist.

**When to use:** Always, for any new doctor check. This is the Phase 217 architecture and `commands/doctor.md:173-180` documents it as the extension contract.

**Registry entry shape** (append to `data/doctor-modules.json` `modules[]`):

**Runner skeleton** (the exact shape both reference modules use):

```javascript
// Source: pattern composited from lib/core/doctor/cascade-rooms-module.cjs
//         (registry iteration) and lib/core/doctor/umbilical-module.cjs
//         (per-room room.db handle + close-in-finally).
'use strict';

const fs = require('node:fs');
const path = require('node:path');

const { readRegistry } = require('./shared.cjs');
const {
  openRoomDbForCaller,
  closeRoomDbForCaller,
} = require('../navigation/spine-events.cjs');

// Re-declared locally: cascade-rooms-module.cjs does NOT export resolveRoomPath.
function resolveRoomPath(roomsHome, info) {
  const relPath = info && info.path;
  if (!relPath) return null;
  return path.isAbsolute(relPath) ? relPath : path.join(roomsHome, relPath);
}

function check(_ctx) {
  const reg = readRegistry();
  if (!reg) {
    return {
      status: 'skip',
      detail: 'no registry at ~/MindrianRooms/.rooms/registry.json (or MINDRIAN_ROOMS_HOME)',
      rooms: [],
      totals: { rooms: 0, nodes: 0, edges: 0 },
    };
  }
  const roomsHome = reg.roomsHome;
  const rooms = (reg.registry && reg.registry.rooms) || {};
  const out = [];
  let totalNodes = 0;
  let totalEdges = 0;

  for (const name of Object.keys(rooms)) {
    const roomPath = resolveRoomPath(roomsHome, rooms[name]);
    if (!roomPath) continue;
    let db = null;
    try {
      db = openRoomDbForCaller(roomPath);        // null when room.db is absent
      if (!db) {
        out.push({ room: name, node_count: 0, edge_count: 0, has_db: false });
        continue;
      }
      const n = db.prepare('SELECT count(*) AS c FROM nodes').get().c;
      const e = db.prepare('SELECT count(*) AS c FROM edges').get().c;
      totalNodes += n;
      totalEdges += e;
      out.push({ room: name, node_count: n, edge_count: e, has_db: true });
    } catch (_e) {
      // T-217-01 self-DoS guard: one bad room never aborts the sweep.
      out.push({ room: name, node_count: 0, edge_count: 0, has_db: false, unreadable: true });
    } finally {
      closeRoomDbForCaller(db);
    }
  }

  return {
    status: 'ok',   // NEVER 'warn' -- see Pitfall 3
    detail: out.length + ' room(s) measured: ' + totalNodes + ' node row(s), '
      + totalEdges + ' edge row(s)',
    rooms: out,
    totals: { rooms: out.length, nodes: totalNodes, edges: totalEdges },
  };
}

module.exports = { check };   // NO fix export -- see Pitfall 4
```

function openRoomDbForCaller(roomDir) {

### Anti-Patterns to Avoid

- **Folding the density line into `scripts/compute-state` (bash).** `stateOps.computeState` shells `bash scripts/compute-state` and then *writes the stdout to `STATE.md`* (`lib/core/state-ops.cjs:44`). A count folded there becomes a **persisted, immediately-stale snapshot on disk**, which is exactly what SEED-074's hard guard warns against ("re-measure fresh, do not reuse a stale snapshot"). It also would need a `room.db` read from bash, which has no navigation chokepoint. Do not do this.
- **Adding an acceptance point to `buildAcceptanceChecklist`.** Definitively wrong (see next section). It is the release hard-abort gate.
- **Returning `status: 'warn'` when counts are high/low/anything.** Renders as drift, inflates the drift tally, and triggers the `[F.1 Next Move] Run /mos:doctor --fix` block for a module with no `fix()`. Also a direct D-06 violation (implies a health judgment).
- **Requiring `node:sqlite` or `lib/core/room-db.cjs` from the doctor module.** Blocked by `scripts/check-substrate.cjs` in `--diff` (pre-commit) mode; `lib/core/doctor/` is not on `ALLOWED_DIRECT_IMPORT`.
- **Any adjective in `detail`.** "sparse", "dense", "healthy graph", "low", "growing" -- all forbidden by D-06. Report integers and nouns only.

## The `--acceptance` question: DEFINITIVELY RESOLVED

CONTEXT.md flagged real doubt here. The answer is unambiguous and comes from `scripts/doctor.cjs`'s own dispatch order.

**`--acceptance` and the module registry are two output streams that never merge.**

`main()` dispatches `flags.acceptance` at `scripts/doctor.cjs:2717`. That block calls `runAcceptance(...)`, and inside the `.then()` it calls `process.exit(...)` (line 2767); the block then `return`s (line 2773). The accumulative engine -- and therefore every `cadence: 'always'` module -- runs at line **3493**, which is unreachable on an `--acceptance` invocation. There is no path by which a registry module's result appears in `--acceptance` output.

Corroborating evidence:
- The comment at line 2714 states the acceptance dispatch is placed "BEFORE the class-flag block so the existing per-class drift detectors do not run twice."

## The `room.db` Schema (Discretion item, now resolved)

CONTEXT.md left "which typed node tables count as nodes" to research. **The premise does not apply: there are no typed node tables.**

`lib/core/lazygraph-ops.cjs::initSchema` (line 32) creates exactly this, and `room-db.cjs::openRoomDb` calls it on every open:

```sql
-- Source: lib/core/lazygraph-ops.cjs:34-63
CREATE TABLE IF NOT EXISTS nodes (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  properties TEXT DEFAULT '{}'
);
CREATE TABLE IF NOT EXISTS edges (
  source TEXT NOT NULL,
  target TEXT NOT NULL,
  type TEXT NOT NULL,
  properties TEXT DEFAULT '{}',
  PRIMARY KEY (source, target, type)
);
CREATE INDEX IF NOT EXISTS idx_nodes_type ON nodes(type);
CREATE INDEX IF NOT EXISTS idx_edges_type ON edges(type);
-- ... plus stakeholders, plus the rs_discoveries VIEW over nodes
```

Later migrations add columns (`phase-109-nodes-provenance` adds `source_path`, `created_by`, `created_at`, `last_seen_at`, `review_status`; `phase-160` adds bitemporal columns; `phase-224` adds `edges.review_status`), never new node/edge tables. `lib/core/navigation/typed-claim.cjs`, `typed-opportunity.cjs`, `typed-frame.cjs`, `synthetic-expert.cjs`, `typed-entity.cjs` etc. are **writers** that INSERT into `nodes` with a different `type` value. `EDGE_TYPES` (23 values, `lazygraph-ops.cjs:26`) is likewise a `type`-column vocabulary, not a table list.

**Therefore:**
- Total node count: `SELECT count(*) FROM nodes`
- Total edge count: `SELECT count(*) FROM edges`
- One combined figure each. Do not sum sub-tables (there are none) and do not report per-type breakdowns (out of scope, and a per-type breakdown edges toward salience framing that D-06 forbids).

**Detecting "schema-less" without throwing.** Two options:

```javascript
// Option A -- the honest probe. Works on a handle that is already open.
const n = db.prepare(
  "SELECT count(*) AS c FROM sqlite_master WHERE type='table' AND name IN ('nodes','edges')"
).get().c;   // 2 = both present, 0 = schema-less
```

```javascript
// Option B -- try/catch the count itself. node:sqlite throws "no such table: nodes".
let n = 0; try { n = db.prepare('SELECT count(*) AS c FROM nodes').get().c; } catch (_e) { n = 0; }
```

Option B is the repo's own idiom (`umbilical-module.cjs:207-216` and `304-309` both wrap `db.prepare(...)` in try/catch and treat the throw as "no rows"). **However**, note that by the time you hold a handle from `openRoomDbForCaller`, `initSchema` has already run, so `nodes` and `edges` are guaranteed to exist. The schema-less case is only reachable if the read-only alternative is adopted. Plan accordingly.

### Canon Part 7 collision: `graphStats` already exists

**This must be addressed explicitly in the plan, not silently ignored.**

`lib/core/lazygraph-ops.cjs::graphStats(conn)` (line 690) already computes exactly what this phase needs:

```javascript
// Source: lib/core/lazygraph-ops.cjs:709-716
const totalNodes = Object.values(nodeCounts).reduce((sum, n) => sum + n, 0);
const totalEdges = Object.values(edges).reduce((sum, n) => sum + n, 0);
return Promise.resolve({ nodes: nodeCounts, edges, total: { nodes: totalNodes, edges: totalEdges } });
```

It is already reachable by users as `room_graph --command graph-stats` (`tool-router.cjs` ROOM_GRAPH_COMMANDS).

**Why it cannot simply be reused as-is, and why this phase is still justified:**

1. **Wrong reach.** `graphStats` is single-room. `graph-ops.cjs::graphStats(roomDir)` (line 118) opens ONE room. SEED-074's gate needs a *census* across every registered room. That is the actual new capability.
2. **Wrong door.** `graph-ops.cjs` reaches `room.db` via `lazygraph.openGraph(roomDir)`, not `navigation.cjs`. `openGraph` calls are flagged by `check-substrate.cjs` as `opengraph-bypass` (37 baseline violations). Calling `graph-ops.cjs::graphStats` from a doctor module would inherit that bypass, violating D-04 and Canon Part 9.
3. **Wrong shape.** `graphStats` is `async`; the accumulative engine loop is **synchronous** (`doctor.cjs:2198` calls `checkFn(ctx)` directly). This is the exact reason classes M and S are Phase 217 carve-outs. An async runner cannot join the registry without an engine change, which D-02 forbids.
4. **Wrong grain.** `graphStats` returns a full per-type breakdown of node types and all 23 edge types. Surfacing per-type ranking is the shape of a salience report, which is D-06/SEED-074 territory.

**Recommendation for the plan:** state the above in the module's header comment, count directly with two `SELECT count(*)` statements (the truth `graphStats` itself computes, minus the per-type breakdown), and cross-reference `graphStats` so a future reader sees the reuse question was asked and answered rather than missed.

**Recommendation for `room_state` (D-07):** do NOT call `graph-ops.cjs::graphStats` there either, even though `tool-router.cjs` is async-friendly. Use the same `openRoomDbForCaller` + two counts, so both surfaces of this phase report through one door and one query. Two code paths that can disagree about the same number is worse than mild duplication.

## Common Pitfalls

### Pitfall 1: `openRoomDbForCaller` MUTATES the database it "reads" (the phase's central decision)

**What goes wrong:** A check that documents itself as read-only silently runs 13 `CREATE TABLE IF NOT EXISTS` statements plus five migrations against 38 real user databases, on every bare `/mos:doctor` invocation.

**Why it happens:** `openRoomDbForCaller` -> `roomDbMod.openRoomDb(roomDir)` (`spine-events.cjs:344`). `openRoomDb` (`room-db.cjs:100-149`) does, in order: `fs.mkdirSync(<roomDir>/.mindrian, {recursive:true})`; `new DatabaseSync(dbPath, {timeout:5000})`; `PRAGMA journal_mode=WAL` + `foreign_keys=ON` + `synchronous=NORMAL`; `lazygraph.initSchema(db)`; `memory.initMemorySchema(db)`; then `runPhase109NodesProvenance`, `runPhase109SessionFocus`, `runPhase160NodesBitemporal`, `runPhase222RankerWeights`, `runPhase224EdgeReviewStatus`. There is no read-only variant and no opt-out flag.

**Verified empirically, not inferred.** I copied `~/MindrianRooms/ador-ip-test/.mindrian/room.db` to a scratch dir and called `openRoomDbForCaller` on the copy:

```
tables before 28 -> after 29
ADDED tables: [ 'ranker_weights' ]
edges cols before: source,target,type,properties
edges cols after : source,target,type,properties,review_status
```

Two schema objects were created by an operation whose only purpose was to read two counts. The live-room table-count distribution (18 rooms at 13 tables, 7 at 14, 5 at 15, 5 at 28, 3 at 29) confirms most rooms are behind the migration chain and would be advanced by the sweep.

**How to avoid -- three options, ranked:**

- **(A) Add a read-only sibling door to the chokepoint (RECOMMENDED).** Add `openRoomDbReadOnlyForCaller(roomDir)` to `lib/core/navigation/spine-events.cjs` and re-export from `lib/core/navigation.cjs`. Implementation is ~10 lines: existence check, `new DatabaseSync(dbPath, { readOnly: true })`, return `null` on any throw. This lives INSIDE the allow-listed `lib/core/navigation/` directory so `check-substrate.cjs` is satisfied and Canon Part 9 is honored (the chokepoint gains a door; nothing bypasses it). D-04's intent -- "never a direct `room.db` open" -- is fully preserved; D-04's literal wording names the existing door, so this is a plan-level extension the navigator should sign off on. It also makes `check()` honestly non-mutating, matching every sibling module, and makes the schema-less probe meaningful. Cost: one file outside `lib/core/doctor/`, so D-02's "no engine code change" becomes "no *doctor engine* code change" (still true).
- **(B) Accept the mutation, document it loudly.** The migrations are idempotent, additive, and non-destructive, and every one of them would run on the room's next real use anyway. Cost: the module's header must state "this check is NOT read-only" in bold, it breaks the doctor-wide `check()` convention, and Pitfall 2 becomes acute (the test suite would migrate the developer's real rooms).
- **(C) Skip rooms whose schema is behind.** Rejected: determining that requires opening the db, which is the mutation.

**Warning signs:** `room.db` mtimes changing across a bare `/mos:doctor`; `ranker_weights` appearing in rooms the user has not touched; `-wal`/`-shm` files reappearing.

### Pitfall 2: the contract-parity test runs `check()` against the developer's REAL rooms

**What goes wrong:** `npm test` / `tests/run-all-217.sh` silently sweeps 45 live rooms, and (combined with Pitfall 1) migrates all of them.

**Why it happens:** `tests/test-doctor-module-contract-parity.cjs:116` calls `runner.check({ home: freshHome(), running: '99.99.99', dryRun: true, fix: false, flags: {} })` with `freshHome()` being an empty `mkdtempSync` dir. But `shared.cjs::readRegistry()` **ignores `ctx.home`** -- it reads `process.env.MINDRIAN_ROOMS_HOME || path.join(os.homedir(), 'MindrianRooms')`. The test sets no such env var. So `check()` reads the real registry. This is true of `cascade-rooms` today too, but cascade-rooms only does `fs.existsSync` probes, so nobody noticed.

**How to avoid:**
- Adopt option (A) from Pitfall 1, which makes the sweep harmless.
- And/or have `check(ctx)` honor `ctx.home` when present (read the registry at `path.join(ctx.home, '.rooms', 'registry.json')` before falling back to `readRegistry()`). This is a small, self-contained hardening that makes the module correct under the contract test's stated intent.
- Either way, the new hermetic test MUST set `MINDRIAN_ROOMS_HOME` to a scratch dir on every `spawnSync`, exactly as `test-doctor-class-b.cjs:102-105` does (that file even asserts it).

**Warning signs:** the phase test suite taking longer than expected; `git status` in `~/MindrianRooms` showing db changes after a test run.

### Pitfall 3: returning `warn` turns a measurement into a false drift signal

**What goes wrong:** `computeSummary` maps `warn` (and `error`) to `drift++` (`doctor.cjs:1884`). A non-zero drift tally on a non-`--fix` run prints the `[F.1 Next Move] Run /mos:doctor --fix` block (`doctor.cjs:1810-1816`) -- proposing a fix for a module that has none. It also implies the graph is in a bad state, a direct D-06 violation.

**How to avoid:** return `'ok'` whenever the sweep completed (regardless of the numbers) and `'skip'` when there is no registry. Never `'warn'`. There is no threshold in this phase; a threshold is SEED-074's gate, which this phase deliberately does not open.

**Warning signs:** any `if (nodeCount > N)` in the module. That is the gate, and it is out of scope.

### Pitfall 4: exporting a `fix()` stub fails the suite

**What goes wrong:** `tests/test-doctor-module-contract-parity.cjs` rule 8: `fix_supported: false` **and** `typeof runner.fix !== 'undefined'` -> violation -> `process.exit(1)`.

**How to avoid:** `module.exports = { check };` and nothing else fix-shaped. (Named helper exports for unit tests are fine, as `umbilical-module.cjs` does with `parseUmbilicalMarker` -- just never a key literally called `fix`.)

### Pitfall 5: `introduced_version` above the running version silently disables the module

**What goes wrong:** `doctor.cjs:2179-2183` pushes the module onto `deferred[]` and never calls `check()`. No row appears, no error appears. It looks like the module simply produced nothing.

**How to avoid:** set `introduced_version` to the version this actually ships in (currently `1.15.3-beta.47`; bump only in lockstep with a real release via `scripts/release.sh`). Verify by running `node scripts/doctor.cjs --json` and confirming `report.checks['room-graph-density']` exists and `report.checks['accumulative-engine'].deferred` does not contain it.

### Pitfall 6: `resolveRoomPath` is not exported

**What goes wrong:** `require('./cascade-rooms-module.cjs').resolveRoomPath` is `undefined`. `cascade-rooms-module.cjs:181-184` exports only `{ check, fix }`.

**How to avoid:** re-declare the 5-line function locally (shown in Pattern 1). Do not export it from cascade-rooms just for this -- that widens a stable module's surface for no reason.

### Pitfall 7: em-dashes in the registry `description`

**What goes wrong:** the house rule bans U+2014 everywhere. Class K (`stale-first-touch-copy`) actively scans declared surfaces for em-dashes.

**How to avoid:** hyphens only, in the JSON `description`, in code comments, in `detail` strings, in `commands/doctor.md`, and in test names.

### Pitfall 8: `node:sqlite` prints an ExperimentalWarning to stderr

**What goes wrong:** Node v22 emits `ExperimentalWarning: SQLite is an experimental feature` on stderr the first time `node:sqlite` loads. A test that pipes stderr into a JSON parser breaks. I hit this exact thing while taking the census.

**How to avoid:** parse `stdout` only (which `test-doctor-class-b.cjs` already does), never `stdout + stderr`. Doctor's `--json` writes to stdout.

**Honest verdict, verbatim in substance:** the corpus has **nothing** on node/edge counts as a lightweight health-check size metric. There is no idiomatic named pattern for it in this corpus. It is not covered.

**The one genuinely useful thing it did tell us, and it is a terminology warning:** the corpus's only typed placement of the word **"density"** is as a **graph algorithm**, a direct sibling of PageRank, Community Detection, Degree Centrality and Connectivity, all children of "Graph algorithms" via `builds_on` edges sourced from `agentflare-ai/sqlite-graph` (the same repo SEED-074 itself surfaced) and `graphqlite`. In graph theory "density" means the ratio `|E| / (|V|(|V|-1))` -- a computed structural property, precisely the family of thing SEED-074 gates.

**Implication for this phase:** "density" is the wrong word for what this phase actually ships, which is a raw row count. The phase NAME can stay (it is the roadmap label and SEED-074's own wording), and the registry `id` `room-graph-density` is acceptable as a stable identifier. But **no rendered output copy should use the word "density"**, both because it invites the D-06 health-judgment reading and because it names an algorithm this phase explicitly does not implement. Recommended output vocabulary: "node rows", "edge rows", "counts", "Local graph: N nodes, M edges". If the plan wants a clean break, `room-graph-size` is the more accurate id -- flag it to the navigator rather than deciding unilaterally, since D-02's file name is already written down in CONTEXT.md.
