<objective>
Close Pitfall 4, the ghost-trigger hazard, which is the one place this phase genuinely intersects Phase 236.

The prompt that opened this phase worried the FTS table would become a fourth thing Phase 236's fix does not know to protect, meaning data LOSS. Live probe proved it is the INVERSE. `clearIndexerOwnedRows` (`lazygraph-ops.cjs:126-152`) deletes `Artifact` and `Section` nodes; the FTS index KEEPS their rows and keeps matching them. Measured: after the Phase 236 scoped wipe, `nodes` held 1 row while `eureka_fts` held 2, and a MATCH still returned both dead node ids.

The hazard is data RESURRECTION. A content-tier trigger would fire on content that no longer exists and point at a dead `node_id`. That is a silent correctness bug of exactly the false-success class this repo already tracks in `feedback_false_success_silent_skip_gates_academy_testers`, and it is the same bug class the whole v1.16.0 milestone exists to close.

Purpose: the FTS index is 100 percent derived and holds no original data, so it is safe to destroy and rebuild at will. The fix is one guarded DELETE statement inside the transaction `rebuildGraph` already opens. It rides Phase 236's existing atomicity for free and cannot lose data because there is no original data there to lose.

Output: one production statement plus its fence.
</objective>
