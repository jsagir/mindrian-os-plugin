Two facts make this implementable and both were confirmed live on disk:

1. `rrfFuse` exists at `lib/core/eureka/hybrid-retrieve.cjs:90-118`, is rank-position based, 1-based, `1/(k+rank)`, accepts either a bare array or a tagged `{ source, items }` list, and records which sources contributed. Writing a second one is a Canon Part 7 violation. It is also structurally immune to bm25's negative-score sign convention, because it reads array POSITION and never touches `item.rank` or `item.score`; both input lists are already sorted best-first (`lexicalSearch` via `ORDER BY rank ASC` over negative bm25, `scored` via `b.score - a.score` at `:733`). No normalization, no sign flip, no min-max scaling is needed anywhere.

2. RESEARCH BLOCKER B-1 is real and confirmed on disk: `scored` at `:717-729` is built from `data/command-registry.json` rows and carries no `trigger_tier`, no `reach_id` and no sensor provenance. `command` is the ONLY stable join key. Fusion therefore operates over command slugs, and the tier candidate lists must be lists of command slugs.

Purpose, and the reason this plan does MORE than the minimum: v1.16.0 is a milestone whose entire audit finding was wired-at-one-end seams (Phases 235, 237, 238, 239 each repaired one). Shipping a new optional argument that no production caller ever passes would commit this milestone's own signature defect. `lib/core/orchestration-candidate-lift.cjs:107-121` is a LIVE production caller of `rankForSelector` that already has `sensorReaches` AND `projectionOffer.options` in scope at the call site. That is where the seam gets its second end.
