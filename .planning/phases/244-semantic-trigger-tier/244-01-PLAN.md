<objective>
Lay the two foundations every other plan in this phase consumes, and stand up the phase gate that will judge them.

Phase 244 is a WIRING phase, not a build phase. Before any sensor can be written, two things must exist that do not exist today: (a) a fourth trigger tier named `content`, ranked below `context` and above `keyword`, because Canon Part 11 R3 forbids ranking lexical relevance as problem-state but corpus-relative bm25 evidence is strictly stronger than a hand-picked keyword hit; (b) a PUBLIC way to ask whether `eureka_fts` exists in a given room.db, because `tableExists` currently lives under the `_test` seam of `lib/core/eureka/tri-modal-index.cjs` and production code must never import a test seam.

Purpose: `lexicalSearch` (`tri-modal-index.cjs:418`) gates only on the FTS5 CAPABILITY probe, never on whether `eureka_fts` exists in THIS db. On every live room today the table is absent, so `lexicalSearch` falls into its `catch (_e) { return []; }` and a missing index is indistinguishable from a genuine zero-hit. That is the `feedback_false_success_silent_skip_gates_academy_testers` bug class and it is the exact symptom that opened this phase. A public `tableExists` is what makes `index_absent` a distinguishable state for Plans 02, 05 and 06.

Output: `tests/run-all-244.sh`, two test files, and two narrow additive source edits. Zero new npm dependencies. Zero network.
</objective>
