<objective>
Make the sleeper risk visible. 244-RESEARCH.md names Pitfall 2 as this phase's biggest sleeper risk in its own words: the content tier ships, passes every fixture test, and fires zero times in production because the index it queries was never built. The warning sign is precise: every acceptance test passes and the navigator reports "natural language still does not trigger anything", which is the exact symptom that opened this phase.

Plan 02 gave the index a lazy build lifecycle. This plan makes its state observable, so a silent failure becomes a reported one. ROADMAP SC1 requires "a presence/freshness check added to `node scripts/doctor.cjs --acceptance`, so an unbuilt index is visible rather than silently producing zero fires".

Purpose: visibility, not a gate. This distinction is load-bearing and is a real design decision this plan must make correctly.

The severity decision, with its evidence: EVERY existing entry in the `--acceptance` checklist array in `scripts/doctor.cjs` carries `severity: 'blocker'`, and the documented exit contract at `:513-514` is "`--acceptance`: any point failed (hard abort)". An acceptance point that fails whenever a room lacks `eureka_fts` would fail EVERY release until every registered room has been rebuilt, because absent is the DEFAULT state of every production room today, verified live against the 8.4 MB `rethinking-mindrianos` room.db. So the point must be built to fail on a genuine DEFECT and to report, loudly and in `detail`, on the merely-unbuilt case. Absent is a fact to surface; stale is a bug to fail on.

Output: one new doctor module, one JSON registration, one acceptance point, one test.

CORRECTION TO 244-RESEARCH.md that the executor must not conflate: the research says "add an `eureka_fts` presence/freshness module to `node scripts/doctor.cjs --acceptance`" as if it were one surface. It is two, with two different shapes. `data/doctor-modules.json` is a hand-maintained array of `{ id, introduced_version, cadence, flag, fix_supported, runner, description }` entries pointing at `lib/core/doctor/<name>-module.cjs`, and registering there requires NO edit to `scripts/doctor.cjs`. The `--acceptance` checklist is a SEPARATE hand-written array of `{ id, label, severity, applies_to, run }` objects inside `scripts/doctor.cjs`. A module in `doctor-modules.json` does NOT automatically become an acceptance point. This plan builds both, deliberately.
</objective>
