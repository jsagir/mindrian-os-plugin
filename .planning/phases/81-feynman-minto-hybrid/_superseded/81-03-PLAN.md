# Plan 81-03: Feynman stages 4 and 5 (mental model + sweet spot)

## Goal

Replace the 81-01 stub bodies of `feynmanStage4_mentalModel` and `feynmanStage5_sweetSpot` with real Anthropic API calls routed through `lib/memory/llm-call.cjs`. Record three fixture cases per stage, commit them, and prove via a full 4-stage pipeline integration test that the stitched output matches the Feynman-MINTO narrative schema from 81-CONTEXT D-1 (essence, plain, elevator, models, sweetSpot, keyClaims, fundamentals). Stages 3 and 6 remain skipped. Assert the entire 4-stage pipeline makes at most 4 LLM calls per run. Goal-backward: a developer runs `node lib/memory/feynman-stages.test.cjs` and sees the 4-stage integration test green, producing a structured object that the 81-04 renderer can consume directly.

## Risks

- **Risk: Merge conflict with 81-02 in `lib/memory/feynman-stages.cjs`**. Both plans modify the same file by filling in different stub bodies. If executed in parallel without coordination, git merge may produce a conflict.
  - **Mitigation:** plan executors should open the file once, fill in their respective stub bodies, commit independently, and rely on git's line-level merge. Since the changes are in disjoint function bodies (stage1+stage2 vs stage4+stage5), git merge handles them cleanly in practice. If a true conflict arises, manual resolution is trivial. The `runFullPipeline` function added in 81-03 references all four stages - it must be added AFTER 81-02 lands stage1 and stage2, OR it must be written to not crash-load if stages 1/2 are still stubs (fine because `runFullPipeline` throws at call time, not at load time). The plan execution order is: start 81-02 and 81-03 in parallel, land 81-02 first (stage1+stage2), then land 81-03 on top (stage4+stage5+runFullPipeline). If 81-03 lands first, `runFullPipeline` silently waits until 81-02 lands before the integration test passes - this is a detectable failure state, not a silent wrong.
- **Risk: stage 5 prompt bundles two outputs (sweetSpot + keyClaims) in one response**. If the prompt or model produces only one, the parser throws and the fixture record fails.
  - **Mitigation:** prompt explicitly demands both fields. Parser throws `LLMParseError` clearly identifying which field is missing. Recording script refuses to commit a fixture that would fail assertions, catching the problem at record time, not at replay time.
- **Risk: stage 4 output (analogies) is highly temperature-sensitive**. Re-recording may produce wildly different analogies.
  - **Mitigation:** assertions are shape-only. An analogy about "a library" vs "a kitchen" both pass as long as the shape is right. Documented in 81-RESEARCH Section 3.
- **Risk: full pipeline cost exceeds $0.15 per-run cap**.
  - **Mitigation:** first full-pipeline recording measures actual cost. If over the cap, either reduce `maxTokens` per stage, switch to a cheaper model, or raise the default cap. The plan execution log captures the measured cost for 81-05's CHANGELOG entry.
- **Risk: accidental addition of stage 3 or stage 6**. An executor misreading the plan might add them.
  - **Mitigation:** the grep regression guard in the test file fails loudly. Multiple comment markers in `feynman-stages.cjs` reinforce the rule.
- **Risk: `runFullPipeline` may be assumed by 81-04 to always return a `_pipeline_meta` field**. If 81-03 omits it, 81-04 breaks.
  - **Mitigation:** the full-pipeline integration test in 81-03 asserts the exact shape of `_pipeline_meta`. 81-04 planning already references this contract.

## Deviation Notes

- **`runFullPipeline` orchestrator added here rather than in 81-04.** 81-RESEARCH Section 7 (81-03 row) says "A full 4-stage pipeline integration test". I interpret that as needing an actual orchestrator function in the library, not just a test-side loop. Putting the orchestrator in `feynman-stages.cjs` means 81-04's renderer calls one function instead of wiring four calls itself, and the defense-in-depth budget check (throwing mid-pipeline if cumulative cost exceeds per-run cap) lives in one place. This is additive to 81-RESEARCH, not contradictory.
- **`full-pipeline/expected-shape.json` is a schema-lite file, not a recorded response.** The full-pipeline output contains four separate LLM responses stitched together. Recording it as a single fixture would be redundant with the per-stage fixtures. Instead, the test uses the per-stage fixtures (via the shim) and asserts the stitched output matches an expected shape document.
- **Parallelism with 81-02.** Both plans modify `lib/memory/feynman-stages.cjs`. See the Risks section for the strategy. The user instruction explicitly marks 81-02 and 81-03 as parallel-safe provided 81-01 is complete, so I am honoring that.
