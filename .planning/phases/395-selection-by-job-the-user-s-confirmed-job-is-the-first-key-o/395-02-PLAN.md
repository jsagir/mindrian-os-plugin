## Goal of this slice

When the job that ranked the next move came from the goal, every place that shows the move says so and names the job. A goal change causes the section briefs to be written again. A user can set a first goal job with the two gate tools that exist.

What a user gets:

* With a goal job set, the brief and the `suggest_next` reply name the goal job and its origin. They no longer call it "the nest job".
* After a goal change, a brief on disk reads as stale and the next stop writes it again with the new move.
* With no job set and jobs to offer, the `suggest_next` reply holds one field, `how_to_set_job`, that tells the model the exact two tool calls that set a job.
* A new goal job outside the job vocabulary is refused at the gate. Nothing is written.
* A stored problem type that is not one of Theo's four ids no longer stops a job change.

## What this slice does not do

* It does not change the order rule of the selector (slice 2).
* It does not add a tool. It does not change a tool description or an input schema.
* It does not change `lib/mcp/tools/gate.cjs`, `lib/mcp/gate-render.cjs`, `lib/hmi/jtbd-state.cjs`, `scripts/vault-section-minto-generator.cjs`, `scripts/on-stop` or `lib/memory/triple-context-formatter.cjs`.
* It does not check the vocabulary inside `setGoal` or inside `applyGoalFile` (see finding F3).
* It does not rewrite the briefs at the moment of the goal write. The existing stop walk and the MINTO regeneration write them (see assumption A5).
* It does not make the elicitation dialog write a goal (see finding F2).
* It does not touch the chain, the consult to Theo, the ledger, or any hook.

## Assumptions (the owner is away; each one is a choice the checker can reverse)

* **A1.** Item 4 goes in although the elicitation rung does not write a goal (F2). The sentence states the success condition, so it does not claim a job is set when it is not.
* **A2.** The vocabulary check is only on `rewrite-jtbd` in `ratifyGoalProposal` (F3). A goal in free text that is stored by another route stays stored and is ignored for selection, as in 395-01.
* **A3.** Side effect of A2: the card that `buildStrategyCard` builds puts the goal's own job in the `rewrite-jtbd` preview when the classifier gave no job (`lib/core/strategy/strategy-card.cjs:221,246`). If that goal job is free text, this approve is now refused with `goal_job_not_in_vocabulary`. The goal stays as it was. `buildStrategyCard` has no caller in shipped code (cold check M5).
* **A4.** The selection job goes into the base `fingerprint` of the record basis, not only into the extras. Reason: `lib/memory/triple-context-formatter.cjs:657-667` compares the base fingerprint to decide "fresh" or "stale" and calls `recordBasis(sectionPath)` with no extras. With the job in the base fingerprint, that reader says "stale" after a goal change with no change in its file. `full_fingerprint` is made from `fingerprint`, so the write-again rule in `scripts/vault-section-minto-generator.cjs:871-875` also sees the change.
* **A5.** `recordBasis` takes a fourth, optional argument `roomDir`. Its default is the parent folder of `sectionPath`. The formatter passes no room folder and reads only nests that are direct children of the room, so the default is correct for it.
* **A6.** The briefs are written again by the callers that exist: the stop walk (`scripts/on-stop:506-539`) and the MINTO regeneration. Between the goal write and the next stop, a brief on disk has the old move, and the session-start reader marks it stale. No new caller is added.
* **A7.** The problem type of the goal is part of the basis line, although no reader of this slice uses it for the move. The task for this plan asks for it. Effect: a change of the problem type alone also writes the briefs again.
* **A8.** Label texts chosen here: source label `your goal job (<job id>)`; brief line `Job: <job id> (your goal job; it ranks the move below). This nest's own job: <section job id>.`; basis line `- selection job: <job id> (your goal job), problem type <id or "not set">`. The `why` text of 395-01 (`serves your goal job`) stays.
* **A9.** `how_to_set_job` is added only on the two return paths of `resolveNextMove` that carry the job fields. It is absent, not `null`, in every other case, so a reply for a nest with a job has the same bytes as now.
* **A10.** When a new goal job is refused, the decision node of the gate is still written and confirmed, and the reply carries `strategy_ratification.reason: 'goal_job_not_in_vocabulary'`. This is the same rule as the existing `goal_write_failed` case (`goal-gate.cjs:19-22`): a goal fault never changes `ok` of the gate reply.
* **A11.** A goal job `explore` still wins with `state: 'ok'` (cold check N6). Not changed here; it belongs to slice 2.
* **A12.** The expected commands in the new test come from data in the repository (`data/command-registry.json`, the ledger, the section contracts). The test compares against the registry at run time where it can. If a later data change makes check E1 fail because the primary no longer serves the goal job, that is a data change to review, not a fault of this plan.
