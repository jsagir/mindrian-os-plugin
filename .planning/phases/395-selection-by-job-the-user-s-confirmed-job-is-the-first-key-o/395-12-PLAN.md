## 1. Findings

### 1.1 Root cause of report 1 (PROVEN by a run, READ in the code)

* READ: `scripts/mindrian-mcp-server.cjs:190` computes the boot-time room once, at process start: `const roomDir = path.resolve(process.env.MINDRIAN_ROOM || './room');`. The shipped `.mcp.json` sets no `MINDRIAN_ROOM`, so the boot-time room is `./room` under the cwd of the server process.
* READ: `scripts/mindrian-mcp-server.cjs:256` passes that value into `registerRouterTools(s, roomDir, ...)` (`lib/mcp/tool-router.cjs:988`). Every router handler closes over it.
* READ: `room_state` (`lib/mcp/tool-router.cjs:1030-1035`) resolves the room per call: `sessionRoom.resolveMcpSessionRoom({ sessionId, ctx: { fallbackRoomDir: roomDir, surface } })`. That reads the session binding file (`lib/core/session-binding.cjs`, leg `session.primary` of `lib/core/resolve-active-room.cjs` `resolveSessionRoom`). So `room_state` reads the bound room.
* READ: the line that picks the wrong room for the report is `lib/mcp/tool-router.cjs:1703`: `return textResponse(buildContext(pluginRoot, roomDir, command, context) + ...)`. Here `roomDir` is the boot-time closure. `buildContext` (`:797-808`) calls `loadRoomState(roomDir)` (`:745`), which reads `<boot room>/STATE.md`. The handler never asks the session binding.
* READ: `ls` shows that `/home/jsagi/room` exists (existence only; content not read). ASSUMED: the host of session jsagi-96 started the server with cwd `/home/jsagi`, so the boot-time room was that folder, a room that is not the bound room.
* PROVEN (scratch copy of `74fda0093`, throwaway HOME): the real stdio server `scripts/mindrian-mcp-server.cjs`, started by an MCP SDK client with cwd `$T/cwd` (where `$T/cwd/room/STATE.md` holds marker A), after `room_bind` to born room B (marker B, `effective: true`):
  * `room_state status`: reads A false, reads B true.
  * `intelligence find-connections`: reads A true, reads B false.
* PROVEN (in-process, same fixtures, session bound to B): 7 more tools read A and not B: `methodology lean-canvas`, `analysis analyze-systems`, `export dashboard`, `orchestration scout`, `room_content help`, `meeting pipeline`, `room_graph visualize-room`. `methodology` also WRITES its pipeline step into the boot-time room (`.mindrian/pipeline-state.json`), not into B.

Root cause in one sentence: eight router tools in `lib/mcp/tool-router.cjs` read and write the boot-time room of the server process (`MINDRIAN_ROOM`, else `./room` under the server cwd), frozen in the `registerRouterTools` closure, and never ask the session binding that `room_bind`, `room_create` and `gate_answer` write.

## 2. Decisions of this plan

* One helper `resolveToolRoomDir(extra, bootRoomDir, surface)` in `lib/mcp/tool-router.cjs`. It calls the SAME resolver that `room_state` calls (`sessionRoom.resolveMcpSessionRoom`, the read ladder). When the source is `session.primary` (the session chose the room), it returns that room. Else it returns the boot-time room.
* Each of the 8 handlers gets 1 first line `const roomDir = resolveToolRoomDir(extra, bootRoomDir, surface);`. The new `const` shadows the closure name, so every existing use inside the handler (reads, writes, fallback arguments) takes the bound room with no other edit. `registerRouterTools` keeps the boot-time value as `bootRoomDir` (a `const` cannot read a name it shadows in the same scope). 4 handlers (`room_graph`, `methodology`, `analysis`, `export`) did not take `extra`; they get it as the second parameter. The MCP SDK passes `extra` to every tool handler.
* No room bound: the tools keep the boot-time room. This is the behavior of these 8 tools today, so an unbound session sees no change. The plan does NOT copy the `reg.active` fallback of `room_state` into these tools: that fallback is the machine-wide registry pointer, which another session can move (and which can name a sealed room); several of the 8 tools write. ASSUMED (assumption A3) as the right choice; see known limit L1.
* The governed writes inside `room_content` and `meeting` still go through `resolveWriteTargetOrRefusal`. Their fallback argument is now the per-call room. This does not change their result: the fallback is used only when the write ladder has no hit, and a read hit of `session.primary` is also a write hit (READ, `lib/core/resolve-active-room.cjs` `resolveWriteRoom` falls to `resolveSessionRoom` after the `.room-root` leg).
* No change to the output text of any tool. No new egress (the resolver reads the local binding file and registry only).
