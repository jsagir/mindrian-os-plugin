## 1. Design

* **One new mode, `--setup`, in `eureka-engine-enable.cjs`.** Without `--approved-via` it prints the consent card (plain text; `--json` gives the facts), exits 2, and runs nothing. With `--approved-via cli` or `gate` it runs the engine's own public setup script and streams its output to the screen. Then it reads the last line. On `OK <folder>` or `OK engine-only <folder>` it saves the folder through the existing `--path` code and prints the check (graph, pairs-and-scout and the other families). On `FAIL <step> <reason>` it prints the 3-line error (`x`, `Why:`, `Fix:`) with a plain sentence for each of the 6 steps, and it saves nothing. With no result line it prints the 3-line error "stopped without its result line".
* **The pin (owner ruling 34).** One constant, `EUREKA_SETUP_COMMIT = '9b91d252f532366b7a1958cbbf2d98eaaa9753eb'`, in `eureka-engine-enable.cjs`. `SETUP_SCRIPT_BASE = 'https://raw.githubusercontent.com/jsagir/mindrian-eureka/' + EUREKA_SETUP_COMMIT + '/scripts/'`, and the 2 script URLs are `SETUP_SCRIPT_BASE + 'setup-mindrianos.sh'` and `+ 'setup-mindrianos.ps1'`. The card names it: "the engine's setup steps as tested for this MindrianOS version (engine commit 9b91d25)". Test arm S17 fails when the constant is not 40 hex characters, when any URL (both commands, both cards) does not use exactly that commit, or when the module or the docs name a branch URL. The docs give no raw script URL at all; Desktop users get `npx @mindrian_os/cli --eureka`, which carries the pin of that version.
* **The command that it runs.** macOS and Linux: `bash -c 'curl -fsSL "$0" | bash' <pinned URL of setup-mindrianos.sh>` (the engine's own documented line). Windows: `powershell.exe -NoProfile -ExecutionPolicy Bypass -Command "irm <pinned URL of setup-mindrianos.ps1> | iex"`. `shell: false`; the URLs are built from the constant. The child environment is an allowlist (the existing `CHILD_ENV_KEYS` plus `MINDRIAN_EUREKA_ROOT`, the Hugging Face and certificate variables, and the Windows system variables). No `CLAUDE_` variable, no room variable and no Brain variable reaches the child. The timeout is 30 minutes.
* **The install and onboarding flow.**
  * Terminal installer (`npx @mindrian_os/cli`, `bin/cli.js`): after "MindrianOS is installed and current", it offers the step. In an interactive terminal it prints the card and asks `Set up the Eureka engine now? (y/N)`; the default is No. `--eureka` says yes without the question (the card still prints first). `--no-eureka` skips the offer. Without a terminal (a pipe, CI) it prints one line: run `/mos:eureka enable engine --setup` later. The two flags are removed before `claude plugin install`. The Eureka result never changes the exit code of the install (0).
  * Claude Code CLI: `/mos:eureka enable engine --setup` (new step 6 of the `enable engine` section): run the card, show it, fire the F.0 card with AskUserQuestion (Set up now, Not now), and only on a yes run it with `--approved-via cli` (Bash timeout 600000 ms). `/mos:setup` gets one line that offers it once and points to that command; it does not run it.
  * `--check` with an absent engine: the Fix line offers the one-step setup first, then `--path <folder>`.
  * Claude Desktop: no shell step for Larry. Larry shows the card text and tells the person to run `npx @mindrian_os/cli --eureka` in a terminal on the same computer (the pinned steps of that version). Desktop then reads the saved setting from the same home folder.
  * Cowork: it keeps its own home folder, so an engine set up on the computer is not seen there. The engine tools answer engine absent. Nothing new runs there.
  * A host that cannot run a shell script gets the card text and the terminal line, nothing else.
* **What does not change.** Part 8: no room content and no Brain call (the setup child gets no room data). No network before the card: the card branch returns before any spawn (tests S1 and S14). The engine code is not vendored. `--path` and `--sync` keep working (test S13, and the 15 arms of `test-387-eureka-engine-enable.cjs`). The engine runs offline after setup (the run-time transport does not change). No model is downloaded unless the person approved the setup: the only code path that downloads the model is the engine's own script, and the plugin holds no model download call (test S14).
* **Part 3 decision gate.** The card is the gate: Set up now (APPROVE), Not now (DEFER; "run it later with `/mos:eureka enable engine --setup`"). A wrong `--approved-via` value is refused (exit 1).
* **Not built** (smallest that works): no MCP tool, no new command, no new hitl stage, no change of the resolver, no pin of the engine code (the script cannot take a commit yet; see section 0.2 and the request to jsagi-96).

## 11. Known limits

* The pin fixes the setup steps, not the engine code. The pinned script clones or updates the engine at its newest `main` (`git clone` with no branch, `git pull --ff-only`), and it accepts no commit. So two installs on different days can get different engine code. The card says "the newest engine code". The fix is the request to jsagi-96 in section 0.2.
* The model line goes into `~/.bashrc` and `~/.zshrc` only (the engine script). A fish shell, or an app started from a menu, does not get the variable. `--check` still sees the model through the Hugging Face cache (READ). Whether every engine tool finds the model at run time without the variable is outside this plan (UNVERIFIED).
* In Claude Code the Bash tool stops at 10 minutes (600000 ms). A slow first download can need more time; then the person can run `npx @mindrian_os/cli --eureka` or the same command in a terminal. The command itself waits up to 30 minutes.
* On a terminal the setup output shows while it runs; inside Claude Code it shows when the Bash call ends.
* The real run was 1 time, on Linux aarch64, warm. This planner made no macOS and no Windows run (the engine CI is green on both, READ).
* The step needs `git`, and on macOS and Linux `bash` and `curl`. A missing `curl` gives "stopped without its result line".
* Cowork does not see an engine set up on the computer.
