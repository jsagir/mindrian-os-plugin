## Goal of this slice

Inside the one selector (`composeNextMove` in `lib/core/feyminto/next-move.cjs`), the job orders the candidates first. Theo, the contract, the ledger and the navigator table supply the candidates. The job puts them in order.

Sort keys after this plan, when a job is known:

1. The candidate serves the selection job. The selection job is the goal job when one is set (as `resolveSelectionJob` gives it), else the section job.
2. The ledger rating of the candidate for that job: strong, then partial or not rated, then poor.
3. The count of sources, as today. Then the ties of today: ledger order, contract order, Theo rank, name.

When no job is known (`state: 'job_unknown'`), the order is exactly the order of today.

What a user gets: in a nest where a runnable candidate serves the job, the proposed move serves the job, also when another candidate has more sources. Example from a real run: in `market-analysis` (job `understand-market`) the proposed move changes from `user-needs`, which does not serve that job and which the ledger rates 0.2 of 2 for it, to `macro-trends`, which serves it and which the ledger rates 1.91 of 2.

## Design

### Key 1: the candidate serves the job

`composeNextMove` already sets the key `job` on a candidate when `data/command-registry.json` lists the selection job in `serves_jtbd` of the command (line 154). Key 1 is that fact, as the first sort key. Nothing new is read.

### Key 2: the ledger rating for the job (decision D1)

The task for this plan names key 2 as "ledger confidence for that job". Findings 4 to 7 show that the raw confidence is the wrong number: it says how sure the scorer is, not how well the command fits. The number that says "this command is a good first move for this job" is `score`.

Decision D1: key 2 is the ledger `score` of the command in the row `<job>|*|*`, used in 3 levels, and the `confidence` is used as the gate that says whether the score counts.

| Level | Meaning | Rule |
|---|---|---|
| 2 | strong | the score counts and is 1.5 or more |
| 1 | partial, or not rated | the score counts and is 0.5 or more and less than 1.5; or the command has no score that counts |
| 0 | poor | the score counts and is less than 0.5 |

* The limits 0.5 and 1.5 are the middle points between the 3 criteria of the scoring question (0 poor, 1 partial, 2 strong).
* A score counts by the shipped rule of finding 8. No new rule is made.
* A command with no counted score gets level 1. No information is not a poor rating. A counted poor rating goes after it.
* Why levels and not the raw score: a small difference between 2 scores would decide before the count of sources. Measured (variant S1, raw score as key 2): in `funding` the primary becomes `think-hats` (score 0.39, 1 source) in place of `grade` (score 0.35, 2 sources). Both are poor ratings; the 0.04 between them is not a reason. With levels, both are level 0 and the count of sources decides, as today.
* The rating is read from the raw ledger row, not from the filtered list (finding 7). It only orders candidates. It adds none.
* `composeNextMove` reads the row itself, as it reads the command registry itself. So a caller that composes by hand (arm NM4 of `tests/test-36925-brief.cjs`) and `nextMoveForSection` get the same order.
* A new optional input `jobFit` (`{ name: 0 | 1 | 2 }`) replaces the ledger read. `nextMoveForSection` does not pass it. Its use: a test can state the ratings, so the test does not break when the ledger is rebuilt before a release.

### Goal job `explore` (decision D2)

Decision D2: a goal job `explore` does not rank the move. `resolveSelectionJob` treats it as "no goal job": the section job is used, and a nest with no section job stays `job_unknown`.

* Reason: `explore` names no intent (finding 11), and on HEAD it flattens the room to 1 command (finding 10).
* Why in `resolveSelectionJob`: it is 1 condition in 1 function, and both readers follow it (finding 12). A rule only in the selector would leave the brief with the line "selection job: explore (your goal job)" for a move that the section job ranked.
* Effect, PROVEN: with the goal `explore`, the output of the selector for all 15 folders on 2 surfaces is byte-identical to the output with no goal, and the brief fingerprint is the same as with no goal. 28 of 30 primaries change against HEAD (HEAD with goal `explore` against this plan with goal `explore`).
* A section whose own job is `explore` (`opportunity-bank` by the canon) keeps that job. The rule is for the goal only.
* The stored goal is not changed. Only its use for selection changes.

### The why sentence

Today the primary carries this sentence when Theo's first command is another one: "Theo ranked X first, but agreement across sources outranks one source's order". After this plan the primary can be before Theo's first command for another reason. The sentence then names that reason:

* the primary serves the job and Theo's first command does not: "Theo ranked X first, but a command that serves the job is ordered first";
* both are equal on key 1 and the primary has the higher ledger level: "Theo ranked X first, but the ledger rates this command higher for the job";
* in every other case: the sentence of today, under the condition of today.

With no job known, only the third case can occur.

### No job known

`jobFirst` is `jobId !== null`. When it is false, the 2 new keys give 0 and the sort is the sort of today; the ledger row is not read; the `jobFit` input is not read; the why sentence takes the branch of today. See "No-job proof".

// data/section-command-ledger.json row `<job>|*|*` carries a `score` from 0 (poor fit) through 1 (partial fit) to
// 2 (strong fit), and a `confidence` that says how sure the scorer is of that score. A high confidence does NOT mean
// a good fit, so the confidence is used only as the gate it already is in section-ruling-candidates.cjs: a score
// counts when its confidence is at or above the ledger's floor, or when it has no confidence and is ground truth.
// Levels: 2 strong (score at or above 1.5), 1 partial (0.5 up to 1.5), 0 poor (under 0.5). A command with no
// counted score has no entry; the caller gives it level 1 (no information is not a poor rating).
const JOB_FIT_STRONG = 1.5;
const JOB_FIT_POOR = 0.5;
const JOB_FIT_UNRATED = 1;
let ledgerDocCache = null;
function jobFitFor(jobId) {

  if (ledgerDocCache === null) ledgerDocCache = readJson(path.join(PLUGIN_ROOT, 'data', 'section-command-ledger.json')) || {};

  arr(isObj(doc.rows) ? doc.rows[jobId + '|*|*'] : null).forEach((r) => {

    const counted = typeof r.confidence === 'number' ? (floor === null || r.confidence >= floor) : r.source === 'ground-truth';
    if (!counted) return;
    out.set(stripCmd(r.command), r.score >= JOB_FIT_STRONG ? 2 : (r.score < JOB_FIT_POOR ? 0 : 1));
  });
