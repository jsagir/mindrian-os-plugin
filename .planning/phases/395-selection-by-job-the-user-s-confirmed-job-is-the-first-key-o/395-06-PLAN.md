## Owner rulings that govern this slice

1. The user's job comes first (BUILD-RULES 11).
2. "Job orders, Theo supplies" (BUILD-RULES 13).
3. One selector for everything a user sees: every proposal that reaches a user comes from the one selector, the per-turn block among them (BUILD-RULES 19).
4. Keep everything: no file and no rule is deleted. A quiet switch is allowed.

## Goal of this slice

On a turn where the per-turn hook prints an offer, and the one selector (`nextMoveForSection`) returned a runnable primary for the section in focus, the offer is that primary. When the selector returns no runnable primary, or does not run, the behaviour is exactly as it is now.

What a user gets: the command in `offer_next_step`, in the `Offer:` line, in the status line cue and in the offer history is the command that the brief and `suggest_next` name as the primary for the same section. Before this plan it was the selector id that is first in the registry file (see "The fault").

## What this slice does not do

* It does not change WHETHER an offer is made. Every rule that makes no offer runs as before, on the same numbers (decision D1).
* It does not change the selector (`lib/core/feyminto/next-move.cjs`), the ranker (`lib/workflow/f-selector-ranker.cjs`), the hook (`scripts/intent-classifier.cjs`), the presenter, the block text format, or any file of plan 395-05.
* It does not print alternatives. The hook prints 1 offer and no list of alternatives today (map row 13), so there is no list to put in the selector's order (decision D5).
* It does not change `fire_skill`, the dial card (the reach rows under the block), the `suggest_next` fields `suggestion` and `chain_offer`, or the act planner. Those are later plans (see "Three surfaces" and "Known limits").
* It deletes no rule. Section 2 says what each old rule still does.

## The fault, with proof

PROVEN on a scratch copy of `1538bbec3`. The real hook ran as a child process on a born fixture room (section `problem-definition` in focus, operator `DECISION_GATE`, job cue `find-problem`, a fresh governing thought). A preload file recorded `decide()`, `resolveOffer()` and `rankForSelector()`.

```text
selector (nextMoveForSection, cli):  /mos:root-cause, /mos:causal, /mos:beautiful-question   primary: /mos:root-cause
ctx.tierCandidates (in decide):      /mos:root-cause, /mos:causal, /mos:beautiful-question   source: feyminto_face
rankForSelector, top 3:              /mos:beautiful-question 0.500, /mos:causal 0.500, /mos:root-cause 0.500
resolveOffer -> offer_next_step:     /mos:beautiful-question
```

The 3 selector ids have the same ranker score (0.500). The fusion is by position in 2 lists: the registry order and the selector order. A selector id always scores higher than a command that is not a selector id (see map row 5), so the 3 selector ids take the 3 places. Among them the order of the rows in `data/command-registry.json` decides when the scores are equal (that order is near the alphabet). So the offer is the selector id that is first in the registry file. The same was seen for `market-analysis` (selector primary `/mos:macro-trends`, offer `/mos:analyze-timing`) and for 8 more turns of the table in section 4.

Measured in process with `decide()` on a born room: 14 nests, no goal and 13 goal jobs, 5 operator modes, 980 turns. In 338 turns the selector had a runnable primary and an offer was made. The offer was the primary in 166 of 338 (49 percent). It was a selector id in 338 of 338.

## 2. The rule

### The rule, in words

R1 (first writer, `resolveOffer`). After every abstention rule passed and after the tier 0 step kept the top row: when `ctx.tierCandidatesSource === 'feyminto_face'`, and the first id of `ctx.tierCandidates[0].items` has a row in the ranked list, that row is the offer. If that command is in rejection backoff, there is no offer.

R2 (second writer, the chain composer). When `ctx.tierCandidatesSource === 'feyminto_face'`, a chain proposal fills the empty offer only when its command is the selector primary. Else the offer stays empty and the rationale gets the sentence `Chain proposal held: the section selector names another primary.`

Quiet switch: the env `MINDRIAN_NAV_NO_PRIMARY_PIN=1` turns R1 and R2 off. The behaviour is then the behaviour of `1538bbec3` (PROVEN: turn q1, stdout byte-identical; new test A4, A7, B7, B9).

### Why it is the smallest

* The offer has 2 writers. Rules 5 to 9 of the map all act inside 1 call (`rankForSelector`), and its result has 1 reader on the offer path (`resolveOffer`). 1 guard at that reader covers the fusion and every pass after it. The chain composer is the other writer. 1 guard there covers it. No other place can change the offer in production.
* No old rule is edited. R1 is 1 added block after step 6 of `resolveOffer` plus 1 helper. R2 is 1 changed condition plus 1 helper. 72 added lines, 1 changed line, in 2 files.
* The other choices were larger or changed more. A change of the fusion (`_applyTierFusion`) changes the ranked list for every caller of the ranker and moves the margin, so it changes when an offer is made; it also breaks the pins of `tests/test-244-rrf-fusion.cjs`. A new order argument for the ranker needs 2 places (ranker and `resolveOffer`). A guard in `decide()` after line 1752 has no ranker row, so it cannot build the reason, the framework or the confidence.
* R1 reads the primary from the list that `decide()` already wrote. It does not call the selector again and reads no file.
