## Design

### A1: the chain fact stays, marked as held, with a true sentence for each class

`selectorHoldsChainOffer` (yes or no) becomes `selectorChainHold` (null or the class of the hold). The held branch writes, after the text that is already in the rationale:

```text
class 1 (not a selector id):
  Framework chain: X FEEDS_INTO Y (Brain confidence 0.85, held). Chain proposal held: the section selector names another primary.
class 2 (a selector alternative):
  Framework chain: X FEEDS_INTO Y (Brain confidence 0.85, held). Chain proposal held: the section selector names another primary. The selector lists the command of this chain step as an alternative.
class 3 (no command):
  Framework chain: X FEEDS_INTO Y (Brain confidence 0.85, held). Chain step held: this framework has no command to offer, and the section selector names the next move.
```

* The fact has the form of the sentence that the fill branch writes (`Framework chain: X FEEDS_INTO Y (Brain confidence n).`), with `, held` before the bracket closes. A reader of the `Why:` line sees which framework Theo names next and that no offer was made from it.
* The sentence of classes 1 and 2 starts with the words that the old checks A8 and B9 pin. No held text names a command, so check A8 ("stdout does not hold `/mos:lean-canvas`") holds, and no second writer proposes a command (ruling 19).
* `X` and `Y` are framework names from the chain line of the Brain face and from the completed-framework detector. The fill branch printed the same 2 names in the same line before plan 395-06. No user words and no room text are added.
* No field of the decision or of the trace is added or removed. `offer_next_step` is the same on every turn (PROVEN, 870 turns).
