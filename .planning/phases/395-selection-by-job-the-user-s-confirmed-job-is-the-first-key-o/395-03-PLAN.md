## Goal of this slice

On every user prompt in Claude Code, the hook gives the engine the section in focus and the surface. The engine then calls the one selector (`nextMoveForSection`) and the per-turn block is ranked with the selector's ids.

What a user gets: on a turn where the engine makes an offer, the offer in the `NAVIGATION DECISION` block comes from the commands the selector names for the section in focus. Before this plan it came from the registry order alone.

## What this slice does not do

* It does not make the offer equal to the selector's primary. 17 rules can change the offer (facts-07 item C5). That is plan 395-05.
* It does not change the order rule inside the selector (plan 395-04).
* It does not change how the hook finds the section in focus (`resolveActiveSectionPathForRoom`).
* It does not change `lib/core/navigation-engine.cjs`, the ranker, the block text format, or any file of plan 395-02.
* It does not add a time guard (see "Cost").

## Design

### The value of `section`

`decide()` needs the folder name of the section, as a slug, such that `path.join(ctx.roomDir, ctx.section)` is the section folder. The hook has the absolute `sectionPath` and the absolute `roomDir`. The value is `path.relative(roomDir, sectionPath)` when that text matches `/^[a-z0-9-]+$/`. In every other case the value is `undefined`, and `decide()` behaves as it does today (the condition at line 1150 is false).

The value is `undefined`, and not the non-slug text, on purpose. A non-slug text would give the reason `bad_section` and would also start the ledger block at `navigation-engine.cjs:1183-1207` with a text that is not a section name.

### What the hook knows at that point

* There is 1 section in focus for a turn, or none. `resolveActiveSectionPathForRoom(roomDir)` (`scripts/intent-classifier.cjs:1032`, called at line 2264) returns 1 absolute folder or `null`.
* Step 1: `<room>/.mindrian/active-section.json`, key `section`. The value can be absolute or relative to the room. The folder must exist. No shipped code writes this file (PROVEN by grep of the tree outside `tests`, `docs`, `.planning`: only `scripts/intent-classifier.cjs` and `scripts/context-monitor` name it, and both read it).
* Step 2 (the path a real room uses): the top-level folder, name not starting with a dot, whose `MINTO.md` has the newest change time.
* Step 3: `null`. A room that was just born has no `MINTO.md` in any section (PROVEN in a run), so it has no section in focus and the selector is not reached. This plan does not change that. It is a limit to record for a later plan.
* The focus is for the room, not for the session.

| Case | `sectionPath` | `section` after this plan | Selector |
|---|---|---|---|
| A core section, direct child of the room | `<room>/problem-definition` | `problem-definition` | runs |
| No section in focus | `null` | `undefined` | not reached, as today |
| Folder name is not a slug (`Custom_Notes`) | `<room>/Custom_Notes` | `undefined` | not reached, as today |
| Nested folder (`problem-definition/deep`) | `<room>/problem-definition/deep` | `undefined` | not reached, as today |
| Absolute path outside the room | that path | `undefined` (the relative path starts with `..`) | not reached, as today |

### The value of `surface`

`'cli'`. The hook is registered only in `hooks/hooks.json` (`UserPromptSubmit`, command `intent-classifier`), which Claude Code runs. An MCP host does not run it. With `'cli'` the selector takes as primary the first candidate that is runnable in Claude Code. Without the key, `decide()` would use `'mcp'` (line 1161).

### A second effect of `section`

When the selector has no runnable primary for the section, `decide()` runs the ledger block (`navigation-engine.cjs:1183-1207`). That block also needs `ctx.section`. So it also starts to run on hook turns. It reads the section job from `section-registry.getSectionJob`, not from the goal (facts-07 item C4). This is the shipped fallback; this plan does not change it.

## Cost

Method: the fixture room above, on `/tmp` (ext4, WSL2), 12 cores, load average 3. The real hook ran as a child process 15 times on the unchanged tree and 15 times on the changed copy. The preload file timed `decide()` inside the hook process. The parent timed the whole child process.

| Measure | Unchanged | Changed | Added |
|---|---|---|---|
| `decide()` inside the hook, median of 15 | 14.4 ms | 49.1 ms | 34.7 ms |
| `decide()` inside the hook, maximum of 15 | 20.0 ms | 54.5 ms | |
| Whole hook process, median of 15 | 239 ms | 256 ms | 17 ms |
| Whole hook process, maximum of 15 | 324 ms | 313 ms | |

Other numbers:
* The selector alone, called again in a warm process: median 1.04 ms, maximum 2.74 ms (50 calls). One warm call makes 122 file system calls (54 `readFileSync`, 45 `existsSync`, 22 `statSync`, 1 `readdirSync`).
* The selector alone in a fresh process: 100 ms median, 118 ms maximum (9 runs). Most of that is module loading. Of the file system calls in that run, 8 are on the room and 859 are on plugin files.
* Thus the added time in the hook is mostly module loading on first use (about 35 ms), and the room adds 8 file calls.

Result: the added time is 35 ms of a 1,200 ms budget (3 percent). It is not large. No bound is added in this plan.

Limit of this measure: the room was on a fast file system. `decide()` is synchronous, so the 1,200 ms timer in the hook cannot stop it. On a slow file system (Phase 394: WSL2 `/mnt/c`), the 8 room calls and the plugin file calls cost more. Proposal for Phase 394, not done here: at the context literal, set `section` to `undefined` when `Date.now() - startedAt >= NAV_HARD_TIMEOUT_MS`, the same rule as `shouldSkipReachPenalties`.
