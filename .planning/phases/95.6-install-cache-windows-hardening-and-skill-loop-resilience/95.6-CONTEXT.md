### Trigger evidence (locked from the tester's session)

### D-01: Windows long-path preflight in install.sh (fix bug #1)

**Symptom the Wave-2 tester hit:** `git clone` failed with `fatal: cannot create directory at '.planning/phases/92-refactor-constitution-and-trust-layer-formalizes-audit-driven-refactor-work-constitution-v1-1-directive-1-validation-directive-2-consolidation-directive-3-unidirectional-flow-trust-layer': Filename too long`. Windows MAX_PATH (260 chars) exceeded.

**Fix:** Add OS detection to install.sh. On Windows + Git Bash, run `git config --global core.longpaths true` BEFORE the clone. Surface a clear error if the user is on Windows without Git for Windows installed. Pair with a banner-line explanation so the user understands what was changed in their global git config.

**Why this alone is not enough:** Even with `core.longpaths true`, the .planning/phases/92-... directory name is a UX bug independently. See D-02.

### D-02: Rename the 92-trust-layer-refactor phase directory (hygiene + bug fix in one move)

**Current name:** `.planning/phases/92-refactor-constitution-and-trust-layer-formalizes-audit-driven-refactor-work-constitution-v1-1-directive-1-validation-directive-2-consolidation-directive-3-unidirectional-flow-trust-layer/`

**Length:** 189 characters at the leaf. Exceeds Windows MAX_PATH on its own when combined with a typical user home path.

**Fix:** Rename to `.planning/phases/92-trust-layer-refactor/`. Update all internal references in PLAN.md files, ROADMAP.md, the canon-phase-map, and any cross-phase wiki-links. The frontmatter and CONTEXT.md inside the directory carry the longer name as `full_slug:` for searchability.

**Acceptance:** `find .planning/phases -mindepth 1 -maxdepth 1 -type d | awk -F/ '{print length($NF), $NF}' | sort -rn | head -3` shows no leaf-name above 60 characters.

### D-03: Harden install.sh skill-loop (fix bug #2)

**Symptom the Wave-2 tester hit:** `cp: cannot stat '/c/Users/GaryLaben/.claude/plugins/mindrian-os/skills/mullins-scaffold//SKILL.md': No such file or directory`. The cp loop hits `set -euo pipefail` and the entire script exits, leaving agents/, hooks, settings.json, and the larry-extended default agent registration unfinished.

**Root cause:** `skills/mullins-scaffold/` exists in the repo as a directory but lacks `SKILL.md`. The install.sh skill-loop assumes every skill subdirectory has SKILL.md present.

**Fix (two-part, both required):**

(a) **Audit and backfill canonical skills.** Run `find skills -mindepth 1 -maxdepth 1 -type d -exec test ! -f {}/SKILL.md \\;` to enumerate every skill directory missing SKILL.md. Backfill the canonical ones (currently `skills/mullins-scaffold/` is known broken; verify there are not others).

(b) **Defensive guard in install.sh.** Pre-filter the skill-loop to only iterate over skills with SKILL.md present. For any skill skipped, print a yellow warning to stderr (`WARN: skipping skill <name>: no SKILL.md`). The script continues. Skills are non-critical for first-load; commands and agents are the load-bearing surface.

**Why both:** (a) fixes the data, (b) fixes the contract. Without (b), a future drift recreates the same failure mode. Without (a), the warning fires on every install and trains testers to ignore warnings.

### D-04: Manual-completion fallback section in README

**Why:** the tester's CC manually completed the install after install.sh halted. The recovery steps it executed (agent symlinks + settings.json fragments with hook + larry-extended default + MINDRIAN_OS_ROOT env var) are not currently documented anywhere. Next tester whose install.sh halfway-fails has to either reproduce the tester's CC's improvisation or contact the maintainer.

**Fix:** Add a `## Manual Recovery` section to README.md that documents the exact PowerShell + symlink commands needed to complete an install that halted partway. Reference the tester's CC transcript as the canonical recovery template. Keep it short (under 30 lines) and copy-pasteable.

### D-05: Publish @mindrian/os to npm in lockstep (fix bug #3)

**Symptom the Wave-2 tester hit:** `npx @mindrian/os@next` returned `404 Not Found - GET https://registry.npmjs.org/@mindrian%2fos`. The package has never been published.

**Root cause (corrected 2026-05-10 per code review):** `scripts/release.sh` has Steps 1-11. There is NO Step 9.5. The npm publish gate documented in memory entry `feedback_release_lockstep_npm.md` was never implemented in the release script despite the memory claim. `grep "npm publish\|@mindrian" scripts/release.sh` returns 0 matches. This is a missing-feature, NOT a broken-feature. v1.13.0-beta.1 through beta.8 all shipped without the npm side because the gate that was supposed to enforce lockstep publishing did not exist.

**Fix (sequenced):**

(1) ADD Step 9.5 to scripts/release.sh as the canonical npm publish gate. The gate runs after `git push` (Step 9) and before local cache update (Step 10). Implementation: `npm publish --tag <next|latest>` with @next for `-beta./alpha./rc./next.` suffixes and @latest for clean X.Y.Z. Surface explicit error if publish fails so future releases halt rather than silently shipping unpublished.

(2) Manually publish v1.13.0-beta.9 (the version this phase ships) to recover the lockstep contract going forward. Use the new Step 9.5 implementation as the publish vehicle. The legacy beta.1-beta.8 versions stay unpublished; document the gap honestly in CHANGELOG.

(3) Until step (2) lands, REMOVE the npx command from the install site. The site at mindrianos-install-site.vercel.app currently advertises `npx @mindrian/os@next` as the "fastest path" with a copy button. The site cannot keep promising what the registry cannot serve.

**Acceptance:** `npm view @mindrian/os@next version` returns the current beta version. The install site either advertises the working npm path or removes the npm block entirely.

### D-06: Fix the BSL-1.1 mislabel everywhere

**Symptom (re-grounded 2026-05-10 per code review):** The original CONTEXT claim that the tester's CC flagged BSL-1.1 in two separate sessions is unsupported by `[private tester archive]` (zero hits for "BSL" or "open[- ]source" in the canonical tester record). The actual urgency driver is RESEARCH.md F-06 (the institutional adoption pipeline): NATO Defense College Rome IT review, Hopkins curriculum review committee, and Hebrew University + Israeli Innovation Authority programs will all audit the license language at scale before adopting MindrianOS for faculty/student use. "BSL-1.1 (open source)" in any plugin-shipped doc is an institutional veto risk for any of these surfaces. Cautious AI tooling (Claude Code, ChatGPT, Gemini) will also catch the mislabel in real time during install attempts, which compounds the risk on a per-tester basis.

**Root cause:** Marketing copy inherited "open source" framing from earlier project versions. BSL-1.1 is not open source; it is source-available with a time-deferred OSS conversion clause. Cautious AI tooling (Claude Code, ChatGPT, Gemini) will all flag this the same way.

**Fix:** Find-and-replace across the repo + install site + tester docs:

- `grep -rln "open[- ]source" docs/ README.md install.sh .claude-plugin/ scripts/` -> audit each match in context, replace with "source-available" where it describes BSL-1.1.
- Same audit for docs/testers/outbox/ and the install site repo (~/mindrianos-install-site/).
- Add a one-line license clarification to README.md: "MindrianOS is source-available under BSL-1.1, not open source."

**Acceptance:** `grep -rln "BSL.*open.source\\|open.source.*BSL" .` returns 0 hits.

### D-09: Statusline registration is missing on completed installs (added 2026-05-09)

**Symptom (two confirmed sites):**

- the Wave-2 tester's machine after his 2026-05-08 install: statusline does not render at the bottom of Claude Code. The expected line `⬡ MindrianOS-Plugin <room-name> <context%>` is absent.
- Jonathan's "other machine" (separate install, not the canonical dev workspace): same symptom. Statusline silent.

Both machines completed install enough to have commands and Larry, but the bottom-of-terminal statusline that the SessionStart UI contract promises (per the v1.12.5.1 first-session check that prompts users with "Look at the bottom of your terminal. Do you see a line starting with ⬡ MindrianOS-Plugin?") never renders.

**Root cause (suspected, to confirm in plan-phase):**

install.sh writes a `statusLine` block into `~/.claude/settings.json`. If install.sh halts mid-loop (D-03 bug), the statusline registration step never runs because it sits AFTER the skill-loop in the script. the tester's manual recovery via his CC (FEEDBACK.md 2026-05-09) wrote hooks + larry-extended default agent + MINDRIAN_OS_ROOT env var but did NOT include a statusLine entry. Net effect: any tester whose install.sh halted before the statusline step is left with a half-installed UI surface and no error to indicate it.

For Jonathan's machine: separate vector. The 2026-05-06 dogfood `/mos:doctor --all --json` run found install dir entirely missing. The atomic-recovery path (Phase 95.2) restores the cache to install dir, but if the recovery does not also re-stamp the user's `settings.json` statusLine block, the recovered install is structurally incomplete in the same way as a halted-install.sh case.

**Fix (sequenced):**

(1) Verify install.sh actually writes the statusLine block. If not, add it. If yes, document where in the script it lives so D-03 hardening preserves the order.

(2) Make statusline registration idempotent and independent. It should not depend on the skill-loop or any other non-statusline step. A function `register_statusline()` that runs FIRST in the install order, after node + git preflight, before any cp loops.

(3) Extend `/mos:doctor` to detect missing statusLine block as a class of drift (call it class G or whatever fits the existing taxonomy). `/mos:doctor --statusline-visibility` already exists per the v1.12.5.1 first-session check; verify it actually surfaces and offers --fix.

(4) `/mos:doctor --fix` should write the statusLine block when missing, idempotently. Same pattern as the SessionStart hook registration in Phase 95.2.

**Acceptance:**

- `cat ~/.claude/settings.json | jq '.statusLine'` returns the canonical MindrianOS statusLine block on a fresh install AND on a recovered-from-cache install AND on a manually-completed install.
- `/mos:doctor --statusline-visibility` returns `ok` after install. Returns `missing` and offers `/mos:doctor --fix` when block is absent.
- A fresh `claude` session in any folder shows the statusline at the bottom within 1 second of startup.

**Cross-references:**

- v1.12.5.1 SessionStart first-session-check copy (the prompt that surfaces the visibility question to users)
- Phase 95.2 atomic-recovery (related: recovery should re-stamp statusLine)
- Phase 88.1 statusline / mos:status / SessionStart banner LOCAL-context surfaces (where statusline rendering originally landed; v1.10.15)

### D-10: Subagent capability parity for skills + MCP (added 2026-05-10 per leading-approach packaging research)

**Why this exists:** Older Anthropic guidance asserted that "subagents auto-receive MCP tools but skills must be explicitly loaded." Verified 2026-05-10 against current Anthropic subagent docs (code.claude.com/docs/en/sub-agents): subagents accept BOTH `mcpServers` and `skills` as first-class frontmatter fields. Skills declared in subagent frontmatter inject FULL content at startup (not just description). Subagents can also invoke unlisted project / user / plugin skills through the Skill tool. The MCP-vs-skill choice for any specific capability rides on Layer 1/2/3 fit, NOT on subagent reachability.

**Fix:** Document this parity explicitly in Phase 95.6 plans and in any future MindrianOS subagent design. Where a subagent needs Brain access, declare `mcpServers: [mindrian-os]` in its frontmatter. Where it needs methodology framing, declare `skills: [...]` in its frontmatter. Both paths are first-class and equivalent for subagent access.

**Acceptance:** All 8 MindrianOS subagents in `agents/*.md` have explicit `mcpServers` and/or `skills` frontmatter fields where they need Brain or methodology access. No subagent relies on the implicit-MCP-inheritance pattern that was true in older Anthropic versions.

**Cross-references:** 95.6-PACKAGING-RESEARCH.md Section 2 (Architecture); Anthropic subagent docs at code.claude.com/docs/en/sub-agents.

### D-11: Reserved marketplace names + Deferred Tool Loading awareness (added 2026-05-10 per leading-approach packaging research)

**Why this exists:** Two compliance + future-proofing items surfaced during the 2026-05-10 packaging research:

(a) Anthropic blocks reserved marketplace identifiers: `claude-code-marketplace`, `claude-code-plugins`, `claude-plugins-official`, `anthropic-marketplace`, `anthropic-plugins`, `agent-skills`, `knowledge-work-plugins`, `life-sciences`, plus impersonation patterns (`official-claude-plugins`, `anthropic-tools-v2`, etc.). Every MindrianOS surface name must clear this list at release time.

(b) Anthropic shipped Deferred Tool Loading in 2026: MCP tool names load at startup; full schemas load on demand via ToolSearch. For plugins with 50+ MCP tools, this cuts context overhead by an order of magnitude. MindrianOS currently has 1 MCP server with a small tool surface; future tool growth on the mindrian-os MCP should design for deferred loading by declaring tools that fetch their schema on demand rather than at startup.

**Fix:** 

(a) Add a release-gate compliance check: `grep -E "(claude-code-marketplace|claude-code-plugins|claude-plugins-official|anthropic-marketplace|anthropic-plugins|agent-skills|knowledge-work-plugins|life-sciences|official-claude|anthropic-tools-v2)" .claude-plugin/plugin.json marketplace.json | grep -v "comment\|note"` should return zero hits where these strings appear as identifiers (not just mentions in comments).

(b) Document in `mcp-server-brain/CLAUDE.md` (or equivalent) the Deferred Tool Loading pattern. When new Brain MCP tools are added, prefer the schema-on-demand pattern over schema-at-startup. Include a check at release time: `mcp-server-brain` should never declare more than ~10-15 tools at startup; additional capability should be reachable via ToolSearch + on-demand schema fetch.

**Acceptance:** 

(a) Reserved names check returns zero hits.

(b) `mcp-server-brain` declares at most 10-15 tools at startup; any documented future tools beyond that count are designed for deferred loading.

**Cross-references:** 95.6-PACKAGING-RESEARCH.md Sections 5 + 2; Anthropic plugin marketplace docs at code.claude.com/docs/en/plugin-marketplaces (reserved names list); alexop.dev "Understanding Claude Code's Full Stack" 2026 article (Deferred Tool Loading reference).
