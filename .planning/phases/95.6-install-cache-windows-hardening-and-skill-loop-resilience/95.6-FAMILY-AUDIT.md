# Phase 95.6 Family Audit -- Install-Cache Failure Family vs the Wave-2 tester Findings

## Executive summary

The install-cache failure family has accumulated **four incidents, seven drift classes, six phases, and approximately 11 distinct fixes** between 2026-04-13 and 2026-05-09. Each incident produced new defenses for the layer that broke. None of the prior phases generalized across failure modes: each class-specific fix passed its own regression test while the next incident exposed a different layer.

The the Wave-2 tester process (2026-05-08 to 2026-05-09) is qualitatively different from cases #1-3. Cases #1-3 were RECOVERY incidents -- the install once worked, drifted from a working state, and needed to be restored. Case #4 is an INSTALL incident -- the install never worked on the tester's machine to begin with. Every prior phase assumed the install path itself was reliable and built recovery on top of that assumption. the tester's session breaks the assumption.

**The audit's central finding:** Phases 93, 94, 94.1, 95, 95.1, 95.2 collectively address recovery but do not address install correctness. Phase 95.6 must own the install path itself, or the family will keep producing incidents at a layer the existing fixes cannot reach.

## 3. Pattern analysis

Three patterns recur across the family.

### Pattern A: each fix is class-specific; defenses do not generalize across failure modes

Phase 95.2 atomic recovery removes the half-done state from EXISTING during recovery. It does nothing for an install that never started recovering because install.sh died at line N out of M. Phase 93 /mos:doctor checks for version drift. It does not check for shell-environment correctness. Phase 95.1 added five new drift classes but each is a discrete check; none of them ask "did the most recent install run complete?" The drift classes detect post-hoc state divergence; they do not detect mid-install incompleteness.

**Implication for 95.6:** add a ROOM-AS-RECEIPT pattern at the install layer too -- the install must produce a receipt that proves all stages ran. Without that receipt, the install state is unverifiable from the outside.

### Pattern B: detection lags by exactly one incident

Every incident in the family was detected by a HUMAN (Lawrence x2 plus Jonathan x1 plus the Wave-2 tester x1), not by automated monitoring. Each phase ships a defense for the LAST incident:

- Case #1 (Lawrence catches drift) -> Phase 93 ships /mos:doctor (would have caught case #1)
- Case #2 (Jonathan catches drift) -> Phase 95.1 extends doctor with B/C/D/E/F (does not catch case #3)
- Case #3 (Jonathan catches missing install) -> Phase 95.2 ships preflight (does not catch case #4)
- Case #4 (the tester's CC catches install failure) -> Phase 95.6 in flight (does it catch case #5?)

The pattern is structurally tilted toward late detection. The fix for case N detects case N. Case N+1 surfaces a layer the case-N fix never considered.

**Implication for 95.6:** the goal is not to fix the tester's six bugs (though that is necessary). The goal is to make case #5 detectable BEFORE the next tester hits it. Plans must include forward-looking detection -- pre-install checks, post-install receipts, dogfood-on-fresh-machine cadence.

### Pattern C: the cure-via-install.sh paradigm has a ceiling; scripts reach upstream causes only by operating OUTSIDE the install.sh boundary

(Reframed 2026-05-10 per code review. Original framing said "scripts can't reach upstream causes" which overreaches: R-03 cross-shell wrapper and R-05 settings.json allowlist below are themselves scripts that DO reach upstream. The honest framing is that install.sh ITSELF cannot reach these layers; cures must operate from a different surface.)

Cases #1-3 were all install.sh-internal-fixable: workspace guard, /mos:doctor + --fix, atomic-swap recovery in scripts/doctor.cjs (which uses `fs.cpSync` since Phase 95.2, not shell `cp -aT`; the `cp -aT` exec-shell pattern was specifically removed for Windows-functionality reasons). Case #4 reveals causes upstream of install.sh:

- **npm publish** requires the npm registry, an external system; reachable from `scripts/release.sh` Step 9.5 (which does not yet exist; see D-05) but NOT from inside install.sh.
- **Long-path failure** requires git client config (`core.longpaths`); reachable from a pre-install preflight wrapper that runs BEFORE install.sh, but not from install.sh itself which runs INSIDE the broken-clone state.
- **Skill-loop halt** requires a missing data file (skills/mullins-scaffold/SKILL.md); reachable from a release-gate test or pre-commit hook, but the install.sh skill-loop fires at install time, AFTER the data has shipped.
- **Permission fatigue** requires Claude Code-side decisions; partially reachable from a settings.json allowlist (R-05) which is NOT inside install.sh but adjacent to it.
- **PowerShell-vs-CMD** requires shell-aware logic; reachable from a thin wrapper script that detects the launching shell BEFORE invoking install.sh, but not from install.sh which runs INSIDE Git Bash and cannot see what spawned it.

**Implication for 95.6:** at least three plans must operate OUTSIDE the install.sh boundary: scripts/release.sh extension (R-06 / D-05), pre-install preflight wrapper (R-02 + R-03), and release-gate data-integrity check (R-04). The install site must also stop advertising paths that do not work; that is a separate repo (mindrianos-install-site) that scripts/release.sh has no control over today and needs its own CI gate (R-06).

## 4. Gap detection: what no phase has yet addressed

After the family map and phase matrix, six categories of gap remain:

### Gap 1: Install correctness is unverified

No prior phase verifies that an install actually completed correctly on a fresh machine. /mos:doctor checks state AFTER install. SessionStart preflight checks state AFTER plugin load. Neither checks "did install.sh exit with all 14+ steps successful in order?"

The install.sh script uses `set -euo pipefail`. Any single step failure halts the script. The remaining steps are silently skipped. the tester's session: install.sh halted at the skill-loop on step ~7 of ~14. Steps 8-14 (agents registration, hooks, statusLine, MINDRIAN_OS_ROOT) never ran. No surface anywhere reported "install incomplete."

**What's needed:** install.sh should write an install-receipt at completion (e.g., `~/.claude/plugins/mindrian-os/.install-receipt.json`) listing every step that ran. /mos:doctor should check the receipt against the expected step list. SessionStart preflight should warn if receipt is missing or incomplete.

### Gap 2: External dependencies are assumed available

install.sh assumes `git`, `node`, `npm`, `bash`, and the npm registry are all present and functional. the tester's case proved one of these (npm registry's @mindrian/os) is not, even though the install site assumed it was. No prior phase has audited what install.sh assumes is true.

**What's needed:** a pre-install dependency audit -- a script that lists every external dependency the install needs and verifies presence + version + reachability. Run before install.sh. Halt with a clear message if anything fails.

### Gap 3: Cross-shell / cross-OS ergonomics

install.sh is bash-only. Windows users must invoke through Git Bash. the tester's session showed PowerShell rejection of the same logic. Mac and Linux are presumed to work (untested at scale on this exact install path in 2026). No prior phase has tested install.sh across all three OS targets per release.

**What's needed:** matrix testing -- a set of fresh-VM install runs (Windows + Mac + Linux + Cowork) per release gate. Even one tester per OS per release would have caught the tester's case #4 a week earlier.

### Gap 4: Repo data integrity (the SKILL.md gap)

The skills/mullins-scaffold/ directory exists in the repo but lacks SKILL.md. install.sh's cp loop assumes every skill subdirectory has SKILL.md. The two diverged silently. No prior phase audited skill directory completeness.

**What's needed:** a pre-commit hook or release-gate test that asserts every skills/* directory has SKILL.md. Block commits that violate. Block releases that ship with violations.

### Gap 5: Install ergonomics (permission-prompt fatigue)

Lawrence has trained himself to "always hit 2" without reading. the Wave-2 tester clicked yes 10+ times during install. This is not a bug per se, but it is a security-theater problem -- if testers are trained to autopilot through prompts, the prompts no longer serve their purpose. Worse, the prompts make the install feel hostile to non-technical testers.

**What's needed:** either (a) reduce prompt count by bundling commands, or (b) ship a settings.json permission allowlist for install paths (so only the first prompt asks for blanket approval), or (c) document `--dangerously-skip-permissions` as the explicit "I trust this install" path with clear scope warnings.

### Gap 6: Marketing copy lies under load

The install site advertises `npx @mindrian/os@next` as the canonical "fastest path" with a copy button. The package does not exist on npm. The site also calls BSL-1.1 "open source" in places. Both are credibility flags that any cautious AI tooling (Claude Code, ChatGPT, Gemini) will catch in real time.

**What's needed:** install site must be release-gated -- it cannot promise paths that do not work. The CI for the install site repo should grep for forbidden phrases (open source describing BSL-1.1) and forbidden install commands (npx of unpublished packages). Fail builds that violate.

## 5. Recommendations -- what 95.6 must address that prior phases assumed away

These are recommendations to feed into plan-phase when it eventually runs. Each recommendation maps to one or more decisions D-XX in 95.6-CONTEXT.md and addresses a gap from section 4 above.

### Recommendation R-01: Install receipt + completeness check

Plan 95.6-NN. Add an install-receipt write at the end of install.sh: `~/.claude/plugins/mindrian-os/.install-receipt.json` listing every step that ran with timestamps and exit codes. Extend /mos:doctor with a class H ("install incomplete") that checks the receipt against the expected step list. Extend SessionStart preflight to warn if receipt is missing or incomplete.

Maps to: D-03 (skill-loop hardening, but generalizes the principle), D-09 (statusline registration verification).
Addresses: Gap 1 (install correctness unverified).

### Recommendation R-02: Pre-install dependency audit

Plan 95.6-NN. Before install.sh runs its work, it should verify: `git --version` + `node --version` + `npm --version` + `bash --version` + `curl https://registry.npmjs.org/-/ping` (network check) + `git config --get core.longpaths` (Windows only, set to true if missing). Halt with a clear table-formatted report of which dependencies are present and which are missing.

**Timing-surface distinction (added 2026-05-10 per code review):** R-02's pre-install dependency audit runs BEFORE install.sh executes its work. This is a different timing surface from Phase 95.2's SessionStart preflight (`scripts/preflight-doctor.cjs`, the 8th SessionStart entry in `hooks/hooks.json`), which runs AFTER install completes, on Claude Code session start, and warns if the resulting install state is broken. Both surfaces are required and orthogonal: R-02 catches "install never started cleanly" (the tester's case #4); 95.2 preflight catches "install drifted post-completion" (cases #2-3). Plans for R-02 must NOT re-architect what 95.2 already shipped.

Maps to: D-01 (Windows long-path preflight is a sub-case of this).
Addresses: Gap 2 (external dependencies assumed available).

### Recommendation R-03: Cross-shell wrapper

Plan 95.6-NN. Ship a thin wrapper that detects PowerShell vs CMD vs bash vs zsh and invokes install.sh with appropriate quoting + path translation. On Windows, the wrapper is a `.cmd` file that auto-locates Git Bash and calls install.sh through it. On Mac / Linux, the wrapper is a no-op pass-through. The wrapper is the canonical install entrypoint going forward; install.sh becomes the implementation, not the entrypoint.

Maps to: D-01 (Windows preflight + shell detection is a sub-case).
Addresses: Gap 3 (cross-shell ergonomics).

### Recommendation R-04: Repo data-integrity gate

Plan 95.6-NN. Add a release-gate test that asserts every `skills/*/` directory has a SKILL.md. Add a pre-commit hook with the same assertion. Backfill missing files in canonical skills (`skills/mullins-scaffold/SKILL.md` is the known-broken one as of 2026-05-09). Add a defensive pre-filter in install.sh's cp loop that warns and continues on missing SKILL.md (so future drift produces a soft warning, not a hard halt).

Maps to: D-03 (skill-loop hardening).
Addresses: Gap 4 (repo data integrity).

### Recommendation R-05: Install permission allowlist

Plan 95.6-NN. Investigate Claude Code's permission allowlist mechanism (settings.json `permissions.allow` matchers per CLAUDE.md). Ship a recommended allowlist for install paths (`Bash(git clone:*)`, `Bash(bash install.sh:*)`, `Write(*~/.claude/*)`, etc.) so install runs as a single approval rather than 10+. Document the allowlist in README's manual-recovery section. As a fallback, document `--dangerously-skip-permissions` with explicit scope warnings.

Maps to: D-03 sub-decision (permission ergonomics, surfaced in 95.6-RESEARCH.md).
Addresses: Gap 5 (install ergonomics).

### Recommendation R-06: Install site CI gate

Plan 95.6-NN. The install site repo (`~/mindrianos-install-site/`, separate from the plugin repo) needs a CI gate that:
- greps for "BSL-1.1.*open[- ]source" or "open[- ]source.*BSL" -- fails builds with hits
- verifies `npm view @mindrian/os@next version` returns a non-error string -- fails builds if the advertised npm path is broken
- The plugin repo's `scripts/release.sh` Step 9.5 (which does NOT yet exist; verified 2026-05-10 -- script has Steps 1-11 with no `npm publish` invocation anywhere) must be ADDED as the canonical npm publish gate, then verify the install site CI is green before tagging the release.

Maps to: D-05 (npm publish lockstep) + D-06 (BSL-1.1 mislabel sweep).
Addresses: Gap 6 (marketing copy lies under load).

### Recommendation R-07: File the case #4 autopsy

Independent of plans. Write `[private case archive]` capturing the full case #4 narrative. Pattern matches the existing 2026-04-13, 2026-04-28, 2026-05-06 autopsies in structure. This is the canonical record going forward and the trigger for the eventual case #5 (which will inevitably surface, given Pattern B).

Addresses: documentation gap. Required before 95.6 ships per the family's autopsy convention.

### Recommendation R-08: Cross-platform tester matrix

Out-of-scope for 95.6 plans, but proposed for the next milestone. Establish a matrix of fresh-VM install tests per OS (Windows 11 + Mac + Linux + Cowork) per release gate. Even one tester per OS per release would have caught case #4 a week earlier. Could be automated via Vercel + cloud VMs or could stay manual (a small group of testers across OS targets, run install on every beta).

Addresses: Gap 3 (cross-shell ergonomics, structural).

## 6. Patterns the audit DID NOT find but expected to

Three things the audit looked for and did not surface, listed for completeness:

### Anti-finding 1: No coordinated milestone-level theme

The install-cache failure family has accumulated four cases across three months without a milestone-level theme uniting the work. v1.11.1 hotfix, v1.11.2 hotfix, v1.13.0-beta.6 atomic-swap, v1.13.0-beta.9 (planned, 95.6) -- these read as independent emergencies. There is no "v1.X install-cache stability" milestone that owns the family end-to-end.

This is not a fix-needed item. It is a strategic question: is the family big enough to get its own milestone, or does it stay folded into v1.13.0 + v1.14.0 as opportunistic fixes? The audit cannot decide; the founder + Lawrence should.

### Anti-finding 2: No regression test asserting "the previous incident cannot recur"

Each case shipped fixes. Most cases shipped tests for those fixes. None of the phases includes a test that asserts "the symptom of the previous incident is undetectable on this build." For example, no test simulates "delete ~/.claude/plugins/mindrian-os entirely, then run /mos:doctor --fix" and asserts a working install is restored. The closest is `tests/test-doctor-atomic-swap.cjs` (Phase 95.2) but that simulates a `cp` mid-failure, not a wholesale missing install.

**Recommendation:** out-of-scope for 95.6 plans, but a Wave-3 candidate: a `tests/test-install-family-regression.cjs` that simulates each historical incident and asserts current /mos:doctor + install.sh handles them.

### Anti-finding 3: No tester-instrumented telemetry

The Brain telemetry column-name mismatch from case #2 was caught by accident (Jonathan was building a tester onboarding email and noticed the dashboard was empty). After the fix, telemetry works -- but no install-side telemetry exists. We have zero data on:
- How long install.sh takes per OS
- How often install.sh halts mid-run vs completes
- Which step is the most common halt point
- Cross-tester install-success rate

This is not actionable in 95.6 but should be filed as a v1.14 candidate. Telemetry must be Canon Part 8 compliant -- methodology / install metadata only, never user content.
