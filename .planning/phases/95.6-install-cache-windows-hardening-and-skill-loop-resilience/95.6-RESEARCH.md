## 2. Per-Decision Research

### D-01: Windows long-path preflight in install.sh

**Confirmed live (call ~28:21):**

> Gary: "Fail command, couldn't create directory."
> Jonathan: "Same thing it won't mind."

This is the long-path failure firing again on the second clone attempt. Gary's CC fixed it on attempt 1 with `git config --global core.longpaths true`, but the partial-directory state from earlier broke the second clone. **The bug fires twice in one session** if the user does any retry-after-failure dance.

**New signal -- shell variability:**

> Gary started in PowerShell. The install command failed.
> Jonathan: "Yeah, we need terminal." (~6:16)
> Gary: "Let me, uh, do a different share and then..."
> Then Gary opened CMD via "Start, write CMD" (Jonathan's instruction at ~34:18) and the install proceeded.

**Implication:** PowerShell vs CMD on Windows behave differently for the install path. Either:

(a) The `.sh` script invocation through Git Bash needs different escaping in PowerShell vs CMD.
(b) PowerShell's execution policy was blocking something.
(c) The path-quoting (`"$HOME/.claude/..."`) parses differently between shells.

**Recommendation for D-01:** Detect both PowerShell AND CMD invocation, document both paths. Bias the README toward CMD as the canonical Windows shell because that worked for Gary live. Or: ship a PowerShell-native install script alongside install.sh so users do not have to invoke Git Bash from inside PowerShell.

### D-02: Rename 92-trust-layer-refactor

**Confirmed-on-confirmed:** the 189-char leaf name is the proximate cause of the long-path failure. Already locked in CONTEXT.md. No new signal from the call.

**Plan implication:** D-02 is the single most leveraged fix in 95.6. It touches one rename + reference updates and removes the entire failure class for any future Windows tester regardless of whether they enable longpaths. Should be Wave-1 priority.

### Tier 1 decision -> behavioral contract -> validation

#### D-02 -- Rename `92-...` phase dir to `92-trust-layer-refactor`

1. **Behavioral contract.** No leaf directory name under `.planning/phases/` exceeds ~60 chars, so a fresh `git clone` into a typical Windows home path never hits MAX_PATH because of phase 92. No PLAN/ROADMAP/canon-map cross-reference to the old long path is left dangling. Git rename-detection preserves the directory's history.
2. **How it gets validated.** Test type: **unit (repo-state assertion)** plus a **grep dangling-reference check**. File: `tests/test-92-rename-no-long-leaves.cjs` (or fold into the existing `tests/test-canon-crossref-completeness.cjs` pattern). Verification commands (each must hold; suite exits 0):
   - `find .planning/phases -mindepth 1 -maxdepth 1 -type d | awk -F/ '{print length($NF)}' | sort -rn | head -1` -> value <= 60
   - `grep -rln --color=never "92-refactor-constitution-and-trust-layer" . --exclude-dir=.git` -> 0 hits outside the rename's own Searchability Note
   - `git log --follow -- .planning/phases/92-trust-layer-refactor/ | head -1` -> non-empty (rename detected, history preserved)
3. **Nyquist sampling note.** Mechanical, fully automatable, no runtime state. **Lowest coverage need** of the Tier 1 set -- one repo-state assertion is sufficient. Does NOT graceful-degrade: a missed dangling reference re-introduces the failure class, so the dangling-ref grep is mandatory, not optional.

#### D-03 -- install.sh skill-loop hardening (audit + backfill + defensive pre-filter)

1. **Behavioral contract.** (a) Every `skills/*/` directory in the repo has a `SKILL.md` (data fixed). (b) install.sh either fully registers (agents, hooks, larry-extended default, `MINDRIAN_OS_ROOT`, statusLine block) or, if a skill dir is structurally incomplete, prints `WARN: skipping skill <name>: no SKILL.md` to stderr and **continues** -- it never halts mid-loop, never leaves a half-written `settings.json`. There is no path where `set -euo pipefail` aborts the script on a missing skill file.
2. **How it gets validated.**
   - Test type 1: **release-gate data-integrity unit.** File: `tests/test-skills-have-skill-md.cjs`. Command: `find skills -mindepth 1 -maxdepth 1 -type d -exec test '!' -f {}/SKILL.md ';' -print` -> empty output. Wire into `tests/run-all.sh` so it blocks the release gate. (Prerequisite: backfill `skills/mullins-scaffold/SKILL.md`, the known-missing file.)
   - Test type 2: **hermetic shell-fixture for install.sh.** File: `tests/test-install-sh-skill-loop.sh`. Fixture: scratch repo clone with a deliberately SKILL.md-less skill dir injected; run `bash install.sh` against a `/tmp` fake `~/.claude`. Assert: exit code 0; stderr contains the `WARN: skipping skill` line; `settings.json` afterward has the agent block, hooks block, larry-extended default, `MINDRIAN_OS_ROOT`, and `statusLine` all present (this overlaps D-09's check by design -- a halt before the statusLine step is exactly what broke Gary).
3. **Nyquist sampling note.** **Highest coverage need of the entire phase.** This is "the bug that broke Gary live" on a screen-shared call, reproduced twice. Sample it both ways (data-integrity AND install-completion) and run the install-completion fixture on every commit touching `install.sh` or `skills/`. Does NOT graceful-degrade -- a regression here is a silent broken install for the next tester.

#### D-01 -- Windows long-path preflight in install.sh (OS detection + `core.longpaths`)

1. **Behavioral contract.** On Windows + Git Bash, the install path runs `git config --global core.longpaths true` (with a banner line explaining the global-config change) before any clone that could exceed MAX_PATH. On non-Windows it is a no-op pass-through. On Windows without Git for Windows, install fails with a clear, named error rather than a cryptic clone failure. A retry-after-failure does not re-trigger the long-path error (partial-clone state is cleaned, or the longpaths config is already in place). A cold Windows clone completes without a long-path error caused by phase 92.
2. **How it gets validated.**
   - Test type: **hermetic shell-fixture with OS-detection injection.** File: `tests/test-install-preflight-longpath.sh`. Fixture: stub the OS-detection variable (e.g. `MOS_TEST_FORCE_OS=windows`) and a fake `git` on `PATH` that records the args it was called with. Assert: when forced-Windows, `git config --global core.longpaths true` is among the recorded calls and the banner line is emitted; when forced-non-Windows, it is not. Assert the "Git for Windows missing" branch emits the named error and exits non-zero. Verification: `bash tests/test-install-preflight-longpath.sh` exits 0.
   - Cross-shell: if D-01's plan ships a wrapper, the same fixture also asserts the install entrypoint behaves under both a `cmd`-style and a `powershell`-style invocation env (per RESEARCH section D-01's PowerShell-vs-CMD finding). Otherwise the cross-shell check is a manual step in the cold-machine gate below.
3. **Nyquist sampling note.** **High coverage need** -- "the next Windows tester hits this." The fixture simulates Windows on a Linux CI box (OS-detection injection) so it runs every commit, but the *true* signal is the cold-machine manual gate (a real Surface-class Windows box). Partially graceful-degrades: D-02's rename removes the *phase-92* instance of the failure even if D-01's preflight regresses, so D-02 is a defense-in-depth backstop -- but D-01 still needs its own automated coverage because other long paths can appear later.

#### D-05a -- Add Step 9.5 npm publish gate to `scripts/release.sh`

1. **Behavioral contract.** `scripts/release.sh` contains a Step 9.5 that runs after `git push` (Step 9) and before the local cache update (Step 10), invokes `npm publish` with `--tag next` for `-beta./alpha./rc./next.`-suffixed versions and `--tag latest` for clean `X.Y.Z`, and **halts the release with an explicit error if publish fails** (no silently-shipping-unpublished). After beta.9 is cut, `npm view @mindrian/os@next version` returns the current beta version (recovery publish done); until then the install site does not advertise `npx @mindrian/os@next`.
2. **How it gets validated.**
   - Test type 1: **unit / script-shape assertion (no live registry).** File: `tests/test-release-npm-gate.sh`. Assert: `grep -n "npm publish" scripts/release.sh` returns a match; the match sits between the Step 9 (`git push`) block and the Step 10 (cache update) block; the dist-tag selection logic branches on the version suffix; a `MOS_TEST_DRY_RUN=1` path exists so the gate is exercisable without touching the registry. Verification: `bash tests/test-release-npm-gate.sh` exits 0.
   - Test type 2: **manual / live-registry verification (post-publish only).** Command: `npm view @mindrian/os@next version` returns `1.13.0-beta.9` (or current). Release-time check, NOT per-commit -- npm publishes are publicly visible and not easily revocable, so the live step is gated behind the manual cold-machine acceptance run and the release checklist, never run in CI.
   - Test type 3: **install-site copy check** (overlaps D-06/R-06): `grep -rln "npx @mindrian/os" ~/mindrianos-install-site/` -> 0 hits until the recovery publish lands. Separate repo; manual pre-release verification, not part of this repo's automated suite.
3. **Nyquist sampling note.** **Medium coverage need.** The script-shape assertion is cheap and runs on every commit touching `release.sh`. The live-registry step is high-stakes-but-low-frequency (once per release) -- treat it as a manual gate, not a sampled test. Graceful-degrades only in that the install site can drop the npm block as the fallback; the gate itself does not (a release that skips it ships unpublished, the original bug).

#### D-09 -- Statusline registration + `/mos:doctor` self-verify

1. **Behavioral contract.** install.sh writes the canonical `statusLine` block into `~/.claude/settings.json` via an idempotent `register_statusline()` that runs FIRST in install order (after node + git preflight, before any cp loops), so it survives even if a later step fails. The block is also re-stamped by the Phase 95.2 atomic-recovery path. `/mos:doctor` detects a missing `statusLine` block as a drift class (the audit calls it "class H" -- "install incomplete" -- which subsumes the missing-statusLine case); `/mos:doctor --statusline-visibility` returns `ok` after a complete install and `missing` (offering `--fix`) when the block is absent; `/mos:doctor --fix` writes the block idempotently when missing. On a first session after install, `/mos:doctor` reports all-green or names exactly what is missing -- there is no "silent install-incomplete" state. Acceptance triple: `cat ~/.claude/settings.json | jq '.statusLine'` returns the canonical block on a fresh install AND a recovered-from-cache install AND a manually-completed install.
2. **How it gets validated.**

### The cold-machine manual gate (the empirical Dimension-8 gate)

Automated fixtures simulate Windows on a Linux CI box; they cannot prove the real thing. D-01 + D-03 + D-09 ultimately require a real Windows tester (Gary, or a Wave-3 equivalent) to run the canonical install path with **zero AI hand-holding** -- no Claude Code improvising the missing symlinks or settings.json fragments -- and reach an all-green `/mos:doctor`. Capture this as `tests/manual/95.6-windows-cold-install-acceptance.md` with this checklist:

1. Fresh Windows 11 machine, Git for Windows installed, no prior MindrianOS state. (Surface-class touch device preferred -- matches Gary's Surface Pro 7; bring an external keyboard for the permission prompts.)
2. Run the canonical install path exactly as the install site documents it (CMD shell -- what worked for Gary live; note any PowerShell deviation).
3. Observe: `git clone` completes with no MAX_PATH error and no manual `core.longpaths` intervention required (D-01 + D-02).
4. Observe: `install.sh` exits 0; if any skill dir is incomplete it prints a `WARN` and continues; agents, hooks, larry-extended default, `MINDRIAN_OS_ROOT` all registered (D-03).
5. Open a fresh `claude` session: the statusline `(hexagon) MindrianOS-Plugin <room> <context%>` renders at the bottom within ~1s (D-09).
6. Run `/mos:doctor --all` (or `/mos:doctor --statusline-visibility`): all-green, OR it names exactly what is missing and `--fix` resolves it.
7. Reach `/mos:onboard` -> Larry greets, in under 5 minutes total, with no maintainer help.
8. (D-05a, if recovery publish has landed) `npm view @mindrian/os@next version` returns the shipped beta version; if not yet landed, confirm the install site does not advertise the npx path.

This gate is separate from -- and authoritative over -- the automated suites. A green CI run with a failed cold-machine gate means the phase is not done. It also realizes the Phase 95.2 D-13 dogfood-self-test mandate one layer earlier (at the install boundary, not just the recovery boundary) and produces the source material for the R-07 case-#4 autopsy (`docs/autopsies/2026-05-09-gary-laben-install-failure.md`).
