## 2. Per-Decision Research

### D-01: Windows long-path preflight in install.sh

**Confirmed live (call ~28:21):**

> Gary: "Fail command, couldn't create directory."
> Jonathan: "Same thing it won't mind."

This is the long-path failure firing again on the second clone attempt. Gary's CC fixed it on attempt 1 with `git config --global core.longpaths true`, but the partial-directory state from earlier broke the second clone. **The bug fires twice in one session** if the user does any retry-after-failure dance.

**New signal -- shell variability:**

> Gary started in PowerShell. The install command failed.
> Jonathan: "Yeah, we need terminal." (~6:16)
> Gary: "Let me, uh, do a different share and then..."
> Then Gary opened CMD via "Start, write CMD" (Jonathan's instruction at ~34:18) and the install proceeded.

**Implication:** PowerShell vs CMD on Windows behave differently for the install path. Either:

(a) The `.sh` script invocation through Git Bash needs different escaping in PowerShell vs CMD.
(b) PowerShell's execution policy was blocking something.
(c) The path-quoting (`"$HOME/.claude/..."`) parses differently between shells.

**Recommendation for D-01:** Detect both PowerShell AND CMD invocation, document both paths. Bias the README toward CMD as the canonical Windows shell because that worked for Gary live. Or: ship a PowerShell-native install script alongside install.sh so users do not have to invoke Git Bash from inside PowerShell.

### D-02: Rename 92-trust-layer-refactor

**Confirmed-on-confirmed:** the 189-char leaf name is the proximate cause of the long-path failure. Already locked in CONTEXT.md. No new signal from the call.

**Plan implication:** D-02 is the single most leveraged fix in 95.6. It touches one rename + reference updates and removes the entire failure class for any future Windows tester regardless of whether they enable longpaths. Should be Wave-1 priority.

### D-03: Harden install.sh skill-loop

**Confirmed live (call ~31:09):**

> Gary: "Error, exit code one."
> Jonathan (via): "Failed. Why? Ah."
> Jonathan: "Okay. It seems I need to do some work."

This is the install.sh skill-loop halt firing in the live call, identical symptom to Gary's 2026-05-08 Claude Code session. The bug is reproducible and not Gary-specific.

**New signal -- repetitive permission prompts:**

> Gary: "Fail command, couldn't create directory."
> Jonathan: "Same thing it won't mind."
> Gary: "Yes." Jonathan: "Yes." Lawrence: "Yes."
> Gary: "Yeah, yeah." Jonathan: "All the way."
> Gary: "Go with another one?" Jonathan: "Mm-hmm."
> ...continues for ~30 seconds with Gary clicking yes on every permission prompt...
> Lawrence: "Just as a side, I always hit two." (Lawrence's standing rule: always pick "always allow")

**Implication beyond D-03:** The install process triggers many separate permission prompts in Claude Code, one per command Bash invocation. Even when install.sh runs cleanly, the user is forced through 10+ prompt cycles. This is a friction surface separate from D-03 but related: Phase 95.6 should reduce the prompt count by either (a) bundling commands into fewer Bash invocations, or (b) instructing users to pre-approve via `--dangerously-skip-permissions` for the install session, or (c) writing a settings.json permission allowlist for the install paths.

**Recommendation:** Add a sub-decision under D-03 (or a new D-10) for "install permission ergonomics." This is Lawrence's standing pain point too -- he has trained himself to "always hit 2" without reading.

Gary's machine is a Surface Pro 7. Touch-first Windows tablet form factor. Several of his "yes" clicks during the install were screen taps, not keyboard. **Implication:** install ergonomics need to account for non-keyboard-primary Windows users. Specifically:

- The "press 2 for always allow" pattern Lawrence uses requires a keyboard.

- PowerShell vs CMD shell choice may interact with whether the user is keyboard-primary or touch-primary.

**Action:** Add to D-04 README manual-recovery section: a note about touch-Windows users and recommended input method (external keyboard + mouse during install).
