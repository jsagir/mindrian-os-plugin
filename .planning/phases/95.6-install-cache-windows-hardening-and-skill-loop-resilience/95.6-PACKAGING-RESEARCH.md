## 1. The thesis (one paragraph)

MindrianOS is already a mature, layered Claude Code plugin (83 commands, 8 agents, 9 skills, 23 hooks, 1 MCP server). The packaging question is therefore not "MCP or Skill" but "how do you ship this cleanly through Claude Code's native marketplace mechanism without depending on third-party hubs." The answer has three parts: (a) publish `@mindrian/os` to npm and let Claude Code's native marketplace mechanism install it via `{"source": "npm", "package": "@mindrian/os"}`; (b) ship a thin `bin/cli.js` solely as a value-add for the Brain key setup wizard + doctor parity (NOT as the install entry point); (c) keep the SessionStart hook idempotent npm-install pattern for runtime dependency management. The MCP server stays. The skills stay. The architecture is correct; only the distribution layer is missing.

## 3. Distribution paths (in order of preference)

### Path A: Native marketplace npm source (PRIMARY)

This is the simplest path. Once `@mindrian/os` is published, the user's marketplace.json points at it directly:

```json
{
  "name": "mindrian-marketplace",
  "plugins": [
    {
      "name": "mos",
      "source": {
        "source": "npm",
        "package": "@mindrian/os",
        "version": "^1.13.0"
      }
    }
  ]
}
```

Claude Code installs from npm natively. No bin CLI required for this path. Verified against `code.claude.com/docs/en/plugin-marketplaces` 2026-05-10. `version` field accepts npm semver ranges. `registry` field optional for private registries.

User-facing install:
```
/plugin marketplace add jsagir/mindrian-marketplace
/plugin install mos@mindrian-marketplace
```

This is the canonical Anthropic-supported flow. **It's also the path that's currently broken because @mindrian/os is unpublished.** Fix this and most install pain goes away.

### Path B: Direct npx invocation (SECONDARY)

For users who want a single-line install without registering a marketplace:

```
npx @mindrian/os install
```

This requires a `bin` field in package.json pointing at `bin/cli.js`. The CLI's `install` subcommand:
1. Detects Claude Code on PATH (prints native installer URL if absent).
2. Adds the marketplace via `claude plugin marketplace add jsagir/mindrian-marketplace`.
3. Installs the plugin via `claude plugin install mos@mindrian-marketplace`.
4. Runs the Brain key setup wizard (prompts for MINDRIAN_BRAIN_KEY, writes to user environment with proper Windows quoting per `feedback_gmail_qp_env_var_corruption`).
5. Surfaces verification: `/plugin marketplace update` + `/mos:onboard`.

Path B is a thin wrapper around Path A. The bin CLI's PRIMARY value is the Brain key wizard + the doctor parity (Path C below). Without those, Path A is sufficient.

### Path C: `npx @mindrian/os doctor` (DIAGNOSTIC)

The bin CLI exposes the same checks `/mos:doctor` runs, but from outside Claude Code so users can run them BEFORE starting a session. This catches the install-cache drift incidents (2026-04-13 #1, 2026-04-28 #2, 2026-05-06 #3, 2026-05-08 the Wave-2 tester case #4) before they become live failures.

```
npx @mindrian/os doctor              # read-only check
npx @mindrian/os doctor --fix        # mirror /mos:doctor --fix logic
npx @mindrian/os update               # wraps /mos:update for CLI users
```

Path C makes the bin CLI worth shipping even though Path A handles the install itself.

## 4. SessionStart hook for runtime dependencies

Anthropic-documented pattern (verified 2026-05-10 against code.claude.com/docs/en/hooks):

```json
{
  "hooks": {
    "SessionStart": [{
      "hooks": [{
        "type": "command",
        "command": "diff -q \"${CLAUDE_PLUGIN_ROOT}/package.json\" \"${CLAUDE_PLUGIN_DATA}/package.json\" >/dev/null 2>&1 || (cd \"${CLAUDE_PLUGIN_DATA}\" && cp \"${CLAUDE_PLUGIN_ROOT}/package.json\" . && npm install) || rm -f \"${CLAUDE_PLUGIN_DATA}/package.json\""
      }]
    }]
  }
}
```

The hook is idempotent: it diffs the plugin's package.json against the data-dir copy and reinstalls only when they diverge. Failure deletes the data-dir copy so the next session retries cleanly. This is the official pattern for managing plugin node_modules and is exactly what mcp-server-brain needs.

**Note on Setup vs SessionStart (Anthropic distinction):** Setup hooks run on `--init / --init-only / --maintenance` only, not on every session. SessionStart hooks fire every session. Plugins requiring per-session dependency reconciliation use SessionStart with idempotent guards (above). Plugins requiring true one-time setup (e.g., DB schema migration) use Setup. MindrianOS uses SessionStart for npm-install-on-drift; Setup is reserved for future use.

Both facts converge on a single fix: **ADD an npm publish gate to scripts/release.sh that runs in lockstep with every plugin release.** Without this, Path A (the primary distribution path) is permanently broken.

## 10. 2026-05-10 Update: Four Canonical Distribution Paths (Tavily-Validated)

A second-pass research input landed 2026-05-10 with significant new findings beyond Sections 1-9 above. Tavily-validated against current Anthropic plugin docs at code.claude.com/docs/en/plugin-marketplaces, code.claude.com/docs/en/discover-plugins, and code.claude.com/docs/en/plugins. The npm-as-distribution framing in Sections 1-9 is correct but incomplete: Claude Code now supports FOUR canonical distribution paths, not one.

### 10.1 Path inventory (current state of plugin distribution as of 2026-05-10)

```
Path 1 -- Marketplace + GitHub source (oldest, most established)
  marketplace.json points at GitHub repo:
    {"source": {"source": "github", "repo": "jsagir/mindrian-os-plugin"}}
  User flow:
    /plugin marketplace add jsagir/mindrian-os-marketplace
    /plugin install mos@mindrian-os-marketplace
  STATUS: works today; this is what mindrian-marketplace currently does.

Path 2 -- Marketplace + npm source (the "leading approach" in Sections 1-9)
  marketplace.json points at npm package:
    {"source": {"source": "npm", "package": "@mindrian/os", "version": "^1.13.0"}}
  User flow: same as Path 1; Claude Code resolves the npm package transparently.
  STATUS: blocked on Phase 95.6 D-05a (Step 9.5 npm publish gate to release.sh).
  When unblocked: cleanest distribution; users do not need to know it's npm under the hood.

Path 3 -- Direct ZIP / URL (NEW; Tavily-confirmed 2026-05-10)
  Plugin shipped as a .zip archive. User invocation:
    claude --plugin-url https://mindrian-os.com/dist/mindrian-os-v1.13.0-beta.9.zip
    claude --plugin-dir ./mindrian-os-v1.13.0.zip
  Both --plugin-url and --plugin-dir accept .zip archives natively.
  STATUS: works today; useful for internal distribution, staging, try-before-install,
    private-network deployments where public npm or GitHub is not reachable.
  Implication: NATO IT could host the .zip on their internal network for faculty.

Path 4 -- Pre-baked CI/Docker via CLAUDE_CODE_PLUGIN_SEED_DIR (NEW; Tavily-confirmed)
  Build-time pre-installation. Two env vars:
    CLAUDE_CODE_PLUGIN_CACHE_DIR -- target path during build; plugins install directly here
    CLAUDE_CODE_PLUGIN_SEED_DIR  -- runtime path; Claude Code reads pre-baked plugins from here
  Build-time recipe:
    CLAUDE_CODE_PLUGIN_CACHE_DIR=/opt/claude-seed claude plugin marketplace add jsagir/mindrian-os-marketplace
    CLAUDE_CODE_PLUGIN_CACHE_DIR=/opt/claude-seed claude plugin install mos@mindrian-os-marketplace
    # then COPY /opt/claude-seed into image
  Runtime: machines with CLAUDE_CODE_PLUGIN_SEED_DIR=/opt/claude-seed get MindrianOS pre-installed.
    /plugin marketplace remove and /plugin marketplace update are BLOCKED on seed-managed plugins
    (admin-controlled state).
  STATUS: works today; canonical path for institutional / classroom / managed deployments.
  Implication for NATO: faculty machines could be image-baked with MindrianOS and never
    require per-user install. Zero network calls at runtime. Highest reliability tier.
```

### 10.2 Implications for Phase 95.6

The expanded distribution surface materially changes the architecture:

**Implication A:** D-05 was previously framed as "npm publish + marketplace npm source." Path 3 (ZIP/URL) and Path 4 (SEED_DIR) are independent and do not require npm publish. Even if npm publish (D-05a) ships late, Path 3 + Path 4 unblock institutional deployment via a different route.

**Implication B:** NATO Defense College Rome adoption is the forcing function for v1.13.0 production-ready (per `v1.13.0-PRODUCTION-READINESS-AUDIT.md`). Path 4 pre-baking via `CLAUDE_CODE_PLUGIN_SEED_DIR` is the highest-reliability deployment path because it eliminates per-faculty-machine install variability entirely. NATO IT bakes a Docker image OR a Windows install snapshot with MindrianOS pre-seeded, distributes the image to faculty machines, and faculty get a working install at first launch with zero install-time failure surface.

**Implication C:** The "any user" production-readiness bar (per maintainer directive) is best served by Path 1 + Path 2 (marketplace, public source). Path 3 (ZIP) is for power users + private deployments. Path 4 (SEED_DIR) is for institutional managed environments.

**Implication D:** Documentation must surface all four paths with clear "use this path when..." guidance. The install site (mindrianos-install-site.vercel.app) currently advertises only the npm path (and lies about it because npm is unpublished). It should be rewritten to surface all four paths, with the marketplace + GitHub source as the immediate-now-unblocked default while npm waits on D-05a.
