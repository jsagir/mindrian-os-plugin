### 1.1 Navigator reasoning, recorded

The ruling was `option-a` with no amendments to any leg. The reasoning given, recorded here
so a later reader sees a grounded rationale and not a bare preference:

1. **Option-a reuses this repo's existing house pattern rather than minting a new one.** A
   sibling registry modeled on `data/first-touch-surfaces.json` is a shape the repo already
   ships twice, and it already has a scanner precedent in `lib/core/stale-copy-scanner.cjs`.
   This is Canon Part 7 reuse-before-build applied literally: copy an existing contract shape
   instead of inventing a second one. See `267.3-AUDIT.md` Section 2.3.

   the 17 that block Phase 271.** Narrowing (option-d) reproduces the exact debt-ratchet
   failure that `DEFERRED-271-D1` already documented this session: a gate that only fires on
   staged files leaves the rest of the debt invisible, and the next unrelated sweep hits the
   same wall. Paying the cost once is cheaper than paying it again on a schedule set by
   whichever future phase happens to stage the files. See `267.3-AUDIT.md` Section 4.4.

3. **The two new vocabulary terms are each grounded in the rule doc's own existing language,
   not invented from scratch.** `methodology_reframe` names the move
   `docs/reward-before-investment-rule.md` already describes for the reframe family, applied
   to a command's own material rather than to onboard's opening sentence.
   `--none (diagnostic surface)` names a category the rule doc itself already names in its own
   words at `docs/reward-before-investment-rule.md:59-60` ("A `/mos:status` output is not a
   reward"; "A status report is not a reward"). Neither term asserts anything the canon does
   not already say. See `267.3-AUDIT.md` Section 3.

4. **Options b and c were rejected on the grounds the plan itself already stated**: option-b
   introduces a second parsing surface with no precedent in this repo, and option-c overloads
   a generated invocation-wiring registry with hand-authored reward semantics. Neither
   rejection needed new evidence beyond what the plan already recorded.

## 2. D-A. The out-of-frontmatter declaration mechanism

**RULED: a new sibling registry file, `data/first-reward-surfaces.json`.**

**Motivating audit finding:** `267.3-AUDIT.md` Section 2 (the unreachable surface inventory)
and Section 2.3 (the existing precedent this phase would copy). Section 2 establishes that
four injected-prose surfaces in `scripts/session-start` (`FIRST_INSTALL` at `:666`, `UPDATE`
at `:680`, `MODE_ROUTING` at `:707`, `COLD_START_MENU` at `:657`) plus seven of nine
`SessionStart` hook entries emit user-facing first-touch prose and carry no declaration,
because a bash script has no frontmatter block and because the guard's four independent scope
proofs (`267.3-AUDIT.md` Section 1.3) confine it to `commands/*.md`.

### The contract

`data/first-reward-surfaces.json` is modeled on the record shape of
`data/first-touch-surfaces.json`. It is registry-is-the-table: the file IS the contract, read
by a scanner, never a hardcoded list inside the scanner.

Per-record fields, the first three copied from the existing registry's shape and the last two
this registry's own:

| Field | Source | Meaning |
|---|---|---|
| `id` | copied from `data/first-touch-surfaces.json` | stable surface identifier, e.g. `session-start:FIRST_INSTALL` |
| `file` | copied | repo-relative path to the declaring surface |
| `kind` | copied | `shell_script`, `cjs`, `command_md`, `agent_md`, matching the existing registry's vocabulary |
| `interactive_first_reward` | new to this registry | one member of the amended `REWARD_TYPES`, validated against the identical closed vocabulary the frontmatter path uses |
| `why` | new to this registry | one Feynman-simplified sentence naming the surface's actual first-reward moment |

### Why a SIBLING file and not an extension of `data/first-touch-surfaces.json`

That file's consumers all key off version-stamping semantics:
`lib/core/stale-copy-scanner.cjs`, `lib/core/first-touch-version-stamper.cjs`,
`scripts/doctor.cjs`, and `lib/core/doctor/stale-first-touch-copy-module.cjs`. Adding reward
semantics would make one file answer to two independent gates, so a change made for one gate
could silently move the other. Two files, one shape, no coupling.

### Why this satisfies Canon Part 7

The record shape is copied, not invented. The scanner pattern is copied
(`lib/core/stale-copy-scanner.cjs` already reads a declaration registry from `data/` and its
`purpose` field says so). The validation vocabulary is the SAME `REWARD_TYPES` set the
frontmatter path already uses, so the two declaration surfaces cannot drift on what a legal
value is.

### What plan 267.3-02 builds against this ruling

- `data/first-reward-surfaces.json`, the registry itself.
- `scanDeclaredSurfaces()`, a new export of `lib/core/mva-rule-linter.cjs` that reads the
  registry and runs the SAME `validateFrontmatter` verdict logic against each record's
  `interactive_first_reward`, so one classifier serves both surfaces.
- `node scripts/check-reward-before-investment.cjs --surfaces`, the registry audit mode.

## 3. D-B. The vocabulary amendment

**RULED: exactly two new `REWARD_TYPES` members. No more, no fewer. No respellings.**

**Motivating audit finding:** `267.3-AUDIT.md` Section 3 in full. Section 3.1 establishes
that five of the six existing members were minted against exactly one flow each. Section 3.2
establishes that ten conversational methodology commands have no honest term. Section 3.3
establishes that nine diagnostic / operator / report commands have no honest term either, and
that `--none (scripting only)` MISLABELS them because the rule doc's scripting override at
`docs/reward-before-investment-rule.md:95` is conditional on an actual
`--no-interactive` / `--script` / `-q` invocation.

### 3.1 The two new members, spelled literally

Copy these character for character. They are the strings plan 267.3-02 codes into
`lib/core/mva-rule-linter.cjs` and the strings plans 267.3-04, 267.3-06 and 267.3-07 write
into 67 command frontmatter blocks.

```
methodology_reframe
```

```
--none (diagnostic surface)
```

Note precisely: `methodology_reframe` is lowercase with a single underscore and no hyphen.
`--none (diagnostic surface)` is two leading hyphens, the word `none`, ONE space, then the
parenthesized phrase `diagnostic surface` in lowercase with a single space inside it, and a
closing parenthesis. No trailing period, no trailing space.

### 3.2 What each term means, and the canon-amendment reason for each

**`methodology_reframe`**

A conversational methodology command whose first delivered value is Larry's analysis or
reframe over the user's OWN material. The user has already supplied the substance; the
variable reward is what Larry does with it in the first turn, before any further investment.

Amendment reason: this is a genuinely different reward from every existing member.
`reframe_question` (`docs/reward-before-investment-rule.md:83-84`) is bound to onboard's
single-sentence opener, where Larry reframes a SENTENCE before any material exists.
`instant_brief` (`:133`) is the 30-second MVA pipeline output. `paragraph_preview` (`:136`)
is a partial extraction from a transcript's first paragraph. `schema_preview` (`:135`) is a
structural preview of what WOULD be extracted, which is a promise about extraction, not an
analysis. `calibration_distribution_preview` (`:135`) is a score distribution. None of the
five describes "Larry reasons over what you brought and hands back a reframe." The term is
grounded in the rule doc's own reframe vocabulary rather than invented; it applies that same
move to a different input.

Applies to (from `267.3-AUDIT.md` Section 3.2, regenerated live, ten commands):
`analyze-systems`, `auto-explore`, `challenge-assumptions`, `compare-ventures`,
`find-connections`, `leadership`, `lean-canvas`, `mullins`, `score-innovation`,
`systems-thinking`. Two further `methodology` commands, `causal` and `whitespace`, read
`CODE` bodies and are a per-command call for plan 267.3-04, not pre-assigned here.

**`--none (diagnostic surface)`**

A command that reports state rather than delivering a variable reward. This is an OPT-OUT,
not a reward.

Amendment reason: the rule doc itself already names this category in its own words, twice, at
`docs/reward-before-investment-rule.md:59-60`: "A `/mos:status` output is not a reward
(predictable report)." and "A status report is not a reward." The gap is that the vocabulary
gave that named category no legal value to declare. Using `--none (scripting only)` instead
would be a false statement about the command's invocation, because the scripting override at
`docs/reward-before-investment-rule.md:95` is legitimate only "IF the command is invoked with
a `--no-interactive`, `--script`, or `-q` flag", and these commands are invoked
interactively. `267.3-AUDIT.md` Section 3.3 shows `status` declaring `hitl_shape: F.1`, a
genuine Decision-Gate fork, which is the opposite of a silent script.

**Spelling rationale, ruled deliberately.** The term is spelled in the same `--none (...)`
family as the existing scripting opt-out so a reader scanning frontmatter sees at a glance
that it is an opt-out and not a reward. Two opt-outs that look alike and one reward
vocabulary that looks different is the readable arrangement; a bare word like
`diagnostic_report` would read as a reward type and invite exactly the misclassification this
ruling exists to prevent.

Applies to (from `267.3-AUDIT.md` Section 3.3, nine commands): `status`, `doctor`, `heal`,
`dogfood-flush`, `hmi-status`, `dial-memory-refresh`, `feynman-timeline-refresh`,
`diagnostics`, `update`.

### 3.3 The full amended vocabulary, eight members

The complete post-amendment `REWARD_TYPES` set that plan 267.3-02 writes into
`lib/core/mva-rule-linter.cjs:49-56`. The first six are unchanged and must not be respelled.

```
reframe_question
instant_brief
schema_preview
calibration_distribution_preview
paragraph_preview
--none (scripting only)
methodology_reframe
--none (diagnostic surface)
```

Order in the frozen `Set` is not semantically meaningful, but appending the two new members
after the existing six keeps the diff minimal and keeps the original six visibly intact.

### 3.4 The amendment is recorded as a canon amendment, not a code change

`lib/core/mva-rule-linter.cjs:15-17` states: "REWARD_TYPES is the v1.13.0 canonical closed
vocabulary. Future additions are canon amendments, not command-level inventions."
`docs/reward-before-investment-rule.md:139` states the same: "Future expansions are canon
amendments, not command-level inventions."

So plan 267.3-02 must land BOTH halves together: the two new members in
`lib/core/mva-rule-linter.cjs`, AND a written amendment entry in
`docs/reward-before-investment-rule.md` recording each new term with its reason and citing
this ruling. A code change without the doc entry is a command-level invention wearing a
library's clothes.

### 3.5 What this ruling does NOT authorize

Declaring a value on any specific command. `lib/core/mva-rule-linter.cjs` binding decision B5
(`lib/core/mva-rule-linter.cjs:19-21`) states the linter validates only the DECLARATION and
that per-command remediations are follow-up work. The class lists in Sections 3.2 above are
the audit's measured signal, not a rubber stamp. Plan 267.3-04 builds the per-command
classification rubric and rules each command's value with its cited first-reward moment. The
`publish` miscall recorded in `267.3-AUDIT.md` Section 3.3 is the standing reminder of what a
rubber stamp costs.

## 4. D-C. The lint scope

**RULED: keep `--staged` as the commit gate exactly as Phase 245-02 built it, AND add the
already-existing full audit to `scripts/verify-release` as a fail-closed gate, promoted only
at phase close after the backfill lands.**

**Motivating audit finding:** `267.3-AUDIT.md` Section 4.4 and Section 5 (D-C). Section 4.4
quotes `DEFERRED-271-D1`'s own structural diagnosis: "The linter scans staged `commands/*.md`
only. These 16 files had not been staged since the reward-before-investment rule shipped, so
the gap was invisible to every commit that did not happen to touch them." A file-scoped gate
cannot measure a repo-wide gap. Right now 67 of 113 commands are undeclared and no commit is
blocked by that fact.

### The three parts of this ruling

**1. The commit gate is NOT changed.** `scripts/check-reward-before-investment.cjs --staged`
and the hook arm at `scripts/hooks/pre-commit-room-minto-guard.sh:299-313` stay exactly as
Phase 245-02 shipped them. That narrowing was a correct root-cause fix, recorded at
`docs/reward-before-investment-rule.md:117-129`: before it, one pre-existing offender blocked
every commit that touched any command, which made `COMMIT_NO_VERIFY=1` mandatory rather than
exceptional. Widening the commit gate would undo that fix and re-create a permanent forced
bypass. Nothing about the per-file verdict is relaxed either; a staged file with a missing or
invalid declaration still fails the commit.

**2. The whole-tree audit goes to the RELEASE gate, not the commit gate.** The full audit
already exists as the CLI's default mode (`scripts/check-reward-before-investment.cjs:127`)
and it already exits 1 today. It gains a fail-closed wire into `scripts/verify-release`. A
release is the right cadence for a repo-wide invariant: it is periodic, it is deliberate, and
it does not block an unrelated one-file commit.

**3. The gate is wired now and PROMOTED later.** This is the 271-05 discipline applied
literally: wire the gate, do not relax it, and do not turn it on before the work that makes
it green is done. Turning the whole-tree audit red at the moment it is wired would make every
release red immediately, which produces a bypass habit rather than a gate. So plan 267.3-03
wires the registry-scoped `--surfaces` gate (whose registry starts green because it is
authored complete), and plan 267.3-08 promotes the full `commands/` audit to fail-closed only
after plans 04, 06 and 07 have landed the 67 declarations and the audit reads zero missing
and zero invalid.

No gate is relaxed, allowlisted, edited, or bypassed at any point in this sequence. That is
GUARD-10 and it is not negotiable.

## 5. Rejected options, preserved with their reasons

A rejected option is never deleted. Recorded here so a later reader can see what was
considered and why it lost, and so a future phase does not re-propose a settled question as
if it were new.

### option-b: parsed comment convention inside the bash script

**REJECTED.**

What it proposed: put the declaration in a comment three lines above the prose it describes,
inside `scripts/session-start`, and teach the linter to parse it.

Reason rejected: it requires the linter to grow a bash parser, which is a SECOND parsing
surface sitting next to the existing YAML-ish frontmatter parser at
`lib/core/mva-rule-linter.cjs:71-111`, and a place for the two to drift on what a legal
declaration looks like. It also does not generalize: a future injected-prose surface that is
not bash (a `.cjs` hook, for example, and `267.3-AUDIT.md` Section 2.2 counts six such
prose-emitting `.cjs` entries) would need a third parser. And there is no precedent for this
shape anywhere in the repo, where the registry-is-the-table pattern already exists twice.

What was genuinely good about it, recorded so the value is not lost: the declaration would
sit next to the prose it describes, so a contributor editing `scripts/session-start:666` could
not miss it. Mitigation carried into option-a: the registry's `why` field must name the
surface's actual first-reward moment in one sentence, and plan 267.3-03's registry entries
must cite the exact `scripts/session-start` line each record describes, so the registry points
back at the prose even though it does not sit beside it.

### option-c: extend the born-wired connector registry (Canon Part 11 machinery)

**REJECTED.**

What it proposed: reuse `data/connector-registry.json`, since Canon Part 11 already says
"every invocable surface is born declared" and that registry already enumerates surfaces.

Reason rejected: the connector registry is GENERATED by
`scripts/build-connector-registry.cjs` and it is about INVOCATION wiring, not first-touch
reward contracts. Adding a hand-authored reward field to a generated file means the generator
either overwrites the hand-authored content or has to learn to preserve it, and both are worse
than a second file. Separately, `scripts/session-start` is a HOOK, not an invocable surface,
so it does not belong in an invocation registry at all: the very surface this ruling exists to
cover is the one that would not fit.

The Canon Part 11 adjacency the ROADMAP noted at `.planning/ROADMAP.md:722` is real and is
honored a different way: option-a copies Part 11's DECLARATION DISCIPLINE (a closed
vocabulary, a registry read by a gate, a written reason per record) without overloading Part
11's generated artifact.

### option-d: option-a, but narrow to the 17 Phase-271-blocking commands

**REJECTED.**

What it proposed: the same mechanism and vocabulary as option-a, but declare only the 17
commands currently blocking Phase 271 and register the other 50 as a follow-up phase.

Reason rejected: it leaves 50 commands undeclared behind a gate that only fires when someone
stages them, which is the EXACT debt-ratchet failure `DEFERRED-271-D1` documented, in this
same session, about this same rule. `267.3-AUDIT.md` Section 4.4 quotes the mechanism
verbatim. The next unrelated sweep that happens to stage those 50 files hits the identical
wall, stalls the identical way, and pays the identical cost of an unplanned blocking ruling
mid-phase. Narrowing does not remove the work; it schedules it at a time chosen by an
unrelated phase.

The ROADMAP's own scope-widening paragraph recommends against it, and the SCOPE RULING made
at plan time already answered the widening question YES for both halves.

Its one genuine advantage, recorded honestly: it would unblock the release gate faster. That
advantage is real and it was weighed and rejected, because a faster unblock that guarantees a
repeat of the same stall is not faster over the life of the repo.
