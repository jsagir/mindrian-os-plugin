# Phase 267.3 Plan 03: Session-Start Declarations and the Surfaces Gate Summary

The first prose any MindrianOS user ever sees now carries a machine-readable, honest
first-reward declaration, findable from inside the bash file, bound to a live literal by a
tripwire that was proven to fire, and locked behind a fail-closed release gate.

## What was built

### Why all four declare the opt-out, and why that is the honest answer

The plan's Task 1 is explicit that a `why` claiming a reward the code does not produce is a
false declaration. Measured against `.planning/research/2026-08-27-hooked-first-install-audit.md`:

- **FIRST_INSTALL** scored **2/10 on the Reward leg (GAP R-1)**. Its one reward claim
  ("Based on your work in [domain], here is what I already know about your space") is a prose
  instruction to the model with no MindrianOS machinery behind it, failing the rule's own
  decisive attributable-to-MindrianOS test. The machinery that would pass it,
  `sweepDomainInsights`, requires an open room `db` handle that a first install by definition
  does not have.
- **UPDATE** does have real machinery (the `ONBOARD_STEPS` / `CHANGELOG_DIFF` extraction), but
  its output is fully predictable given the version pair. That is precisely the case
  `docs/reward-before-investment-rule.md:59-60` already names in its own words: a state report
  is not a reward. This one is an honest opt-out with nothing owed against it.
- **MODE_ROUTING** hands back a three-option routing card and asks the user to pick before
  anything is given. That is investment before reward, the exact ordering the rule exists to
  prevent.
- **COLD_START_MENU** is a static four-command list. Its one measured defect is a routing gap
  and not a false reward claim: it never names `/mos:ignite`, the front door built to deliver
  the Hooked first-cycle reward.

Three of the four `why` fields name Phase 267.2 as the owner of the repair, per standing
constraint 7 in `267.3-DECISIONS.md`: this phase declares the contract, it does not change the
onboarding flow.

**The valuable side effect:** the product's most-first flow now says out loud, in a file a gate
reads, that it delivers no variable reward. That was true before this plan and invisible.

### Four comment-only declaration blocks (`scripts/session-start`)

One block above each declared branch, in the file's existing comment style, each naming the
registry id, the declared value, and `data/first-reward-surfaces.json`. This is the mitigation
`267.3-DECISIONS.md` Section 5 promised when it rejected option-b: the rejected design's one
genuine advantage was that a contributor editing the prose could not miss the declaration, and
these comments recover that without a bash parser.

`scripts/session-start` went from 1887 to 1921 lines: **34 insertions, 0 deletions, every one a
comment.**

### The anchor tripwire (`tests/test-267.3-session-start-declaration.cjs`, 296 lines)

`scanDeclaredSurfaces()` checks that a record's FILE exists. Nothing checked that the record's
ANCHOR still points at something inside it. A refactor that renamed `COLD_START_MENU` or
reworded a payload would leave the declaration describing prose that no longer exists, with
`file_not_found` silent and every gate green (threat T-267.3-13). Seven checks close that:

1. every `file` resolves to a real file under the repo root
2. every `anchor` is a literal substring of that file
3. a `scripts/session-start` record anchors INSIDE the FIRST_INSTALL branch specifically, not
   merely somewhere in the file (the branch is bounded by locating the payload `if` and the
   `UPDATE` `elif` at run time, so the test carries no line numbers either)
4. every `id` is unique registry-wide
5. every value is a member of the LIVE `REWARD_TYPES` Set required out of
   `lib/core/mva-rule-linter.cjs` at run time, never a pasted token list
6. no `why` carries a U+2014
7. a synthetic registry whose anchor was renamed away fails the same predicate

Tests 1, 2 and 7 all call one shared `auditAnchors()`, so the live sweep and the negative case
cannot drift into being two different checks one of which happens to be toothless. Test 7 also
carries a control case (anchor present must pass) so a predicate that returned a failure for
everything would red too.

### Gate 10d (`scripts/verify-release`)

Sited immediately after gate 10c and modeled line for line on it: captures output and exit code
(`SURFACES_OUT` / `SURFACES_CODE` mirroring `ANCHOR_OUT` / `ANCHOR_CODE`), fails the release on
non-zero, prints the captured tail so the offending surface id is visible in the release log,
and emits a pass line naming the surface count read from the registry's own output.

The comment above it records, in the file, why the whole-tree `commands/` audit is deliberately
NOT wired here and names plan 267.3-08 as its owner, so a later reader does not "fix" the
omission and turn every release red for work this plan does not do.

## Deviations from Plan

### 1. [Rule 1 - Bug] Task 1's verify command 5 is a false-positive generator; replaced with three strictly stronger checks

- **Found during:** Task 1, at verification time.
- **Issue:** the plan's fifth verify command is
  `git diff -- scripts/session-start | grep -c 'SEED-021' | grep -qx 0`. Default `git diff`
  emits three lines of CONTEXT around every hunk. The FIRST_INSTALL comment block sits
  immediately above line 665, and line 666 (the SEED-021-bearing payload) therefore appears as
  an unchanged context line; the same happens at MODE_ROUTING. The command returned **3** while
  the actual number of *changed* lines mentioning SEED-021 was **0**. All three hits were
  confirmed to be context lines (leading space in the diff prefix), not `+` or `-` lines.
  Placing the comments far enough away to escape the 3-line context window was not an option:
  the plan requires the comment "immediately above each declared branch", and the payload is
  always the next line.
- **Fix:** the check was NOT weakened or dropped. It was replaced with three checks that are
  each strictly stronger, all of which pass: (A) every non-comment line byte-identical to the
  pre-plan HEAD, (B) zero *changed* lines mention SEED-021 via `git diff -U0`, (C) the
  SEED-021-bearing lines themselves diffed then-versus-now and byte-identical, count unchanged.
  Proof A alone proves strictly more than the original command intended to, since it covers
  every prose payload in the file and not only the SEED-021 lines. Task 1's verify command 4
  (comments-only, which already uses `-U0`) passed as written and was not modified.
- **Files modified:** none. This changed a verification method, not the code.
- **Commit:** the proofs are recorded here and were run against `1166ca48`.

### 2. [Rule 2 - Missing critical functionality] `--none (diagnostic surface)` is a strained fit for two of the four branches, and the strain is recorded rather than papered over

- **Found during:** Task 1, classification.
- **Issue:** `267.3-DECISIONS.md` D-B defines `--none (diagnostic surface)` as "a command that
  reports state rather than delivering a variable reward." That definition fits UPDATE (a
  version-delta report) and COLD_START_MENU (a report of what is available) cleanly. It fits
  FIRST_INSTALL and MODE_ROUTING only in its opt-out half: neither delivers a variable reward,
  but neither is really "reporting state" either - one is a welcome-and-ask, the other a routing
  card. All six reward members would have been demonstrably false, and
  `--none (scripting only)` would have been a false claim about invocation (no
  `--no-interactive` / `--script` / `-q` path exists), which is the precise error the
  `publish` miscall in `267.3-AUDIT.md` Section 3.3 already paid for once.
- **Fix:** used the nearest honest member and put the full reasoning in each record's `why`
  field and in the in-file comment, which is what the `why` field exists for. Minting a third
  opt-out spelling was NOT done: D-B ruled "exactly two new members. No more, no fewer," and a
  registry-local invention is forbidden by the registry's own `_doc.reward_vocabulary_note`.
- **Carried forward, not fixed here:** whether the vocabulary needs a distinct pre-reward
  opt-out term (something in the `--none (...)` family for a surface that asks before it gives)
  is a genuine open question for a future canon amendment. It is recorded as
  `DEFERRED-267.3-D2` in this phase's `deferred-items.md`. Ruling it inside an execution plan
  would be exactly the command-level invention the canon forbids.
