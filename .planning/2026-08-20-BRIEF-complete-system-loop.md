## 3. The live-vs-cache decision, resolved (not proposed)

This is not an open architecture question. It is already decided, and decided against a live call. SEED-045's own charter carries a section titled **"THE CONSTITUTIONAL CORRECTION (C-1 / C-3, BLOCKING)"**:

> "The advisor reads a LOCAL DERIVED CACHE, NEVER a live Brain query at decide()/rank time. This is non-negotiable."

Grounded in three separate canon citations inside that same file: Canon Part 11 R7 ("no live Brain call on the hot path"), Part 11 R4 ("one governed path, no second selection brain"), and Part 8 entry-19 ("live Brain read/write of the projection is DEFERRED; live nav-engine consumption of the cache is deferred-to-wire, not a live query"). This session's own code read of `navigation-engine.cjs` found the exact same thing independently, from the code side: the file is a deliberate "PURE LOCAL READER" with its own stated live-arming review gate. Three independent sources (canon text, a ratified charter, and direct code inspection) agree.

**How this reconciles with "the Brain is always on."** Key Decisions #1/#5/#8 mean the Brain is never optional as the SOURCE of methodology -- a keyless or unreachable session gets an honest refusal, never a locally-fabricated substitute. It does not mean a live network round-trip happens on every per-turn routing decision. The mechanism that honors both commitments already exists: an offline-derived `brain_confidence` prior, already wired as the 0.40 weight in `f-selector-ranker.cjs` D4, sourced from the Phase 157 projection cache that is periodically synced FROM the Brain. "Always on" is satisfied by the cache always being Brain-derived and never fabricated; it is not satisfied by a live call on the hot path, and the canon explicitly forbids that path.

**Where a live call IS legitimate:** command-time, not decide()-time. When a navigator explicitly runs `/mos:suggest-next` or `/mos:act`, that is a deliberate invocation, not a per-turn hot-path decision, and the honest-refusal doctrine (Build the Loop's non-negotiable test: "can a user ever be served methodology that did not come from the Brain, without being told? The answer must be no") could be satisfied there by either a fresh cache read with a visible timestamp, or a genuinely new command-scoped live call if the phase's own research step decides the projection cache is too stale to trust for a single explicit ask. That decision belongs to Gate 0's findings, not to this brief.

**A third option, raised mid-session, and the right one for this specific surface: push the composition server-side, inside the mindrian-os MCP tool handler itself.** Instead of the model orchestrating two separate tool calls (one to `mindrian-os` for local state, one to `mindrian-brain` for methodology) and synthesizing them itself, the `suggest_next` / `reach_candidates` tool implementations in `mindrian-os` could call `lib/core/brain-client.cjs` directly, server-side, and return one answer already grounded in both. This does not conflict with the blocking correction in section 3 above -- it conflicts with nothing, because it is scoped to the EXPLICIT on-demand tool entry points, never the automatic per-turn `decide()`/`dispatchSensors` hot path. The tool descriptions already on file for `suggest_next` and `reach_candidates` confirm this shape exists today: both are documented as pulling "through the shipped dispatchSensors reach path... the SAME candidate-reach registry the per-turn navigation engine consumes, called here on demand as a read." The shared registry stays pure-local always (R7 is about that registry's automatic hot-path use); the on-demand entry points calling it are a different, already-distinguished call site, and that is exactly where server-side Brain composition belongs.

Weighed on the merits:
- **For.** "Always on" becomes structural instead of behavioral -- a model can forget to make a second tool call across a long session or under a lighter-weight configuration; a tool contract that always composes both sources server-side cannot forget. It also fits an already-accepted precedent: `bin/mindrian-brain-mcp-client.cjs` is already a local Node process proxying to the remote Brain, so a `mindrian-os` handler calling `brain-client.cjs` server-side is not a new category of trust boundary, it is reusing the one that already exists.
- **Against, and how each resolves.** (1) Tool latency now silently includes a remote round-trip -- resolve with an explicit timeout and a graceful in-response degrade (return the local ranking plus `brain_grounded: false, reason: "timeout"` rather than hanging the tool call). (2) What does the tool return on a Render cold start mid-call -- this is not a new problem to solve, Canon Part 3 already specifies the exact two states this needs (Mode A: Brain reachable, ranked with confidence; Mode B: Brain unreachable, local-only, no RECOMMENDED marker); server-side composition just means the Mode A/B switch now happens inside the tool handler instead of being orchestrated by the model across two calls, which is a cleaner realization of an already-designed fallback, not a new one. (3) **This bypasses the current Part 8 egress-guard hook**, which matches on `mcp__*brain*` tool names -- a Brain call happening inside a `mindrian-os`-named tool's handler is invisible to that matcher. This is not hypothetical: this exact gap is already the reason a prior outage stayed invisible (`docs/2026-08-10-HANDOFF-build-the-loop-milestone.md` section 4: "Calls through the `pws-brain-mcp` project scope worked the whole time because the broken hook's matcher never covered that server name"). And this session's own read of `scripts/part8-egress-guard-hook.cjs` found the fix already planned, not hypothetical: the hook's own code comment states "the complementary fail-CLOSED belt lands in brain-client.cjs (sibling plan 239-05)." **Position: adopt the server-side composition for `suggest_next`/`reach_candidates` specifically, and make shipping Phase 239-05's fail-closed belt inside `brain-client.cjs` a prerequisite of that work, not a someday-follow-up** -- moving composition server-side makes the hook's blind spot immediately live rather than theoretical, so the belt that was already planned to close it should land in the same phase, not after.

## 4. The section-affinity model

**Proposed canonical 8** (5 from the navigator's own examples, 3 filled in from the venture-room structure already visible across this session's work, e.g. the Village of Life hub's real section layout):

1. **Bank of Opportunities** -- Eureka, HSI, Usher's Model, Opportunity Recognition as Pattern Recognition.
2. **Meetings** -- JTBD, Six Thinking Hats / Bono persona work (where jobs and multi-perspective debate actually surface, per the navigator).
3. **Team** -- Leadership frameworks (Adaptive Leadership, Tuckman).
4. **Patent / Legal** -- IP/legal-relevant frameworks.
5. **Funding** (sub-folders: Dilutive, Non-Dilutive) -- grant grading and opportunity-qualification (`/mos:grade`, `/mos:qualify-opportunity`, `/mos:opportunities`) live under Non-Dilutive specifically, per the navigator's own instruction.
6. **Research / Market** -- S-Curve, Adoption-Capacity Theory, Dominant Design, PEST/Macro-Changes, Scenario Planning.
7. **Product / Curriculum** -- Lean Canvas, PWS Value Proposition, Mullins Model.
8. **Advisors / Partners** -- external-relationship frameworks (Six Hats persona work on stakeholder alignment, Systems Thinking on partner dependencies).

This list needs the navigator's explicit approval before it becomes graph data -- it is a proposal grounded in his examples plus pattern-matching against real room structure, not a discovery. `DataRoomSection` exists as a schema label today with zero populated instances; this is genuinely new content, not a fix.

**The edge-type question, flagged before inventing anything.** Canon Part 4 keeps a CLOSED typed-edge vocabulary; a new edge type is a canon amendment, not a command-level addition. Part 4 already ratifies `TAGGED_WITH` -- "the lightweight categorization tag from any node to a domain or subdomain" -- which may already be the correct edge for Framework-to-Section relevance without needing a new type at all. Per Part 7 (Reuse Before Build), the phase's research step should check whether `TAGGED_WITH` (with a `weight` property added, if properties can be added without a full amendment) covers this before proposing a new `RELEVANT_IN_SECTION` type. If a new type is genuinely needed, that is a canon amendment, a heavier gate than the rest of this work, and should be scoped as its own decision point, not bundled silently into a phase.

**The Part 8 boundary crossing, designed explicitly.** The navigator's CURRENT section (which folder they're standing in) is local room data. Sending it to the Brain is legal only as a canonical enum value (e.g. `opportunity_bank`), never as the user's own custom folder name. A user who renames "Bank of Opportunities" to "Grant Pipeline" locally must have that custom name mapped to the canonical slug ENTIRELY on the local side -- the mapping table itself never crosses the wire, only the resolved canonical enum does. This mirrors the existing pattern exactly: "Allowed Brain queries carry only generic framework handles and phase identifiers" (Part 8).

**Where the ranking boost actually plugs in:** `f-selector-ranker.cjs`, the same file that already carries the 0.40 `brain_confidence` weight (per SEED-045). Section-affinity becomes one more weighted input alongside phase, problem type, and hat sequence -- not a new ranking mechanism, an additive term in the one that exists.

## 6. Risks and traps (this repo's own scar tissue)

- **Stale-plugin-cache trap.** A fix on `main` is not live until a release ships AND is actually picked up by a running session -- proven by 4 independent occurrences over 3 weeks per this navigator's own standing house rule. Nothing in this phase should be reported "done" without confirming a real release shipped and was verified live.
- **Two-graph confusion.** "Local graph" in this brief means the room's SQL-backed local graph (`room.db` / local Aura), never the Brain. Every workstream above must state explicitly which graph it touches.
- **Repo ownership must be explicit, not assumed.** The Brain graph's own content (dedup, mislabel triage, new SAPPhIRE/section nodes, the ~25 missing edges) is `ProblemsWorthSolving-Brain` repo work. The projection-cache refresh, `f-selector-ranker.cjs` changes, and any `suggest-next`/`act` reconciliation are `MindrianOS-Plugin` repo work. A phase plan that doesn't say which repo owns which step will stall at the first PR.
- **The Brain-side write paths exist and are verified live (2026-08-20, confirmed against the Render API), so execution access is NOT a blocker.** The full deployment is self-contained on Render, workspace "Jonathan's workspace" (tea-d25gpsnfte5s7385eolg): `pws-brain-mcp` (srv-d9gfa03tqb8s73csfmtg, pro plan, Docker, active, auto-deploys on commit to `github.com/jsagir/ProblemsWorthSolving-Brain` main) and `pws-brain-db` (srv-d9geq2urnols73cimkfg, the Memgraph private service itself, active, Bolt 7687 open internally, 10GB disk, SSH `srv-d9geq2urnols73cimkfg@ssh.oregon.render.com`). That second address resolves an open item directly: the 2026-08-11 handoff said the remaining index DROPs "need Bolt/SSH, no DDL seam over HTTPS" -- the SSH seam into the DB service is exactly that, and it exists. So every piece of graph surgery this milestone needs (the ~25 edges, dedup, relabel remediation, DataRoomSection nodes, curated flags) has TWO sanctioned paths: (a) commit ingestion/migration scripts to the Brain repo, which auto-deploy on push, the default for anything repeatable; (b) direct SSH/Bolt into `pws-brain-db` for surgical one-offs, always with human sign-off on the exact statements first (the 2026-02-05 relabel disaster is the standing reason no bulk mutation runs unreviewed). The plugin-side `brain_write` MCP tool being blocked by the Part 8 egress guard -- which this session hit directly -- is therefore irrelevant to execution: the milestone never needed that path, and the guard blocking it is the guard working. The old `mindrian-brain` service is confirmed suspended, closing the audit's "dead spend" finding.
- **Brain API key management is also unblocked.** Supabase (the `brain_api_keys` table that `brain-admin.cjs` reads) is reachable via the Supabase MCP plugin in this environment, so operator/admin key operations do not depend on the local `.env` that was missing earlier this session.
- **The 2026-02-05 relabel disaster is the direct cautionary precedent.** The original mislabeling this whole chain traces back to was caused by a bulk automated relabel with no human-reviewed triage list. The existing remediation plan in `.planning/debug/brain-schema-entropy-and-cooccurs-bloat.md` already gets this right: P1-2 proposes a human-reviewed candidate list before any node gets its Framework label back, explicitly rejecting a blind bulk re-add. Any Gate 0 remediation must follow that same shape -- propose, get sign-off, then execute -- not repeat the mistake it's fixing.
- **Every schema-touching PR needs Canon Custodian review.** Part 8's own PR gate: "Every PR touching mcp-server-brain/, lib/core/brain-*, or any MCP tool that queries the Brain must pass the brain-boundary-scan check and receive explicit review from a Canon Custodian before merge." This applies to the projection-cache refresh and to any new DataRoomSection/section-affinity schema, even though the shape is already canon-sanctioned.
